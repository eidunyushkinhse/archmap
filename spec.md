# ArchMap — spec.md

Описание продукта
Веб-сервис для описания многослойных программных систем
с произвольной глубиной иерархии. Альтернатива Structurizr
без ограничения в 4 слоя.

Проблема
C4-модель ограничивает описание системы четырьмя слоями.
В реальных системах компоненты содержат субкомпоненты
произвольной глубины. Structurizr это не решает.

Решение
Дерево узлов произвольной глубины. Каждый узел — либо
атомарный компонент, либо контейнер для дочерних узлов.
Архитектор сам решает, на каком уровне останавливаться.

Проекты (изоляция схем)
Пользователь работает не с одной глобальной схемой, а с несколькими изолированными
проектами. Проект — отдельная схема со своим деревом, связями и процессами; данные
проектов не пересекаются. Одна организация (без multi-tenant): проекты общие для
всех, роль глобальная.
- После входа открывается лендинг «Мои проекты» (сетка карточек: превью схемы,
  описание, дата изменения, последний редактор, счётчики объектов/связей; меню ⋯;
  табы Активные/Архив, поиск, пустые состояния).
  - Превью — РЕАЛЬНАЯ топология корневого уровня схемы (узлы-корни + связи между
    ними, спроецированные на корневых предков, как на холсте), а не декоративный
    граф. Бэкенд отдаёт мини-граф в ответе /projects батчем (без N+1). Раскладка
    превью считается ТЕМ ЖЕ движком, что и холст (ELK layered): узлы без
    сохранённых координат кладёт ELK, сохранённые позиции (ручной drag)
    перезаписывают — поэтому превью схематично отражает реальное расположение
    узлов верхнего слоя относительно друг друга (а не декоративный круг/центроид,
    которые раньше давали круг при отсутствии владеемых позиций и схлопывание в
    одну точку при единственной). ELK асинхронный (ленивый чанк) — на время
    раскладки карточка показывает каркас-заглушку; при сбое ELK фолбэк на
    центроид/окружность.
- Создание: двухпанельная модалка-витрина (открывается с лендинга и из дропдауна
  шапки, без редиректов). Слева способ старта «Пустой / Шаблон / Копия / Импорт /
  ИИ-агент», список вариантов и имя+описание; справа живое превью выбранного
  варианта.
  - Шаблоны: 6 пресетов, приближенных к практике C4 (Монолит, Веб-приложение,
    Микросервисы, Событийная, Бессерверная, CQRS) с tagline/описанием/чипами
    технологий; внешние системы сидятся с is_external (серые). Каталог отдаёт
    read-only GET /projects/templates; координаты узлов в каталоге = раскладка
    сида, поэтому превью в модалке (C4Preview: формы и палитра холста 1:1,
    подписи рёбер) совпадает с будущим холстом.
  - Копия — глубокий клон схемы с новыми id.
  - Импорт: вставка/загрузка YAML в формате «Экспорта» (start="import" +
    import_yamls, N документов; одиночный import_yaml жив для совместимости;
    зеркало build_export — имя, форма, статус, роль, технология, external,
    описание, вложенность, связи по именам либо путям «Предок / Имя»; раскладку
    не тащит — холст раскладывает авто-ELK). Документы-чипы «Файл N» в панели
    (ImportPane): загрузка нескольких файлов, удаление, вставка текста. Живая
    сводка валидации через dry-run POST /projects/import/preview (все ошибки
    списком с путём до места и префиксом «файл N», ничего не пишет в БД);
    кнопка создания требует зелёной сводки по текущим документам.
  - Мульти-YAML сливается детерминированно на бэке (merge_imports, план и
    семантика — docs/archive/plan-repo-import.md): идентичность узла = нормализованное
    имя в пределах смердженного родителя; «богатое побеждает» (заполненное бьёт
    пустое, не-дефолт бьёт дефолт), расхождения заполненных значений не решаются
    молча — первое по порядку файлов + строка в отчёт; точные дубли рёбер
    выбрасываются; fuzzy-похожие имена сиблингов из разных файлов НЕ склеиваются
    (только предупреждение «возможно, одно и то же»), как и несовпавшие корни.
    Сводка превью несёт отчёт слияния (из K файлов / склеено узлов / конфликты /
    «Проверьте» / дубли связей) и кнопку «Скопировать замечания для агента».
    ЗАМЕЧАНИЯ УНОСЯТСЯ АГЕНТУ РАЗНЫМ ТЕКСТОМ (2026-08-13, полевой QA
    docs/qa-zabbix-7.md): ошибки разбора — «исправь их»; предупреждения зелёной
    сводки — «устрани, ДОПОЛНЯЯ схему: находи недостающие связи, а НЕ удаляй
    объекты». Причина — слабая модель на «исправь» отвечает ампутацией (в двух
    раундах QA 31→27 и 30→14 узлов). Там же дифф попыток: сводка сравнивает состав
    узлов с предыдущей зелёной проверкой и над сводкой пишет, что исчезло («Стало N
    объектов (было M). Исчезли: …») — удаление объектов не проходит молча. Состав
    даёт то же превью (node_names — все узлы слитого дерева).
    Проверки СОДЕРЖАНИЯ в превью (не полагаются на аккуратность агента): люди
    внутри системы, объекты без единой связи и СВЯЗИ, УПИРАЮЩИЕСЯ В КОНТЕЙНЕР с
    компонентами — каждая названа поимённо («связь «vote → redis»: конец в
    контейнере «vote» … уточни её до конкретного компонента»), кап 10 + «…ещё N».
    Иначе это всплывает только ПОСЛЕ импорта алертом «связь в промежуточный узел»,
    когда агент уже ушёл; промпт в ремарк-протоколе говорит, что такое замечание
    лечится переносом конца связи на компонент, а не удалением связи.
  - ИИ-агент («Из репозитория», BYOA): схему строит ИИ-агент пользователя
    (Claude Code, Cursor, ...; планка качества промпта — слабая модель уровня
    DeepSeek v4 Flash). Слева параметры — глубина (2/3 слоя), язык описаний,
    подсказки агенту; имя системы = название проекта. «Скопировать промпт» →
    GET /projects/import/prompt (шаблон на бэке рядом с валидатором: процедура
    обследования репозитория, конвенции именования для авто-слияния — имена
    сервисов из деплой-конфигов, чужие сервисы заглушками, приватные БД
    «<сервис>-db», SaaS с external: true, — встроенный валидный пример, чек-лист
    самопроверки, инструкция починки по списку ошибок). Один и тот же промпт
    запускается в каждом репозитории системы; YAML-ответы вставляются в ту же
    панель импорта и сливаются. Код пользователя ArchMap не покидает периметр —
    серверная интеграция с AI-API отклонена осознанно (см. план).
    ОБНОВЛЕНИЕ ЖИВОЙ СХЕМЫ (2026-08-07): прогон агента можно накатить не только на
    новый проект, но и на существующий — иконка «Обновить из репозитория» в шапке
    (архитектор). Окно показывает ПЛАН: новые объекты, изменённые (с указанием,
    какие поля меняются и чем опознан узел), пропавшие, новые и пропавшие связи;
    неизменное — счётчиком в сводке. Раскладка, схемы логики, OpenAPI-спеки и
    бизнес-процессы синк НЕ трогает, удалений нет ни в каком режиме — пропавшее
    максимум помечается статусом «устаревший». Консервативные дефолты (проза и
    имена не перезаписываются, слой компонентов вне синка) снимаются галочками.
    Применение отправляет курсор схемы из превью: изменилась в другой сессии —
    отказ с просьбой обновить план, а не запись вслепую.
    API: POST /projects/{id}/sync/preview и /sync/apply.
    ЯКОРЬ ИСТОЧНИКА (2026-08-07): у узла есть необязательный блок source —
    объективные приметы (git-remote, путь в монорепо, образ, деплоймент, сетевое
    имя). Агент заполняет его по фактам: своим узлам — репозиторий и всё видимое,
    чужим сервисам — только сетевое имя, по которому к ним ходят. Слияние файлов
    матчит узлы сперва по якорю (поверх имени и иерархии — так склеивается сервис,
    названный «app» у себя и «payments» у соседей), потом по имени; тёзка с
    ПРОТИВОРЕЧАЩИМ якорем не склеивается (два «api» разных команд остаются
    разными). Сильнейший ключ сохраняется в узле (source_ref, только на чтение) —
    им будущая синхронизация опознает узел даже после переименования сервиса.
    MCP-СЕРВЕР (2026-08-10): всё перечисленное агент может делать НАПРЯМУЮ, без
    переноса YAML руками, — пакет mcp/ (Python, официальный MCP SDK, stdio).
    18 инструментов по задачам, а не по эндпоинтам: чтение (проекты, дерево и
    связи, карточка объекта с доками и спекой, алерты незавершённости, процессы,
    экспорт YAML), правила формата (те же промпты import/docs, что отдаёт
    интерфейс), запись пачкой парой «превью → применение» (импорт, синк, доки) и
    точечные правки объекта и связи. ГРАНИЦЫ (решения 2026-08-10): удалений НЕТ
    ни одного — снос узла уводит поддерево, связи, доки и спеки, поэтому агент
    может лишь пометить status=deprecated, а физически удалит человек кнопкой
    «Принять переход», увидев список; «текущего проекта» на сервере нет — проект
    указывают явно каждым вызовом (скрытое состояние делало бы результат
    зависимым от порядка вызовов); имя проекта не угадывается — при нескольких
    подходящих сервер отвечает ошибкой со списком, а не берёт первый похожий.
    Аутентификация — логин/пароль в mcp/.env (файл в .gitignore: конфиг клиента
    .mcp.json трекается, и пароль уехал бы в репозиторий), токен сервер добывает
    сам и перелогинивается при истечении. Запись требует роли «архитектор».
- Свитчер в шапке схемы: имя текущего проекта + дропдаун (поиск по имени, выбор,
  «+ Новый проект», «Все проекты»). Переключение перезагружает схему с корня и
  сбрасывает историю Undo/Redo.
- Архивирование — мягкое (флаг archived_at, данные целы), восстановление возвращает
  в активные. Удаление навсегда доступно только из архива и требует ввода имени
  (каскадом сносит всю схему). Управление проектами — только architect.

Роли
Архитектор: создаёт и редактирует узлы, связи,
  прикрепляет схемы логики (mermaid) и OpenAPI-спеки к узлам.

Пользователь: просматривает дерево, навигирует по уровням,
  открывает схемы логики и OpenAPI-спеку через UI.

Сущности
Project (проект — изолированная схема)
- id          UUID
- name        строка, обязательное
- description строка, опционально
- archived_at дата/время | null (null = активен; иначе — в архиве, мягкое удаление)
- created_at, updated_at («дата изменения схемы» — трогается смысловой правкой)
- created_by_id, updated_by_id  UUID → User («кто менял последним»)
- Все доменные сущности (Node, Edge, BusinessProcess) несут project_id (NOT NULL,
  каскад при удалении проекта). Данные проектов НЕ пересекаются: каждый запрос
  скоупится текущим проектом (заголовок X-Project-Id). Роль (architect/viewer)
  глобальная, проектом не меняется.

Node
- id          UUID
- project_id  UUID → Project (проект-владелец, NOT NULL)
- name        строка, обязательное
- description строка, опционально
- role        строка, свободное: "сервис", "БД", "брокер"...
- technology  строка, свободное: "Python", "Kafka"...
- parent_id   UUID | null
- shape       форма отображения (C4): service | database | broker | person
- is_external флаг «внешний узел» (на чужих уровнях рисуется «гостём»)
- status      жизненный цикл: existing (as-is, дефолт) | planned (to-be) | deprecated.
              Версионируемая семантика, не раскладка. Кодируется цветом тела узла
              (синий/зелёный/красный) + бейджем «новый»/«выводится»
- docs        коллекция именованных схем логики (node_docs): имя (уникально в
              пределах узла), вид (обзор | обработчик API-операции | фоновый
              воркер), опциональная привязка к операции спеки («METHOD /path»),
              текст (Mermaid), версия (CAS). Сервис держит много сценариев —
              обработчик на операцию + воркеры, каждый отдельной схемой.
              Прежнее одиночное поле flowchart перенесено миграцией в док
              «Логика». В graph-выдаче едет только мета (без текстов), контент
              подтягивается при открытии оверлея.
- openapi_spec текст (YAML), опционально
- created_at, updated_at
- has_children вычисляемое поле в API (есть ли дочерние узлы) — для дерева слева

Edge
- id          UUID
- label       строка, опционально (в UI поле называется «Описание»)
- technology  строка, опционально: "REST", "gRPC", "Kafka"
- source_id   UUID → Node
- target_id   UUID → Node
- created_at

Геометрия стрелок — целиком АВТОМАТИЧЕСКАЯ (2026-07-09)
Ручной слой стрелок УДАЛЁН по решению архитектора: изломы (waypoints с грипами),
реконнект концов (смена хэндла перетаскиванием), ручная фиксация хэндлов и
перетаскивание плашки подписи вдоль стрелки больше не существуют. Маршрут, сторона
стыковки и позиция плашки назначаются раскладкой (глобальный роутер + авто-плашки);
пользователь управляет стрелками опосредованно — перемещая узлы. Легаси-строки
пучков "b:<src>><tgt>" в view_layout игнорируются и вычищаются штатной чисткой
(удаление узла, «Переразложить уровень»).
(Возврат подвижных плашек пробовали 2026-07-13 (П4) и ОТКАТИЛИ по решению
пользователя — движение «вынесенных» плашек не устроило; фича заблокирована,
вернуться к идее позже. Инфраструктура легальных интервалов (labelCandidates)
и preferredT в раскладке остаётся — на будущее.)

Предсказуемые маршруты стрелок (2026-07-13): маршрут принадлежит ТОЛЬКО роутеру.
Детур-правило A12 («если подпись не влезает инлайн — изогнуть саму стрелку в объезд,
где плашке найдётся место») УДАЛЕНО: оно превращало прямые маршруты в необъяснимые
объезды (стрелка при свободном прямом коридоре шла полкой сверху/снизу) и
дестабилизировало живое превью драга. Невлезающая подпись решается leader-выноской
(плашка сбоку + пунктирный поводок). Заодно убран двойной клиренс плашек у узлов
(эрозия кандидатов дублировала Минковский-раздувание и требовала сегмент ≥ 2× ширины
плашки — подписи массово уходили в выноски): теперь инлайн садится на любой сегмент,
где плашка реально помещается; раздуваются только слитые плечи R4.

Поводок выноски и узлы (2026-07-15): поводок по возможности не ныряет под узлы
(узлы рендерятся поверх слоя рёбер — скрытый участок пунктира рвёт связь
«плашка↔стрелка» на глаз). Избегание МЯГКОЕ: пересечения поводка с узлами — компонент
ключа выбора позиции (слабее наложений самой плашки, сильнее пересечений с чужими
стрелками), поэтому чистое направление выигрывает даже более дальнее/диагональное,
а в полной тесноте нырок допустим — плашка размещается всегда.

Плашка выделенной стрелки — на переднем слое (2026-07-15): в тесноте плашки могут
вынужденно ложиться друг на друга; плашка выбранной стрелки поднимается над
соседними, чтобы читаться. Работает для обоих видов выделения: клик по стрелке
(RF-selected, реактивный z-index плашки) и панельное индиго-выделение по двойному
клику (класс lg-linked-label тем же императивным эффектом, что красит стрелку).
Поднятие — только над другими плашками (внутри слоя подписей), не над узлами.

Качество роутера (2026-07-13, после снятия детуров): в routeAll два канонических
механизма (libavoid):
 • ШТРАФ ЕЗДЫ ПО ЧУЖОЙ ЛИНИИ (shared-path penalty, 1/px): раньше коллинеарная езда
   по уже проложенному сегменту была бесплатной — маршруты седлали чужие линии на
   сотни px, складывались в необъяснимые изгибы и парковались в чужие хэндлы (вход в
   точку чужого выхода — нарушение Т4). ИСКЛЮЧЕНИЕ: ствол веера из ОБЩЕГО порта той же
   роли (out-out из одной точки, in-in в одну точку) бесплатен — крайний сегмент
   владельца у общего порта; это легитимное слияние по Т4.
 • ВТОРОЙ ПРОХОД (rip-up & re-route): первый проход последовательный (длинные первыми),
   ранние рёбра слепы к ещё не проложенным. Теперь каждое ребро перепрокладывается при
   полном знании всех остальных; новый маршрут принимается только при выигрыше больше
   гистерезисного порога (100), «чистые» рёбра (без пересечений/наложений) пропускаются.
   Это убрало «жертв порядка» (двойные пересечения там, где можно без них). Rip-up
   итерируется до фикспойнта (cap 3) — эпик «читаемые пучки» T6.
 • ПОРТОВЫЙ ШТРАФ (2026-07-15, фикс регрессии «встречные стрелки делят плечи»):
   парковка конца в порт, занятый чужим концом ПРОТИВОПОЛОЖНОЙ роли (вход в точку
   чужого выхода и наоборот), стоит PORT_CONFLICT_COST=600 прямо в A* (PortCandidate.
   penalty) и в оценке готовых ломаных (гистерезис/rip-up; конфликт делает ребро
   «грязным»). Веер одной роли (out-out/in-in в общем доке) легален и не штрафуется.
   Штраф мягкий: сосед-слот выигрывает, но при полной блокаде порт остаётся достижим
   (деградация вместо отказа). Раньше это держал только пост-хок distributeSlots — он
   умеет отказывать (латеральный сдвиг ломает соседний сегмент/упирается в тело), и
   тогда вход+выход оставались в одной точке: встречное наложение концевых плеч,
   неисправимое нуджингом (оба конца пришпилены к общему хэндлу).
 • ДОВОДКА НУДЖИНГА ПОСЛЕ T4 (2026-07-15): мини-проход «плашки → препятствия»
   перепрокладывает грязные рёбра ПОСЛЕ канальной разводки — свежий маршрут мог лечь
   коллинеарно на чужое плечо и оставался так до конца прогона. Теперь после принятия
   перепроложенных маршрутов канальный нуджинг запускается ещё раз (идемпотентен для
   уже разведённых каналов), затем плашки размещаются по финальной геометрии.
 • КЛИРЕНС КАНАЛЬНОЙ РАЗВОДКИ (2026-07-15, фикс регрессии T2 «плечо в теле узла»,
   разбор в docs/archive/plan-nudge-clearance.md): у канального нуджинга не было понятия
   клиренса (роутер держит 12, спрямление джогов 8, нуджинг — 0: только вето
   пенетрации глубже 2px), и жёсткая шкала слотов «center + j·gap» с пином
   концевого хвоста выталкивала крайнее плечо тесного коридора на грань узла и
   внутрь тела. Теперь цели канала считает VPSC: пины (концевые сегменты) держат
   оси весом ∞, клиренс-границы узлов (грань ± NUDGE_CLEAR=8) по пробегу КАЖДОЙ
   группы — стенки-псевдопины, соседи ≥ gap; в тесноте gap деградирует 14→12→10→8
   (ниже нельзя — сольются дуги мостиков JUMP_RADIUS=6); совсем не влезло — канал
   не разводится (лучше остаточное наложение, чем ложь о теле узла). Плечо, уже
   лежащее в клиренс-полосе (исторический канал на грани), выталкивается в ближний
   свободный зазор, если тот не дальше 2×gap; замурованное (вынужденная теснота
   роутера, узлы в 12px) пинится на месте — нуджинг не делает хуже. canApply
   страхует применение той же клиренс-проверкой. Прежние ветки «жёсткая шкала» и
   «лесенка сдвига шкалы» удалены как частные случаи VPSC-решения.

Живое превью стрелок во время драга узлов (v2, оптимизация 2026-07-21): стрелки
двигаются ЖЁСТКИМ СДВИГОМ из снимка старта — форма маршрута не меняется, только
трансляция. Это даёт идеально плавное движение без скачков и моргания:
 • ребро между ДВУМЯ перетаскиваемыми узлами едет ЖЁСТКО с ними (весь маршрут и
   плашка сдвигаются на дельту группы от снимка старта) — без «прилипшей середины»;
 • ребро с ОДНИМ перетаскиваемым концом тоже едет жёстким сдвигом из снимка старта
   (форма маршрута не меняется, только трансляция) + хэндлы обновляются каждый кадр
   через assignEdgeHandles (сторона входа/выхода меняется live). A* роутинг НЕ
   гоняется во время драга — он запустится на отпускании через обычный конвейер
   раскладки (computeViewLayout → buildAutoRoutes).
 • ПЛАШКИ едут с рёбрами жёстким сдвигом из снимка старта (среднее смещение концов).
   Живое размещение плашек НЕ гоняется во время драга — оно запустится на отпускании.
 • НЕ гоняется вживую: A* роутинг, канальный нуджинг, rip-up чужих рёбер, T4-мини-
   проход, сварка стволов, размещение плашек — всё это запустится на отпускании через
   конвейер; возможный доворот прячется перерисовкой drawIn.
 Раньше (до 2026-07-21) чередование A* роутинга и жёсткого сдвига давало разные формы
 стрелок → визуальные артефакты (скачки, моргание). Профилирование показало: A* роутинг
 занимает 3-9ms на кадр (80-90% времени), даже для 5 рёбер. Упрощение до жёсткого сдвига
 дало идеально плавные стрелки и максимальную производительность.
Перерисовка стрелок после ручного жеста (2026-07-09): по завершении ручного
действия, меняющего раскладку (отпускание драга узлов/группы, Undo/Redo),
стрелки, чья геометрия пересчиталась ИНАЧЕ (хэндлы/маршрут/концы/центр плашки),
не «прыгают» на новые места, а анимированно отрисовываются заново (drawIn, как
при раскрытии контейнеров) — остаточная разница превью/финала спрятана анимацией.
Новые/исчезнувшие стрелки не участвуют, prefers-reduced-motion уважается.

Мостики на пересечениях стрелок (line jumps)
Стрелка, пересекающая другую стрелку, «перепрыгивает» её маленькой полудугой —
читаемость пучка линий. Дуга появляется ТОЛЬКО на «крестике»: когда сегменты двух
РАЗНЫХ стрелок перпендикулярны и пересекаются СТРОГО внутри обоих. Если стрелки идут
вместе (исходят из одного хэндла, коллинеарны до чьего-то излома) — их совпадающие
сегменты параллельны, это не крестик, дуги нет; строгая «внутренность» отсекает и
T-стыки (конец одной лежит на линии другой), и общий хэндл, и углы. На каждом
пересечении прыгает ровно одна стрелка — ГОРИЗОНТАЛЬНАЯ (стандартная конвенция),
дуга выгибается вверх. Работает на основной схеме и на страничной схеме (секция
«Схема» страницы объекта идёт тем же level-конвейером, реестр мостиков включён)
для стрелок, рисуемых ортогональной ломаной (архитектор: обычные/кастомные/
обводы/мастер); viewer-smoothstep не затронут. Это РАСКЛАДКА (визуал) — ничего не
персистится.

Хранение раскладки (R3, единое хранилище view_layout): по строке на объект вида,
payload {x, y, expanded}. Геометрия стрелок в БД больше не хранится (ручной слой
удалён 2026-07-09); прежние строки пучков "b:<src>><tgt>" — легаси, игнорируются.
Это РАСКЛАДКА — не версионируется.

Сквозные связи
Edge может соединять узлы с разных уровней иерархии
(например, А с уровня 1 и Б1 с уровня 2, где Б1 — дочерний узел Б).

Правила отображения:
- На уровне, где оба конца — локальные узлы: связь отображается как обычно.
- На родительском уровне: сквозная связь А → Б1 проецируется как А → Б,
  где Б — ближайший предок Б1, принадлежащий этому уровню.
- На уровне, где один конец — внешний: внешний узел отображается как
  «гость» (визуально отличается), стрелка идёт от/к нему.
- У промежуточного гостя есть кнопка «Войти» (иконка «ветвь в потомка») — переход на его слой-схему
  компонентов. Узел из другой ветки дерева, поэтому путь строится заново
  (предки + сам узел), а не аппендом к текущему breadcrumb. Кнопка есть:
  • у листа-гостя, если у него есть дети (GhostNode.has_children, считается в
    _build_graph); у атомарного листа кнопки нет — проваливаться некуда;
  • у свёрнутого контейнера (предок гостя, показанный коробкой): он всегда
    промежуточный, поэтому «Войти» есть всегда — рядом с лупой «раскрыть инлайн».
    Лупа разворачивает содержимое на текущем уровне, «Войти» уводит на слой узла.
- Двойной клик по гостю открывает его детализацию в правой панели — read-only
  (гость несёт лишь имя/роль/технологию/статус/путь предков, без description/
  доков/openapi и без правок; реальный узел живёт в другой ветке). Кнопка
  «Перейти к источнику» уводит на уровень-родитель, где узел показан как локал.
- Двойной клик по узлу/связи, кроме открытия детализации в правой панели, устойчиво
  подсвечивает связанное: у узла — его инцидентные стрелки, у связи — сама стрелка и
  оба её узла (индиго-акцент glow'ом — очерчивает и линию, и наконечник; держится, пока
  объект открыт в панели). Индиго-подсветка узла ПОЛНОВЕСНАЯ (та же громкость, что у
  синего свечения обычного выделения) и ПРИОРИТЕТНЕЕ синего: пока объект открыт в
  панели, узел индиго, даже если он же выделен кликом. Так «выделение панели» и
  «выделение кликом» не конфликтуют: снятие кликового выделения (клик по холсту) не
  меняет картинку — не возникает ложного «с узла сняли, а со стрелок нет», а при
  инспекции связи её концы очевидно подсвечены наравне с линией. Двойной клик по
  ПУСТОМУ холсту сбрасывает подсветку и очищает
  правую панель (штатный зум-по-даблклику при этом отключён).
- Раскрытие ЛЮБЫХ контейнеров (R5, ядро задумки): лупа есть и у ЛОКАЛЬНОГО
  сервиса с детьми — узел раскрывается на месте в рамку со ВСЕМИ своими детьми
  (у гостей — только связанные: это и есть C4-контекст), рекурсивно, но НЕ
  глубже двух слоёв от текущего уровня (MAX_INLINE_DEPTH, container.md C8):
  контейнер на предельной глубине лупу не показывает и инлайн не раскрывается —
  глубже только «Войти» на слой узла (бережёт рендерер от глубоких рамок). Концы
  стрелок проецируются на видимых потомков; связь «прямо в
  контейнер» при его раскрытии скрывается (алерт-кейс). Дети догружаются лениво
  при первом раскрытии; при первом показе раскладываются сеткой от позиции
  контейнера и фиксируются (own-on-first-render). Раскрытие — часть состояния
  ВИДА: персистится (payload.expanded) и переживает перезаход; у наблюдателя
  (viewer) раскрытия эфемерны — смотрит без записи. Сворачивание возвращает
  узел на его сохранённую позицию.
- Анимация раскрытия/сворачивания (2026-07-09): переходы РЕЖИССИРУЮТСЯ, чтобы
  пользователь видел, откуда взялся узел и почему сдвинулся сосед. Раскрытие:
  дети спавнятся стопкой из центра свёрнутого узла и плавно разъезжаются по
  посчитанным позициям; рамка с именем родителя проявляется ПОСЛЕ разъезда;
  сдвинутые раскрытием соседи едут параллельно с детьми. Сворачивание —
  зеркально: дети съезжаются в точку будущего узла (рамка гаснет, соседи едут),
  по завершении стопка подменяется свёрнутым узлом. Стрелки, у которых движется/
  появляется хоть один конец, на время перехода честно скрываются, а по концу
  разъезда РИСУЮТСЯ анимированно от исходного хэндла к целевому (штрих
  pathLength=1 + stroke-dashoffset); наконечник и плашка с текстом появляются
  по завершении отрисовки. При большом числе стрелок отрисовка идёт КАСКАДОМ
  (Ф5 эпика плавности, 2026-07-15): волнами по 8 стрелок с шагом 60мс, короткие
  маршруты первыми — связи «расцветают» от ближних к дальним; конец фазы — по
  последней волне. Каскад за флагом DRAW_CASCADE (layoutAnimation.ts) — откат
  одной константой.
  Анимация чисто презентационная (раскладку не меняет: финал байт-в-байт равен
  рендеру после перезагрузки), уважает prefers-reduced-motion, не цепляет драг
  (transition живёт на холсте только в окно перехода). Реализация:
  useLayoutAnimation + планировщики layoutAnimation.ts + CSS lg-canvas--anim.
  Устойчивость к нагрузке (2026-07-13): отсчёт концов фаз (разъезд, отрисовка
  стрелок) ведётся от ПЕРВОГО ПОКАЗАННОГО КАДРА фазы (rAF→setTimeout), а не от
  setState — прогон раскладки по замерам, приходящий прямо в окно анимации,
  откладывает первый кадр, и wall-clock-отсчёт снимал drawIn до видимого старта
  («анимация пропадала», когда стрелок много). Сам конвейер оптимизирован без
  смены результата (индекс сегментов, скип rip-up при неизменном окружении, кэш
  сетки/проходимости A* между попытками): раскрытая сцена ~56мс/прогон против
  ~120-200 до — блок в окне анимации сжался до пары кадров.
  Плавность (эпик 2026-07-14/15, Ф1-Ф3): на окно анимации пересчёты раскладки
  ОТКЛАДЫВАЮТСЯ и досчитываются в «мёртвой зоне» конца разъезда (узлы стоят,
  стрелки ещё скрыты — drawIn рисует уже свежие маршруты); зеркальные прогоны

  главный поток в анимации занят только рендерами.
- Раскладка привязана к ВИДУ (R3): таблица view_layout(project_id, view_id,
  item_id, payload JSONB) — ЕДИНОЕ хранилище всей раскладки. item_id: id
  сущности → {x,y} (локалы, гости и свёрнутые контейнеры единообразно; один
  узел — гость на разных видах в разных местах) и {expanded} (раскрытие
  контейнера — R5). Всё это РАСКЛАДКА — не версионируется.
- Владение позицией «own-on-first-render» (рефакторинг движка, 2026-06-28): у каждой
  сущности (локала и гостя) своя АБСОЛЮТНАЯ позиция, персистимая при первом показе на
  уровне (гость засевается на кольце — см. ниже — и сразу фиксируется). Дальше узел
  двигается ТОЛЬКО ручным драгом или командой «Переразложить» — не пересчитывается за
  «живым якорем». Это убрало классы багов: драг локала не тащит связанных гостей, а
  раскрытая рамка не «убегает».
- Команда «Переразложить уровень» (кнопка в шапке, только архитектор и режим схемы):
  сброс ручного layout текущего уровня в авто — позиции в строках view_layout
  этого вида удаляются (позиции, легаси-геометрия пучков); строки с флагом раскрытия
  сохраняются: раскрытые контейнеры НЕ сворачиваются, их дети раскладываются заново.
  Видимые узлы и рамки плавно переезжают на авто-позиции (анимация). Уровень
  выглядит как при первом открытии. Скоуп строго по container_id (соседние уровни и
  узлы вне уровня нетронуты). Действие необратимо (подтверждается модалкой), историю
  Undo уровня после сброса чистим.
- СВЯЗИ, УПИРАЮЩИЕСЯ В РАМКУ. Связь можно протянуть не только между атомарными
  узлами, но и «прямо в контейнер» — это допустимо, хотя и неточно (схема не
  говорит, какая именно его часть участвует; такие связи подсвечивает алерт «связь
  в промежуточный объект»). Раньше на схеме от такой связи не оставалось ничего:
  контейнер на своём уровне заменён детьми, рисовать было не на чем, и рядом просто
  висел сосед без единой стрелки. Теперь связь ВИДНА и читается буквально: она идёт
  от узла как обычно, доходит до рамки контейнера и упирается в неё наконечником
  (или наоборот — исходит из рамки и входит в узел). Работает в трёх местах: когда
  контейнер раскрыт лупой на уровне; когда ты стоишь ВНУТРИ него (упирается в
  родную рамку уровня); и на пустом слое, где рамка рисуется всегда.
  Конец, воткнутый в рамку, можно ОТЦЕПИТЬ и прицепить к любому узлу внутри неё —
  так неточная связь уточняется до конкретного ребёнка, без удаления и пересоздания.
  Тянется только этот конец: вся остальная геометрия стрелок остаётся полностью
  автоматической. Промах мимо детей рамки отменяет жест — конец возвращается на
  рамку, связь не может остаться с одним концом. Если в рамку упирается общая
  стрелка нескольких связей, переезжают все они разом (одним шагом Undo).
- Запрет проникновения в чужую родную рамку (C4-инвариант): гость (и гостевая
  рамка раскрытого промежуточного контейнера) НИКОГДА не лежит внутри родной
  рамки уровня, в которую не входит по членству. Родные рамки = предки из
  breadcrumb, концентрически вложены; гость — член рамок до своего общего предка
  включительно, поэтому единственная «запретная» для него рамка — следующая глубже
  общего предка. При дефолтном спавне, росте родной рамки (добавили узел) и ручном
  драге гость минимально сдвигается к ближайшему краю запретной рамки + интервал;
  задвинуть его внутрь руками нельзя. Раскрытая рамка — настоящий узел канвы
  (R4, compound): дети сидят внутри в её координатах, «Свернуть» — ✕ в плашке. Это РАСКЛАДКА — авто-сдвиг не персистится (драг персистит уже
  скорректированную позицию).
- Дефолтная раскладка гостя (без ручной позиции) — boundary labeling на «кольце»
  запретной рамки: гость ставится на ПЕРИМЕТР рамки F_{memberDepth+1} (та же рамка,
  что у keep-out, + интервал) — оптимальное место кратчайшей стрелки лежит на её
  границе. Базовая ось — горизонталь (поток C4 слева-направо, ближний к связанным
  узлам край), верх/низ берётся, когда горизонталь увела бы стрелку сквозь тела
  других узлов. Гости одной стороны раздвигаются изотонически (PAV) вокруг центра
  масс. Кольца разной глубины решаются изнутри наружу (рамка растёт за уже
  размещёнными глубокими гостями), поэтому keep-out выполняется по построению, а
  его проход остаётся лишь страховкой (ручные позиции, рост рамки за ручным гостем).
- Раскладка детей раскрытой гостевой рамки (промежуточный гость «вошёл» коробкой,
  его дети видны рамкой). При ПЕРВОМ показе дети не размещаются ELK-движком, а встают
  ВНУТРЕННЕЙ ПОЛКОЙ вдоль стороны рамки, обращённой к кольцу, в порядке проекции якоря —
  центроида центров связанных локальных узлов (нет связей → центроид всех локалов).
  • Перелив в колонки: если полка по высоте не влезает в пролёт кольца, дети переливаются
    в несколько колонок (вместимость колонки = пролёт / шаг узла). Самые «тяготеющие к
    контенту» (больше связей, ближе к центру масс якорей) — во внутреннюю колонку у кольца,
    остальные выталкиваются наружу; внутри колонки порядок — по якорю.
  • Дальше — own-on-first-render, как у всех: позиция каждого ребёнка сразу фиксируется
    АБСОЛЮТОМ (строка view_layout) и меняется только ручным драгом / «Переразложить».
  • Живого следования детей за сдвигом коробки-родителя НЕТ (снято рефакторингом
    ownership 2026-06-28 вместе с остальными «живыми якорями»): позиции детей
    абсолютны с первого показа; при сворачивании коробка возвращается ровно на
    свою сохранённую позицию.
  Всё это РАСКЛАДКА (визуал), не версионируется.
- Мастер-стрелка (несколько слитых связей одного направления) — синтетическое ребро
  без своей строки в БД; её геометрию, как и всем стрелкам, назначает авто-раскладка.
- Статус жизненного цикла узла (Node.status: existing/planned/deprecated) кодируется
  цветом тела: existing — синий (прежняя C4-рампа по глубине), planned — зелёный с
  бейджем «новый», deprecated — красный с бейджем «выводится»; внешние узлы — приглушённый
  тон того же статуса. Гости красятся по своему статусу. Связь наследует статус сильнейшего
  конца (deprecated > planned > existing): deprecated — красный пунктир, planned — зелёная,
  иначе серая. Это ВЕРСИОНИРУЕМАЯ СЕМАНТИКА (как shape/is_external), не раскладка.
- Фильтр «Вид схемы» (as-is / переход / to-be) — клиентский визуальный слой поверх данных:
  as-is показывает existing+deprecated (что работает сейчас), to-be — existing+planned
  (целевая система), переход — всё (дефолт). Скрытые статусом узлы и их рёбра НЕ удаляются,
  а приглушаются (opacity) — раскладка и связи сохраняются. Вид персистится в localStorage
  (не серверное, не свойство схемы). Легенда снизу-слева (свотч + счётчик видимых узлов
  статуса) показывается только когда на уровне есть хотя бы один не-existing узел.

MVP — в объёме
✓ Дерево узлов произвольной глубины
✓ Боковая панель из сворачиваемых секций (аккордеон, каждая секция
    разворачивается/сворачивается независимо):
    - «Дерево узлов» (как в Confluence): иерархия по parent_id, ленивое
      раскрытие веток. Узлы-пользователи (shape: person) в legacy-дереве не
      показываются — оно про детализацию системы, а внутрь пользователя
      проваливаться нечего (на графе они есть); в плоском дереве страниц и
      редактора персоны стоят в общей иерархии наравне с прочими объектами;
    - «Добавить узел» (только архитектор): палитра из четырёх шаблонов-форм
      (сервис, БД, брокер, пользователь). Узел создаётся перетаскиванием
      шаблона на схему — см. ниже;
    Вся панель целиком сворачивается в узкую полосу. (Бизнес-процессы переехали
    из дерева в самостоятельный режим «Процессы» — см. ниже.)
✓ Бизнес-процессы — sequence-конструктор поверх C4. Архитектор строит диаграммы
    процессов, в которых участники = узлы C4, а сообщения нельзя нарисовать
    произвольно — только выбрать из плеч уже задокументированных связей. Так
    процессы и архитектура держатся в одной правде по построению:
    - оболочка: процессы живут в самостоятельном режиме «Процессы» (переключатель
      Объекты/Процессы в шапке со скользящей подсветкой, персист в localStorage;
      дефолт — «Объекты»), а не в
      модалке. Слева — рейл процессов (свернуть/развернуть, «+ Новый процесс», список
      с бейджами статусов и ···-меню дублировать/удалить), справа — холст выбранного
      процесса с тулбаром над диаграммой. Правка инлайн по тумблеру «Редактировать /
      Готово» (только архитектор), просмотр read-only доступен обеим ролям;
    - связь C4 — это «канал с плечами»: синхронный канал даёт два плеча — вызов
      (forward) и ответ (return); асинхронный — одно (forward, рисуется как событие).
      новая связь всегда создаётся синхронной; переключить канал в асинхронный
      можно тумблером «синхронная/асинхронная» в шапке канала в композиторе
      бизнес-процесса (поле Edge.is_synchronous; дефолт для связей без значения —
      синхронный). Это ЕДИНСТВЕННОЕ место правки типа: в C4-модалке связи тумблера
      нет — тип канала живёт только в бизнес-процессах, на схему C4 он не влияет.
      Авто-вывода по технологии нет — он зависел от текстового поля, что неочевидно;
    - два слоя: «что с чем взаимодействует» (участники + сообщения) заперто
      архитектурой; «в каком порядке / при каких условиях» (порядок, фрагменты
      alt/opt/loop/par) — свободный слой процесса. Фрагмент накидывается на ВЫБРАННЫЙ
      диапазон сообщений (выбор типа в тулбаре → протягивание по строкам), фрагментов
      может быть несколько, в т.ч. вложенных; удаление — кликом по шапке фрагмента;
    - ПОДПИСЬ ШАГА ВСЕГДА СВОЯ (решение пользователя 2026-08-11). Прежде подпись бывала
      своей ЛИБО пустой, а пустая значила «показывать то, что даёт канал» (метку связи у
      вызова, «ответ» у ответа), и выводилась при каждом чтении. На экране два таких шага
      неразличимы, а вели себя по-разному: один следовал за переименованием связи, другой
      нет — ровно тот разнобой, ради которого модель и менялась. Теперь дефолт канала
      ЗАМОРАЖИВАЕТСЯ ОДИН РАЗ, при создании шага, и дальше это обычный текст; API отдаёт
      подпись как есть и ничего не выводит. Пустая подпись означает ровно «подписи нет».
      ЦЕНА ПРИНЯТА СОЗНАТЕЛЬНО: переименование связи в схеме до процессов больше не
      доезжает — подписи правятся руками. Взамен подпись не меняется под ногами и
      переживает удаление связи (шаг остаётся повисшим, но подписанным).
      КАРТОЧКА ШАГА — клик по стрелке/подписи в режиме правки: поле подписи, «Удалить»
      слева, «Отмена»/«Сохранить». До этого клик открывал ТОЛЬКО «Удалить
      сообщение?»: задать или снять подпись из интерфейса было нечем, хотя бэк умел.
      Устройство карточки то же, что у ветви «иначе» (правка и удаление одним жестом).
      Правка обратима (undo/redo), пустое сохранение в историю не пишется.
      ⚠️ Разовая миграция заморозила то, что до сих пор выводилось на лету: иначе шаги с
      пустой подписью остались бы без текста. Обратно не отыгрывается — после заморозки
      не отличить выведенное от набранного руками;
    - ПОРЯДОК ШАГОВ меняется перетаскиванием шага вверх-вниз (2026-08-10). Ручка —
      И подпись, И САМА СТРЕЛКА (правка по приёмке: пользователь инстинктивно берётся
      за стрелку; линия тонкая, поэтому поверх неё лежит невидимая полоса захвата).
      Эта же полоса принимает КЛИК (открывает карточку шага, см. ниже): раньше
      отзывалась только подпись, а стрелка не делала ничего — одна сущность вела себя
      по-разному в зависимости от того, куда попал курсор. Клик после перетаскивания
      гасится:
      подпись идёт за курсором, остальные строки живо расступаются, отпускание пишет
      новый порядок одной транзакцией (PATCH /processes/{id}/messages/reorder, order
      0..N-1). Бэк требует ПОЛНЫЙ перечень сообщений: частичный оставил бы дубли
      позиций. Порог сдвига отделяет драг от клика — карточка шага по-прежнему
      открывается кликом. ГРАНИЦЫ ФРАГМЕНТОВ ПРИ ЭТОМ СТОЯТ НА МЕСТЕ (решение
      пользователя): фрагмент — диапазон ПОЗИЦИЙ, а не набор шагов, поэтому шаг,
      въехавший в строки блока, оказывается внутри него, а вытесненный — снаружи.
      Во время жеста это видно: блок не движется, шаги едут сквозь него;
    - ОХВАТ ФРАГМЕНТА правится протягиванием его верхней/нижней границы (2026-08-10):
      на рёбрах рамки — полосы захвата (само ребро 1.5px, курсором не попасть),
      грань метит в ближайшую строку сообщения. Во время жеста ШИРИНА рамки
      подстраивается под самую широкую стрелку НОВОГО охвата и делает это
      анимированно: ширина выводится из крайних колонок покрытых сообщений, поэтому
      меняется скачком, а без перехода читалась бы как мигание. Тянущаяся грань
      (top/height) не анимируется — она обязана идти за курсором без запаздывания.
      Грань не заходит за противоположную (диапазон минимум в строку; бэк держит то
      же правило: from_order ≤ to_order). Пишется PATCH фрагмента, откат — в undo;
    - ВЕТВИ «ИНАЧЕ» у alt авторятся там же (2026-08-10): в шапке фрагмента кнопка
      «+ иначе». Ветвей может быть СКОЛЬКО УГОДНО — ограничение «одна» было нашим и
      сидело в модели, mermaid принимает цепочку else любой длины (проверено его
      настоящим парсером). Кнопка живёт, пока под новую ветвь хватает шагов: каждая
      ветвь занимает свою строку, первая начинается с from_order (её условие — guard
      самого фрагмента, поэтому в списке ветвей её нет). По нажатию граница встаёт в
      свободном месте охвата — обычно посередине хвоста, за последней ветвью; дальше
      тянется той же механикой, что и грани рамки. Соседние ветви не перепрыгивают
      друг друга (порядок строгий), клик по чипу условия открывает правку текста и
      снятие ветви. Границы рамки ветви не проглатывают: верхняя не опускается ниже
      первой, нижняя не поднимается выше последней. Инварианты держит и бэк: ветви
      бывают только у alt, их границы строго возрастают и лежат строго внутри охвата
      (from_order < start_order ≤ to_order), а число ветвей не превышает числа шагов
      в охвате (иначе последней не досталось бы ни одного). Проверяется РЕЗУЛЬТАТ
      патча — частичная правка может сломать инвариант, не упоминая нарушенного поля;
      счётная проверка применяется только к ПРИСЛАННОМУ списку, иначе фрагмент, из-под
      которого удалили шаги, стало бы невозможно править вовсе. Ветви правятся целиком
      одним списком (как и порядок сообщений) — тогда откат возвращает набор разом;
    - ИМПОРТ ПРОЦЕССА ИЗ MERMAID (2026-08-10) — обратная операция к экспорту.
      Кнопка «Импорт из Mermaid» в рейле процессов; создаётся НОВЫЙ процесс
      (слияние с существующим — отдельная задача). Разбор живёт на бэке (как импорт
      YAML): сопоставление имён с узлами и подбор каналов требуют базы, и вторая
      реализация на клиенте разошлась бы с этой; заодно импорт достаётся API и MCP.
      ПОДДЕРЖИВАЕМОЕ ПОДМНОЖЕСТВО: participant/actor (с алиасом и без), стрелки
      ->> / -->> / -) / -> / --> / --), самосообщения, alt/opt/loop/par + else + end.
      Непонятые строки НЕ выпадают молча — уходят в отчёт превью и итога.
      ПРЕВЬЮ ничего не пишет: показывает участников с кандидатами-узлами (имя, а при
      тёзках — родитель, чем их различать), число шагов и фрагментов. Авто-сопоставление
      ТОЛЬКО при единственном кандидате: имена узлов не уникальны, выбирать за
      пользователя нельзя. ПОЛЬЗОВАТЕЛЬ НЕ ОБЯЗАН сопоставить каждого — оставленные
      без узла заводятся НЕПРИВЯЗАННЫМИ (см. ниже) и попадают в алерт AL27; сколько
      их будет, сказано до применения.
      ШАГИ встают на канал схемы только при ЕДИНСТВЕННОМ подходящем (между парой
      узлов бывает и REST, и Kafka — выбирать нельзя); остальные импортируются
      ПОВИСШИМИ и попадают в AL26. Ни один шаг сценария не теряется — иначе разъехались
      бы границы фрагментов, они держат ПОЗИЦИИ.
      ИТОГ ИМПОРТА называет внутренние операции участника (самосообщения) ОТДЕЛЬНОЙ
      графой, а не записывает их в «без связи»: канала C4 у них нет по контракту, и
      поломкой это не является (та же норма — у «Восстановить связи» и у алерта AL26).
      Считаются они по факту, а не вычитанием из общего числа шагов, иначе строка либо
      врёт, либо не сходится.
      Незакрытый фрагмент закрывается последним шагом (терять блок хуже, чем додумать
      конец), пустой — отбрасывается, ветвь на первой строке охвата — тоже: импорт не
      кладёт в базу то, что этот же бэк отвергнет при правке.
      ПОДПИСИ ИМПОРТ СОХРАНЯЕТ КАК ЕСТЬ — подпись у шага всегда своя (см. ниже),
      сверять пришедший текст не с чем. Прочерк «—», которым экспорт обозначает пустую
      подпись, читается как «подписи нет», а не как текст из тире.

      потому что чинится иначе: «Восстановить связи» ищет канал повисшему шагу, а
      здесь связь на месте — помогает возврат синхронности либо удаление шага. По
      той же причине счётчик кнопки считает ТОЛЬКО повисшие: иначе она обещала бы
      починку, которой не умеет.

      «Синхронный»/«Асинхронный» рядом с подписью. В C4-модалке связи этого признака
      НЕТ и не будет — состав плеч это вопрос процесса, а не схемы объекта. Правка
      задевает связь целиком, поэтому карточка говорит об этом прямо и предупреждает
      числом, сколько шагов-ответов сломает уход в асинхронный. Второе место правки —
      композитор нового сообщения (там же, где связь можно достроить).

      (node_id = null). Вторая ось «незадокументированности», симметричная повисшему
      сообщению: линия жизни есть, объекта архитектуры за ней нет. Два пути: импорт
      без сопоставления и УДАЛЕНИЕ УЗЛА — FK гасит ссылку (SET NULL). Прежде стоял
      CASCADE, и удаление узла молча сносило участника вместе со всеми его шагами;
      теперь процесс переживает удаление, а расхождение видно (алерт AL27).
      Рисуется «сломанным» янтарным — как повисшая стрелка; вместо формы C4 знак
      разрыва, подпись «нет узла в схеме». ПРИВЯЗКА к узлу — кнопкой на его же шапке
      (расхождение и путь исправления в одном месте). Перепривязка привязанного
      запрещена: шаги опираются на плечи каналов ЕГО узла. При привязке повисшие шаги
      участника ПОДХВАТЫВАЮТ каналы (снова — только при единственном кандидате), итог
      показывается строкой. Расхождение имён (в диаграмме одно, у узла другое)
      показывается ДО записи: после привязки действует имя узла, схема — источник
      истины, но потеря имени из диаграммы не молчаливая.

      двое таких были бы неразличимы. Отсюда граница слоёв: C4 (каналы, плечи,
      направления) говорит узлами, слой процесса — участниками.

      участник убирается сразу, без подтверждения;

      полем order (PATCH .../participants/reorder), операция обратима (Undo/Redo);

      не даёт нарисовать фантом, а ведёт «Добавить связь в схему». Легальность

      чип «связь удалена», пунктир);
    - статусы в бизнес-процессах: на sequence-диаграмме ЦВЕТ = статус узла
      (единообразно с C4), а ТИП плеча — это ФОРМА (линия + наконечник), не цвет.

      открытый. Шапки/линии жизни/активации planned и deprecated тонируются по статусу,
      шапка несёт бейдж «новый»/«выводится»; existing — без изменений. Переключатель

      вне вида (opacity, мгновенно, без удаления); подсказка вида — плашкой над канвой.
      Вид персистится в localStorage тем же ключом, что и на C4-схеме (общая привычка

✓ Отмена и повтор перемещений (Undo/Redo, архитектор). Ctrl/⌘+Z отменяет, Ctrl/⌘+
    Shift+Z или Ctrl/⌘+Y повторяет. Поскольку правки персистятся в Postgres сразу,
    отмена — это компенсирующий вызов API, а не откат фронт-стейта; визуально
    мгновенно (зеркало в локальный стейт), сеть фоном. Итерация 1 покрывает все
    ПЕРЕМЕЩЕНИЯ: позиции узлов/гостей/контейнеров (вся перетянутая группа = один
    шаг). Ручной слой стрелок удалён (2026-07-09) — команды изломов/плашки/хэндла
    больше не создаются. История — до 50
    шагов, в памяти вкладки, СКВОЗНАЯ по уровням: если откатываемая правка сделана на
    другом уровне, Undo/Redo сначала РЕДИРЕКТИТ пользователя на этот уровень, затем
    выполняет откат. Undo/Redo доступны и горячими клавишами, и кнопками тулбара на
    холсте. Итерация 2 добавляет отмену УДАЛЕНИЙ: перед каскадным удалением клиент
    снимает снимок поддерева (узлы + рёбра + строки раскладки), а Undo восстанавливает
    его на сервере с СОХРАНЕНИЕМ исходных id (POST /nodes/restore), Redo — повторное
    удаление. Структурное восстановление требует серверной проекции гостей/рёбер,
    поэтому undo/redo удаления перечитывают уровень (а не зеркалят в стейт, как
    перемещения). Итерация 3 добавляет отмену СОЗДАНИЙ и ПРАВОК ПОЛЕЙ узлов и связей:
    снимок+restore стал универсальным примитивом структурного отката (создание/удаление
    и узлов, и связей — с сохранением исходных id; у связей свой снимок
    GET /edges/{id}/deletion-snapshot), а правка полей откатывается простым возвратом
    прежних значений (update). Покрыты все жесты создания связи и правка её концов
    (undo возвращает концы). Группировка одного жеста (мультидраг) сворачивается
    в одну команду, а компенсирующие вызовы

    вательские конфликты разруливаются optimistic CAS + поллингом (этапы 0+1 —
    в продукте, см. «Совместная работа: конкурентные сессии»); realtime (этап 2) —
    за пределами MVP.

Версионирование документации (планируется, см. tasks.md → бэклог)
Документация (узлы и связи) поддерживается в версионируемом состоянии.
- Версионируется только СЕМАНТИКА. Версионируемые поля:
    узел — name, description, role, technology, parent_id, openapi_spec,
           shape, is_external + доки логики узла (node_docs);
    связь — label, technology, source_id, target_id.
  Поля раскладки (pos_x/pos_y, source_handle/target_handle) НЕ версионируются —
  перемещение узлов в версию не попадает.
- Публикация ПАЧКОЙ. «Пачка» = семантический diff между живым состоянием и
  последней опубликованной версией; кнопка «Опубликовать» проводит черту (как
  git commit). Отдельный «принцип формирования пачки» не задаётся.
- Автор и время фиксируются на уровне версии целиком (без аудита отдельных
  действий внутри пачки).
- Возможности: история версий, состояние на версии N, diff(A, B) с подсветкой
  added/removed/modified (узлы и связи + изменённые поля), откат к версии
  (forward-revert — история не стирается).
- Конкурентность (несколько редакторов): оптимистичная блокировка по версии
  сущности — устаревшая правка отклоняется с конфликтом.
- Хранилище — PostgreSQL (НЕ Git). Git рассматривался и отклонён: при
  многопользовательской записи даёт конфликты слияния. Возможный задел на потом —
  экспорт опубликованных версий в Git как витрина/ревью, не как БД.

Совместная работа: конкурентные сессии (этапы 0+1 — в продукте, план
docs/archive/plan-concurrency.md; realtime-этап 2 — за пределами MVP)
Один проект могут открывать несколько сессий (вкладок/пользователей); пишут
только архитекторы. Защита от конфликтов строится в два этапа:
- Этап 0 — защита от молчаливой потери (optimistic CAS). У вида есть версия:
  батч раскладки с устаревшей версией отклоняется (409) и переигрывается поверх
  свежего состояния — прямое действие пользователя (драг/undo/раскрытие)
  доносится, производные сдвиги конвейера выбрасываются и пересчитываются от
  свежего мира. Смысловые правки узла/связи (включая тексты OpenAPI и схем
  логики node_docs — у каждой схемы своя версия)
  защищены версией сущности: устаревшее сохранение отклоняется с явным
  сообщением вместо тихой перезаписи чужой работы. Запись раскладки в удалённый
  вид — 404 (не 500).
- Этап 1 — взаимная видимость. Клиент раз в 10 секунд и при возврате фокуса
  сверяет курсоры изменений проекта и перечитывает данные, если их изменил
  кто-то другой (не посреди жеста и не под открытой модалкой); свои записи
  чужими не считаются (echo-suppression: свои записи обновляют курсор из
  ответов, страница дополнительно сверяет содержимое). Два курсора: graph_rev —
  схема (узлы/рёбра/раскладка) → тост «Схема обновлена в другой сессии» на
  схеме; meta_rev — мета узла (атрибуты/доки/openapi) → тост «Данные обновлены
  в другой сессии» на странице объекта. Наблюдатель получает живые обновления
  наравне с архитектором.
Принцип: интент пользователя переживает ребейз, интент конвейера — нет.
