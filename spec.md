# ArchMap — spec.md

Описание продукта
Веб-сервис для описания многослойных программных систем
с произвольной глубиной иерархии. Альтернатива Structurizr
без ограничения в 4 слоя.

Проблема
C4-модель ограничивает описание системы четырьмя слоями.
В реальных системах компоненты содержат субкомпоненты
произвольной глубины. Structurizr это не решает.

Решение
Дерево узлов произвольной глубины. Каждый узел — либо
атомарный компонент, либо контейнер для дочерних узлов.
Архитектор сам решает, на каком уровне останавливаться.

Проекты (изоляция схем)
Пользователь работает не с одной глобальной схемой, а с несколькими изолированными
проектами. Проект — отдельная схема со своим деревом, связями и процессами; данные
проектов не пересекаются. Одна организация (без multi-tenant); доступ к проекту —
по его участникам (см. «Доступ к проектам» ниже).
- После входа открывается лендинг «Мои проекты» (сетка карточек: превью схемы,
  описание, дата изменения, последний редактор, счётчики объектов/связей; меню ⋯;
  табы Активные/Архив, поиск, пустые состояния).
  - Превью — РЕАЛЬНАЯ топология корневого уровня схемы (узлы-корни + связи между
    ними, спроецированные на корневых предков, как на холсте), а не декоративный
    граф. Бэкенд отдаёт мини-граф в ответе /projects батчем (без N+1). Раскладка
    превью считается ТЕМ ЖЕ движком, что и холст (ELK layered): узлы без
    сохранённых координат кладёт ELK, сохранённые позиции (ручной drag)
    перезаписывают — поэтому превью схематично отражает реальное расположение
    узлов верхнего слоя относительно друг друга (а не декоративный круг/центроид,
    которые раньше давали круг при отсутствии владеемых позиций и схлопывание в
    одну точку при единственной). ELK асинхронный (ленивый чанк) — на время
    раскладки карточка показывает каркас-заглушку; при сбое ELK фолбэк на
    центроид/окружность.
- Пустой проект (0 объектов): на странице проекта окно схемы показывает «Схема
  пуста», а архитектору — кнопку «Начать наполнение», ведущую в редактор-карту;
  кнопки «Редактировать» над пустой схемой нет, её место занимает новая (решение
  2026-09-05; прежняя «+ Объект» не делала ничего). Наблюдателю — только
  «Схема пуста».
- Создание: двухпанельная модалка (открывается с лендинга и из дропдауна шапки,
  без редиректов). Слева способ старта «Пустой / Копия / Импорт / ИИ-агент»
  (сеткой 2×2, по умолчанию «Пустой»), список вариантов и имя+описание; справа
  превью выбранного варианта.
  - Демо-пакет «Маркетплейс «Ярмарка»» (template_packages/demo-marketplace/,
    сидер app/demo_package.py) сохранён для будущего онбординга.
  - Копия — глубокий клон схемы с новыми id.
  - Импорт: вставка/загрузка YAML в формате «Экспорта» и полных архивов .zip —
    ЕДИНЫМ путём (multipart, см. «ЕДИНЫЙ ИМПОРТ ПРОЕКТА»; старый ввоз списком
    текстов — start="import" и POST /projects/import/preview — снесён
    2026-09-05, потребителей не осталось). YAML — зеркало build_export: имя,
    форма, элемент архитектуры (element, только заданный), статус, роль, технология,
    external, описание, вложенность, связи по
    именам либо путям «Предок / Имя»; раскладку не тащит — холст раскладывает
    авто-ELK. Входы-чипы в панели (ImportPane): загрузка нескольких файлов,
    удаление, вставка текста. Живая сводка валидации через dry-run
    POST /projects/import/unified-preview (все ошибки списком с путём до места
    и адресом «вход N», ничего не пишет в БД); кнопка создания требует зелёной
    сводки по текущим входам.
  - Мульти-YAML сливается детерминированно на бэке (merge_imports, план и
    семантика — docs/archive/plan-repo-import.md): идентичность узла = нормализованное
    имя в пределах смердженного родителя; «богатое побеждает» (заполненное бьёт
    пустое, не-дефолт бьёт дефолт), расхождения заполненных значений не решаются
    молча — первое по порядку файлов + строка в отчёт; точные дубли рёбер
    выбрасываются; fuzzy-похожие имена сиблингов из разных файлов НЕ склеиваются
    (только предупреждение «возможно, одно и то же»), как и несовпавшие корни.
    Сводка превью несёт отчёт слияния (из K файлов / склеено узлов / конфликты /
    «Проверьте» / дубли связей) и кнопку «Скопировать замечания для агента».
    ЗАМЕЧАНИЯ УНОСЯТСЯ АГЕНТУ РАЗНЫМ ТЕКСТОМ (2026-08-13, полевой QA
    docs/qa-zabbix-7.md): ошибки разбора — «исправь их»; предупреждения зелёной
    сводки — «устрани, ДОПОЛНЯЯ схему: находи недостающие связи, а НЕ удаляй
    объекты». Причина — слабая модель на «исправь» отвечает ампутацией (в двух
    раундах QA 31→27 и 30→14 узлов). Там же дифф попыток: сводка сравнивает состав
    узлов с предыдущей зелёной проверкой и над сводкой пишет, что исчезло («Стало N
    объектов (было M). Исчезли: …») — удаление объектов не проходит молча. Состав
    даёт то же превью (node_names — все узлы слитого дерева).
    Проверки СОДЕРЖАНИЯ в превью (не полагаются на аккуратность агента): люди
    внутри системы, объекты без единой связи, ИЗОЛИРОВАННЫЕ ГРУППЫ (связаны между
    собой, оторваны от ядра — «группа из 2 объектов не связана с остальной схемой:
    «Оператор», «Admin UI»»; связность считается ровно как у одноимённого алерта:
    рёбра связывают, иерархия — нет, крупнейшую группу не называем) и СВЯЗИ,
    УПИРАЮЩИЕСЯ В КОНТЕЙНЕР с компонентами — каждая названа поимённо («связь
    «vote → redis»: конец в контейнере «vote» … уточни её до конкретного
    компонента»), кап 10 + «…ещё N».
    Иначе это всплывает только ПОСЛЕ импорта алертом «связь в промежуточный узел»,
    когда агент уже ушёл; промпт в ремарк-протоколе говорит, что такое замечание
    лечится переносом конца связи на компонент, а не удалением связи.
  - ИИ-агент («Из репозитория», BYOA): схему строит ИИ-агент пользователя
    (Claude Code, Cursor, ...; планка качества промпта — слабая модель уровня
    DeepSeek v4 Flash). Слева параметры — язык описаний, подсказки агенту;
    имя системы = название проекта. Чекбокс «Проект объединяет несколько
    продуктов» и федеративный вариант промпта (тюнинг федерации, П1: раздел
    «свой продукт — контейнером, соседи — заглушками» и перестроенный пример)
    СНЯТЫ 2026-09-06: федерация — те же одиночные прогоны универсальным промптом
    в каждом репозитории и мердж результатов (docs/plan-byoa-quality.md,
    поправка пользователя).
    Промпт также несёт три безусловных правила профилактики конфабуляций
    (П13): каждая шина — отдельный узел-брокер; хранилище/поисковый движок —
    только с основанием в коде или конфиге деплоя; technology — из манифестов,
    не по роли. «Скопировать промпт» →
    GET /projects/import/prompt (шаблон на бэке рядом с валидатором: процедура
    обследования репозитория, конвенции именования для авто-слияния — имена
    сервисов из деплой-конфигов, чужие сервисы заглушками, приватные БД
    «<сервис>-db», SaaS с external: true, — встроенный валидный пример, чек-лист
    самопроверки, инструкция починки по списку ошибок). Один и тот же промпт
    запускается в каждом репозитории системы; YAML-ответы вставляются в ту же
    панель импорта и сливаются. Код пользователя ArchMap не покидает периметр —
    серверная интеграция с AI-API отклонена осознанно (см. план).
    ЗАМЕЧАНИЯ ПРЕВЬЮ — ПОФАЙЛОВО (2026-08-15): превью раскладывает замечания в
    file_remarks[i] («для агента этого репозитория») и schema_errors/
    schema_warnings («для пользователя» — рассудить два репозитория может
    только видящий оба). АДРЕСАЦИЯ — ПО ПРОИСХОЖДЕНИЮ ВИНОВНЫХ СУЩНОСТЕЙ, а не
    по классу замечания (Ф7): есть файл, внёсший вклад в КАЖДУЮ виновную
    сущность (узлы — по sources слияния, связь — по первоисточнику), —
    замечание этому файлу (при нескольких кандидатах — наименьшему: слияние
    всюду решает в пользу первого файла, его правка и доедет); нет общего
    файла — схемной корзине. Следствия: изолированная группа целиком из одного
    файла адресуется его агенту при ЛЮБОМ составе панели (остров, погашенный
    соседним файлом, не показывается никому — подсистема вправе быть связанной
    с миром через чужой репозиторий); группа из узлов разных файлов — схемная;
    СВЯЗЬ В СОБСТВЕННОГО ПОТОМКА (вторая итерация, К4): связь, у которой один
    конец — потомок другого (любой глубины, направление любое), — свой класс и
    в превью, и в алертах (AL32, секция «Связи с собственной частью»):
    «иерархия уже выражает вложенность — удалите связь или перевесьте её».
    Прочие советы на такой связи гасятся (ни «уточните до компонента», ни
    «допишите канал» — совет на связь ровно один), паритет превью и алерта
    закреплён тестом-зеркалом;
    КОНТЕЙНЕРНЫЕ КОНЦЫ (тюнинг федерации, П5): замечание «уточните до
    конкретного компонента» несёт ПЕРЕЧЕНЬ реальных компонентов контейнера
    («server / poller», «server / trapper», … кап 6 имён, при двух концах — по
    4 на конец, хвост «и ещё N») и ВСЕГДА адресуется файлу-первоисточнику
    связи — со вложенным перечнем знание чужих компонентов агенту не нужно
    (урок «цель с ответом» в четвёртый раз; прежний схемный вариант «агент
    файла 1 их не видит» вытеснен); списки «объектов без единой связи»
    генерятся ПО-ФАЙЛОВО (строка на файл-владельца — его агенту; сироты-склейки
    без общего файла — схемной корзине);
    конфликты слияния, похожие имена/рёбра, warn_roots и лимиты — всегда
    схемные (виновны ≥2 файлов по построению). КОНФЛИКТЫ СКЛЕЙКИ (тюнинг, П2):
    при споре поля «заглушка против содержательного вклада» побеждает
    СОДЕРЖАТЕЛЬНЫЙ независимо от порядка файлов (содержательность вклада = есть
    children ЛИБО source.repo; external заглушки не заражает настоящий узел);
    «первый побеждает» остаётся для вкладов равной содержательности. МАТЧ ПО ИСТОЧНИКУ (тюнинг П3 → вторая итерация К3): решает СИЛЬНЕЙШИЙ ОБЩИЙ тип ключа
    (git > img > k8s > host — общий предикат identity.compare_identity, тот же,
    что у синка): совпадение слабого поля гасит спор сильного только тогда,
    когда у одной из сторон сильного поля НЕТ (заглушка соседа с единственным
    host склеивается с продуктом — так федерация и собирается), а два узла,
    каждый со своим repo, остаются разными даже на общем host (полевая ложная
    склейка «плагин × ядро Grafana» — закрыта). Отдельного «мягкого режима» у
    мерджа НЕТ: попытка завести его в первой итерации ту склейку и породила.
    Итог стабилизируется пост-шагом «вклад-свидетель» (одноимённые узлы одного
    родителя объединяются, если есть пара вкладов с источниками по обе стороны и НИ
    ОДНА пара не противоречит — иначе заглушка работает мостом и отменяет
    правило транзитивно) до неподвижной точки: СОСТАВ УЗЛОВ НЕ ЗАВИСИТ ОТ
    ПОРЯДКА ФАЙЛОВ (без пост-шага 4 порядка из 6 расщепляли продукт);
    настоящие тёзки — раздельны по-прежнему. ИНВАРИАНТ: добавление файла, не
    трогающего виновные сущности, не меняет ни текст, ни адресата замечания;
    перестановка файлов меняет номер, но не адресацию. При ОДНОМ файле всё
    уходит его агенту как следствие правила (не спецкод) — поведение прежнее. В мульти-режиме панель показывает замечания АКТИВНОГО чипа со
    своей кнопкой «Скопировать замечания для агента» (интро говорит «один из
    нескольких файлов системы — выведи весь СВОЙ документ»), секция «Замечания
    к слитой схеме» идёт без кнопки с подписью «чинят там, где виден весь
    ландшафт»; чипы несут настоящие имена файлов при загрузке с диска
    («2 · billing.yaml»), нумерация совпадает с «(файл N)» в текстах. Плоские
    errors/warnings/conflicts контракта сохранены байт-в-байт (их читает MCP).
    После «Скопировать замечания» — конфирм про устаревание файла в панели
    (в мульти-режиме убирает только активный файл); повторная проверка
    байт-в-байт того же входа поднимает гвард «содержимое не изменилось —
    агент мог отчитаться об исправлении, не внеся его» (полевой урок: слабая
    модель отчитывается о починке без правки файла).
    ОБНОВЛЕНИЕ ЖИВОЙ СХЕМЫ (2026-08-07): прогон агента можно накатить не только на
    новый проект, но и на существующий — иконка «Обновить из репозитория» в шапке
    (архитектор). Окно показывает ПЛАН: новые объекты, изменённые (с указанием,
    какие поля меняются и чем опознан узел), пропавшие, новые, изменённые и пропавшие
    связи; неизменное — счётчиком в сводке. СВЯЗИ (2026-10-28, по репорту с рабочего
    проекта): канал брокера и тип канала новой связи переносятся из прогона, как при
    импорте (до того терялись — связи с брокером приезжали без канала, AL31). Связь
    прогона опознаётся среди живых связей той же пары концов, внутри пары — по каналу
    (одна пара ходит по нескольким топикам — по связи на канал), а не по подписи:
    подпись дрейфует от прогона к прогону. Живая связь без канала подбирается по паре
    и подписи и получает канал действием «изменённая связь» (строка «канал ← topic.a»,
    «тип ← асинхронный») — так повторный синк тех же файлов лечит проект, заполненный
    синком до починки. Заполненный канал не перезаписывается: другой канал в прогоне —
    новая связь, прежняя показана пропавшей; пропавшей считается каждая связь пары.
    Раскладка, схемы логики, OpenAPI-спеки и
    бизнес-процессы синк НЕ трогает, удалений нет ни в каком режиме — пропавшее
    максимум помечается статусом «устаревший». Консервативные дефолты (проза и
    имена не перезаписываются, компоненты контейнеров вне синка — с 2026-10-30 по
    элементу архитектуры, см. «Элемент архитектуры») снимаются галочками.
    Применение отправляет курсор схемы из превью: изменилась в другой сессии —
    отказ с просьбой обновить план, а не запись вслепую.
    API: POST /projects/{id}/sync/preview и /sync/apply.
    ИСТОЧНИК ОБЪЕКТА (до 2026-10-17 — «якорь»; 2026-08-07; два вида и управляемость — 2026-09-04,
    docs/plan-anchor-ux.md): у узла есть необязательный блок source. ВИДОВ ДВА и
    они взаимоисключающи — КОД (repo + path внутри него) у объектов, чей код лежит
    в продукте, и ИМЯ ЗАВИСИМОСТИ (host) — как продукт САМ называет базу, брокер
    или соседний продукт в своих манифестах и дефолтах. Источник описывает ПРОДУКТ, а
    не КОНТУР РАЗВЁРТЫВАНИЯ (как и конфигурация: значений сред не храним), поэтому
    образ контейнера и объект Kubernetes источниками не являются, а localhost и адреса
    конкретных серверов источником не становятся. Агент заполняет блок по фактам: своим
    узлам — репозиторий и путь, чужим сервисам и приватной инфраструктуре — только
    имя, по которому к ним ходят. Слияние файлов матчит узлы сперва по источнику (поверх
    имени и иерархии — так склеивается сервис, названный «app» у себя и «payments» у
    соседей), потом по имени; тёзка с ПРОТИВОРЕЧАЩИМ источником не склеивается (два «api»
    разных команд остаются разными). Сильнейший ключ сохраняется в узле (source_ref),
    им синхронизация опознаёт узел даже после переименования сервиса. Источник ВИДЕН И
    УПРАВЛЯЕМ: ответ узла несёт и ключ, и его разбор (source {repo, path, host}), а
    PATCH узла с блоком source задаёт и чистит источник — ручной узел перестал быть

Пользователи и администратор (2026-09-30, docs/tasks/admin-users.md)
Мотив — развёртывание в закрытом контуре без интернета, где учётки не должны
заводиться открытой регистрацией. Всё в основном коде, режимы — настройками.
- Администратор — отдельный ПРИЗНАК пользователя (is_admin) поверх роли, и у него
  полные права (решение владельца 2026-10-18, «чтобы не путаться»): администратор
  всегда architect. Выдача прав поднимает роль до «Архитектора»; понизить
  администратора нельзя, пока он администратор (409), — «снять админа и понизить»
  можно одним действием; новый администратор заводится архитектором. На экране
  «Пользователи» выбор роли у администратора закрыт, в окне «Новый пользователь»
  галочка «Администратор» подставляет «Архитектора»; в меню профиля у него подпись
  «Администратор» без роли. Данные приводит миграция c5f9f33cbf72.
- Первый администратор — командой на сервере:
  python -m app.admin create-admin <логин> [--reset-password] (роли у команды нет:
  администратор всегда архитектор).
  Пароль вводится в консоли дважды. Существующего пользователя команда делает
  администратором и снимает блокировку, пароль не трогает без --reset-password.
- Самостоятельной регистрации нет (2026-10-18): эндпоинт /auth/register и настройка
  ALLOW_SIGNUP удалены — открытая регистрация позволяла самому выбрать роль architect.
  Учётки появляются только командой create-admin и на экране «Пользователи».
  GET /auth/config (без авторизации) отдаёт {demo_mode, demo_limits}.
- Перебор паролей: попытки входа с одного адреса ограничены на краю установки —
  nginx на сервере, само приложение в контейнере (app/standalone.py, считаются только
  неудачные, LOGIN_ATTEMPTS_PER_MINUTE). Отказ — 429 «Слишком много попыток входа.
  Подождите минуту и попробуйте снова.», форма входа показывает этот текст.
- Экран «Пользователи» (#/admin/users, пункт меню профиля, виден только
  администратору): таблица (логин, роль, администратор, статус, дата создания),
  «Новый пользователь» (логин, роль, признак администратора, временный пароль,
  который администратор передаёт человеку сам: почты нет), у каждого — смена
  роли, выдать или снять администратора, сбросить пароль, заблокировать или
  разблокировать. Блокировка и снятие администратора — с подтверждением.
- «Сменить пароль» — пункт меню профиля у всех: текущий, новый, повтор.
  Пароль — не короче 8 символов, других правил сложности нет.
- Меню профиля — того же вида, что «Действия со схемой» и ⋯ карточки проекта: сверху
  роль (у администратора — «Администратор») приглушённой подписью, пункты словами без иконок, «Выйти» —
  обычным пунктом за разделителем.
- «Токены для MCP» — пункт меню профиля у всех (не у гостя демо): свои личные
  токены (название, начало токена, «только чтение», когда использовался, срок),
  выпуск (название — по умолчанию свободное «Агент», «Агент 2»…; срок 30 дней /
  90 дней / год / бессрочно, по умолчанию 90; «Только чтение») и отзыв через
  подтверждение. У «Пользователя» (глобальная роль viewer) любой токен — только для
  чтения: галочка включена и закрыта, бэкенд не выпускает другого (403) и прежние
  токены (выпущенные до понижения роли) пускает только на чтение. Токен показывается
  один раз — сразу после выпуска («Токен будет показан только один раз. Скопируйте
  его сейчас.»), с подключением вкладками «CLI» и «Desktop», без привязки к клиенту:
  CLI — `<cli> mcp add --transport http archmap … --header "Authorization: Bearer …"`
  (общий синтаксис Claude Code, Qwen Code, Gemini CLI и других; `<cli>` — заглушка
  имени программы), Desktop — блок `mcpServers` с `url` и `headers` для mcp.json;
  адрес — origin страницы + /mcp. Потом в списке только начало. Подробности —
  «MCP-сервер» выше.
- Блокировка вместо удаления (в проектах живут created_by/updated_by):
  заблокированный не входит (401 «Учётная запись заблокирована»), его уже выданный
  токен перестаёт работать сразу — флаг сверяется с БД на каждом запросе; фронт
  при таком ответе выходит на экран входа с этим текстом.
- Страница входа (2026-10-02, docs/tasks/login-page.md): слева заголовок
  «Документация, понятная вам и вашим агентам» и анимированное превью схемы
  (система «Сервис заказов» раз в 3 секунды раскрывается в рамку с её контейнерами и
  сворачивается; при prefers-reduced-motion — статичный раскрытый кадр), справа
  форма «Логин / Пароль» с кнопкой показа пароля. Ошибка входа — красная плашка,
  причина выхода (блокировка) — жёлтая. Регистрации и «Забыли пароль?» на ней нет:
  «Нет учётной записи? Попросите администратора её завести.» Уже 820px — только форма.
- Роль и признак администратора берутся из БД на каждом запросе: смена роли
  действует со следующего запроса. Фронт читает их из GET /auth/me при старте
  приложения (роль в JWT — лишь запасное значение до ответа).
- Токен входа — осознанные границы (аудит 2026-10, M6). JWT живёт 7 дней
  (ACCESS_TOKEN_EXPIRE_MINUTES), продления нет — по истечении вход заново. Списка
  отозванных токенов нет: «Выйти» забывает токен в браузере, сам токен действует до
  срока. Смена и сброс пароля (2026-10-18) закрывают ВСЕ прежние входы: в токене
  номер поколения сессий (claim sv = users.session_version, токен без него — поколение
  0), смена или сброс растит номер, и токен со старым отбивается 401 «Пароль изменён.
  Войдите с новым паролем.» (фронт показывает этот текст на экране входа). Сессия,
  сменившая пароль сама, получает новый токен в ответе POST /auth/password и
  продолжает работу; запрос, ушедший со старым токеном, пока его меняли, выхода не
  вызывает. Сброс командой create-admin --reset-password закрывает входы так же.
  Личные токены для MCP от поколения не зависят. Записи на каждый запрос нет: номер
  сверяется со строкой пользователя, которая и так читается. Мгновенный выключатель
  без смены пароля — блокировка (is_active сверяется на каждом запросе); обезвредить
  разом все токены — сменить SECRET_KEY (разлогинит всех).
- Защиты от потери управления: нельзя заблокировать себя и снять права с себя,
  нельзя заблокировать или снять права с последнего активного администратора
  (подсчёт под блокировкой строк — два админа не разжалуют друг друга разом).
  На экране эти кнопки отключены с подсказкой почему.
- Вне скоупа: SSO/LDAP, журнал действий, разграничение проектов по
  пользователям, почта, удаление пользователей, принудительная смена временного
  пароля при первом входе.

Сущности
Project (проект — изолированная схема)
- id          UUID
- name        строка, обязательное
- description строка, опционально
- archived_at дата/время | null (null = активен; иначе — в архиве, мягкое удаление)
- created_at, updated_at («дата изменения схемы» — трогается смысловой правкой)
- created_by_id, updated_by_id  UUID → User («кто менял последним»)
- Все доменные сущности (Node, Edge, BusinessProcess) несут project_id (NOT NULL,
  каскад при удалении проекта). Данные проектов НЕ пересекаются: каждый запрос
  скоупится текущим проектом (заголовок X-Project-Id). Роль (architect/viewer)
  глобальная, проектом не меняется; viewer в проектах бывает только читателем.

Node
- id          UUID
- project_id  UUID → Project (проект-владелец, NOT NULL)
- name        строка, обязательное
- description строка, опционально
- role        строка, свободное: "сервис", "БД", "брокер"...
- technology  строка, свободное: "Python", "Kafka"...
- parent_id   UUID | null
- shape       форма отображения (C4): service | database | broker | person
- is_external флаг «внешний узел» (на чужих уровнях рисуется «гостём»)
- status      жизненный цикл: existing (as-is, дефолт) | planned (to-be) | deprecated.
              Версионируемая семантика, не раскладка. Кодируется цветом тела узла
              (синий/зелёный/красный) + бейджем «новый»/«выводится»
- docs        коллекция именованных схем логики (node_docs): имя (уникально в
              пределах узла), вид (операция | воркер — оба точки входа: сценарий,
              запускаемый извне, и фоновая работа), опциональная привязка к
              операции спеки («METHOD /path»),
              текст (Mermaid), версия (CAS). Сервис держит много сценариев —
              обработчик на операцию + воркеры, каждый отдельной схемой.
              Прежнее одиночное поле flowchart перенесено миграцией в док
              «Логика». В graph-выдаче едет только мета (без текстов), контент
              подтягивается при открытии оверлея.
- openapi_spec текст (YAML), опционально
- created_at, updated_at
- has_children вычисляемое поле в API (есть ли дочерние узлы) — для дерева слева
- element     элемент архитектуры: system | container | null (null — «не сказано»:
              узел с детьми читается системой, как до эпика). Задаётся только у
              сервиса; у листа хранится как намерение (см. «Элемент архитектуры»)
- element_effective вычисляемое поле в API: system | container | component, у
              «Пользователя» null. Внутри контейнера все объекты — компоненты, лист
              вне контейнера — сам контейнер, узел с детьми — система, если не сказано
              «контейнер»

Edge
- id          UUID
- label       строка, опционально (в UI поле называется «Описание»)
- technology  строка, опционально: "REST", "gRPC", "Kafka"
- source_id   UUID → Node
- target_id   UUID → Node
- created_at

Геометрия стрелок — целиком АВТОМАТИЧЕСКАЯ (2026-07-09)
Ручной слой стрелок УДАЛЁН по решению архитектора: изломы (waypoints с грипами),
реконнект концов (смена хэндла перетаскиванием), ручная фиксация хэндлов и
перетаскивание плашки подписи вдоль стрелки больше не существуют. Маршрут, сторона
стыковки и позиция плашки назначаются раскладкой (глобальный роутер + авто-плашки);
пользователь управляет стрелками опосредованно — перемещая узлы. Легаси-строки
пучков "b:<src>><tgt>" в view_layout игнорируются и вычищаются штатной чисткой
(удаление узла, «Переразложить уровень»).
(Возврат подвижных плашек пробовали 2026-07-13 (П4) и ОТКАТИЛИ по решению
пользователя — движение «вынесенных» плашек не устроило; фича заблокирована,
вернуться к идее позже. Инфраструктура легальных интервалов (labelCandidates)
и preferredT в раскладке остаётся — на будущее.)

Предсказуемые маршруты стрелок (2026-07-13): маршрут принадлежит ТОЛЬКО роутеру.
Детур-правило A12 («если подпись не влезает инлайн — изогнуть саму стрелку в объезд,
где плашке найдётся место») УДАЛЕНО: оно превращало прямые маршруты в необъяснимые
объезды (стрелка при свободном прямом коридоре шла полкой сверху/снизу) и
дестабилизировало живое превью драга. Невлезающая подпись решается leader-выноской
(плашка сбоку + пунктирный поводок). Заодно убран двойной клиренс плашек у узлов
(эрозия кандидатов дублировала Минковский-раздувание и требовала сегмент ≥ 2× ширины
плашки — подписи массово уходили в выноски): теперь инлайн садится на любой сегмент,
где плашка реально помещается; раздуваются только слитые плечи R4.

Поводок выноски и узлы (2026-07-15): поводок по возможности не ныряет под узлы
(узлы рендерятся поверх слоя рёбер — скрытый участок пунктира рвёт связь
«плашка↔стрелка» на глаз). Избегание МЯГКОЕ: пересечения поводка с узлами — компонент
ключа выбора позиции (слабее наложений самой плашки, сильнее пересечений с чужими
стрелками), поэтому чистое направление выигрывает даже более дальнее/диагональное,
а в полной тесноте нырок допустим — плашка размещается всегда.

Плашка выделенной стрелки — на переднем слое (2026-07-15): в тесноте плашки могут
вынужденно ложиться друг на друга; плашка выбранной стрелки поднимается над
соседними, чтобы читаться. Работает для обоих видов выделения: клик по стрелке
(RF-selected, реактивный z-index плашки) и панельное индиго-выделение по двойному
клику (класс lg-linked-label тем же императивным эффектом, что красит стрелку).
Поднятие — только над другими плашками (внутри слоя подписей), не над узлами.

Качество роутера (2026-07-13, после снятия детуров): в routeAll два канонических
механизма (libavoid):
 • ШТРАФ ЕЗДЫ ПО ЧУЖОЙ ЛИНИИ (shared-path penalty, 1/px): раньше коллинеарная езда
   по уже проложенному сегменту была бесплатной — маршруты седлали чужие линии на
   сотни px, складывались в необъяснимые изгибы и парковались в чужие хэндлы (вход в
   точку чужого выхода — нарушение Т4). С 2026-10-11 (порт на связь, у каждой связи
   своя линия) исключений нет: общих портов не бывает, любая езда — чужая.
 • ВТОРОЙ ПРОХОД (rip-up & re-route): первый проход последовательный (длинные первыми),
   ранние рёбра слепы к ещё не проложенным. Теперь каждое ребро перепрокладывается при
   полном знании всех остальных; новый маршрут принимается только при выигрыше больше
   гистерезисного порога (100), «чистые» рёбра (без пересечений/наложений) пропускаются.
   Это убрало «жертв порядка» (двойные пересечения там, где можно без них). Rip-up
   итерируется до фикспойнта (cap 3) — эпик «читаемые пучки» T6.
 • ПОРТОВЫЙ ШТРАФ (2026-07-15, фикс регрессии «встречные стрелки делят плечи»):
   парковка конца в порт, занятый чужим концом ПРОТИВОПОЛОЖНОЙ роли (вход в точку
   чужого выхода и наоборот), стоит PORT_CONFLICT_COST=600 прямо в A* (PortCandidate.
   penalty) и в оценке готовых ломаных (гистерезис/rip-up; конфликт делает ребро
   «грязным»). Веер одной роли (out-out/in-in в общем доке) легален и не штрафуется.
   Штраф мягкий: сосед-слот выигрывает, но при полной блокаде порт остаётся достижим
   (деградация вместо отказа). Раньше это держал только пост-хок distributeSlots — он
   умеет отказывать (латеральный сдвиг ломает соседний сегмент/упирается в тело), и
   тогда вход+выход оставались в одной точке: встречное наложение концевых плеч,
   неисправимое нуджингом (оба конца пришпилены к общему хэндлу).
 • ДОВОДКА НУДЖИНГА ПОСЛЕ T4 (2026-07-15): мини-проход «плашки → препятствия»
   перепрокладывает грязные рёбра ПОСЛЕ канальной разводки — свежий маршрут мог лечь
   коллинеарно на чужое плечо и оставался так до конца прогона. Теперь после принятия
   перепроложенных маршрутов канальный нуджинг запускается ещё раз (идемпотентен для
   уже разведённых каналов), затем плашки размещаются по финальной геометрии.
 • КЛИРЕНС КАНАЛЬНОЙ РАЗВОДКИ (2026-07-15, фикс регрессии T2 «плечо в теле узла»,
   разбор в docs/archive/plan-nudge-clearance.md): у канального нуджинга не было понятия
   клиренса (роутер держит 12, спрямление джогов 8, нуджинг — 0: только вето
   пенетрации глубже 2px), и жёсткая шкала слотов «center + j·gap» с пином
   концевого хвоста выталкивала крайнее плечо тесного коридора на грань узла и
   внутрь тела. Теперь цели канала считает VPSC: пины (концевые сегменты) держат
   оси весом ∞, клиренс-границы узлов (грань ± NUDGE_CLEAR=8) по пробегу КАЖДОЙ
   группы — стенки-псевдопины, соседи ≥ gap; в тесноте gap деградирует 14→12→10→8
   (ниже нельзя — сольются дуги мостиков JUMP_RADIUS=6); совсем не влезло — канал
   не разводится (лучше остаточное наложение, чем ложь о теле узла). Плечо, уже
   лежащее в клиренс-полосе (исторический канал на грани), выталкивается в ближний
   свободный зазор, если тот не дальше 2×gap; замурованное (вынужденная теснота
   роутера, узлы в 12px) пинится на месте — нуджинг не делает хуже. canApply
   страхует применение той же клиренс-проверкой. Прежние ветки «жёсткая шкала» и
   «лесенка сдвига шкалы» удалены как частные случаи VPSC-решения.

Эпик «читаемые пучки» (2026-07-13, tasks.md; фазы T3+T1+T6 сделаны):
 • T1 МУЛЬТИ-СЛОТОВЫЕ ПОРТЫ: свободным рёбрам A* предлагает все 3 слота каждой стороны
   (12 портов), а не только центры. Веер сам расползается по свободным слотам (езда
   по чужому штрафуется), in/out разводятся в поиске;
   пост-хок distributeSlots остаётся фолбэком. Эффект: хабы (Покупатель, API Gateway)
   читаемы, прямые там, где слот позволяет («Доставка → Покупатель» через всю сцену).
 • T3 ПОСТ-СПРЯМЛЕНИЕ ДЖОГОВ (straightenJogs, чистая функция): короткий (≤24px)
   перпендикулярный перескок между сонаправленными сегментами переносится в соседний
   излом (длина не меняется, изломов −2), если это не режет тела и полная стоимость
   строго меньше — джог, уворачивающийся от реальной езды/креста, остаётся. Доки не
   двигаются. Остаточные 8px-смещения от нуджинга — повестка T2.
 • T2 КАНАЛЬНАЯ РАЗВОДКА «АЛЛЕЙ»: в канал нуджинга собираются не только точные
   наложения, но и почти-параллельные сегменты разных рёбер (≤1.5×gap при пробеге
   >24px) — коридор разводится равными зазорами вокруг своего центра, «плетёнки»
   линий на пиксельных отступах исчезают. Порядок в канале — по текущим осям
   (идемпотентность), при совпадении — по подходам маршрутов. Сегменты одного ребра
   на одной линии двигаются вместе. Многопиновые каналы (двум и более пришпиленным
   плечам раньше — пропуск) решаются VPSC: пины держат оси
   (вес ∞), подвижные распределяются с зазором; невыполнимые — не трогаем. После
   нуджинга — полировка джогов (straightenJogs по финальной геометрии).
 • T4 ПЛАШКИ → ПРЕПЯТСТВИЯ МАРШРУТОВ: после размещения подписей один мини-проход
   перепрокладывает «грязные» рёбра (маршрут сквозь прямоугольник ЧУЖОЙ плашки) со
   штрафом за переход границы плашки (как рамки; своя плашка не отталкивает — online
   лежит на собственной линии), затем плашки размещаются заново. Вторая итерация
   осознанно не делается (редкий остаток «сдвинутая плашка легла на другую линию»).
 • T5 ЧИТАЕМОСТЬ ВЫНОСОК: поводок 1.5px (#6b7280, пунктир 4-3) — тонкий 1px терялся
   в гуще линий; вынесенная плашка получает halo (белая кайма + мягкая тень) и
   отделяется от линий под ней. Online-плашки без halo (лежат на своей линии).
 Эпик закрыт. Отложены с триггерами: полный MLCM-порядок в каналах, центрирование
 аллей, вторая итерация T4.

Живое превью стрелок во время драга узлов (v2, оптимизация 2026-07-21): стрелки
двигаются ЖЁСТКИМ СДВИГОМ из снимка старта — форма маршрута не меняется, только
трансляция. Это даёт идеально плавное движение без скачков и моргания:
 • ребро между ДВУМЯ перетаскиваемыми узлами едет ЖЁСТКО с ними (весь маршрут и
   плашка сдвигаются на дельту группы от снимка старта) — без «прилипшей середины»;
 • ребро с ОДНИМ перетаскиваемым концом тоже едет жёстким сдвигом из снимка старта
   (форма маршрута не меняется, только трансляция) + хэндлы обновляются каждый кадр
   через assignEdgeHandles (сторона входа/выхода меняется live). A* роутинг НЕ
   гоняется во время драга — он запустится на отпускании через обычный конвейер
   раскладки (computeViewLayout → buildAutoRoutes).
 • ПЛАШКИ едут с рёбрами жёстким сдвигом из снимка старта (среднее смещение концов).
   Живое размещение плашек НЕ гоняется во время драга — оно запустится на отпускании.
 • НЕ гоняется вживую: A* роутинг, канальный нуджинг, rip-up чужих рёбер, T4-мини-
   проход, размещение плашек — всё это запустится на отпускании через конвейер;
   возможный доворот прячется перерисовкой drawIn.
 Раньше (до 2026-07-21) чередование A* роутинга и жёсткого сдвига давало разные формы
 стрелок → визуальные артефакты (скачки, моргание). Профилирование показало: A* роутинг
 занимает 3-9ms на кадр (80-90% времени), даже для 5 рёбер. Упрощение до жёсткого сдвига
 дало идеально плавные стрелки и максимальную производительность.
Перерисовка стрелок после ручного жеста (2026-07-09): по завершении ручного
действия, меняющего раскладку (отпускание драга узлов/группы, Undo/Redo),
стрелки, чья геометрия пересчиталась ИНАЧЕ (хэндлы/маршрут/концы/центр плашки),
не «прыгают» на новые места, а анимированно отрисовываются заново (drawIn, как
при раскрытии контейнеров) — остаточная разница превью/финала спрятана анимацией.
Новые/исчезнувшие стрелки не участвуют, prefers-reduced-motion уважается.

Мостики на пересечениях стрелок (line jumps)
Стрелка, пересекающая другую стрелку, «перепрыгивает» её маленькой полудугой —
читаемость пучка линий. Дуга появляется ТОЛЬКО на «крестике»: когда сегменты двух
РАЗНЫХ стрелок перпендикулярны и пересекаются СТРОГО внутри обоих. Если стрелки идут
вместе (исходят из одного хэндла, коллинеарны до чьего-то излома) — их совпадающие
сегменты параллельны, это не крестик, дуги нет; строгая «внутренность» отсекает и
T-стыки (конец одной лежит на линии другой), и общий хэндл, и углы. На каждом
пересечении прыгает ровно одна стрелка — ГОРИЗОНТАЛЬНАЯ (стандартная конвенция),
дуга выгибается вверх. Работает на основной схеме и на страничной схеме (секция
«Схема» страницы объекта идёт тем же level-конвейером, реестр мостиков включён)
для стрелок, рисуемых ортогональной ломаной (архитектор: обычные/кастомные/
обводы/мастер); viewer-smoothstep не затронут. Это РАСКЛАДКА (визуал) — ничего не
персистится.

Хранение раскладки (R3, единое хранилище view_layout): по строке на объект вида,
payload {x, y, expanded}. Геометрия стрелок в БД больше не хранится (ручной слой
удалён 2026-07-09); прежние строки пучков "b:<src>><tgt>" — легаси, игнорируются.
Это РАСКЛАДКА — не версионируется.

Сквозные связи
Edge может соединять узлы с разных уровней иерархии
(например, А с уровня 1 и Б1 с уровня 2, где Б1 — дочерний узел Б).

Правила отображения:
- На уровне, где оба конца — локальные узлы: связь отображается как обычно.
- На родительском уровне: сквозная связь А → Б1 проецируется как А → Б,
  где Б — ближайший предок Б1, принадлежащий этому уровню.
- На уровне, где один конец — внешний: внешний узел отображается как
  «гость» (визуально отличается), стрелка идёт от/к нему.
- У промежуточного гостя есть кнопка «Войти» (иконка «ветвь в потомка») — переход на его слой-схему
  компонентов. Узел из другой ветки дерева, поэтому путь строится заново
  (предки + сам узел), а не аппендом к текущему breadcrumb. Кнопка есть:
  • у листа-гостя, если у него есть дети (GhostNode.has_children, считается в
    _build_graph); у атомарного листа кнопки нет — проваливаться некуда;
  • у свёрнутого контейнера (предок гостя, показанный коробкой): он всегда
    промежуточный, поэтому «Войти» есть всегда — рядом с лупой «раскрыть инлайн».
    Лупа разворачивает содержимое на текущем уровне, «Войти» уводит на слой узла.
- Двойной клик по гостю открывает его детализацию в правой панели — read-only
  (гость несёт лишь имя/роль/технологию/статус/путь предков, без description/
  доков/openapi и без правок; реальный узел живёт в другой ветке). Кнопка
  «Перейти к источнику» уводит на уровень-родитель, где узел показан как локал;
  «Документация → Открыть» — на страницу узла. Так же — свёрнутый гостевой
  контейнер (2026-10-05).
- Двойной клик по узлу/связи, кроме открытия детализации в правой панели, устойчиво
  подсвечивает связанное: у узла — его инцидентные стрелки, у связи — сама стрелка и
  оба её узла (индиго-акцент glow'ом — очерчивает и линию, и наконечник; держится, пока
  объект открыт в панели). Индиго-подсветка узла ПОЛНОВЕСНАЯ (та же громкость, что у
  синего свечения обычного выделения) и ПРИОРИТЕТНЕЕ синего: пока объект открыт в
  панели, узел индиго, даже если он же выделен кликом. Так «выделение панели» и
  «выделение кликом» не конфликтуют: снятие кликового выделения (клик по холсту) не
  меняет картинку — не возникает ложного «с узла сняли, а со стрелок нет», а при
  инспекции связи её концы очевидно подсвечены наравне с линией. Двойной клик по
  ПУСТОМУ холсту сбрасывает подсветку и очищает
  правую панель (штатный зум-по-даблклику при этом отключён).
- Раскрытие ЛЮБЫХ контейнеров (R5, ядро задумки): лупа есть и у ЛОКАЛЬНОГО
  сервиса с детьми — узел раскрывается на месте в рамку со ВСЕМИ своими детьми
  (у гостей — только связанные: это и есть C4-контекст), рекурсивно, но НЕ
  глубже двух слоёв от текущего уровня (MAX_INLINE_DEPTH, container.md C8):
  контейнер на предельной глубине лупу не показывает и инлайн не раскрывается —
  глубже только «Войти» на слой узла (бережёт рендерер от глубоких рамок). Концы
  стрелок проецируются на видимых потомков; связь «прямо в
  контейнер» при его раскрытии скрывается (алерт-кейс). Дети догружаются лениво
  при первом раскрытии; при первом показе раскладываются сеткой от позиции
  контейнера и фиксируются (own-on-first-render). Раскрытие — часть состояния
  ВИДА: персистится (payload.expanded) и переживает перезаход; у наблюдателя
  (viewer) раскрытия эфемерны — смотрит без записи. Сворачивание возвращает
  узел на его сохранённую позицию.
- Анимация раскрытия/сворачивания (2026-07-09): переходы РЕЖИССИРУЮТСЯ, чтобы
  пользователь видел, откуда взялся узел и почему сдвинулся сосед. Раскрытие:
  дети спавнятся стопкой из центра свёрнутого узла и плавно разъезжаются по
  посчитанным позициям; рамка с именем родителя проявляется ПОСЛЕ разъезда;
  сдвинутые раскрытием соседи едут параллельно с детьми. Сворачивание —
  зеркально: дети съезжаются в точку будущего узла (рамка гаснет, соседи едут),
  по завершении стопка подменяется свёрнутым узлом. Стрелки, у которых движется/
  появляется хоть один конец, на время перехода честно скрываются, а по концу
  разъезда РИСУЮТСЯ анимированно от исходного хэндла к целевому (штрих
  pathLength=1 + stroke-dashoffset); наконечник и плашка с текстом появляются
  по завершении отрисовки. При большом числе стрелок отрисовка идёт КАСКАДОМ
  (Ф5 эпика плавности, 2026-07-15): волнами по 8 стрелок с шагом 60мс, короткие
  маршруты первыми — связи «расцветают» от ближних к дальним; конец фазы — по
  последней волне. Каскад за флагом DRAW_CASCADE (layoutAnimation.ts) — откат
  одной константой.
  Анимация чисто презентационная (раскладку не меняет: финал байт-в-байт равен
  рендеру после перезагрузки), уважает prefers-reduced-motion, не цепляет драг
  (transition живёт на холсте только в окно перехода). Реализация:
  useLayoutAnimation + планировщики layoutAnimation.ts + CSS lg-canvas--anim.
  Устойчивость к нагрузке (2026-07-13): отсчёт концов фаз (разъезд, отрисовка
  стрелок) ведётся от ПЕРВОГО ПОКАЗАННОГО КАДРА фазы (rAF→setTimeout), а не от
  setState — прогон раскладки по замерам, приходящий прямо в окно анимации,
  откладывает первый кадр, и wall-clock-отсчёт снимал drawIn до видимого старта
  («анимация пропадала», когда стрелок много). Сам конвейер оптимизирован без
  смены результата (индекс сегментов, скип rip-up при неизменном окружении, кэш
  сетки/проходимости A* между попытками): раскрытая сцена ~56мс/прогон против
  ~120-200 до — блок в окне анимации сжался до пары кадров.
  Плавность (эпик 2026-07-14/15, Ф1-Ф3): на окно анимации пересчёты раскладки
  ОТКЛАДЫВАЮТСЯ и досчитываются в «мёртвой зоне» конца разъезда (узлы стоят,
  стрелки ещё скрыты — drawIn рисует уже свежие маршруты); зеркальные прогоны
  скипаются по полной сигнатуре результата; сборка RF реконсилируется
  (неизменённые узлы/рёбра сохраняют identity — ре-рендерится только задетое,
  выделение переживает пересчёт); сам конвейер исполняется в Web Worker —
  главный поток в анимации занят только рендерами.
- Раскладка привязана к ВИДУ (R3): таблица view_layout(project_id, view_id,
  item_id, payload JSONB) — ЕДИНОЕ хранилище всей раскладки. item_id: id
  сущности → {x,y} (локалы, гости и свёрнутые контейнеры единообразно; один
  узел — гость на разных видах в разных местах) и {expanded} (раскрытие
  контейнера — R5). Всё это РАСКЛАДКА — не версионируется.
- Владение позицией «own-on-first-render» (рефакторинг движка, 2026-06-28): у каждой
  сущности (локала и гостя) своя АБСОЛЮТНАЯ позиция, персистимая при первом показе на
  уровне (гость засевается на кольце — см. ниже — и сразу фиксируется). Дальше узел
  двигается ТОЛЬКО ручным драгом или командой «Переразложить» — не пересчитывается за
  «живым якорем». Это убрало классы багов: драг локала не тащит связанных гостей, а
  раскрытая рамка не «убегает».
- Команда «Переразложить уровень» (кнопка в шапке, только архитектор и режим схемы):
  сброс ручного layout текущего уровня в авто — позиции в строках view_layout
  этого вида удаляются (позиции, легаси-геометрия пучков); строки с флагом раскрытия
  сохраняются: раскрытые контейнеры НЕ сворачиваются, их дети раскладываются заново.
  Видимые узлы и рамки плавно переезжают на авто-позиции (анимация). Уровень
  выглядит как при первом открытии. Скоуп строго по container_id (соседние уровни и
  узлы вне уровня нетронуты). Действие необратимо (подтверждается модалкой), историю
  Undo уровня после сброса чистим.
- СВЯЗИ, УПИРАЮЩИЕСЯ В РАМКУ. Связь можно протянуть не только между атомарными
  узлами, но и «прямо в контейнер» — это допустимо, хотя и неточно (схема не
  говорит, какая именно его часть участвует; такие связи подсвечивает алерт «связь
  в промежуточный объект»). Раньше на схеме от такой связи не оставалось ничего:
  контейнер на своём уровне заменён детьми, рисовать было не на чем, и рядом просто
  висел сосед без единой стрелки. Теперь связь ВИДНА и читается буквально: она идёт
  от узла как обычно, доходит до рамки контейнера и упирается в неё наконечником
  (или наоборот — исходит из рамки и входит в узел). Работает в трёх местах: когда
  контейнер раскрыт лупой на уровне; когда ты стоишь ВНУТРИ него (упирается в
  родную рамку уровня); и на пустом слое, где рамка рисуется всегда.
  Конец, воткнутый в рамку, можно ОТЦЕПИТЬ и прицепить к любому узлу внутри неё —
  так неточная связь уточняется до конкретного ребёнка, без удаления и пересоздания.
  Тянется только этот конец: вся остальная геометрия стрелок остаётся полностью
  автоматической. Промах мимо детей рамки отменяет жест — конец возвращается на
  рамку, связь не может остаться с одним концом. Если в рамку упирается общая
  стрелка нескольких связей, переезжают все они разом (одним шагом Undo).
- Запрет проникновения в чужую родную рамку (C4-инвариант): гость (и гостевая
  рамка раскрытого промежуточного контейнера) НИКОГДА не лежит внутри родной
  рамки уровня, в которую не входит по членству. Родные рамки = предки из
  breadcrumb, концентрически вложены; гость — член рамок до своего общего предка
  включительно, поэтому единственная «запретная» для него рамка — следующая глубже
  общего предка. При дефолтном спавне, росте родной рамки (добавили узел) и ручном
  драге гость минимально сдвигается к ближайшему краю запретной рамки + интервал;
  задвинуть его внутрь руками нельзя. Раскрытая рамка — настоящий узел канвы
  (R4, compound): дети сидят внутри в её координатах, «Свернуть» — ✕ в плашке. Это РАСКЛАДКА — авто-сдвиг не персистится (драг персистит уже
  скорректированную позицию).
- Дефолтная раскладка гостя (без ручной позиции) — boundary labeling на «кольце»
  запретной рамки: гость ставится на ПЕРИМЕТР рамки F_{memberDepth+1} (та же рамка,
  что у keep-out, + интервал) — оптимальное место кратчайшей стрелки лежит на её
  границе. Базовая ось — горизонталь (поток C4 слева-направо, ближний к связанным
  узлам край), верх/низ берётся, когда горизонталь увела бы стрелку сквозь тела
  других узлов. Гости одной стороны раздвигаются изотонически (PAV) вокруг центра
  масс. Кольца разной глубины решаются изнутри наружу (рамка растёт за уже
  размещёнными глубокими гостями), поэтому keep-out выполняется по построению, а
  его проход остаётся лишь страховкой (ручные позиции, рост рамки за ручным гостем).
- Раскладка детей раскрытой гостевой рамки (промежуточный гость «вошёл» коробкой,
  его дети видны рамкой). При ПЕРВОМ показе дети не размещаются ELK-движком, а встают
  ВНУТРЕННЕЙ ПОЛКОЙ вдоль стороны рамки, обращённой к кольцу, в порядке проекции якоря —
  центроида центров связанных локальных узлов (нет связей → центроид всех локалов).
  • Перелив в колонки: если полка по высоте не влезает в пролёт кольца, дети переливаются
    в несколько колонок (вместимость колонки = пролёт / шаг узла). Самые «тяготеющие к
    контенту» (больше связей, ближе к центру масс якорей) — во внутреннюю колонку у кольца,
    остальные выталкиваются наружу; внутри колонки порядок — по якорю.
  • Дальше — own-on-first-render, как у всех: позиция каждого ребёнка сразу фиксируется
    АБСОЛЮТОМ (строка view_layout) и меняется только ручным драгом / «Переразложить».
  • Живого следования детей за сдвигом коробки-родителя НЕТ (снято рефакторингом
    ownership 2026-06-28 вместе с остальными «живыми якорями»): позиции детей
    абсолютны с первого показа; при сворачивании коробка возвращается ровно на
    свою сохранённую позицию.
  Всё это РАСКЛАДКА (визуал), не версионируется.
- Мастер-стрелка (несколько слитых связей одного направления) — синтетическое ребро
  без своей строки в БД; её геометрию, как и всем стрелкам, назначает авто-раскладка.
- Статус жизненного цикла узла (Node.status: existing/planned/deprecated) кодируется
  цветом тела: existing — синий (прежняя C4-рампа по глубине), planned — зелёный с
  бейджем «новый», deprecated — красный с бейджем «выводится»; внешние узлы — приглушённый
  тон того же статуса. Гости красятся по своему статусу. Связь наследует статус сильнейшего
  конца (deprecated > planned > existing): deprecated — красный пунктир, planned — зелёная,
  иначе серая. Это ВЕРСИОНИРУЕМАЯ СЕМАНТИКА (как shape/is_external), не раскладка.
- Фильтр «Вид схемы» (as-is / переход / to-be) — клиентский визуальный слой поверх данных:
  as-is показывает existing+deprecated (что работает сейчас), to-be — existing+planned
  (целевая система), переход — всё (дефолт). Скрытые статусом узлы и их рёбра НЕ удаляются,
  а приглушаются (opacity) — раскладка и связи сохраняются. Вид персистится в localStorage
  (не серверное, не свойство схемы). Легенда снизу-слева (свотч + счётчик видимых узлов
  статуса) показывается только когда на уровне есть хотя бы один не-existing узел.
- Тумблер «Скрыть подписи связей» — второй клиентский визуальный слой: прячет плашки
  подписей и поводки выносок со всех схем (редактор-карта, страницы, контекст), не
  трогая раскладку и маршруты (чистое скрытие, переключение мгновенно). Плашка
  выделенной стрелки остаётся видимой — способ прочитать подпись, не выключая режим;
  детализация доступна двойным кликом по самой линии. Кнопка — сосед «Переразложить»:
  на страницах в правом верхнем углу холста (все роли), в редакторе — в топбаре.
  Персистится в localStorage по проектам (как «Вид схемы»).
- Разовый совет на перегруженных схемах (>80 узлов или >200 стрелок на уровне): тост
  «На вашей схеме очень много объектов, поэтому стрелки могут быть расставлены
  неаккуратно. Подёргайте несколько узлов, и стрелки выправятся сами» — честное
  объявление механики фоновой уборки (стрелки на плотных сценах доводятся до чистоты
  серией правок). Показывается один раз на вид и только тому, кто может двигать узлы.

MVP — в объёме
✓ Дерево узлов произвольной глубины
✓ Боковая панель из сворачиваемых секций (аккордеон, каждая секция
    разворачивается/сворачивается независимо):
    - «Дерево узлов» (как в Confluence): иерархия по parent_id, ленивое
      раскрытие веток. Узлы-пользователи (shape: person) в legacy-дереве не
      показываются — оно про детализацию системы, а внутрь пользователя
      проваливаться нечего (на графе они есть); в плоском дереве страниц и
      редактора персоны стоят в общей иерархии наравне с прочими объектами;
    - «Добавить узел» (только архитектор): палитра из четырёх шаблонов-форм
      (сервис, БД, брокер, пользователь). Узел создаётся перетаскиванием
      шаблона на схему — см. ниже;
    Вся панель целиком сворачивается в узкую полосу. (Бизнес-процессы переехали
    из дерева в самостоятельный режим «Процессы» — см. ниже.)
✓ Бизнес-процессы — sequence-конструктор поверх C4. Архитектор строит диаграммы
    процессов, в которых участники = узлы C4, а сообщения нельзя нарисовать
    произвольно — только выбрать из плеч уже задокументированных связей. Так
    процессы и архитектура держатся в одной правде по построению:
    - оболочка: процессы живут в самостоятельном режиме «Процессы» (переключатель
      Объекты/Процессы в шапке со скользящей подсветкой, персист в localStorage;
      дефолт — «Объекты»), а не в
      модалке. Слева — рейл процессов (свернуть/развернуть, «+ Новый процесс», список
      с бейджами статусов и ···-меню дублировать/удалить; переименование — двойной
      клик по имени в списке: поле на месте имени, Enter или уход из поля сохраняют,
      Escape отменяет, пустое имя не сохраняется; только архитектор, 2026-10-18), справа — холст выбранного
      процесса с тулбаром над диаграммой. Правка инлайн по тумблеру «Редактировать /
      Готово» (только архитектор), просмотр read-only доступен обеим ролям;
    - связь C4 — это «канал с плечами»: синхронный канал даёт два плеча — вызов
      (forward) и ответ (return); асинхронный — одно (forward, рисуется как событие).
      новая связь всегда создаётся синхронной; переключить канал в асинхронный
      можно тумблером «синхронная/асинхронная» в шапке канала в композиторе
      бизнес-процесса (поле Edge.is_synchronous; дефолт для связей без значения —
      синхронный). Это ЕДИНСТВЕННОЕ место правки типа: в C4-модалке связи тумблера
      нет — тип канала живёт только в бизнес-процессах, на схему C4 он не влияет.
      Авто-вывода по технологии нет — он зависел от текстового поля, что неочевидно;
    - два слоя: «что с чем взаимодействует» (участники + сообщения) заперто
      архитектурой; «в каком порядке / при каких условиях» (порядок, фрагменты
      alt/opt/loop/par) — свободный слой процесса. Фрагмент накидывается на ВЫБРАННЫЙ
      диапазон сообщений (выбор типа в тулбаре → протягивание по строкам), фрагментов
      может быть несколько, в т.ч. вложенных; удаление — кликом по шапке фрагмента;
    - ПОДПИСЬ ШАГА ВСЕГДА СВОЯ (решение пользователя 2026-08-11). Прежде подпись бывала
      своей ЛИБО пустой, а пустая значила «показывать то, что даёт канал» (метку связи у
      вызова, «ответ» у ответа), и выводилась при каждом чтении. На экране два таких шага
      неразличимы, а вели себя по-разному: один следовал за переименованием связи, другой
      нет — ровно тот разнобой, ради которого модель и менялась. Теперь дефолт канала
      ЗАМОРАЖИВАЕТСЯ ОДИН РАЗ, при создании шага, и дальше это обычный текст; API отдаёт
      подпись как есть и ничего не выводит. Пустая подпись означает ровно «подписи нет».
      ЦЕНА ПРИНЯТА СОЗНАТЕЛЬНО: переименование связи в схеме до процессов больше не
      доезжает — подписи правятся руками. Взамен подпись не меняется под ногами и
      переживает удаление связи (шаг остаётся повисшим, но подписанным).
      КАРТОЧКА ШАГА — клик по стрелке/подписи в режиме правки: поле подписи, «Удалить»

      CASCADE, и удаление узла молча сносило участника вместе со всеми его шагами;

      разрыва, подпись «нет узла в схеме». ПРИВЯЗКА к узлу — кнопкой на его же шапке

      показывается строкой. Расхождение имён (в диаграмме одно, у узла другое)
      показывается ДО записи: после привязки действует имя узла, схема — источник
      истины, но потеря имени из диаграммы не молчаливая.

      направления) говорит узлами, слой процесса — участниками.

      плеча и сходимость проекции проверяет бэкенд (точка enforcement — POST
      /messages). Удаление связи из схемы не теряет сообщение: оно становится
      «повисшим» (valid=false) и подсвечивается янтарём (глиф «разорванная цепь»,
      чип «связь удалена», пунктир);
    - статусы в бизнес-процессах: на sequence-диаграмме ЦВЕТ = статус узла
      (единообразно с C4), а ТИП плеча — это ФОРМА (линия + наконечник), не цвет.
      Плечо красится по «сильнейшему» статусу концов: existing — чёрное (как стрелки
      связей C4), planned — зелёное, deprecated — красное; вызов = сплошная +
      закрашенный наконечник, ответ = пунктир + открытый, событие = сплошная +
      открытый. Шапки/линии жизни/активации planned и deprecated тонируются по статусу,
      шапка несёт бейдж «новый»/«выводится»; existing — без изменений. Переключатель
      «Вид схемы» (as-is / переход / to-be) в тулбаре гасит участников и сообщения
      вне вида (opacity, мгновенно, без удаления); подсказка вида — плашкой над канвой.
      Вид персистится в localStorage тем же ключом, что и на C4-схеме (общая привычка
      пользователя). В рейле процессов — производный бейдж to-be / вывод / миграция
      из статусов участников (на видимость процессов в списке не влияет).
    Холст процесса — sequence-диаграмма с линиями жизни (узлы C4), полосами
    активации, плечами (цвет = статус, форма = тип) и фрагментами; читается единой
    семьёй с C4-схемой в соседнем режиме.
✓ Создание узла перетаскиванием: архитектор тянет шаблон нужной формы из
    секции «Добавить узел» на схему уровня. Во время перетаскивания за курсором
    следует не плитка шаблона, а пустая рамка-превью будущего узла (форма с
    прозрачным телом): она масштабируется под текущий зум схемы (совпадает с
    реальным размером узлов) и примагничивается к центральным осям соседей —
    архитектор сразу видит точное место и координаты создаваемого узла.
    В точке отпускания открывается модалка создания узла с уже выбранной формой
    (поэтому поля «Отображение» в модалке нет) и заполняемыми полями. Узел
    появляется там, где показывала рамка (координаты, с учётом примагничивания,
    сохраняются в pos_x/pos_y). Пустой уровень показывает сам холст (канву с
    точками) — drop-зоной служит вся его область, узел встаёт под курсором.
    На пустом уровне видно РАМКУ РОДИТЕЛЯ — пунктирный прямоугольник размером
    «как под один узел» с его подписью: слой это внутренность родителя, и это
    должно читаться сразу, а не после первого узла. Если у родителя есть свои
    связи, они тут же и нарисованы — идут от соседей и упираются наконечником
    в эту рамку (см. «Связи, упирающиеся в рамку» ниже).
    Словесной подсказки на пустом слое нет: старт объясняют рамка родителя, его
    подпись, его связи и подсветка приёма при перетаскивании шаблона внутрь.
    Рейл тостов схемы в правом верхнем углу ОБЛАСТИ ХОЛСТА остаётся (индикатор
    незавершённости, сообщения о чужих правках — стекуются колонкой).
    Тосты схемы не заслоняют шапку и боковые панели: их анимации обрезаются
    границей области графа — въезд/уезд идут «из-за края холста», а не за край
    экрана поверх правой панели. Холст открывается слегка
    отдалённым (зум ≈0.85), вход на разреженный уровень тоже не подлетает вплотную.
    Отдалить схему можно до зума 0.05 (решение 2026-10-12; прежний предел 0.5 на
    больших уровнях не давал увидеть схему целиком, в т.ч. кнопкой «Центрировать»);
    на сильном отдалении линии связей держат экранную толщину, а сетка точек скрыта.
    Дроп в раскрытую рамку: если шаблон отпущен внутрь раскрытой инлайн-рамки
    контейнера (напр. ObsCore на уровне HelixMon), новый узел создаётся РЕБЁНКОМ
    этого контейнера, а не текущего уровня, и появляется внутри рамки. Во время
    перетаскивания рамка-цель подсвечивается (при вложенных рамках цель — самая
    глубокая под курсором). Позиция дропа принадлежит виду текущего уровня.

    • «Структура» у базы данных — таблицы и колонки ЗАПИСЯМИ (имя, тип, обязательность,
      ключи, смысл значения; контур — необязательное поле таблицы). Внешний ключ карты
      выбирается из колонок узла.
    • ER-диаграмма — ПРОИЗВОДНОЕ представление этих записей (mermaid erDiagram по
      кнопке). Правда — записи: из текста диаграммы нельзя построить обратный индекс.
      Кардинальность связи честная, обязательность внешнего ключа её различает.
    • «Каналы» у брокера — та же форма для событий: канал (имя, необязательная группа —
      vhost/namespace/account, вид — topic/queue/exchange) с метой доставки (ключ
      партиционирования, гарантия, retention) и полями сообщения ЗАПИСЯМИ. Мета — не
      украшение: ею отвечают на три частых инцидента (порядок применения событий,
      повторная обработка, «при переигрывании ничего не нашлось»). Каналы бывают только
      у формы «брокер» — и интерфейс, и API это правило держат.
    • «Конфигурация» у сервиса — переменные окружения и параметры ЗАПИСЯМИ: имя,
      тип значения, обязательность, дефолт ИЗ КОДА и «что переключает». Владелец —
      ВСЕГДА САМ СЕРВИС: узлов-хранилищ конфигурации (ConfigMap, Consul, Vault) не
      заводим, а одинаковый параметр у двух сервисов — это две записи, потому что
      назначение и дефолт у них разные. Перечень ПЛОСКИЙ: ни групп, ни второго уровня.
      ЗНАЧЕНИЙ НЕ ХРАНИМ НИКОГДА — они разные по средам и часто секретны, а ArchMap не
      хранилище секретов; «по умолчанию» несёт текст дефолта из кода, а не значение
      среды. Конфигурация — артефакт сервиса (как логика и спека), у неподходящей формы
      показывается legacy-механикой, а не прячется.
    • ОБРАЩЕНИЯ К ДАННЫМ — ПОМЕТКОЙ В ТЕКСТЕ СХЕМЫ ЛОГИКИ, у ВЫЗЫВАЮЩЕГО (как OpenAPI
      живёт у поставщика API). Пометка — строка в подписи шага:
          F["Запись заказа<br>пишет: orders, order_items"]
          C["Счёт в Payment API<br>читает: orders.total_amount, orders.currency"]
      ГРАММАТИКА (нормативно, реализация — backend/app/data_refs.py):
      – маркеры «читает:»/«пишет:» и «reads:»/«writes:», регистр любой; СЛИТНАЯ форма
        «читает/пишет:» («reads/writes:», пробелы вокруг слэша допустимы) естественна для
        языка и обещает ОБА факта: каждая ссылка после неё даёт две пометки — и read, и
        write (дедуп общий, поэтому раздельная пометка тем же режимом её не удваивает);
      – СОБЫТИЯ адресуются СВОИМИ маркерами: «публикует:»/«потребляет:» и
        «publishes:»/«consumes:» (слитная форма «публикует/потребляет:» — тоже обе
        пометки). Слова разные не для красоты: семантика доставки ≠ семантика записи
        (сопровождение спрашивает «кто ещё потребляет», а не «кто пишет»), и КАТАЛОГ
        РЕЗОЛВА у них свой — только каналы брокеров. Поэтому одноимённые таблица и
        канал не конфликтуют ПО ПОСТРОЕНИЮ: «пишет: orders» — про таблицу, «публикует:
        orders» — про канал, и класс двусмысленностей просто не рождается;
      – КОНФИГУРАЦИЯ адресуется маркером «зависит от:» («depends on:»): развилка
        зависит не только от данных («если статус paid»), но и от ручек («если
        FEATURE_X включён»). Маркер ДВУСЛОВНЫЙ — единственный такой: пробел внутри
        него читается как «один или несколько», поэтому «зависит  от:» и перенос
        строки между словами — тот же маркер. Каталог свой, и область поиска у него
        УЖЕ, чем у двух семей выше: не проект, а ОДИН УЗЕЛ — ближайший контейнер
        владельца схемы (с 2026-10-29, «Элемент архитектуры»: у компонента — его
        контейнер-предок; до того — сам владелец схемы). Отсюда: квалификатора
        «Узел / имя» у такой пометки НЕТ и быть не может (искать за пределами
        объекта незачем); точка имя НЕ делит — «feature.new_checkout» это целое
        имя параметра, групп у конфигурации не бывает; неоднозначность НЕВОЗМОЖНА
        по построению (имя уникально в пределах узла), поэтому единственный промах —
        «параметра нет у этого объекта». Одноимённые таблица, канал и параметр не
        конфликтуют, как и первые две семьи между собой: маркер выбирает мир;
      – после маркера — ссылки ЧЕРЕЗ ЗАПЯТУЮ до терминатора: конец строки, «<br>»,
        кавычка, «]», «)», «}», «|»; в подписи РЕБРА без кавычек — ещё и начало
        стрелки («--», «==», «.-», «-.», пробел перед стрелочным символом), иначе в
        ссылку уезжал хвост «orders --> B» (2026-09-26);
      – ссылка: [Узел-БД / ][раздел.]таблица[.колонка]; у событий та же форма —
        [Брокер / ][группа.]канал[.поле сообщения] (группа = vhost/namespace/account).
        ТОЧКИ В ИМЕНИ КАНАЛА ДОПУСТИМЫ («orders.created», «orders.created.v2» — норма
        именования Kafka): у каналов резолв пробует ещё две равноправные гипотезы —
        «весь хвост = имя канала» и «хвост без последнего сегмента = имя, последний =
        поле». Совпало больше одной трактовки (есть и канал «orders.created», и канал
        «orders» с полем «created») — обычная неоднозначность, лечится квалификатором
        «Брокер / канал». У ТАБЛИЦ этих гипотез НЕТ (точки в именах таблиц редки, и
        лишние трактовки плодили бы неоднозначность на ровном месте).
        ДВОЕТОЧИЕ В ИМЕНИ КАНАЛА ТОЖЕ ДОПУСТИМО (2026-09-26): ключи Redis Pub/Sub
        «timeline:public», «timeline:hashtag:rails» — делителем оно не служит; у
        таблиц «x:y» — битая пометка.
        Квалификатор узла отделяется
        « / » и может содержать пробелы (имя узла или хвост его пути); голая часть —
        токен БЕЗ пробелов (буквы/цифры/«_»/«-»/точки), поэтому таблица с пробелом в
        имени пометкой не адресуется вовсе;
      – совпадение имён ТОЧНОЕ, регистр значим; «x.y» пробуется И как «таблица.колонка»,
        И как «раздел.таблица» — сработали обе гипотезы, значит неоднозначно, и лечится
        это квалификатором, а не угадыванием за пользователя; у каналов те же две
        гипотезы («канал.поле» против «группа.канал»), и квалификатор там — «Брокер /
        канал»;
      – дедуп в пределах схемы по (ссылка, режим); колонка необязательна — «вся таблица»
        законный и обычный ответ (SELECT * никуда не делся);
      – разбор — по ВСЕМУ тексту схемы, mermaid не парсится: пометка в подписи связи или
        заголовке subgraph считается наравне;
      – маркер есть ОБЕЩАНИЕ ФАКТА: «читает: договор из архива» — не «ничего», а алерт;
        текст обещал данные, которых в структуре нет.
      ПЕРИМЕТР: пометками адресуются ТОЛЬКО объекты карты — таблицы описанных баз,
      каналы описанных брокеров и параметры конфигурации самого объекта. HTTP-вызовы,
      файлы и очереди «в голове» пометками не описываются: у них свой язык (связи,
      спеки), а маркер, не нашедший цели, обязан светиться алертом, а не считаться
      нормой. ⚠️ У конфигурации цена этого правила видна прямее всех: «зависит от:
      нагрузки» — обычная русская фраза, и она даст замечание. Так и задумано (иначе
      прозой можно спрятать любой факт), поэтому текст замечания называет ОБА выхода —
      описать параметр либо убрать двоеточие.
      РЕЗОЛВ — НА ЧТЕНИИ (чистая функция от пометок, каталогов таблиц и каналов
      ПРОЕКТА и путей узлов). Обращения нигде не хранятся: кэша нет, инвалидации не
      существует как класса задач, а переименование таблицы, канала или узла зажигает
      алерт само.

      пометку — одна заметка на пакет (доки грузят раньше структуры, и это нормальный

    • ГДЕ ПОМЕТКИ КАНАЛОВ ВИДНЫ — те же четыре места, зеркально: «Кто публикует / кто
      потребляет» в теле канала на странице брокера (GET /nodes/{id}/channels/usage);

      ещё не описана» отдельна для таблиц и для каналов.

      это следствие устройства: «Зависит» под параметром в секции «Конфигурация»

    • КАНАЛ НА СВЯЗИ: стрелка, у которой хотя бы один конец — брокер, НАЗЫВАЕТ канал.
      Поле «Канал» (топик/очередь) живёт в панели связи редактора-карты и появляется
      только у таких стрелок; правится и откатывается (Undo) как описание и технология.
      Это ссылка ПО ИМЕНИ, а не выбор из списка: канал бывает описан позже схемы, и
      запрет писать его сейчас заставлял бы документировать брокер раньше карты. Под
      полем — мягкая подсказка резолва по структуре брокера-конца: «✓ канал» либо
      «⚠ канала нет в структуре брокера» (сообщает, не запрещает). КОНВЕНЦИЯ
      НАПРАВЛЕНИЯ: «сервис → брокер» читается как публикация, «брокер → сервис» — как
      доставка подписчику; на поиск канала направление не влияет (у моста между двумя
      брокерами канал ищется у обоих концов). ЧЕМ ПРОВЕРЯЕТСЯ: класс алертов «Связи с
      брокером без канала» (AL31 — «канал не указан» / «канал «X» не найден у брокера
      «Y»», переход к самой связи на холсте); в YAML-обмене канал ездит полем `channel`
      у ребра (экспорт пишет его, только когда он есть), а превью импорта «Из
      репозитория» называет ПОИМЁННО связи в брокер, оставшиеся без канала, и связи,
      у которых в channel оказался ПЕРЕЧЕНЬ каналов («email, notify_tornado, …» —
      его надо расщепить по связи на канал), — пока агент ещё рядом и может
      дописать. ИМПОРТ ЗАВОДИТ КАНАЛЫ ПО СВЯЗЯМ (2026-09-06): каждое имя, названное
      в `channel` у стрелки в брокер и не описанное ни пакетом каналов архива, ни
      живой структурой, становится записью-ЗАГЛУШКОЙ у брокера (мета пустая,
      описание — фиксированный текст «Заведён импортом по связи схемы…»); отчёт
      импорта и догрузки называет их число отдельной строкой. Схема знает, что канал
      ЕСТЬ, — без записи панель алертов после ввоза честной схемы тонула в «канал не
      найден у брокера» (59 из 60 замечаний у сильной модели). Заглушка — не
      описание: сверка покрытия пакета каналов её не считает, а пакет, описавший
      канал, заполняет её без тумблера перезаписи и снимает маркер. Догрузка заводит
      заглушки только по своим новым связям — живое она не трогает.
    • «Через ИИ-агента» — BYOA-дозаливка: промпт → пакет YAML → превью → применение.
      Агент читает миграции и ORM-модели. Удалений нет ни при какой настройке;
      перезапись заполненного — по явному тумблеру. Пакет описывает ТОЛЬКО структуру:
      обращения агент проставляет пометками в схемах логики (промпт «Доки от агента»
      учит конвенции и проверяет её чек-листом), и промпт структуры говорит это прямо.
      ДВА ИСТОЧНИКА СХЕМЫ (решение пользователя 2026-08-18). Лучший — репозиторий
      ВЛАДЕЛЬЦА базы. Но база бывает чужой и недостижимой (коробочный продукт, legacy,
      соседняя система), а код-ПОТРЕБИТЕЛЬ ходит в неё своими запросами — строит SQL,
      зовёт таблицы по именам. Тогда схема описывается ПО ЗАПРОСАМ: имена в них
      настоящие, иначе код бы не работал. Такие таблицы НИЧЕМ не помечаются — они
      обычные; из промпта убрано лишь достраивание «по здравому смыслу» (колонки
      id/created_at, которых запрос не называет, и типы, которые из кода не следуют).
      ПОЧЕМУ ЭТО БЕЗОПАСНО: мердж дозаливки add-only, поэтому позднее описание из
      репозитория самой базы просто ДОПОЛНИТ восстановленное — недостающие колонки
      допишутся, лишних не появится. А расхождения двух картин превью называет
      ПОИМЁННО («колонка «history.itemid» — тип «int», в ArchMap «bigint»»), и это
      не только защита от тихой подмены, но и КРИТЕРИЙ КАЧЕСТВА BYOA: сошлись две
      независимо восстановленные картины без правок — промпт хорош; разошлись — работать
      надо над промптом. Чек-лист скептика принимает запрос как доказательство таблицы
      наравне с DDL, а пустой тип у восстановленной колонки сомнением не считает.
    • «ОПИСАТЬ КАНАЛЫ С ПОМОЩЬЮ ИИ-АГЕНТА» — та же дозаливка для брокера (второй пункт
      меню «+ Канал»), но с одним отличием, из которого следует всё остальное: у брокера
      НЕТ репозитория-владельца. Топик объявлен в коде тех, кто его публикует и
      потребляет, поэтому промпт велит прогонять задачу В КАЖДОМ репозитории, который
      ходит в брокер, и описывать только то, что видит этот код; окно говорит это же
      подзаголовком, до кнопки промпта. Пакеты разных репозиториев ДОЛИВАЮТСЯ друг к
      другу: поля сообщения добавляются к уже описанному каналу, а если два репозитория
      назвали мету по-разному (разный retention, разная гарантия доставки) — побеждает
      описанное раньше, а расхождение уходит в замечания поимённо («retention в пакете
      «30d», в ArchMap «7d»»). Иначе смысл карты зависел бы от порядка загрузки пакетов.
      Мету, которой в коде нет, промпт запрещает выдумывать прямым текстом: пустое поле
      законно, а придуманная гарантия доставки дороже пропуска — по ней решают, обязана
      ли обработка быть идемпотентной. Каналы, которые УЖЕ называют связи схемы, промпт
      перечисляет отдельным разделом как минимум пакета (канала нет в коде этого
      репозитория — назови его в ответе, а не выдумывай) и велит искать точки
      ПУБЛИКАЦИИ, а не только регистрации потребителей: очередь, в которую этот код
      лишь пишет, иначе теряется — её видит доковая сессия, а канальная нет. Адрес брокера — комментарием «# archmap-node:»
      первой строкой файла, промпт знает брокеров ЭТОГО проекта и подставляет адрес в
      образец; каналы могут приехать только узлу-брокеру (иначе ошибка с перечнем
      брокеров проекта), файл без адреса уезжает объекту окна. Когда брокеров в проекте
      НЕСКОЛЬКО, промпт отдельно объясняет выбор владельца: у каждого брокера свой файл
      со своим адресом, канал кладётся тому, чей клиент использует его по коду
      (очереди Celery — брокеру из конфигурации воркера, Kafka-топики — узлу Kafka), и
      прямо запрещает адресовать всё первому в перечне. Проверяет это и превью: канал
      адресован одному брокеру, а СВЯЗЬ схемы называет его у другого, который такого
      канала не знает, — предупреждение «проверьте адресацию» (два независимых
      источника разошлись; одноимённые каналы у двух брокеров законны и молчат).
      И ПОКРЫТИЕ того же минимума: канал, который называет связь, а пакет и описание
      брокера не знают, — предупреждение «либо в коде он зовётся иначе (похоже на
      …), либо имя на связи неточно: проверьте связь»; чинить можно любую сторону, и
      обе названы, потому что имя на связи агент тоже выдумывает.
    • ПРОМПТ «ДОКИ ОТ АГЕНТА» УЧИТ И СОБЫТИЯМ: шаг публикует или потребляет событие —

    показывается, только если есть что терять: у поддерева есть внешние связи
    (ровно один конец вне поддерева) ИЛИ у узла есть дети; в списке — именно эти
    внешние связи (включая связи потомков наружу). Лист без связей удаляется
    сразу, без модалки.
✓ Отмена и повтор перемещений (Undo/Redo, архитектор). Ctrl/⌘+Z отменяет, Ctrl/⌘+
    Shift+Z или Ctrl/⌘+Y повторяет. Поскольку правки персистятся в Postgres сразу,
    отмена — это компенсирующий вызов API, а не откат фронт-стейта; визуально
    мгновенно (зеркало в локальный стейт), сеть фоном. Итерация 1 покрывает все
    ПЕРЕМЕЩЕНИЯ: позиции узлов/гостей/контейнеров (вся перетянутая группа = один
    шаг). Ручной слой стрелок удалён (2026-07-09) — команды изломов/плашки/хэндла
    больше не создаются. История — до 50
    шагов, в памяти вкладки, СКВОЗНАЯ по уровням: если откатываемая правка сделана на
    другом уровне, Undo/Redo сначала РЕДИРЕКТИТ пользователя на этот уровень, затем
    выполняет откат. Undo/Redo доступны и горячими клавишами, и кнопками тулбара на
    холсте. Итерация 2 добавляет отмену УДАЛЕНИЙ: перед каскадным удалением клиент
    снимает снимок поддерева (узлы + рёбра + строки раскладки), а Undo восстанавливает
    его на сервере с СОХРАНЕНИЕМ исходных id (POST /nodes/restore), Redo — повторное
    удаление. Структурное восстановление требует серверной проекции гостей/рёбер,
    поэтому undo/redo удаления перечитывают уровень (а не зеркалят в стейт, как
    перемещения). Итерация 3 добавляет отмену СОЗДАНИЙ и ПРАВОК ПОЛЕЙ узлов и связей:
    снимок+restore стал универсальным примитивом структурного отката (создание/удаление
    и узлов, и связей — с сохранением исходных id; у связей свой снимок
    GET /edges/{id}/deletion-snapshot), а правка полей откатывается простым возвратом
    прежних значений (update). Покрыты все жесты создания связи и правка её концов
    (undo возвращает концы). Группировка одного жеста (мультидраг) сворачивается
    в одну команду, а компенсирующие вызовы
    защищены rollback-on-error (отказ записи → ресинк уровня из БД). Многопользо-
    вательские конфликты разруливаются optimistic CAS + поллингом (этапы 0+1 —
    в продукте, см. «Совместная работа: конкурентные сессии»); realtime (этап 2) —
    за пределами MVP.

Доступ к проектам (2026-10-01, docs/tasks/project-access.md)
Раньше любой вошедший видел и правил все проекты. Теперь доступ к проекту — по его
участникам; отдельных организаций в одной установке нет.
- Роли в проекте:
  - владелец — правит; управляет участниками и видимостью; переименовывает,
    архивирует, восстанавливает, удаляет; передаёт владение. Владелец у проекта
    ровно один, им становится создатель проекта;
  - редактор — правит схему, доки, процессы, факты, импорт в проект;
  - читатель — только смотрит и экспортирует.
- Общая роль решает, кем человек может быть в проектах (2026-10-18, решение владельца):
  «Архитектор» (architect) создаёт проекты (пустой, копия, единый импорт в новый
  проект) и бывает владельцем, редактором или читателем; «Пользователь» (viewer)
  только смотрит — в проекте он лишь читатель. Редактором его не назначить и проект
  ему не передать (409); в окне «Доступ» у него «Редактор» закрыт, в «Новый владелец»
  его нет. Понижение до «Пользователя» на экране «Пользователи» делает его
  редакторства чтением (обратное повышение их не возвращает), а владельцу проектов
  закрыто — сначала передать проекты. Внутри проекта права определяет только роль в
  нём: architect без роли редактора проект не правит. «Архитектор» и «наблюдатель» в описаниях страниц и холста — это
  права в открытом проекте: архитектор = владелец или редактор, наблюдатель =
  читатель. Интерфейс правки внутри проекта показывается по роли в проекте (my_role).
- Состав участников (окно «Доступ») видят редактор и владелец. Читателю его не
  показываем: у него на карточке проекта нет меню ⋯ (остался бы один пункт
  «Открыть»), ручка участников отвечает 403.
- Общая роль viewer в интерфейсе называется «Пользователь» (раньше «Наблюдатель»),
  чтобы администратор не путал её с ролью «Читатель» в проекте.
- Видимость: по умолчанию проект виден только участникам. Флажок «Виден всем
  пользователям» даёт остальным пользователям чтение.
- Администратор видит все проекты (в обеих вкладках) и в любом действует как
  владелец, включая участников и передачу владения.
- Недоступный проект для пользователя не существует: любая его ручка отвечает 404
  «Проект не найден», в том числе для архивного (доступ проверяется раньше архива).
  Копировать можно только проект, который пользователь видит.
- Карточка на лендинге: в меню ⋯ «Открыть» и «Доступ» — редактору и владельцу;
  «Редактировать», «Архивировать», «Восстановить», «Удалить навсегда» — только
  владельцу. У читателя меню ⋯ нет, меток роли на карточке нет ни у кого.
- Окно «Доступ к проекту» (не-владельцу — только для чтения, с пометкой «Менять
  доступ может владелец проекта.»): флажок «Виден всем пользователям» с подсказкой
  «Остальные пользователи смогут только смотреть»; список участников (логин, роль
  «Редактор» / «Читатель», «Удалить»); строка владельца с меткой «Владелец» и
  кнопкой «Передать владение» (выбор пользователя и подтверждение «Передать проект
  «{имя}» пользователю {логин}? Вы останетесь редактором.»); добавление: логин с
  подсказками из списка активных пользователей, роль, «Добавить». Почты и
  приглашений нет.
- Передача владения: новый владелец становится владельцем (не был участником —
  добавляется), прежний остаётся редактором; заблокированному передать нельзя.
  Владельца нельзя удалить или понизить — только передать владение.
- API: карточка проекта (ProjectResponse) несёт my_role, owner_username,
  visible_to_all; участники — GET/PUT/DELETE /projects/{id}/members[/{user_id}];
  передача — POST /projects/{id}/transfer; выбор участника — GET /users (активные
  пользователи, только id и логин, любому вошедшему).
- Обновление прежней установки (миграция): все существующие проекты видны всем;
  владелец — автор проекта, иначе первый администратор, иначе первый architect;
  все пользователи с общей ролью architect — редакторы каждого проекта.

Версионирование документации (2026-10-22, docs/tasks/doc-versions.md)
Версия — у ОБЪЕКТА: срез его документации (у контейнера — вместе с поддеревом),
который редактор фиксирует явно, с комментарием (номер версии, релиза или задачи,
по которой менялся код). Обычные сохранения между фиксациями в историю не
попадают.
- В срез входят свойства, связи (с путями концов для показа), схемы логики, спека
  OpenAPI, структура БД, каналы, конфигурация, статус страницы и процессы с
  участием объекта (размещение добавит эпик развёртывания). Раскладка холста в
  версию не входит. Снимок — zlib канонического JSON в таблице node_versions;
  «есть ли изменения с vN» решает хэш семантической проекции: пути чужих концов,
  рендер процессов и живые поля чужих узлов-участников в него не входят, поэтому
  переименование соседа ложного «есть изменения» не даёт.
- Панель «Версии документации» открывается пунктом ⋯-меню страницы объекта
  (меню видит и читатель — с пунктами просмотра) и показывает одно за раз: список
  версий (номер, комментарий, дата, автор) и строку «Есть изменения с vN: …» с
  кнопкой «Зафиксировать версию» (редактор); что изменилось в версии — список
  элементов (свойства, статус страницы, связь, схема логики, OpenAPI, таблица,
  канал, конфигурация, процесс) со сравнением «с vM» или «с текущим состоянием»;
  одну дельту — с переключателем «Изменения · Было · Стало» (построчная дельта
  текстов, таблица «поле · было · стало» у свойств, строки с пометками у фактов,
  связей и шагов процесса; изменённая ячейка — зачёркнутое «было» и «стало»). Так
  же читают старую версию. Сопоставление по id: переименование — изменение, а не
  удаление с созданием. Версию удаляет владелец проекта, номера не сдвигаются.
- Откат («Восстановить эту версию», редактор) возвращает документацию объекта к
  версии в одной транзакции и пишет историю вперёд: незафиксированное — версией
  «Перед откатом к vN», итог — версией «Откат к vN». Объекты, появившиеся после
  версии, удаляются (окно подтверждения называет их число); связь к исчезнувшему
  чужому объекту и прежний родитель, которого больше нет, остаются замечаниями.
  Процессы (общие с другими объектами) и статус страницы (им управляет человек)
  откат не трогает; откат к версии без отличий — отказ «Нечего восстанавливать».
  Личному токену откат закрыт. Страница сразу перечитывает документацию.
- Страница проекта — корень: та же кнопка ⋯ → «Версии документации» фиксирует и
  откатывает срез всего проекта. Демо-проект — до 30 версий.
- Агент по MCP (v0.7.0): `archmap_versions` (список и «есть изменения»),
  `archmap_version_diff` (элементы дельты и текст одного элемента),
  `archmap_version_doc` (схема, спека или процесс на версии);
  `archmap_version_create` — пишущий инструмент, только по явной просьбе
  человека; отката у агента нет.

Статус страницы (2026-10-22, docs/tasks/page-status.md)
У страницы объекта есть статус «в работе» (жёлтая пилюля рядом с именем в шапке)
или «согласовано» (зелёная). Новые объекты — «в работе». Статус жизненного цикла
объекта (существует / планируется / выводится) — отдельное понятие и остаётся как
есть.
- Контейнер (лист или с компонентами), компонент и «Пользователь» — свой статус
  (решение Р14 эпика «Элемент архитектуры», 2026-10-29): редактор проекта (владелец
  или редактор) открывает выпадашку пилюли и выбирает «В работе — страница ещё
  правится» или «Согласовано — проверено редактором» (текущий отмечен галочкой);
  читатель видит пилюлю без стрелки, с подсказкой «Статус меняет редактор проекта».
- Система: статус не хранится, а складывается из вложенных объектов любой глубины,
  кроме вложенных систем, — контейнеров, компонентов и «Пользователей» (внешние
  считаются наравне): «согласовано», когда согласованы ВСЕ они. Пилюля несёт счётчик
  «· N из M» и подсказку «Статус системы складывается из вложенных объектов»; клик по
  ней (обе роли) открывает их список с жёлтой или зелёной точкой, строка ведёт на
  страницу объекта. Поставить статус системе руками нельзя: PATCH с approval отвечает
  422 «Статус системы складывается из вложенных объектов» (элемент — по дереву после
  правки: запрос, делающий систему контейнером, статус принимает). Система, оставшаяся
  без детей, снова контейнер и показывает прежний сохранённый статус. При элементе
  null (все проекты до эпика) это прежнее «узел с детьми — по всем детям».
- Правка документации статус не сбрасывает — им управляет человек. Смена статуса —
  правка меты страницы (курсор meta_rev): страница в другой сессии освежается, у
  страницы системы перечитываются вложенные объекты.
- API: NodeResponse несёт approval (хранимое) и approval_effective (вычисленное;
  у всего, кроме системы, совпадает) во всех выдачах узлов, включая граф уровня и контекст-схему;
  NodeUpdate принимает approval. Снимок удаления (Undo) и копия проекта статус
  переносят.
- MCP: карточка archmap_node печатает «Статус страницы: …» (у системы — «складывается
  из вложенных объектов, согласовано N из M» по тем же объектам, что пилюля);
  archmap_update_node принимает approval — агент ставит его только по явной просьбе
  человека и только у контейнера или компонента.
- Отложено: точки статуса в дереве объектов и счётчик на странице проекта, статус в
  экспорте и архиве знания. На холсте и в archmap_schema статус не показывается.

Элемент архитектуры (эпик 2026-10-29 в работе, docs/plan-c4-elements.md)
Узел с детьми — система (группа контейнеров, сама не запускается) или контейнер
(запускается отдельно, вложенные объекты — его компоненты). Сделано в фазах Ф1–Ф2, Ф3а, Ф3б, Ф4, Ф5, Ф6, Ф7 и Ф8:
- Поле element (system | container | null) хранится у узла; null — «не сказано» и
  читается как сегодня. Действующий элемент element_effective считает сервер и отдаёт
  во всех выдачах узла: ручки /nodes, граф уровня (локалы, гости и их предки),
  контекст-схема, граф развёртывания. Внутри контейнера все объекты — компоненты, в том
  числе составные; лист вне контейнера — контейнер; у «Пользователя» элемента нет.
- POST и PATCH /nodes принимают element, null очищает (всегда можно). Отказы 422 (на
  смену значения): элемент задаётся только у сервиса; у объекта внутри контейнера не
  задаётся — он компонент; внутри контейнера не может лежать база данных или брокер
  (текст: «Внутри лежит база данных «…», она не может входить в состав контейнера.
  Вынесите её на уровень выше и повторите.») и другой контейнер. У листа значение
  хранится как намерение и срабатывает с первым вложенным объектом. «Пользователь»
  внутри контейнера отказом не считается. Смена элемента — правка схемы (graph_rev).
- Копия проекта, снимок удаления (Undo) и версии документации переносят element; дельта
  версий показывает строку «элемент архитектуры», откат версии возвращает значение.
- MCP: archmap_create_node и archmap_update_node принимают element (пустая строка
  снимает), карточка archmap_node печатает «Элемент архитектуры: …» (у компонента — с
  именем контейнера), дерево archmap_schema помечает контейнер с компонентами.
- Форматы обмена (Ф2): экспорт YAML и c4.yaml архива пишут `element:` сразу после
  `shape:` и только заданный (проект без элементов экспортируется прежними байтами;
  формат архива не поднят). Импорт разбирает поле (чужое значение — ошибка, как у
  формы); недопустимое значение файл не валит, а снимается с замечанием: у не-сервиса
  («элемент архитектуры задаётся только у сервиса — значение пропущено»), у объекта
  внутри контейнера («… считается его компонентом — элемент архитектуры пропущен»). У
  листа-сервиса значение берётся как есть (намерение). База данных или брокер внутри
  контейнера (и глубже, в его компонентах) выносится на уровень выше — к родителю
  контейнера, у корневого — на верхний уровень; контейнер остаётся контейнером
  (решение владельца Р6). Замечание: «Путь контейнера: внутри лежит база данных «…»,
  она не может входить в состав контейнера — вынесена на уровень выше, в «Путь
  родителя»» (или «— вынесена на верхний уровень»). Вынесенный объект едет со своим
  поддеревом, без своего размещения берёт площадки ближайшего узла на пути до
  контейнера; файлы семей архива находят его по адресу, как его записал C4 архива.
  Вложенных объектов у базы данных, брокера и «Пользователя» не бывает (Ф5): ввоз
  поднимает их детей с поддеревьями к родителю такого объекта с замечанием «Путь: у
  базы данных «orders-db» вложенных объектов не бывает — «orders-schema» поднят на
  уровень выше, в «Путь родителя»» («у брокера», «у пользователя»); подъём идёт первым,
  поднятый дальше проверяется по новому месту, без своих площадок берёт объявление
  прежнего родителя (если тот не внутри контейнера). Разбор, слияние, единый ввоз и
  архив идут одной функцией.
- Мердж нескольких файлов: «не задан» уступает любому значению; «система» против
  «контейнера» — спор поля по правилу П2 (содержательный вклад побеждает, при равной
  содержательности — вопрос «спор поля» в превью с подписями «Система»/«Контейнер»);
  слитое дерево проверяется теми же правилами, и замечание «контейнер по файлу N, а
  файл M положил внутрь объекты (…), не зная, что это контейнер — они стали его
  компонентами; проверьте, не система ли это». База из одного файла в контейнере из
  другого выносится так же, пути слитого дерева — уже по новому месту. Ответ
  «Контейнер» на вопрос о споре выносит базу при применении (пункт отчёта); склейка
  «это один объект» переносит выжившему детей и элемент поглощённого ещё до записи, и
  те же правила видят дерево после неё.
- Догрузка архивом и синк из репозитория — только в пустое: живое «не задан» доливается
  после проверки теми же правилами по живому дереву (отказ — строкой отчёта), заданное
  живое не трогается, другое значение во входе — строкой отчёта («в архиве другое … —
  оставлено живое», «в YAML элемент архитектуры другой … — в схеме оставляем как
  есть»). Новые объекты создаются с элементом из входа как есть. Живое дерево ввоз не
  перестраивает: новая база из архива в живом контейнере создаётся у его родителя
  (замечание с путём), а живая база в контейнере, который предлагает архив, остаётся на
  месте — контейнер тогда не ложится («— объект оставлен системой»). Синк, получив базу
  или брокер внутри живого контейнера (или его компонента), матчит и создаёт их у
  родителя контейнера со строкой плана ««…»: база данных не может входить в состав
  контейнера «…» — будет создана уровнем выше, в «…»» (на повторном прогоне — «в схеме
  она лежит уровнем выше…»); база, уже лежащая в живом контейнере, находится на месте.
  Галочка «Обновлять компоненты контейнеров» для этого не нужна: база и брокер
  компонентами не бывают и остаются в зоне синка (Ф6, ниже); база в компоненте, которого
  синк без галочки не трогает, пропускается вместе с ним. Фикспойнт синка сохраняется.
- Конфигурация и спецификация — факты контейнера (Ф3а). Пометка «зависит от:» ищет
  параметр только у ближайшего контейнера владельца схемы: у контейнера и у листа вне
  контейнера — у него самого, у компонента — у контейнера-предка; свой параметр
  компонента пометкой не находится, у схемы системы искать негде. Плашка редактора
  схемы у компонента подписывает цель «Конфигурация «orders» · X». Обратный индекс
  параметра (GET /nodes/{id}/config/usage) — схемы контейнера и всех его компонентов;
  строка несёт владельца схемы (node_id, node_name), и под параметром «зависит:» схема
  компонента называется с его именем; у компонента и системы индекс пуст. Замечание
  «Обращения к неописанным параметрам» (AL33) несёт контейнер, где искали
  (container_id, container_name; у системы — пусто), и текст панели и MCP называет его:
  «параметра нет в конфигурации контейнера «X»…», у системы — «схема у системы, а
  параметры живут у контейнера…». Промпт доков со страницы компонента перечисляет
  параметры контейнера-предка, без среза — всех контейнеров. Превью доков называет
  контейнер в заметках о конфигурации. Ввоз конфигурации предлагает адресами
  контейнеры (лист вне контейнера и контейнер с компонентами); у системы и компонента
  — предупреждение с местом параметров, записи применяются как есть. Спецификация из
  пакета доков с адресом компонента (и голая спецификация из окна компонента) едет его
  контейнеру со строкой превью; окно компонента допускает адрес своего контейнера у
  записи только со спецификацией; две спецификации от компонентов одного контейнера —
  конфликт «уже задана файлом»; у системы — предупреждение, спецификация остаётся у
  неё. Предупреждения о схемах логики (доки, разведка) — словами элемента: «— система»
  или «— контейнер с компонентами», с отсылкой к «Рекомендациям».
- Рекомендации и статус страницы по элементу (Ф3б). «Системы и контейнеры со своей
  документацией» (AL24): у системы — замечание на свои схемы логики, спецификацию и
  конфигурацию, у контейнера с компонентами — только на схемы логики; запись несёт
  element_effective, панель и MCP дают совет по нему. Новый класс «Конфигурация и
  спецификации у компонентов» (component_facts, AL36): компонент со своей спецификацией
  или параметрами, с контейнером, где им место; всего классов 16. Заголовки «Связи в
  систему или контейнер», «Связи с собственной частью», «Пользователи внутри системы»;
  правила связей прежние. Статус страницы (Р14): свой у контейнера (в том числе с
  компонентами), компонента и «Пользователя», у системы складывается из всех вложенных
  объектов, кроме вложенных систем, PATCH у системы — 422 «Статус системы складывается
  из вложенных объектов»; пилюля и карточка MCP — по элементу (раздел «Статус страницы»).
- Размещение по единицам (Ф4, решения Р16/Р17). Единица размещения — контейнер: лист вне
  контейнера или контейнер с компонентами; площадки хранит только он. У компонента
  размещения нет: PUT /deployment/placements, PATCH site_ids и MCP отказывают 422
  «Площадки задаются контейнеру: «api» — компонент контейнера «orders»» (молча
  контейнеру не переадресуется), ввоз YAML с sites у компонента отбрасывает их с
  замечанием «путь: размещение задаётся контейнеру «orders» — площадки у компонента
  пропущены». Система размещается целиком — набор получают её контейнеры (сквозь
  вложенные системы), её размещение складывается из них; система без контейнеров — 422
  «В «X» нет объектов, которые можно разместить». Экспорт пишет sites у контейнера, у
  цельной системы — у неё самой; объявление системы при ввозе и догрузке достаётся её
  контейнерам. Холст «Развёртывание»: контейнер — всегда одна сплошная карточка на
  площадку без числа внутри, компоненты не рисуются (их связи идут от контейнера),
  пунктир и число — только у цельной системы (число её контейнеров); уровня контейнера
  нет — адрес такого уровня отвечает «Внутри контейнера «orders» отдельного размещения
  нет: компоненты развёртываются вместе с ним». Дерево слева открывает уровень только у
  системы, щелчок по компоненту показывает карточки его контейнера, булавки у
  компонента нет (с Ф8 компонентов в этом дереве нет, контейнер — строка без шеврона;
  компонент находит только поиск). Подтверждения у системы (тексты Ф8) — «Все контейнеры
  системы будут размещены там же, включая те, что сейчас стоят на других площадках:» и
  «Размещение всех контейнеров системы будет снято:»; окно «Размещение» пишет набор её контейнерам. Экземпляры,
  оставшиеся у узла, ставшего компонентом, не считаются нигде; их показывает
  рекомендация «Конфигурация и спецификации у компонентов» («площадки»). MCP:
  archmap_deployment считает контейнеры («целиком, N объектов» — у системы), у
  компонента с node_id — «Размещения нет: это компонент — площадки задаются контейнеру
  «orders»»; sites у archmap_update_node — контейнеру или системе целиком.
- Запреты вложенности на сервере (Ф5, Р6). Создание объекта внутри базы, брокера или
  «Пользователя» — 422 «Внутрь этого объекта нельзя вкладывать другие — детей не бывает»
  (раньше POST /nodes проверял только, что родитель есть). База данных и брокер не входят
  в состав контейнера ни при создании (422 «База данных «orders-db» не может входить в
  состав контейнера «orders». Создайте её на уровне выше.»), ни при переносе самой базы
  или поддерева с ней и смене формы (400, тексты — спека docs/specs/node.md N4б); проверка
  — по дереву после правки. Дерево не принимает базу и брокер, брошенные в компонент, в
  контейнер с компонентами и в лист с элементом «контейнер».
- Окно первого вложенного объекта (Ф5, Р4). Сервис-лист без элемента, получая первый
  вложенный сервис (кнопка «+» в дереве, бросок на холст его уровня, перенос в дереве),
  сначала спрашивает «Внутри «X» появился первый объект»: «Контейнер» — одно приложение,
  запускается целиком, объекты внутри описывают, из чего оно состоит, документация и
  площадки остаются у X; «Система» — несколько приложений, у каждого свои документация и
  площадки. Предвыбор — «Контейнер», если у листа есть спецификация, площадки или
  параметры конфигурации, иначе «Система». «Продолжить» записывает элемент и продолжает
  действие, «Отмена» ничего не меняет. Первой вложенной базе, брокеру или «Пользователю»
  лист становится системой без вопроса; компонент окна не получает; обучающий тур задаёт
  систему явно. Окно появляется до окна «Новый объект», а не поверх него.
- Строка «Элемент архитектуры» в инспекторе и «Свойствах» (Ф5, Ф8). Редактору у объекта
  с вложенными — выпадашка «Система» («группа контейнеров, сама не запускается») /
  «Контейнер» («запускается отдельно, внутри его компоненты»); иначе текстом: лист —
  «Контейнер», внешний лист — «Внешняя система», компонент — «Компонент контейнера
  «orders»» с именем-ссылкой на страницу контейнера (ответ узла несёт вычисляемое
  container_name, id контейнера интерфейс берёт из цепочки предков: крошки страницы,
  крошки редактора с раскрытой рамкой, путь гостя; цепочка разошлась — имя текстом), у
  «Пользователя» строки нет. У термина — «?» «Что такое система, контейнер и компонент»:
  четыре абзаца («Контейнер.», «Компонент.», «Система.», «Как выбрать.»). У объекта с
  вложенными строки «Тип» нет (форма всегда «Сервис»), «Элемент архитектуры» — первая
  строка; у листа — сразу под «Типом». Сводная технология потомков (только чтение) —
  только у системы, у контейнера с компонентами и составного компонента технология своя
  и правится. Подсказка поля «Роль» — «API, воркер, шлюз…». Инспектор гостя — та же
  строка текстом.
- Смена элемента и перенос с последствиями (Ф5, Р18). GET /nodes/{id}/element-preview
  ?element= и GET /nodes/{id}/move-preview?parent_id= (редактор) отвечают видом
  последствия (система → контейнер, контейнер → система, вход в контейнер, выход из
  него), площадками до и после по объектам и именами тех, чья документация окажется не
  на месте. Есть последствия — окно «было → стало» («Сделать «orders» контейнером?»,
  «Сделать «orders» системой?», «Сделать «api» частью «orders»?», «Сделать «api»
  отдельным приложением?») с разделами «Площадки» и «Документация», запись — после
  подтверждения и без Undo (обратное действие — та же смена или перенос назад со своими
  последствиями); без последствий — обычная правка. PATCH переносит размещение в той же
  транзакции: контейнер занимает объединение площадок своих частей, а их экземпляры
  снимаются; при обратной смене каждая новая единица получает площадки бывшего
  контейнера; входящий в контейнер отдаёт свои площадки контейнеру, вышедший получает
  площадки контейнера. Документация сама не переезжает — её отмечают рекомендации, а
  переносят кнопки ниже.
- «Перенести документацию» и «Собрать с компонентов» (Ф5, Р19). POST
  /nodes/{id}/docs/distribute (путь прежний): получатели — сервисы в поддереве узла на
  любой глубине; схемы логики — компоненту (в том числе составному) или сервису без
  вложенных вне контейнера, спецификация — потомку-контейнеру, все собственные параметры
  конфигурации (params_target_id) — одному потомку-контейнеру; база, брокер и
  «Пользователь» не получатели ничего. Отказы словами продукта: 404 «Схема не найдена
  среди собственных схем объекта», 409 «Получатель не входит в состав объекта», «У «api»
  уже есть схема «…»», «У «orders» уже есть спецификация», «У «orders» уже есть параметр
  «…»», 422 «Схемы логики переносятся компонентам и объектам без вложенных, а «X» —
  система.» (и о спецификации, конфигурации — «… только контейнеру»). Окно «Перенести
  документацию»: у системы — схемы логики, спецификация и конфигурация («2 параметра» →
  контейнер или «Не переносить»), у контейнера с компонентами — только схемы; получатели
  подписаны путём от объекта («orders / api»); кнопка — в «Логике», у системы ещё в
  «OpenAPI» и «Конфигурации». Обратное — GET /nodes/{id}/facts/collect-preview и POST
  /nodes/{id}/facts/collect: параметры компонентов переезжают контейнеру, одноимённые —
  один параметр, остаётся выбранное описание («Одинаковые имена: X у api и checkout.
  Какое описание оставить?»), спецификация — выбранная («Спецификаций несколько. Какую
  отдать «orders»?»), прочие остаются у компонентов; у не-контейнера — 422 «Собирать можно
  только контейнеру с компонентами». Кнопка «Собрать с компонентов» — в «Конфигурации» и
  «OpenAPI» контейнера, только когда по этой части есть что собирать.
- Первый вложенный объект у листа с размещением (Ф6, правило 5 D34). Лист вне
  контейнера со своими площадками, получив первого ребёнка и став системой (элемент не
  задан или «система»), отдаёт площадки единицам нового поддерева: каждая добавляет их к
  своим, у листа экземпляры снимаются. При создании ребёнка (POST /nodes) — в той же
  транзакции, без окна: окно первого вложенного объекта уже обещает, что площадки
  ведутся у вложенных. При переносе в такой лист — превью move-preview вида first_child
  и окно «Перенести «api» в «orders»?»: ««orders» станет системой из вложенных
  объектов, и его площадки перейдут к ним.», под таблицей площадок — ««api» получит
  площадки «orders». Лишние можно убрать на холсте «Развёртывание».», кнопка
  «Перенести». Если переносимое при этом выходит из контейнера, площадки прежнего
  контейнера и листа объединяются. Лист с элементом «контейнер» становится контейнером с
  компонентом — переноса нет; первому вложенному «Пользователю» площадки не переходят.
- Синк по элементу (Ф6). Без галочки «Обновлять компоненты контейнеров» синк не трогает
  компоненты — всё, что лежит внутри контейнера, на любой глубине: объект прогона вне
  зоны, если над ним в прогоне объект с элементом «контейнер» или ближайший сопоставленный
  живой предок — контейнер (заданный элемент) или его компонент; «пропавшими» считаются
  только живые объекты не внутри контейнера. База и брокер компонентами не бывают: под
  живым контейнером они в зоне и без галочки и выносятся уровнем выше (Р6, см. выше),
  живая база прямо в контейнере тоже в зоне. Системы вкладываются друг в друга сколько
  угодно и в зоне на любой глубине. Если элемент не задан нигде — ни в прогоне, ни в
  проекте (старые проекты и YAML), — зона прежняя, по глубине прогона (корень и его
  дети). Подсказка галочки: «Затрагивать не только контейнеры (сервисы, базы, брокеры),
  но и их компоненты. По умолчанию выключено: компоненты агент описывает менее надёжно, и
  такие изменения обычно только мешают увидеть главное.»
- Слова превью ввоза по элементу (Ф6). Замечание и вопрос о связи в объект с вложенными
  (правило прежнее) говорят словами его действующего элемента в слитом дереве. Система:
  «связь «A → Торговля»: конец в системе «Торговля», у которой есть вложенные объекты, —
  уточните её до одного из них: «Торговля / catalog», «Торговля / orders»»; вопрос
  «Связь «A → Торговля» приходит в систему «Торговля». С каким объектом внутри системы
  «Торговля» связан объект «A»?» (контекст «внутри N объектов, считая вложенные»),
  вариант «Оставить на системе «Торговля»», краткий ответ «на системе». Контейнер —
  прежние слова с компонентами, пояснение «В одном файле «orders» описан одним объектом,
  а в другом у него есть компоненты. После слияния он станет контейнером, а вызовы
  принимают его компоненты. Конец связи нужно перевесить на один из них.». Оба конца — с
  согласованием («оба конца в системе «A» и контейнере «B», у которых есть вложенные
  объекты, — уточните её до вложенных объектов: …»). Объект с вложенными без элемента в
  файлах — система, и так и называется. Группа вопросов — «В систему или контейнер»;
  теги в списках разбора — «система» / «контейнер» по элементу. Контракт:
  ContainerEdgeOut.container_element, ComponentOut.element_effective,
  RemainderOut.node_elements.
- Вопрос «похоже на контейнер» (Ф6, Р7). Подсказка — не запись, а вопрос превью ввоза
  (создание и догрузка; в догрузке только о новых объектах), когда у объекта нет поля
  element во входе и сработал строгий признак: у него источник кода с путём
  (`git:repo#path`), и каждый прямой вложенный объект — сервис того же репозитория с
  путём внутри этого каталога и без имени зависимости; база, брокер, «Пользователь» и
  объект без источника кода признак гасят. Тексты: «Похоже, «orders» — контейнер с
  компонентами. Отметить его контейнером?», контекст «api, checkout, scheduler лежат в
  services/orders того же репозитория» (шесть имён, дальше «…ещё N»), варианты
  «Контейнер» (по источникам) и «Система» (как сейчас), группа «Контейнеры» после
  «Полей». Ответ «Контейнер» отмечает объект до записи — дальше обычные правила ввоза
  (база внутри выносится выше, у компонентов площадки снимаются); строка отчёта «Ваши
  решения: отмечено контейнерами N». Контракт: RemainderOut.container_hints
  (ContainerHintOut), раздел решений container_hints {id: container | system}. На
  демо-пакете вопрос не возникает.
- Холст объектов по элементу (Ф7, Р20/Р21). Рамка раскрытого объекта и рамка уровня —
  пунктир у всех; у контейнера она залита его цветом по палитре глубины (тот же цвет, что
  у свёрнутого объекта, непрозрачность 8 %), у системы и составного компонента —
  прозрачная, как прежде. Плашки рамок прежние («🔍 имя ✕», без названия элемента);
  сплошная граница с заливкой — по-прежнему только у площадки холста «Развёртывание»,
  рамок контейнеров там нет. Свёрнутый предок гостя подписан своим элементом —
  «система», «контейнер» или «компонент» (до Ф7 — всегда «контейнер»). Кнопка входа на
  слой объекта с вложенными: у системы «Войти», у контейнера и составного компонента —
  «Войти к компонентам» (у своего объекта, гостя и свёрнутого предка одинаково; у объекта
  без вложенных — «Войти»). Бейдж числа вложенных: у системы — глиф-дерево, у контейнера
  и составного компонента — четыре квадратика «компоненты»; число — прямые вложенные, как
  прежде. Подсказка неактивной лупы на пределе глубины: «Раскрывать вложенное можно
  только два раза подряд. Чтобы увидеть состав этого объекта, войдите в него». Цель
  протяжки связи, зона входа и выбор вложенного объекта — без изменений (Р22).
- Страница объекта по элементу (Ф8, Р34). Документацию потомков (схемы логики и
  спецификации группами по прямым вложенным) собирают только контейнер с компонентами и
  составной компонент; страница системы её не показывает (статус системы по-прежнему
  складывается из её единиц). «Логика»: у системы, контейнера с компонентами и
  составного компонента своих схем быть не должно — есть, значит предупреждение («У
  системы остались собственные схемы логики. Схемы описывают код, их место у
  контейнеров и компонентов», «У контейнера есть свои схемы логики. Схемы описывают код,
  их место у компонентов», у составного компонента — «У компонента есть свои схемы логики. Схемы описывают код,
  их место у вложенных компонентов») и «Перенести
  документацию», меню «+ Добавить» нет; пусто — «Это система, своих схем логики у неё
  нет. Схемы логики описывают у её контейнеров и компонентов» или «Схемы логики
  компонентов появятся здесь, когда их опишут»; подзаголовок групп — «Схемы
  компонентов». «OpenAPI»: у контейнера своя спецификация, как у объекта без вложенных
  (меню «+ Добавить», без предупреждения), при компонентах ниже — «Спецификации
  компонентов» с пометкой «Спецификацию отдаёт контейнер целиком, у компонентов она не
  на месте» и «Собрать с компонентов»; у системы — «Это система, своего API у неё нет.
  Спецификации описывают у её контейнеров», старая своя — «У системы осталась
  собственная спецификация. API отдают контейнеры, перенесите её одному из них» и
  «Перенести документацию»; у компонента — «API этого компонента отдаёт контейнер
  «orders», спецификация описана у него» и «Открыть спецификацию» (страница контейнера;
  нет спецификации — «…спецификация пока не описана», без кнопки), ниже «Операции
  компонента» — его схемы логики с привязкой к операции (нет — «Схемы логики этого
  компонента не привязаны к операциям спецификации»), старая своя — «Спецификацию
  отдаёт контейнер целиком. Перенесите её в «orders»: на его странице есть кнопка
  «Собрать с компонентов»». «Конфигурация»: у системы меню «+ Параметр» нет, пусто — «Это
  система, своей конфигурации у неё нет. Параметры описывают у её контейнеров», старые
  параметры — «Конфигурацию читают контейнеры, у системы её нет. Перенесите параметры
  одному из них» и «Перенести документацию»; у контейнера с компонентами «?» «Зависит
  от» говорит о схемах «этого контейнера и его компонентов»; у компонента — «Конфигурацию
  читает контейнер «orders», параметры описаны у него» с «Открыть» и строка «Схемы этого
  компонента зависят от: A, B» (обратный индекс контейнера по схемам компонента), старые
  свои параметры — «Конфигурацию читает контейнер целиком. Перенесите параметры в
  «orders»: на его странице есть кнопка «Собрать с компонентов»», без «+ Параметр».
  «Размещение»: у компонента — площадки контейнера и серым «как у контейнера «orders»»
  (имя — ссылка), без «Изменить», редактору мелко «Компонент размещается вместе с
  контейнером»; у системы частичная площадка — «часть контейнеров». Кнопка пустой схемы
  объекта — «Добавить компонент» у контейнера и внутри него, иначе «Добавить вложенный
  объект». Окно «Размещение» одной системы — подзаголовок «<имя> · площадки получат все
  контейнеры системы», ошибка «Не удалось загрузить контейнеры системы.»; подтверждения
  размещения и снятия у системы — «Все контейнеры системы будут размещены там же, включая
  те, что сейчас стоят на других площадках:» и «Размещение всех контейнеров системы будет
  снято:». Составной компонент в «OpenAPI» показывает спецификации вложенных той же
  группой с пометкой, кнопки «Собрать с компонентов» у него нет.
- Дерево объектов и глифы (Ф8). Глиф строки дерева, результата поиска, пикеров, шапки
  страницы и инспекторов — по элементу (types/treeNesting): система и составной
  компонент — пунктирный скруглённый прямоугольник, контейнер с компонентами — «коробка
  с крышкой», объект без вложенных — глиф формы. Подсказка «+» в строке — «Создать
  компонент внутри «orders»» у контейнера и внутри контейнера, иначе «Создать объект
  внутри «X»». В режиме «Развёртывание» компонентов в дереве нет: ветка контейнера не
  раскрывается и не грузится, контейнер — строка без шеврона (булавка у систем и
  контейнеров). Перенос строк — только в редакторе, через превью последствий Ф5.
- Легенда холста (Ф8). Раздел «Обозначения»: на холсте объектов — «Объект с другого
  уровня», «Рамка системы» (серый пунктир), «Рамка контейнера» (тот же пунктир с
  заливкой цвета глубины); на холсте «Развёртывание» к прежним строкам добавлена
  «Система целиком на площадке» (пунктирная карточка).
- Тексты словами элемента (Ф8). «Переразложить»: «…Раскрытые системы и контейнеры
  останутся раскрытыми, их содержимое разложится заново…»; справка источника —
  «перенесённый в другую систему сервис», «Объект без источника опознаётся только по
  имени среди соседей по уровню»; превью входа — «система «Сервис заказов» раскрывается
  и сворачивается», подпись свёрнутого узла «система»; пилюля живой схемы лендинга —
  «Нажмите, чтобы двигать объекты и заглядывать внутрь систем» (сборка лендинга — Ф11);
  тур: шаг 7 — «Внутри его контейнеры: API, база данных и воркер. Каждый из них
  запускается отдельно. Свернуть можно крестиком у названия рамки.», шаг 21 — «Внутри
  системы «{system}» появился сервис. Система только объединяет то, что внутри, и вызовы
  принимает не она, а её сервисы.»
- При element = null у всех узлов все объекты с вложенными читаются системами: холст и
  дерево — как прежде, а страница такого объекта документацию потомков больше не
  собирает (Р34).

Схема развёртывания (2026-10-22, ТЗ docs/tasks/deployment-view.md, спека холста docs/specs/deployment.md)
Третий режим рядом с «Объектами» и «Процессами». Площадка (облако, кластер
Kubernetes, виртуальная машина, физический сервер, другое) — сущность проекта с
возможной вложенностью (облако → кластер). Объект стоит на площадках
ЭКЗЕМПЛЯРАМИ — на одной или нескольких; размещение хранится только у единиц —
контейнеров (лист вне контейнера или контейнер с компонентами; с 2026-10-29, эпик
«Элемент архитектуры», Ф4), у компонента размещения нет; система — это её контейнеры:
она размещается целиком (её площадки получают все контейнеры внутри), а её
собственное размещение складывается из их размещения (решение 2026-10-27,
наследования нет). Холст режима показывает объекты
выбранного уровня (поддерево системы, по умолчанию весь проект), сгруппированные
по площадкам в ЗОНЫ — области с лёгкой заливкой и тонкой светлой границей (вложенная
площадка — зона в зоне, заливки складываются). Система, все контейнеры которой стоят
на одном наборе площадок, рисуется ЦЕЛЬНОЙ карточкой, иначе — своими объектами;
контейнер — всегда одной карточкой, его компоненты не рисуются; контейнер или
цельная система с несколькими экземплярами рисуется в каждой зоне с
пометкой «1/2»; связи идут между экземплярами — от каждого экземпляра источника к
ближайшим экземплярам цели (ближе экземпляр на той же площадке, затем — с которым
длиннее общая цепочка площадок-предков; равноудалённые — все); объекты без размещения
— в пунктирной группе
«Размещение не указано».
Размещение задаётся булавкой на строке дерева объектов слева и щелчком по площадке на
холсте, мультивыбором на холсте и кнопкой «Указать размещение» (набор площадок
галочками, новая площадка с родителем, снять размещение) или со страницы объекта.
Система размещается целиком: её площадки получают все контейнеры внутри; компоненту
площадки не задаются — только его контейнеру. Площадки и экземпляры едут в экспорт, архив, версии и MCP; сред
(прод/стейдж) нет — одна целевая топология.
- Режим «Развёртывание» (сделано, Ф2): третья вкладка переключателя в шапке
  проекта. Тулбар: путь уровня текстом (с Ф6; уровень выбирают в дереве слева), «Площадки» (окно
  с деревом площадок: у каждой строки шеврон, свёрнуто по умолчанию, под раскрытой —
  вложенные и «+», под корнями — свой «+»; «+» раскрывает форму новой площадки на
  месте, родитель — где нажали, поля «Внутри площадки» у создания нет; редактору в
  строке карандаш и корзина — изменить (в форме правки родитель меняется), удалить с
  подтверждением, площадку с вложенными удалить нельзя), «Переразложить» (редактор) и тумблер
  «Подписи связей» — все три квадратными иконками справа в тулбаре. Холст — тот же, что у схемы объектов: рамки, драг,
  сохранение расположения, отмена, анимации, автоматические стрелки. На плашке
  площадки — иконка вида, имя и технология. Двойной клик по карточке объекта —
  страница объекта. Цвет карточки — как на схеме объектов: по глубине объекта в
  дереве архитектуры, а не по вложенности площадок (приёмка 2026-10-27). Связи — как на
  схеме объектов (приёмка 2026-10-27): двойной клик по стрелке или клик по её подписи
  подсвечивает связь и оба её объекта; если на общем участке несколько связей — окно
  «Выберите связь»; двойной клик по пустому месту снимает подсветку.
- Выделение (Ctrl/⌘+клик или рамка) у редактора открывает панель «Выбрано N
  объектов · Указать размещение · Снять выделение»; карточки того же объекта в
  других рамках подсвечиваются. Окно «Размещение»: галочка — площадка у всех
  выбранных, частичная — у части (нетронутая остаётся у каждого как была); у
  контейнера галочки — по его объектам (частичная — стоит часть); дерево то же, что в
  окне «Площадки» (шевроны, «+» под площадкой и под корнями), раскрыты сразу предки
  площадок, где стоят выбранные; новая площадка отмечена сразу; «Убрать размещение»
  снимает размещение (у контейнера — у всех объектов внутри, после вопроса со списком).
  Читатель видит холст и площадки без правки.
- Холст по решениям 2026-10-23 (сделано, Ф5). Уровень — ОБЪЁМ: поддерево контейнера
  (сам контейнер не рисуется), площадки те же на любом уровне, связи только внутри
  объёма. Уровень живёт в адресе `#/p/<проект>/deploy/<контейнер>`: «назад» браузера
  возвращает прежний уровень, а запомненный режим открывает проект сразу в
  «Развёртывании». Цельный контейнер (у всех объектов внутри одинаковый набор
  площадок, «не указано» — тоже набор) — одна карточка в каждой площадке набора с
  числом объектов внутри и пунктирным контуром; иначе он рассыпается до детей, и
  правило повторяется вглубь. Контейнеры на этой схеме не раскрываются: двойной клик
  по карточке контейнера — вход в его уровень. Площадка — зона с заливкой; клик по
  плашке сворачивает её в карточку площадки (иконка вида, имя, число объектов на ней
  на этом уровне, лупа): стрелки упираются в карточку, связи внутри свёрнутой
  прячутся; лупа или двойной клик раскрывает. Свёрнутость редактор сохраняет в виде,
  читатель — на сессию; «Переразложить» сбрасывает расстановку, но не свёрнутость.
  Пустая на уровне площадка — та же карточка без лупы.
- Страница объекта (сделано, Ф3): строка «Размещение» в «Свойствах» перечисляет
  площадки, где стоит объект (у вложенной — «в <родитель>»; у контейнера — площадки
  его объектов, где стоит часть — «часть объектов»; пусто — «не указано»; у
  «Пользователя» строки нет);
  редактор по «Изменить» открывает то же окно «Размещение» для этого объекта.
- Экспорт, импорт и архив (сделано, Ф4): YAML схемы несёт раздел `deployment:
  {sites: [{name, kind, technology, description, parent}]}` (родитель — именем) и у
  объекта `sites: [имена]`; контейнер, все объекты которого стоят на одном наборе
  площадок, пишет `sites` сам, а его поддерево — нет (импорт раздаёт объявление
  контейнера объектам без своего); экспорт поддерева берёт площадки его объектов с
  предками.
  Импорт принимает площадки по имени; площадка, названная объектом без объявления,
  создаётся с видом «другое» и замечанием. Ввоз нескольких входов склеивает площадки
  по имени (вид — у первой объявившей, расхождение — замечанием); догрузка архива
  берёт площадку проекта по имени как есть, недостающую создаёт и только добавляет
  размещение. Синк с прогоном агента размещение не меняет: агент его не знает. В
  превью ввоза — «N площадок»; демо-предел площадок действует и при ввозе.
- MCP (сделано, Ф4, версия 0.8.0; 0.9.0 — без наследования): в карточке `archmap_node`
  — строка «Размещение» (у контейнера — площадки его объектов, «часть объектов» у
  частичных); `archmap_update_node` ставит объект на площадки по именам (`sites`, `[]`
  снимает; контейнеру — всем объектам внутри; площадки через MCP не создаются); читающий
  `archmap_deployment` — площадки деревом с составом (контейнер целиком — одной строкой
  со счётчиком объектов) и объектами без размещения либо размещение одного объекта.
- Дерево объектов и размещение щелчком (сделано, Ф6). Слева — то же дерево объектов,
  что на карте, без создания объектов и переноса строк (объекты создаются на карте, на
  схему развёртывания добавляются уже описанные). Щелчок по контейнеру — его уровень;
  по объекту — выделить все его карточки и подвести к ним холст (если объекта на этом
  уровне нет — сначала уровень его родителя). Селекта уровня нет: в тулбаре путь
  уровня текстом («Весь проект» или «Витрина › Заказы») и «Весь проект» для возврата в
  корень. Редактору на строке объекта при наведении видна булавка «Указать
  размещение»: она включает режим размещения — над холстом «Куда поставить «X»?
  Щёлкните площадку», «Снять размещение» (если размещение есть; у контейнера — хоть у
  кого-то внутри) и «Отмена», Esc
  отменяет. Щелчок по зоне площадки, по свёрнутой карточке площадки или по карточке
  объекта на площадке ставит объект туда; группа «Размещение не указано» площадкой не
  считается. После записи объект на холсте выделяется, а если его на этом уровне нет —
  тост «„X“ размещён на „S“». Площадку перетаскиванием карточки не сменить — карточка
  двигается только внутри своей площадки; второй экземпляр — только окном «Размещение».
- Контейнер размещается целиком (сделано, Ф6; пересмотрено 2026-10-27 по приёмке):
  отдельного признака «унаследовано» нет — размещение хранится у объектов, контейнеру
  оно пишется всем объектам внутри, а его собственное складывается из них (площадка,
  где стоит часть, — «часть объектов»). Если у кого-то внутри размещение на других
  площадках, перед записью вопрос «Разместить «X» на «S»?» с пояснением и списком
  «объект: площадки»; «Разместить» слева, «Отмена» справа. «Убрать размещение» у
  контейнера снимает его у всех объектов внутри — после вопроса «Снять размещение
  «X»?» со списком; в окне «Размещение» этот вопрос — второй шаг окна («Снять» /
  «Назад»), а галочки контейнера показывают его объекты, и вопросов при размещении
  окно не задаёт.
- Единица размещения — контейнер (сделано 2026-10-29, эпик «Элемент архитектуры», Ф4;
  подробно — в его разделе, спека холста — D33): пункты выше, где «контейнер» значит
  «узел с детьми», с этой фазы читаются как «система», а «объект» — как «контейнер»
  (лист вне контейнера или контейнер с компонентами). Компоненту площадки не
  задаются (отказ 422 текстом), уровня контейнера на холсте нет, контейнер с
  компонентами — одна сплошная карточка, подтверждения размещения системы говорят о
  её контейнерах (тексты Ф8). При element = null у всех узлов поведение прежнее.
- Отложено: необязательные после Ф6 — алерт «объект без размещения», площадки в
  демо-пакете, «что ляжет, если ляжет площадка», промпт импорта о площадках.

Совместная работа: конкурентные сессии (этапы 0+1 — в продукте, план
docs/archive/plan-concurrency.md; realtime-этап 2 — за пределами MVP)
Один проект могут открывать несколько сессий (вкладок/пользователей); пишут
только владелец и редакторы проекта. Защита от конфликтов строится в два этапа:
- Этап 0 — защита от молчаливой потери (optimistic CAS). У вида есть версия:
  батч раскладки с устаревшей версией отклоняется (409) и переигрывается поверх
  свежего состояния — прямое действие пользователя (драг/undo/раскрытие)
  доносится, производные сдвиги конвейера выбрасываются и пересчитываются от
  свежего мира. Смысловые правки узла/связи (включая тексты OpenAPI и схем
  логики node_docs — у каждой схемы своя версия)
  защищены версией сущности: устаревшее сохранение отклоняется с явным
  сообщением вместо тихой перезаписи чужой работы. Запись раскладки в удалённый
  вид — 404 (не 500).
- Этап 1 — взаимная видимость. Клиент раз в 10 секунд и при возврате фокуса
  сверяет курсоры изменений проекта и перечитывает данные, если их изменил
  кто-то другой (не посреди жеста и не под открытой модалкой); свои записи
  чужими не считаются (echo-suppression: свои записи обновляют курсор из
  ответов, страница дополнительно сверяет содержимое). Два курсора: graph_rev —
  схема (узлы/рёбра/раскладка) → тост «Схема обновлена в другой сессии» на
  схеме; meta_rev — мета узла (атрибуты/доки/openapi) → тост «Данные обновлены
  в другой сессии» на странице объекта. Читатель проекта получает живые
  обновления наравне с редактором. Сервер недоступен (сеть, 5xx) — интервал
  сверки удваивается до 80 секунд, а после двух отказов подряд вверху экрана
  горит «Нет связи с сервером — изменения не подтягиваются»; первая удачная
  сверка её гасит.
Принцип: интент пользователя переживает ребейз, интент конвейера — нет.

Отказы и сбои в интерфейсе (аудит 2026-10, фаза 2 docs/plan-audit-2026-10.md)
Интерфейс не молчит об ошибках и не оставляет человека без выхода:
- исключение при отрисовке страницы — карточка «Что-то сломалось» с кнопками
  «Обновить страницу» и «К проектам» вместо белого экрана; упавший обучающий тур
  просто исчезает;
- не загрузились объект, проект, уровень схемы или схема на странице объекта —
  экран «Не удалось загрузить …» с причиной (не найдено, нет доступа, нет связи,
  текст сервера) и «Повторить» вместо вечной «Загрузки…» или пустого холста;
- токен истёк — экран входа с плашкой «Сессия истекла — войдите снова», после
  входа человек возвращается на ту же страницу (гость демо — на «Все проекты»);
- после выката новой версии открытая вкладка не может догрузить свои части —
  внизу экрана «Вышла новая версия ArchMap — обновите страницу» с кнопкой;
  страница не перезагружается сама, чтобы не потерять несохранённую правку;
- запись расположения не прошла — на холсте «Не удалось сохранить расположение —
  схема вернулась к последней сохранённой версии»; внешность, статус узла и
  направление связи при отказе возвращаются к сохранённым; отказ переноса в
  дереве — тост с причиной;
- «Скопировать промпт» работает и на http (без защищённого контекста), а если
  браузер не дал записать в буфер — под кнопкой появляется текст промпта для
  ручного копирования;
- очень большая схема логики (больше 150 000 символов или 1 500 связей) не
  рисуется сама: «Схема большая — отрисовка может занять время» и «Показать всё
  равно»;
- заблокированное хранилище браузера (политика, приватный режим) не мешает
  работать: настройки вида живут до перезагрузки вкладки.

Окна с полями ввода: подтверждение клавишей (2026-10-16)
Любое окно, которое просит что-то ввести, подтверждается с клавиатуры так же, как
главной кнопкой: Enter в однострочном поле, Ctrl/Cmd+Enter в многострочном (там Enter —
перенос строки). Механизм один — в общей модалке (ui/Modal, свойство onSubmit), а не
обработчик на каждом поле; клавиша делает ровно то, что кнопка, и молчит там, где кнопка
неактивна (не выбран конец связи, имя проекта не совпало, пароли не совпали, идёт
сохранение). Поле, которое само обработало Enter (комбобокс выбрал подсказку), набор
через IME и Enter на флажках и кнопках окно не подтверждают. Подключено: новый объект,
новая связь (прямая и с объектом вне уровня), правка связи со страницы (пока окно
спрашивает об удалении — только кнопкой), правка проекта, удаление проекта навсегда
(после совпадения имени), импорт процесса из Mermaid (шаг «Разобрать», затем
«Импортировать»), новый пользователь, смена и сброс пароля. Окно «Новый проект» ловит
Enter только в поле названия: на табе «Импорт» в нём живут поля вопросов остатка и форм
связей. Поле «Добавить участника» в окне доступа по Enter добавляет участника, а не
закрывает окно.

Пользовательская документация (отдельный репозиторий archmap-docs, docs.archmap.tech)
Отдельный сайт в стиле приложения; три руководства по ролям сервиса:
пользователя (чтение схем, навигация, страница объекта, доступ), архитектора (холст,
импорт и обновление, источника, факты, агенты и MCP) и администратора (установка,
обновление, пользователи и роли, копии). Живёт в отдельном репозитории
github.com/eidunyushkinhse/archmap-docs (решение 2026-10-16: документация — не часть кода
продукта; история вынесена из docs-site/). Исходники — Markdown в content/; собирает свой
движок на markdown-it (решение 2026-10-16: готовые движки не дают стиль ArchMap «как
влитой», а нужных правил включения и проверки в них нет).
- Единый источник истины: общий текст пишется один раз во фрагменте
  (content/_shared) и включается строкой <!--@include: …--> в любое число страниц;
  правка в одном месте меняет все. Ссылки и картинки внутри фрагмента считаются от
  него самого. Карта «фрагмент → страницы» — npm run report.
- Ссылки между страницами — относительными путями к .md, якоря — #id (из текста
  заголовка или явный {#id}, устойчивый к переименованию); картинки —
  относительными путями с подписью. Сборка проверяет всё это и останавливается на
  битой ссылке, якоре или файле (с подсказкой, какие якоря есть).
- Блоки ::: note | tip | warning | danger | details, код с подсветкой и кнопкой
  «Копировать», таблицы, <kbd>.
- Интерфейс (решение 2026-10-16 «confluence-подобное дерево, без перегруза»):
  шапка — логотип, «Документация», поиск; слева дерево всех страниц в стиле дерева
  объектов продукта (верхний уровень: Домашняя страница и три руководства; ветки
  раскрываются шевроном, память раскрытий в браузере; на телефоне — ящик); справа
  статья с крошками и «Назад/Дальше»; поиск по всей документации на клиенте
  (MiniSearch; индекс кусками по заголовкам собирается при сборке).
- Роли: читатель — любой посетитель, кнопок входа и правки не видит; автор — один
  пароль, вход по скрытому адресу /login (ссылок на него нет), сессия 90 дней в
  cookie — с каждого устройства входят один раз; неудачные попытки ограничены.
  У автора в шапке «Редактировать» и меню «Автор» (редактор, выход).
- Редактор /edit/: дерево страниц и фрагментов, поля фронтматтера, текст с живым
  предпросмотром тем же движком, вставки (фрагмент с верным относительным путём,
  ссылка на страницу, блок, картинка с загрузкой), создание страницы/раздела/
  фрагмента (адрес — транслитерация названия), удаление с защитой разделов.
  Сохранение пишет файл в content/ и пересобирает сайт; битые ссылки и якоря
  показываются автору, сайт при этом живёт (строгая проверка — в CI-сборке).
- Автокоммит (решение 2026-10-16 «правки — через автокоммит сервером»): каждая правка
  через редактор — отдельный коммит в репозиторий документации, который делает сам
  сервер («Правка «…» (user/x.md)», «Новая страница …», «Удалена страница …»,
  «Картинка …»); на стенде коммиты сразу отправляются в GitHub (отклонённая отправка
  повторяется после pull --rebase). Хэш коммита и результат отправки автор видит в
  строке статуса редактора; правки файлов мимо редактора сервер не коммитит.
- Статус: прототип на localhost с мок-страницами (2026-10-16), репозиторий archmap-docs
  создан. Впереди — хостинг docs.archmap.tech (сервер за nginx, DOCS_TRUST_PROXY,
  DOCS_GIT_PUSH с deploy key), ссылка «Документация» на лендинге вместо GitHub, наполнение.

За пределами MVP
- Автогенерация OpenAPI-спек из кода
- Автообновление связей на основе статического анализа кода
- Переменные окружения сервисов
- Интеграции, переключаемые переменными окружения
- Multi-tenant (отдельные организации в одной установке); доступ к проектам по
  участникам — в продукте (см. «Доступ к проектам»)
- Realtime-совместное редактирование (этап 2 плана конкурентности): WebSocket
  вместо поллинга, presence («кто на каком виде», чужое выделение, «X двигает
  узел») вместо жёстких локов. Триггер — наплыв
  пользователей; детали — docs/archive/plan-concurrency.md и tasks.md (дальний бэклог).
  Этапы 0+1 (CAS + поллинг) — в продукте, см. раздел «Совместная работа» выше.
