# ArchMap — spec.md

Описание продукта
Веб-сервис для описания многослойных программных систем
с произвольной глубиной иерархии. Альтернатива Structurizr
без ограничения в 4 слоя.

Проблема
C4-модель ограничивает описание системы четырьмя слоями.
В реальных системах компоненты содержат субкомпоненты
произвольной глубины. Structurizr это не решает.

Решение
Дерево узлов произвольной глубины. Каждый узел — либо
атомарный компонент, либо контейнер для дочерних узлов.
Архитектор сам решает, на каком уровне останавливаться.

Проекты (изоляция схем)
Пользователь работает не с одной глобальной схемой, а с несколькими изолированными
проектами. Проект — отдельная схема со своим деревом, связями и процессами; данные
проектов не пересекаются. Одна организация (без multi-tenant): проекты общие для
всех, роль глобальная.
- После входа открывается лендинг «Мои проекты» (сетка карточек: превью схемы,
  описание, дата изменения, последний редактор, счётчики объектов/связей; меню ⋯;
  табы Активные/Архив, поиск, пустые состояния).
  - Превью — РЕАЛЬНАЯ топология корневого уровня схемы (узлы-корни + связи между
    ними, спроецированные на корневых предков, как на холсте), а не декоративный
    граф. Бэкенд отдаёт мини-граф в ответе /projects батчем (без N+1).
- Создание: имя + описание + старт «пустой / из шаблона (3 пресета) / копия проекта»
  (копия — глубокий клон схемы с новыми id).
- Свитчер в шапке схемы: имя текущего проекта + дропдаун (поиск по имени, выбор,
  «+ Новый проект», «Все проекты»). Переключение перезагружает схему с корня и
  сбрасывает историю Undo/Redo.
- Архивирование — мягкое (флаг archived_at, данные целы), восстановление возвращает
  в активные. Удаление навсегда доступно только из архива и требует ввода имени
  (каскадом сносит всю схему). Управление проектами — только architect.

Роли
Архитектор: создаёт и редактирует узлы, связи,
  прикрепляет flowchart и OpenAPI-спеки к узлам.

Пользователь: просматривает дерево, навигирует по уровням,
  открывает flowchart и OpenAPI-спеку через UI.

Сущности
Project (проект — изолированная схема)
- id          UUID
- name        строка, обязательное
- description строка, опционально
- archived_at дата/время | null (null = активен; иначе — в архиве, мягкое удаление)
- created_at, updated_at («дата изменения схемы» — трогается смысловой правкой)
- created_by_id, updated_by_id  UUID → User («кто менял последним»)
- Все доменные сущности (Node, Edge, BusinessProcess) несут project_id (NOT NULL,
  каскад при удалении проекта). Данные проектов НЕ пересекаются: каждый запрос
  скоупится текущим проектом (заголовок X-Project-Id). Роль (architect/viewer)
  глобальная, проектом не меняется.

Node
- id          UUID
- project_id  UUID → Project (проект-владелец, NOT NULL)
- name        строка, обязательное
- description строка, опционально
- role        строка, свободное: "сервис", "БД", "брокер"...
- technology  строка, свободное: "Python", "Kafka"...
- parent_id   UUID | null
- shape       форма отображения (C4): service | database | broker | person
- is_external флаг «внешний узел» (на чужих уровнях рисуется «гостём»)
- status      жизненный цикл: existing (as-is, дефолт) | planned (to-be) | deprecated.
              Версионируемая семантика, не раскладка. Кодируется цветом тела узла
              (синий/зелёный/красный) + бейджем «новый»/«выводится»
- flowchart   текст (Mermaid), опционально
- openapi_spec текст (YAML), опционально
- created_at, updated_at
- has_children вычисляемое поле в API (есть ли дочерние узлы) — для дерева слева

Edge
- id          UUID
- label       строка, опционально (в UI поле называется «Описание»)
- technology  строка, опционально: "REST", "gRPC", "Kafka"
- source_id   UUID → Node
- target_id   UUID → Node
- created_at

Геометрия стрелок — целиком АВТОМАТИЧЕСКАЯ (2026-07-09)
Ручной слой стрелок УДАЛЁН по решению архитектора: изломы (waypoints с грипами),
реконнект концов (смена хэндла перетаскиванием), ручная фиксация хэндлов и
перетаскивание плашки подписи вдоль стрелки больше не существуют. Маршрут, сторона
стыковки и позиция плашки назначаются раскладкой (глобальный роутер + авто-плашки);
пользователь управляет стрелками опосредованно — перемещая узлы. Легаси-строки
пучков "b:<src>><tgt>" в view_layout игнорируются и вычищаются штатной чисткой
(удаление узла, «Переразложить уровень»).
(Возврат подвижных плашек пробовали 2026-07-13 (П4) и ОТКАТИЛИ по решению
пользователя — движение «вынесенных» плашек не устроило; фича заблокирована,
вернуться к идее позже. Инфраструктура легальных интервалов (labelCandidates)
и preferredT в раскладке остаётся — на будущее.)

Предсказуемые маршруты стрелок (2026-07-13): маршрут принадлежит ТОЛЬКО роутеру.
Детур-правило A12 («если подпись не влезает инлайн — изогнуть саму стрелку в объезд,
где плашке найдётся место») УДАЛЕНО: оно превращало прямые маршруты в необъяснимые
объезды (стрелка при свободном прямом коридоре шла полкой сверху/снизу) и
дестабилизировало живое превью драга. Невлезающая подпись решается leader-выноской
(плашка сбоку + пунктирный поводок). Заодно убран двойной клиренс плашек у узлов
(эрозия кандидатов дублировала Минковский-раздувание и требовала сегмент ≥ 2× ширины
плашки — подписи массово уходили в выноски): теперь инлайн садится на любой сегмент,
где плашка реально помещается; раздуваются только слитые плечи R4.

Качество роутера (2026-07-13, после снятия детуров): в routeAll два канонических
механизма (libavoid):
 • ШТРАФ ЕЗДЫ ПО ЧУЖОЙ ЛИНИИ (shared-path penalty, 1/px): раньше коллинеарная езда
   по уже проложенному сегменту была бесплатной — маршруты седлали чужие линии на
   сотни px, складывались в необъяснимые изгибы и парковались в чужие хэндлы (вход в
   точку чужого выхода — нарушение Т4). ИСКЛЮЧЕНИЕ: ствол веера из ОБЩЕГО порта той же
   роли (out-out из одной точки, in-in в одну точку) бесплатен — крайний сегмент
   владельца у общего порта; это легитимное слияние по Т4.
 • ВТОРОЙ ПРОХОД (rip-up & re-route): первый проход последовательный (длинные первыми),
   ранние рёбра слепы к ещё не проложенным. Теперь каждое ребро перепрокладывается при
   полном знании всех остальных; новый маршрут принимается только при выигрыше больше
   гистерезисного порога (100), «чистые» рёбра (без пересечений/наложений) пропускаются.
   Это убрало «жертв порядка» (двойные пересечения там, где можно без них). Rip-up
   итерируется до фикспойнта (cap 3) — эпик «читаемые пучки» T6.

Эпик «читаемые пучки» (2026-07-13, tasks.md; фазы T3+T1+T6 сделаны):
 • T1 МУЛЬТИ-СЛОТОВЫЕ ПОРТЫ: свободным рёбрам A* предлагает все 3 слота каждой стороны
   (12 портов), а не только центры. Веер сам расползается по свободным слотам (езда
   по чужому штрафуется, ствол в общем слоте бесплатен), in/out разводятся в поиске;
   пост-хок distributeSlots остаётся фолбэком. Эффект: хабы (Покупатель, API Gateway)
   читаемы, прямые там, где слот позволяет («Доставка → Покупатель» через всю сцену).
 • T3 ПОСТ-СПРЯМЛЕНИЕ ДЖОГОВ (straightenJogs, чистая функция): короткий (≤24px)
   перпендикулярный перескок между сонаправленными сегментами переносится в соседний
   излом (длина не меняется, изломов −2), если это не режет тела и полная стоимость
   строго меньше — джог, уворачивающийся от реальной езды/креста, остаётся. Доки не
   двигаются. Остаточные 8px-смещения от нуджинга — повестка T2.
 • T2 КАНАЛЬНАЯ РАЗВОДКА «АЛЛЕЙ»: в канал нуджинга собираются не только точные
   наложения, но и почти-параллельные сегменты разных рёбер (≤1.5×gap при пробеге
   >24px) — коридор разводится равными зазорами вокруг своего центра, «плетёнки»
   линий на пиксельных отступах исчезают. Порядок в канале — по текущим осям
   (идемпотентность), при совпадении — по подходам маршрутов. Стволы бакетируются
   по оси (Т4-слияние действует только на одной линии). Многопиновые каналы (двум
   и более пришпиленным стволам раньше — пропуск) решаются VPSC: пины держат оси
   (вес ∞), подвижные распределяются с зазором; невыполнимые — не трогаем. После
   нуджинга — полировка джогов (straightenJogs по финальной геометрии).
 • T4 ПЛАШКИ → ПРЕПЯТСТВИЯ МАРШРУТОВ: после размещения подписей один мини-проход
   перепрокладывает «грязные» рёбра (маршрут сквозь прямоугольник ЧУЖОЙ плашки) со
   штрафом за переход границы плашки (как рамки; своя плашка не отталкивает — online
   лежит на собственной линии), затем плашки размещаются заново. Вторая итерация
   осознанно не делается (редкий остаток «сдвинутая плашка легла на другую линию»).
 • T5 ЧИТАЕМОСТЬ ВЫНОСОК: поводок 1.5px (#6b7280, пунктир 4-3) — тонкий 1px терялся
   в гуще линий; вынесенная плашка получает halo (белая кайма + мягкая тень) и
   отделяется от линий под ней. Online-плашки без halo (лежат на своей линии).
 Эпик закрыт. Отложены с триггерами: полный MLCM-порядок в каналах, центрирование
 аллей, вторая итерация T4.

Живое превью стрелок во время драга узлов (2026-07-13): чтобы превью совпадало с
будущим маршрутом, во время драга стрелки обновляются по правилам раскладки, а не
«концы за узлом, нутро из снимка»:
 • ребро между ДВУМЯ перетаскиваемыми узлами едет ЖЁСТКО с ними (весь маршрут и
   плашка сдвигаются на дельту группы от снимка старта) — без «прилипшей середины»;
 • ребро с ОДНИМ перетаскиваемым концом пере-раскладывается настоящим роутером
   (buildAutoRoutes) по живым позициям — тем же движком, что и финал. Ради FPS
   роутер гоняется ТОЛЬКО для затронутых стрелок; маршруты ПРОЧИХ рёбер подаются ему
   предпроложенным контекстом (preplaced) — пересечения/наложения с ними живой A*
   видит как финал. Гостевые/сквозные рёбра роутятся наравне с локальными.
 • ПЛАШКИ едут с рёбрами живьём: размещаются ТОЛЬКО затронутые, но тем же движком и с
   тем же взаимным давлением — плашки незатронутых рёбер (за жест неподвижны) подложены
   жёсткими препятствиями скоринга (obstacleRects, кэш на жест). Замер на реальной
   сцене: совпадение позиции с финалом 0.0px во всех контрольных точках (и online, и
   leader), стоимость кадра ~1.5-3ms. Фолбэк без размещения: снимок + среднее смещение.
 • НЕ гоняется вживую только канальный нуджинг и rip-up ЧУЖИХ рёбер — на отпускании
   возможен небольшой доворот, сглаженный drawIn.
Перерисовка стрелок после ручного жеста (2026-07-09): по завершении ручного
действия, меняющего раскладку (отпускание драга узлов/группы, Undo/Redo),
стрелки, чья геометрия пересчиталась ИНАЧЕ (хэндлы/маршрут/концы/центр плашки),
не «прыгают» на новые места, а анимированно отрисовываются заново (drawIn, как
при раскрытии контейнеров) — остаточная разница превью/финала спрятана анимацией.
Новые/исчезнувшие стрелки не участвуют, prefers-reduced-motion уважается.

Мостики на пересечениях стрелок (line jumps)
Стрелка, пересекающая другую стрелку, «перепрыгивает» её маленькой полудугой —
читаемость пучка линий. Дуга появляется ТОЛЬКО на «крестике»: когда сегменты двух
РАЗНЫХ стрелок перпендикулярны и пересекаются СТРОГО внутри обоих. Если стрелки идут
вместе (исходят из одного хэндла, коллинеарны до чьего-то излома) — их совпадающие
сегменты параллельны, это не крестик, дуги нет; строгая «внутренность» отсекает и
T-стыки (конец одной лежит на линии другой), и общий хэндл, и углы. На каждом
пересечении прыгает ровно одна стрелка — ГОРИЗОНТАЛЬНАЯ (стандартная конвенция),
дуга выгибается вверх. Работает на основной схеме для стрелок, рисуемых ортогональной
ломаной (архитектор: обычные/кастомные/обводы/мастер); контекст-схема и viewer-
smoothstep не затронуты. Это РАСКЛАДКА (визуал) — ничего не персистится.

Хранение раскладки (R3, единое хранилище view_layout): по строке на объект вида,
payload {x, y, expanded}. Геометрия стрелок в БД больше не хранится (ручной слой
удалён 2026-07-09); прежние строки пучков "b:<src>><tgt>" — легаси, игнорируются.
Это РАСКЛАДКА — не версионируется.

Сквозные связи
Edge может соединять узлы с разных уровней иерархии
(например, А с уровня 1 и Б1 с уровня 2, где Б1 — дочерний узел Б).

Правила отображения:
- На уровне, где оба конца — локальные узлы: связь отображается как обычно.
- На родительском уровне: сквозная связь А → Б1 проецируется как А → Б,
  где Б — ближайший предок Б1, принадлежащий этому уровню.
- На уровне, где один конец — внешний: внешний узел отображается как
  «гость» (визуально отличается), стрелка идёт от/к нему.
- У промежуточного гостя есть кнопка «Войти» (иконка «ветвь в потомка») — переход на его слой-схему
  компонентов. Узел из другой ветки дерева, поэтому путь строится заново
  (предки + сам узел), а не аппендом к текущему breadcrumb. Кнопка есть:
  • у листа-гостя, если у него есть дети (GhostNode.has_children, считается в
    _build_graph); у атомарного листа кнопки нет — проваливаться некуда;
  • у свёрнутого контейнера (предок гостя, показанный коробкой): он всегда
    промежуточный, поэтому «Войти» есть всегда — рядом с лупой «раскрыть инлайн».
    Лупа разворачивает содержимое на текущем уровне, «Войти» уводит на слой узла.
- Двойной клик по гостю открывает его детализацию в правой панели — read-only
  (гость несёт лишь имя/роль/технологию/статус/путь предков, без description/
  flowchart/openapi и без правок; реальный узел живёт в другой ветке). Кнопка
  «Перейти к источнику» уводит на уровень-родитель, где узел показан как локал.
- Двойной клик по узлу/связи, кроме открытия детализации в правой панели, устойчиво
  подсвечивает связанное: у узла — его инцидентные стрелки, у связи — сама стрелка и
  оба её узла (индиго-акцент glow'ом — очерчивает и линию, и наконечник; держится, пока
  объект открыт в панели). Индиго-подсветка узла ПОЛНОВЕСНАЯ (та же громкость, что у
  синего свечения обычного выделения) и ПРИОРИТЕТНЕЕ синего: пока объект открыт в
  панели, узел индиго, даже если он же выделен кликом. Так «выделение панели» и
  «выделение кликом» не конфликтуют: снятие кликового выделения (клик по холсту) не
  меняет картинку — не возникает ложного «с узла сняли, а со стрелок нет», а при
  инспекции связи её концы очевидно подсвечены наравне с линией. Двойной клик по
  ПУСТОМУ холсту сбрасывает подсветку и очищает
  правую панель (штатный зум-по-даблклику при этом отключён).
- Раскрытие ЛЮБЫХ контейнеров (R5, ядро задумки): лупа есть и у ЛОКАЛЬНОГО
  сервиса с детьми — узел раскрывается на месте в рамку со ВСЕМИ своими детьми
  (у гостей — только связанные: это и есть C4-контекст), рекурсивно на любую
  глубину. Концы стрелок проецируются на видимых потомков; связь «прямо в
  контейнер» при его раскрытии скрывается (алерт-кейс). Дети догружаются лениво
  при первом раскрытии; при первом показе раскладываются сеткой от позиции
  контейнера и фиксируются (own-on-first-render). Раскрытие — часть состояния
  ВИДА: персистится (payload.expanded) и переживает перезаход; у наблюдателя
  (viewer) раскрытия эфемерны — смотрит без записи. Сворачивание возвращает
  узел на его сохранённую позицию.
- Анимация раскрытия/сворачивания (2026-07-09): переходы РЕЖИССИРУЮТСЯ, чтобы
  пользователь видел, откуда взялся узел и почему сдвинулся сосед. Раскрытие:
  дети спавнятся стопкой из центра свёрнутого узла и плавно разъезжаются по
  посчитанным позициям; рамка с именем родителя проявляется ПОСЛЕ разъезда;
  сдвинутые раскрытием соседи едут параллельно с детьми. Сворачивание —
  зеркально: дети съезжаются в точку будущего узла (рамка гаснет, соседи едут),
  по завершении стопка подменяется свёрнутым узлом. Стрелки, у которых движется/
  появляется хоть один конец, на время перехода честно скрываются, а по концу
  разъезда РИСУЮТСЯ анимированно от исходного хэндла к целевому (штрих
  pathLength=1 + stroke-dashoffset); наконечник и плашка с текстом появляются
  по завершении отрисовки. При большом числе стрелок отрисовка идёт КАСКАДОМ
  (Ф5 эпика плавности, 2026-07-15): волнами по 8 стрелок с шагом 60мс, короткие
  маршруты первыми — связи «расцветают» от ближних к дальним; конец фазы — по
  последней волне. Каскад за флагом DRAW_CASCADE (layoutAnimation.ts) — откат
  одной константой.
  Анимация чисто презентационная (раскладку не меняет: финал байт-в-байт равен
  рендеру после перезагрузки), уважает prefers-reduced-motion, не цепляет драг
  (transition живёт на холсте только в окно перехода). Реализация:
  useLayoutAnimation + планировщики layoutAnimation.ts + CSS lg-canvas--anim.
  Устойчивость к нагрузке (2026-07-13): отсчёт концов фаз (разъезд, отрисовка
  стрелок) ведётся от ПЕРВОГО ПОКАЗАННОГО КАДРА фазы (rAF→setTimeout), а не от
  setState — прогон раскладки по замерам, приходящий прямо в окно анимации,
  откладывает первый кадр, и wall-clock-отсчёт снимал drawIn до видимого старта
  («анимация пропадала», когда стрелок много). Сам конвейер оптимизирован без
  смены результата (индекс сегментов, скип rip-up при неизменном окружении, кэш
  сетки/проходимости A* между попытками): раскрытая сцена ~56мс/прогон против
  ~120-200 до — блок в окне анимации сжался до пары кадров.
  Плавность (эпик 2026-07-14/15, Ф1-Ф3): на окно анимации пересчёты раскладки
  ОТКЛАДЫВАЮТСЯ и досчитываются в «мёртвой зоне» конца разъезда (узлы стоят,
  стрелки ещё скрыты — drawIn рисует уже свежие маршруты); зеркальные прогоны
  скипаются по полной сигнатуре результата; сборка RF реконсилируется
  (неизменённые узлы/рёбра сохраняют identity — ре-рендерится только задетое,
  выделение переживает пересчёт); сам конвейер исполняется в Web Worker —
  главный поток в анимации занят только рендерами.
- Раскладка привязана к ВИДУ (R3): таблица view_layout(project_id, view_id,
  item_id, payload JSONB) — ЕДИНОЕ хранилище всей раскладки. item_id: id
  сущности → {x,y} (локалы, гости и свёрнутые контейнеры единообразно; один
  узел — гость на разных видах в разных местах) и {expanded} (раскрытие
  контейнера — R5). Всё это РАСКЛАДКА — не версионируется.
- Владение позицией «own-on-first-render» (рефакторинг движка, 2026-06-28): у каждой
  сущности (локала и гостя) своя АБСОЛЮТНАЯ позиция, персистимая при первом показе на
  уровне (гость засевается на кольце — см. ниже — и сразу фиксируется). Дальше узел
  двигается ТОЛЬКО ручным драгом или командой «Переразложить» — не пересчитывается за
  «живым якорем». Это убрало классы багов: драг локала не тащит связанных гостей, а
  раскрытая рамка не «убегает».
- Команда «Переразложить уровень» (кнопка в шапке, только архитектор и режим схемы):
  полный сброс ручного layout текущего уровня в авто — все строки view_layout
  этого вида удаляются (позиции, раскрытия, легаси-геометрия пучков). Уровень
  выглядит как при первом открытии. Скоуп строго по container_id (соседние уровни и
  узлы вне уровня нетронуты). Действие необратимо (подтверждается модалкой), историю
  Undo уровня после сброса чистим.
- Запрет проникновения в чужую родную рамку (C4-инвариант): гость (и гостевая
  рамка раскрытого промежуточного контейнера) НИКОГДА не лежит внутри родной
  рамки уровня, в которую не входит по членству. Родные рамки = предки из
  breadcrumb, концентрически вложены; гость — член рамок до своего общего предка
  включительно, поэтому единственная «запретная» для него рамка — следующая глубже
  общего предка. При дефолтном спавне, росте родной рамки (добавили узел) и ручном
  драге гость минимально сдвигается к ближайшему краю запретной рамки + интервал;
  задвинуть его внутрь руками нельзя. Раскрытая рамка — настоящий узел канвы
  (R4, compound): дети сидят внутри в её координатах, «Свернуть» — ✕ в плашке. Это РАСКЛАДКА — авто-сдвиг не персистится (драг персистит уже
  скорректированную позицию).
- Дефолтная раскладка гостя (без ручной позиции) — boundary labeling на «кольце»
  запретной рамки: гость ставится на ПЕРИМЕТР рамки F_{memberDepth+1} (та же рамка,
  что у keep-out, + интервал) — оптимальное место кратчайшей стрелки лежит на её
  границе. Базовая ось — горизонталь (поток C4 слева-направо, ближний к связанным
  узлам край), верх/низ берётся, когда горизонталь увела бы стрелку сквозь тела
  других узлов. Гости одной стороны раздвигаются изотонически (PAV) вокруг центра
  масс. Кольца разной глубины решаются изнутри наружу (рамка растёт за уже
  размещёнными глубокими гостями), поэтому keep-out выполняется по построению, а
  его проход остаётся лишь страховкой (ручные позиции, рост рамки за ручным гостем).
- Раскладка детей раскрытой гостевой рамки (промежуточный гость «вошёл» коробкой,
  его дети видны рамкой). При ПЕРВОМ показе дети не размещаются ELK-движком, а встают
  ВНУТРЕННЕЙ ПОЛКОЙ вдоль стороны рамки, обращённой к кольцу, в порядке проекции якоря —
  центроида центров связанных локальных узлов (нет связей → центроид всех локалов).
  • Перелив в колонки: если полка по высоте не влезает в пролёт кольца, дети переливаются
    в несколько колонок (вместимость колонки = пролёт / шаг узла). Самые «тяготеющие к
    контенту» (больше связей, ближе к центру масс якорей) — во внутреннюю колонку у кольца,
    остальные выталкиваются наружу; внутри колонки порядок — по якорю.
  • Дальше — own-on-first-render, как у всех: позиция каждого ребёнка сразу фиксируется
    АБСОЛЮТОМ (строка view_layout) и меняется только ручным драгом / «Переразложить».
  • Авто-группа (которую ещё не трогали руками) производно следует за ручным сдвигом
    свёрнутой коробки-родителя: блок детей смещается на дельту коробки от её кольцевого
    слота (ничего не персистится, дефолтный слот → сдвиг 0); при сворачивании коробка
    возвращается ровно на своё место.
  Всё это РАСКЛАДКА (визуал), не версионируется.
- Мастер-стрелка (несколько слитых связей одного направления) — синтетическое ребро
  без своей строки в БД; её геометрию, как и всем стрелкам, назначает авто-раскладка.
- Статус жизненного цикла узла (Node.status: existing/planned/deprecated) кодируется
  цветом тела: existing — синий (прежняя C4-рампа по глубине), planned — зелёный с
  бейджем «новый», deprecated — красный с бейджем «выводится»; внешние узлы — приглушённый
  тон того же статуса. Гости красятся по своему статусу. Связь наследует статус сильнейшего
  конца (deprecated > planned > existing): deprecated — красный пунктир, planned — зелёная,
  иначе серая. Это ВЕРСИОНИРУЕМАЯ СЕМАНТИКА (как shape/is_external), не раскладка.
- Фильтр «Вид схемы» (as-is / переход / to-be) — клиентский визуальный слой поверх данных:
  as-is показывает existing+deprecated (что работает сейчас), to-be — existing+planned
  (целевая система), переход — всё (дефолт). Скрытые статусом узлы и их рёбра НЕ удаляются,
  а приглушаются (opacity) — раскладка и связи сохраняются. Вид персистится в localStorage
  (не серверное, не свойство схемы). Легенда снизу-слева (свотч + счётчик видимых узлов
  статуса) показывается только когда на уровне есть хотя бы один не-existing узел.

MVP — в объёме
✓ Дерево узлов произвольной глубины
✓ Боковая панель из сворачиваемых секций (аккордеон, каждая секция
    разворачивается/сворачивается независимо):
    - «Дерево узлов» (как в Confluence): иерархия по parent_id, ленивое
      раскрытие веток. Узлы-пользователи (shape: person) в дереве не
      показываются — дерево про детализацию системы, а внутрь пользователя
      проваливаться нечего (на графе они есть);
    - «Добавить узел» (только архитектор): палитра из четырёх шаблонов-форм
      (сервис, БД, брокер, пользователь). Узел создаётся перетаскиванием
      шаблона на схему — см. ниже;
    Вся панель целиком сворачивается в узкую полосу. (Бизнес-процессы переехали
    из дерева в самостоятельный режим «Процессы» — см. ниже.)
✓ Бизнес-процессы — sequence-конструктор поверх C4. Архитектор строит диаграммы
    процессов, в которых участники = узлы C4, а сообщения нельзя нарисовать
    произвольно — только выбрать из плеч уже задокументированных связей. Так
    процессы и архитектура держатся в одной правде по построению:
    - оболочка: процессы живут в самостоятельном режиме «Процессы» (переключатель
      Схема/Процессы в шапке, персист в localStorage; дефолт — «Схема»), а не в
      модалке. Слева — рейл процессов (свернуть/развернуть, «+ Новый процесс», список
      с бейджами статусов и ···-меню дублировать/удалить), справа — холст выбранного
      процесса с тулбаром над диаграммой. Правка инлайн по тумблеру «Редактировать /
      Готово» (только архитектор), просмотр read-only доступен обеим ролям;
    - связь C4 — это «канал с плечами»: синхронный канал даёт два плеча — вызов
      (forward) и ответ (return); асинхронный — одно (forward, рисуется как событие).
      новая связь всегда создаётся синхронной; переключить канал в асинхронный
      можно тумблером «синхронная/асинхронная» в шапке канала в композиторе
      бизнес-процесса (поле Edge.is_synchronous; дефолт для связей без значения —
      синхронный). Это ЕДИНСТВЕННОЕ место правки типа: в C4-модалке связи тумблера
      нет — тип канала живёт только в бизнес-процессах, на схему C4 он не влияет.
      Авто-вывода по технологии нет — он зависел от текстового поля, что неочевидно;
    - два слоя: «что с чем взаимодействует» (участники + сообщения) заперто
      архитектурой; «в каком порядке / при каких условиях» (порядок, фрагменты
      alt/opt/loop/par) — свободный слой процесса. Фрагмент накидывается на ВЫБРАННЫЙ
      диапазон сообщений (выбор типа в тулбаре → протягивание по строкам), фрагментов
      может быть несколько, в т.ч. вложенных; удаление — кликом по шапке фрагмента;
    - исключение из «запертого слоя» — самозамкнутая стрелка (внутренняя операция
      участника, напр. «валидация»): её в C4 нет, поэтому сообщение хранится без связи
      (from==to, edge_id=null) и не подчиняется правилу «сообщение = плечо канала».
      Создаётся протягиванием из кружка участника обратно на себя;
    - редактор процесса умеет откат (undo/redo, как C4-канвас): кнопки в тулбаре +
      Ctrl+Z / Ctrl+Shift+Z; все мутации обратимы компенсирующим вызовом API;
    - сквозные связи: конец ребра вглубь чужого поддерева проецируется на
      ближайшего предка-участника; спроецированные концы фиксируются на сообщении,
      поэтому рендер не плывёт при смене набора участников;
    - добавление сообщения = drag-to-connect: под каждой линией жизни кружок «+»,
      из которого тянут стрелку к другому участнику (при драге кружки становятся
      хэндлами-целями). Источник→цель задаёт пару и направление; композитор
      открывается уже с выбранной парой (схематичные карточки узлов + стрелка по
      порядку колонок схемы), без полей «От кого/Кому»;
    - добавление участника: дерево узлов C4 с раскрытием + фильтр по имени +
      мультивыбор (добавить пачкой); уже добавленные помечены и недоступны;
    - удаление участника со схемы: крестик в правом верхнем углу шапки линии жизни
      (проявляется по ховеру). Если через участника проведены сообщения — всплывает
      подтверждение со списком этих связей (текст и вид как у C4-модалки удаления
      узла); вместе с участником каскадом удаляются его сообщения. Если связей нет —
      участник убирается сразу, без подтверждения;
    - валидатор: если между участниками нет задокументированной связи, композитор
      не даёт нарисовать фантом, а ведёт «Добавить связь в схему». Легальность
      плеча и сходимость проекции проверяет бэкенд (точка enforcement — POST
      /messages). Удаление связи из схемы не теряет сообщение: оно становится
      «повисшим» (valid=false) и подсвечивается янтарём (глиф «разорванная цепь»,
      чип «связь удалена», пунктир);
    - статусы в бизнес-процессах: на sequence-диаграмме ЦВЕТ = статус узла
      (единообразно с C4), а ТИП плеча — это ФОРМА (линия + наконечник), не цвет.
      Плечо красится по «сильнейшему» статусу концов: existing — чёрное (как стрелки
      связей C4), planned — зелёное, deprecated — красное; вызов = сплошная +
      закрашенный наконечник, ответ = пунктир + открытый, событие = сплошная +
      открытый. Шапки/линии жизни/активации planned и deprecated тонируются по статусу,
      шапка несёт бейдж «новый»/«выводится»; existing — без изменений. Переключатель
      «Вид схемы» (as-is / переход / to-be) в тулбаре гасит участников и сообщения
      вне вида (opacity, мгновенно, без удаления); подсказка вида — плашкой над канвой.
      Вид персистится в localStorage тем же ключом, что и на C4-схеме (общая привычка
      пользователя). В рейле процессов — производный бейдж to-be / вывод / миграция
      из статусов участников (на видимость процессов в списке не влияет).
    Холст процесса — sequence-диаграмма с линиями жизни (узлы C4), полосами
    активации, плечами (цвет = статус, форма = тип) и фрагментами; читается единой
    семьёй с C4-схемой в соседнем режиме.
✓ Создание узла перетаскиванием: архитектор тянет шаблон нужной формы из
    секции «Добавить узел» на схему уровня. Во время перетаскивания за курсором
    следует не плитка шаблона, а пустая рамка-превью будущего узла (форма с
    прозрачным телом): она масштабируется под текущий зум схемы (совпадает с
    реальным размером узлов) и примагничивается к центральным осям соседей —
    архитектор сразу видит точное место и координаты создаваемого узла.
    В точке отпускания открывается модалка создания узла с уже выбранной формой
    (поэтому поля «Отображение» в модалке нет) и заполняемыми полями. Узел
    появляется там, где показывала рамка (координаты, с учётом примагничивания,
    сохраняются в pos_x/pos_y). Пустой уровень показывает сам холст (канву с
    точками) — drop-зоной служит вся его область, узел встаёт под курсором.
    Подсказка «нет узлов / перетащите форму» висит тостом в правом верхнем углу
    ОБЛАСТИ ХОЛСТА (рейл тостов схемы, там же индикатор незавершённости — они
    стекуются колонкой) и уезжает за край холста после добавления первого узла.
    Тосты схемы не заслоняют шапку и боковые панели: их анимации обрезаются
    границей области графа — въезд/уезд идут «из-за края холста», а не за край
    экрана поверх правой панели. Холст открывается слегка
    отдалённым (зум ≈0.85), вход на разреженный уровень тоже не подлетает вплотную.
    Дроп в раскрытую рамку: если шаблон отпущен внутрь раскрытой инлайн-рамки
    контейнера (напр. ObsCore на уровне HelixMon), новый узел создаётся РЕБЁНКОМ
    этого контейнера, а не текущего уровня, и появляется внутри рамки. Во время
    перетаскивания рамка-цель подсвечивается (при вложенных рамках цель — самая
    глубокая под курсором). Позиция дропа принадлежит виду текущего уровня.
✓ Клик по имени узла в дереве: промежуточный узел (есть дети) → переход на его

✓ Кнопка узла на графе: «Войти» (иконка «ветвь в потомка» — спуститься на уровень ниже;

✓ Бейдж «есть дети (N)» в правом-нижнем углу узла с под-схемой (глиф-дерево + число

    раскрываемая справочная ветка прямых детей (глифы/шевроны как в дереве, ленивая

    Создание объекта — по-прежнему модалкой (дроп шаблона на холст).
✓ Контекстная схема узла (для листьев): модалка с

    самого узла или любого его потомка), обёрнутый в рамки своих предков.
    Соседи — пунктиром (как гости), связи проецируются на фокус. Схема
    только для просмотра (без правки, раскладка не сохраняется).

✓ Связи между узлами (label + technology)
✓ Формы узлов (C4): сервис, БД, брокер, пользователь. Контейнером (можно

✓ Внешние узлы (флаг is_external; на чужих уровнях — «гость»)
✓ Визуализация текущего уровня как интерактивная диаграмма:
    - узлы отображаются как блоки на диаграмме, не как плитки
    - связи отображаются как стрелки между узлами, не как таблица
    - двойной клик по плашке с описанием стрелки (или по линии) открывает мету
      связи; несколько слитых связей — окно «Выберите связь». У стрелки без
      описания вместо плашки — компактный плейсхолдер «•••» (он же точка входа).
      Архитектору в окне выбора доступна кнопка «Добавить связь» — дозаписать новую
      связь того же направления, не протягивая отдельную стрелку
    - плашка с описанием ЗАМОРОЖЕНА (2026-07-09): её позицию назначает авто-
      размещение (инлайн на свободном участке либо выноска с поводком), руками
      она не двигается
    - связь создаётся протягиванием новой стрелки от узла (архитектор): хэндлы
      узла раскрываются по ховеру, конец отпускается на цели. Попадание в ХЭНДЛ
      любого узла (с прощающим радиусом) создаёт прямую связь к нему. Отпускание
      на ТЕЛО узла мимо хэндлов: лист — прямая связь; узел-сервис С ДЕТЬМИ —
      «зона входа»: открывается выбор его потомка (поиск скоупится поддеревом),
      связь ведётся к нему и становится сквозной. Во время протягивания зона входа
      показывается явно — её контент гаснет, по центру возникает знак «стрелка вниз
      в лунку». На пустом холсте — отменяется.
    - быстрая связь по клику (архитектор): помимо ручного протягивания, у каждого
      хэндла по ховеру всплывает стрелка-подсказка. Если перевести курсор на неё,
      система сама подбирает узел С ПОДХОДЯЩЕЙ СТОРОНЫ относительно хэндла и
      ОТНОСИТЕЛЬНО НЕДАЛЕКО (из хэндла «выпускается коридор» вдоль нормали стороны;
      кандидат должен лежать впереди и перекрывать коридор по перпендикуляру; узлы за
      лимитом расстояния отбрасываются — никаких «километровых» стрелок; из подходящих
      берётся ближний и наиболее соосный). Предложенная связь подсвечивается
      полупрозрачной чёрной стрелкой; клик по стрелке-подсказке
      создаёт её через ту же модалку «Новая связь», что и ручное протягивание.
    - связь к узлу ВНЕ текущего уровня (которого нет на холсте — ни локально, ни
      гостем): во время протягивания на любом не-корневом уровне у верхнего края
      холста появляется плитка-полоса «Связать с узлом вне уровня» (элемент
      интерфейса, не объект графа; подсвечивается при наведении конца стрелки).
      Отпускание конца на неё открывает окно выбора дальнего конца из ВСЕЙ схемы
      (дерево + поиск по имени; узлы текущего уровня и сам источник недоступны).
      Выбранный узел становится дальним концом, связь — сквозной. Закрывает кейс,
      когда оба нужных узла нельзя свести на один холст.
    - магнитное выравнивание узлов по центру при перетаскивании. Плюс снап по
      РАВНЫМ ИНТЕРВАЛАМ (distribution, как в Figma): если два соседа стоят на одной
      линии (горизонтальной/вертикальной), перетаскиваемый узел прилипает к позиции с
      равными зазорами — два сценария: (а) ВСТАВКА МЕЖДУ соседями: узел садится по
      центру просвета пары, зазоры до левого и правого соседа равны (нужен просвет
      шире узла); (б) ПРОДОЛЖЕНИЕ ряда наружу тем же шагом за край. Подсвечивается
      двумя розовыми засечками равной длины (два равных зазора). Центр-выравнивание приоритетнее по
      каждой оси; снап по зазорам работает на свободной оси (ось ряда). Действует и
      при драге узла, и при перетаскивании шаблона-превью из палитры.
✓ Алерты незавершённости схемы (только архитектор): индикатор «подвисших»
    элементов («Вариант 1 · Минимал-знак»). При наличии активных алертов в
    правом верхнем углу схемы — компактный круглый янтарный знак «!» с бабл-
    счётчиком общего числа замечаний; при появлении и при росте числа знак
    коротко пульсирует (3 цикла). Клик раскрывает компактную панель с тремя
    категориями (пустые скрыты); каждый пункт — кликабельная строка с hover-
    подсветкой и «прицелом»: клик переводит холст к объекту на схеме (onLocate).
    Алерты глобальные, поэтому переход сперва приводит холст к «домашнему»
    уровню цели (узел → его родитель; связь → общий предок концов; группа →
    общий предок узлов кластера), затем центрирует/вписывает её и коротко
    подсвечивает (~2 с янтарным свечением). Когда устранено ПОСЛЕДНЕЕ замечание
    (total: >0 → 0), на ~2.5 с всплывает зелёный тост «Схема завершена» и уезжает
    за край (постоянно не висит; на первичной загрузке чистой схемы не
    показывается). Анимации уважают prefers-reduced-motion. Формулировки — на
    «объект», не «узел». Срабатывают три типа:
    (1) атомарные (листовые) узлы без единой связи;
    (2) связи, у которых хотя бы один конец упирается в промежуточный
        (контейнерный) узел, а не в атомарный;
    (3) изолированные группы — схема распалась на несколько не связанных между
        собой кластеров (связные компоненты графа РЁБЕР; иерархия parent_id не
        учитывается). Зажигается только при ≥2 группах размера ≥2 — один кластер
        плюс висячие узлы фрагментацией не считается (висячие ловит проверка 1).
    Контейнеры в проверке (1) не участвуют (прямых связей у них быть не должно —
    это ловит проверка 2, а группировку детей за «подвисание» не считаем).
    Алерты глобальные (по всей схеме) и считаются на бэке.
    API: GET /api/v1/nodes/alerts
✓ Навигация: войти в узел / вернуться выше
✓ Навигация и выделение на холсте:

✓ Выделение и безопасное удаление узла с канваса. Выбранный (активный) узел
    подсвечивается синим свечением по контуру формы — архитектор видит, какой
    узел исчезнет по Backspace/Delete. Удаление по Backspace/Delete не сносит
    узел напрямую (встроенное удаление React Flow отключено), а открывает то же
    предупреждение со списком связей, что и кнопка «Удалить» в модалке узла
    (общий компонент NodeDeleteConfirm). Действует только у архитектора и только
    при ровно одном выбранном узле. Удаление узла удаляет всё его поддерево
    (дочерние узлы любой глубины) и все связи поддерева. Предупреждение
    показывается, только если есть что терять: у поддерева есть внешние связи
    (ровно один конец вне поддерева) ИЛИ у узла есть дети; в списке — именно эти
    внешние связи (включая связи потомков наружу). Лист без связей удаляется
    сразу, без модалки.
✓ Отмена и повтор перемещений (Undo/Redo, архитектор). Ctrl/⌘+Z отменяет, Ctrl/⌘+
    Shift+Z или Ctrl/⌘+Y повторяет. Поскольку правки персистятся в Postgres сразу,
    отмена — это компенсирующий вызов API, а не откат фронт-стейта; визуально
    мгновенно (зеркало в локальный стейт), сеть фоном. Итерация 1 покрывает все
    ПЕРЕМЕЩЕНИЯ: позиции узлов/гостей/контейнеров (вся перетянутая группа = один
    шаг). Ручной слой стрелок удалён (2026-07-09) — команды изломов/плашки/хэндла
    больше не создаются. История — до 50
    шагов, в памяти вкладки, СКВОЗНАЯ по уровням: если откатываемая правка сделана на
    другом уровне, Undo/Redo сначала РЕДИРЕКТИТ пользователя на этот уровень, затем
    выполняет откат. Undo/Redo доступны и горячими клавишами, и кнопками тулбара на
    холсте. Итерация 2 добавляет отмену УДАЛЕНИЙ: перед каскадным удалением клиент
    снимает снимок поддерева (узлы + рёбра + строки раскладки), а Undo восстанавливает
    его на сервере с СОХРАНЕНИЕМ исходных id (POST /nodes/restore), Redo — повторное
    удаление. Структурное восстановление требует серверной проекции гостей/рёбер,
    поэтому undo/redo удаления перечитывают уровень (а не зеркалят в стейт, как
    перемещения). Итерация 3 добавляет отмену СОЗДАНИЙ и ПРАВОК ПОЛЕЙ узлов и связей:
    снимок+restore стал универсальным примитивом структурного отката (создание/удаление
    и узлов, и связей — с сохранением исходных id; у связей свой снимок
    GET /edges/{id}/deletion-snapshot), а правка полей откатывается простым возвратом
    прежних значений (update). Покрыты все жесты создания связи и правка её концов
    (undo возвращает концы). Группировка одного жеста (мультидраг) сворачивается
    в одну команду, а компенсирующие вызовы

    тельские конфликты в MVP НЕ разруливаются: в рамках MVP архитектор один (см.
    «За пределами MVP»).

Версионирование документации (планируется, см. tasks.md → бэклог)
Документация (узлы и связи) поддерживается в версионируемом состоянии.
- Версионируется только СЕМАНТИКА. Версионируемые поля:
    узел — name, description, role, technology, parent_id, flowchart,
           openapi_spec, shape, is_external;
    связь — label, technology, source_id, target_id.
  Поля раскладки (pos_x/pos_y, source_handle/target_handle) НЕ версионируются —
  перемещение узлов в версию не попадает.
- Публикация ПАЧКОЙ. «Пачка» = семантический diff между живым состоянием и
  последней опубликованной версией; кнопка «Опубликовать» проводит черту (как
  git commit). Отдельный «принцип формирования пачки» не задаётся.
- Автор и время фиксируются на уровне версии целиком (без аудита отдельных
  действий внутри пачки).
- Возможности: история версий, состояние на версии N, diff(A, B) с подсветкой
  added/removed/modified (узлы и связи + изменённые поля), откат к версии
  (forward-revert — история не стирается).
- Конкурентность (несколько редакторов): оптимистичная блокировка по версии
  сущности — устаревшая правка отклоняется с конфликтом.
- Хранилище — PostgreSQL (НЕ Git). Git рассматривался и отклонён: при
  многопользовательской записи даёт конфликты слияния. Возможный задел на потом —
  экспорт опубликованных версий в Git как витрина/ревью, не как БД.

За пределами MVP
- Автогенерация OpenAPI-спек из кода
- Автообновление связей на основе статического анализа кода
- Переменные окружения сервисов
- Интеграции, переключаемые переменными окружения
- Multi-tenant
- Многопользовательское редактирование одной схемы (конкурентные правки). В MVP
  архитектор один, поэтому конфликты не разруливаются: правки идут last-write-wins,
  а отказ записи лечится ресинком уровня из БД (resync-on-error). Когда понадобится
  совместная работа — задел на потом (по возрастанию усилий): оптимистичная блокировка
  по версии на смысловых полях (409 → ресинк), пессимистичная блокировка схемы
  («один редактор за раз»), полноценный realtime (websockets + рассылка / CRDT).
