# Сборщик фактов ArchMap (scan/)

Документ для разработчика. Что и зачем делаем, решено в ТЗ эпика
[docs/tasks/fact-collector.md](../docs/tasks/fact-collector.md); здесь только как этим
пользоваться и как это устроено.

## Что это

Один файл `archmap-scan.pyz`, который человек, агент или CI запускают в своём
репозитории. Сборщик читает манифесты развёртывания и сборки, миграции и примеры
окружения и пишет каталог файлов в форматах, которые ArchMap уже ввозит: `schema.yaml`
(контейнеры, базы данных, брокеры, связи из манифестов и по каналам из кода), `facts/*.yaml`
(таблицы, параметры конфигурации и каналы брокеров), отчёт о покрытии и сводку, а для агента
основания каждой записи, точки входа (маршруты, воркеры, расписания, потребители) и
подсказки. Сборщик не выполняет код репозитория, не ходит в сеть, не пишет никуда, кроме
каталога вывода, и не выдумывает: описаний, подписей со смыслом и ролей сверх словаря нет,
у каждой записи есть основание «файл:строка». Чего сборщик не умеет, он называет в отчёте
о покрытии статусом семьи, а не молчанием.

Версия: 0.7.0 (`archmap_scan/__init__.py`; номер пишется в шапку каждого файла
вывода и в `coverage.yaml`).

## Окружение

```bash
python3 -m venv scan/venv
scan/venv/bin/pip install -r scan/requirements-dev.txt
```

Рантайм-зависимость одна: PyYAML (пин как у `mcp/` и бэкенда). Код обязан работать на
Python 3.10: ruff и mypy проверяют именно эту версию (`scan/pyproject.toml`).

## Гейт

```bash
( cd scan && ./venv/bin/ruff check . && ./venv/bin/mypy && ./venv/bin/python -m pytest -q )
```

Тот же гейт гоняет pre-commit при правке файлов `scan/`. Тесты времени (враждебный вход,
`tests/helpers.time_limit`) меряют через `tests/helpers.timed` процессорное время своего процесса
`time.process_time()`, а не время по часам, и прогон за пределом повторяют один раз, беря меньшее
из двух: под нагрузкой (dev-стек, подкачка, занятый хост) полный гейт не роняет тесты, которые
поодиночке проходят, а квадратичный разбор выходит за предел в обоих прогонах (часть 5, П7).
Фикстуры (`scan/fixtures/`) это чужой код для разбора: ruff, mypy и pytest их не трогают, сборщик их только читает.
Покрытие: `./venv/bin/python -m pytest -q --cov --cov-report=term-missing`.

## Запуск из исходников

```bash
scan/venv/bin/python -m archmap_scan ПУТЬ --out /tmp/archmap-scan
scan/venv/bin/python -m archmap_scan --help
```

Тесты на деревьях внутри репозитория ArchMap запускают сборщик с `--no-git`: иначе корнем
git окажется сам ArchMap, и пути в выводе будут от его корня.

## Сборка файла

```bash
scan/venv/bin/python scan/build.py   # → scan/dist/archmap-scan.pyz, печатает размер и sha256
                                     # (другой интерпретатор кладёт другой PyYAML и даёт другой sha256)
scan/venv/bin/python scan/build.py --out ПУТЬ
python3 -I -S scan/dist/archmap-scan.pyz scan/fixtures/yarmarka --out /tmp/y --no-git
```

`build.py` кладёт в архив пакет `archmap_scan`, чистую Python-часть PyYAML из
site-packages того интерпретатора, которым запущен (без `_yaml*.so`, `__pycache__` и
`dist-info`), текст лицензии PyYAML, если он есть в метаданных пакета, и `__main__.py`.
Даты и права записей одинаковые, записи отсортированы: одинаковые исходники и одна версия
PyYAML дают одинаковый sha256. Запуск с `-I -S` проверяет, что файлу не нужно ничего вне
архива. `scan/dist/` в `.gitignore`.

## Раздача

Собранный файл раздаёт сам ArchMap без входа: `GET /api/v1/scan/archmap-scan.pyz` (ETag по
sha256, заголовок `X-ArchMap-Scan-Version`, `If-None-Match` даёт 304) и `GET /api/v1/scan`
(`{version, sha256, size}`); код в `backend/app/routers/scan.py` и `backend/app/scan_file.py`.
Путь к файлу задаёт настройка `SCAN_FILE` (по умолчанию `../scan/dist/archmap-scan.pyz` от
рабочего каталога бэкенда `backend/`). Во всех трёх поставках файл собирает тот же
`build.py`: в образе он лежит в `/opt/archmap/scan/archmap-scan.pyz` (Dockerfile задаёт
`SCAN_FILE`), в серверной поставке в `scan/archmap-scan.pyz` рядом с `backend/` (путь задаёт
служба `deploy/archmap.service`), в разработке `./dev.sh` сам собирает `scan/dist/archmap-scan.pyz`
питоном `backend/venv`, если файла нет или исходники новее. Без файла оба адреса отвечают 404.

Кто запускает файл. ИИ-агент пользователя — первым шагом промпта ввоза и обновления из кода
(`backend/app/import_prompt.py`, шаг «0»): промпт называет адрес файла на этом сервере, когда
клиент передал свой адрес (`origin`) и файл есть в поставке. Агент с локальным MCP-сервером
запускает его инструментом `archmap_scan` (`mcp/archmap_mcp/tools.py`: скачивание в кэш
`ARCHMAP_SCAN_DIR` со сверкой sha256, подпроцесс `python -I -S -X utf8`, предел
`ARCHMAP_SCAN_TIMEOUT`), агент без него — командами `curl` и `python3` из промпта. Человек
без агента скачивает файл ссылкой в окне «Новый проект» на способе «Импорт» или в окне
«Обновить из кода». Превью ввоза и план обновления узнают вход сборщика по шапке
`# archmap-scan <версия>` (`backend/app/scan_origin.py`) и помечают его.

## Фикстуры и ожидаемый вывод

`scan/fixtures/<разборщик>/` — малые деревья на каждый разборщик, у яруса кода — с
ловушками: файл в `tests/`, строка в комментарии, имя выражением. `scan/fixtures/yarmarka/` —
синтетический монорепо по ТЗ §9 с ловушками в `tests/`, `docs/` и `.archmapignore`, а в коде
сервисов — маршрут и топик выражением и секрет с дефолтом; его
полный вывод лежит в `scan/fixtures/yarmarka.expected/`, тест сравнивает байт в байт.
После осознанной правки вывода:

```bash
( cd scan && UPDATE_SCAN_EXPECTED=1 ./venv/bin/python -m pytest -q tests/test_yarmarka.py )
git diff scan/fixtures/yarmarka.expected/   # это ревью правки; коммитить вместе с ней
```

## Устройство

- `cli.py` — ключи и коды выхода; `scan.py` — конвейер «контекст → обход → разборщики →
  сборка → вывод».
- `context.py` — корень, область, адрес origin и коммит; единственная внешняя команда —
  git из перечня `GIT_COMMANDS`. `walk.py` — обход, соглашения, `.archmapignore`, пределы
  чтения файлов.
- `parsers/*.py` — по модулю на источник, функция `parse(files, ctx) -> Findings`;
  `registry.py` — реестр разборщиков по семьям, по нему же считается покрытие. `compose.py`
  читает и YAML не с именем compose, если он compose по содержимому (ТЗ §13.3). Когда
  манифестов нет, `buildfiles.py` даёт контейнеры по `*_PROGRAMS` в `Makefile.am` и по
  каталогам Go `cmd/<имя>/` с `func main()` (ТЗ §13.4).
- `assemble.py` и `owners.py` — объекты, связи, отнесение таблиц и параметров к владельцу;
  `vocab.py` — словари образов, фреймворков и ролей; `secrets.py` — что из значений можно
  писать. Один процесс, описанный двумя манифестами (Dockerfile и юнит systemd с тем же
  каталогом кода), склеивается в один контейнер с записью в `hints.merged` (ТЗ §13.5).
- `yamlload.py`, `tomlite.py`, `sqlddl.py`, `pyast.py` — чтение YAML, TOML, SQL DDL и Python
  с пределами против враждебного входа.
- Файлы настроек проекта: `appsettings` (`appsettings.json` .NET, свой разбор JSON с
  комментариями) и `hjson` (`config/defaults.hjson`); записи идут чтениями кода с признаком
  `from_file`.
- Таблицы: `sql`, `alembic`, `django`, схема Rails `railsschema` и `kysely` (ярус кода), разбор
  DDL у SQL-файлов и шаблонов Kysely общий (`sqlddl.py`). `openapi_owner.py` отдаёт операции
  файла OpenAPI маршрутами сервису, который его отдаёт, или оставляет подсказку с причиной;
  код, который называет файл литералом его имени, собирает разборщик `served`.
- Ярус кода: маршруты `fastapi`, `flask`, `djangourls`, `express`, `nest`, `gohttp`,
  `rails-routes` (маска Ruby — `codetext.RUBY`), `aspnet`, `actix`, параметры
  `pyenv`, `nodeenv`, `goenv`, `dotnetenv`, `javaenv` (общее у C# и Java — `clike.py`),
  `rustenv`, каналы `celery`, `kafka`, `rabbitmq`, `nats`, `bullmq`, `sidekiq`, расписания
  `celerybeat`, `gocron`, `clokwerk`, `nodecron`, `crontab`, таблицы из шаблонов `sql` в миграциях Node.js `kysely`; файлы по
  стеку пакета — `codebase.py`, владельцы записей — `codefacts.py`.
  Записи из служебных каталогов и конфигов инструментов (`walk.TOOLING_TOKENS`) и переменные
  ОС (`vocab.is_os_variable`) уходят в подсказки, а не в факты (ТЗ §13.1). Реестры каналов
  (`class Topic(Enum)`, словарь, у имени которого последнее слово `topic`/`queue`/`subject`)
  и декоратор потребителя очереди — `pyregistry.py`, одно правило для четырёх разборщиков
  каналов.
  `djangourls` резолвит обёртки регистрации маршрутов (функция репозитория возвращает `path`
  с первым параметром путём, как `rest_path` у Zulip; методы из `GET=`, `POST=`), `gohttp`
  берёт путь из обёртки `toPath("/p")` на известном объекте маршрутизации и префикс группы
  через параметр функции регистрации от мест её вызова в том же каталоге (`gocode.py`,
  ТЗ §15).
- `output/` — писатели `schema.yaml`, `facts/`, `agent/`, `coverage.yaml`, `summary.txt` и
  маркера каталога; `texts.py` — все строки для людей.
- Политика «боевое или для разработки» (ТЗ §15 п. 10 Б). Признак манифеста разработки по
  месту и форме считает одна функция `walk.dev_sign` (каталог или имя файла с частью из
  `DEV_TOKENS`), у Procfile ещё `walk.dev_procfile` (его запускает goreman, foreman, overmind
  или hivemind из Makefile или скрипта). Compose добавляет сервис основы, который расширяют
  только файлы разработки (`compose._dev_bases`), и стенд в каталоге кода контейнера из
  другого боевого файла (`assemble._stands`); devservices отдаёт в подсказки сервисы вне
  режима default без своего режима и отладочные. Решает `assemble._dev_units`. Если боевые
  манифесты развёртывания есть (ступень 1), кандидаты разработки уходят в `hints.profiles` с
  причиной «манифест разработки: <признак>», а сервис с тем же именем в боевом манифесте
  остаётся по боевому. Если их нет (ступень 2, Sentry), кандидаты разработки становятся
  объектами с записью в `hints.dev_manifest_objects`, и об этом говорят `coverage.yaml`
  (`from_dev_manifests`) и сводка.
- Правила фазы 3в (ТЗ §15 п. 10, по строке на правило):
  - литерал с конкатенацией (`"/"+root`, `"OTEL_"+name`) уходит в `dynamic_names`, а не в
    факты (`codetext.Code.joined`, `pycode.joined`);
  - файл k8s отбрасывается как шаблон только по признаку Helm (`k8s._HELM`);
  - `sqlddl.py`: `CREATE TABLE … AS` даёт таблицу без колонок с подсказкой (с части 3 —
    колонки по именам списка SELECT, З2), имя без кавычек в
    нижнем регистре (кроме MySQL, MariaDB, SQLite и SQL Server), `RENAME CONSTRAINT` и
    `ALTER TRIGGER` понятны, временные таблицы не создаются;
  - пример окружения по суффиксу `example|sample|template|dist` и `example.env`
    (`envexample.is_example`);
  - файл общего кода отдаётся только контейнеру того же языка (`owners.file_owners`);
  - Dockerfile в подкаталоге привязывается к сервису по skaffold, сборке в файле разработки и
    имени образа, `Dockerfile.<суффикс>` — вариант того же контейнера (`hints.merged`);
  - транзитивные зависимости pip-compile (`# via`) и `// indirect` в go.mod фреймворк не
    задают, читаются `*.csproj` и `*.sln`;
  - задача на образе базы или брокера с `command` и `restart: no|on-failure` — сервис
    (`assemble._tasks`);
  - файлы и каталоги CI (`walk.CI_DIRS`, `walk.CI_PREFIXES`) не читаются, в покрытии их
    причина `ci`;
  - строка сводки «параметры общего кода» только по общему каталогу кода;
  - реестр каналов по последнему слову имени с делением по регистру (`CeleryQueue`),
    `…_TO_TOPICS` не реестр, очереди SQS не очереди Celery;
  - имена стеков в `unsupported` только по прямым зависимостям и файлам контейнеров
    (контейнеры по файлам сборки границы не задают, тогда по всему репозиторию), `unknown`
    только при неопознанном стеке;
  - словарь образов знает pgautoupgrade, ClickHouse в имени образа и browserless; Redis
    брокер, если в манифестах сборки контейнера-клиента Sidekiq, BullMQ, RQ или Celery
    (`assemble._build_packages`); база с depends_on к брокеру связана с ним;
  - сводка говорит «Не разобрано» и не обещает полноты.
- Правила части 1б по дымовому прогону 15 репозиториев (ТЗ §15 п. 12, по строке на пункт):
  - каталоги зависимостей `walk.DEPENDENCY_DIRS` (`vendor`, `node_modules` и подобные) не
    читаются и с git, в покрытии причина `dependencies`; `dist`, `build`, `target` с git
    читаются (С1);
  - шаблон Dockerfile (`Dockerfile.j2`, `*.tpl`, `*.template`, `Dockerfile.in`, `*.jinja*`) не
    читается, в покрытии причина `template`; `<имя>.Dockerfile` равен `Dockerfile.<имя>` (С2);
  - `docs`, `examples`, `samples` и подобные исключаются и частью сегмента через дефис или
    подчёркивание (`docker-stack-docs`); манифест в каталоге служебной сборки (`tools`,
    `scripts`, `artifacts`, `*-build-image`, `_*` и другие, `walk.service_sign`) — кандидат
    разработки по политике Б, Dockerfile такой на ступени 2 становится объектом с пометкой (С3);
  - язык по образу Dockerfile у итоговой стадии, у `scratch` и `alpine` у предыдущей стадии с
    языком (С4);
  - каталог кода сервиса без своего (или с корневым) по имени сервиса или образа в корне и
    каталогах монорепо (`assemble._named_dir`); Dockerfile служебного каталога с «COPY .»
    берёт каталог ближайшего предка с манифестом сборки, общий Dockerfile образов одной
    организации уходит в подсказку; Gradle с плагином Kotlin даёт Kotlin (С5);
  - сервис compose с командой разработки (`vocab.dev_command`), раннером тестов в имени или
    на образе инструмента разработки (`vocab.DEV_TOOL_IMAGES`) — кандидат разработки; файл
    Laravel Sail разработка целиком; Dockerfile в `.devcontainer/` к боевому объекту не
    привязывается (С6);
  - корневой контейнер без манифестов в корне или только со служебным `package.json` (без
    dependencies) берёт язык из манифестов свободных подкаталогов, если они одного языка
    (`assemble._free_packages`); `coverage.stacks` перечисляет только языки, фреймворки и
    виды из словаря (`vocab.is_stack`); язык контейнера, код на котором не читается, даёт
    `unsupported` вместо `unknown` (С7);
  - `Dockerfile.<суффикс>` и `<префикс>.Dockerfile` рядом с основным Dockerfile одного
    контейнера (не в корне репозитория) — вариант при любом суффиксе, Dockerfile в
    подкаталоге каталога кода контейнера без своего манифеста сборки — тоже вариант
    (`hints.merged`); Dockerfile мобильного приложения (`walk.mobile_dir`: `react-native`,
    `android`, `ios`, `mobile`, `flutter`) уходит в `hints.unassigned` (С8);
  - ENGINE sqlite3 настроек Django, когда другой модуль того же пакета настроек переопределяет
    `DATABASES` без sqlite (`TableSet.dialect_default`) или таблицы у базы другого вида из
    манифестов, вида базы не даёт: подсказка «sqlite как значение по умолчанию настроек» (С9);
  - файл k8s с `RELEASE-NAME` в `metadata.name` или образе — вывод `helm template`, не
    разбирается: пометка семьи containers и запись `hints.unparsed` (`k8s.rendered`, С10);
  - соседние каталоги наборов SQL с именами диалектов (`hsqldb`, `h2`, `sqlite`, `derby`,
    `mysql`, `mariadb`, `postgres`, `postgresql`, `pgsql`, `mssql`, `sqlserver`, `oracle`) с
    серверным среди них — одна база по первому в алфавите серверному диалекту, остальные в
    подсказках «встроенная база для разработки и тестов» и «несколько диалектов» (С11);
  - маркер сборки в корне (`WORKSPACE`, `WORKSPACE.bazel`, `MODULE.bazel`, `BUILD.bazel` —
    «C++ (Bazel)», `CMakeLists.txt` — «C/C++ (CMake)», `buildfiles.root_stack`): `Cargo.toml` и
    `go.mod` тогда SDK и утилиты (ни неявного контейнера, ни процессов `cmd/`, ни языка
    корневым контейнерам), стек первым в `stacks` и в `unsupported` (С12);
  - закоммиченный в git `.env` из каталога файла compose раскрывает `${VAR}` и `${VAR:-x}` в
    `image`, `build`, `environment` и `depends_on` (`compose._dotenvs`); без git и
    незакоммиченный не читается, параметрами его значения не становятся (С13).
- Правила части 2 (ТЗ §15 п. 13, по строке на пункт):
  - модуль-реестр констант по последнему слову имени файла во множественном числе
    (`topics.py`, `kafka-topics.ts`, `celery_queues.py`): `ИМЯ = строка | f-строка |
    get_from_env(…, дефолт)` даёт канал по литеральной части, голое `ИМЯ` в вызове клиента
    раскрывается по импорту, файл без клиента Kafka, но с именем из реестра читается только
    по таким аргументам; связь с каналом вытесняет «использует» той же пары из манифестов
    в любом направлении, как в части 1 (решение части 2 оставлять обе отменено частью 2б),
    «использует» к базе и к брокеру без связей с каналом остаётся (В1);
  - BullMQ и Bull (`parsers/bullmq.py`): `new Queue('x')` и `@InjectQueue('x')` публикуют,
    `new Worker('x')` и `@Processor('x')` потребляют, `BullModule.registerQueue({ name })`
