# Ф4 — раскрытие промежуточного гостя без наложений (исследование + план)

Часть рефактора движка раскладки **own-on-first-render** (см. tasks.md, память
`engine-refactor-ownership`). Ф1–Ф3 закрыты. Это документ Ф4.

Полигон: тестовый проект **«АБВ»** (`c49155b6-…`). Структура:
корень А, Б; дети А — В, Г, Д (локалы уровня А); дети Б — Е, Ж, З; у Ж ребёнок И.
Связи: В→Е, В→З, В⇄И (двунаправленная). Пользователь на уровне А раскрывает Б
(видит Е, З и контейнер Ж), затем раскрывает Ж → появляется И.

---

## 1. Симптом

При раскрытии промежуточного гостя (вложенной рамки Ж) появившийся ребёнок И
**садится поверх соседей**, движку всё равно на наложения. В данных «АБВ» после
раскрытия: З = (123, 318), И = (89, 310) — один и тот же пятачок.
(Историческое, до рефактора: раскрытие давало «дикое смещение» рамки в другой конец
схемы — лишь бы избежать пересечения; теперь — наоборот, рандомный спавн поверх.)

## 2. Диагноз (подтверждён кодом + данными)

**В движке нет разведения гостей между собой.** Ровно два класса ограничений:

1. `engine.ts:layoutLevel` — ELK `layered` по всем узлам, НО строка
   `if (node.savedPos != null) positions.set(node.id, node.savedPos)` затирает
   результат ELK для любого владеемого узла. ⇒ ELK реально позиционирует только узлы
   **без** позиции — нового авто-гостя (И). Его координата посчитана относительно
   ELK-раскладки ВСЕХ узлов, которой после затирания на экране нет ⇒ позиция И
   в чужой системе координат ⇒ визуально случайна.
2. `keepGhostsOut.ts:enforceFramesKeepOut` выталкивает гостей только из **нативных**
   (breadcrumb) рамок и никогда — друг из друга.

Сцепленные следствия:
- `ringPlacement.placeGhostsOnRings` обрабатывает только `auto`-группы, а препятствиями
  считает **только локальные** узлы (`localRects`/`crossingsAt`). Владеемые гости-соседи
  (Е/З/Ж) невидимы ⇒ кольцо для И ставит его на З.
- `collectGhostSeeds` замораживает кривую позицию навсегда (own-on-first-render).

Почему задача сложная: рамка = bbox её членов. Сдвинул И → вырос bbox рамки Ж → она
может налезть на Б → каскад. Плюс концентрический keep-out нативных рамок. Это
**иерархическая минимально-смещающая задача с separation-constraints** (containment +
non-overlap), а не локальный фикс.

## 3. Требования (зафиксированы архитектором 2026-06-29)

- **R1. Expand-in-place.** Центр раскрытой рамки = центр узла, который раскрыли (или с
  минимальным смещением). Раскрытая рамка — «якорь» жеста; двигаются соседи, не она.
  (Та же логика, что уже работает для гостей первого уровня.)
- **R2. Минимум суммарного смещения** соседей.
- **R3. Сохранение относительного порядка и топологии** соседей (никаких перестановок
  «лево/право», «над/под»).
- **R4. Приоритет подвижности:** сиблинги раскрытой рамки → «родня» уровнем выше →
  локалы. Локалов трогать **только если иначе схему не развести**.
- **R5. Все запреты соблюдены:** нативный keep-out (концентрический), нет наложения
  узлов, нет пересечения рамок (рамка = bbox членов), члены остаются в своей рамке.

## 4. Выбранный подход — VPSC, свой, по слоям containment

R2+R3 — это в точности целевая функция **VPSC** (Variable Placement with Separation
Constraints, Dwyer–Marriott–Stuckey): минимизировать Σ wᵢ(xᵢ − dᵢ)² при ограничениях
xⱼ − xᵢ ≥ gap, раздельно по осям x и y. Она даёт минимальное смещение и **по построению**
не нарушает порядок (ограничения генерятся из текущего порядка и не «переворачиваются»).

Соответствие требованиям:
- R2 = сама целевая функция. R3 = свойство ограничений.
- R4 = **веса** wᵢ: локал — огромный вес (≈ неподвижен), родня — средний, сиблинг —
  малый, раскрытая рамка — пиннится (desired = старый центр узла, большой вес).
- R1 = desired-позиция раскрытой рамки = центр свёрнутого узла.
- R5 (иерархия) — самое сложное. Решаем как уже делает `ringPlacement`:
  **по слоям containment, изнутри наружу.** На каждом слое рамку трактуем как жёсткий
  супер-узел (её bbox), гоняем ПЛОСКИЙ VPSC над супер-узлами слоя + нативными рамками
  как фиксированными препятствиями; при сдвиге супер-узла все его члены транслируются.
  Нативный keep-out — separation-ограничение «гость снаружи нативной рамки» (уже есть
  геометрия в `pushOut`).

Почему свой VPSC, а не WebCoLa/cola.js: проект ценит bespoke-геометрию (context
намеренно НЕ сажали на ELK), а иерархия здесь специфична (рамка = bbox членов,
концентрический нативный keep-out, пиннинг раскрытой рамки) — групповая модель WebCoLa
не ложится 1:1, а его VPSC-ядро невелико и переиспользуемо. Ядро 1D-солвера хорошо
документировано и покрывается юнит-тестами. (Если свой солвер не сойдётся по качеству —
fallback на cola.js/vpsc; откат изолирован, см. §6.)

## 5. План по под-фазам (каждая = зелёный гейт + маленький коммит)

- **Ф4.0 (спайк, де-риск).** Изолированный модуль `layout/vpsc.ts` — 1D weighted
  separation solver: вход (desired[], weight[], constraints[left,right,gap]) → feasible
  positions, минимизирующие Σ w(x−d)², порядок сохранён. Юнит-тесты `vpsc.test.ts`
  (базовые случаи + регресс на числах «АБВ»: И не должен садиться на З). Без проводки
  в пайплайн. Цель — доказать алгоритм. **← начинаем здесь.**
- **Ф4.1 (СДЕЛАНО).** `overlapConstraints.ts:generateOverlapConstraints(rects, pad)` —
  node-node non-overlap по оси МИНИМАЛЬНОГО перекрытия (дешевле развести → R2), сторона
  по центрам (порядок сохраняется → R3); возвращает раздельные наборы {x, y}. Чистая
  функция, 8 тестов (выбор оси, гэп, пропуск неналегающих, связка с солвером, «АБВ»).
  ⚠️ Решение: native keep-out СЮДА НЕ кладём — он односторонний (узел вне рамки), это
  невыпуклое «слева ИЛИ справа», в чистый VPSC не лезет. Но при минимальном смещении
  СТОРОНА известна из текущей позиции → фиксируем сторону → ограничение линейно. Поэтому
  keep-out генерим в Ф4.2, где есть контекст рамок (или оставляем существующий enforce-проход).
- **Ф4.2.** Оркестрация по слоям containment изнутри наружу: супер-узлы, веса
  (локал≫родня>сиблинг, пин раскрытой рамки), трансляция членов, native keep-out как
  фиксированная-сторона, итерация x→y до сходимости. Тест на «АБВ».
- **Ф4.3.** Проводка в пайплайн `LevelGraph` на событии раскрытия (заменяет/дополняет
  текущий ring+enforce для случая раскрытия вложенного гостя). expand-in-place (R1).
- **Ф4.4.** Засев/персист сдвинутых соседей (own-on-first-render остаётся консистентным:
  expand двигает владеемых соседей → новые absolute персистятся). Регресс-тесты.

## 6. Риски и откат

- VPSC-ядро фиддли (блоки/слияния). Митигация: Ф4.0 — изолированный модуль с тестами
  до любой проводки. Если качество/сходимость недостаточны — fallback на cola.js/vpsc
  (только vpsc-модуль) или на инкрементальный MTV-проход; откат — один-два коммита.
- Перф: VPSC по слоям на каждое раскрытие. Слои малы (сиблинги одной рамки) → дёшево.
- Конфликт expand-in-place (R1) и keep-out: если центр свёрнутого узла внутри запретной
  зоны — пин уступает keep-out (вес native = ∞). Зафиксировать в тестах Ф4.2.
