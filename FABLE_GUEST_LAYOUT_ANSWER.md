# Ответ Fable: раскладка гостей — это boundary labeling на кольце keep-out

> Ответ на FABLE_GUEST_LAYOUT.md. Прочитаны: `frames.ts`, `outsideGhosts.ts`,
> `keepGhostsOut.ts`, `engine.ts`, `projectGhosts.ts`, `detours.ts`, `level.ts`,
> async-эффект в `LevelGraph.tsx` (365–566), `constants.ts`, тесты `outsideGhosts.test.ts`.

## TL;DR

Задача «куда ставить гостей» — не 2D-задача. Ваш же инвариант keep-out уже
доказал это: у каждого гостя ровно ОДНА связывающая запретная рамка
`F_{memberDepth+1}` (комментарий в шапке `keepGhostsOut.ts` — концентричность ⇒
очистив её, очищаем все глубже). Допустимая область гостя — дополнение этой
раздутой рамки, а минимум длины стрелки при якоре внутри рамки достигается **на
границе** раздутой рамки. Значит, оптимальные позиции живут на **1D-периметре
(«кольце») запретной рамки**, и задача целиком сводится к классической
**boundary labeling** (Bekos–Kaufmann–Symvonis–Wolff, 2004; обзор external
labeling — Bekos–Niedermann–Nöllenburg): расставить коробки фиксированного
размера вдоль периметра прямоугольника возле проекций их якорей, без наложений,
с минимальным суммарным смещением. Это решается **точно, детерминированно и за
O(n log n)** — без силовых солверов и без перевода рамок в ELK.

Две колонки лево/право — это вырожденный случай этой задачи (периметр, урезанный
до двух вертикальных отрезков, + жадная стопка «только вниз»). Все пять симптомов
из постановки — прямые следствия этого урезания.

## Переформулировка

Для каждого гостя `g` без ручной позиции:

1. **Запретная рамка** `R_g = F_{memberDepth(g)+1}` (как в `keepGhostsOut`),
   раздутая на клиренс (формула из `outsideGhosts` + `KEEPOUT_GAP`).
2. **Якорь** `a_g` — центроид связанных отображаемых узлов (по `layoutEdges`,
   как сейчас считаются `xs/ys`), при нескольких связях — взвешенный.
3. **Желаемая позиция** — проекция `a_g` на периметр кольца: ближайшая точка
   на границе. Это автоматически даёт все ЧЕТЫРЕ стороны (верх/низ бесплатно)
   и кратчайшую стрелку.
4. **Де-коллизия** — одномерная: гости одного кольца упорядочиваются по
   периметрической координате `t` и раздвигаются с минимальным суммарным
   сдвигом: `min Σ (t_i − t_желаемое_i)²` при `t_{i+1} − t_i ≥ gap_{ij}`.
   При фиксированном порядке это выпуклая задача, решаемая точно алгоритмом
   **pool-adjacent-violators** (изотоническая регрессия), O(n) после сортировки.
   Это «совместная оптимизация» из вашего списка: соседи договариваются,
   кластер центрируется вокруг якорей — в отличие от текущего
   `y = max(desired, last + NODE_H + 28)`, который умеет толкать только вниз
   (верхний гость прибит, нижние уезжают сколь угодно далеко).

### Почему это закрывает все пять симптомов

| Симптом | Чем закрывается |
|---|---|
| Длинные стрелки | позиция = ближайшая точка периметра к якорю, не «лево/право от центра» |
| Стрелки под узлами | выбор стороны со штрафом за пересечения (см. ниже) |
| Нет верх/низ | периметр включает все 4 стороны по построению |
| Нет совместной оптимизации | PAV — точный минимум суммарного смещения по кольцу |
| Грубая де-коллизия | та же 1D-задача, симметричное раздвигание вместо стопки вниз |

### Выбор стороны с учётом пересечений («стрелки под узлами»)

Чистая проекция якоря — хорошее дефолтное `t`, но дешёво сделать лучше:
кандидаты — 4 проекции якоря (по одной на сторону). Для каждого кандидата
пробный ортогональный маршрут (уже есть всё: `orthogonalPointsForHandles` +
`pathCrossesRects` из `edgePath`, ровно как в `detours.ts`) и лексикографическая
стоимость: `(число пересечённых тел узлов, манхэттенская длина стрелки)`.
Берём минимум; ничья → старое правило направления (источник-слева /
приёмник-справа — сохраняет дух текущих тестов и даёт детерминизм для гостя
без связей), затем по id. Для гостя с несколькими связями стоимость суммируется
по связям.

### Каскад концентрических колец — keep-out по построению

Кольца разных гостей разные (зависят от `memberDepth`), и bbox рамки `F_d`
включает гостей с членством ≥ d, т.е. рамка растёт за уже размещёнными более
глубокими гостями. Поэтому кольца решаются **изнутри наружу**: по убыванию
запретной глубины `d`. К моменту решения кольца `d` все более глубокие гости
уже стоят и уже раздули bbox `F_d` (считаем через существующий `computeFrames`).
Результат: инвариант keep-out выполняется **по построению**, а заодно по
построению выполняется и ограничение №3 («внутри общей родной рамки, снаружи
более глубоких» — кольцо `F_{L+1}` лежит ровно в этом кольцевом зазоре).

`enforceFramesKeepOut` при этом НЕ удаляется — он остаётся страховочной сеткой
(ручные позиции, рост рамки за ручным гостем, деградации). На авто-размещённых
гостях он должен становиться no-op — это, кстати, отличный инвариант для теста.

### Остальные жёсткие ограничения

- **Ручные позиции** — гость с `levelPositions` в кольцо не попадает (как
  сейчас). V2-улучшение: его коробка проецируется на кольцо как «блокированный
  интервал» — авто-гости его обтекают. В v1 можно не делать (текущее поведение
  не лучше).
- **Раскрытая гостевая рамка — жёсткая группа**: на кольце она — один
  «супер-узел» с габаритами своего bbox (внутренняя раскладка членов — как
  сейчас: ELK + центрирование по `expandOrigins`; кольцо двигает группу общей
  дельтой — та же семантика групп, что в `enforceFramesKeepOut`).
- **Детерминизм и стабильность**: чистая функция входа; сортировки со
  стабильным тай-брейком по id; PAV — решение выпуклой задачи, непрерывно
  зависит от входа (якорь пополз → `t` ползёт, не прыгает). Дискретные скачки
  остаются только при смене стороны — тот же класс, что нынешний флип
  лево/право у центра, но дистанция флипа меньше (4 стороны ближе друг к
  другу, чем 2). Ни итераций до сходимости, ни RNG, ни состояния между
  прогонами.
- **Перф**: O(G·log G) на де-коллизию + O(G·4·N) на пробы пересечений —
  ничто на фоне async-ELK, который уже считается на каждый чих.
- **RF-координаты/хэндлы**: на выходе те же `positions` (левый-верхний угол)
  и тот же пересчёт `assignEdgeHandles` — контракт `OutsideGhostsResult`
  сохраняется почти дословно.

## Прямые ответы на «риски и открытые вопросы»

**Моделировать рамки в ELK (compound + external ports)? — Нет.** Три причины.

1. *Родные рамки — не иерархия ELK.* Это вложенные bbox'ы ОДНОГО И ТОГО ЖЕ
   множества локальных узлов (breadcrumb), а не партиция дерева. Compound-узлы
   из них — цепочка из единственных детей, фикция. А гость с членством до
   глубины L должен стоять *между* кольцами `F_L` и `F_{L+1}` — external port
   живёт на ОДНОЙ границе, «между двумя» он не умеет.
2. *Ручной drag убивает глобальный оптимум ELK.* Ваш режим — «ELK даёт
   черновик, savedPos перетирает, остальное адаптируется». Это режим
   constraint-repair, а не глобальной раскладки: после первого же ручного
   сдвига «умная» ELK-расстановка портов и рамок устаревает. Вкладываться в
   неё — платить сложностью (fixed-position + hierarchy + port constraints в
   ELK — реально хрупкая комбинация) за оптимум, который живёт до первого
   драга.
3. *Стабильность.* Малое изменение графа у layered-алгоритма может перещёлкнуть
   ранги — прыжки именно того сорта, от которого вы лечите гостей.

**Размещать сразу валидно или «грубо + enforce»? — Сразу валидно.** Кольцо и
есть граница keep-out, валидность бесплатна. `enforceFramesKeepOut` понижается
до страховки/ассерта. (Сейчас порядок «грубо → вынос → энфорс» порождает и
isFlung-хак, и мусорные ELK-позиции, которые надо исключать из bbox — всё это
исчезает.)

**Силовой/констрейнт-солвер (WebCoLa и т.п.)? — Нет.** После выбора стороны
ядро задачи ВЫПУКЛОЕ и ОДНОМЕРНОЕ — общий итеративный солвер аппроксимировал бы
то, что PAV решает точно. Силовые модели тащат недетерминизм инициализации,
негарантированную сходимость и стоимость на каждый пересчёт — ровно те риски,
которые постановка запрещает.

**Стрелки под узлами.** Частично закрывается штрафом за пересечения при выборе
стороны. Полное решение — маршрутизация рёбер, и тут у переформулировки есть
бонус на будущее: кольцевые зазоры между концентрическими рамками — готовые
«каналы» для канальной трассировки обводов; `detours.ts` (вертикальные обводы
verh/niz) станет частным случаем. Не делать сейчас — `computeDetours` остаётся
как есть и будет срабатывать заметно реже.

## Миграция тремя зелёными шагами

Каждый шаг проходит гейт и полезен сам по себе:

1. **PAV вместо стопки** внутри текущих колонок (`placeCol`). Маленький чистый
   модуль `pav.ts` с юнит-тестами; контракт `outsideGhosts.test.ts` меняется
   только в кейсах совпадающих desiredY (раздвигание симметричное, а не вниз).
2. **Четыре стороны + стоимость с пересечениями.** Колонки лево/право →
   проекция на периметр ВНЕШНЕЙ рамки + выбор стороны по
   `(пересечения, длина)`, тай-брейк — старое правило направления. Тесты
   «источник→слева / приёмник→справа» для гостя без явного перевеса сторон
   выживают как тай-брейк-кейсы.
3. **Каскад концентрических колец.** Кольцо каждому гостю по его
   `memberDepth+1`, изнутри наружу; внутренние гости и «улетевшие» перестают
   быть спецслучаями (isFlung удаляется); keep-out — по построению;
   тест-инвариант «enforce — no-op на авто-гостях».

## Краевые случаи (зафиксировать в тестах нового модуля)

- Гость без связей с уровнем → старое правило (правая сторона), стопка по id.
- Якорь — единственный узел, кольцо вокруг него: проекция вырождена → тай-брейк
  направлением (сохраняет первые два теста `outsideGhosts.test.ts` дословно).
- Гость, связанный только с другими гостями: якоря берутся из уже размещённых
  (более глубоких колец) позиций; внутри одного кольца — позиции до де-коллизии;
  если якорей нет вовсе — правило «без связей».
- Углы кольца: центр коробки не заходит в угловые зоны (полуширина коробки);
  в v1 допустимо проще — 4 независимые «полки» с переливом за угол.
- Переполнение стороны: PAV честно выдавит хвост за угловую зону — допустимо,
  страховка keep-out всё равно держит инвариант.

## Чего эта переформулировка сознательно НЕ решает

- Глобальную красоту раскладки локальных узлов — это по-прежнему ELK.
- Полную маршрутизацию рёбер без пересечений — отдельная задача; кольца дают
  ей естественные каналы, но это следующий проект, не этот.
- Кросс-сторонняя оптимизация порядка стрелок (минимум взаимных пересечений
  лидеров) — в boundary labeling известно, что порядок по якорям на стороне
  устраняет пересечения лидеров одной стороны; проекционные `t` дают это почти
  всегда бесплатно, строгая гарантия — возможное v3.
