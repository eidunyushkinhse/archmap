Ты — ИИ-агент с доступом к файлам репозитория и терминалу.
Задача: подготовь OpenAPI-спецификации для сервисов, чей код лежит в ЭТОМ репозитории. Архитектурная схема системы уже создана в ArchMap — ниже её срез. Схему НЕ меняй и не пересобирай: результат — ПАКЕТ ФАЙЛОВ с документами, привязанными к УЖЕ СУЩЕСТВУЮЩИМ узлам схемы.

## Срез схемы (адреса узлов)
```yaml
nodes:
- name: Ярмарка
  shape: service
  children:
  - name: orders
    shape: service
  - name: Каталог-БД
    shape: database
edges: []
```
Спецификация уезжает ГЛАВНОМУ узлу этого среза — первому в списке.

## Что документировать
Только узлы, чью реализацию видишь в ЭТОМ репозитории (обычно один контейнер и его компоненты; база данных рядом с ним). Узлы других репозиториев пропусти — их задокументируют прогоны в их репозиториях. Если своего сервиса в срезе нет — ничего не выдумывай: пропусти и скажи об этом в финальном ответе.

### OpenAPI-спецификация
Спецификация описывает API, который узел САМ ПРЕДОСТАВЛЯЕТ (его входящие операции). У узла без собственного HTTP API (фронтенд, воркер, БД) спецификации нет вовсе — спецификация сервиса, который он лишь вызывает, принадлежит тому сервису.
Одна спецификация на контейнер: у компонента своего API нет, и спецификацию, загруженную для компонента, ArchMap перенесёт его контейнеру. Добывай по ранжиру:
1. В репозитории уже лежит готовая спецификация (openapi.yaml, swagger.json, api/*.yaml) — СКОПИРУЙ файл в пакет командой (cp), НЕ перепечатывай содержимое. Происхождение: found.
2. Фреймворк умеет отдать спецификацию — сгенерируй её В ФАЙЛ командой (FastAPI: python -c "import json; from app.main import app; s = app.openapi(); s['info']['x-archmap-origin'] = 'generated'; print(json.dumps(s))" > archmap-docs/<сервис>-api.json; springdoc: GET /v3/api-docs; swagger-jsdoc и аналоги). Происхождение: generated.
3. Ни того ни другого — синтезируй МИНИМАЛЬНУЮ честную спецификацию по коду роутеров: только реально существующие пути/методы/основные параметры и ответы. Ничего не выдумывай. Происхождение: synthesized. Обход роутеров — процедура, а не беглый просмотр:
   - Найди файл-СПИСОК маршрутов (таблица роутов, urls.*, routes.*, регистрация хэндлеров) и дочитай его ДО ПОСЛЕДНЕЙ СТРОКИ: маршруты дописывают в хвост файла, и чтение, оборванное на середине, молча уносит из раздела paths целые подсистемы.
   - Одно объявление маршрута часто несёт НЕСКОЛЬКО методов (GET и POST на одном пути, список methods=[...], несколько хэндлеров в одной записи) — заведи у пути ключ-операцию на КАЖДЫЙ объявленный метод (get:, post:, delete: …), а не на первый из списка.
   - Список маршрутов в репозитории обычно не один: маршруты добавляют и ниже по файлу, и в ДРУГИХ файлах (свои urls/routes у подсистем, подключаемые роутеры, плагины). Найди ВСЕ такие файлы и внеси в спецификацию пути каждого — пропущенный файл уносит из спецификации весь свой раздел путей. Путь пиши целиком, вместе с префиксом, под которым роутер подключён.
Первой строкой файла спецификации (если это YAML) добавь комментарий с происхождением: «# archmap-origin: found | generated | synthesized». Если спецификация в JSON — комментариев в нём нет, положи происхождение ключом «x-archmap-origin» в объект info (команда генерации выше так и делает).

## Формат результата — пакет archmap-docs/
Создай в корне репозитория папку archmap-docs/ и сложи в неё файл спецификации. Никакого файла-описи не нужно: каждый файл сам себя описывает. Пользователь загрузит файлы папки в ArchMap разом — перетаскиванием или вставкой текста.
Язык подписей схем и имён — русский. Ключи шапки и значения kind — латиницей ровно как в примере.

## Перед завершением проверь себя
1. Файл спецификации скопирован/сгенерирован командой, НЕ перепечатан вручную; первой строкой YAML-спецификации — комментарий с происхождением.
2. Спецификация и operation-схемы описывают ВХОДЯЩИЙ API узла; у узла без собственного API спецификации нет совсем; у компонента спецификации нет, она у его контейнера.
3. Задокументированы только узлы, чью реализацию видно в ЭТОМ репозитории.
4. В финальном ответе перечислены ВСЕ созданные файлы — по именам.

В финальном ответе пользователю перечисли СОЗДАННЫЕ ФАЙЛЫ по именам (это важно: файлы он будет переносить в ArchMap руками и должен видеть, что ничего не потерял), какие узлы задокументировал, откуда взята спецификация, что пропустил и почему.
Если пользователь пришлёт список замечаний валидатора — исправь пакет и сообщи, какие файлы изменились.
