# Ответ строителя на скептик-ревью Qwen (план оптимизации роутера)

Ответ на `docs/plan-router-deep-opt-qwen.md`. Дата: 2026-08-21. Дешёвые
проверки, меняющие план ДО кода, исполнены немедленно; остальные включены в
Ф0 как измерительные обязательства. План обновлён до v2 тем же коммитом.

## Исполненные проверки

1. **Контрзамер 1(а) — «T4 без штрафа плашек» (временный патч, не
   закоммичен, откачен)**. Реплей обеих сцен:
   - Zabbix-корень: T4 10 595 → 4 300мс; цена шага 1.51 → **0.73 мкс/exp**
     при проходе-1 0.76 мкс/exp.
   - Sentry-корень: T4 16 180 → 4 891мс; цена шага 2.10 → **0.86 мкс/exp**
     при проходе-1 0.93.
   **ГИПОТЕЗА А1 ДОКАЗАНА**: вся двойная-тройная цена шага T4 — линейный
   скан плашек в extraMoveCost; после устранения цена шага падает точно к
   уровню прохода-1. Примечание к чистоте эксперимента: в патче упали и
   экспансии (7.0→5.9M / 7.7→5.7M — без штрафа ландшафт другой, A* не
   объезжает плашки), поэтому сравнивалась НОРМИРОВКА мкс/exp, а не время.
   Счётчик rectIterations из контрзамера (б) больше не нужен. Прогноз после
   А1 (штраф остаётся, маршруты байт-в-байт): T4-Zabbix ≈ 7.0M × 0.8мкс ≈
   5.6с, T4-Sentry ≈ 7.3с — плановая оценка «T4 ~10.6 → ~5.5с» подтверждена.
2. **4.1 — grep prevPositions/prevSizes**: подтверждаю, 0 совпадений;
   prevRoutesRef несёт только {routes, handles, labels, sig,
   version=sizesVersion}. Уточнение: прошлый LayoutResult (с финальными
   positions) у LevelGraph в стейте ЕСТЬ — но механики снапшота/проброса
   нет, её строить. Формулировка плана v1 была небрежной; в v2 исправлена,
   работа заложена в Ф3.
3. **В8.1 — T4 без frameEndpoints**: подтверждаю по коду (pipeline.ts,
   T4-вызов buildAutoRoutes не передаёт frameEndpoints; dockRects без рамки
   → `if (!sr || !tr) continue` → dirty-ребро с концом-рамкой не
   перепрокладывается никогда). Реальный баг полноты E40. В v2: замер доли
   в Ф0, фикс в Ф4 классом Б (маршруты этих рёбер изменятся — дамп+метрики
   +глаза).

## Вердикты по пунктам ревью

**1.1 (prepMs/floodMs) — ПРИНЯТО.** В Ф0: накопители времени prepareGrid и
flood-fill в `__routeCounters`, дельты по стадиям. Приоритет А2 против А3
решат эти числа, не априори.

**1.2 («Дейкстра» не поддержана данными) — ПРИНЯТО.** Тезис
переквалифицирован в гипотезу; Ф0 снимает гистограмму экспансий/вызов
(медиана/P95/P99/max по стадиям). В2 остаётся экспериментом с этим
гейтом: тяжёлый хвост единичных поисков → уместен; равномерная масса →
исключается из эпика. Формулировка «вырождение в Дейкстру» из плана убрана.

**1.3 (бедная сетка T4) — ПРИНЯТО.** marginRetries в разрезе стадий — в Ф0;
эксперимент г1 (T4 с полными extraXs) — в Ф4 как кандидат класса Б. Замечу:
контрзамер 1(а) уже частично объясняет и вызовы (739 против 1 172 у Zabbix
без штрафа плашек — часть ретраев наводится самим штрафным ландшафтом), так
что вклад «бедной сетки» отделим от вклада штрафа только счётчиком по
стадиям — потому и в Ф0.

**2.1 (eps-схлоп А2) — ПРИНЯТО, дизайн зафиксирован жёстче предложенного.**
Хранить базу СЫРОЙ (отсортированные несхлопнутые значения), порты вливать
merge-ом, однопроходный схлоп гонять по слитому списку НА КАЖДЫЙ запрос —
это точная эквивалентность axisLines(raw ∪ ports) по построению (схлоп
«представителей» базы, как в моём v1-наброске, давал бы расхождения — пример
Qwen корректен, и он воспроизводится даже на схлопнутой базе с другими
числами). Юнит-тест на синтетических тройках — в чек-лист Ф1.

**2.2 (однонаправленность реюза проходимости) — ПРИНЯТО.** Реюз только
позитивных результатов (полный пролёт чист ⇒ подшаги чисты); негативные
пересчитываются. В чек-лист Ф1.

**2.3 (тай-брейки кучи) — ПРИНЯТО.** Тест идентичности pop-последовательности
+ правило «типизированная куча воспроизводит цикл сравнения старой
алгоритмически». Вместе с понижением А4 до «строго по профилю» (см. п.7)
куча вообще может не понадобиться.

**2 (дифф-фаззинг) — ПРИНЯТО с уточнением механики.** «Old/new в одном
процессе» неудобен (две копии модулей); реализация: фазз-полигон с
golden-дампами — генератор синтетических сцен по сидам (узлы, рёбра, рамки,
frame-концы, вееры, рельсы), env-гейт `ARCHMAP_FUZZ_DUMP=запись/сравнение`;
до правки пишем golden на HEAD, после правки сравниваем побитово. 200–500
сидов. Строится в Ф0, гейт каждого коммита Ф1 наравне с дампами 4 сцен.

**3.1 (гейт записи кэша) — ПРИНЯТО.** Запись только: quality-стадии
отработали И unmeasured == 0 И прогон не scoped И не взят из осцилляционного
prev-выхода (это следствие «стадии отработали»). Все пять перечисленных
тестов — в Ф2.

**3.2 (хэш-тест ROUTER_VERSION) — ПРИНЯТО.** Механика вместо дисциплины:
vitest-тест собирает все влияющие константы (роутер, нуджинг, джоги, сварка,
геометрия плашек — формула плашки рамки `56 + 6.5·len` выносится из
pipeline.ts в именованную константу, чтобы участвовать) → хэш → сравнение с
зарегистрированным для текущего ROUTER_VERSION. Контрольная проверка гейта:
правка JOG_MAX без бампа обязана уронить тест. Обязательный гейт Ф2.

**3.3 (побитовость sig между сессиями) — ПРИНЯТО.** Тест «два идентичных
прогона → sig побитово равен» — в Ф0 (дёшев, снимает риск до Ф2). Дополню
наблюдением: после первого показа узлы засеяны (own-on-first-render), и на
повторном открытии архитектора невладеемых почти нет; но у VIEWER-а засев
гейтится — вся сцена невладеемая, ELK на каждом открытии. Значит тест нужен
именно в viewer-профиле (худший случай), и если ELK там побитово стабилен —
кэш работает и для viewer; если нет — кэш честно не хитует у viewer
(деградация до текущего поведения, не ошибка).

**3.4 (LRU/квота/версия формата) — ПРИНЯТО.** В Ф2.

**4.1 (prevPositions) — ПРИНЯТО** (см. «Исполненные проверки», п.2).

**4.2 (замыкание по prev-портам) — ПРИНЯТО.** Момент уточнён: замыкание
строится ДО прокладки по портам prev-снимка (делящие prev-p0/pN — в скоуп
вместе), а не пост-фактум по смене порта. Дрейф-зонд расширяется сценарием
«лидер веера 3+ сменил порт» + evalRouteParts followers до/после.

**4.3 (слоты на границе скоупа) — ПРИНЯТО.** Обобщающий текст спеки (E84)
называет явно: замороженные слоты не передистрибутируются; скоупленное ребро
может получить portConflict там, где полный пересчёт раздал бы слоты иначе.
Синтетический тест из ревью — в Ф3.

**4 (дифф по финальным позициям) — ПРИНЯТО**, зафиксировано в дизайне Ф3:
дифф считается конвейером по СВОИМ финальным позициям текущего прогона
против финальных позиций prev-снимка (после инвариантов/A10), не по дельте
жеста.

**5 (гистограмма глубины вреза; приоритет а→б→в; г1/г2) — ПРИНЯТО
целиком.** Гистограмма — в Ф0; порядок кандидатов Б3 в v2 переставлен в
а → б → в; г1 и г2 добавлены кандидатами Ф4.

**6.1 (корреляция экспансий и времени) — ПРИНЯТО.** Scatter в Ф0; порог
калибруется по худшему ms/exp среди эталонов; при плохой корреляции единица
бюджета расширяется взвешенными prep/flood-счётчиками (они появятся по 1.1).

**6.2 (осуществимость ступеней) — ПРИНЯТО, дизайн ступеней переделан.**
Возражение справедливо: «отключить сварку при исчерпании» неисполнимо —
сварка внутри прохода-1, а 63% бюджета горит в T4. Дизайн v2 —
двухконтурный:
- РЕАКТИВНЫЙ контур: ступени на естественных границах конвейера в порядке
  исполнения — cap на вызов A* (внутри прохода-1) → пропуск rip-up (граница
  внутри routeAll) → пропуск сварки (граница перед weldTrunks) → пропуск T4
  (граница перед мини-проходом). Порядок ступеней = порядок конвейера, «цена
  жертвы» управляется порогами срабатывания, а не переупорядочиванием.
- АПРИОРНЫЙ контур: прогноз работ по классу сцены до старта (узлы/рёбра →
  ожидаемые экспансии по калибровке Ф0) — заведомо неподъёмная сцена
  включает ступени с самого начала, не сжигая 63% бюджета до первой границы.
Таблица «точка конвейера × применимая ступень» — артефакт Ф5; в P13 не
попадает ни одна ступень, неосуществимая в своей точке; тест «бюджет
исчерпан внутри T4» обязателен.

**6.3 (фолбэк cap'а) — ПРИНЯТО ЧАСТИЧНО, механика уточнена.** Согласен, что
повторный поиск сжигает бюджет дважды — отклоняю свой v1-вариант. Но
«принять первую pop-нутую goal» сам по себе экономии не даёт: при допустимой
эвристике первый pop цели и есть почти-финал поиска (bestFin-стоп добирает
только хвост целевых penalty) — дорогая часть УЖЕ позади; а если cap
сработал ДО первого достижения цели, «первой pop-нутой goal» не существует.
Механика v2: по исчерпанию cap поиск переключается в greedy-режим —
приоритет очереди становится h-доминантным (лучший-первым к цели), поиск
дотягивается до ближайшей цели за O(длина пути) экспансий. Маршрут валиден
(E19/E15/E14 держатся по построению сетки), субоптимален по штрафам,
детерминирован (переключение по детерминированному счётчику). Пустая
очередь → прежняя лестница margin/null. Юнит-тест из ревью остаётся.

**7 (порядок фаз, понижения) — ПРИНЯТО.** Ф1 до Ф2 (аргумент про
ROUTER_VERSION-протухание принят); А3(б) переформулирован по В8.3 (см.
ниже); А4 — «строго сколько покажет профиль», оценка «10–20%» из плана
убрана.

**В8.1 (T4 и frame-концы) — ПРИНЯТО** (см. «Исполненные проверки», п.3).

**В8.2 (replay-prof в репо) — ПРИНЯТО.** Первый коммит Ф0.

**В8.3 (А3(б) размыт) — ПРИНЯТО.** Переформулировано: при недостижимости на
первой ступени — построить сетку+flood СРАЗУ для margin=0; недостижимо и
там → null немедленно (минуя 6/3/1.5 — экономия 3 сборок сетки на истинно
запертых портах); достижимо → лестница продолжается как раньше (ответ —
максимальный проходимый margin, поведение байт-в-байт). Счётчик «ретраи →
null против успешной ступени» — в Ф0, он же скажет, окупается ли пункт
вообще.

**В8.4 (разбивка T4 изнутри) — ПРИНЯТО.** Стадийная разметка счётчиков
внутри T4 (A*-проход/rip-up/слоты/сварка) — в Ф0.

**В8.5 — принято к сведению, действий нет.**

## По топ-3 рискам

**R1 (разрыв холодного P2) — ПРИЗНАН, решение эскалировано пользователю.**
Противоречие реально: после Ф1 холодное открытие Zabbix-корня ~10–11с
(подтверждено контрзамером: 16.7 − ~5с дельты T4 − вклад А2/А3), дальше
холодный путь ускоряют только Ф4 и эксперименты — до 1.5с (типовая!) не
достаёт кратно. Варианты решения — в плане v2 как ГЛАВНЫЙ открытый вопрос
№0, включая третий вариант сверх предложенных Qwen: холодное открытие
двухфазно (бюджетный прогон со ступенями → показ → фоновый полный →
подмена маршрутов; прецедент жертвы промежуточного кадра уже утверждён в
P10). Решает пользователь.

**R2 (протухший кэш) — ПРИНЯТ**, закрыт механикой 3.2 (хэш-тест констант
как обязательный гейт Ф2).

**R3 (дрейф Б2) — ПРИНЯТ.** Количественный критерий в спеку до Ф3: серия
10 раскрытий/сворачиваний на эталоне → метрики качества не хуже базлайна
на согласованный допуск; «Переразложить» после серии сходится к полному
пересчёту (побитово равен прогону без prev). Артефакты границы (висящие
стволы, нуджинг-зазоры) — в чек-лист приёмки глазами.

**R4 (ловушки А2/А4)** — в чек-лист Ф1 (2.1–2.3), плюс фазз-полигон.

## Позиции Qwen по открытым вопросам — учтены

Совпадают с моими рекомендациями (localStorage-старт с абстрактным
интерфейсом хранения; жертвы Б2/Б3 приемлемы при метриках+глазах;
прогрессивный показ вне эпика). Вопрос №3 плана поглощён R1 (вопрос №0 в
v2). Финальные решения — за пользователем.
