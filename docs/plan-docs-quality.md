## Отличие от методики C4

У состава был реестр в коде, и compare.py матчил узлы механически. У алгоритма реестра нет, поэтому истина
эталона — не картинка, а **реестр фактов** (шаги, развилки с исходами, зависимости с режимом, лог-точки и
исходы ошибок, пары предшествования), каждый с доказательством `file:line`. Единственное место, где нужна
модель-судья, — выравнивание вершин кандидата на факты реестра; всё остальное считается механически.

## Эталон = четыре артефакта

Схема `.mmd` по конвенциям продукта (заголовки `%% archmap-*`, пометки, ≤ 30 вершин); `facts.yaml`
(реестр); `deps.yaml` (справочник таблиц/каналов/параметров ДОСЛОВНО из кода — каталог для штатного
резолва пометок); `questions.yaml` (6–8 вопросов оператора с ключом). Рубрика читаемости R1–R6 и схемы
файлов — materials/docs-etalons-2026-09-08/rubric.md. Сборка: строитель (сильная модель) → скептик
полноты по коду → правки → скептик абстракции по рубрике → правки → механические проверки → заморозка.

| метрика | что мерит | как считаем | тип |
|---|---|---|---|
| Синтаксис | рендерится ли | Mermaid версии фронта (11.15) в headless Chromium | бинарная |
| Формат ArchMap | заголовки, kind, operation, разбор пометок | превью импорта без ошибок разбора | бинарная |
| Резолв зависимостей | «ArchMap сможет интерпретировать» | импорт в проект с каталогом из deps.yaml, нерезолвленных пометок (AL29/AL30/AL33) | счёт, норма 0 |
| Верность зависимостей | имена и режимы против кода | множества (имя, режим) против реестра: полнота/точность по таблицам, каналам, параметрам; режим отдельно | механически |
| Полнота шагов и развилок | пропуски операций и условий | судья выравнивает вершины кандидата на факты («есть/частично/нет» + цитата вершины), доли считаются механически; развилка = условие + оба исхода | судья + счёт |
| Лишнее и выдумки | чего нет в реестре | вершины без факта; до заморозки судья с кодом делит на «верно, эталон неполный» / «детализация» / «выдумка»; после — доля лишнего как Xn | судья + счёт |
| Порядок | последовательность | пары предшествования реестра проверяются достижимостью в графе кандидата после выравнивания | механически |
| Лог-точки и исходы | видно ли оператору, что логируется и как падает | подмножество фактов, полнота отдельным столбцом | счёт |
| Уровень абстракции | нет ли кода в подписях | доля вершин с кодовыми идентификаторами вне пометок (CamelCase, snake_case со скобками, self/this, пути, «класс/функция/метод»); эталоны ≈ 0 | механически |
| Тест оператора | читаемость как полезность | судья видит ТОЛЬКО схему кандидата и отвечает на вопросы оператора; доля верных; контроль: эталон 100 %, пустая схема ≈ 0 | судья + счёт |
| Компактность | обозримость | вершины кандидат/эталон, длина подписей, доля развилок, кап 30 | механически |
| Надёжность судьи | можно ли верить | два прогона судьи, каппа; калибровка на двух ручных разметках | служебная |

Сводная метрика (аналог D): Dice по фактам (шаги + развилки + зависимости). Панель рисков: выдумки,
резолв, абстракция, тест оператора, синтаксис, размер. Вердикт как в Ф3: пять повторностей, сдвиг только
за размах, Манн–Уитни p ≤ 0.1; один замер Opus как потолок. Оговорка про судью-оператора: модель читает
кодовые идентификаторы без труда и не штрафует «схему для разработчика» — поэтому уровень абстракции
считается отдельным лексическим фильтром, а не доверяется тесту.

## Базлайн промпта доков — раунд base (2026-09-10/11)

**Стенд.** Каталог замеров `materials/docs-runner-2026-09-10/` (README там): пять полигонов в БД «<Продукт> Docs-base
2026-09-10» — копии эталонных C4-проектов (Mastodon — малый C4 из трёх узлов) со снятыми схемами в поддереве владельца и
каталогами таблиц/каналов/параметров из deps.yaml эталона; промпт доков штатной ручкой GET /docs-import/prompt с node_id
владельца, include=logic, target = сценарий («POST /api/v1/messages», «monitors-clock-tick», «тик планировщика алертинга
ngalert», «escalator», «POST /api/v1/statuses»). Репозитории продуктов переклонированы на коммиты эталонов (`repos/`).
Строитель — Haiku 4.5 (Agent, model=haiku), 5 реплик на эталон = 25 сессий, 65–115k токенов и 2–12 мин каждая; пакет пишется в
каталог реплики вместо корня репозитория. Механика — `tools/collect.py` (синтаксис Mermaid 11.15, шапка и превью дозаливки в
полигон, нерезолвленные пометки по семьям, пары зависимостей (имя, режим) против фактов D, компактность, лексический фильтр
абстракции, граф рёбер); судья-выравниватель (модель по умолчанию, только текст, без кода) → alignment.yaml; оператор (только
схема) → answers.yaml; оценщик по эталону → grades.yaml; `tools/panel.py` → summary-base.md. Dice = 2·(S_f+0.5S_p+B_f+0.5B_p+D_hit)
/ (|S|+|B|+|D_fact|+V+|D_cand|).

**Контроли пройдены.** Эталоны через сборщик: синтаксис и формат ок, пары D полные, нерезолв 0 (кроме Mastodon — см. P2).
Тест оператора: эталон 100 % на всех пяти, пустая схема 0 % на всех пяти (оператор не отвечает по памяти о продукте).
Надёжность судьи: второй прогон на реплике a пяти эталонов — совпадение статусов 97 % (дальше хватает одного судьи).

## Открытые вопросы к этапу правок

- **Оркестраторный вариант промпта доков не замерен раннером** (находка 2026-09-17, вопрос пользователя). Кнопка «Доки от
  агента» по умолчанию копирует обёртку «строитель → скептик → починка → скептик» (эпик аудита скептиком, кап два круга; в API

  Правки строителя переносятся в обёртку дословно (блок А), поэтому не обесцениваются, но вклад скептика в полноту схем логики
  (S, B, L, Op) не измерен ни разу: на C4 его мерили (потолок Opus, кап кругов), для доков — только полевые прогоны на алерты и
  синтаксис; чек-лист скептика нацелен на пометки и расхождения с кодом, класс «пропуск» оговорён одной строкой. Кандидат на
  замер ПОСЛЕ правок строителя: один раунд «оркестратор на Haiku» (строитель и скептик — Haiku, оркестратор — модель
  пользователя) против лучшего строительного раунда на тех же метриках; если вклад мал — следующая цель правок чек-лист
  скептика, а не строителя.
