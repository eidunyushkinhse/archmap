# Полевой QA разведки (Zulip, 2026-08-17)

Первый живой прогон эпика: до этого всё было проверено тестами, то есть было известно
лишь, что код делает написанное в коде. Здесь путь проходится дефолтной кнопкой на
монолите с механически посчитанной истиной (docs/qa-recon-completeness.md).

Стенд: репозиторий Zulip, `variant=orchestrated` (два независимых разведчика →
объединение командой → скептик), слабая модель (Haiku). Артефакты прогона —
scratchpad/f5/, служебные файлы петли — `archmap-orch/` в самом репозитории.

## Часть 1. Разведка и приём (измерено, проверено по коду)

### Числа

| | |
|---|---|
| Операций в перечне | **330** (уникальных после нормализации 326) |
| Воркеров (очередей) | 14 |
| **Полнота по истине ядра** | **208 / 212 = 98.1 %** |
| Строк вне истины | 118 |
| — из них РЕАЛЬНЫХ (проверено по коду) | 22 |
| — из них ЛОЖНЫХ | **96** |
| Отчёт скептика | 2 строки, обе — верные пропуски |

Полноту считал скриптом по нормализованной паре «метод + путь» (префиксы монтирования
`/api/v1` и `/json` снимаются: истина и ответ пишут их по-разному, и без нормализации
сравнение мерило бы не то).

### Что сработало

1. **Объединение двух прогонов держит полноту**: 98.1 % ядра одним заходом петли.
2. **Скептик дал два верных пропуска и ни одного ложного**: обе строки
   (`POST /json/{realm,server}/…/billing/session/start_card_update_session`) проверены
   в `corporate/urls.py:353-357` — существуют.
3. **Приёмник сам выбрал объединённый файл из трёх** (в репозитории после петли лежат
   `archmap-recon.yaml` и два черновика прогонов): в предупреждениях названо, что взято
   и что пропущено, ошибки нет. Доработка Ф1 подтверждена на живом.
4. **Сомнения разведчика доехали до пользователя**: раздел `doubts` пробрасывается в
   предупреждения превью. Одно из них — прямо про вебхуки (см. ниже), то есть модель
   сама отметила слабое место.
5. Превью на 344 строки собралось без ошибок, действия — все `create`.

### ⚠️ Дефект №1 (главный): пример из промпта утёк в данные

**96 строк вида `POST /hooks/<интеграция>` — путь, которого в Zulip нет.** Реальные
вебхуки монтируются как `POST /api/v1/external/<имя>`; слово «hooks» встречается в
`zproject/urls.py` ровно один раз и это флаг `allow_incoming_webhooks`, а не маршрут.

Источник найден точно. В правиле промпта про маршруты, сгенерированные циклом, стоит
иллюстрация:

> Такую группу выпиши ОДНОЙ строкой `operations` — путь-шаблон дословно как в коде
> (**`POST /hooks/<name>`**), а сколько их и из какого справочника — строкой в `sources`.

Модель взяла из репозитория справочник интеграций (`INCOMING_WEBHOOK_INTEGRATIONS`),
но приклеила к его именам **префикс из примера**, а не из кода. Заодно нарушила и само
правило «ОДНОЙ строкой», выписав 96 отдельных.

Это **пятое подтверждение правила «ПРИМЕР СИЛЬНЕЕ ПРАВИЛА»** и первый случай, когда
иллюстрация утекла не в форму ответа, а в его СОДЕРЖАНИЕ. Цена — 29 % перечня: приёмник
создал бы 96 заглушек с адресами, которых нет в коде, и пользователь пошёл бы описывать
несуществующие операции.

⚠️ Гипотеза о вкладе Ф0 (не проверена): в черновике, показавшем 100 %, пример был
длиннее — «`POST /hooks/<name> — 40 шт., генерируется из списка PROVIDERS`», то есть
внутри самой строки стояло указание на свёртку. При переносе в YAML-формат счёт
переехал в `sources`, и «одной строкой» осталось только правилом. Возможно, это
ослабило свёртку — но прямого сравнения двух формулировок на одном стенде не делалось.

### ⚠️ Дефект №2: скептик не заметил 96 ложных строк

В чек-листе потока `recon` пункт есть: «Строки перечня, которых в коде НЕТ: путь или имя
очереди, не находимые поиском по репозиторию, — сомнение». Он стоит ПОСЛЕДНИМ и без
метода проверки, тогда как остальные пункты (замеренные) снабжены способом «как искать».
Скептик отработал только обратную задачу (пропуски) — ровно ту, на которой он и мерялся.

### Истина узка — 22 строки «вне истины» реальны

Проверено по коду, моделью названы верно:
- **9 строк биллинга** (`/realm/<realm_uuid>/billing/…`, `/server/<server_uuid>/…`) —
  `corporate/urls.py:368-370` и рядом; экстрактор истины их не собрал, потому что они
  объявлены через `path(...)`, а не через `rest_path`/`remote_server_path`;
- **13 прочих маршрутов** репозитория, попадающих в `urls_other.tsv`.

⚠️ То есть автоматический счёт «выдумок» соврал бы в полтора раза: скорер насчитал 94,
из них реальными оказались не все, но и ложными — не все. Дисциплина «проверь спорную
строку по коду, прежде чем записать модели ошибку» сработала второй раз за эпик (первый —
при построении самой истины, docs/qa-recon-completeness.md).

## Часть 2. Документирование по списку

Не пройдена: прогон остановился на разборе спорных строк. Шаги, оставшиеся к замеру, —
описание заглушек через кнопку «Описать» (проверка `fill` на живом), рост счётчика,
повторная разведка без дублей, алерты-паразиты.

## Вердикт (по части 1)

Механика пути работает: полнота высокая, объединение и скептик дают вклад, приёмник
разбирается с папкой прогона сам, сомнения доезжают до человека. Но **перечень
непригоден к заливке без правки промпта**: почти треть строк — адреса, которых нет в
коде, и родились они из иллюстрации в самом задании.

Первое, что чинить: убрать из промпта конкретный путь-пример и усилить в чек-листе
скептика проверку «каждая строка находится поиском по репозиторию» — с методом, как у
остальных пунктов.
