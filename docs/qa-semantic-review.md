# Семантический аудит документации «Zulip v2» и «Sentry v3» (2026-08-15)

Вопрос: осмысленна ли документация, которую Haiku довёл до нуля алертов, — при
сопоставлении с фактической архитектурой сервисов. Метод: два независимых
фактчекера (Opus) построчно сверили пакеты с кодом клонов и официальными доками
(zulip: docs/overview/architecture-overview.md и docs/subsystems/*; sentry:
develop.sentry.dev + devservices/config.yml); вердикт и синтез — мои. Все
претензии ниже имеют доказательства файл:строка в отчётах проверок; здесь —
главное.

## Вердикт одной строкой

Оба пакета **точны в «списочных» слоях и систематически врут в «смысловых»**:
что можно механически считать с кода (имена очередей, таблиц, колонок, сервисов),
слабая модель списывает почти безупречно; где нужно ПОНИМАНИЕ (топология, направления,
привязка каналов к шине, технологии, сюжет потока) — она достраивает «типовую
архитектуру» из шаблона, и эта достройка самосогласована: выдумка подпирает выдумку,
и изнутри пакета её не опровергнуть.

## Главные искажения — Zulip v2

1. **Elasticsearch — выдуман целиком и самосогласованно**: узел + ребро «индексация
   для поиска» + схема 19 с шагами «запрос к поисковому индексу» и НЕСУЩЕСТВУЮЩИМ
   эндпоинтом `GET /messages/search`. Реальность: поиск — Postgres FTS
   (`zerver_message.search_tsvector`, docs/subsystems/full-text-search.md), поисковый
   оператор живёт внутри `GET /messages` narrow.
2. **Tornado «читает БД»** в схеме long-poll — прямо против главного ограничения
   дизайна («no DB/cache queries in Tornado paths», architecture-overview.md);
   `fetch_events` работает только с in-memory очередями.
3. **Push через «Firebase»**: выпал штатный Push Notification Bouncer
   (push.zulipchat.com — транспорт самохостед-серверов) и ВЕСЬ APNs; таблица
   `zerver_pushdevicetoken` — legacy-путь, современный E2EE идёт через `Device`.
4. **Redis-мифология**: модель отдаёт Redis сессии и state Tornado-очередей; реально
   сессии — memcached+Postgres, очереди Tornado — память+файл, Redis — рейт-лимиты.
5. **corporate-app → django-api «по HTTP»** — оба Django-приложения одного процесса.
6. Склейка `digest_emails` (периодический дайджест) с «missed messages»
   (`missedmessage_emails` — другая очередь, воркера в модели нет вовсе).

Главный пропуск: **Tornado — сам продюсер** очередей push/email-уведомлений
(`event_queue.py:1063,1079`) — ни модель, ни одна из 30 схем этого не показывают,
цепочка «сообщение → push» в пакете обрывается. Плюс 7 из 14 продовых очередей
задокументированы как каналы, но потреблять их в модели некому.

## Главные искажения — Sentry v3

1. **Ось системы подменена**: узла Kafka НЕТ, вся шина отдана «sentry-taskbroker».
   Реальный taskbroker обслуживает ~9 топиков задач; **44 из 53 каналов пакета
   повешены на узел, который их не видит**. README пакета сам пишет «all Kafka
   broker channels» — данные говорят taskbroker. Это находка №1 Sentry-v1 в новой
   форме: тогда всё свалили на kafka, теперь всё на taskbroker; Ф7б бессилен —
   брокер в схеме один, выбирать не из чего (корень — уровень ИМПОРТА).
2. **`sentry-tasks` — 0 вхождений в репозитории**, но объявлен `kind: topic`,
   протянут через 4 связи модели и 5 схем, и снабжён выдуманным полем `silo_mode`,
   описывающим несуществующий механизм маршрутизации (реально роутит продюсер по
   namespace; silo фиксируется при старте процесса).
3. **Инверсия поиска (схема 007)**: поиск issues показан как Postgres-fulltext со
   Snuba «для статистики»; реально `SENTRY_SEARCH` — Snuba-бэкенд, Snuba и есть
   поисковый движок.
4. **Связи**: `Web/api → Relay` развёрнута (Relay сам ходит за конфигом);
   `Snuba → sentry-db` — выдумка; `Launchpad → Snuba` — выдумка (и это его
   единственная связь); Symbolicator зовётся HTTP из задач, не gRPC из API.
5. **«Таблицы» sentry-cache — 1/9 точна**: три записи — на самом деле Postgres-таблицы,
   одна — питоновский dict, «sessions» — signed cookies; Redis-неймспейсы поданы как
   схемы с колонками. Плюс 3 abstract-класса Django выданы за таблицы, и два файла
   структуры дублируют один узел.
6. Пропуски: Kafka, ClickHouse, nodestore (где реально лежат тела событий),
   post-process-forwarder, Seer.

## Паттерн (важнее частностей)

1. **Списочное — можно доверять**: инвентари имён (очереди, топики, таблицы,
   сервисы, колонки) списаны с кода с точностью 96–100% и реально экономят часы.
2. **Смысловое — нельзя без вычитки**: топология, направления, привязка к шине,
   технологии, сюжеты — конфабуляции в духе «типовой системы» (раз поиск →
   Elasticsearch; раз push → Firebase; раз Redis → сессии; раз каталог corporate →
   отдельный HTTP-сервис; раз брокер → один).
3. **Ноль алертов ≠ правда.** Валидатор сторожит СОГЛАСОВАННОСТЬ — и слабая модель
   производит согласованную ложь: elasticsearch-узел + ребро + схема; sentry-tasks
   канал + связи + схемы + поле. Самосогласованность — ровно то, что петля замечаний
   поощряет. Семантика проверяется только против кода — вторым проходом.

## Кандидаты для продукта (НЕ в работе — решение за пользователем)

- Промпт импорта: «каждая технологическая шина — ОТДЕЛЬНЫЙ узел-брокер (Kafka и
  очередь задач — разные узлы)»; «узел-хранилище/поисковый движок должен иметь
  основание в коде или конфиге деплоя — не добавляй по типовой аналогии»;
  «technology бери из манифестов (Cargo.toml, package.json), не угадывай по роли».
- Тот же принцип «цели с ответом» для связей недоступен (код валидатору не виден) —
  класс лечится только ВТОРЫМ агентским проходом: BYOA-«аудит пакета» промптом
  скептика («докажи по коду каждый узел-хранилище, каждую связь и направление;
  верни список недоказанного») — кандидат на новую фичу рядом с дозаливками.
- Превью данных: предупреждать «два файла пакета адресуют один узел» (дубль схемы) и
  «db_table-имя не в snake_case модели» — дёшево, ловит abstract/угаданные имена.
- Превью каналов: Ф8е-замечание дополнить «канала нет в коде — НЕ добавляй его в
  пакет» (урок «sentry-tasks»: соглашательство хуже пропуска).
