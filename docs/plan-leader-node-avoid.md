# План: поводки выносок по возможности не ныряют под узлы

Статус: Ф1 СДЕЛАНА 2026-07-15, ждёт глазной проверки. Итоги реализации:
- Ключ расширен как задумано; сигнатура placeLabels всё же изменилась (план это
  упустил): obstacleRects живого драга (чужие плашки) теперь идут ОТДЕЛЬНЫМ
  4-м параметром, не подмешиваются в nodes — иначе live-скоринг штрафовал бы
  поводок за чужие плашки, а финальный нет (расход live==final).
- Метрики сцены «Ярмарки» (leader_check.ts): поводков под узлами A 1→0, B 4→1.
  Остаток d8d57a99 вынужденный в точном смысле: чистых направлений поводка 23
  из 48, но у всех бокс грязный (узлы/плашки/чужие плечи) — старшие компоненты
  ключа сознательно перевешивают.
- Дамп-гейт: routes/handles/positions бит-в-бит на A/B/B_prev; изменились
  только плашки нырявших рёбер; T4-каскад не сработал (риск не материализовался).
- vitest 395 (+6), tsc чистый. Ф2 (запасные якоря) НЕ делалась — триггер:
  вынужденные нырки мешают глазам.

Заказ 2026-07-15: пунктирный поводок вынесенной
плашки может проходить под узлами — читаемость страдает. Требование мягкое:
НЕ запрещать полностью (в тесноте плашке бывает некуда деться — тогда поводок
под узлом допустим), но по возможности избегать.

## Диагноз (где именно дыра)

Размещение плашек — жадный best-fit в `placeLabels.ts` (`frontend/src/components/graph/layout/placeLabels.ts`).
Для каждой плашки генерятся кандидаты: online (точки вдоль своей линии) и
leader (отступ от якоря по 8 направлениям × 6 магнитуд, `leaderCands`,
placeLabels.ts:86). Выбор — лексикографический ключ (placeLabels.ts:202-221):

    [ovHard, ovLegs, online<leader, cross, k]

- `ovHard` — наложения САМОЙ ПЛАШКИ на узлы + уже размещённые плашки (жёсткое);
- `ovLegs` — наложения ПЛАШКИ на чужие плечи стрелок (мягкое);
- `cross`  — пересечения ПОВОДКА с чужими стрелками (`connectorCrossings`,
  placeLabels.ts:148-155);
- `k` — индекс-предпочтение (ближе к якорю / оси раньше диагоналей).

Пересечение поводка с УЗЛАМИ не оценивается НИГДЕ. Кандидат «бокс чист, но
пунктир идёт сквозь узел» равен по ключу кандидату с полностью чистым
поводком — побеждает тот, что раньше по k (ближе/осевее), и пунктир ныряет
под узел. Рендер (edges.tsx:253-261) рисует поводок anchor→center в SVG-слое
рёбер, узлы — HTML поверх: участок под узлом буквально невидим, связь
«плашка ↔ стрелка» на глаз рвётся.

Препятствия в вызовах уже под рукой: pipeline.ts:511-513 передаёт `nodeRects`
(тела узлов уровня + гостей, БЕЗ рамок раскрытых контейнеров — рамки идут
отдельным списком `routerFrames`), живой драг (useLiveDragHandles.ts:237)
собирает тот же список. Т.е. сигнатуру `placeLabels` менять не нужно.

## Решение (Ф1, ядро)

Новый компонент ключа `nodeCross` — число узлов из `nodes`, которые пересекает
отрезок поводка anchor→leaderEnd (тот же отрезок, что оценивает `cross`;
хвост leaderEnd→center лежит под боксом плашки, а чистоту бокса уже держит
`ovHard`). Считается только для leader-кандидатов, у online всегда 0.

Новый ключ:

    [ovHard, ovLegs, online<leader, nodeCross, cross, k]

Позиция `nodeCross` — между режимом и `cross`:
- слабее `ovHard`/`ovLegs`: «текст лёг на узел/чужую линию» хуже, чем
  «пунктир нырнул под узел» — текст портится прямо, приоритеты статус-кво
  не пересматриваем;
- сильнее `cross`: исчезновение поводка под узлом хуже, чем видимое
  перекрестье с чужой стрелкой;
- относительно флага online/leader позиция ничем не проявляется (у online
  nodeCross=0 по построению), ставим после флага для читаемости.

Мягкость по построению: это счётчик в лексикографике, не запрет. Есть чистое
направление — выигрывает оно (даже если дальше от якоря или диагональное);
все направления грязные — выбирается минимум пересечений, плашка размещается
всегда. Ровно «по возможности избегать».

Реализация:
- `placeLabels.ts`: хелпер `segCrossesRect(a, b, r)` — пересечение отрезка с
  прямоугольником по Лиангу-Барски (родня уже живущего там `boxEntryParam`;
  «якорь внутри узла» считаем пересечением — клиника, штраф уместен) +
  `rectCrossings(a, b, rects)` — счётчик; в цикле кандидатов
  (placeLabels.ts:209-221) ключ расширяется до 6 компонент.
- Больше НИЧЕГО не трогаем: `leaderCands`, якорь (центр длиннейшего
  уникального плеча, A15), интервалы online (labelCandidates), вызовы в
  pipeline.ts:558/611 и useLiveDragHandles.ts:253 остаются как есть — новый
  скоринг автоматически действует и в финале, и в живом драге (live==final
  сохраняется по построению: движок один).

Оценка перфа: +48 leader-кандидатов × ~10-30 узлов Лианга-Барски на одну
выноску — на порядок дешевле уже существующих проверок тех же кандидатов по
~сотне legRects/сегментов (overlapCount + connectorCrossings). В живом драге
размещаются только затронутые жестом плашки (1-3) — вклад не заметен.

## Скоуп / не-скоуп

Делаем (Ф1): штраф nodeCross по телам узлов (локалы + гости) для level/main.

Сознательно НЕ делаем:
- Контекст-схема не затрагивается: buildLabelPlacements зовётся только в
  `!isContext`-ветке, у контекста своя модель подписей (полка).
- Плашки раскрытых рамок («🔍 имя ✕») в препятствия поводка НЕ добавляем:
  пришлось бы менять сигнатуры/вызовы ради редчайшего кейса, а включение их
  в общий `nodes` изменило бы заодно ovHard и online-домен (расширение
  поведения без заказа). Поле раскрытой рамки — прозрачное, проход поводка
  по нему легитимен, ложных штрафов нет уже сейчас.
- Излом поводка (Г-образный обход) — поводок остаётся прямым by design.
- Изгиб МАРШРУТА ради плашки — детур-стадия A12 удалена осознанно
  (2026-07-13), не возвращаем.

Ф2 (опционально, ТОЛЬКО если после Ф1 глазами останутся частые вынужденные
нырки): запасные якоря вдоль ТОГО ЖЕ длиннейшего уникального плеча (доли
0.25/0.75 в дополнение к центру), пробуются только когда от центрального
якоря все 48 кандидатов грязны по nodeCross. Опознаваемость сохраняется
(отрезок тот же), пространство поиска ×3 только в вырожденных случаях.
По умолчанию НЕ делаем — сначала смотрим эффект Ф1.

## Тесты (vitest, placeLabels.test.ts)

1. «Поводок обходит узел»: якорь замурован сверху/снизу вплотную
   (A={70,-46,60,40}, B={70,6,60,200}, путь (0,0)→(200,0), candidates=[]) —
   по старому ключу первым чистым боксом идёт кандидат НАД A с поводком
   сквозь A (k=16), по новому побеждает боковой с чистым поводком (k=18).
   Assert поведенческий: mode=leader и отрезок anchor→center не пересекает
   ни A, ни B (не привязываться к точному центру). Конструкция проверена
   на числах при анализе.
2. «Вынужденный нырок допустим»: якорь замурован со всех сторон (все чистые
   боксы только за препятствиями) — плашка ВСЁ РАВНО размещается (leader),
   nodeCross>0 не отвергает кандидатов насмерть.
3. Обратная совместимость: существующие тесты проходят без правок — при
   пустых `nodes` (большинство кейсов) nodeCross=0 у всех, ключ эквивалентен
   старому.

## Риски

- Каскад T4: переехавшая выноска меняет labelRect → «грязные» маршруты могут
  перепроложиться. Это заказанное изменение поведения, не регрессия; дамп-гейт
  подтверждает, что каскад ограничен затронутыми рёбрами.
- Хвоста магнитуд (до ~142px от якоря) может не хватить, чтобы «выпрыгнуть»
  за крупный узел — тогда останется вынужденный нырок (допустимо по ТЗ).
  Рычаги на потом: удлинить ряд магнитуд или Ф2 (запасные якоря).
- Перф живого драга — см. оценку выше, вклад ничтожен; при сомнении быстрый
  профиль жеста в devtools.
