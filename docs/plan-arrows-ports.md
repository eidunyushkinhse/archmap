# План эпика «Стрелки без жёстких хэндлов: порт на связь, как в Mermaid» (старт 2026-10-10)

СТАТУС: Ф0 (полигон + базлайн + правила на бумаге) СДЕЛАНА 2026-10-10. Ветка эпика —
feat/arrows-ports. Дальше: Ф1 — порт на связь.

## Мотив

Пользователь (2026-10-10, по испытаниям демо на людях): корневая схема «Ярмарки»
выглядит плохо; в актуальном Mermaid узлы даже с большим числом стрелок выглядят
аккуратно; «от хэндлов, скорее всего, придётся отказаться». Это поднятый из бэклога
эпик-кандидат «СТРЕЛКИ БЕЗ ЖЁСТКИХ ХЭНДЛОВ» (идея 2026-09-29): роутер сводит концы
разнонаправленных стрелок в один хэндл вопреки запретам, а мягкие правила действуют
только на «фокус» сдвига.

Решения пользователя (2026-10-10):
- старый роутер в прежнем виде не используется нигде: ОДИН роутер по правилам Mermaid
  и при автораскладке, и после ручных сдвигов (вариант «маршруты ELK при авто, наш
  роутер после сдвига» отвергнут: два вида схемы и два кода);
- от 12 фиксированных хэндлов отказываемся полностью: точки стыковки динамические, по
  одной на связь, с равным шагом, как в Mermaid;
- пучки (несколько связей одной пары — одна линия со списком) ОСТАЮТСЯ;
- у рамок (длинные стороны) точки — проекция дальнего конца с минимальным зазором, а
  не равный шаг по всей стороне;
- UX протяжки новой связи и перевеса существующей решается по ходу эпика отдельно.

## Разбор Mermaid 12 (факты, субагент 2026-10-10; исходники develop 33d0a499, npm 12.1.0)

- С 12.0.0 flowchart по умолчанию раскладывается ELK layered (тот же elkjs, что у нас);
  dagre — только `layout: dagre`. Лицензия MIT. Отдельного роутера НЕТ: позиции и
  маршруты считает ELK одним прогоном.
- Порты неявные, по порту на конец связи. Сторона — по слоям: к нижним слоям — низ,
  к верхним — верх; входы и выходы ВПЕРЕМЕШКУ на одной стороне. Позиции — поле ~10 px и
  равный шаг (L − 2·поле)/(k + 1); порядок — из минимизации пересечений (≈ по дальнему
  концу). У каждой связи своя дорожка в канале между слоями (mergeEdges=false).
- Подписи — объекты раскладки (inline): место под них резервирует ELK.
- Постобработка Mermaid: ступеньки ≤16 px в 30 px от порта выпрямляются, скругление
  r=5, дуги-переходы r=6, расталкивание встречных подписей.
- Для узлов, сдвинутых вручную, Mermaid стрелок не строит. ELK «только трассировать»
  при закреплённых позициях не умеет: INTERACTIVE-стратегии двигают узлы на 31–136 px,
  алгоритм fixed рёбра не трассирует, libavoid есть только в Java-ELK.
- Замер: на узле 152×66 семь портов в раскладке сверху вниз стоят с шагом 16,5 px,
  слева направо — 5,8 px. Для широких узлов с хабами сверху вниз просторнее.

## Что показал код (разведка 2026-10-10)

«Грязь» на корне — следствие одного решения: 12 слотов на узел (constants.ts
SIDE_HANDLES, доли продублированы в autoRoutes/quickConnect/shapes).
- Сторону и слот выбирает A* среди 12×12 портов на связь (orthoRoute/routeAll); занятые
  слоты гонят связь на другую сторону — отсюда петли вокруг соседей.
- Стволы E25, сварка E78/E79 (weldTrunks), группы канального нуджинга, замыкание скоупа
  E84, хит-тест ствола E80 — всё существует потому, что связи делят слот. Рельсы встречных
  пар A11 и штраф чужого порта PORT_CONFLICT_COST=600 лечат тот же симптом.
- Подписи ставятся ПОСЛЕ прокладки; роутер их размер не видит (LABEL_CROSS_COST только
  под T4_REROUTE=false); невлезающая подпись уходит на выноску-поводок.
- ELK получает узлы фиксированного размера NODE_W×NODE_H и рёбра без подписей; из его
  ответа берутся только x/y, sections выбрасываются.
- Живой драг роутер НЕ гоняет: концы инцидентных связей интерполируются из снимка;
  после дропа перепрокладываются только инцидентные рёбра, остальные заморожены (E84).
  Шапка useLiveDragHandles.ts обещает роутинг на каждом кадре — противоречит коду.
- Жёсткая зависимость рендера: edges.tsx переснимает концы линии с DOM-хэндлов React
  Flow (E81, seamRoute), без найденного id хэндла RF ребро не рисует (ошибка 008).
  Для динамических точек это надо развернуть: точка роутера — главная.

## Правила нового роутера (на бумаге; уточняются по полигону)

- **R1 — порт на связь.** У каждого конца каждой нарисованной линии (пучок = одна
  линия) своя точка на контуре узла. Общих точек нет по построению.
- **R2 — сторона.** Ось потока уровня — направление автораскладки (при DOWN —
  вертикаль; у сохранённых уровней выводится из геометрии: Σ|dx| против Σ|dy| по
  связям). Если узлы РАЗНЕСЕНЫ вдоль оси потока — стороны оси потока, обращённые друг
  к другу (A низ → B верх). Если узлы стоят РЯДОМ (пересекаются по оси потока) —
  поперечные стороны, обращённые друг к другу. Гистерезис ±16 px, чтобы при драге
  сторона не дёргалась. На раскладке ELK правило совпадает с ELK (слои разнесены по
  оси потока); правило «доминантной оси» (level.ts autoHandles) для веера хаба даёт
  боковые стороны и отвергнуто.
- **R3 — порядок.** Точки на стороне упорядочены по координате дальнего конца
  (центр узла-соседа; при равенстве — по id связи). Входы и выходы вперемешку.
- **R4 — шаг.** Узел: поле 10 px, шаг (L − 20)/(k + 1), точки симметричны относительно
  центра стороны. Рамка (раскрытый контейнер): проекция дальнего конца на сторону,
  зажатая полем, затем 1D-разведение с минимальным зазором 24 px (pav.ts).
- **R5 — своя дорожка.** Стволов, сварки и общих плеч нет. Параллельные плечи разводит
  канальный нуджинг с зазором дорожек 12 px (ELK edgeEdge ≈ 10–12).
- **R6 — подпись внутри дорожки.** Плашка лежит на самом длинном плече (предпочтение
  — подальше от узлов) и расширяет дорожку на свою ширину в нуджинге; размеры плашек и
  реальные габариты узлов передаются ELK при автораскладке (inline-подписи). Выносок
  нет вовсе; не влезающая подпись переносится по словам, в крайнем случае ложится на
  линию с подложкой (метрика это считает).
- **R7 — полировка.** Ступеньки ≤16 px в 30 px от порта выпрямляются (спрямление
  джогов уже есть), скругление EDGE_CORNER_RADIUS, дуги на пересечениях (есть).
- **R8 — пучки.** Несколько связей одной пары и направления — одна линия со списком,
  как сейчас; порт и дорожка — у линии.
- **R9 — инкрементальность.** После дропа перепрокладываются инцидентные связи; у
  соседей, чьи стороны изменили набор или порядок точек, концы НЕ-инцидентных связей
  «пересаживаются» (сдвиг конца и стаба без A*), скоуп E84 расширяется этим пересадом.
- **R10 — автораскладка.** ELK layered сверху вниз (DOWN) для всех уровней, корни тоже
  (правило N30 force/layered — проверить на полигоне и, если layered с портами выглядит
  как Mermaid, снять); узлы — реальные размеры, подписи — объекты раскладки, зазоры —
  flowSpacing; «Переразложить» возвращает вид автораскладки.

### Выводы Ф0
1. У эталона ELK ровно то, чего нет у нас: 0 общих точек, 0 езды по чужой линии, 0
   выносок, все концы на сторонах оси потока. Пересечений у ELK НЕ меньше нашего на
   плотных уровнях (6 против 4 на уровне системы): чистота крепления — это порты,
   дорожки и подписи, а не число пересечений.
2. Наш роутер на позициях ELK кладёт 28–35 % концов на боковые стороны и делит точки
   (слоты), подписи уходят на выноски — это и есть «грязь», она не от раскладки.
3. Цена обхода у ELK выше (обратные связи огибают слой: обход до 3,8), у нас ниже за
   счёт боковых сторон. Правило R2 оставляет боковые стороны только для узлов,
   стоящих рядом, — ждём рост обхода на обратных связях, как у Mermaid; это
   осознанно.
4. Полигон считает все сцены за ~2 с — гейт можно гонять на каждом коммите эпика.

## Фазы

- **Ф0 — полигон + базлайн + правила.** СДЕЛАНА (выше).
- **Ф1 — порт на связь.** Порт выбирается ДО A* по R1–R4 (сторона, порядок, шаг;
  рамки — проекция + зазор); A* получает один старт и один финиш; точка роутера
  становится главной при отрисовке (edges.tsx перестаёт переснимать концы с DOM-
  хэндлов; React Flow получает по одному служебному хэндлу на узел, чтобы ребро
  рисовалось); рельсы A11, distributeSlots, PORT_CONFLICT_COST и 12 слотов как точки
  стыковки удаляются; хэндлы-точки на узле остаются только как источник жеста (UX —
  Ф5). ГЕЙТ: sharedPorts = 0 на всех сценах; концы на оси потока = 1,00 на позициях
  ELK; порты совпадают с ELK (отклонение ≤ 4 px) не менее чем у 80 % концов.
- **Ф2 — своя дорожка.** Стволы E25, сварка E78/E79, группы ствола в нуджинге, E84-
  замыкание по стволам и хит-тест ствола удаляются; нуджинг разводит все плечи с
  зазором дорожек; пересад портов соседей после дропа (R9); гистерезис стороны в
  драге. ГЕЙТ: езда по чужой линии = 0; кресты ≤ эталон ELK + 1 на каждой сцене;
  после сдвига — те же нули; бюджет роутера (perf.md P12) не хуже базлайна.
- **Ф3 — подписи внутри раскладки.** Размеры подписей и реальные габариты узлов — в
  ELK (inline); подпись как ширина дорожки в нуджинге; плашка на самом длинном плече;
  выноски и поводки удаляются (placeLabels leader-ветка, projectLabelOntoRoute по
  необходимости); T4 упрощается. ГЕЙТ: выносок 0; подписей поверх чужой линии ≤
  эталон; оторванных от своей линии 0.
- **Ф4 — полировка и форма.** Выпрямление ступенек у порта по R7, направление DOWN,
  корни на layered (N30 — по полигону), гости при автораскладке (кольцо как сейчас
  или слой ELK снаружи родной рамки, как в эталоне — решение пользователя по
  картинкам), спеки edge/node/canvas (≈30 инвариантов: E7–E13, E21a, E25–E34,
  E36–E37, E44, E51, E59–E63, E72–E75, E78–E81, E84; N30), шапка useLiveDragHandles.
  ГЕЙТ: полный сьют, полигон на всех сценах, приёмка глазами на демо-стенде.
- **Ф5 — взаимодействие.** Протяжка новой связи и перевес с динамическими точками:
  решение пользователя по прототипу. Техническое условие: ручка перевеса сидит на
  точке роутера, а не на DOM-хэндле.

Контекст-схема страницы объекта — ВНЕ эпика (bespoke, не на ELK; контекстные
стрелки имеют свою механику полок). Бэкенд и API не меняются.

## Риски и ограничения

- Качество на автораскладке: локальный роутер может дать лишнее пересечение там, где
  ELK с глобальным порядком дорожек не дал бы. Мера — эталон ELK на полигоне (гейт Ф2).
  Запасной ход, если не сойдётся: маршруты ELK как затравка в ТОТ ЖЕ конвейер
  (порты/дорожки/подписи/полировка общие) — не второй роутер.
- Равный шаг связывает все связи стороны: после дропа соседям нужен пересад точек.
  Это новый код в горячем пути после дропа; цена мала (без A*), но E84 усложняется.
- Смена стороны при драге на границе «разнесены/рядом» — дрожание без гистерезиса.
- Объём: самая большая правка движка со времён «стрелок v2» (graph/layout — 40 файлов,
  9570 строк; удаляются trunks/weldTrunks/railPairs и leader-ветка плашек). Полигон
  обязан включать рамки и гостей (включает).
- Роутер — самый выстраданный модуль проекта: любая правка — с полигоном до/после;
  качество не жертвуется молча, жертвы утверждает пользователь.
