# Экспорт/импорт полным архивом — ревизия фичи (2026-08-18)

Решения груминга 2026-08-03 (zip + манифест; только контент; импорт = новый
проект; слияние — отдельная задача) устарели не сами по себе — устарел ОБЪЁМ
знания. С тех пор появились: структура БД, каналы брокеров, конфигурация,
разведка (заглушки), процессы доехали до привязок к схемам и кругового прогона.
Ревизия сделана ПО КОДУ 2026-08-18: каждая категория проверена на «есть ли
формат переноса и что теряется сегодня».

## Реестр знания: сверка с copy_plan

Авторитетный перечень «что есть знание проекта» уже существует — это
`app/copy_plan.py`: копия проекта внутри инстанса переносит ВСЁ и защищена
сторожем полноты (test_copy_plan ловит каждую новую колонку). Архив — та же
операция, только через файлы и между инстансами. ПРИНЦИП: категория знания =
таблица из copy_plan; новая колонка обязана получить решение «едет в архив /
не едет» тем же сторожевым паттерном.

| Категория (перечень пользователя) | Хранение | Формат переноса | Статус |
|---|---|---|---|
| C4-архитектура (узлы, иерархия, связи) | Node, Edge | YAML (build_export ↔ import_yaml) | ЕСТЬ, две дыры — см. Д1, Д2 |
| Схемы логики | NodeDoc | .mmd с шапкой archmap-* (mmd_header) | ввоз ЕСТЬ (docs_import), ВЫВОЗА НЕТ; render_header есть |
| OpenAPI-спеки | Node.openapi_spec | YAML-файл как есть | ввоз ЕСТЬ (BYOA/спека узла), вывоза нет |
| Параметры конфигурации | ConfigParam | YAML с «# archmap-node:» (config_import) | ввоз ЕСТЬ, вывоза нет |
| Структура БД | DbTable + DbColumn | YAML с «# archmap-node:» (data_import) | ввоз ЕСТЬ, вывоза нет |
| Каналы брокеров | BrokerChannel + ChannelField | YAML с «# archmap-node:» (channels_import) | ввоз ЕСТЬ, вывоза нет |
| Бизнес-процессы | BusinessProcess + Participant + Message + Fragment/Branch | mermaid sequenceDiagram (toMermaid ↔ process_import) | формат ЕСТЬ В ОБЕ СТОРОНЫ, но экспортёр фронтовый — см. Р2 |
| Привязки шагов к схемам | ProcessMessage.doc_id | `%% archmap-doc: путь / имя` (Ф7 эпика процессов) | ГОТОВО целиком, транспорт построен и полевой прогон пройден |

Пометки в текстах схем («читает:/пишет:/публикует:/потребляет:/зависит от:»)
отдельной категорией НЕ являются: живут в тексте .mmd, едут вместе со схемами,
обратные индексы и алерты пересчитываются на чтении.

## Категории, ПРОПУЩЕННЫЕ в перечне

1. **source_ref — якорь источника узла** (эпик arch-sync). Без него после
   переноса «Обновить из репозитория» теряет идентичность узлов: матчинг
   деградирует к имени, переименованный сервис задвоится. Импорт принимать
   УМЕЕТ (source_keys → source_ref), экспорт НЕ ПИШЕТ. Это знание, оно обязано
   ехать (Д1).
2. **Тип канала — Edge.is_synchronous.** Не пишет экспорт, не принимает импорт
   (Д2). Потеря тихая и лживая: асинхронный канал приедет «синхронным по
   дефолту», у него появится плечо «ответ», которого в исходном проекте не
   существовало.
3. **Заглушки разведки** — NodeDoc с пустым content (described вычисляемое:
   `len(trim(content)) > 0`). Перечень точек входа БЕЗ описания — это план
   работ, терять его нельзя. Пустой .mmd должен пережить вывоз и ввоз (Д4).
4. **Имя и описание проекта** — манифест архива.
5. **Раскладка (view_layout)** — груминг решил «не включаем, пересчёт ELK».
   Продукт ушагал: позиции и раскрытия — ручной труд пользователя, для
   БЭКАПА его потеря болезненна. Развилка Р1 — подтвердить или пересмотреть.

Сознательно НЕ едет: версии CAS, created_at/updated_at, курсоры поллинга
(служебное; у копии — own), scope_node_id процессов (фича отклонена 2026-08-10,
у всех null), пользователи и роли (не знание проекта), archived_at.

## Дыры (что потеряется, если собрать архив из сегодняшних кусков)

- **Д1. source_ref не пишется экспортом** — импорт готов; правка одной стороны.
- **Д2. is_synchronous нет ни в экспорте, ни в импорте** — правка обеих сторон;
  поле опциональное, старые YAML остаются валидными.
- **Д3. Вывоза нет ни у одной семьи файлов**: доки (.mmd + шапка), спеки, БД,
  каналы, конфиги — все форматы ввозные (их писал агент BYOA). Нужны
  рендеры-экспортёры, обратные толерантным парсерам. Форматы менять не надо —
  писать в них.
- **Д4. Заглушки**: docs_import создаёт заглушки перечнем разведки, а не пустым
  файлом — проверить/разрешить пустое тело при ввозе из архива.
- **Д5. Экспорт процессов живёт на фронте** (detailToMermaid) — архив собирает
  бэк. Вторую реализацию заводить нельзя (принцип проекта) — см. Р2.
- **Д6. Тёзки путей**: адресация всех файловых форматов — «путь узла» в
  заголовке; при узлах-тёзках с одинаковым путём резолв неоднозначен. Для
  привязок шагов это уже решено честной деградацией (непривязанный шаг + AL34);
  для семей фактов приёмники отвечают ошибкой строки в отчёте. Деградация
  видимая — приемлемо, зафиксировать как норму архива.

## РЕШЕНИЯ ПО РАЗВИЛКАМ (пользователь, 2026-08-18)

- **Р1. Раскладку НЕ включаем — принципиальное решение.** Дословный мотив:
  «Если наш рендерер недостаточно хорош, и пользователю не хватает
  автораскладки, значит, мне нужно работать над рендерером. Сама возможность
  изменения раскладки вручную — скорее приятный бонус, даже игрушка, но явно
  не „ценное знание“, которое нужно хранить при экспорте-импорте». Решение
  груминга подтверждено; к вопросу не возвращаться — при жалобах на раскладку
  после импорта чинить РЕНДЕРЕР, а не формат архива.
- **Р2. Экспортёр процессов переносится на бэк** (единственная реализация):
  фронтовая кнопка получает ручку, detailToMermaid с фронта удаляется; архив и
  MCP получают экспорт процессов даром.
- **Р3. source_ref и is_synchronous пишутся И в семантический LLM-экспорт** —
  поля опциональные, контекст не раздувают, а синк и честность типа канала
  выигрывают.

## Фазы (ветка feat/archive-export)

- **Ф0. Контракт C4 (Д1, Д2).** Экспорт пишет `source` (source_ref) и `sync`
  (is_synchronous, только явное значение); импорт принимает `sync`. Общий
  build_export — правка достаётся и LLM-экспорту (Р3).
- **Ф1. Рендеры семей (Д3, Д4).** Экспортёры файлов в СУЩЕСТВУЮЩИХ ввозных
  форматах: доки .mmd (шапка archmap-* + archmap-node), спеки, БД, каналы,
  конфигурация. Критерий каждой пары — круговой прогон: рендер → существующий
  парсер → та же семантика. Заглушки (пустое тело) обязаны пережить круг.
- **Ф2. Экспорт процессов на бэк (Д5, Р2).** Порт detailToMermaid в
  app/process_export.py, ручка GET /processes/{id}/export; фронт удаляет свой
  конвертер и зовёт ручку. Гарантия переноса — построчное совпадение с выдачей
  фронтового конвертера на живых процессах (снятой ДО удаления).
- **Ф3. Сборка архива.** manifest.yaml (версия формата, имя/описание проекта,
  состав, порядок применения) + zip; ручка GET /projects/export-archive.
- **Ф4. Импорт архива.** POST /projects/import-archive: новый проект, применение
  строго по порядку манифеста СУЩЕСТВУЮЩИМИ приёмниками, сводный отчёт по
  категориям (что доехало, что в замечаниях). Д6 — тёзки путей — остаётся
  честной деградацией приёмников, отчёт её показывает.
- **Ф5. UI.** Кнопка «Экспорт архива» (страница проекта), «Из архива» в
  создании проекта; отчёт импорта в окне.
- **Ф6. Полевой прогон.** Живой проект «Плагин Zabbix для Grafana» → архив →
  импорт → сверка ВСЕХ категорий реестра (включая привязки шагов и заглушки),
  затем удаление дубля-проекта.

## Эскиз состава архива (уточнение груминга, формат прежний: zip + манифест)

    manifest.yaml   # версия формата, имя/описание проекта, состав, порядок применения
    c4.yaml         # build_export + source_ref + is_synchronous (Д1, Д2)
    docs/*.mmd      # схемы логики: шапка archmap-name/kind/operation/node
    specs/*.yaml    # OpenAPI по узлам (адрес узла в манифесте или соседнем ключе)
    db/*.yaml       # формат data_import («# archmap-node: …»)
    channels/*.yaml # формат channels_import
    config/*.yaml   # формат config_import
    processes/*.mmd # sequenceDiagram + %% archmap-doc (привязки шагов)

Имена файлов смысла не несут (адрес — в заголовке файла), поэтому коллизии имён
не проблема. ПОРЯДОК ПРИМЕНЕНИЯ при импорте обязателен и фиксируется манифестом:
C4 → семьи фактов и доки (адресуются узлами) → спеки → процессы (участники — по
узлам, привязки — по схемам). Импорт создаёт НОВЫЙ проект (решение груминга в
силе); слияние — отдельная задача.

Максимум переиспользования: ввоз каждой семьи — СУЩЕСТВУЮЩИМИ толерантными
приёмниками (docs_import, data_import, channels_import, config_import,
process_import), у них уже есть отчёты, слияние дублей и политика «удалений
нет». Новый код — рендеры-экспортёры, манифест, zip-обвязка и две правки
контракта C4 (Д1, Д2).
