# План: «Аудит вторым агентом-скептиком» во всех BYOA-потоках

Ветка: feat/skeptic-audit. Статус: Ф0 в работе.

## Зачем

Семантический аудит пакетов Zulip/Sentry (docs/qa-semantic-review.md) показал:
валидатор ArchMap сторожит СОГЛАСОВАННОСТЬ (пометки ↔ структура ↔ связи ↔ каналы),
а слабая модель производит СОГЛАСОВАННУЮ ложь — выдуманный Elasticsearch с узлом,
ребром и схемой; вычеркнутая Kafka с 44/53 каналами на чужом брокере. Ноль алертов
≠ правда: списочные слои (имена) точны на 96–100%, смысловые (топология,
направления, технологии, сюжеты) — конфабуляции «типовой системы». Класс лечится
только вторым агентским проходом ПРОТИВ КОДА — аудитом скептика.

Экспериментальная база (все три — 2026-08-15):
- docs/qa-orchestrator-experiment.md — Haiku-оркестратор исполняет чеклист
  «строитель → скептик → починка → скептик» 5/5, файловая передача блоков,
  правило «маршрутизатор, не судья» работает;
- docs/qa-skeptic-threshold.md — порог уверенности V1 выбран стендом с известными
  ответами (18 прогонов): ложноположительность ~0, жёсткий протокол вреден
  (Гудхарт), главный рычаг полноты — поимённый чек-лист слабых классов;
- docs/qa-f8-validation.md — валидаторная петля доведена до нуля алертов, её
  замечания чинятся ДОПИСЫВАНИЕМ (в отличие от аудиторских — см. ловушку №4).

## Продуктовые решения (зафиксированы с пользователем 2026-08-15)

1. **Обязательность = дефолт.** Главная кнопка «Скопировать промпт» каждого
   BYOA-окна отдаёт ОРКЕСТРАТОРНЫЙ промпт: агент пользователя сам спавнит
   субагентов строителя и скептика, гоняет петлю починки (кап 2 круга аудита)
   и выдаёт пакет, уже прошедший аудит. Запасные варианты — ссылками под кнопкой:
   «Промпт без аудита» (агент без субагентов) и «Только промпт аудита» (догнать
   уже собранный пакет).
2. **Скоуп — все BYOA-поверхности разом**: импорт «Из репозитория» (та же ручка
   обслуживает синк «Обновить из репозитория»), доки (логика и OpenAPI-спека —
   один генератор), структура БД, каналы брокера. Шесть точек UI при четырёх
   промпт-генераторах. MCP-паритет — вне скоупа (бэклог).
3. **Отчёт аудита — у пользователя (MVP).** Оркестратор цитирует непогашенные
   сомнения дословно в финальном ответе; standalone-скептик заканчивает отчёт
   готовой инструкцией передачи строителю. ArchMap отчёт не принимает и не
   хранит (бэклог: приём отчёта в превью, бейдж «аудит пройден»).
4. **Целевой сценарий пользователя** (минимум действий): нажал «Скопировать
   промпт» → запустил агента с субагентами в консоли → получил пакет → залил в
   ArchMap → документация с минимумом ошибок. Всё, что может сделать ArchMap,
   делает ArchMap; что не может ArchMap — делает агент; пользователю остаётся
   только неизбежное.

## Архитектура

**Бэк** — новый модуль `backend/app/skeptic_prompt.py`:
- `build_skeptic_prompt(flow, ...)` — промпт скептика per-поток: роль
  «недоверенная модель», поимённый чек-лист слабых классов потока (см. ниже),
  V1-порог дословно, формат отчёта. Параметры — что нужно потоку (пути пакета).
- `build_orchestrated_prompt(builder_prompt, skeptic_prompt, flow)` — обёртка:
  гейт «нужны субагенты», чистые каталоги, файловая передача блоков через
  cat/heredoc, петля с капом 2 круга, правило маршрутизатора, финал.

**Ручки** — к четырём существующим GET-ручкам промптов добавляется query-параметр
`variant: "builder" | "orchestrated" | "skeptic"`, дефолт `builder`:
- `GET /projects/import/prompt` (routers/projects.py) — покрывает и синк;
- `GET /docs-import/prompt` (routers/docs_import.py) — покрывает логику и спеку;
- `GET /data-import/prompt` (routers/data_import.py);
- `GET /channels-import/prompt` (routers/channels_import.py).
Дефолт `builder` возвращает НЫНЕШНИЙ промпт байт-в-байт (совместимость: MCP-тулзы
archmap_import_prompt/archmap_docs_prompt зовут ручки без параметра).

**Фронт** — тройка «главная кнопка + две ссылки» в шести окнах: DocsAgentModal,
SpecAgentModal, DataAgentModal, ChannelsAgentModal (docsImport/),
CreateProjectDialog режим «Из репозитория», SyncRepoModal (project/ и корень
components/). Общий компонент в agentModalShared (или рядом), чтобы подписи были
едиными. Тексты:
- под главной кнопкой: «Промпт включает аудит вторым агентом-скептиком: перед
  выдачей пакет проверяется по коду. Вашему агенту понадобятся субагенты.»
- ссылки: «Промпт без аудита» · «Только промпт аудита».

## Содержание промптов

### Общие блоки скептика (проверены стендом, менять только через эксперимент)

Роль: «модель построена ДРУГИМ агентом; считай её НЕДОВЕРЕННОЙ: каждое
утверждение — гипотеза, пока не подтверждена кодом или конфигом репозитория».

Порог V1 (дословно из docs/qa-skeptic-threshold.md): «Сомнение записывается
ТОЛЬКО при конкретном доказательстве: процитированная строка кода, доказывающая
обратное, или результат поиска, в котором имя не находится. Умозаключения без
доказательства («обычно делают иначе», «вероятно, это не так») сомнением не
являются — не записывай их вовсе. Не уверен — молчи: пропущенное сомнение
дешевле ложного.»

Правила: ничего не чинить — только отчёт; подтверждённое в отчёт не включать;
не выдумывать сомнений ради объёма; каждый вердикт — с доказательством
(файл:строка либо «поиск по репозиторию не находит „X“»). Формат отчёта: одна
строка на сомнение; нет сомнений — единственная строка «ПОДТВЕРЖДЕНО ВСЁ».

### Чек-листы per-поток (из docs/qa-semantic-review.md — слабые классы поимённо)

**Импорт/синк** (architecture.yaml): каждый узел-хранилище/брокер/внешний —
основание в коде или конфиге (зависимость, клиент, настройка, деплой), не «по
типовой аналогии»; каждая технологическая шина — отдельный узел (Kafka и очередь
задач не сливать); technology — из манифестов (Cargo.toml, package.json,
requirements), не по роли узла; каждая связь — существование И направление (кто
кого зовёт по коду); связь «по HTTP» между частями одной кодовой базы — проверь,
не один ли это процесс (INSTALLED_APPS, wsgi, монтирование urls); каждое
«хранит X» в описании — найди настройку-доказательство (SESSION_ENGINE,
CACHES…); channel у связи — дословно из кода.

**Каналы**: каждый канал пакета — точка публикации или потребления в коде
(файл:строка), нет вхождений — сомнение; поля сообщений — против реальной
структуры публикуемого сообщения, не типовой формы клиента; мета (retention,
гарантия доставки) — только из конфига; владелец-брокер — чей клиент использует
канал по коду.

**Структура БД**: каждая таблица — реальная модель/DDL (abstract-класс ORM —
не таблица); db_table — дословное имя из модели/миграции; «таблицы» узлов-кэшей —
реальные ли это структуры с колонками (Redis-неймспейс — не схема); два файла
пакета на один узел — дубль.

**Доки (логика+спека)**: каждая пометка «читает:/пишет:/публикует:/потребляет:» —
реальное обращение в ЭТОМ сценарии (файл:строка); шаги схем — существующие
эндпоинты/функции; сюжет схемы — против кода потока (не «типовой архитектуры»);
пути и методы OpenAPI — против роутинга кода.

### Оркестраторная обёртка (генерализация zl-orch-header эксперимента)

Шапка-гейт: «Ты — ОРКЕСТРАТОР. Сам не исследуешь репозиторий и не пишешь
документацию — только запускаешь субагентов и передаёшь файлы. Нужны субагенты
(инструмент Task/Agent); если их нет — остановись и скажи пользователю взять в
ArchMap промпт без аудита.»

Шаги: (1) пересоздай ЧИСТЫЙ каталог archmap-orch/ (прежний удали — пакеты
прошлых прогонов заражают следующие); сохрани блок А (строитель) и блок Б
(скептик) из маркеров ===BLOCK-A-START===… в файлы ЧЕРЕЗ ТЕРМИНАЛ (cat/heredoc),
дословно, не перенабирая; (2) субагент-строитель: «прочитай builder-prompt.txt и
выполни»; результат — для импорта в archmap-orch/architecture.yaml, для дозаливок
пакет в каталоге конвенции промпта, собранный С НУЛЯ; (3) субагент-скептик:
«прочитай skeptic-prompt.txt и выполни» (отчёт в archmap-orch/skeptic-report-N.md);
(4) прочитай отчёт с наибольшим N; «ПОДТВЕРЖДЕНО ВСЁ» → шаг 6; (5) субагент-
строитель-починка: исходный промпт + текущий пакет + отчёт аудита; «чини имена,
направления и описания; сущность удаляй ТОЛЬКО если замечание прямо говорит,
что её нет в коде, и НЕ выдумывай замену» → повтори шаг 3; больше двух кругов
аудита не делай; (6) финал: сколько кругов; последний отчёт ДОСЛОВНО целиком;
путь к пакету; «загрузите пакет в окно ArchMap».

Жёсткое правило: оркестратор не оценивает и не отбрасывает замечания скептика,
споры не разрешает; всё неразрешённое — дословно в финальный ответ.

## Фазы

- **Ф0 (бэк, Opus-исполнитель)**: app/skeptic_prompt.py + variant в четырёх
  ручках + pytest (структурные тесты промптов: маркеры блоков, гейт, кап кругов,
  чек-листы по потокам; тест байт-в-байт дефолта) + `npm run gen:api` (параметры
  ручек попадают в OpenAPI) + коммит api.gen.ts. Гейты: ruff, pytest, tsc -b.
- **Ф1 (фронт, Opus-исполнитель)**: тройка кнопок в шести окнах, общий компонент,
  vitest на модалки. Гейты: tsc -b, eslint, vitest.
- **Ф2 (доки)**: spec.md (аудит — обязательный паттерн BYOA), tasks.md.
- **Ф3 (полевой QA, архитектор сам)**: Haiku-оркестратор с кнопочных промптов на
  живом репозитории; метрики — механика петли, финальные алерты, выборочная
  семантика; отчёт docs/qa-*.

## Ловушки (⚠ обязательны к переносу в ТЗ исполнителей)

1. Дефолт `variant=builder` обязан вернуть нынешний промпт БАЙТ-В-БАЙТ —
   закрепить тестом (MCP и существующие вызовы фронта не должны измениться).
2. Блоки А/Б в оркестраторной обёртке — ЖИВЫЕ вызовы существующих генераторов
   (build_import_prompt и др.), не копии текстов: промпты продолжают развиваться,
   копия молча протухнет.
3. Перепечатка блоков агентом теряет типографские символы („“→") — обёртка велит
   сохранять через cat/heredoc; маркеры ===BLOCK-…=== не должны встречаться в
   телах блоков (проверить тестом).
4. Замечания АУДИТА чинятся иначе, чем замечания ВАЛИДАТОРА: валидаторные —
   «дополняй, не удаляй» (интро кнопок), аудиторские — «выдуманную сущность
   удали, замену не выдумывай» (урок «соглашательства»: на замечание о
   несуществующем канале модель добавила канал-обёртку). Тексты промптов обязаны
   называть источник замечаний, чтобы правила не смешивались в одной сессии.
5. Конвенции каталогов пакетов брать из существующих промптов (доки —
   archmap-docs/; данные/каналы — проверить в data_prompt.py/channels_prompt.py),
   не выдумывать новые.
6. Типы фронта проверять ТОЛЬКО `tsc -b`; tsserver стабильно врёт про
   api.gen.ts после перегенерации (будить ts_diagnostics, истина — tsc -b).
7. Формат ответа промпт-ручек не менять (тот же тип ответа, новый опциональный
   параметр).

## Вне скоупа (бэклог с триггерами)

- Приём отчёта аудита в ArchMap (вставка в модалку → строки в превью, бейдж
  «аудит: N непогашенных») — триггер: запрос пользователя после полевого QA.
- MCP-паритет: variant у MCP-тулз промптов (+ data/channels промпты в MCP,
  асимметрия уже есть) — триггер: живой MCP-сценарий с аудитом.
- Хранение истории аудитов в БД — триггер: multi-user.
