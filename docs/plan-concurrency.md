# План: конкурентные сессии — этапы 0+1 (fence + поллинг)

Дата: 2026-07-16. Одобрен пользователем (этап 2 — в дальний бэклог, триггер
«наплыв пользователей»). Диагноз и обзор индустрии — в ответе-анализе сессии;
краткая выжимка ниже, чтобы план читался автономно.

## Диагноз (сжато)

Сегодня согласования между сессиями НЕТ вообще: докстринг `routers/views.py`
честно объявляет last-write-wins, у `view_layout` нет ни версии, ни таймстемпов,
фронт не перечитывает состояние иначе как при навигации/ошибке записи. Пишут
только архитекторы (viewer не персистит ничего), поэтому конфликт записи-записи —
«архитектор × архитектор», включая две вкладки одного человека.

Главные дыры (номера — из матрицы конфликтов анализа):
1. Производные записи конвейера (keep-out / разведение пересечений / own-on-first-render
   сиды) уходят от УСТАРЕВШЕЙ картины мира и двигают узлы, которых пользователь
   не касался, — устаревание размазывается по сцене.
2. Тексты доков (`flowchart`/`openapi_spec`) перезаписываются целиком через
   `PATCH /nodes/{id}` без какой-либо проверки устаревания — час правки может
   молча испариться. Критичнее всего.
3. Два 500-угла: батч раскладки в только что удалённый вид (FK по `view_id`);
   гонка INSERT одного ключа `view_layout` двумя сессиями (уникальный констрейнт,
   реалистично — два клиента одновременно сеют own-on-first-render свежего вида).
4. Тихие сироты: upsert раскладки для удалённого узла вставляется без ошибки
   (`item_id` — строка без FK).
5. Undo — компенсирующие вызовы из in-memory стека: откат в отставшей вкладке
   затирает чужие свежие правки.

## Принцип решения

**Интент пользователя переживает ребейз; интент конвейера — нет.**
Прямое действие (драг/undo/expand) после конфликта переигрывается поверх свежего
мира — «этот узел сюда» валидно независимо от чужих правок. Производная запись
(сиды, keep-out) при конфликте выбрасывается — конвейер пересчитает её от свежих
данных штатным ходом после ресинка.

Индустриальная рамка: optimistic CAS (Zwibbler/draw.io/SQLAlchemy version_id_col)
как ступень к server-authoritative LWW (Figma/tldraw); полный разбор — в анализе.

## Этап 0 — «не терять и не портить молча» (optimistic CAS)

### Схема БД (одна миграция Alembic)

- Таблица `view_state`: `id` UUID PK, `project_id` FK projects CASCADE NOT NULL,
  `view_id` FK nodes CASCADE **nullable** (NULL = корневой вид), `version` int
  NOT NULL default 1. Уникальный ключ `(project_id, view_id)` с
  `postgresql_nulls_not_distinct=True` — зеркало паттерна `view_layout`.
  Отсутствие строки трактуется как `version = 0` (виды не пересоздаём заранее).
- `nodes.version` int NOT NULL server_default '1'.
- `edges.version` int NOT NULL server_default '1'.
- `projects.graph_rev` int NOT NULL server_default '0' — счётчик «в проекте
  что-то поменялось» (курсор поллинга этапа 1; НЕ трогает `updated_at`,
  семантика карточек проектов не меняется).

Разделение ролей счётчиков: `view_state.version` — **fence записи раскладки**
(view-гранулярность, иначе ложные 409 между разными уровнями);
`projects.graph_rev` — **курсор свежести** (project-гранулярность: лишний рефетч
безвреден, зато точки бампа тривиальны).

### Бэкенд

Новый модуль `app/view_state.py`:
- `current_version(db, project, view_id) -> int` (0, если строки нет);
- `bump(db, project, view_id, *, lock=True) -> int` — get-or-create строки
  (под `with_for_update`), `version += 1`, вернуть новое. Гонка создания строки —
  через savepoint (`begin_nested`) + повторный SELECT при IntegrityError.
- `bump_graph_rev(db, project)` — инкремент счётчика проекта (отдельно от
  `touch_project`: раскладка бампает rev, но НЕ `updated_at`).

`PUT /views/{view_id}/layout`:
- контейнер вида проверяется (`scoped_node`) → 404 вместо нынешнего 500 по FK;
- `ViewLayoutBatch` получает `base_version: int | None`;
- строка версии берётся `FOR UPDATE` **до** применения батча — это одновременно
  и fence, и мьютекс писателей вида (гонка INSERT одного ключа исчезает);
- `base_version` задан и ≠ текущей → **409** `{"detail": "Вид изменён в другой
  сессии"}`; не задан → без проверки (совместимость), но lock+bump всё равно;
- успех: применить батч, `version += 1`, `bump_graph_rev`, ответ **200
  `{"version": N, "graph_rev": M}`** (был 204) — клиент отслеживает без рефетча.

Точки бампа `view_state.version` (fence должен видеть смену мира вида):
- сам PUT layout; relayout уровня (`_clear_level_layout`);
- `POST /nodes/` — вид родителя (членство изменилось; плюс возможная строка позиции);
- `DELETE /nodes/{id}` — вид родителя + DISTINCT `view_id` всех вычищенных
  строк раскладки (LIKE-чистка уже их находит);
- `PATCH /nodes/{id}` со сменой `parent_id` — старый и новый родительские виды.

Точки бампа `projects.graph_rev`: ВСЕ мутации узлов/рёбер/раскладки/relayout
(процессы — вне скоупа этапа, зафиксировать как residual).

CAS смысловых полей:
- `NodeUpdate`/`EdgeUpdate` получают `base_version: int | None`; задан и ≠
  `row.version` → **409** «Узел/связь изменён(а) в другой сессии»; успех →
  `version += 1`. `NodeResponse`/`EdgeResponse` отдают `version`.
- DELETE узла/ребра — без CAS (LWW-удаление осмысленно).

`GET /nodes/graph` и `GET /nodes/{id}/graph`: `GraphResponse` получает
`version` (вида) и `graph_rev` — базовая точка отсчёта клиента при загрузке.

Эндпоинт поллинга (этап 1, но кладётся здесь же):
`GET /views/{view_id}/state` → `{"version": N, "graph_rev": M}` — доступен
любому залогиненному (viewer тоже поллит).

Замечание по 409: `deps.py` уже использует 409 для «проект в архиве» —
тексты `detail` различать; клиентская ветка 409 применяется только к путям
записи, GET-409 архива в retry не попадает.

### Фронтенд

- Перегенерация типов (`npm run gen:api`) после правок Pydantic-схем; истина —
  `tsc -b` (tsserver может стейлить `api.gen.ts` — будить `ts_diagnostics`).
- `client.ts`: класс `ApiError extends Error { status: number }` — фронт
  начинает различать коды (сейчас теряются).
- `viewsApi.saveLayout(viewId, items, baseVersion)` → тело `{items,
  base_version}`, ответ `{version, graph_rev}`. Новый `viewsApi.state(viewId)`.
- TreePage держит `viewMetaRef = {version, graphRev}`: заполняется из
  `GraphResponse` при `load()`, обновляется из ответов PUT (echo-suppression:
  свои записи не выглядят чужими). Реф передаётся в LevelGraph.
- `commitLayout(patch, {origin: "user" | "derived"})`:
  - вызовы: persistGroup / flushKeyboard / undo-redo перемещений /
    commitExpanded → `"user"`; интенты конвейера (сиды/keep-out) → `"derived"`;
  - шлёт `base_version` из рефа; успех → обновить реф + зеркало (как сейчас);
  - **409 + origin user** → ресинк уровня (`load()`) → повторить патч ОДИН раз
    поверх свежего мира (отфильтровав ключи, чьих узлов больше нет на уровне);
  - **409 + origin derived** → только ресинк (конвейер пересчитает);
  - прочие ошибки → как сейчас (`resyncOnPersistError`).
  Возврат-bool «запись инициирована» (фикс 3535083) сохраняется — откат превью
  жеста без записи не меняется.
- Политика undo: КОМПЕНСАЦИИ смысловых полей (nodesApi/edgesApi из истории)
  идут БЕЗ `base_version` (unfenced — явный интент отката, LWW); undo
  перемещений идёт через commitLayout как `"user"` (fence + retry).
- Инспектор: `PATCH` с `base_version = node.version`; 409 → видимое сообщение
  «Узел изменён в другой сессии — данные обновлены» + ресинк (нынешний пустой
  `catch {}` уходит).

### Тесты этапа 0

pytest: fence ок/стейл/отсутствует; версия в ответах PUT и GET graph; бампы на
create/delete/parent-move/relayout; 404 мёртвого вида; CAS PATCH узла/ребра
(ок → version+1; стейл → 409); `graph_rev` монотонен по всем типам мутаций;
эндпоинт `/state`. vitest: `ApiError`; чистая логика решения после отказа
(retry/resync по origin+status+retried); фильтр ключей ретрая.

## Этап 1 — «видеть друг друга» (поллинг курсора)

- Хук в TreePage: каждые `POLL_MS = 10000` + немедленно на `focus` окна
  (пауза при `document.hidden`): `viewsApi.state(currentParentId)` → если
  `graph_rev` > известного → рефетч `load(currentParentId)` + тост «Схема
  обновлена» (существующий toastRail).
- Гарды рефетча: НЕ посреди жеста (реф активности жеста из LevelGraph;
  пропущенный тик догонит следующий — максимум ~2×POLL_MS задержки) и НЕ при
  открытых модалках/оверлее доков (стейт модалок уже в TreePage). Черновики
  инспектора отдельно не гардим: их защищает CAS (стейловый save → 409 → явное
  сообщение вместо тихой потери).
- Echo-suppression: `graph_rev` обновляется из ответов PUT layout и из
  `GraphResponse` при каждом `load()`; свои структурные правки и так зовут
  `load()`. Остаточный лишний рефетч после PATCH из инспектора — осознанно
  допустим (данные идентичны, реконсиляция дешёвая).
- Viewer поллит наравне с архитектором (живость чтения).
- vitest: фейк-таймеры — тик без изменений молчит, рост rev дёргает колбэк,
  гард жеста откладывает, focus триггерит немедленно.

## Сквозной e2e-гейт (scratchpad, по образцу verify_fix_probe.mjs)

Одноразовый клон-проект; сессия A в headless-браузере, «сессия B» — прямые
API-вызовы вторым токеном: (1) B двигает узел → A подхватывает без F5 за
≤2×POLL_MS; (2) стейловый PUT B → 409, авто-ретрай доносит интент; (3) стейловый
PATCH текста → 409 и сообщение, текст A не потерян; (4) соло-режим: серия
драгов A без единого 409 (fence не мешает одиночке). Смоук-проект удалить
(archive + DELETE с confirm).

## Ловушки

- SQLite в pytest: `postgresql_nulls_not_distinct` игнорируется, `FOR UPDATE` —
  no-op; тесты однопоточные, приложенческий get-or-create обязателен (как у
  `view_layout`), гонку создания строки версии закрывает savepoint.
- НЕ использовать `ON CONFLICT` для view_state — та же причина, что
  задокументирована в `views.py` (PG/SQLite расходятся на NULL-ключах).
- openapi-typescript: default-non-nullable — поля с дефолтом становятся
  ОБЯЗАТЕЛЬНЫМИ в генерате (`GraphResponse.version` required — это ок);
  `base_version` держать `int | None = None` (optional).
- 409 архивного проекта (`deps.py`) ≠ 409 конфликта — различать по контексту
  вызова (retry только на путях записи).
- Поллинг-хук: без setState-в-эффекте зеркал (react-hooks/set-state-in-effect),
  интервал по рефам; при смене проекта/уровня known-rev сбрасывается вместе с
  `load()`.
- Гонка X-Project-Id при navigate уже починена (V20) — поллинг стартует после
  первого `load()`, скоуп синхронен.
- `relayout` по-прежнему завершится `load()` на фронте — его ответ не меняем.

## Этап 2 — дальний бэклог (триггер: наплыв пользователей)

WebSocket-канал на проект (FastAPI native; Railway держит WS бессрочно),
серверный broadcast `{view, version, changed_ids, actor}` вместо поллинга,
presence (кто на каком виде, чужое выделение, «X двигает узел») ВМЕСТО жёстких
локов элементов; undo — только свои операции (уже так). Смежное: membership/ACL
проектов (сейчас роль глобальная, любой залогиненный ходит в любой проект);
«общая правда рендера» — детерминизм маршрутов между сессиями (связка с
бэклогом «дрейф гистерезисных прогонов», tie-break prev). Одна инстанция →
внутрипроцессный pub/sub; при масштабировании — LISTEN/NOTIFY или Redis.
