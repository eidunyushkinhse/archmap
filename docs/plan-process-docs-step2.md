### Главная находка: коллизия адреса законна и уже случилась дважды

- `Zabbix 7 v2 / Zabbix 7 v2` — **восемь** схем на одном адресе `POST /api/jsonrpc`:
  «Создание хоста», «Получение событий», «Создание триггера»…
- `Плагин Zabbix для Grafana / datasource-service` — две схемы на `POST /query`:
  «Аутентификация per-user» и «Запрос метрических данных».

Это не «агент поделил крупный сценарий», как предполагал челлендж, а **JSON-RPC over
HTTP**: у целого класса API (JSON-RPC, GraphQL, gRPC-gateway) вся логика висит на
одном пути, а метод лежит В ТЕЛЕ запроса. Оба случая пришли из полевых прогонов, а не
из полигона.

**Следствие: уникальность `operation` вводить НЕЛЬЗЯ.** Ограничение отвергло бы
корректные данные двух живых проектов, а промпт пришлось бы учить врать — выдумывать
разные адреса восьми схемам, у которых адрес действительно один.

## Что из этого следует для адреса шага

Адрес обязан покрывать 100 % схем и быть однозначным. Кандидаты:

| Кандидат | Покрытие | Однозначность | Чем платим |
|---|---|---|---|
| `operation` (исходный дизайн) | 80 % | НЕТ (8-кратная коллизия) | воркеры и клиентские сценарии недостижимы |
| Имя схемы (мягкая ссылка) | 100 % | ДА — `UniqueConstraint(node_id, name)` | переименование рвёт связь молча |
| `doc_id` (FK) | 100 % | ДА по построению | нужна карта id при копировании проекта |

### Про цену FK: возражение челленджа устарело

Челлендж отверг FK доводом «карта узлов при копировании ЕСТЬ, а карты доков нет».
Проверено: карты доков действительно нет (`projects.py:_copy_node_docs` раздаёт новые
id без карты), но

- рядом лежит `_copy_db_structure`, который заводит `tmap` и `colmap` ровно потому,
  что этого потребовал FK `references_column_id` — прецедент и образец есть;
- `ProcessMessage` в `copy_plan.py` УЖЕ перекладывается через четыре карты (процесс,
  связь, два участника). Пятая карта — та же строчка, а не новая механика;
- снапшот-восстановление доков идёт с ИСХОДНЫМ id (`NodeDocSnapshot`), то есть
  undo/восстановление FK не рвёт.

## Решения, которые нужно принять

**Р1. Чем адресуется шаг.** Рекомендация — **`doc_id` (FK на схему)**. Он единственный
покрывает все три класса (операции, воркеры, клиентские сценарии) и однозначен на
данных, которые уже есть. Альтернатива «имя схемы» дешевле на копировании, но молча
рвётся при переименовании — а имя правится в интерфейсе по blur.

**Р2. Уникальность `operation`.** Рекомендация — **не вводить**, поле остаётся
необязательной подсказкой (и связью со спекой), а не адресом. Обосновано замером.

**Р3. Что показывать в каталоге выбора у шага.** При Р1 = `doc_id` вопрос «фильтровать
по виду или по непустому полю» (дефект Д2) исчезает: в каталоге ВСЕ схемы узла,
сгруппированные по виду, адрес операции — подпись строки, а не ключ. Решить надо
другое: показывать ли схемы ПОТОМКОВ узла-участника (см. блокер Б4 про контейнеры).

**Р4. Что делать, когда цель исчезла.** Схему удалили или дозаливка завела новую под
другим именем. Варианты: FK `ON DELETE SET NULL` + алерт «шаг ведёт в никуда» (видно,
но шумит на раннем этапе) либо тихое обнуление (не шумит, но расхождение не видно).
Прецедент продукта — «расхождение должно быть ВИДНО» (разведка показывает `vanished`,
а не удаляет).

**Побочно закрывается.** Вопрос порядка работ «решение по воркерам и клиентским
сценариям» при Р1 = `doc_id` отдельного решения не требует: они адресуются наравне со
всеми. Связь со спекой OpenAPI тоже перестаёт быть работой: шаг знает схему, схема уже
хранит свой `operation` — резолвер по OpenAPI, которого в проекте нет, не понадобится.

**Остаётся открытым до кода** (из tasks.md): заводить ли алерт на неразрешённый адрес
сразу. При `doc_id` неразрешённость возможна только после удаления схемы — случай
редкий, поэтому цена алерта ниже, чем предполагалось при строковом адресе.

## РЕШЕНИЯ ПОЛЬЗОВАТЕЛЯ (2026-08-18) — шаг 2 закрыт

- **Р1. Адрес шага — `doc_id`, внешний ключ на схему логики.** Строковый адрес
  (operation) и мягкая ссылка по имени отвергнуты.
- **Р2. Уникальность `operation` НЕ вводим.** Поле остаётся необязательной подсказкой
  и связью со спекой, адресом оно не является.
- **Р3. Каталог показывает схемы ПОТОМКОВ узла-участника**, а не только его
  собственные (иначе у контейнера-участника каталог вечно пуст — блокер Б4).
- **Р4. Исчезнувшая цель — АЛЕРТ.** Тихое обнуление отвергнуто: расхождение должно
  быть видно, как `vanished` у разведки.

### Что эти решения делают с дизайном

**Пара «узел + строка» схлопывается в одно поле.** Исходный дизайн хранил у шага
владельца по id ПЛЮС строку операции. `doc_id` — UUID первичного ключа, схема сама
знает свой узел, поэтому второе поле не нужно вовсе.

**Переезд схемы больше не рвёт привязку.** Дефект Д8 («владелец меняется молча при…»)
частично растворяется: «распределить по детям» ПЕРЕВЕШИВАЕТ схему на потомка, id при
этом сохраняется — шаг продолжает указывать на ту же схему, что и правильно. При Р3
такая схема к тому же остаётся в каталоге участника-контейнера.

**Связь со спекой достаётся даром.** Шаг знает схему, схема хранит свой `operation` —
резолвер операций по OpenAPI, который челлендж оценивал как «целиком новую работу»,
не нужен.

### Р4 УТОЧНЁН (пользователь, 2026-08-18): алерт на ЛЮБОЙ непривязанный шаг

Отдельная колонка `doc_hint`, отличающая «сломалось» от «не привязывали», НЕ НУЖНА:
алерт кидается на любой шаг без живой привязки, независимо от истории. Мотив
пользователя: «шумно, зато консистентно».

Что это меняет по смыслу: алерт перестаёт быть сообщением о поломке и становится
алертом ПОЛНОТЫ — той же семьи, что «не описана» у разведки. Он не «сломалось», а
«шаг не документирован», и гаснет по мере привязки. Схема при этом проще на колонку:
только `doc_id` с `ON DELETE SET NULL`.

9 проектам, в самом большом процессе 13. То есть класс алертов стартует со 156 строк
и убывает.

**Весь ли шум вычищаемый — проверено:** 77 шагов из 156 имеют на конце участника,
привязанного к узлу-НЕ-сервису (БД, брокер, человек), а у таких форм схем логики не
бывает вовсе. Но шагов, где НЕ-сервис на ОБОИХ концах, — **ноль**. Значит при любом
правиле владельца у каждого шага есть конец, способный нести схему, и алерт гасится
работой, а не мирится навсегда. Если правило владельца на шаге 3 назначит владельцем
именно нечитаемый конец — этот замер придётся повторить.

**Вариант `ON DELETE RESTRICT`** (запретить удаление схемы, на которую ссылается шаг)
отвергнут: продукт нигде не блокирует удаление ради ссылок.
