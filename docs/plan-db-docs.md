# План: ДОКУМЕНТАЦИЯ БАЗ ДАННЫХ (и брокеров — вторым кругом)

Подготовлено 2026-08-12. Ветка `feat/db-docs`. Файл самодостаточен — реализовывать
можно после сжатия контекста, ничего не потеряно.

---

## 0. Задача и её происхождение

Идея «ER-диаграммы вместо flowchart у баз данных» лежала в бэклоге с 2026-08-01.
Разбор 2026-08-12 показал, что формулировка была уже́ решения.

ЦЕЛЬ, названная пользователем: инженер сопровождения должен быстро отвечать на вопрос
«из какой колонки какой таблицы берётся это значение в рамках вот этого процесса».

ER на этот вопрос НЕ отвечает. ER описывает СТРУКТУРУ («где значение может лежать»),
а спрошено ПРОИСХОЖДЕНИЕ («откуда оно здесь взялось»). Нужны два артефакта, и ER из
них вспомогательный:

- **структура** — какие таблицы и колонки есть (карта местности);
- **обращения** — кто читает и кто пишет, в рамках какой операции (маршрут по ней).

Ценность в обращениях; ER — производная картинка поверх структуры.

## 1. Принцип размещения (продлеваем существующий, не изобретаем второй)

В продукте уже есть эта развязка — для API: **контракт живёт у поставщика**
(`Node.openapi_spec` у узла, который API предоставляет), **использование — у
вызывающего** (`node_docs` с `kind=operation`, привязка полем `operation` =
«METHOD /path»). Промпт агента это правило проговаривает прямо.

Продлеваем на данные:

| | контракт (у кого) | использование (у кого) |
|---|---|---|
| API | `openapi_spec` у сервиса-поставщика | док операции вызывающего |
| **БД** | **структура у узла-БД** | **обращения в доке операции сервиса** |
| **брокер** | **каналы у узла-брокера** | **публикации/чтения в доке операции** |

Обратный индекс на странице БД («к `orders.status` обращаются: Биллинг `POST /pay` —
пишет; Витрина `GET /orders` — читает») получается РАЗВОРОТОМ этих же записей, без
отдельного ввода. Он и есть ответ инженеру сопровождения.

## 2. Решения пользователя (2026-08-12, до кода)

1. **Источник правды — ЗАПИСИ, а не mermaid-текст.** Груминг 2026-08-03 записывал
   «рисуем mermaid erDiagram» — рисование остаётся, но правдой становится структура.
   Причина: из текста диаграммы обратный индекс не построить (пришлось бы парсить и
   диаграмму, и прозу), то есть главный запрос оказался бы невыполним. mermaid
   `erDiagram` — ПРОИЗВОДНОЕ представление, генерируется из записей.
2. **Глубина обращений: таблица обязательно, колонка по возможности.** Требовать
   колоночную точность везде — заведомо получать выдумку (`SELECT *` в коде обычен).
3. **Сначала БД, брокеры — вторым кругом.** Механика симметрична, объём удваивается.
4. **Канал брокера указывается на СВЯЗИ.** Стрелка «сервис → брокер» обязана называть
   топик, иначе связь есть, а смысла в ней нет. Это второй круг, но решение принято
   заранее: модель связи будет затронута, и архив (см. §6) должен это учесть.

## 3. Что документируем у БД (и что сознательно НЕ документируем)

Нужное, чтобы ПОНЯТЬ данные:
- **таблица**: имя, назначение одной фразой, необязательная группа/схема (контур БД —
  отдельной сущности не заводим, обычное поле);
- **колонка**: имя, тип, обязательность, признак ключа, смысл — ОСОБЕННО у
  enum-подобных (`status: new|paid|shipped`): вопросы сопровождения чаще всего про них;
- **связи**: PK/FK — из них и рисуется ER;
- **обращения**: живут у сервисов (§1).

НЕ документируем осознанно: индексы, партиционирование, тюнинг, история миграций. Это
ответы на «почему медленно» и «как выкатить» — другая задача; объём документации они
удваивают, а миграции к тому же правдивее живут в репозитории.

## 4. Что документируем у брокера (ВТОРОЙ КРУГ, зафиксировано чтобы не переоткрывать)

Ориентир — AsyncAPI (нарочно сделан похожим на OpenAPI). У узла-брокера — **каналы**,
у каждого: имя и тип (топик/очередь/exchange); схема сообщения; ключ партиционирования;
гарантия доставки (at-least-once / at-most-once); retention; описание.

Три средних пункта — не занудство, а три самых частых инцидента: порядок применения
событий, повторная обработка, «при переигрывании ничего не нашлось». Сегодня C4-схема
не отвечает ни на один.

## 5. Модель данных (первый круг)

Новые таблицы (Alembic):

- `db_tables`: id, `node_id` → nodes (CASCADE), `name`, `schema_name` (nullable —
  контур/логическая группа), `description`, `version` (CAS как у node_docs),
  created_at/updated_at. Уникально (node_id, name, schema_name).
- `db_columns`: id, `table_id` → db_tables (CASCADE), `name`, `type`, `nullable`,
  `is_primary_key`, `references_column_id` → db_columns (SET NULL — внешний ключ для
  ER), `description`, `order`. Уникально (table_id, name).
- `doc_data_access`: id, `node_doc_id` → node_docs (CASCADE), `table_id` → db_tables
  (CASCADE), `column_id` → db_columns (CASCADE, nullable = обращение на уровне
  таблицы), `mode` Literal["read","write"], `note`. Уникально
  (node_doc_id, table_id, column_id, mode).

⚠️ `doc_data_access` цепляется к node_doc, а не к «узлу + операции»: док И ЕСТЬ
описание операции (или воркера), это его единица. Сервис, трогающий таблицу вне
задокументированной операции, обращение не покажет — и правильно: показывать нечего.

⚠️ CASCADE на удаление дока/таблицы: обращение без одного из концов бессмысленно.
Проверить, что удаление узла-БД не уносит доки чужих сервисов (уносит только
обращения) — тест обязателен.

## 6. Связь с архивом (почему этот эпик ИДЁТ ПЕРВЫМ)

Наблюдение пользователя: манифест «всего проекта» разъедется с документацией «всего
проекта», если архив сделать раньше. Верно — архив должен нести и структуру БД, и
обращения, и (вторым кругом) каналы брокеров. Порядок: сначала эта модель, потом
манифест. В плане архива уже заложено «место под процессы» — сюда же добавится место
под данные.

## 7. Фазы (первый круг — БД)

Каждая фаза — коммит, гейт зелёный до коммита, новые тесты сломаны и проверены на
падение. `npm run gen:api` в том же коммите, где меняются Pydantic-схемы.

- **Ф0. СДЕЛАНО. Модель и API.** Три таблицы + миграция, CRUD-эндпоинты, скоуп проекта,
  роль архитектора, CAS. Тесты pytest: каскады, уникальность, скоуп.
- **Ф1. СДЕЛАНО. Документация ПО ФОРМЕ узла.** Сегодня страница показывает «Логика» и «OpenAPI»
  ЛЮБОМУ атомарному объекту — у базы данных есть слот под OpenAPI-спеку и flowchart,
  которых у неё не бывает (промпт агента это прямо оговаривает, а интерфейс всё равно
  предлагает). Набор секций начинает зависеть от `shape`: у БД — «Структура», у
  сервиса — прежние. Легаси-содержимое не прячем: показываем с предупреждением и
  путём переноса (тот же приём, что у контейнеров со своей документацией, AL24).
  Правило вынесено в `types/shapeDocs` — одна точка правды для страницы, будущего
  редактора структуры и каналов брокера. Карточка «Структура» СОЗНАТЕЛЬНО не заводится
  пустой: она приезжает вместе со своим содержимым в Ф2.
- **Ф2. СДЕЛАНО. Ручной редактор структуры.** Таблицы и колонки на странице узла-БД
  (`DbStructureSection`). Правки поштучно по blur/change, без формы и «Сохранить»:
  строк много, правка точечная. Таблица под CAS, колонка — нет (короткие поля,
  last-write-wins). Внешний ключ КАРТЫ выбирается селектом «таблица.колонка» уже
  здесь — без него Ф3 нарисовала бы ER без связей. Новая таблица/колонка получает
  свободное имя («таблица_2»), иначе повторное нажатие упиралось бы в 409.
- **Ф3. СДЕЛАНО. ER как ПРОИЗВОДНОЕ.** `dbErDiagram.tablesToErDiagram` — чистая
  функция, показ по кнопке в самой секции (тот же `MermaidRenderer`, что у схем логики).
  ГРАНИЦЫ СИНТАКСИСА erDiagram выяснены ЖИВЫМ ПАРСЕРОМ mermaid 11.15, не по документации:
  у атрибута обязательны И тип, И имя (пустой тип → «_»); пробел в имени атрибута ломает
  разбор (кавычки там не спасают); кавычка внутри комментария ломает; имя сущности в
  кавычках держит и пробелы, и кириллицу; связь без метки не парсится, с пустой — да.
  ⚠️ Проверки ОДНИМ парсером мало: «uuid код заказа» он читает как тип «uuid» + имя
  «код» + мусор, а «код заказа» без типа — как тип+имя, то есть кривой вывод остаётся
  валидным. Тест фиксирует и текст вывода (поймано фальсификацией).
- **Ф4. СДЕЛАНО. Обращения.** Секция «Обращения к данным» на странице СЕРВИСА
  (`DataAccessSection`, по доку на блок) + обратный индекс «Кто обращается» под
  колонками таблицы на странице базы. Ради этой фазы всё и делалось.
  Отдельной секцией, а не внутри «Логики»: на странице сервиса читается «куда я хожу»,
  на странице базы — «кто ко мне ходит», и обе стороны — разворот ОДНИХ записей.
  Бэк: `GET /tables` (каталог проекта для пикера — СВОЙ префикс, иначе путь
  `/nodes/tables` перехватил бы `/nodes/{node_id}` и упал на разборе uuid) и
  `GET /nodes/{id}/tables/usage` (объявлен ДО `/{table_id}` по той же причине).
- **Ф5. BYOA.** Промпт агента и дозаливка: структура и обращения — то, что агент отдаёт
  надёжнее диаграмм (читает миграции и ORM-модели). Ручной ввод для БД с сорока
  таблицами непригоден, так что без этой фазы эпик наполовину бесполезен.
- **Ф6. Спеки и документация.** spec.md (новый вид документации), docs/specs — по
  задетым (страница объекта — вне реестра спек, но alerts.md может получить класс
  «структура без обращений» — решить в фазе). tasks.md.

## 8. Путь пользователя, ради которого всё (проверять на приёмке)

Инженер видит расхождение в поле «статус заказа»:

1. Открывает процесс «Оплата заказа», находит шаг «Биллинг → БД: списать».
2. Из шага проваливается в док операции — ЗАВИСИМОСТЬ: «Процессы → доки шага»
   (бэклог, решено «привязка ручная»). Без неё путь начинается с шага 3.
3. В доке видит: пишет `orders.status`, читает `accounts.balance`.
4. Кликает `orders` → страница узла-БД: ER, карточка таблицы, значения enum и
   обратный индекс «кто ещё эту колонку трогает».
