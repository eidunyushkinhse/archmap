Подготовлено 2026-08-12. Ветка `feat/db-docs`. Файл самодостаточен — реализовывать
можно после сжатия контекста, ничего не потеряно.

## 0. Задача и её происхождение

Идея «ER-диаграммы вместо flowchart у баз данных» лежала в бэклоге с 2026-08-01.
Разбор 2026-08-12 показал, что формулировка была уже́ решения.

ЦЕЛЬ, названная пользователем: инженер сопровождения должен быстро отвечать на вопрос
«из какой колонки какой таблицы берётся это значение в рамках вот этого процесса».

ER на этот вопрос НЕ отвечает. ER описывает СТРУКТУРУ («где значение может лежать»),
а спрошено ПРОИСХОЖДЕНИЕ («откуда оно здесь взялось»). Нужны два артефакта, и ER из
них вспомогательный:

- **структура** — какие таблицы и колонки есть (карта местности);
- **обращения** — кто читает и кто пишет, в рамках какой операции (маршрут по ней).

Ценность в обращениях; ER — производная картинка поверх структуры.

## 1. Принцип размещения (продлеваем существующий, не изобретаем второй)

В продукте уже есть эта развязка — для API: **контракт живёт у поставщика**
(`Node.openapi_spec` у узла, который API предоставляет), **использование — у
вызывающего** (`node_docs` с `kind=operation`, привязка полем `operation` =
«METHOD /path»). Промпт агента это правило проговаривает прямо.

Продлеваем на данные:

| | контракт (у кого) | использование (у кого) |
|---|---|---|
| API | `openapi_spec` у сервиса-поставщика | док операции вызывающего |
| **БД** | **структура у узла-БД** | **обращения в доке операции сервиса** |
| **брокер** | **каналы у узла-брокера** | **публикации/чтения в доке операции** |

Обратный индекс на странице БД («к `orders.status` обращаются: Биллинг `POST /pay` —
пишет; Витрина `GET /orders` — читает») получается РАЗВОРОТОМ этих же записей, без
отдельного ввода. Он и есть ответ инженеру сопровождения.

## 2. Решения пользователя (2026-08-12, до кода)

1. **Источник правды — ЗАПИСИ, а не mermaid-текст.** Груминг 2026-08-03 записывал
   «рисуем mermaid erDiagram» — рисование остаётся, но правдой становится структура.
   Причина: из текста диаграммы обратный индекс не построить (пришлось бы парсить и
   диаграмму, и прозу), то есть главный запрос оказался бы невыполним. mermaid
   `erDiagram` — ПРОИЗВОДНОЕ представление, генерируется из записей.
2. **Глубина обращений: таблица обязательно, колонка по возможности.** Требовать
   колоночную точность везде — заведомо получать выдумку (`SELECT *` в коде обычен).
3. **Сначала БД, брокеры — вторым кругом.** Механика симметрична, объём удваивается.
4. **Канал брокера указывается на СВЯЗИ.** Стрелка «сервис → брокер» обязана называть
   топик, иначе связь есть, а смысла в ней нет. Это второй круг, но решение принято
   заранее: модель связи будет затронута, и архив (см. §6) должен это учесть.

## 2а. Универсальность по движкам (проверено 2026-08-12)

Узел «База данных» должен одинаково годиться для PostgreSQL, MySQL, MongoDB,
ClickHouse и дальше по списку. Модель это выдерживает, потому что у всех них одна
форма: **владелец → (необязательная группа) → именованная сущность → типизированные
поля → ссылки между полями**. Различаются только СЛОВА:

| движок | уровень группы | сущность |
|---|---|---|
| PostgreSQL | schema | таблица |
| MySQL | database | таблица |
| MongoDB | database | коллекция |
| ClickHouse | database | таблица |
| Cassandra | keyspace | таблица |
| Elasticsearch | — | индекс |
| Redis | — (номера БД) | ключи по шаблону |

Отсюда два решения:
- **уровень группы называется «РАЗДЕЛ»** — нейтрально; подсказка поля перечисляет
  термины движков. Поле НЕОБЯЗАТЕЛЬНО, и раскрывашки разделов появляются, только если
  раздел где-то указан: у Redis и Elasticsearch этого уровня нет, и навязанная
  вложенность была бы шумом;
- **слова «таблица» и «колонка» ОСТАВЛЕНЫ** осознанно. Они понятны и в мире Mongo
  («коллекция»/«поле»), а нейтральные «сущность»/«атрибут» звучат абстрактнее, чем
  предмет. Известная цена: для Redis структура вырождается в плоский список ключевых
  шаблонов, а для Elasticsearch — в индексы с полями маппинга. Это приемлемо: обе
  описываются той же парой «сущность + типизированные поля».

Что НЕ уперлось в движок: обращения (кто читает/пишет), обратный индекс и ER — они
опираются на «сущность.поле», а не на SQL.

## 3. Что документируем у БД (и что сознательно НЕ документируем)

Нужное, чтобы ПОНЯТЬ данные:
- **таблица**: имя, назначение одной фразой, необязательная группа/схема (контур БД —
  отдельной сущности не заводим, обычное поле);
- **колонка**: имя, тип, обязательность, признак ключа, смысл — ОСОБЕННО у
  enum-подобных (`status: new|paid|shipped`): вопросы сопровождения чаще всего про них;
- **связи**: PK/FK — из них и рисуется ER;
- **обращения**: живут у сервисов (§1).

НЕ документируем осознанно: индексы, партиционирование, тюнинг, история миграций. Это
ответы на «почему медленно» и «как выкатить» — другая задача; объём документации они
удваивают, а миграции к тому же правдивее живут в репозитории.

## 4. Что документируем у брокера (ВТОРОЙ КРУГ, зафиксировано чтобы не переоткрывать)

**РАЗВЁРНУТ В ОТДЕЛЬНЫЙ ПЛАН** (2026-08-14, с уроками эпика БД и QA-прогонов):
docs/plan-broker-docs.md. Ниже — исходный эскиз, оставлен для истории.

Ориентир — AsyncAPI (нарочно сделан похожим на OpenAPI). У узла-брокера — **каналы**,
у каждого: имя и тип (топик/очередь/exchange); схема сообщения; ключ партиционирования;
гарантия доставки (at-least-once / at-most-once); retention; описание.

Три средних пункта — не занудство, а три самых частых инцидента: порядок применения
событий, повторная обработка, «при переигрывании ничего не нашлось». Сегодня C4-схема
не отвечает ни на один.

## 5. Модель данных (первый круг)

Новые таблицы (Alembic):

- `db_tables`: id, `node_id` → nodes (CASCADE), `name`, `schema_name` (nullable —
  контур/логическая группа), `description`, `version` (CAS как у node_docs),
  created_at/updated_at. Уникально (node_id, name, schema_name).
- `db_columns`: id, `table_id` → db_tables (CASCADE), `name`, `type`, `nullable`,
  `is_primary_key`, `references_column_id` → db_columns (SET NULL — внешний ключ для
  ER), `description`, `order`. Уникально (table_id, name).
- `doc_data_access`: id, `node_doc_id` → node_docs (CASCADE), `table_id` → db_tables
  (CASCADE), `column_id` → db_columns (CASCADE, nullable = обращение на уровне
  таблицы), `mode` Literal["read","write"], `note`. Уникально
  (node_doc_id, table_id, column_id, mode).
  **УСТАРЕЛО ПИВОТОМ §9**: заменяется производным кэшем `doc_data_ref` — обращения
  больше не вводятся записями, а извлекаются из текста схем логики.

⚠️ `doc_data_access` цепляется к node_doc, а не к «узлу + операции»: док И ЕСТЬ
описание операции (или воркера), это его единица. Сервис, трогающий таблицу вне
задокументированной операции, обращение не покажет — и правильно: показывать нечего.
(Это решение переживает пивот §9: пометка физически живёт в тексте дока.)

⚠️ CASCADE на удаление дока/таблицы: обращение без одного из концов бессмысленно.
Проверить, что удаление узла-БД не уносит доки чужих сервисов (уносит только
обращения) — тест обязателен.

## 6. Связь с архивом (почему этот эпик ИДЁТ ПЕРВЫМ)

Наблюдение пользователя: манифест «всего проекта» разъедется с документацией «всего
проекта», если архив сделать раньше. Верно — архив должен нести и структуру БД, и

## 7. Фазы (первый круг — БД)

Каждая фаза — коммит, гейт зелёный до коммита, новые тесты сломаны и проверены на
падение. `npm run gen:api` в том же коммите, где меняются Pydantic-схемы.

- **Ф0. СДЕЛАНО. Модель и API.** Три таблицы + миграция, CRUD-эндпоинты, скоуп проекта,
  роль архитектора, CAS. Тесты pytest: каскады, уникальность, скоуп.
- **Ф1. СДЕЛАНО. Документация ПО ФОРМЕ узла.** Сегодня страница показывает «Логика» и «OpenAPI»
  ЛЮБОМУ атомарному объекту — у базы данных есть слот под OpenAPI-спеку и flowchart,
  которых у неё не бывает (промпт агента это прямо оговаривает, а интерфейс всё равно
  предлагает). Набор секций начинает зависеть от `shape`: у БД — «Структура», у
  сервиса — прежние. Легаси-содержимое не прячем: показываем с предупреждением и
  путём переноса (тот же приём, что у контейнеров со своей документацией, AL24).
  Правило вынесено в `types/shapeDocs` — одна точка правды для страницы, будущего
  редактора структуры и каналов брокера. Карточка «Структура» СОЗНАТЕЛЬНО не заводится
  пустой: она приезжает вместе со своим содержимым в Ф2.
- **Ф2. СДЕЛАНО. Ручной редактор структуры.** Таблицы и колонки на странице узла-БД
  (`DbStructureSection`). Правки поштучно по blur/change, без формы и «Сохранить»:
  строк много, правка точечная. Таблица под CAS, колонка — нет (короткие поля,
  last-write-wins). Внешний ключ КАРТЫ выбирается селектом «таблица.колонка» уже
  здесь — без него Ф3 нарисовала бы ER без связей. Новая таблица/колонка получает
  свободное имя («таблица_2»), иначе повторное нажатие упиралось бы в 409.
- **Ф3. СДЕЛАНО. ER как ПРОИЗВОДНОЕ.** `dbErDiagram.tablesToErDiagram` — чистая
  функция, показ по кнопке в самой секции (тот же `MermaidRenderer`, что у схем логики).
  ГРАНИЦЫ СИНТАКСИСА erDiagram выяснены ЖИВЫМ ПАРСЕРОМ mermaid 11.15, не по документации:
  у атрибута обязательны И тип, И имя (пустой тип → «_»); пробел в имени атрибута ломает
  разбор (кавычки там не спасают); кавычка внутри комментария ломает; имя сущности в
  кавычках держит и пробелы, и кириллицу; связь без метки не парсится, с пустой — да.
  ⚠️ НАЙДЕНО ГЛАЗАМИ НА ЖИВЫХ ДАННЫХ 2026-08-12: «numeric(12,2)» уронил диаграмму
  целиком — запятая в идентификаторе erDiagram недопустима, как и точка, слэш,
  двоеточие; начинаться с цифры тоже нельзя. Санитайзер переведён на БЕЛЫЙ список
  (буквы, цифры, «_», «-», круглые и квадратные скобки): перечислять плохие символы
  здесь бессмысленно — следующий тип нашёлся бы снова.
  ⚠️ Проверки ОДНИМ парсером мало: «uuid код заказа» он читает как тип «uuid» + имя
  «код» + мусор, а «код заказа» без типа — как тип+имя, то есть кривой вывод остаётся
  валидным. Тест фиксирует и текст вывода (поймано фальсификацией).
- **Ф4. СДЕЛАНО. Обращения.** Секция «Обращения к данным» на странице СЕРВИСА
  (`DataAccessSection`, по доку на блок) + обратный индекс «Кто обращается» под
  колонками таблицы на странице базы. Ради этой фазы всё и делалось.
  Отдельной секцией, а не внутри «Логики»: на странице сервиса читается «куда я хожу»,
  на странице базы — «кто ко мне ходит», и обе стороны — разворот ОДНИХ записей.
  Бэк: `GET /tables` (каталог проекта для пикера — СВОЙ префикс, иначе путь
  `/nodes/tables` перехватил бы `/nodes/{node_id}` и упал на разборе uuid) и
  `GET /nodes/{id}/tables/usage` (объявлен ДО `/{table_id}` по той же причине).
- **Ф5а. СДЕЛАНО. BYOA — бэкенд.** `data_prompt.py` (промпт), `data_import.py`
  (толерантный разбор YAML + план + применение), роутер `/data-import/{prompt,preview,
  apply}`. Формат пакета: YAML-файлы рядом с .mmd, адрес узла ведущим комментарием
  «# archmap-node:», разделы `tables` и `access`. Удалений нет ни при какой политике;
  `overwrite` перетирает только заполненное.
  ⚠️ ГЛАВНАЯ ЛОВУШКА (поймана тестами): обращение часто указывает на таблицу, которая
  создаётся ЭТИМ ЖЕ пакетом, — на момент плана её ещё нет. Поэтому план хранит СТРОКУ-
  ссылку, а не объект таблицы, и цель резолвится повторно при применении; внешние
  ключи разрешаются вторым проходом по той же причине (цель может лежать ниже по файлу).
  НАЙДЕНО НА ЖИВЫХ ДАННЫХ (наполнение «Ярмарки» тем же путём, 2026-08-12), две правки:
  • ЧАСТИЧНЫЙ ПУТЬ узла. Промпт просит писать «Сервис заказов / Order API», но полный
    путь начинается с корневого контейнера проекта, которого агент не знает (он видит
    свой репозиторий). Резолв дополнен совпадением по хвосту — по границе « / », чтобы
    «…/ Заказы» не цеплялось к «…/ Мои Заказы».
  • БИТЫЙ YAML НАШЕГО ФАЙЛА молчал: разборщик возвращал «это не файл данных», и
    пользователь получал «в пакете нет файлов со структурой данных» — при том, что
    данные там были. Теперь файл с разделами tables/access, не разобравшийся как YAML,
    даёт внятную ошибку с самой частой причиной (двоеточие с пробелом внутри значения —
    ровно на этом и споткнулся мой собственный пакет).
- **Ф5б. СДЕЛАНО. Окно дозаливки данных.** `DataAgentModal` — третье окно того же
  семейства, целиком на общей машинерии (`useDocsFiles`, `useFileDrop`,
  `agentModalShared`, `ItemList/NoteList`). Своего в нём только контракт и отчёт:
  промпт без параметров (агент читает код, а не рисует — язык подписей и режимы
  «пакетом/по одной» тут не нужны), тумблер перезаписи с дефолтом «не трогать
  заполненное». Вход к нему — пункт меню «+ Таблица» (см. ниже), а не своя кнопка.
- **Ф5в. СДЕЛАНО. Приёмочная косметика секции.** Добавление таблицы — ОДНА кнопка с
  шевроном и меню «Вручную | Через ИИ-агента», на общем `AddDocsMenu` (у него появилась
  подпись параметром): два способа завести одну сущность не должны выглядеть как две
  разные кнопки, а «Логика» и «OpenAPI» устроены ровно так. Счётчики (колонок у

- **Ф6. Спеки и документация.** spec.md (новый вид документации), docs/specs — по
  задетым (страница объекта — вне реестра спек, но alerts.md может получить класс
  «структура без обращений» — решить в фазе). tasks.md.

## 8. Путь пользователя, ради которого всё (проверять на приёмке)

Инженер видит расхождение в поле «статус заказа»:

1. Открывает процесс «Оплата заказа», находит шаг «Биллинг → БД: списать».
2. Из шага проваливается в док операции — ЗАВИСИМОСТЬ: «Процессы → доки шага»
   (бэклог, решено «привязка ручная»). Без неё путь начинается с шага 3.
3. В доке видит: пишет `orders.status`, читает `accounts.balance`.
4. Кликает `orders` → страница узла-БД: ER, карточка таблицы, значения enum и
   обратный индекс «кто ещё эту колонку трогает».

## 9. ПИВОТ (принят 2026-08-13): пометки в тексте — истина обращений

### 9.0 Почему пересматриваем Ф4/Ф5 до слияния ветки

Обкатка Ф0–Ф5 на живых данных показала: конструкция с обращениями-записями хрупкая
по замыслу, а не по недоделкам. Один факт («операция пишет `orders.status`») вводился
ДВАЖДЫ — прозой в диаграмме для человека и записью для машины — и всё дальнейшее
(якоря на шаги, эвристический валидатор, порядок прогонов, мердж-политики) было
подпорками под неизбежное расхождение двух вводов. Плюс расхождение путей: ручной
пользователь никогда не заполнит формы обращений, агент заполняет их криво — получаются
два класса документации, и цельной картинки нет.

Решение пользователя: **обращения живут в самом тексте схемы логики** структурной
пометкой (паттерн doc-комментариев: проза для человека, пометка в прозе — для машины).
`doc_data_access` из редактируемой сущности превращается в производный кэш. Принцип:
повествовательные факты — в тексте, табличные (структура) — в записях, связь между
ними — по имени, шов непрерывно проверяют алерты.

Что это растворяет (для истории, чтобы не переизобретать):
- паритет ручного и агентского пути — по построению (оба пишут один артефакт);
- якоря «обращение → шаг» не нужны: пометка физически внутри шага;
- совпадение имени дока в пакете агента не нужно: обращение не ссылается на док;
- порядок и мердж прогонов по репозиториям не нужны: каждый док несёт своё;
- политика «удалений нет» для обращений не нужна: кэш перестраивается, не мерджится;
- перенос промпта данных на страницу сервиса не нужен: access-часть уезжает в
  СУЩЕСТВУЮЩИЙ промпт логики, промпт структуры остаётся на странице базы, где дефолт
  «к объекту окна» корректен.

### 9.1 Формат пометки (нормативно; в Ф-П6 переносится в spec.md)

Пометка — фрагмент текста дока (на практике — строка в подписи вершины mermaid):

    A["Проверить заказ<br>читает: orders.status, orders.total"]
    B["Списать средства<br>пишет: accounts.balance"]

- Маркеры: `читает:` / `пишет:` и `reads:` / `writes:`. Первая буква — любой регистр.
- После маркера — ссылки через запятую, до терминатора: конец строки, `<br>`/`<br/>`,
  `"`, `]`, `)`, `}`.
- Ссылка: `[Узел-БД / ][раздел.]таблица[.колонка]`. Квалификатор узла отделяется
  « / » и может содержать пробелы (имя узла или суффикс пути, как в data_import);
  голая часть — токен БЕЗ пробелов (буквы/цифры/`_`/`-`/точки).
- Извлечение — регексом по всему `NodeDoc.content`, mermaid НЕ парсим: пометка в
  подписи ребра или заголовке subgraph тоже считается (осознанно — это дешевле и
  предсказуемее разбора синтаксиса).
- Дедуп в пределах дока по (нормализованная ссылка, режим).
- Глубина по-прежнему опциональна: только таблица — законно (`SELECT *` обычен).

### 9.2 Резолв (на чтении, чистая функция; никакой магии)

Кандидаты — все `db_tables` проекта. Токен без точек — имя таблицы; `x.y` — пробуем
И «таблица x, колонка y», И «раздел x, таблица y» (обе гипотезы сработали →
неоднозначно); `s.t.c` — раздел.таблица.колонка. Квалификатор узла сужает кандидатов
(суффиксное совпадение пути либо голое имя). Совпадение имён точное, регистр значим.

Статусы: ok | unknown-table | ambiguous | unknown-column (таблица нашлась, колонки
нет → обращение считается к таблице целиком, но подсвечивается). Предпочтения «по
связям сервиса» НЕ делаем: молчаливое угадывание хуже требования квалификатора.

⚠️ Резолв — на ЧТЕНИИ, а не на записи: он чистая функция от (пометки, каталог таблиц,
имена узлов), и это убирает ВСЕ точки инвалидации (переименование таблицы/раздела/
узла, удаление колонки…). Объёмы — сотни строк на проект, в памяти это мгновенно.

### 9.3 Хранение: НЕ НУЖНО ВООБЩЕ (уточнение при постановке П2, 2026-08-13)

Изначально планировался производный кэш `doc_data_ref`, перестраиваемый на каждой
записи content. При постановке П2 выяснилось, что и он лишний: точек записи content
больше двух (node_docs create/update, docs_import.apply, restore, будущие импортёры),
и «не забыть дёрнуть refresh» — ровно тот класс хрупкости, от которого пивот уходит.
Объёмы позволяют разбирать текст на чтении: сотни доков по несколько КБ — миллисекунды
регекса. Итог: обращения НИГДЕ не хранятся — usage, превью и алерты зовут
parse+resolve по актуальным докам проекта. Инвалидация не существует как класс задач.
Вырастут проекты до тысяч доков — кэш вернётся как оптимизация, не меняя контрактов.

Alembic-миграция остаётся одна: drop `doc_data_access` (в П3; данных в проде нет —
ветка не слита, дев-данные Ярмарки пересеваются в 9.7).

### 9.9 Ловушки (заранее)

- `x.y`: «таблица.колонка» против «раздел.таблица» — обе гипотезы, совпали → ambiguous;
  тест обязателен (иначе молча выберется первая и будет казаться, что работает).
- Имя таблицы с пробелом пометкой НЕ адресуется (токен без пробелов) → у такой
  таблицы обращения всегда unknown. Осознанно: не запрещаем в структуре, ловим алертом.
- Слово «читает:» в обычной прозе подписи тоже извлечётся — принято как фича
  (маркер = обещание факта), в промпте и spec.md сказать прямо.
- api.gen.ts перегенерировать в КАЖДОМ коммите, где менялись Pydantic-схемы (П3, П4).
- Переименование таблицы/узла рвёт пометки по имени — это ВИДИМОЕ состояние (алерт),
  не баг; assisted-переименование (замена по докам) — в бэклог, не в этот заход.
