# План эпика «Доработка MCP-сервера» (2026-09-04)

Ветка `feat/mcp-catchup`, слить в main через `--no-ff`. Режим — «код субагентам
Opus по фазам, приёмка основным» (отработан на роутере и едином импорте).
Копилка хвостов — запись «ДОРАБОТКА MCP-СЕРВЕРА» в tasks.md (2026-08-17 →
2026-09-03). Состав утверждён пользователем 2026-09-04 целиком, ничего не режем.

## Мотив

MCP-сервер (mcp/) даёт агенту пользователя 18 инструментов: чтение (проекты,
дерево, карточка, алерты, процессы, YAML-экспорт), правила формата (промпт
импорта и промпт доков с вариантами скептика), запись пачкой «превью →
применение» (импорт нового проекта, синк из кода, дозаливка схем и спек) и
точечные правки объектов/связей. За четыре эпика после него бэкенд ушёл вперёд,
а MCP не догонял — точечные заходы дороже пакетного (свой гейт ruff+mypy+pytest).
Итог: агент через MCP не может разведать монолит, залить ни одну из трёх семей
табличных фактов, выгрузить архив, создать проект единым путём или догрузить
архив к живому, привязать шаг к схеме — и, самое обманчивое, видит 6 классов
алертов из 15: там, где интерфейс показывает проблемы, агент получает
«Замечаний нет — схема завершена».

## Ревизия (Ф0, сделана 2026-09-04)

- `tools.py` (749 строк): каталог `TOOLS` — словари {name, description, schema,
  handler}; хендлеры `t_*` (client, args) → str; `resolve_project` (имя/uuid,
  неоднозначность — ошибка со списком). Тела запросов собирают `_docs_body`,
  `_sync_body`. Промпты — прокси бэкенда (`GET /projects/import/prompt`,
  `GET /docs-import/prompt`), текст возвращается как есть.
- `render.py` (134): текстовые сводки (дерево, карточка, алерты — 6 классов).
- `client.py` (191): `request(method, path, *, project_id, json, params)` — JSON
  только; X-Project-Id заголовком; отказы 401/403/404/409/422 → `ArchMapError`
  с человеческим текстом. Multipart и бинарного ответа НЕТ — нужны для Ф4.
- `server.py` (96): stdio, регистрирует `TOOLS`, ошибки — текстом с isError.
- Тесты (`tests/`, 35): настоящий клиент поверх `httpx.MockTransport`
  (`FakeApi`: путь → ответ, журнал запросов). ⚠️ Подменённый транспорт тело НЕ
  валидирует — тела инструментов сверяют схемами САМОГО БЭКЕНДА через
  `conftest.backend("schemas.…")` + `model_validate` (ловушка 422 у старого
  /projects/import/preview, память «моки прячут форму тел»).
- Гейт: `cd mcp && ./venv/bin/ruff check . && ./venv/bin/mypy && ./venv/bin/python -m pytest -q`.
- Бэкенд-эндпоинты под новые инструменты (все существуют, контракты не меняем):
  разведка `GET /recon/prompt`, `POST /recon/{preview,apply}` (ReconImportIn:
  files[(name, content)], node_id); семьи фактов `/data-import`,
  `/channels-import`, `/config-import` — у каждой `GET /prompt`,
  `POST /preview`, `POST /apply` (DataImportIn / ChannelsImportIn /
  ConfigImportIn); чтение фактов `GET /nodes/{id}/tables|channels|config` (+
  `/usage`); архив `GET /export/archive` (zip, бинарный ответ); единый импорт
  `POST /projects/import/unified-preview` и `POST /projects/import-unified`
  (multipart: files[], name, description, resolutions=JSON); догрузка
  `POST /projects/{id}/import-archive/{preview,apply}` (multipart: files[],
  resolutions, base_graph_rev, base_meta_rev → 409 при расхождении); привязка
  шага `PATCH /processes/{pid}/messages/{mid}` (MessageUpdate.doc_id,
  base_version → 409), каталог схем шага
  `GET /processes/{pid}/messages/{mid}/docs`; обратный индекс схем
  `GET /nodes/{id}/docs/usage`; алерты — `AlertsResponse` в
  `backend/app/schemas/node.py` (15 классов, реестр docs/specs/alerts.md).

## Решения проектирования

1. **Инструменты по задачам, не по эндпоинтам** (принцип tools.py). Три семьи
   табличных фактов — НЕ девять инструментов, а три с аргументом `family`
   (`tables | channels | config`): `archmap_facts_prompt`,
   `archmap_facts_preview`, `archmap_facts_apply`. Хендлер отображает семью в
   эндпоинт и тело; сводка отчёта — общая форма (создано/обновлено/замечания).
2. **Файлы — с локального диска.** MCP-сервер живёт на машине агента (stdio),
   поэтому zip-архивы и большие пакеты передаются ПУТЯМИ (`paths: [str]`), а не
   телом вызова: base64 в контексте модели — расточительство. YAML по-прежнему
   можно отдать текстом (`files: [{name, content}]`), оба входа смешиваются.
   Архив выгружается в файл (`out_path`), инструмент возвращает сводку
   манифеста и путь.
3. **Единый импорт заменяет старый путь.** `archmap_import_preview/apply`
   переезжают на `/projects/import/unified-preview` и `/projects/import-unified`
   с поддержкой N входов, споров содержимого (`resolutions`) и имени/описания.
   Старый `POST /projects/import/preview` после этого не имеет потребителей —
   снесён отдельным решением пользователя 2026-09-05 (см. хвост ниже).
4. **Догрузка к живому — свои инструменты** `archmap_import_into_preview` /
   `archmap_import_into_apply` (fence по обеим ревизиям: превью печатает
   base_graph_rev/base_meta_rev, применение их возвращает; 409 → перечитать
   превью).
5. **Привязка шага** — `archmap_bind_step` (process, message_id, doc_id | null
   для снятия, base_version из выдачи процесса) + каталог схем шага в выдаче
   `archmap_processes` по запросу (`message_id`), чтобы агент выбирал из
   допустимых. Удалений по-прежнему нет.
6. **Карточка объекта** обогащается: вид схемы словарём (операция/воркер),
   метка «не описана» у заглушек, «в N процессах» по обратному индексу,
   структура БД (таблицы/колонки), каналы брокера (с полями), параметры
   конфигурации — по форме объекта (запросы к семьям только там, где семья
   уместна: таблицы у database, каналы у broker, конфиг у service).
7. **Алерты — все 15 классов** в том же порядке и с теми же заголовками, что в
   панели SchemaAlerts.tsx, чтобы агент и человек говорили одними словами.
8. Правила сервера не меняются: удалений нет, «текущего проекта» нет, имя
   проекта не угадывается, запись только парой превью → применение.

## Фазы

- **Ф1 — алерты и карточка.** render.alerts до 15 классов (AL27–AL35);
  карточка объекта по решению 6. Тесты на рендер каждого класса (фикстуры
  валидируются `AlertsResponse` бэка) и на карточку каждой формы.
- **Ф2 — разведка и семьи фактов.** `archmap_recon_prompt/preview/apply`;
  `archmap_facts_prompt/preview/apply` с `family`. Тела — `model_validate`
  схемами бэка; отчёты — по образцу `_docs_report`.
- **Ф3 — архив и единый импорт.** client: multipart (`files=`, `data=`) и
  бинарный ответ; `archmap_export_archive`; перевод `archmap_import_preview/
  apply` на единый путь (N входов, споры, имя/описание); `archmap_import_into_
  preview/apply`. Сентинел: старые вызовы с одним YAML-текстом дают тот же
  результат, что и раньше (превью → создание).
- **Ф4 — привязка шагов.** `archmap_bind_step`, каталог схем шага в
  `archmap_processes`.
- **Ф5 — приёмка и полевой прогон (основной).** README: каталог инструментов и
  сценарии; версия сервера; живой прогон против ./dev.sh учёткой из mcp/.env
  (демо «Ярмарка v2» — чтение; запись — в одноразовом проекте); tasks.md,
  spec.md (раздел MCP), память. Вопрос пользователю: сносить ли старый путь
  импорта.

## Скоуп-гард

Не в эпике: удаления любых сущностей через MCP; импорт/экспорт процессов через
MCP (только привязка шага); правки промптов бэкенда (эпик BYOA); изменение
контрактов бэкенда (кроме возможного сноса старого пути импорта — отдельным
решением); UI.

## Риски и ловушки

- Подменённый транспорт не ловит форму тел — каждое новое тело сверять схемой
  бэка (`conftest.backend`), иначе 422 на живом (уже было).
- Multipart в httpx: `files=[("files", (name, bytes, mime))]` для списка
  файлов; `resolutions` — строка JSON в форме, не объект.
- Бинарный ответ архива: `request` возвращает `resp.json()` — нужен отдельный
  путь без разбора JSON; заголовок Content-Disposition ASCII (истинное имя —
  в манифесте).
- Заглушка = тело после SQL-trim пустое (NodeDoc.described) — метку «не
  описана» брать из поля `described`, а не считать по content.
- Логин живого сервиса form-encoded (память process-docs-epic).
