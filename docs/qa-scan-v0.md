приходят из манифестов (`zulip-django`, `postgresql`, `self-hosted`), поэтому ручное
сопоставление:

**Zulip, 19 детей эталона.** Найдено под именем манифеста 12: Django = `zulip-django`,
Tornado = `zulip-tornado`, KaTeX-сервер = `zulip-katex`, tusd = `zulip-tus`, Планировщик
писем = `zulip_deliver_scheduled_emails`, Планировщик сообщений =
`zulip_deliver_scheduled_messages`, Почтовый шлюз = `zulip-email-server`, Воркеры очередей =
`zulip_events` (шаблонные программы `zulip_events_<queue>` ушли в подсказку),
process_fts_updates = `process-fts-updates`, Cron-задачи = `cron`, nginx = `nginx`, PostgreSQL =
`postgresql` (по `Dockerfile-postgresql`, без адреса). Не найти по манифестам 5: RabbitMQ, Redis,
memcached, Smokescreen, go-camo описаны только в puppet (`puppet/zulip/manifests/profile/*.pp`),
которого сборщик не читает. Не процесс 2: Веб-клиент (статика, её раздаёт nginx), Хранилище
загрузок (диск или S3 по настройке). Лишнее 13: `prometheus_*_exporter`, `prometheus`,

`redis-tunnel`, `weblate_exporter`: настоящие программы supervisor из `puppet/zulip_ops`
(хостинг самого Zulip), эталон их не считает продуктом. Технология у них пустая (бинари не
в словаре), и это честно.

**Sentry, 23 ребёнка эталона.** Найдено 2: Sentry Web = `self-hosted` (единственный Dockerfile
репозитория, по правилу единственного контейнера владеет `src/`), PostgreSQL = `PostgreSQL`
(по `ENGINE` в `src/sentry/conf/server.py`, без адреса). Не найти по манифестам 21: Kafka,
Redis, Memcached, ClickHouse, Filestore, taskbroker-sentry, taskworker, taskworker-scheduler,
Консьюмеры Kafka (процессы команд `sentry run …`, манифестов нет) и 9 сервисов других
репозиториев (Relay, Snuba, Symbolicator, Vroom, Seer, Chartcuterie, Launchpad, Objectstore,
uptime-checker, taskbroker). Все они описаны в `devservices/config.yml`: раздел `services:`
в формате compose (bigtable, redis-cluster, memcached, spotlight, relay-cell, relay-edge,
taskbroker-sentry) и раздел `x-sentry-service-config.dependencies` с `repo_link` на 14
репозиториев. Файл не называется compose, поэтому сборщик его не открыл. Web UI
(`static/app`) не процесс.

**Grafana, 4 ребёнка.** Сервер Grafana = `grafana` (корневой Dockerfile, Go + React) и ещё раз
`grafana-server` (юнит systemd из `packaging/`): дубль одного процесса из двух манифестов
одного корня, из-за него 426 маршрутов Go ушли в подсказку «несколько владельцев». Не
найти 3: Веб-приложение (статика в том же процессе), БД Grafana (SQLite по умолчанию, в
манифестах нет, миграции в Go-коде), NATS (встроенный). Лишнее 3: `custom`, `deb`, `rpm` из
`packaging/` (образы и пакеты дистрибутивов).

**Zabbix, 10 детей.** Ничего: манифестов развёртывания в репозитории нет, процессы в C
собираются autotools (`configure.ac`, `Makefile.am`), Go-процессы лежат по соглашению
`src/go/cmd/<имя>/`, Java gateway в `build.xml`. Сводка говорит «Ничего не найдено» и
называет PHP и неопознанный стек, без выдумок.

Итого по контейнерам: всё, что есть в compose, Dockerfile, supervisor, systemd и Procfile
эталонных репозиториев, найдено; промахи лестницы идут от имён. Пропуски сверх этого
распадаются на три класса: описано в формате, которого сборщик не читает (puppet,
devservices, autotools); процесс без манифеста; не процесс.

## 3. Каналы

Ориентир ТЗ: полнота ≥ 80 % и точность ≥ 90 % на Sentry и Zulip. Факт: 0 каналов строкой
на обоих, у Grafana и Zabbix каналов в эталоне нет (Grafana: один шаблонный subject NATS).

| репозиторий | каналов в эталоне | записано сборщиком | имён выражением в подсказках | где имена живут в коде |
|---|---|---|---|---|
| Sentry | 40 | 0 | 3 | перечисление `Topic` в `src/sentry/conf/types/kafka_definition.py` (`INGEST_EVENTS = "ingest-events"`) и словарь `KAFKA_TOPIC_TO_CLUSTER` в `conf/server.py:2740` (все 40 имён строкой); в вызовах продюсеров только `Topic.X` и `ArroyoTopic(topic)` |
| Zulip | 15 | 0 | 3 | декоратор `@assign_queue("deferred_work")` в `zerver/worker/*.py` у каждого потребителя (14 из 15 имён эталона, 15-й `notify_tornado` задан иначе; тестовые очереди помечены `is_test_queue=True`); публикация через свои обёртки `queue_event_on_commit("deferred_work", …)` с именем первым аргументом |

Вывод: правило «имя строкой в вызове клиента брокера» на зрелых кодовых базах не работает,
а имена при этом лежат в одном месте: реестр топиков (перечисление или словарь) и
декоратор потребителя. Два разборщика закрыли бы 40 из 40 и 14 из 15 с основанием
файл:строка.

Точность по выборке 55 %, и причина одна: разборщики кода читают всё дерево стека, включая
служебные каталоги (`tools/`, `scripts/`, `.github/`, `bin/`), тестовые помощники вне
`tests/` (`testutils/`, `testing/`) и конфиги инструментов (`jest.config.*`,
`playwright.config.*`, `*.config.js` в корне). Это не параметры контейнера, а окружение
разработчика и CI. Дешёвая починка: перечень служебных каталогов и файлов для разборщиков
кода (как `CODE_DEV_TOKENS`), плюс стандартные переменные ОС (`HOME`, `USER`, `PATH`, `TZ`,
`LANG`, прокси) в словарь-исключение. Таблицы и маршруты этим шумом не страдают: у них
источники только в миграциях и файлах маршрутов.

## 7. Что это значит для фазы 3 (решения владельца)

Ранжировано по цене и выигрышу на этих четырёх репозиториях:

1. **Шум параметров** (раздел 5): перечень служебных каталогов и файлов для разборщиков
   кода и словарь переменных ОС. Малая правка в `scan/`, поднимает точность параметров с
   55 % к 90 % и выше по выборке. Можно сделать до фазы 3 отдельной мини-фазой.
2. **Реестры каналов** (раздел 3): перечисление строк и словарь имён топиков в модуле,
   который импортируют вызовы клиента (Sentry 40 из 40), и декоратор потребителя с именем
   очереди (Zulip 14 из 15; `@assign_queue` конкретен, общий случай: декоратор проекта,
   первый аргумент которого строка, а модуль подключает клиент брокера). Это и есть путь к
   ориентиру «≥ 80 %» ТЗ.
3. **Манифесты не по имени, а по содержимому**: файл YAML с разделом `services:` и ключами
   `image`/`build` у сервисов читать как compose (Sentry `devservices/config.yml`: +7
   контейнеров), а `repo_link`/`repo_name` в нём давать подсказкой «сервис из другого
   репозитория» (+9 заглушек для агента). Puppet (Zulip: RabbitMQ, Redis, memcached,
   Smokescreen, go-camo) оставить в «не покрыто» с именем стека.
4. **Процессы по соглашениям кода без манифестов**: `cmd/<имя>/main.go` и `src/go/cmd/<имя>/`
   (Zabbix web service, Grafana `pkg/cmd/*`), `bin_PROGRAMS`/`sbin_PROGRAMS` autotools (Zabbix
   server, proxy, agent, get, sender), `build.xml` Java. Для Zabbix это 7 из 10 детей
   эталона; иначе репозиторий остаётся пустым.
5. **Дубли одного процесса из двух манифестов одного корня** (Grafana `grafana` и
   `grafana-server`; Zulip supervisor и Dockerfile): склейка по общему каталогу кода, когда
   команда одного указывает на бинарь другого. Освободит 426 маршрутов Grafana.
6. **Лишние объекты от хостинга и упаковки** (Zulip `zulip_ops`, Grafana `packaging/`): не
   трогать, это факты манифестов; агент или человек уберут при импорте.

Агентский шаг промпта (ТЗ, фаза 3) имеет смысл после пунктов 1 и 2: сейчас сводка честно
говорит «каналов нет», и агенту пришлось бы искать их заново.
