## 0. Цель

Контейнер — узел с детьми (`shape === "service"` && `has_children`). Реализовать три
правила (заданы в дизайн-сессии 2026-08-03, зафиксированы в tasks.md в эпике

## 1. ПРАВИЛА (полный свод решений дизайн-сессии 2026-08-03)

### Правило (а) — у контейнера НЕТ своей логики и спек
- Секция «Логика» на странице контейнера = **ОБЪЕДИНЕНИЕ доков всех НЕПОСРЕДСТВЕННЫХ
  детей** (единый список с пометкой, от какого ребёнка). Секция «OpenAPI» — аналогично
  (объединение openapi_spec детей).
- **Свои** доки/спеки контейнера (grandfather — созданные, когда узел был атомарным) —
  **ОТДЕЛЬНО сверху с предупреждением**, не в общем объединении.
- **Углубление** (узел с доками стал контейнером — добавили ребёнка): доки **остаются**
  на контейнере (grandfather) + алерт-подсказка; перенос — отдельное действие,
  НЕ блокирует создание ребёнка.
- **Перенос**: кнопка **«Распределить по детям»** в секции у своих (grandfather) доков
  **И** клик по алерту → **ОДНА модалка**: назначить каждый свой док/спеку конкретному
  ребёнку (выбор из детей), `node_docs.node_id` переносится на детей.
- **Enforced**: на странице контейнера **скрыты** «+ Добавить схему» и «+ Добавить
  спецификацию» (новое создавать нельзя — только перенос grandfather-доков на детей).

### Правило (б) — у контейнера НЕТ своей технологии
- Поле «Технология» на странице контейнера = **агрегированный список уникальных
  технологий детей** (напр. «Python, PostgreSQL, Kafka»), **НЕ редактируется**.

### Правило (в) — тип
- «Контейнер» vs «сервис» **вычисляется по наличию детей** (уже так и работает везде:
  `canHaveChildren(shape) && has_children`). Отдельным признаком не хранить.
- Детей может иметь **только `shape === "service"`** (БД и брокеры всегда атомарны) —
  уже обеспечено `canHaveChildren` (frontend/src/types/index.ts:19) и N4 в node.md.

### Дополнительные решения
- Поле **«Роль»** у контейнера **остаётся редактируемым** (роль описывает назначение
  контейнера, не сумму детей).
- **Дети контейнера — смешанные разрешены** (сервис + БД + брокер в одном контейнере).
- **АЛЕРТ**: новая категория в «Незавершённости схемы» (рядом с AL5/AL6/AL7):
  «У контейнера есть собственные доки/спеки — распределите по детям»; клик ведёт на
  страницу контейнера / в модалку распределения.
- **Глиф/бейдж контейнера на холсте — БЕЗ изменений** (свёрнутый гостевой — пунктирная
  коробка ContainerNode; локальный — глиф service с ChildrenBadge; раскрытый — FrameNode).
- **Процессы (контейнеры-участники) — БЕЗ изменений** (resolve_to_participant уже
  проецирует на ближайшего предка-участника).
- **Экспорт — нейтрален**: build_export доки/спеки не включает ни у каких узлов.
- **Миграция grandfather** — оставить как есть + алерт (не переносить принудительно).

## 2. ТЕКУЩЕЕ СОСТОЯНИЕ (разведка 2026-08-03) — что менять

### Бэкенд
- **`backend/app/models/node.py`** — Node: name, description, role, technology (свободные
  строки, nullable), parent_id (FK self, ondelete CASCADE), openapi_spec (Text, nullable),
  is_external, shape (service|database|broker|person, дефолт service), status
  (existing|planned|deprecated), version (CAS). Связи: children (cascade all,delete-orphan,
  passive_deletes), docs→NodeDoc (lazy="selectin"), outgoing/incoming_edges.
  **`has_children`/`child_count` — НЕ колонки БД**, а вычисляемые атрибуты экземпляра
  (аннотация без Mapped, дефолты child_count=0, has_children=False). Проставляются в:
  - `_mark_has_children(db, nodes)` — `backend/app/routers/nodes.py` (один SQL
    GROUP BY parent_id); зовётся в list_nodes, create_node, search_nodes,
    list_all_nodes, get_node, update_node, get_children, get_descendants.
  - `build_graph()` — `backend/app/graph_queries.py` (Counter по parent_id; тот же
    Counter питает `ghost_registry()` для GhostNodeResponse).
- **ЗАПРЕТОВ НЕТ**: контейнер сейчас может иметь свои node_docs, openapi_spec,
  technology, role — ни модель, ни роутеры это не проверяют.
- **`backend/app/schemas/node.py`** — NodeResponse: role, technology, openapi_spec,
  docs: list[NodeDocMeta] (меты без content), shape, status, is_external, child_count,
  has_children, version, даты. GhostNodeResponse — то же + ancestors.
- **NodeDoc** (backend/app/models/node_doc.py): id, node_id, name, kind
  (overview|operation|worker), operation, content (mermaid), version. CRUD —
  `backend/app/routers/node_docs.py`.
- **Алерты**: `compute_alerts(db, project_id)` — `backend/app/alerts.py`; эндпоинт
  GET /nodes/alerts в routers/nodes.py. 3 категории (AlertsResponse в schemas/node.py):
  disconnected_nodes (AL5, контейнеры исключены), intermediate_edges (AL6 — связь в
  контейнер, единственный нынешний контейнерный алерт), isolated_groups (AL7).
  Алерта «у контейнера свои доки» НЕТ. Спека alerts.md (AL1–AL23).
- **Создание детей**: create_node (routers/nodes.py) проверяет только существование
  родителя (scoped_node); ничего с доками/спеками/технологией родителя НЕ делает.
- **Экспорт**: build_export (backend/app/export.py) — контейнер через вложенность
  children; доки/спеки НЕ включает ни у кого.

### Фронтенд

  - `isContainer = canHaveChildren(shape) && node.has_children` (строка ~160) —

## 3. РАЗБИВКА НА ЭТАПЫ

### ЭТАП 1 — данные для страницы контейнера (бэк или фронт-агрегация)
Страница контейнера должна получить: (1) свои доки/спеку (уже есть в node), (2) доки и
технологии НЕПОСРЕДСТВЕННЫХ детей. Два варианта:
- **Вариант A (рекомендуется, проще)**: фронт сам фетчит детей через
  `nodesApi.getChildren(node.id)` (отдаёт NodeResponse[] с docs-метами и technology) и
  считает объединение доков + агрегированные технологии на клиенте. Бэк не менять
  (разве что убедиться, что getChildren помечает has_children — он уже зовёт
  _mark_has_children).
- **Вариант B**: добавить в NodeResponse агрегированные поля (children_technologies,
  children_docs_meta) — больше работы на бэке, но один запрос.
РЕШЕНИЕ при реализации: начать с варианта A; если запрос детей тяжёл — перейти к B.
Уточнить: объединение берём по НЕПОСРЕДСТВЕННЫМ детям (внуки — на своих страницах).

### ЭТАП 2 — отображение страницы контейнера (правила а + б), фронт
В `NodePage.tsx` для `isContainer`:
- «Логика»: свои (grandfather) доки `node.docs` — отдельным блоком СВЕРХУ с плашкой-
  предупреждением и кнопкой «Распределить по детям»; ниже — объединение доков детей
  (каждый с пометкой имени ребёнка-источника). Если своих доков нет — только объединение.
- «OpenAPI»: аналогично (своя спека `node.openapi_spec` сверху с предупреждением;
  объединение спек детей).
- «Технология» (в «Свойства»): агрегированный список уникальных технологий детей,
  read-only (не input). Своё поле technology контейнера не показываем/не редактируем.
- «Роль»: оставить редактируемой (как сейчас).
- **Скрыть** `addLogicMenu`/`addSpecMenu` («+ Добавить схему/спецификацию») для контейнера.
- Пустые состояния: если у контейнера нет ни своих доков, ни доков детей — «Схемы логики
  не заданы» (без меню добавления).

### ЭТАП 3 — модалка распределения доков (перенос на детей)
- Новый компонент (напр. `frontend/src/components/DistributeDocsModal.tsx`), по образцу
  EdgeEditModal (ui/Modal + список). Для каждого своего дока/спеки контейнера — выбор
  ребёнка (из непосредственных детей). Кнопка «Распределить»/«Применить».
- **Бэк-эндпоинт переноса**: обновить `node_docs.node_id` (перенести док с контейнера на
  ребёнка). Варианты: (а) PATCH в node_docs-роутере с полем node_id + проверкой, что новый
  родитель — ребёнок исходного узла; (б) отдельный эндпоинт
  POST /nodes/{id}/distribute-docs с маппингом {doc_id: child_id}. Выбрать при реализации,
  согласовать с контрактом. Не забыть про openapi_spec (он один на узел — переносится
  целиком на одного ребёнка; продумать, если детей несколько).
- Версия/CAS: перенос меняет node_docs — учесть version (как в node_docs CRUD).
- Точки входа: кнопка «Распределить по детям» в секции «Логика» (у своих доков) + клик по
  алерту (этап 4) — обе открывают одну модалку.

### ЭТАП 4 — новый алерт «у контейнера свои доки»
- **Бэк**: в `compute_alerts` (backend/app/alerts.py) добавить категорию — контейнеры, у

## 5. ПОДВОДНЫЕ КАМНИ
- **Объединение по непосредственным детям** (не внукам) — зафиксировать; вложенные
  контейнеры показывают свои доки на своих страницах.
- **openapi_spec один на узел**: при переносе на нескольких детей — решить (перенести
  одному, или запретить если детей >1 и спека одна). Продумать в этапе 3.
- **grandfather-технология**: у контейнера может остаться своё поле technology — его не
  показываем (правило б), но в БД оно остаётся (не вычищаем принудительно).
- **CAS/version** при переносе node_docs и изменении узлов — учесть (как в node_docs CRUD).
- **Правила НЕ трогают**: глиф/бейдж на холсте, процессы (контейнеры-участники), экспорт,
  создание детей (оно по-прежнему свободное, просто доки остаются grandfather'ом).
- **person** не может быть контейнером (canHaveChildren false) — не обрабатываем.
- NodePage рендерит секции для всех кроме person — проверить, что isContainer-ветка не
  ломает атомарные узлы и person.
