## 0. Как мы сюда пришли

2026-08-10 сделан авторинг ветки «иначе» у `alt` (коммит `e8e6470`, принят не был —
пользователь сразу задал вопрос). Я спрятал кнопку «+ иначе» после появления первой
ветки. Пользователь спросил: «а разве внутри alt может быть только одна ветка? я бы
не убирал кнопку, пока под создание новых веток хватает стрелок».

**Он прав.** Моя формулировка «делить нечего» затуманила суть: кнопка пряталась не
по UX-решению, а потому что вторую границу физически некуда записать.

### Проверено, не додумано

**Mermaid держит N ветвей.** Прогнал настоящим парсером `mermaid@11.15.0` (не по
памяти, не по докам):

```
одна ветка else → ПРИНЯТО
ТРИ ветки else → ПРИНЯТО
```

Воспроизвести (из `frontend/`):

```bash
node --input-type=module -e '
import { JSDOM } from "jsdom";
const dom = new JSDOM("<!doctype html><body></body>", { pretendToBeVisual: true });
globalThis.window = dom.window; globalThis.document = dom.window.document;
const { default: mermaid } = await import("mermaid");
mermaid.initialize({ startOnLoad: false });
await mermaid.parse(`sequenceDiagram\n A->>B: q\n alt ок\n  B->>A: r\n else нет\n  B->>A: e\n else таймаут\n  B->>A: t\n end`);
console.log("три ветки приняты");'
```
⚠️ `globalThis.navigator` присваивать НЕЛЬЗЯ (только getter) — падает.

В грамматике за это отвечает рекурсивное правило `else_sections` (символ 41 в
`node_modules/mermaid/dist/chunks/mermaid.core/sequenceDiagram-*.mjs`, продукция
`case 48`: `$$[$0-3].concat([{type:"else", ...}])` — приписывает ветку к списку).

**Ограничение целиком наше и сидит в МОДЕЛИ, не в экспорте.** Цепочка:

| Слой | Ветвей | Кто ограничивает |
|---|---|---|
| Mermaid | сколько угодно | — |
| `toMermaid.ts` | одну | выводит то, что есть в модели |
| **`ProcessFragment`** | **одну** | ← корень: пара `else_order`/`else_guard` |
| Рендер `SequenceDiagram` | один разделитель | следом за моделью |

Сужение было осознанным в исходном ТЗ — докстринг модели: «для alt — **вторая**
ветка [иначе] (ТЗ §2.2)».

**Импорт процессов НЕ сделан** (в бэклоге `tasks.md`) — обратную совместимость
разбора N ветвей закладывать не нужно. Затронут только экспорт.

**Живых данных под миграцию почти нет:**

```bash
PGPASSWORD=postgres psql -U postgres -h localhost -d archmap -tAc \
  "select count(*), count(else_order) from process_fragments;"   # → 5 | 0
# kind: alt 1, opt 4
```

Переносить нечего, но код переноса писать надо: он обязан быть корректен вообще.

## 1. Ключевое решение

**Отдельная таблица `process_fragment_branches`** (`id`, `fragment_id` CASCADE,
`start_order` int, `guard` varchar(256)), а НЕ JSON-массив в колонке.

Почему не JSON: границы ветвей — те же `order` сообщений, что `from_order`/`to_order`.
Они участвуют в проверках («строго возрастают, все строго внутри охвата») и в
будущем — в пере-нумерации при перестановке шагов. В JSON это ручной разбор в каждом
месте; строками — обычный `ORDER BY` и обычные проверки.

**Первая ветка остаётся в `guard` самого фрагмента** — у неё нет своей границы, она
начинается с `from_order`. Строки таблицы — только ветки со второй и дальше.

## 3. Фазы

Чекпойнт (коммит + прогон гейта) после каждой.

**Ф1. Модель и миграция.** Таблица ветвей; перенос существующих `else_order`/
`else_guard` в строки; удаление старых колонок. Гейт: `alembic upgrade head` и
`downgrade` на копии базы (downgrade обязан вернуть колонки и данные — ветвей больше
одной он сохранить не сможет, это осознанная потеря, записать в docstring миграции).

**Ф2. Контракт.** `branches: [{start_order, guard}]` вместо `else_*`.
Проверки в `_check_fragment` (уже существует, расширить):
- ветви только у `alt`;
- `start_order` строго возрастают;
- каждая строго внутри охвата: `from_order < start_order ≤ to_order`;
- ветвей не больше, чем шагов в охвате (иначе ветка без единого шага).
Проверять РЕЗУЛЬТАТ патча, а не вход (см. §5). Не забыть `app/projects.py`.
После правки схем: `cd frontend && npm run gen:api`, коммитить генерат вместе.

**Ф3. Рендер.** N разделителей вместо одного. `fragHeadOff` начисляет `SQ.ELSE_GAP`
на КАЖДУЮ ветку (сейчас однократно) — самое хрупкое место, см. §5.

**Ф4. Жест.** Каждая граница тянется; соседние не перепрыгивают друг друга; грани
рамки не проглатывают ни одну ветку. Кнопка «+ иначе» живёт, **пока ветвей меньше,
чем шагов в охвате** — правило пользователя.

**Ф5. Экспорт.** N строк `else` в `toMermaid`. Сверить с настоящим парсером mermaid
командой из §0 — не полагаться на глаз.

## 4. Риски

**Смена контракта ломает уже ПРИНЯТОЕ.** Правка охвата фрагмента (`8ea6815`) и
авторинг ветки (`e8e6470`) написаны против `else_*`. Переприёмка обязательна.

**`fragHeadOff` — тихий разъезд.** Он накапливает высоты шапок фрагментов и зазоров
ветвей, чтобы строки не наезжали. Ошибка здесь не падает, а молча смещает геометрию —
ловится только глазами. Обязателен тест «три ветки → три зазора».

**Downgrade необратим для N>1.** Обратная миграция сможет сохранить только первую
ветку. Записать в docstring миграции явно.

## 5. Уроки этого куска кода (НЕ ПОТЕРЯТЬ)

Всё найдено 2026-08-10 при работе над фрагментами; фрешевая сессия этого не знает.

**Один источник правды для границ.** В `SequenceDiagram` есть `fragRows(f)` — даёт
действующие границы (во время жеста живые, иначе сохранённые). Через него проходит
ВСЯ геометрия. Изначально `onRootUp` считал границы заново — и разъехался с
картинкой: клампы про ветку были в рендере, а в коммите нет. **Тест это поймал.**
Правило: и рендер, и отпускание берут `fragRows(f)`, не пересчитывают.

**Фрагмент — диапазон ПОЗИЦИЙ, а не набор шагов** (решение пользователя 2026-08-10,
`03e2f27`). При перестановке шагов границы стоят, состав меняется. Ветви наследуют ту
же семантику: их `start_order` — позиция, а не привязка к сообщению.

**Проверять результат патча, а не вход.** `update_fragment` сперва делал `setattr`,
потом валидировал — отказ оставлял в сессии грязный объект. Сейчас собирается `merged`
из `data.get(field, getattr(frag, field))`, валидируется, и только потом пишется.

**`suppressClick`** — реф в `SequenceDiagram`. После жеста браузер шлёт `click`;
без гашения перетаскивание заканчивалось бы окном удаления. Любая новая ручка,
лежащая на кликабельном элементе, обязана его выставлять.

**Порядок роутов.** `PATCH /{id}/messages/reorder` объявлен ДО `/{message_id}` —
иначе FastAPI примет «reorder» за uuid. Та же грабля была с `/nodes/transition`.

**Порог жеста** `DRAG_SLOP = 4` отделяет драг от клика; ручки граней —
`fragEdgeStyle`, толщина `FRAG_EDGE_H = 11`, полосы захвата стрелок — `GRAB_W = 16`,
`pointerEvents: "stroke"`.

**jsdom-полифилы уже добавлены** в `frontend/src/test-setup.ts`: `IntersectionObserver`
и pointer capture. Тесты жестов работают: `fireEvent.pointerDown/Move/Up`, координаты
через `clientY` (в jsdom `getBoundingClientRect` возвращает нули, и это не мешает).

**Дисциплина тестов.** Каждый тест ЛОМАТЬ и убеждаться, что падает. Файл кода
копировать в scratchpad и восстанавливать оттуда — `git checkout <file>` СНОСИТ
незакоммиченную работу (обжигался).

**Бизнес-процессы НЕ покрыты реестром `docs/specs`** (решение 2026-07-16,
`docs/specs/README.md:76`). Документировать в `spec.md`, инварианты не заводить.
