## 1. Цель и границы

**Цель.** Удалённый MCP-эндпоинт `/mcp` на каждом развёрнутом ArchMap и личные токены
доступа для него. Агент видит и правит ровно то, что видит и правит владелец токена.
Локальный stdio-вариант из `mcp/` остаётся: он нужен для работы с файлами на машине
агента (архивы проекта).

**Входит.**
- Личные токены доступа (PAT): выпустить (показ один раз), список, отозвать; «только
  чтение»; срок; хранение хэшем. Токен — учётная запись всего `/api/v1`, не только MCP.
- `/mcp` (Streamable HTTP, без состояния) в процессе бэкенда во всех трёх поставках:
  сервер с nginx, Docker Compose / единый образ, Helm.
- Удалённый набор инструментов: 28 из 31, без инструментов, работающих с диском агента.
- Защита: только личный токен, проверка Origin, лимиты частоты, предел тела, журнал
  «чей токен что сделал», выключение в демо-режиме.
- Окно «Токены для агентов» в меню профиля с готовыми строками подключения.
- Отказы инструментов помечаются `isError` — в обоих режимах, stdio и удалённом (Р12):
  сейчас докстринг `mcp/archmap_mcp/server.py` это обещает, а код не делает.
- Документация: `mcp/README.md`, `DEPLOY.md`, `spec.md`, `tasks.md`, `CLAUDE.md`/`QWEN.md`;
  передача списка изменений сессии документации (`../archmap-docs`).

**Не входит — и что понадобится потом.**
- **OAuth 2.1 по спецификации MCP** — для Claude Desktop (пользовательские коннекторы) и
  коннекторов claude.ai. Эти клиенты не дают вписать заголовок: они ждут метаданные
  защищённого ресурса (RFC 9728, `/.well-known/oauth-protected-resource`), сервер
  авторизации (метаданные RFC 8414, `/authorize` со входом и согласием, `/token`, PKCE,
  динамическая регистрация клиентов RFC 7591) и токены с аудиторией `/mcp`. Это свой
  сервер авторизации в ArchMap или внешний IdP — отдельный эпик. Задел этого эпика:
  токены уже хранятся хэшем с владельцем и сроком (таблица годится и для выданных по
  OAuth), пути `/.well-known/oauth-*` во всех поставках доходят до API, ответ 401 несёт
  `WWW-Authenticate`. Обход для Claude Desktop — мост `mcp-remote` с заголовком (если он
  разрешён в контуре): только упомянуть в README, не поддерживать.
- Ссылки на скачивание архива, zip телом вызова, удалённая догрузка архивов.
- Токен, ограниченный проектами; экран администратора со всеми токенами; массовый отзыв;
  журнал действий в БД; лимиты, общие на все процессы и реплики (нужен общий счётчик).
- Серверные уведомления, SSE-поток, сессии с состоянием, возобновление.
- MCP на демо-стенде (§3, Р8).
- Удаления через токен, включая «Принять переход» (§3, Р4).

## 3. Решения

**Р1. `/mcp` живёт в процессе бэкенда — маршрутом `Route`, не `Mount`.** Один маршрут в
`app.main` — и он одинаково работает в dev, на сервере (`app.main:app`), в образе
(standalone поверх `app.main`) и в Kubernetes. Отвергнуто:
- отдельный процесс или сервис MCP — это третья служба в трёх поставках (юнит systemd,
  процесс в образе, порт и маршрут в чарте) ради того же HTTP API;
- FastMCP со своим Starlette-приложением через `Mount` — см. ловушки ниже.

⚠️ `Mount("/mcp")` ловит только `/mcp/…`: при `redirect_slashes=False` запрос на `/mcp`
получил бы 404. Нужен `starlette.routing.Route("/mcp", endpoint=<ASGI-объект>)`. Такой
маршрут (не `APIRoute`) в OpenAPI не попадает — `api.gen.ts` от `/mcp` не меняется.

⚠️ Lifespan подприложения Starlette не исполняет — менеджер сессий SDK запускается в
lifespan самого `app.main`.

**Р2. Транспорт — Streamable HTTP, `stateless=True`, `json_response=True`.** Почему:
- рабочих процессов несколько (сервер — 2, образ — `WEB_CONCURRENCY=2`), реплики Helm идут
  без липких сессий — запрос может попасть в любой процесс;
- серверных уведомлений и прогресса у инструментов нет: запрос → ответ;
- JSON-ответ проходит любые прокси без настройки буферизации и не ломается от gzip.

GET и DELETE на `/mcp` → 405 с `Allow: POST`. Спецификация MCP это разрешает («сервер не
предлагает SSE-поток»). Без этого GET в режиме без состояния держал бы висящее соединение
до таймаута прокси (фактическое поведение SDK записать в Ф0). Тело запроса — до
`MAX_REQUEST_MB`: свой предел SDK (4 МиБ) пакет доков крупного монолита превышает.

**Р3. Инструменты переиспользуются как есть, через HTTP API в процессе.** Пакет
`archmap_mcp` остаётся в `mcp/` со своим гейтом (ruff + mypy + pytest); stdio-вариант не
меняет поведения. Бэкенд пакет импортирует. Инструменты по-прежнему ходят в HTTP API, но
в процессе: `httpx.AsyncClient(transport=httpx.ASGITransport(app=<FastAPI>))` с токеном
ВЫЗЫВАЮЩЕГО в `Authorization`. Выигрыш: права, пределы демо, длины полей, CAS и тексты
отказов — ровно те же, что у интерфейса; ни строчки домена не дублируется; тесты MCP на
подменённом транспорте остаются в силе.

Раскладка:
- `mcp/archmap_mcp/remote.py` — протокольный слой: низкоуровневый `Server` на удалённом
  каталоге, менеджер сессий SDK, клиент ArchMap на каждый вызов, журнал вызовов,
  «кто я» по токену. Знает только HTTP API и SDK, кода бэкенда не импортирует.
- `backend/app/mcp_http.py` — клей в бэкенде: демо-режим, метод, Origin, лимиты, проверка
  токена, запуск и остановка в lifespan.

Как бэкенд находит пакет:
- в поставках пакет кладётся РЯДОМ с `app/` (образ — `/opt/archmap/backend/archmap_mcp`,
  архив поставки — `backend/archmap_mcp`), импорт прямой;
- в репозитории пакет лежит в `mcp/`. `app/mcp_http.py` при `ModuleNotFoundError` именно
  для `archmap_mcp` добавляет `<repo>/mcp` в `sys.path`. Это ОДНО место на все входы:
  uvicorn в dev, `npm run gen:api`, CI-джоба contract, `scripts/*.py`, pytest;
- mypy бэкенда — `mypy_path = "../mcp"` и `follow_imports = "silent"` для `archmap_mcp.*`:
  строгость пакета держит его собственный гейт.

Отвергнуто:
- вызывать домен напрямую, без HTTP: переписать 31 инструмент и продублировать правила
  доступа;
- копия пакета в `backend/` — две правды;
- симлинк — Docker `COPY` переносит его висячим;
- `pip install -e ../mcp` — поставка ставится из lock с `--require-hashes`, у локального
  каталога хэша нет;
- `PYTHONPATH` в каждом входе — шесть мест, а следующий вход забудут.

**Р4. Личные токены доступа (PAT).**
- **Формат.** `archmap_` + `secrets.token_urlsafe(32)` (256 бит). В БД — только sha256
  (hex) и префикс для опознания (`archmap_Ab3dEf`, 14 знаков); сам токен показывается
  один раз, в ответе на создание. Хэш без соли и без «перца»: у случайного 256-битного
  секрета перебор невозможен (так хранят токены крупные хостинги кода), а привязка к
  `SECRET_KEY` сломала бы все токены при смене ключа.
- **Таблица `personal_tokens`:**
  - `id`;
  - `user_id` → `users` (CASCADE);
  - `name` (64, уникально у пользователя);
  - `prefix` (16);
  - `token_hash` (64, unique);
  - `read_only` (bool);
  - `created_at`, `last_used_at` (null);
  - `expires_at` (null — бессрочно).
- **Срок** — 30, 90 или 365 дней, или бессрочно; по умолчанию 90. У пользователя — не
  больше 20 токенов. Отзыв — удаление строки: журнал хранит имя и префикс, ссылаться на
  строку незачем.
- **Права = права владельца.** Их решает строка пользователя в БД на каждом запросе, как у
  JWT: блокировка учётки гасит её токены сразу, смена роли действует сразу. Сам токен прав
  не несёт.
- **Учётная запись всего API, а не только MCP.** `get_current_user` принимает PAT на всём
  `/api/v1` (тот же `Authorization: Bearer`; ветка по префиксу — ДО разбора JWT). Почему:
  инструменты MCP ходят в обычный API; заодно токен годится скриптам и CI (синк схемы из
  пайплайна) и локальному stdio (`ARCHMAP_TOKEN` вместо пароля в `mcp/.env`). Отвергнуто
  «токен только через `/mcp`»: внутренним вызовам понадобился бы неподделываемый признак,
  а скрипты остались бы без токена.
- **Чего токен не может (в интерфейсе — можно):**
  - управлять токенами (`/tokens`, кроме `GET /tokens/current`);
  - менять пароль;
  - `/admin/*`;
  - управлять проектом на уровне владельца: `PATCH /projects/{id}` (карточка и
    видимость), `archive`, `restore`, участники, `transfer`;
  - удалять — метод DELETE запрещён целиком;
  - «Принять переход» (`POST /nodes/transition` — физическое удаление по списку).

  Мотив — принцип MCP «удалений нет ни одного; сносит человек глазами» и вред утёкшего
  токена: им можно испортить знание (это откатывается правками), но нельзя снести проект
  или выпустить себе новый токен.
- **Только чтение (`read_only`).** Разрешены лишь GET/HEAD/OPTIONS. Правило — по методу и в
  одном месте (`get_current_user`), а не по списку ручек: новая пишущая ручка закрыта по
  умолчанию. Проверено (§2): все инструменты чтения и промпты — GET, все превью и записи —
  POST/PATCH. Превью требуют роль редактора, поэтому токену только для чтения не нужны.
- **Признак «запрос по токену»** хранится в `request.state` (`get_current_user` получает
  `Request`). ⚠️ НЕ `ContextVar`: `get_current_user` — синхронная зависимость, FastAPI
  исполняет её в пуле потоков, и выставленное там значение до ручки не доходит.
- **Ручки:**
  - `GET /api/v1/tokens` — свои токены;
  - `POST /api/v1/tokens` → 201 `{token, secret}`;
  - `DELETE /api/v1/tokens/{id}` — свой токен (чужой — 404);
  - `GET /api/v1/tokens/current` — ТОЛЬКО по токену: кто владелец и что за токен (нужен
    клею `/mcp`); по JWT — 404.

  Управлять токенами можно только из сессии интерфейса.
- **Демо:** в `DEMO_MODE` выпуск → 403, вход по токену → 401 (Р8).

**Р5. Удалённый набор — 28 из 31: файловые инструменты убраны.**
- `archmap_export_archive` убран. Архив — файл для человека (бэкап, перенос), и в
  интерфейсе для этого есть кнопка. Вернуть архив в разговор — выложить весь проект в
  контекст модели. Ссылка на скачивание — новая поверхность атаки (секрет в URL, в журналах,
  в истории чата) ради сценария, который закрывают интерфейс и локальный вариант.
- `archmap_import_into_preview`/`apply` убраны: принимают только zip путями.
- `archmap_import_preview`/`apply` принимают только YAML текстом (`files`): `paths` убран из
  схемы и описаний. Архив ввозят в интерфейсе («Новый проект» → из файлов) или локальным
  вариантом.

⚠️ **ГЛАВНАЯ ЛОВУШКА ЭПИКА.** В удалённом режиме «диск агента» — это ДИСК СЕРВЕРА
ArchMap. `_inputs`/`_archives` читают `paths`, `_export_target` пишет `out_path`. Дойди
вызов до них — агент читал бы файлы сервера (ключ подписи в `/data`, `/etc/…`) и выгружал
бы их во вход импорта, а архив писал бы на диск сервера. Скрыть инструмент из списка мало:
SDK сверяет аргументы со схемой, но лишних свойств она не запрещает, а `call_tool`
вызывается по любому имени. Нужен отказ на диспетчере удалённого режима: имя из локального
набора → отказ; ключ `paths` или `out_path` в аргументах → отказ. Плюс тест-сторож с
подменёнными `Path.read_bytes`/`is_file`/`stat`/`open`, которые падают при любом обращении
к файловой системе.

Описания удалённого набора не упоминают убранные инструменты, `paths`, `out_path`,
«с диска» (тест).

**Р6. «Только чтение» в MCP.** Токену только для чтения `list_tools` отдаёт инструменты без
записи (флаг `writes` в каталоге): 13 из 28. `call_tool` отказывает пишущему инструменту
понятным текстом. Решает бэкенд (403 по методу); список — лишь подсказка агенту.

⚠️ `_tool_cache` SDK общий для всех запросов, поэтому ни кэш, ни список не защита: защищают
только проверка в `call_tool` и бэкенд.

**Р7. Защита публичного эндпоинта.**
- **Только личный токен.** Без заголовка, с JWT вместо токена, с отозванным или истёкшим
  токеном — 401 `{"detail"}` и `WWW-Authenticate: Bearer error="invalid_token"`, без
  `resource_metadata`: OAuth пока не предлагаем.
- **Проверка токена** — внутренним `GET /api/v1/tokens/current` через тот же
  `ASGITransport`. Путь аутентификации один (`get_current_user`), и в тестах работает
  подмена `get_db`.
- **Origin.** Нет заголовка — пускаем: агенты его не шлют. Есть, но не входит в
  `MCP_ALLOWED_ORIGINS` (по умолчанию пусто) — 403. Этого требует спецификация MCP против
  DNS rebinding. Host не сверяем: эндпоинт публичный по замыслу, а доступ решает токен в
  заголовке, не cookie, — без токена запрос из чужой страницы бесполезен. Список хостов
  иначе пришлось бы настраивать при каждой установке. Защиту SDK
  (`TransportSecuritySettings`) — явно выключенной, свою проверку — в клее.
- **Лимиты** — в памяти процесса, как `AddressLimiter`; это защита от злоупотреблений, а не
  учёт:
  - неудачные проверки токена — 30 в минуту с адреса (`client_address`) → 429;
  - запросы к `/mcp` по одному токену — `MCP_REQUESTS_PER_MINUTE` (по умолчанию 300, 0 —
    без предела) → 429.
- **Тело** — до `MAX_REQUEST_MB`: Standalone и nginx режут по нему же, предел SDK
  выставить тем же числом.
- **Журнал** — логгер `archmap.mcp`, строка на каждый `tools/call`:
  - пользователь;
  - токен (имя и префикс);
  - инструмент;
  - проект (как передан, обрезанный и экранированный — без переводов строк);
  - итог (ок / отказ / сбой), мс, адрес.

  Аргументов НЕ пишем: там документы целиком. Отказы аутентификации — с адресом.
  ⚠️ uvicorn настраивает только свои логгеры: без обработчика INFO из `archmap.mcp`
  пропадёт. Обработчик в stderr ставится в lifespan, если у логгера его ещё нет
  (journald и `docker logs` его соберут).
- **HTTPS.** Вне localhost — только HTTPS (токен идёт в заголовке): в `DEPLOY.md`.

**Р8. Демо-режим — MCP выключен.**
- `/mcp` → 404 «На демо-стенде подключение агента недоступно»;
- выпуск токенов → 403, вход по токену → 401;
- менеджер SDK в lifespan не стартует.

Почему: гость живёт сутки, входа по логину нет, вместо меню профиля у гостя пилюля
«Обучение». Публичный эндпоинт с правом записи для анонимных песочниц — нагрузка и
злоупотребления без пользы продукту. Включить позже — отдельным решением: выпуск токена
гостю из пилюли, предел вызовов на песочницу, уборка токенов вместе с гостем (каскад по
`user_id` уже будет).

**Р9. Поставка: `/mcp` доходит до бэкенда везде.**
- **Образ, Compose, Kubernetes (standalone).** В `is_api_path` добавить `/mcp` и префикс
  `/.well-known/oauth-`. Они уходят в API и получают 404 JSON, а не `index.html`: при 401
  клиенты ищут метаданные OAuth и получили бы страницу интерфейса с кодом 200.
- **Helm.** Шаблоны не меняются: Ingress и HTTPRoute уже ведут `PathPrefix /` в под,
  таймаут HTTPRoute 300s есть. Для Ingress — дописать `/mcp` в комментарий к
  `ingress.annotations` в `values.yaml`.
- **Сервер с nginx.** В `render_nginx`:
  - `location = /mcp` — `proxy_pass`, `proxy_read_timeout 300s`, `proxy_buffering off`
    (для JSON безвредно, нужно, если когда-нибудь включат SSE);
  - `location ^~ /.well-known/oauth-` — `proxy_pass`.

  ⚠️ При обновлении установщик конфиг nginx не переписывает. На существующих серверах
  `/mcp` уйдёт в `try_files` и вернёт 405 или страницу. Поэтому установщик предупреждает
  (в конфиге нет `location = /mcp`) и печатает, что добавить; то же — в разделе
  «Обновление» `DEPLOY.md`.
- **Образ.** `COPY mcp/archmap_mcp`, в `.dockerignore` — `!mcp/archmap_mcp/`;
  `compileall` и для пакета.
- **Архив поставки.** В `PATHS` добавить `mcp/archmap_mcp`, копировать в
  `$STAGE/backend/archmap_mcp`.
- **Dev.** Vite проксирует `/mcp` на бэкенд: адрес в окне токенов
  (`window.location.origin + "/mcp"`) работает и в dev.
- **CI.** В джобах compose и helm (`e2e-kind.sh`) — смоук: вход админом →
  `POST /api/v1/tokens` → `POST /mcp tools/list` → в ответе есть `archmap_projects`;
  без токена → 401.

**Р10. Клиенты.** Заголовок по URL умеют:
- Claude Code: `claude mcp add --transport http archmap https://archmap.example.com/mcp
  --header "Authorization: Bearer …"`;
- Cursor, VS Code, Qwen Code.

Точные ключи конфигов исполнитель сверяет с документацией клиентов на момент написания
README. Токен в файлы под git не кладём: у Claude Code — хранилище пользователя (команда
выше) или подстановка `${ARCHMAP_TOKEN}` в `.mcp.json`. Claude Desktop и коннекторы
claude.ai ждут OAuth — вне эпика (§1).

**Р11. Локальный stdio остаётся** — для работы с файлами (архивы, ввоз zip). Каталог и
поведение не меняются, кроме пометки `isError` у отказов (Р12). Добавляется `ARCHMAP_TOKEN` (в `mcp/.env` или окружении) как
альтернатива логину и паролю — рекомендуемый способ: пароль в файле не нужен, токен
отзывается. Версия пакета — 0.6.0.

**Р12. Отказы помечаются `isError` — в обоих режимах.** Спецификация MCP различает ошибку
протокола (JSON-RPC error) и ошибку исполнения инструмента (`CallToolResult` с
`isError: true` и текстом причины). Отказ ArchMap — второе: текст причины по-прежнему
доходит до модели, а клиент и агент видят, что вызов не удался, и не принимают отказ за
результат (журнал клиента, ретраи, «вызов успешен» в интерфейсе).
- `answer()` возвращает не строку, а ответ с итогом: `ok` / `refused` / `failed`.
  - `refused` — отказ, который агент может исправить: `ArchMapError` (права, 404, 409,
    422, «неизвестный инструмент», «нечего менять»), «ArchMap не настроен», отказы
    удалённого диспетчера (Р5, Р6);
  - `failed` — сбой самого сервера (неожиданное исключение);
  - `ok` — всё остальное, включая содержательные «пустые» ответы («Проектов нет», план
    превью «не пройдёт» с перечнем ошибок): это ответ на вопрос, а не отказ.
- `call_tool` в обоих режимах отдаёт `CallToolResult(content=[TextContent],
  isError=итог != ok)`; тексты не меняются ни в одном слове.
- Итог — тот же, что пишет журнал удалённого режима (Р7: ок / отказ / сбой). Один
  источник: журнал и `isError` не разойдутся.

Отвергнуто: бросать исключение из обработчика, чтобы SDK сам поставил `isError` — SDK
отдаёт тогда `str(e)`, и для сбоя пропал бы текст «Сбой MCP-сервера ArchMap…» с именем
инструмента; плюс исключение не различает отказ и сбой для журнала.

## 5. Фазы

Общее для всех фаз:
