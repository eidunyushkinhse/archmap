# Замер полноты разведки (Zulip, 2026-08-16)

Первый в проекте замер ПОЛНОТЫ выдачи слабой модели. До сих пор мерялась только
точность (96–100%: 133 таблицы из 138, 51 топик из 52, 136 каналов без ошибки), а
сколько модель НЕ нашла — не мерил никто. Для обсуждаемого «нулевого шага»
(промпт-разведка возвращает список операций и воркеров монолита) это главный
показатель: неполный список выглядит ровно так же, как полный.

Артефакты, скрипты и сырые выводы — scratchpad/recon-qa/ (см. отчёт исполнителя).

## Истина (посчитана механически ДО прогонов)

- **Воркеры: 17** классов с декоратором `@assign_queue`, все в `zerver/worker/*.py`
  (14 боевых + 3 тестовых). Вне папки и вне декоратора воркеров нет.
- **Операции: 212** уникальных пар «метод + путь», из них **187 — ядро**
  (то, что ходит под `/api/v1` и `/json`). Объявляются двумя хелперами
  (`rest_path`, `remote_server_path`) в пяти файлах.
- Отдельно посчитано и в истину НЕ включено: 91 маршрут входящих вебхуков
  (генерируются циклом), 203 обычных маршрута, 14 puppet-кронов, крон
  email-mirror, демоны supervisor.
- Разбор AST, не текста. Одно объявление часто несёт 2–4 метода — каждый метод
  отдельная строка.

⚠️ **Дисциплина истины сработала буквально.** Первая версия экстрактора дала 199
операций и объявила 11 ВЕРНЫХ ответов модели «выдумками» — исполнитель не знал
про второй хелпер объявления маршрутов. Каждая «выдумка» была проверена по коду
до записи числа, экстрактор починен. Без этой проверки замер приписал бы модели
11 несуществующих ошибок.

## Прогоны разведки (два независимых, оба с первой попытки)

| | Прогон 1 | Прогон 2 |
|---|---|---|
| Операции, ядро (187) | **187 = 100%** | 186 = 99.5% |
| Операции, расширенная (212) | 207 = 97.6% | 200 = 94.3% |
| Точность операций | 97.2% | 99.0% |
| Выдумки | 1 (`POST /streams` — «по аналогии», в коде только GET) | 0 |
| Воркеры, очереди (14) | **14 = 100%** | **14 = 100%** |
| Имена обработчиков | 4/14 | 14/14 |

**ГЛАВНАЯ ЦИФРА: пропуски двух прогонов НЕ ПЕРЕСЕКАЮТСЯ ВОВСЕ.** Прогон 1
потерял tornado + analytics-remote + self-hosted-billing, прогон 2 — весь
zilencer и один метод. Объединение двух прогонов даёт **212/212 = 100%**.

**Имя обработчика — недоверенное поле.** Полнота списка ОЧЕРЕДЕЙ стабильна
(14/14 дважды), а имена классов скачут 4/14 ↔ 14/14: в слабом прогоне десять
имён синтезированы по конвенции из имени очереди (`embed_links` →
«EmbedLinksWorker» вместо реального `FetchLinksEmbedData`). Адресоваться надо по
имени ОЧЕРЕДИ, а не по имени класса.

## Скептик на ОБРАТНОЙ задаче («найди то, чего в списке нет»)

Порог V1 процитирован дословно. Три захода.

| Что проверял | Истинных пропусков | Нашёл | Выдумал |
|---|---|---|---|
| перечень прогона 1, заход A | 5 | 2 | **0** |
| перечень прогона 1, заход B | 5 | 4 | **0** |
| перечень прогона 2 (пропущен целый файл) | 12 | **11** | **0** |

Итого 17 верных пропусков, **ноль ложных**; все ссылки file:line проверены по
коду и точны.

**Скептик лечит неполноту ИЗБИРАТЕЛЬНО:**
- системный пропуск (непрочитанный источник целиком) — почти нацело, 11/11;
- рассыпанные одиночные — наполовину и с разбросом, 2/5 и 4/5;
- класс «взято одно из нескольких объявленных на строке» не найден НИ РАЗУ ни
  одним заходом: строка в перечне есть, у неё просто не хватает второго метода —
  это не видно ни по счёту файлов, ни по списку источников.

Порог V1 держит и на обратной задаче: ложных сомнений ноль, как и на прямой.

## Вердикт: разведка достижима

Это единственный из измеренных потоков, где слабая модель показала 100% ядра.
Рецепт из замера:

1. **Два прогона и объединение** — дешевле скептика и работает лучше: одиночный
   прогон даёт 94–98% и промахивается непредсказуемо, объединение дало 100% при
   нулевом пересечении пропусков.
2. **Скептик третьим шагом** — он ловит именно то, что переживает объединение:
   непрочитанный источник целиком.
3. **Имена обработчиков считать недоверенными**, адресоваться именем очереди.
4. **Второй метод одного объявления просить отдельным правилом** — единственный
   класс, который не лечится ничем из проверенного.

## Ревизия готового: три вывода, меняющие прежние планы

### 1. Потолок «12 схем на узел» НЕ является связывающим ограничением

Прошлый прогон Zulip дал **13 схем на весь проект** при 201 точке входа
(187 операций + 14 очередей) — покрытие **6.5%**. В том проекте было 36 узлов,
то есть потолок разрешал до ~432 схем. Агент сделал 13.

⚠️ Это ПРЯМО ОПРОВЕРГАЕТ блокер Б1 из docs/plan-process-docs-challenge.md, где
потолок назван препятствием для монолита. Снимать надо не потолок, а
**безадресность задачи**: «опиши логику сервиса» — задание без границ, и модель
сама выбирает, где остановиться. Разведка превращает одно неограниченное задание
в 201 ограниченное, под уже существующий гранулярный режим.

### 2. Самосверка счётом не удерживает вывод модели

Прогон 2 написал в разделе «источники»: «zilencer/urls.py (14 объявлений)» — и не
вывел из этого файла НИ ОДНОЙ строки. Самосверка выполнена, число названо верно и
проигнорировано.

Это измеренная форма полевого предупреждения «обещания в сводках оптимистичнее
фактов». Вывод для ВСЕХ промптов BYOA: число из сводки агента не является
подтверждением полноты пакета — сверять надо машиной по самому пакету.

### 3. Обход точек входа в промпте доков слабее, чем понадобилось для 100%

В `docs_prompt.py:150` одна строка про обход точек входа. В ней нет трёх правил,
каждое из которых в замере стоило реальных пропусков:
- «найди файл-СПИСОК маршрутов и дочитай его ДО КОНЦА» — прогон 1 оборвался на
  хвосте файла, потерял tornado и analytics;
- «одно объявление = несколько методов» — стоило единственного класса, который не
  вылечил и скептик;
- «маршруты добавляются ниже по файлу и в ДРУГИХ файлах» — стоило прогону 2
  всего zilencer.

Эти правила стоит забрать и в промпт доков: иначе документация пропускает то же
самое, только молча.

### 4. Класс фоновой работы, который не ищет ни один промпт

Кроме 14 очередей у Zulip есть 14 puppet-кронов, крон email-mirror и демоны
supervisor (tornado, tus, katex). **Ни один из пяти заходов агента (2 разведки +
3 скептика) их не вернул**, хотя промпт разведки прямо про это просил: модель шла
по маркеру в коде и останавливалась.

Для сервисов, где половина фоновой работы живёт в puppet/cron/systemd,
определение «воркер = маркер в коде» даёт систематически неполный ответ. Это
касается и существующего промпта доков («кроны и фоновые воркеры» там названы, но
поиск ведётся по коду сервиса).
