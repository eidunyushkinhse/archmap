# Условности эталона и формат файла фактов

Фаза 1 плана `docs/plan-proven-etalons.md`. Решения Р1–Р8 УТВЕРЖДЕНЫ владельцем 2026-11-12 в предложенном
виде (Р7 после уточнения о прозрачном прокси).
Автор: Claude Fable 5.2 (архитектор сессии).

Документ отвечает на два вопроса:

- часть А: по каким правилам доказанные факты становятся фигурами схемы и что из этого оценивается;
- часть Б: как записан эталон, чтобы его проверял скрипт.

Источники условностей: промпт ввоза (`backend/app/import_prompt.py`), правила элемента архитектуры
(`docs/plan-c4-elements.md`, раздел 1), спорные решения строителей эталонов v2 (файлы `notes.md` в
`etalons-v2/<ключ>/`), расхождения скептиков замера (`docs/qa-prompt-measure-2026-11.md`, разделы 5,
7, 10.3, 10.4).

## Часть А. Условности

### А0. Главный принцип

У каждого элемента схемы два утверждения:

1. **Существование**: «это есть в коде». Это факт, у него есть свидетель, он оценивается.
2. **Форма**: «это нарисовано так»: вид фигуры, тип, место в дереве, имя, группировка. Это
   условность. Она не оценивается полнотой и точностью.

Форму, о которой говорит промпт, проверяет отдельная метрика исполнения правил (план, раздел 2.2).
Так строитель, нарисовавший верный факт в другой форме, теряет балл за правило промпта, если оно
есть, и не считается выдумщиком.

Не оцениваются никогда: описания, подписи связей, роль, технология текстом, имена, вложенность
систем, люди, поле source. Часть из них проверяют правила промпта, часть остаётся на суждение.

### А2. Решения владельца

Р1–Р8 утверждены 2026-11-12 так, как предложено ниже (Р4: вариант «а»; Р7: связь с прозрачным
прокси без отдельного балла).

#### Р1. Рамка поставки

Спор: 16 объектов эксплуатации Zulip Cloud (`puppet/kandra`), стенды разработки Grafana (`devenv/`),
служебные экземпляры Sentry (второй taskbroker, relay для режима маршрутизации).

Предложение. В шапке эталона названы корневые манифесты поставки. Объект вне рамки определяется
механически, одним из трёх признаков:

- профиль разработки или тестов (профили compose, каталоги стендов, которые сборщик уже уносит в
  подсказки);
- манифест, который не подключает ни один корневой манифест поставки;
- манифест непрерывной сборки.

Такие объекты записаны в эталоне с пометкой «вне поставки» и не оцениваются: строитель, который их
нарисовал, не получает ни плюса, ни минуса по точности. Правило промпта «сервисы профиля разработки
в схему не бери» проверяется исполнением правил.

Выбор рамки для каждого репозитория остаётся разовым суждением и утверждается вместе с эталоном.

#### Р2. Режимы одного бинарника

Спор: роли `grafana server target=…` (скептик считает их контейнерами, эталон свернул в один);
`sentry run consumer X`; `manage.py X`.

Предложение. Режим это контейнер, когда в поставке есть строка, которая запускает именно его. Режим,
который бинарник умеет, но поставка не запускает, это факт с условием (свидетель: запись таблицы
режимов). Его форма не оценивается: и отдельный контейнер, и компонент допустимы.

Следствие для Grafana: строки запуска ролей есть только в файлах разработки, поэтому в эталоне один
контейнер и роли с условием. Обе модели замера, нарисовавшие роли контейнерами, выдумщиками не
считаются.

#### Р3. Группировка не оценивается

Спор: группа супервизора `zulip-workers` как система; подсистемы потребителей Sentry «ради
читаемости»; `zulip_events` как система у одного из прогонов.

Предложение. Вложенная система никогда не факт. Контейнер опознаётся по свидетелю запуска, а не по
пути в дереве, и сравнение идёт по множеству контейнеров. Эталон волен группировать как удобно
читателю.

Альтернатива: группа супервизора с `programs=` это факт «система» (в коде есть строка). Я против:
она требует отдельного правила на каждый вид группировки (пространство имён, чарт, профиль), а
выигрыш в оценке мал.

#### Р4. Задание расписания

Спор: эталон Zulip держит один узел cron, прогоны кандидата рисовали 13–23 задания компонентами и
теряли точность.

Варианты:

- (а) задание это компонент планировщика с реестром: свидетель это строка таблицы расписаний с
  командой; связи задания оцениваются на уровне контейнера-планировщика;
- (б) каждое задание это отдельный контейнер: у него своя команда запуска;
- (в) задание не объект, оцениваются только связи планировщика.

Предложение: (а). Планировщик порождает задания по своей таблице так же, как сервер Zabbix
порождает процессы по таблице типов (У7). Задания видны в схеме и несут свои связи, а число
контейнеров не раздувается.

#### Р5. Redis как хранилище и как шина

Спор: в эталоне Grafana Redis записан базой, хотя код публикует и подписывается; причина в том, что
связь с брокером без канала даёт рекомендацию.

Предложение. Вид узла решает свидетель: есть доказанный литерал публикации или подписки на этом
экземпляре, значит брокер, и каналы записаны с литералом основы (У18). Нет такого свидетеля, значит
база. Сам вид остаётся формой и не оценивается; оцениваются существование экземпляра, каналы и связи.

#### Р6. Фоновые обращения

Спор: все процессы Django у Zulip шлют ошибки в Sentry и ходят в общий кэш; эталон нарисовал связь
у одного контейнера и просил судью не считать остальные выдумкой.

Предложение. Обращение, цепочка которого идёт через общую инициализацию программы, а не через код
задачи контейнера, записано в эталоне один раз с пометкой «фоновое» и перечнем контейнеров. По
отдельным контейнерам оно не оценивается ни в полноте, ни в точности. Признак механический: точка
входа цепочки лежит в общем коде запуска (настройки, инициализация приложения).

#### Р7. Посредники

Спор: у Zulip исходящий HTTP идёт через Smokescreen, эталон держит и прямую связь с адресатом, и
связь с прокси; промпт требует два ребра через посредника.

Прокси из схемы не выпадает. Его узел это контейнер со свидетелем запуска, он оценивается как
любой контейнер. Различаются три случая.

**Прозрачный исходящий прокси.** Код сервиса обращается к адресату по адресу адресата и о прокси не
знает; прокси задан окружением программы (переменная вида `HTTP_proxy` в её строке запуска). Тогда:

- «сервис → адресат» это факт со свидетелем в коде сервиса, оценивается. Прокси не должен прятать,
  кто с кем говорит: модель, которая довела связь до прокси и остановилась, теряет полноту;
- «сервис → прокси» рисуется в эталоне у каждого сервиса, который ходит наружу. Эта связь
  выводится из двух других фактов (у сервиса есть доказанное исходящее обращение; строка окружения
  даёт ему прокси), нового знания о сервисе не несёт и записана с `scope: background`. Отдельного
  балла за неё нет: строитель, который её нарисовал, не выдумщик, а тот, кто не нарисовал, полноту
  не теряет;
- «прокси → адресат» в эталон не идёт: кода прокси в репозитории нет, свидетеля нет. Такая связь в
  модели получает исход «не определено».

**Посредник, к которому код обращается сам** (шлюз, сервис перекодирования картинок по своему
адресу). Обычная связь «сервис → посредник», оценивается.

**Обратный прокси** (nginx перед сервисами). Два факта: клиент → прокси и прокси → сервис;
свидетель второго это строка маршрута в настройках прокси.

Альтернатива для прозрачного прокси: оценивать «сервис → прокси» у каждого сервиса наравне с
остальными связями. Я против: число таких связей равно числу сервисов с выходом наружу, и они
дублируют в оценке уже посчитанные обращения.

#### Р8. Направление связи

Спор: у Zabbix эталон рисует «менеджер → работник» (кто раздаёт задания), хотя соединение открывает
работник.

Предложение. Инициатор это тот, в чьём коде стоит строка обращения. У связи с брокером направление
задаёт вид вызова: публикация идёт к брокеру, подписка от брокера. Смысл «раздаёт задания» остаётся
в подписи. Следствие: связи «менеджер → работник» в эталоне Zabbix разворачиваются.

Альтернатива: не оценивать направление вовсе, сравнивать пары. Я против: направление в простых
случаях проверяется механически и ошибки в нём настоящие.

Следствие для взаимодействия через браузер (решение владельца 2026-11-12). При входе по SAML сервер
отдаёт браузеру перенаправление на провайдера, а ответ провайдера приходит запросом браузера: строки
обращения сервера к провайдеру в коде нет. Такая связь остаётся в эталоне без доказательства и не
оценивается; отдельной формы свидетеля для неё нет. То же для входа по OAuth, пока обращение
сервера к провайдеру не доказано свидетелем.

### А3. Что из условностей уходит в промпт

У5, Р2, Р4, Р5, Р6, Р7 в промпте нет или они сказаны наполовину. После утверждения это кандидаты
фазы 7: они убирают разброс формы между прогонами.

## Часть Б. Формат эталона

Версия после этапов 2а, 2б-1, 2б-2, 2в-1, 2в-2, 2в-3, 2в-4, 2в-4б, 2в-4в, 2в-4г и 2в-5а пробы на Zulip (2026-11-14): формат проверен на
образце из 39 записей, на срезе из 12 связей прежнего эталона и на 208 связях, которые породил обход
от входов программ; правки исполнителя приняты судьёй. Рабочая реализация и образец: каталог эталонов,
`proven/tools/` и `proven/zulip/`.

### Б1. Состав каталога

`~/archmap-etalons-2026-08-19/proven/<репозиторий>/`:

| Файл | Содержимое |
|---|---|
| `header.yaml` | Репозиторий, полный хэш коммита, корни рамки поставки со ссылками, признаки режима поставки (`frame.constants`), список исключений выпуска (`frame.release_excludes`), версия условностей |
| `catalog.yaml` | Каталог репозитория: обёртки публикации, подписки и доступа к кэшу, реестры, файлы настроек, предикаты-обёртки над настройками, планировщики, прозрачные прокси. Каждая обёртка доказана цепочкой до вызова технологии |
| `facts.yaml` | Факты: оцениваемый слой эталона |
| `objects.yaml` | Объекты рамки: контейнеры из перечислителя запусков, хранилища и внешние адресаты. Объект без формы свидетеля записан `unproven` с причиной |
| `walk/edges.yaml` | Связи и каналы, которые породил обход от входов программ. Руками не правится |
| `walk/objects.yaml` | Зеркало объектов, статус которых выводит обход. Запись обязана совпасть с записью `objects.yaml`: у объекта один статус, расхождение статуса или условий это отказ (этап 2в-4). Состав зеркала полный: пропажа записи и лишняя запись это отказ (этап 2в-4б) |
| `walk/reached.yaml` | Строки свидетелей, которых обход достиг, а объекта-цели в записях нет |
| `walk/reach.yaml` | Что достиг обход: исход каждой строки свидетеля (программы, порождённые записи, отказы), пройденные функции, все обрывы. Вход перечислителей |
| `walk/breaks.md` | Обрывы обхода по классам: число мест и примеры |
| `manual.yaml` | Связи, которые обход не породил, хотя форма для них есть: пишутся руками с причиной обрыва |
| `hits/<семья>.yaml` | Попадания перечислителя семьи и вердикт по каждому |
| `c4.yaml` | Схема для чтения и ввоза в ArchMap (как у эталона v2) |
| `notes.md` | Пояснения к суждениям: выбор рамки, спорные формы |

Каталоги технологий (клиенты, вызовы публикации и подписки, исходящие обращения, виды реестров)
лежат в `proven/tools/catalog/`, по файлу на технологию, без номеров строк.

Рамку поставки скрипт считает сам: это замыкание манифестов от корней, названных в шапке. Объект
вне замыкания не может быть записан в поставке, и наоборот.

**Допущений об установке в эталоне нет** (решение владельца 2026-11-12). Если у настройки нет
значения по умолчанию в коде (её обязана задать установка, или оно зависит от машины), эталон его
не додумывает: факт под таким условием записан `conditional` с `default: none`. Когда условие делит
код на две ветки, в эталоне лежат обе, каждая со своим `when`.

Значение по умолчанию скрипт выводит сам: проходом файлов настроек сверху вниз (умолчание вызова
чтения конфигурации, секрет даёт none), по значению переменной манифеста (факты машины дают none).
**Шаблон настроек установщика это умолчания поставки** (решение владельца 2026-11-13). Если
установщик поставки кладёт файл настроек из шаблона, лежащего в репозитории, и код подключает этот
файл в режиме рамки, значения шаблона считаются умолчаниями: это заявление рамки в шапке с
основаниями в строках установщика и файла настроек, как у режима поставки. У Zulip по коду
`LOCAL_UPLOADS_DIR = None`, а шаблон задаёт каталог на диске, поэтому обращения к S3 в свежей
установке не исполняются и записаны `conditional` с умолчанием false. Настройку, которую установщик
после копирования переписывает своим аргументом, задаёт тот, кто его запускает: её умолчание none.
Правки файла установки администратором эталон по-прежнему не додумывает. До этого решения
(этапы 2б-1…2в-2) значения шаблона умолчаниями не считались; правило вводит этап 2в-3.
В шапке это блок `frame.settings_template`: файл шаблона, путь файла настроек установки, имя модуля
и три основания, которые сверяет скрипт (`copy`: установщик копирует шаблон; `link`: установщик
делает файл модулем настроек; `import`: файл настроек подключает модуль, и при константах рамки
подключение исполняется), плюс список `installer_args` (настройка и строки установщика, которые её
переписывают). Полноту списка сверяет скрипт: каждая строка блока установщика, которая пишет в
файл настроек установки, названа, лишних нет. Закомментированная строка шаблона не присваивание.

**Файлы машины, которые кладёт манифест установки, это умолчания поставки** (решение владельца
2026-11-14). Если манифест рамки кладёт на машину файл с содержимым, записанным в самом манифесте
или в шаблоне репозитория, и код читает этот файл, содержимое считается умолчанием по тому же
основанию, что шаблон настроек установщика. Так же считается отсутствие секции файла конфигурации
установки, которую установщик не пишет: код берёт своё умолчание. У Zulip манифест кладёт карту
шардов Tornado `/etc/zulip/sharding.json` с содержимым `{}` (`tornado_sharding.pp:24–31`), а
секции `tornado_sharding` в `zulip.conf` свежей установки нет: процесс Tornado один, порт 9800.
Свидетель называет строку манифеста с содержимым и строку кода, которая файл читает. Файл, который
манифест не перезаписывает (`replace => false`), администратор может изменить: такие правки эталон
по-прежнему не додумывает. Для манифестов и шаблонов правило действует с этапа 2в-5а. Шапка
заявляет файл конфигурации установки и секции, которые пишет установщик
(`frame.install_config: {file, sections, why}`); скрипт сверяет заявление со строками установщика:
каждая строка, которая называет файл, разобрана, лишних секций нет. Раздел
`puppet_config_functions` каталога репозитория называет функцию puppet, которая читает секцию этого
файла, и значение, которое она возвращает без секции (строки определения функции, чтения секции,
факта с путём файла и умолчания сверяются с клоном). Так набор портов Tornado при умолчаниях пуст,
шаблон даёт один upstream и одну программу на порту 9800, и связь nginx с Tornado порождена. Для
кода Python (связь Django с Tornado) правило вводит этап 2в-5б.

**Режим поставки это часть рамки** (решение владельца 2026-11-12). У Zulip один код работает в
боевом режиме и в режиме разработки; режим задаёт не код Python, а строка `deploy_type` в файле
установки, которую всегда пишет установщик поставки (`scripts/lib/install:544`). Раз рамка это
поставка, которую ставит этот установщик (Р1), режим в ней известен: он записан в шапке
(`frame.constants`) со ссылкой на строку установщика и утверждается владельцем вместе с корнями.
Производные от него (`DEVELOPMENT = not PRODUCTION`) скрипт выводит сам, объявлять их нельзя. Код
под режимом разработки в эталон не идёт.

Заявление шапки скрипт сверяет механически: `at` это строка, где признак читается из файла
установки (`has_option` объекта configparser), `basis` это строка установщика, которая пишет эту
опцию в тот же файл и в ту же секцию. Раз опция записана, значение обязано быть true. Признак в
каталоге репозитория отвергается. Сводка проверки печатает заявленные и выведенные признаки.

**Аргументы команды это рамка программы** (этап 2в-1). Один код исполняется разными программами с
разными аргументами: Zulip выбирает таблицу маршрутов по `sys.argv`, а ветку команды по её ключам.
Поэтому настройки, зависящие от `sys.argv`, и значения `options[…]` в `handle` команды скрипт
вычисляет для каждой программы отдельно: из строки `command=` программы-истока после снятия обёрток,
из команды задания расписания. Ключи команды разбираются по `add_arguments` в клоне и по
стандартным ключам библиотеки из каталога. Ветка, которая при аргументах программы не исполняется,
для цепочки закрыта (отказ «ветка»). Значение, которое вывести нельзя, ветку не закрывает. Каждое
задание расписания это отдельная программа со своей рамкой.

**Список исключений выпуска это часть рамки** (этап 2в-2). Сборка выпуска удаляет из архива пути
по списку (у Zulip `tools/release-tarball-exclude.txt`, основание `tools/build-release-tarball:49`).
Список назван в шапке (`frame.release_excludes: {file, basis}`); попадание перечислителя в файле
из списка получает причину `out_of_delivery`.

### Б2. Запись факта

```yaml
- id: c.zulip_events_deferred_work   # c контейнер, s хранилище или брокер, x внешний адресат,
                                     # k компонент, q канал, e связь
  kind: container
  status: proven                     # proven | conditional | unproven
  scope: delivery                    # delivery | background | out_of_delivery
  witness:
    type: launch                     # launch | client | call | literal | registry | query
    at: "<файл>:<строка>"
    literal: zulip_events_deferred_work
    expand: {var: queue, value: deferred_work, at: "<манифест>:<строка>"}
  form:                              # условность, не оценивается
    c4_path: "Zulip / zulip-workers / zulip_events_deferred_work"
    rule: У4
  scanner: candidate                 # found | missed | false | candidate | none
```

Оцениваются записи со `status` proven или conditional и `scope` delivery; conditional идут в отчёте
отдельной строкой. Отдельного статуса для условности нет: компонент, нарезанный моделью, записан
`unproven` с `form.rule: условность`.

Поля свидетеля по типам:

| Тип | Поля | Смысл |
|---|---|---|
| `launch` | `at`, `literal`, необязательные `expand`, `artifact` | `at` это заголовок секции программы; `expand` называет элемент списка, по которому шаблон разворачивает имя; `artifact` это строка манифеста, которая ставит программу, если её кода нет в репозитории |
| `client` | `at`, `tech`, `call`, `address` | Строка создания клиента; `address` это имя настройки с адресом |
| `call` | `at`, `tech`, `call`, `address`, необязательные `literal`, `address_expr` | Строка исходящего обращения. `address` это имя настройки, либо хост литерала URL (тогда `literal: {at, value}` называет строку и сам литерал), либо слово `data` (тогда `address_expr` несёт выражение адреса дословно). Если цель это контейнер поставки, адрес сверяется с портом в его команде запуска. Адрес `unix:<путь>` у обратного прокси сверяется со строкой `socket=` файла uWSGI цели. У внешнего адресата адрес при умолчаниях сверяется с портами и сокетами программ рамки: обращение к программе рамки внешним адресатом записать нельзя |
| `literal` | `at`, `tech`, `literal`, необязательные `via_return`, `assigned_at`, `key_attr`, `loop_at` и `key_at` | Имя канала дословно в вызове публикации или подписки. `via_return` называет функцию, которая возвращает имя (У18): все её `return` начинаются литералом основы. `assigned_at` называет строку присваивания, если в вызове стоит локальная переменная. `key_attr` называет атрибут экземпляра, который реестр ставит классу: значение равно ключу шага реестра в цепочке. `loop_at` и `key_at` называют строку цикла по ключам словаря и строку, где ключ присвоен литералом (этап 2в-4б) |
| `registry` | `at`, `registry`, `literal` | Запись реестра из каталога; `literal` это её ключ |
| `query` | `at`, `tech`, `model` или `call` | Обращение к хранилищу из кода задачи. Для базы это строка запроса менеджера модели: модель принадлежит приложению из списка установленных, база единственная. Для кэша это вызов обёртки доступа из каталога или строка декоратора доступа над функцией, на которой кончается цепочка. Для Redis это метод команды у клиента, созданного строкой свидетеля хранилища |

Клиент базы и кэша это строка настроек (`ENGINE`, `BACKEND`), а свидетель связи это строка запроса:
запросы стоят в коде задачи, цепочка нужна у каждого контейнера.

Условие у записи conditional:

```yaml
condition:
  text: "<когда факт действует>"
  flags: [<ФЛАГ>, ...]             # любой из
  when: true                       # при каком значении флага факт действует
  default: false                   # true | false | none: значения по умолчанию в коде нет
  default_at: "<файл настроек>:<строка>"
  guard: "<файл>:<строка>"          # строка условия на пути
```

Если на пути несколько условий, `condition` это список таких блоков со смыслом «все из». Условия
записи обязаны совпасть с теми, что нашёл скрипт: ни одного пропущенного и ни одного лишнего.
Условие, выполненное по умолчанию, в запись не идёт.

**Место умолчания** `default_at` это действующая строка (этап 2в-4): последнее присваивание
настройки в проходе значений, после шаблона настроек строка шаблона, у настройки, которую пишет
аргумент установщика, строка установщика; после нерешённой развилки годится любая из ветвей.
Строка, которую перекрывает более позднее присваивание, отвергается.

**Операция, а не создание клиента** (этап 2в-4). Каталог технологии различает конструкцию, которая
только строит объект клиента (`creates: true`: `boto3.resource`, `get_connection`, `APNs`,
`OpenAI`), и операции, которые ходят в сеть: раздел `operations: {calls, derive, types}` называет
методы-операции, методы, которые без сети дают производный объект (ведро, объект по имени), и
классы библиотеки для вывода по аннотации. Свидетель связи стоит на строке операции и несёт её имя
(`call`) и строки, где создан получатель (`made_at`: присваивание поля в `__init__`, строка
создания клиента). Объект свидетелем адреса сохраняет строку создания клиента. Метод, который
только строит строку или подписывает ссылку, операцией не считается. Конструктор, который сам
открывает соединение (`smtplib.SMTP` с хостом, IMAP), считается операцией.

**Основание типа получателя** (этап 2в-4в). Если получатель операции в коде не создан, а выведен
по типу библиотеки, свидетель называет основание в поле `typed_at`: строку аннотации параметра или
поля, строку создания объекта класса библиотеки, строку класса клона, который наследует класс
библиотеки. Проверка сама выводит варианты `made_at` и `typed_at` и сверяет запись с ними; запись
без `made_at` и без `typed_at` получает отказ.

**Ленивые операции** (этап 2в-4в). Раздел `operations.lazy` каталога технологии называет атрибуты
с неявной загрузкой (`attrs`: первое чтение шлёт запрос) и методы ленивой выборки (`iter`: запрос
уходит при переборе результата). Свидетель несёт `lazy: attr` и стоит на строке чтения атрибута,
либо `lazy: iter` и стоит на строке цикла, который перебирает выборку прямо или через локальную
переменную (тогда строка её присваивания входит в `made_at`). Чтение атрибута у объекта, тип
которого не выведен, операцией не считается.

**Сырой SQL и соединение драйвером** (этап 2в-5а). Раздел `query.raw` каталога PostgreSQL называет
объект соединения Django по умолчанию (`django.db.connection`, алиас `default`), метод курсора и
методы запроса. Свидетель `query` стоит на строке `C.execute(…)` и несёт `cursor_at`: строку, где
имя `C` связано курсором этого соединения ровно один раз (`with … as C`, строка запроса в теле,
или `C = …` выше строки в блоке, который её охватывает). Курсор-параметр, второе связывание,
`connections[…]` и локальное имя `connection` дают отказ. Раздел `query.driver` называет вызов
драйвера, который открывает соединение сам (`psycopg2.connect`), аргументы хоста и порта, порт по
умолчанию и параметры, которые тоже задают адресат (`dsn`, `hostaddr`, `service`: вызов с ними
отвергается). Свидетель несёт `host_at`: строки, где хост записан в словарь аргументов (словарь
это один пустой литерал модуля, пишут в него только `D["ключ"] = …`). Хост это настройка
`DATABASES[алиас]["HOST"]` (алиас обязан совпасть с адресом хранилища) или литерал локального
адреса; без хоста драйвер идёт на локальный сокет, и хранилище при умолчаниях обязано быть на
машине программы и слушать порт драйвера по умолчанию. Основания в каталоге называют строки
библиотек закреплённых версий.

**Запрос вызовом скрипта** (этап 2в-4в). Раздел `query.scripts` каталога Redis называет методы
клиента, которые возвращают объект скрипта и запроса не шлют (`register_script`); запрос уходит
при вызове объекта скрипта. Свидетель `query` стоит на строке такого вызова и несёт `script_at`:
строку, где скрипт создан у клиента хранилища. Объект скрипта выводится через `return` функции
или метода клона, локальную переменную и атрибут класса.

**Статус внешнего объекта** выводится из связей (этап 2в-4): объект `proven`, если к нему ведёт
хотя бы одна безусловная связь, иначе `conditional` с условиями, общими для его связей.

**Имя канала через переменную** (этап 2в-2). Присваивание `assigned_at` обязано доходить до
вызова: достижение считается по структуре функции (последовательность, ветки `if` со слиянием,
`with`); присваивание в цикле или в `try` вокруг строки форма отвергает. Присвоен литерал или вызов
функции формы `via_return`. В путь связи входят условия строки присваивания и условия веток, при
которых его не перекрывает другое присваивание. У `key_attr` реестр каталога репозитория называет
атрибут и строку, которая его ставит; метод со строкой вызова принадлежит классу, найденному
реестром, или его предку, после шага реестра в цепочке стоят только вызовы `self.<метод>()`, а класс
и его предки атрибут не переприсваивают.

**Имя канала через данные** (этап 2в-4б). Три формы, в каждой имя известно из кода, но стоит не
литералом в строке публикации:

- ключ словаря в цикле: имя это переменная цикла по ключам словаря (`for имя, … in D.items()`),
  словарь это значение вызова функции клона (локальная переменная или поле объекта, каждая запись в
  которое по коду поставки разобрана), функция возвращает одну переменную, заведённую пустым
  словарём, ключи заданы индексом с литералом или с переменной, которой присвоены литералы.
  Свидетель несёт литерал, `loop_at` и `key_at`. Условия пути: строки цикла, записи словаря,
  присваивания ключа и ветки, при которых присваивание доходит до индекса; выбор ключа по данным
  условием не считается;
- публикация методом клиента очереди: конструкция каталога репозитория с полем `receiver_class`
  (метод класса клона, тип получателя выведен, все выведенные типы наследуют класс), имя берётся
  из функции формы `via_return`;
- атрибут воркера: класс может дописать к атрибуту `key_attr` суффикс f-строкой с подстановкой
  (номер шарда): по У18 это тот же канал, литерал равен ключу реестра. Постоянный суффикс, иной
  оператор и простое присваивание по-прежнему отказ. Атрибут читается и у первого параметра
  обёртки декоратора: последний шаг цепочки это шаг в обёртку из вызова `self.<метод>(…)`, а
  украшенный метод принадлежит классу, найденному реестром, или его предку.

Список публикаций канала для формы «вход из канала» выводит имена теми же формами без пути
программы; ошибка допускается только в сторону строгости (атрибут в методе базового класса даёт
ключи всех наследников из реестра).

**Обращение через бэкенд из настройки** (этап 2в-2). Конструкция каталога технологии с полями
`address_setting` и `backend: {setting, values, bases}`: вызов библиотеки создаёт бэкенд по
настройке (у почты `get_connection` по `EMAIL_BACKEND`). Условие пути это «настройка задаёт бэкенд
этой технологии»: скрипт разбирает цепочку `if`, `elif`, `else` файла настроек, в ветках которой
настройке присвоены строки, и собирает ИЛИ по веткам с бэкендом технологии (строка из `values` или
класс клона с предком из `bases`).

**Адрес литералом и адрес из данных** (этап 2в-3). Литерал URL стоит в строке вызова, либо
адрес это параметр функции обращения, и каждый её вызов передаёт литерал с одним хостом; сверка
«адресат не программа рамки» идёт по хосту. Адрес из данных: каждое значение, которое доходит до
адреса, проверяется в своей функции (аргумент каждого вызова, присваивание, элемент перебора, поле
объекта в методе, где оно присвоено); настройка или литерал хоста на любом шаге дают отказ. Граница
прослеживания это вход из канала: первый параметр метода воркера, у которого в каталоге репозитория
записано `input` с основанием (строка, где тело сообщения разбирается из байтов очереди). На входе
из канала правило переходит к публикациям этого канала в коде поставки и проверяет тело сообщения
(или одно поле, если адрес читает одно поле) тем же правилом; свидетель несёт
`channel_input: [{channel, field, published_at, unresolved}]`, где `unresolved` это публикации
без литерала имени канала (этап 2в-4). Значение из поля объекта клона (этап 2в-4б): если тип
получателя выведен и класс объявляет поле, правило находит каждую запись в это поле по коду
поставки (присваивание, наполнение коллекции, аргумент конструктора, умолчание объявления,
наполнение псевдонима) и проверяет каждое записанное выражение в функции записи; упоминание,
которое скрипт не разобрал, даёт отказ; свидетель несёт
`object_field: [{class, field, written_at}]`. Значение, которое правило не прослеживает (результат
функции клона, которая не тождественна), даёт отказ. Функция
клона с одним `return` подставляется в выражение адреса. Сессия HTTP распознаётся и тогда, когда
получатель это поле объекта, присвоенное в `__init__`, или значение функции клона.

Поле объекта, отданное дальше (этап 2в-4в), правило поля считает отказом: аргумент вызова,
`return` и `yield`, элемент литерала коллекции, присваивание не одному имени, псевдоним через
`or`, `and` или тернарный оператор. Исключения это встроенные функции, которые коллекцию не
меняют (`len`, `sorted`, `list`, `set` и подобные), и методы журнала. Конструктор класса поля со
`*args` или `**kwargs` тоже отказ.

**Адрес из поля объекта** (этап 2в-4в). Адрес обращения начинается полем `self` (прямо, f-строкой
или локальной переменной с одним присваиванием), а каждое присваивание этого поля в классе, его
предках, наследниках и их предках несёт значение одной настройки: прямо, через методы строки с
константными аргументами, через локальное имя или `:=`. Объявление поля в теле класса, запись поля
у объекта без выведенного типа и `setattr` с этим именем дают отказ. Свидетель несёт
`address: <настройка>` и `address_field: {field, assigned_at}`; условия строк `assigned_at` входят
в путь.

**Порты для сверки адресатов** (этап 2в-3). Порт программы берётся из распознанной формы ключа её
команды, порт из выражения шаблона вычисляется при умолчаниях или даёт шаблон значений; порты и
сокеты хранилищ рамки берутся из их клиентских конструкций. Внешний адресат не может указывать на
порт программы или хранилища рамки.

У канала есть поле `broker`. У фоновой связи есть поле `containers` с перечнем контейнеров, к
которым она относится.

Статус объекта:

- объект с условием на строке своего свидетеля получает статус от этого условия;
- объект, к которому ведут только условные связи, сам conditional, и его условие совпадает с
  условием одной из этих связей;
- объект, к которому ведут связи обеих веток одной развилки, proven: вместе ветки покрывают все
  значения флага. Правило о существовании объекта: сами связи остаются conditional.

Декоратор доступа к кэшу объявлен в каталоге репозитория двумя стыками: функция, которую он
возвращает, исполняется при вызове украшенной (цепочка вложенных определений, каждое `return` по
имени), и в её теле стоит вызов обёртки доступа. Имя кэша это литерал аргумента декоратора или
значение параметра по умолчанию; если оно приходит переменной, запись `unproven`.

### Б3. Связь и цепочка

```yaml
- id: "e.zulip-django->rabbitmq[deferred_work]"
  kind: edge
  from: c.zulip-django
  to: s.rabbitmq
  channel: q.deferred_work
  direction: publish               # call | publish | subscribe
  status: proven
  scope: delivery
  chain:
  - {step: entry,    at: "<манифест>:<строка>", to: "<файл>:<строка>"}
  - {step: registry, registry: django-urls, at: "<файл>:<строка>", key: "<ключ>", to: "<файл>:<строка>"}
  - {step: call,     at: "<файл>:<строка>", name: "<имя вызываемого>", to: "<файл>:<строка>"}
  witness: {type: literal, tech: rabbitmq, at: "<файл>:<строка>", literal: deferred_work}
```

Правила цепочки:

- первый шаг `entry` стоит на строке команды контейнера-истока (у подписки это получатель);
- условия запуска истока входят в путь связи: связи нет, если нет программы, от которой она идёт;
- стык: `at` следующего шага лежит внутри функции или класса, которые называет `to` предыдущего.
  Строка во вложенной функции не годится: в неё ведёт свой шаг;
- шаг `call` принимается, если тип получателя выведен или определение с таким именем в клоне
  единственное; иначе отказ;
- вызов на несколько строк записывается первой строкой вызова;
- функция, переданная библиотеке, считается вызванной, только если библиотечный вызов объявлен в
  каталоге (`invokers`); запуск потока ведёт в метод `run` его класса;
- шаг `call` с полем `param_of` это вызов параметра: цепочка обязана была войти в функцию вызовом
  на строке `param_of`, а аргументом там стоит лямбда или ссылка на функцию;
- шаг `call` с полем `decorator` это шаг в обёртку декоратора клона (этап 2в-4б): `decorator`
  называет строку декоратора над функцией, которую зовёт строка `at`, `to` стоит на вложенной
  функции, которую декоратор (или фабрика декоратора с аргументами) возвращает по имени каждым
  `return`. У обёртки допустимы только прозрачные декораторы каталога (`functools.wraps`). Вызов
  параметра декоратора внутри обёртки это шаг `call` с `param_of`, равным строке декоратора: он
  ведёт в украшенную функцию, а цепочка обязана была войти в обёртку шагом с этим `decorator`.
  Шаг реестра маршрутов в украшенный обработчик ведёт так же и в обёртку. Условие строки
  декоратора входит в путь. Прямой шаг в украшенную функцию по-прежнему допустим;
- шаг `call` с полем `wrap_at` это шаг в обёртку декоратора, наложенного вызовом на переменную
  (этап 2в-4в): строка `at` зовёт локальную переменную, присваивание в строке `wrap_at` доходит
  до вызова, а его значение это декоратор клона над этой же переменной (прямо, из фабрики или
  под обёрткой библиотеки из `call_wrappers` каталога, как `csrf_protect`). У обёртки допустимы
  только прозрачные декораторы. Вызов параметра декоратора внутри такой обёртки ни к чему не
  привязан: путь в исходную функцию этим шагом не доказывается. Наложение, которое форму не
  проходит, обход пишет обрывом;
- шаг `call` с полем `via` (этап 2в-4в) ведёт из записи маршрута в функцию, которую расширение
  маршрутов отдаёт основе обработчиком (`rest_path` и `rest_dispatch`); `via` это строка
  расширения из каталога репозитория;
- шаг `call` с полями `class_dict` и `ctor` (этап 2в-4в): получатель это экземпляр класса из
  словаря классов уровня модуля. Словарь присвоен один раз безусловно, его значения это классы
  клона, и код поставки в него не пишет; шаг ведёт в метод каждого класса словаря, `class_dict`
  называет строку словаря, `ctor` строку, где класс вызван конструктором; условия строки `ctor`
  входят в путь. Аннотация получателя обязана быть предком каждого класса;
- шаг `call` с полем `class_attr: {attr, assigned_at, passed_at}` (этап 2в-4в): получатель это
  класс в атрибуте экземпляра `self.X`. Значение это каждое присваивание атрибута в классе,
  предках, наследниках и предках наследников; параметр конструктора раскрывается по каждому
  вызову конструктора семьи в коде поставки, аргумент обязан быть литералом класса клона. Запись
  атрибута у объекта без выведенного типа и `setattr` с этим именем дают отказ;
- шаг `call` с полем `class_arg` (этап 2в-4г): строка `at` это вызов библиотеки, который
  принимает класс клона именованным аргументом и зовёт методы его экземпляра. Конструкцию
  объявляет раздел `class_invokers` каталога технологии (вызов, класс библиотеки, имя аргумента,
  методы, признак «результат обязан быть тут же вызван») с основанием в строках исходников
  библиотеки той версии, что закреплена в клоне. Аргумент обязан быть литералом класса клона,
  шаг ведёт в метод этого класса или его предка клона, `class_arg` называет аргумент. Пример:
  `PasswordResetView.as_view(form_class=K)(request)` зовёт `save` формы;
- путь при известных аргументах (этап 2в-4г): если строка вызова шага `call` задаёт параметру
  литерал или не передаёт его при литерале-умолчании, проверка тела функции над таким параметром
  вычисляется (`P`, `not P`, `is None`, сравнение с литералом, связки, в том числе вместе с
  настройкой). Строка следующего шага или свидетеля, которую такая проверка закрывает, для
  цепочки мертва: отказ «аргументы». Значение не берётся, если параметр связывается в теле
  заново, строка вызова передаёт `*args` или `**kwargs`, аргументы шага в строке не видны (шаг
  реестра, вход в обёртку, вызов параметра, метод, который зовёт библиотека), конструктор предка
  вызван через класс (`Base.__init__(self, …)`) или у функции есть декоратор, кроме `staticmethod`,
  `classmethod`, `override` и декораторов раздела `same_args_decorators` каталога технологии: тогда
  параметр остаётся данными. Раздел `same_args_decorators` (этап 2в-5а) называет декоратор
  библиотеки, который зовёт украшенную функцию с теми же аргументами, с основанием в строках
  библиотеки закреплённой версии; декоратор наложен именем или вызовом только с именованными
  аргументами-литералами из списка каталога. У Django это `transaction.atomic`, других декораторов
  в разделе нет: каждый требует основания и решения судьи;
- шаг реестра с полем `expand: {var, value, at}`: ключ это элемент списка, который шаблон
  подставляет в команду целиком (`@queues.join(' ')`); условие элемента списка входит в путь;
- шаг реестра с полем `entry_at` указывает строку регистрации записи (расширения Python-Markdown);
- шаг `include` в конфигурации обратного прокси: включённый файл ставит манифест рамки, следующий
  шаг стоит в нём;
- файлы реестра маршрутов это значение `ROOT_URLCONF` программы, от входа которой идёт цепочка, а
  не объединение всех присваиваний;
- после шага реестра, который ведёт в класс, следующий шаг стоит в методе входа: реестр в каталоге
  называет методы, которые исполняются после поиска (`methods`). У библиотечного контракта это
  список имён (методы HTTP обработчика Tornado, `handleMatch` шаблона Python-Markdown), у реестра
  репозитория каждый метод доказан цепочкой от строки поиска (у воркера: создание экземпляра,
  `setup`, `start`, обработчик события). Годится и метод, до которого от метода входа есть шаги
  `call`. Метод ищется по порядку наследования класса; переопределённый метод предка не годится;
- конструктор класса клона `Cls(…)` это шаг `call` в `__init__` класса или ближайшего предка
  клона, который его определяет; `super().__init__(…)` это шаг в `__init__` предка (этап 2в-3).
  Экземпляр, созданный в той же функции или присвоенный полю в `__init__`, даёт вызову метода
  выведенный тип;
- объект, отданный библиотеке (этап 2в-3): реестр каталога репозитория с `key_source: handoff`
  называет аргумент и модуль библиотеки, которой отдан экземпляр, и методы, которые библиотека
  зовёт (`from: hook` с основанием в коде клона: сигнатура с типами библиотеки или `@override`);
- шаг с полем `impl` (этап 2в-3): метод объекта, реализацию которого выбирает настройка; `impl`
  это строка создания наследника в ветке условия, условие этой строки входит в путь;
- входы программ это данные каталогов (`program_entries`): метод `handle` команды, модуль из
  файла `--ini`, задание планировщика, маршруты обратного прокси, код верхнего уровня файла;
- конец: строка свидетеля лежит внутри функции последнего `to`;
- ключ шага `registry` обычно не стоит в строке поиска, поэтому у реестра в каталоге объявлено
  происхождение ключа: запрос, команда контейнера после подстановки шаблона, обход всех записей,
  литерал;
- связь, цепочка которой идёт через реестр общей инициализации программы, обязана быть
  `scope: background` (Р6); обратное тоже проверяется;
- связь «сервис → прозрачный прокси» (Р7) выводимая: вместо цепочки у неё блок
  `derived: {env: "<шаблон>:<строка окружения>", edges: [<id исходящего обращения>, ...]}`; строка
  окружения стоит в секции запуска истока и указывает на порт прокси. Опоры `edges` это все
  доказанные обращения истока к внешним адресатам через библиотеку, которая берёт прокси из
  окружения: пропущенная или лишняя опора это отказ (этап 2в-4). Связь `proven`, если хотя бы
  одна опора безусловна, иначе `conditional`: в `condition` сначала условия, общие для всех опор
  (и условия запуска истока), затем блок `{text, any_of: [{edge, condition: [...]}, ...]}` со
  смыслом «любое из»;
- связь через обратный прокси доказывается реестром маршрутов прокси (маршрут → адрес → порт в
  команде программы);
- адрес обратного прокси через переменную (этап 2в-5а): `proxy_pass $переменная`, значение которой
  задаёт `set` в том же блоке location (одно присваивание выше строки) или запись `default` блока
  `map`. Файл с `map` обязан быть файлом, который манифест рамки кладёт на машину (файл клона или
  содержимое ресурса `file` без подстановок), и читаться строкой `include` вне блоков в
  конфигурации прокси поставки. Шаг `nginx-upstreams` несёт поле `var`: строку записи `map` и
  строку `include`. Хост из захвата регулярного выражения location или из переменных запроса
  это адрес из данных: отказ, обрыв «обратный прокси через переменную»;
- у выводимой связи планировщика с прокси (этап 2в-5а) строка окружения `derived.env` стоит в
  шаблоне файла задания, который кладёт define реестра планировщика; параметр define берёт своё
  умолчание, только если ни один экземпляр рамки его не передаёт;
- связь от задания расписания (Р4) начинается записью реестра заданий планировщика, а не строкой
  команды контейнера.

### Б4. Что проверяет скрипт

`proven/tools/verify.py <каталог эталона> --repo <клон>`. Код 0 только при отсутствии отказов; пустой
результат любой проверки считается отказом. Полям записи скрипт не верит: имя программы, литерал,
имя вызываемого и адрес он берёт из клона и сравнивает с записью. Ключ `--slice` добавляет срез,
`--objects` добавляет `objects.yaml`. Ключ `--walk` проверяет эталон обхода: объекты всех файлов
без их связей, записи `walk/edges.yaml` и `manual.yaml`. Одна запись в двух файлах допустима, только
если записи совпадают целиком.

| Что | Проверка |
|---|---|
| шапка | Хэш коммита равен HEAD клона, клон чист; корни рамки стоят на строках своих объявлений; признак режима поставки читается из файла, который пишет установщик |
| каталог репозитория | Каждая обёртка и каждый реестр доказаны цепочкой до вызова технологии |
| `launch` | Строка это заголовок программы с именем `literal` (после подстановки `expand`); файл ставит манифест рамки; каждая команда секции разрешается в программу репозитория или в `artifact` |
| `client` | Вызов конструктора из каталога, разрешённый импортом; адрес это настройка, присвоенная в файлах настроек |
| `call` | Исходящий вызов из каталога; адрес выводится из настройки; адрес внешнего адресата при умолчаниях не указывает на порт или сокет программы рамки (`hits/launch.yaml`) |
| `literal` | Вызов публикации или подписки из каталога; аргумент равен строковой константе, либо локальной переменной с доходящим присваиванием литерала, либо атрибуту, который ставит реестр |
| `registry` | Строка это запись реестра каталога с ключом `literal` |
| шаги и цепочка | По правилам Б3 |
| `background` | В цепочке есть шаг общей инициализации; точка входа каждого контейнера перечня проходит её |
| `query` | Строка запроса менеджера модели, вызов обёртки доступа из каталога, декоратор доступа или метод клиента Redis; хранилище выводится из настроек, клиент Redis по строке его создания |
| статус | Скрипт сам находит условия по настройкам на строке свидетеля и на каждом шаге цепочки и сверяет их с записью. `proven` допустим, только если все найденные условия выполнены при значениях по умолчанию из кода |

Какие условия скрипт находит: `if`, `elif`, `else`, `while`, тернарный оператор и логические связки
со знаком; ранний выход выше по функции; `assert` по настройке (ранний выход с тем же разбором;
проверка над данными условия не даёт); предикат-обёртку, объявленную в каталоге репозитория;
локальную переменную, которой одним присваиванием, доходящим до проверки, задана настройка
(`:=` в условии читается как его значение); метод объекта с выведенным типом, тело которого читает
настройки (условие со значением none, этап 2в-4в); проверку над параметром с известным значением
из строки вызова (этап 2в-4г, см. Б3);
переменную модуля, которой ветки одного `if` верхнего уровня по настройке присваивают значения, и
функцию-предикат над ней без параметров; условия шаблона и манифеста вокруг строки, ресурса и
подключения класса. Составное условие «настройка и данные» сводится к
условию по настройке. Одинаковая строка во всех ветках условием не считается. Выражение, которое
скрипт вычислить не может, даёт условие со значением none: запись тогда conditional.

Сторож сторожа `proven/tools/mutate.py` портит записи девятью способами (девятый это статус и
условие) и требует, чтобы отказ получила сама испорченная запись; режим `--forms` портит каждую
новую форму и требует отказа от её собственной проверки. Атаки судьи лежат в `proven/judge/`: этап
2а пойман полностью (18 из 18), этап 2б-1 после переноса режима поставки в шапку тоже (32 из 32),
этап 2б-2 после этапа 2в-1 тоже (30 из 30), этап 2в-1 пойман полностью (12 из 12), этап 2в-2 после
этапа 2в-3 тоже (23 из 23), этап 2в-3 после этапа 2в-4 тоже (38 из 38), этап 2в-4 после этапа
2в-4б тоже (34 из 34), этап 2в-4б пойман полностью (35 из 35), этап 2в-4в тоже (49 из 49), этап 2в-4г тоже (24 из 24), этап 2в-5а тоже (38 из 38). Атака, запись которой стала верной
после нового правила, переводится в контроль (так атака на суффикс шарда этапа 2в-2 стала
контролем на этапе 2в-4б).

**Обход от входов программ** `proven/tools/walk.py <каталог эталона> --repo <клон>` (этап 2в-1)
порождает связи сам: строит граф вызовов вперёд от входов каждой программы рамки теми же правилами
разрешения вызова, что в проверке, и сверяет каждую достигнутую строку с конструкциями каталогов.
Для каждой тройки «исток, цель, канал» выбирается путь с наименьшим набором условий, при равенстве
самый короткий. Каналы порождаются из литералов; фоновые связи (Р6) и выводимые связи (Р7)
строятся так же. Каждая порождённая запись проходит тот же проверяющий скрипт: обходу проверка не
верит. Обход не идёт по ссылке без вызова и не угадывает получателя: такое место считается обрывом
и попадает в `walk/breaks.md` (ссылка без вызова, тип не выведен, динамический вызов, нет формы,
проверка отвергла, вне выпуска). Обход не заходит в файлы из списка исключений выпуска: кода,
которого нет в выпуске, программа исполнить не может. Вывод детерминирован: повторный запуск даёт
те же файлы байт в байт. На Zulip обход занимает около 50 секунд и 796 МБ: 49 программ, 208 связей
и 10 каналов.

Сверки `proven/tools/walkcmp.py`: каждая связь образца и среза с цепочкой обязана быть порождена
обходом с тем же набором условий; каждая связь контейнеров прежнего эталона получает класс
(совпало, либо причина из `v2-reasons.yaml`: обрыв, нет формы, объект не записан, связь через
браузер, имя канала через данные). Условия выводимой связи сравниваются напрямую. На Zulip совпали
150 из 175, сверх прежнего эталона порождено 57: этап 2в-4 убрал пять связей воркеров с S3 и три
связи воркера превью с сайтами, этап 2в-4б добавил шестнадцать связей с каналами, имя которых
выводится через данные, этап 2в-4в добавил связи почтового сервера и Tornado с Redis, пятый сервис
видеозвонков и три связи с Redis, которых при работе нет; этап 2в-4г эти три связи убрал (путь при
известных аргументах), добавил связь API с очередью `soft_reactivation` (метод формы, который
зовёт библиотека) и сопоставил фигуре «сервисы видеозвонков» все пять объектов; этап 2в-5а убрал
две связи воркера мобильных уведомлений, цепочка которых за декоратором не исполнялась, и добавил
связи nginx с Tornado, планировщика с прокси, воркера `user_activity` и программы обновления
поиска с базой (все четыре есть в прежнем эталоне). Сверка сопоставляет фигуре прежнего эталона
каждый объект с её путём. Со срезом после этапа 2в-5а расхождений нет.

Функция клона с параметрами и одним `return` раскрывается своим выражением (этап 2в-3): параметры
считаются данными, поэтому «настройка ИЛИ данные» условия не даёт. Так же раскрывается функция
или метод-предикат с ранними возвратами (этап 2в-4г): тело это цепочка `if <проверка>: return
<True|False>` и последний `return`, значение собирается с конца («вернуть истину» даёт «проверка
ИЛИ остаток», «вернуть ложь» даёт «НЕ проверка И остаток»). Метод раскрывается, если по всем
типам получателя он один и наследники клона его не переопределяют. Условие от функции, которую
скрипт не раскрыл, называет функцию и настройки, которые она читает, и значение функции, при
котором факт действует; полярность настроек такой текст не утверждает, умолчание none.

Известные пробелы после этапа 2в-5а:

- объект «внешние веб-сайты» записан `unproven`: правило поля объекта обрывается там, где
  псевдоним поля результата отрисовки отдан в конструктор запроса на отправку, а дальше в
  обработчике ссылок Markdown (значение связано перебором множества-включения и результатом
  функции клона с обратным вызовом); три верные связи воркера превью не порождены (отдельный этап
  после 2в-5);
- объект «внешние боты» записан `unproven`: обход доходит до строк обращения через класс из
  словаря классов, а адрес приходит из поля модели базы (результат функции клона с запросом к
  модели), такой формы нет. Разбор исполнителя этапа 2в-4г: нужно около девяти форм (тип элемента
  результата функции-запроса, поле модели, записи через словарь полей и `setattr`, граница
  параметров обработчика маршрута), и даже с ними остаётся запись поля из файла импорта
  организации общим кодом `model(**item)` (отдельный этап после 2в-5);
- путь при известных аргументах за декоратором вычисляется только для декораторов раздела
  `same_args_decorators` (у Django это один `transaction.atomic`); под прочими декораторами
  параметр остаётся данными. Аргументы команды программы не учитываются: у связи программы
  обновления поиска с базой свидетель стоит в ветке флага `--nagios-check`, а команда программы
  идёт без аргументов, и при работе соединение открывает другая строка того же файла (связь
  верна, свидетель нет; этап 2в-5б);
- связь, верная статически и невозможная при работе (решение владельца 2026-11-14: такие связи
  остаются в эталоне, их список получает скептик этапа 2г): данные в разных проверках пути выбираются
  независимо, поэтому путь, выполнимый только при несовместимых значениях данных, обход не
  отсекает. На Zulip так порождены связи воркеров `deferred_work` и `outgoing_webhooks` с каналами
  ботов (отправитель сообщения на этих путях всегда бот, а публикация стоит за ранним выходом для
  ботов), и на таких же путях стоят свидетели верных связей cron и Django с этими каналами. У
  связи Tornado с Redis после этапа 2в-4г цепочка идёт через обёртку для вошедших, как запрос идёт
  при работе, но цепочка через обёртку для гостей проверку тоже проходит, хотя маршрут событий
  гостям закрыт флагами маршрута. У связей воркера `deferred_work` с очередью `thumbnail` и с
  сервером KaTeX после этапа 2в-5а цепочка идёт через создание канала под проверкой «адресат это
  канал», а адресат личного сообщения каналом не бывает; сами связи при работе возможны (та же
  функция ниже рендерит текст сообщения), цепочка выбрана по длине, а не по исполнимости. Ветка
  `except` тоже считается данными;
- ветка по данным, недостижимая при умолчаниях (решение владельца 2026-11-14: запись остаётся
  `proven`): публикация Tornado в канал `notify_tornado` стоит
  за сравнением порта пользователя с портом процесса, при одном процессе Tornado она не
  исполняется, а связь записана `proven`;
- прямой шаг в украшенную функцию минует обёртку декоратора: условия тела обёртки в путь такого
  шага не входят (у 26 обёрток поставки Zulip условий по настройкам нет). Обёртки не покрыты, если
  у вложенной функции есть декоратор библиотеки, кроме `functools.wraps` (`csrf_exempt` у
  обработчиков вебхуков и у обёрток входа по ключу API), если декоратор возвращает не вложенную
  функцию по имени и если обёртку украшает другой декоратор клона;
- функция-предикат без параметров с ранними возвратами не раскрывается (такие предикаты
  объявляются в каталоге репозитория); настройка, которую читает не код клона, а библиотека
  (список бэкендов входа через `get_backends`), условием не становится; импорт настроек под
  другим именем внутри функции прячет чтение настройки;
- кандидаты форм «класс из словаря» и «класс в атрибуте» обход отбирает по тексту (присваивание
  имени с заглавной буквы в одну строку): атрибут, который получает класс только через параметр
  конструктора, в форму не попадает. Поля `class_dict` и `ctor` называют одну строку: при
  нескольких словарях или конструкторах форма отказывает;
- условие над параметром, значение которого строка вызова не задаёт литералом, остаётся данными:
  свидетель может стоять в ветке, которую путь связи при работе не исполняет;
- открытые попадания обращений в основном «получатель не выведен» (132 из 183): число открытых
  попаданий мерой полноты пока не является;
- формы «реализация по настройке», «сессия из атрибута или функции», свидетель `object_field` и
  шаг `class_dict` не использует ни одна запись;
- переменная модуля, заданная на уровне модуля и переприсвоенная под `if` по настройке, условием
  не считается (в клоне Zulip таких мест нет);
- условие записи это условие выбранного пути: «ИЛИ» нескольких путей формат не выражает;
- метод библиотеки, имя которого совпадает с единственным определением в клоне, скрипт не отличает;
- реестр маршрутов обратного прокси не проверяет, что файл включён в его конфигурацию;
- признаки Р1 «профиль разработки» и «манифест непрерывной сборки» не реализованы.

Формы, которых нет: адрес из поля модели базы; адрес, вычисленный от номера шарда, в коде Python
(набор портов Tornado для манифестов и шаблонов вычисляется с этапа 2в-5а, для кода Python это
этап 2в-5б); значение из включения и из функции с обратным вызовом; адрес обратного прокси из
захвата пути и из заголовка `X-Accel-Redirect` (хост подписанной ссылки хранилища строит
библиотека); задание расписания файлом, который кладёт манифест (в Zulip таких нет, перечислитель
запусков на таком файле откажет, а не промолчит); клиент LDAP; обращение через внешнюю программу;
сигналы Django. Такие связи записаны `unproven` или не порождены.

Поиск цепочек `proven/tools/chainfind.py <каталог эталона> --repo <клон> --to <файл:строка>
[--from <id контейнера>]` строит обратный граф вызовов от строки свидетеля до входов программ.
После этапа 2в-1 это инструмент разбора одной строки, связи порождает обход.

### Б5. Попадания перечислителя

```yaml
- at: "<файл>:<строка>"
  tech: rabbitmq                 # технология конструкции
  side: publish                  # client | publish | subscribe | call
  call: queue_event_on_commit    # имя вызова
  literal: deferred_work         # имя канала, если оно литерал
  verdict: fact                  # fact | rejected | open
  fact: "e.zulip-django->rabbitmq[deferred_work]"   # запись или список записей, которые породила строка
  reason: null                   # у rejected: test | docs | example | vendored | out_of_delivery | unreachable
                                 # у запусков ещё: launcher | system; у каналов ещё: wrapper;
                                 # у каналов и обращений ещё: clone_name;
                                 # у обращений ещё: receiver_type
  why: null                      # у open: вид причины и пояснение
```

Перечислители семей client, channel и call `proven/tools/hits.py` (этап 2в-2) ищут конструкции
каталогов по тексту всех файлов клона и от графа обхода не зависят. У каналов и обращений
попадание это синтаксический кандидат (этап 2в-3): вызов с именем конструкции каталога в файле,
который несёт её библиотеку (импортирует модуль библиотеки или имя клона, которое к ней ведёт:
класс с предком из библиотеки, функцию, возвращающую её объект, переменную модуля). Кандидат с
нераспознанным получателем получает `open` «получатель не выведен»; кандидат, имя которого ведёт в
функцию клона, получает `rejected` с причиной `clone_name`. Кандидат, у получателя которого выведен
тип, не ведущий в библиотеку конструкции (словарь, список, строка, класс клона без предка из
библиотеки), получает `rejected` с причиной `receiver_type` и пояснением основания в `note`
(этап 2в-4); тип выводится из аннотации параметра или поля, из присваивания литералом или
конструктором, из аннотации возврата функции клона, а догадка без основания оставляет попадание
открытым. Разбор строки общий с обходом
и с проверкой записи (`proofkit/constructs.py`). Вердикт `fact` ставится по исходам обхода
(`walk/reach.yaml`): у каналов и обращений это записи, которые строка породила, у клиента это
хранилище со свидетелем на строке. Отказ `rejected` ставится по пути файла; причина `wrapper` это
строка цепочки обёртки из каталога репозитория. У `open` поле `why` называет вид причины: строка
достигнута, но формы нет; проверка отвергла свидетель; объект-цель не записан; обрыв обхода с
классом; команда управления, которую рамка не запускает; код миграции; функция нигде не вызывается.
Запросы к хранилищам не перечисляются. Сводка по семьям: `hits/summary.md`. На Zulip: клиентов 4
(все `fact`), каналов 78 (`fact` 44, `rejected` 21, `open` 13), обращений 847 (`fact` 28,
`rejected` 636, `open` 183, из них 132 «получатель не выведен»).

Перечислитель запусков `proven/tools/launches.py` (этап 2в-1) находит все программы, которые ставят
манифесты: секции супервизора, задания расписания, службы пакетов, строки заданий файлов `cron.d`
клона (`source: crond`, этап 2в-5а: файл, который не ставит ни один манифест рамки, получает отказ
`out_of_delivery`). Причина `launcher` это служба,
которая сама запускает программы, перечисленные своими секциями; `system` это служба машины, которой
нет в каталогах технологий.

Причина `unreachable` допустима только с записью в `notes.md` и считается в отчёте отдельно: это
суждение, а не механика. Эталон полон, когда вердиктов `open` нет.

### Б6. Связь со слоями эталона v2

Файл `layers.yaml` больше не ведётся. Его сведения переезжают в поле `scanner` записи факта: core
становится found, scanner-miss становится missed, rule-candidate становится candidate, записи
`scanner_false` получают false, слой judgement получает none. Поле нужно фазе 5 (метрика сборщика).
