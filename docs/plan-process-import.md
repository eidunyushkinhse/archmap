# Импорт бизнес-процесса из Mermaid — план эпика

**Статус:** план написан 2026-08-10, ЖДЁТ ОТМАШКИ на реализацию.
**База:** `main` = `140add1`, дерево чистое, всё запушено.
**Начинать:** отдельной веткой `feat/process-import`, слить `--no-ff` (правило CLAUDE.md
для эпиков). Причина именно здесь: меняется модель участника и контракт поверх
принятых фич.

---

## 0. Как мы сюда пришли

Задача лежала в бэклоге с пометкой «сперва анализ, потом код»: у пользователя было
несколько идей, и требовалось проверить, что они не конфликтуют с моделью. 2026-08-10
разобрали и решили.

### Разведка (проверено по коду, не по памяти)

**Развилок две, потому что модель по-разному строга:**

| | Модель | Слот «нет соответствия в C4» |
|---|---|---|
| Участник | `node_id` **NOT NULL** FK на nodes | **нет** — надо заводить |
| Сообщение | `edge_id` nullable, `ON DELETE SET NULL` | **есть** — повисшее сообщение, алерт AL26 |

**Импорт не может быть точным обратным экспорту.** `detailToMermaid` пишет только имя
участника (`participant P1 as Имя`) и подпись шага. Теряются технология, синхронность
и идентичность канала. При этом:
- у узлов **нет** ограничения уникальности имени (проверено: `__table_args__` в
  `models/node.py` — только индекс по `source_ref`);
- между парой узлов может быть **несколько каналов** (уникальности у edges нет,
  `list_channels` возвращает список) — `P1->>P2: запрос` не говорит, какой именно.

Неоднозначность встроена в формат. «Первый подходящий» молча — запрещено.

### Решения пользователя (2026-08-10)

1. **Сценарии.** Поддержать все, основные три: диаграммы от ИИ-агента, возврат своего
   экспорта, перенос процесса между проектами. Легаси-документация — редкий кейс.
2. **Участники.** Сначала ручное сопоставление в превью, НО пользователь не обязан
   найти пару каждой сущности. Несопоставленные остаются **непривязанными**: они
   появляются на схеме процесса как участники без узла проекта, помечены в том же
   стиле, что и стрелки без связи. **Нужен отдельный алерт** «участник процесса без
   узла».
3. **Сообщения.** Импортировать повисшими (`edge_id = null`). Галочку «завести
   недостающие каналы» пока НЕ делаем.
4. **Узлы НЕ создаём** (вариант отклонён на разборе): узел встал бы в корень без формы
   и технологии, а перенести его потом нечем — путь смены вложенности отсутствует
   (см. запись в tasks.md).

## 1. Что из этого следует

Решение №2 — это **изменение модели**, а не деталь импорта. Появляется вторая ось
«незадокументированности», симметричная повисшим сообщениям:

```
сообщение без канала  →  edge_id = null   →  алерт AL26  (есть)
участник без узла     →  node_id = null   →  алерт AL27  (делаем)
```

**Привязка непривязанного участника к узлу ОБЯЗАТЕЛЬНА в этом же эпике.** Алерт без
пути исправления — тупик, на который пользователь уже указывал при приёмке алерта
«Пользователи внутри системы»: «замечание вижу, сделать ничего не могу». Повторять
нельзя.

## 2. Открытый вопрос (решить до Ф1)

**Что делать с участником при удалении УЗЛА?** Сейчас `node_id` несёт
`ondelete="CASCADE"`: удаление узла молча сносит участника и все его сообщения из всех
процессов. Сообщения при удалении СВЯЗИ ведут себя иначе — `SET NULL`, расхождение
остаётся видимым (осознанное решение, см. AL26).

Как только слот «участник без узла» появится, старое поведение станет
непоследовательным: импортированный непривязанный участник живёт, а осиротевший от
удаления узла — исчезает вместе с историей шагов.

**Рекомендация:** перевести на `SET NULL` — процесс переживает удаление узла, а
расхождение попадает в тот же алерт AL27. Это ИЗМЕНЕНИЕ ПРИНЯТОГО ПОВЕДЕНИЯ, поэтому
решает пользователь.

## 4. Фазы

Чекпойнт (коммит + гейт) после каждой.

**Ф1. Модель и миграция.** `node_id` nullable + `name`. Гейт: `upgrade`/`downgrade` на
копии базы.

**Ф2. Контракт и чтение.** `ParticipantOut` с nullable-полями, `participant_out` без
узла, все места, где сейчас `all_nodes[p.node_id]`. Правило: у непривязанного участника
сообщение может быть только повисшим или самосообщением. После правки схем —
`npm run gen:api`.

**Ф3. Рендер.** Линия жизни без узла в «сломанном» стиле, клик не ведёт на объект.

**Ф4. Привязка к узлу.** Пикер на линии жизни непривязанного участника: выбрал узел —
участник привязался. Обязательна (см. §1).

**Ф5. Алерт AL27.** Класс `unbound_participants` + секция панели + переход в процесс.

**Ф6. Импорт.** Парсер (бэк), превью с сопоставлением, применение. Импорт создаёт
**новый** процесс; слияние с существующим — отдельная задача.

## 5. Риски и ловушки

**Подмножество mermaid.** Поддерживаем: `participant ... as ...`, стрелки
`->>`/`-->>`/`-)`, самосообщения, `alt/opt/loop/par` + `else` + `end`. Не поддерживаем:
`autonumber`, `activate/deactivate`, `note`, `box`, ссылки. Непонятые строки обязаны
попасть В ОТЧЁТ, а не молча выпасть.

**Границы фрагментов — ПОЗИЦИИ, а не шаги** (решение пользователя, `03e2f27`). При
импорте фрагменты пересчитываются из строк в order — если хоть один шаг выпадет,
границы разъедутся. Поэтому шаги не выпадают (повисшие), и это не косметика.

**Несколько каналов между парой.** Если подходящих каналов больше одного — выбирать
молча нельзя. Либо в превью выбор, либо импортируем повисшим и говорим об этом в отчёте.
РЕШИТЬ на Ф6 (предпочтение: повисшим + строка отчёта — меньше решений на пользователе).

**`reorder_participants` упадёт на NULL** — там `all_nodes[p.node_id]` без проверки.
Тихая мина: тесты сейчас её не ловят, потому что NULL невозможен.

**Дубли непривязанных.** Два участника с одинаковым именем в одном процессе — на
импорте дедуплицировать по имени. Ограничения в БД нет (NULL-ы не конфликтуют).

**Бизнес-процессы НЕ покрыты реестром docs/specs** (решение 2026-07-16) — документировать
в `spec.md`, инварианты алертов заводить в спеке алертов (AL27 рядом с AL26).
