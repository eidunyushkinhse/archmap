# Запрос второго мнения: правило выбора формы автораскладки

Ты — независимый эксперт-скептик. Claude (основной агент проекта) предлагает
решение; твоя задача — атаковать его: найти дыры в данных, метрике, пороге,
крайних случаях и реализационных рисках. Файл самодостаточен, но код открыт —
читай всё, что нужно (пути указаны). ВАЖНО: у тебя есть право сказать
«согласен, возражений нет» по любому пункту — нужны только РЕАЛЬНЫЕ возражения,
не возражения ради количества.

## Контекст системы (минимум)

ArchMap — веб-сервис многослойных архитектурных C4-схем. Сцена уровня =
локальные узлы + «гости» (внешние концы связей, спроецированные на уровень).
Конвейер раскладки (`frontend/src/components/graph/layout/pipeline.ts`,
исполняется в Web Worker): проекция → раскладка позиций → кольца/разведение
наложений → ортогональный роутер стрелок (A* + rip-up + канальный нуджинг +
сварка стволов + плашки подписей).

Ключевые факты:
- Позиции узлов считает ЕДИНСТВЕННАЯ стадия `layoutLevel`
  (`graph/layout/engine.ts`): сейчас всегда ELK layered, направление RIGHT.
- **own-on-first-render**: позиция каждого узла персистится при первом показе.
  Алгоритм раскладки влияет ТОЛЬКО на первый показ уровня и на явную кнопку
  «Переразложить уровень». Правки графа существующую раскладку не дёргают.
- Профиль производительности (замерен реплеем): 98% времени конвейера — роутер
  стрелок; сам ELK <2%. Значит, форма раскладки влияет на скорость через
  ГЕОМЕТРИЮ рёбер, а не через стоимость алгоритма раскладки.

## Проблема

ELK layered RIGHT на звёздной топологии (хаб + соседи) даёт два слоя, и весь
второй слой встаёт одной вертикальной колонной («сосиска»). На корневых схемах
эталонных проектов аспект (ширина/высота) — 0.39–0.77. Корень C4-проекта —
почти всегда звезда (контекстная диаграмма: система + внешние акторы).

## Предлагаемое решение

В `layoutLevel` (единственная стадия раскладки позиций, для ВСЕХ уровней):

1. Посчитать hub1 на мастер-рёбрах сцены (та же O(E)-свёртка, что в обзоре,
   но на точной отображаемой сцене конвейера).
2. hub1 ≥ HUB_SHARE (= 0.55) → ELK force (фиксированный randomSeed для
   детерминизма, spacing.nodeNode = 80); иначе — layered RIGHT как сейчас.
3. Порог и правило — в спеку узла (N20) с таблицей обзора как обоснованием;
   кэш ELK-результатов уже учитывает опции в сигнатуре.
4. Сироты-подграфы, E < 5 и прочая мелочь — layered (форма на таких сценах
   неразличима, а метрика шумит).

Выбор органики = force — решение пользователя по визуальному сравнению
(альтернативы stress и самописная «звезда» остаются в запасе).

## Отвергнутые альтернативы

- **Исключение для корня** (root → force, остальное → layered): честное
  C4-обоснование (корень = контекстная диаграмма = звезда по построению) и
  проще, но пропускает ВСЕ внутренние звёзды — включая «Консьюмеры Kafka»
  (hub1=1.00), самый болезненный уровень производительности и формы.
- **Одна форма везде**: органика на потоках в 2–4 раза дороже для роутера и
  визуально хуже (данные §2).

## Известные слабости (заявляем честно)

1. Мультихаб-федерация из многих равных систем может разбавить hub1 ниже
   порога (наблюдаемый федеративный корень — 0.70, но он из двух систем).
2. Порог на 32 точках — риск переобучения; зазор может закрыться на других
   проектах.
3. Сцена на границе порога может сменить форму после правок графа при
   явном «Переразложить» (первый показ и обычное редактирование не задеты —
   own-on-first-render).
4. Обзорная метрика считалась на ПРИБЛИЖЁННОЙ проекции сцены (подъём концов
   упрощён относительно боевой проекции конвейера).
5. Гибридные сцены (звезда, внутри которой есть поток) не изучались отдельно.
6. Детерминизм ELK force с фиксированным сидом предполагается, но ещё не
   закреплён тестом.

## Вопросы к скептику

1. Метрика: адекватна ли hub1? Есть ли лучшая дешёвая альтернатива
   (доля топ-2 хабов, дисперсия степеней, соотношение BFS-глубины и ширины)?
   Чем её валидировать?
2. Порог 0.55: как защититься от переобучения на 32 точках?
3. Крайние случаи: мультихаб, изолированные подграфы, гибриды «звезда с
   потоком внутри», сцены на границе порога. Что сломается первым?
4. UX: приемлема ли смена формы уровня по «Переразложить» после правок графа?
   Нужна ли гистерезисная защита порога?
5. Реализация: правильно ли место (layoutLevel), нет ли скрытых зависимостей
   (кэш, детерминизм force, own-on-first-render)?
6. Всё, что мы не увидели.
