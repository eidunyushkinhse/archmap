# План эпика «Якорь как первоклассная сущность» (груминг 2026-09-04, ЖДЁТ «го»)

## Мотив (решение пользователя 2026-09-04)

Якорь (`nodes.source_ref`: репозиторий с путём, образ, k8s-объект или сетевое
имя; сильнейший ключ решает идентичность в мердже, синке, догрузке и федерации)
сегодня — скрытые метаданные: в карточке объекта не показывается, руками не
задаётся и не чистится, ручной узел обречён жить без него и вести себя иначе, чем
агентский с виду такой же узел. Пользователь оценил это как антипаттерн, но
после критической оценки (см. память anchors-concept) выбрал не отказ от
механизма (откат синка «переименование = дубль» и возврат ложных склеек K3), а
ВИДИМОСТЬ и УПРАВЛЯЕМОСТЬ. Ключевое уточнение пользователя: у поля «Якорь» обязан
быть знак вопроса в круге, раскрывающий ПРОСТОЕ пояснение — и механики, и
предпосылок (от чего защищает наличие якоря).

## Текст пояснения (черновик на приёмку пользователя ДО кода)

> **Что такое якорь.** Примета объекта в коде: репозиторий и путь в нём, образ
> контейнера, объект Kubernetes или сетевое имя. Якорь не влияет на схему и
> связи — только на то, как ArchMap узнаёт этот объект при следующих
> обновлениях.
>
> **От чего защищает.** При импорте из кода, слиянии нескольких репозиториев и
> догрузке архивов объекты сопоставляются по якорю, а не по имени. Поэтому
> переименованный или перенесённый в другой контейнер сервис остаётся тем же
> объектом, а не превращается в дубль. И наоборот: два одноимённых объекта с
> разными репозиториями не склеятся по ошибке — ложная склейка хуже дубля,
> потому что выглядит как правильная схема.
>
> **Откуда берётся.** У объектов, созданных агентом по коду, якорь заполняется
> автоматически. Объект без якоря (созданный вручную) опознаётся только по
> имени внутри своего контейнера — задайте якорь здесь, если объект должен
> обновляться из кода.

(≈120 слов; в поповере — три коротких абзаца с подзаголовками.)

## Решения проектирования

1. **Контракт.** `NodeResponse` уже отдаёт `source_ref` строкой; добавить
   структурный `source` (repo, path, image, deployment, host — `SourceRef` из
   identity.py, через `source_ref_dict`) в ответ и `source` в `NodeUpdate`
   (нормализация `identity.normalized` → `canonical_key` → `source_ref`; пустой
   объект — очистка). ⚠️ Изменение контракта санкционировано этим эпиком;
   `npm run gen:api` + api.gen.ts коммитить вместе со схемами.
2. **Карточка объекта (NodePage) и инспектор на карте (NodeInspector).** Поле
   «Якорь» рядом со свойствами: значение читаемым видом («репозиторий
   github.com/x/y, путь src/api», «сетевое имя payments») либо «нет — опознаётся
   по имени»; ⓘ-кнопка (знак вопроса в круге) → поповер с текстом выше;
   архитектору — «Изменить» (форма из полей SourceRef с подсказками, что можно
   вписывать, и запретом выдумывать host) и «Очистить». Наблюдателю — только
   чтение и ⓘ.
3. **Основание склейки словами** в превью импорта, догрузки и синка: у каждой
   склеенной/найденной пары — «по репозиторию», «по сетевому имени», «по имени
   внутри „X“»; у новых — «якоря нет, будет опознаваться по имени». Данные для
   этого в мердже есть (contribs/ступень матча); в отчёты добавить поле, во
   фронт — колонку/пометку.
4. **Устаревшие якоря** — Ф3 по решению: после синка узлы, чей якорь прогон не
   подтвердил, помечать в карточке («якорь не найден последним прогоном») — нужно
   поле `source_seen_at` или флаг в sync_apply. Дёшево, но это новое состояние;
   решить при груминге фазы.
5. **MCP**: карточка объекта печатает якорь; `archmap_update_node` принимает
   `source`; описания инструментов — про основание склейки.
6. **Спеки/доки**: spec.md (раздел якорей и карточки объекта), docs/specs/node.md
   (инвариант «якорь виден и управляем»), README MCP.
