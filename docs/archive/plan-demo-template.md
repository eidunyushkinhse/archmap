# План: демо-шаблон «Маркетплейс "Ярмарка"» (расширенные шаблоны проектов)

Задача из бэклога tasks.md («Backend+Frontend: расширенные шаблоны проектов»,
направление задано груммингом 2026-08-03). Груминг машинерии и содержания —
2026-09-14, решения пользователя того же дня.

## Зачем

Старт из шаблона сегодня — шесть КАРКАСОВ (`templates.py`): узлы, связи и
запечённая раскладка, больше ничего. Пользователь, который создал проект из
шаблона, не видит ни процессов, ни схем логики, ни спек, ни семей фактов —
то есть не видит большей части платформы. Демо-шаблон должен ЗНАКОМИТЬ с
возможностями: многоуровневое C4 + бизнес-процессы + OpenAPI + схемы логики +
три семьи фактов, всё связно и без алертов.

## Что уже есть (сверка с кодом 2026-09-14)

- `seed_template(db, project_id, template_id)` — декларативный сидер: узлы,
  рёбра, строки `view_layout` из `x/y` спеки шаблона. Ни доков, ни процессов,
  ни семей он не умеет и уметь не должен.
- `build_unified_plan(inputs: list[(имя, байты)])` + `apply_unified_plan(db,
  plan, resolutions, name, description, user_id)` — единый импорт, работает
  ПРЯМО В ПРОЦЕССЕ (HTTP не нужен). Принимает архивы и голые YAML вперемешку,
  сеет все семьи родными приёмниками, переписывает привязки шагов процессов.
  Это готовый сидер для «богатого» шаблона — своего писать не надо.
- `build_archive(db, project)` — полный архив знания (zip + манифест),
  детерминированный байт-в-байт. Обратная сторона той же пары.
- Раскладку архив НЕ везёт (решение Р1 эпика архива: «чинить рендерер, а не
  хранить ручную»). Шаблоны её везут. Расхождение снято решением Р3 ниже.
- Превью витрины (`C4Preview`) рисует узлы по `x/y` каталога; превью карточки
  лендинга умеет раскладывать узлы БЕЗ координат тем же ELK, что и холст
  (`schemaPreviewLayout.resolvePointsElk`).

## Решения пользователя (2026-09-14)

- **Р1. Содержание** — «Ярмарка v2» целиком, ПЛЮС один полностью
  задокументированный узел в статусе «выводится» (`deprecated`); место
  выбирает исполнитель по смыслу. Мотив: статусный переход — часть витрины
  возможностей, а `deprecated` в проекте не показан ничем.
- **Р2. Витрина** — пока РЯДОВЫМ седьмым шаблоном, без выделения. На будущее
  (в tasks.md): способ старта «из шаблона» из создания проекта УБРАТЬ вовсе, а
  «Ярмарку» сделать основой онбординга — плитка на главной «Что умеет ArchMap»,
  открывающая проект с онбординг-курсом; курс пользователь продумает отдельно.
  Поэтому Ф2 держим минимальной: всё, что сверх строки в списке, обесценится.
- **Р3. Раскладка** — демо-шаблон НЕ везёт раскладку вовсе: ведёт себя ровно
  как импорт, всё раскладывает движок. Следствие для витрины: превью считает
  координаты тем же ELK (`resolvePointsElk`), то есть показывает ровно то, что
  пользователь увидит на холсте. Контракт `TemplateNodeOut.x/y` становится
  nullable — это правка контракта В РАМКАХ фичи, с перегенерацией `api.gen.ts`.

## Инженерные решения (исполнителя)

- **Пакет шаблона — распакованными файлами** в репозитории
  (`backend/app/templates_data/demo-marketplace/`): manifest.yaml, c4.yaml,
  схемы логики .mmd, YAML семей, спеки, процессы. Не zip-блоб: пакет обязан
  быть читаем в git-diff, иначе обновление шаблона нельзя отревьюить.
- **Сидинг — существующими приёмниками** единого импорта: файлы пакета едут в
  `build_unified_plan` как входы, `apply_unified_plan` создаёт проект. Своего
  сидера у демо-шаблона нет, значит он не может отстать от модели (тот же
  класс болезни, что лечил `copy_plan`).
- **Сторож-фикспойнт** (pytest): сидинг пакета → ожидаемые счётчики по всем
  семьям, ноль замечаний импорта, `compute_alerts == 0`. Пакет протухнет молча
  — тест не даст.
- **Рецепт обновления** — скрипт: экспорт архива живого проекта → распаковка
  поверх пакета → прогон сторожа. Одна команда, чтобы шаблон не расходился с
  эталоном в БД.

## Фазы

- **Ф0. Содержание**: узел «выводится» в живой «Ярмарке v2» (через API, не
  SQL) — описание, роль, технология, якорь, связи, параметры конфигурации,
  схема логики в стиле соседей. Гейт: `compute_alerts == 0`, глаза на карточку.
- **Ф1. Пакет + сидер (бэк)**: пакет в репозитории, ветка `template:` в
  создании проекта через единый импорт, запись каталога (tagline/blurb/techs +
  узлы/связи корневого уровня для превью, без координат), контракт x/y
  nullable, сторож-фикспойнт, скрипт обновления. Гейт: pytest, ruff, mypy.
- **Ф2. Витрина (фронт)**: превью без координат через `resolvePointsElk`,
  строка демо-шаблона в списке, глиф. Гейт: tsc -b, eslint, vitest, глаза.
- **Ф3. Документация**: spec.md (шаблоны), tasks.md (задача + ПОМЕТКА про
  будущий онбординг по Р2), CLAUDE.md/QWEN.md (каталог пакета в структуре),
  журнал фаз здесь.

## Ловушки

- `apply_unified_plan` СОЗДАЁТ проект сам (имя/описание/автор) — ветку
  `template:` в `create_project` надо перестроить так, чтобы пустой Project не
  создавался заранее и не оставался сиротой.
- Тесты бэка гоняются на in-memory SQLite: сидинг пакета обязан проходить там
  же (идёт через ORM — проходит, но проверить в Ф1, а не на приёмке).
- Пакет — часть репозитория: следить за размером и за тем, что в нём нет
  ничего, кроме выдуманного маркетплейса.
- Демо-шаблон и живой проект пользователя — разные сущности: правка живого
  проекта НЕ меняет пакет, пока не прогнан скрипт обновления. Обратное тоже
  верно: пакет — снимок, а не ссылка.
