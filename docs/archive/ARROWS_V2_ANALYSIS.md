# Стрелки V2 — диагноз «шпилек» и план оптимизации (2026-07-08)

Контекст: после эпика вид-центричного движка (R0–R5) поведение стрелок деградировало
визуально — появились «крутые изломы»: стрелка выходит в одну сторону, разворачивается
на 180° и лишь потом уходит к цели. Задача этого дока: (1) диагноз по коду и живым
данным, (2) сводный список требований архитектора, (3) как эту задачу решают другие,
(4) план V2. Предыдущая аналитика — ARROWS_ROUTING_ANALYSIS.md (фазы A0–A15 реализованы).

---

## 1. Диагноз: откуда берутся «шпильки»

Замер по полигонному эталону `scripts/.polygon/baseline-post-R5.json` (24 состояния
HelixMon, детектор — антипараллельные сегменты i и i+2 одной ломаной):
**15 из 38 рёбер (~40%) содержат разворот направления**; в post-R3 было 17 из 35.
То есть проблема не внесена R4/R5 напрямую — она СТАЛА ВИДНЕЕ, и вот почему (§1.7).

Механики, порождающие развороты (в порядке вклада):

### 1.1 Порт без направленной видимости + стаб-патч постфактум (ГЛАВНАЯ)
`routeOrthogonal` (A*) не знает СТОРОНУ хэндла: старт — просто вершина сетки, первый
ход разрешён в любую сторону. Тела своих узлов-концов исключены из препятствий
(иначе конец на границе непроходим), поэтому маршрут может выйти «сквозь своё тело»
или вдоль края. Затем `buildAutoRoutes` накладывает `ensureOutwardStubs`: если первый
сегмент не идёт наружу по нормали ≥20px, вставляется стаб «наружу → поворот →
обратно» (`stubStart`, edgePath.ts:181). Это и есть шпилька: геометрию не выбирал
оптимизатор, её ПРИКЛЕИЛ пост-патч. Второй такой же патч накладывает edges.tsx:281
после переснятия концов на живые хэндлы.

### 1.2 Выбор стороны (A8-проба) отвязан от финального маршрута
Сторона выбирается пробным маршрутом БЕЗ crossCost (routeAll.ts:127-135, осознанное
решение A7.4 ради стабильности хэндлов). Финальный маршрут той же стороны считается
УЖЕ с crossCost (200/пересечение) — и может выкрутиться совсем иначе: объезд ради
двух пересечений оправдывает 400px крюка с разворотом. Проба сказала «эта сторона
хороша», финал по этой стороне — «но только огородами».

### 1.3 Стек пост-хок патчей вместо единого упорядочивания
Поверх A* работают ПЯТЬ разнородных слоёв: рельсы встречных пар (A11, крайние слоты
0.25/0.75) → П-детуры грузных плашек (A12, развороты «наружу-вдоль-обратно» ПО
ПОСТРОЕНИЮ) → разводка хэндлов детур-пар (A12.4) → джоги наложенных плеч (A13,
nudgeOverlaps: 12px-зигзаг посреди длинного плеча — в эталоне виден как «↑21px после
↓579px») → до трёх пере-проходов плашек. Каждый слой локально чинит своё и не видит
соседних; канонического «упорядочить все связи в общем канале и развести равными
зазорами» (ordered nudging) нет — отсюда джоги, изломы и разворачивающиеся стыки.

### 1.4 Fallback margin=0 в тесноте
При запертой сетке роутер повторяет прокладку с клиренсом 0 (orthoRoute.ts:178) —
маршрут прижимается к граням узлов и ведёт вдоль них; визуально «ползёт по стенке» и
провоцирует стаб-патчи (выход вдоль края = «нечистый» для leavesOutward).

### 1.5 Роутер не видит рамок
Раскрытые compound-рамки НЕ препятствия (осознанно отложено в R6). После R5 рамок
стало много (раскрывается любой контейнер), сцены плотные: маршруты режут границы
рамок в произвольных местах, проходят через подписи, «замусоривают» вид. Дети рамок —
препятствия, но их плотная упаковка запирает сетку → margin=0 (§1.4) → теснота.

### 1.6 Жадная последовательная прокладка без пере-прокладки
routeAll кладёт рёбра по одному (длинные первыми); ранние не знают о поздних, нет ни
итерации, ни канальной перестановки. При десятках рёбер поздние вынуждены виться.

### 1.7 Почему «рефакторинг откатил назад» (ощущение)
Ядро роутера рефакторинг НЕ трогал (A7–A15 живы). Но: (а) QW выпилил computeDetours —
ВСЕ гостевые рёбра пошли через глобальный роутер (раньше — узкий коридорный обвод),
покрытие роутера резко выросло, его болячки размножились на самые массовые стрелки;
(б) R5 дал раскрытие любых контейнеров → плотные сцены с рамками, к которым роутер
слеп (§1.5); (в) R3 персистит хэндлы ЖЕСТА создания связи строкой пучка → такие рёбра
навсегда `lockedIds`, сторона зафиксирована на момент создания и не пересматривается
при сдвигах узлов (сейчас в БД 1 такой пучок — фактор пока не массовый, но растёт с
каждым жестом).

## 2. Сводный список требований архитектора (актуализирован 2026-07-08)

Источники: tasks.md (эпик A0), ARROWS_ROUTING_ANALYSIS.md §0, память сессий A9–A15,
формулировки пользователя 2026-07-08. Приоритет сверху вниз.

- **Т0 (НОВОЕ, ГЛАВНОЕ).** Читаемость при любом числе стрелок: схема не превращается
  в «морской узел»/паутину. Конкретно: никаких разворотов на 180° и шпилек; маршрут
  выглядит осмысленно (вышел — пошёл к цели); допустимые развороты — только явные
  обходы препятствий с видимой причиной.
- **Т1 (hard).** Плашки подписей не наползают друг на друга и не лежат под узлами (R2).
- **Т2.** Минимум пересечений стрелок между собой (R3).
- **Т3.** Плашка стоит только на однозначно-своём участке: не на слитом плече (R4),
  не на коллинеарном с чужим участке; якорь выноски — тоже (правило A14).
- **Т4.** Наложение плеч разных стрелок допустимо ТОЛЬКО из одного хэндла (правило
  A13); из разных — плечи разводятся. Слитый ствол родственных стрелок из одного
  хэндла — легитимен и желателен (R4-4a).
- **Т5.** Кратчайший путь — целевая функция среди допустимых (R1): минимизируем
  длину+изломы, когда Т0–Т4 выполнены.
- **Т6.** Выноска-leader — последнее средство; предпочитать инлайн, ради этого можно
  двигать маршрут (A12) и узлы (A10, санкция на раздвижку дана).
- **Т7.** Детерминизм: тот же вход → тот же результат; батч-результат показываем
  целиком, не промежуточные стадии.
- **Т8.** Производительность: пересчёт на каждой раскладке (async), десятки рёбер.
- **ПОНИЖЕНО пользователем 2026-07-08:** запоминание хэндлов (персист выбранной
  стороны/слота) — МОЖНО НЕ СОХРАНЯТЬ. Прочими требованиями стабильности («правка
  одного ребра не смещает чужие», A7.4/A12.5) можно жертвовать осмысленно, если это
  покупает Т0. Ручные waypoints пока уважаем (дроп — отдельным решением).

## 3. Как это решают другие

### 3.1 Канон: libavoid / Wybrow–Marriott–Stuckey (GD'09, Diagrams'14)
Трёхстадийный конвейер, де-факто стандарт (Inkscape, dunnart, ELK-обвязка):
1. **Ортогональный граф видимости с НАПРАВЛЕННЫМИ портами.** Точка стыковки имеет
   ConnDirFlags — какие направления ей «видны». Маршрут физически не может выйти из
   порта назад или вдоль тела: таких рёбер в графе нет. Наша боль §1.1 у них
   исключена ПО ПОСТРОЕНИЮ, стаб-патчи не нужны.
2. **A\*** по этому графу, стоимость = длина + штраф за изломы (доказуемо
   оптимальный маршрут на графе видимости). У нас это уже есть (и неплохо).
3. **Центрирование + упорядоченный nudging.** Все сегменты собираются в «каналы»
   (общие горизонтальные/вертикальные коридоры); связи внутри канала УПОРЯДОЧИВАЮТСЯ
   целиком (минимизируя пересечения на входах/выходах канала), затем разводятся
   равными минимальными зазорами; свободные сегменты центрируются в «аллеях» между
   узлами. Это одно системное действие вместо нашего стека рельсы+джоги+детуры.

### 3.2 yFiles EdgeRouter (коммерческий эталон)
- **PortCandidates с ценами**: выбор стороны/точки стыковки — ЧАСТЬ поиска маршрута
  (несколько стартовых/целевых состояний в одном A*), а не отдельная проба. Наша
  расстыковка «проба без штрафов → финал со штрафами» (§1.2) у них невозможна.
- Штрафы (crossing/bend/node-proximity) — настраиваемая единая стоимость.
- **Bus-style/hyperedge routing**: пучки рёбер одного узла сводятся в ствол с
  ветками — главный приём против «паутины» у хабов (наш ObsCore).
- Групповые узлы (рамки) — препятствия с точками входа; маршрут пересекает границу
  группы упорядоченно, а не где попало.

### 3.3 Академическая рамка
Минимизация пересечений и размещение подписей NP-трудны в общем виде — все
промышленные решения = А*-оптимум пер-ребро + жадный порядок + канальная
перестановка. Наш sequential-with-crossing-penalty — законный подход; не хватает
именно стадий «направленные порты» и «канальное упорядочивание».

Выводы-дельты для нас: (Δ1) направленная видимость портов вместо стаб-патчей;
(Δ2) сторона — внутрь A* (multi-source/multi-target), а не пробой; (Δ3) ordered
nudging каналов вместо рельс+джогов; (Δ4) рамки — препятствия с воротами;
(Δ5) стволы из одного хэндла — узаконенное «слияние» (у нас уже так, сохранить).

## 4. План V2 (свой код, libavoid-js остаётся планом Б)

Кирпичи сохраняются: Hanan-сетка, A* с кучей, crossingCount, coincidentLegs,
labelIntervals/placeLabels, VPSC. Меняется архитектура вокруг них.

- **V2.1 Направленные порты.** A*-состояние старта получает фиксированное первое
  направление (наружная нормаль стороны), стартовая вершина отодвинута на стаб
  (20px) от тела; тело СВОЕГО узла — препятствие для всех прочих направлений выхода.
  Симметрично вход в цель (последний ход — против нормали цели). `ensureOutwardStubs`
  в авто-ветке (autoRoutes.ts:145, edges.tsx:281) умирает — стаб входит в маршрут по
  построению. Инвариант нового полигонного счётчика: **0 разворотов** у авто-рёбер
  (детектор шпилек перенести в scripts/, гонять как метрику).
- **V2.2 Сторона — внутрь поиска.** Один A* на ребро со ВСЕМИ разрешёнными сторонами
  как стартовыми/целевыми состояниями (multi-source/multi-target, цена входа
  одинаковая) — с учётом реального moveCost. Выбранная сторона читается из найденного
  пути. A8-проба и расстыковка §1.2 умирают. Персист хэндлов жеста
  (TreePage.persistGestureHandles) — ВЫПИЛИТЬ (санкция 2026-07-08); lockedIds
  остаётся только для явного ручного реконнекта, и его судьбу решить отдельно.
- **V2.3 Канальный nudging (замена A11+A13).** После прокладки: собрать коллинеарные
  сегменты в каналы → упорядочить связи канала (эвристика GD'09: порядок по
  концам-выходам, минимизация локальных пересечений) → развести равными зазорами
  (VPSC уже есть) → отцентрировать свободные сегменты в аллеях. Рёбра из ОДНОГО
  хэндла держим слитым стволом до точки ветвления (Т4). Рельсы встречных пар и джоги
  nudgeOverlaps становятся частными случаями канального порядка — модули удалить.
- **V2.4 Рамки-препятствия с воротами.** Band рамки (граница+подпись) — препятствие;
  проход внутрь только через «ворота» (интервалы границы, свободные от подписи), с
  малым штрафом за пересечение границы. Убирает «резание» рамок где попало (§1.5) и
  уменьшает тесноту margin=0.
- **V2.5 Плашки — один проход.** После финальной геометрии (V2.3) один
  buildLabelPlacements; A12-детур остаётся последним средством перед leader, но
  проверить его нужность заново — канальный порядок освобождает место инлайн.
- **V2.6 Полигон и метрики.** В dump-levels.mjs добавить пер-уровневые метрики:
  развороты (шпильки), пересечения, изломы/ребро, доля leader-плашек. Снять «до»,
  вести по фазам. Валидация только на живых сценах HelixMon (урок A9.0).

Порядок: V2.1 → V2.2 — самостоятельная ценность (Т0 в основном закрывается уже ими);
V2.3 — ядро «не-паутины»; V2.4–V2.5 — качество; V2.6 — с самого начала.

Риски: (1) канальное упорядочивание — самый сложный новый код (~2 модуля с тестами);
(2) отказ от пробы A8 меняет стороны многих рёбер разом — разовый визуальный сдвиг
схем (санкционировать перед мержем); (3) производительность multi-source A* —
нейтральна (одна прокладка вместо 2–4 проб + финала).
