# Аудит движка C4-схем: от задумки к архитектуре

Дата: 2026-07-07. Статус: аналитика ПЕРЕД решениями — код не менялся.
Фокус (по запросу архитектора): поведение узлов и стрелок на C4-схемах фронтенда.
Точка отсчёта — не текущий код, а главная задача продукта.

---

## 0. Резюме

**Задача продукта:** рендерить многослойные схемы по логике C4 с неограниченной
глубиной и возможностью раскрытия любых элементов.

**Главный вывод.** Кодовая база выросла вокруг понятия «уровень» (страница одного
контейнера), а задумка требует понятия «вид» (произвольный срез дерева с раскрытыми
элементами). Гости — не костыль сами по себе, а симптом: это узлы, которые не влезли
в модель «уровня», и для них пришлось выстроить параллельную физику (кольца, keep-out,
разведение, жёсткие группы, полки детей, якоря изломов, три отдельные таблицы
раскладки). Каждый следующий слой этой физики дороже предыдущего — это видно по
хронологии фиксов (Ф3→Ф4.3→Ф4.4→D8→фикс B→A9–A15).

**Три первичные концепции задумки, которых нет в коде как объектов** (всё остальное —
следствия):

1. **Проекция** — «конец связи поднимается к ближайшему видимому представителю».
   Сердцевинная операция продукта; реализована ≥5 раз в разных местах по-разному,
   нигде не названа.
2. **Контейнер с геометрией** — раскрытая рамка как реальный объект холста.
   Сейчас рамки — производные bbox-оверлеи от позиций узлов; отсюда почти вся
   «гостевая физика».
3. **Единое хранилище раскладки** — «(вид, объект) → геометрия». Сейчас раскладка
   размазана по 5 хранилищам с асимметричными ключами, 8 пишущими эндпоинтами,
   fan-out'ом мастер-стрелок и 6 зеркалами в стейте TreePage.

**Что устроено правильно и сохраняется:** own-on-first-render, собственный
TS-роутер и размещение плашек (A0–A15), кольцевая модель гостей как концепция,
«чтение не пишет в БД», ELK только для позиций, пер-уровневая геометрия связей
как принцип.

**Предложение:** план R0–R6 (раздел 6) — от чистого конвейера раскладки через
единую проекцию и единое хранилище к контейнерам-объектам и финальной фиче задумки:
раскрытию/сворачиванию ЛЮБОГО контейнера (локального тоже). Развилки для решений
архитектора — раздел 7.

## 1. Задумка как модель

Если формализовать главную задачу, получается четыре понятия:

- **Дерево + связи** (семантика): узлы с parent_id произвольной глубины; связи между
  любыми узлами. Это уже так, менять нечего.
- **Вид (view):** `{корень, множество раскрытых узлов, политика показа}`.
  Видимый узел — тот, чья цепочка предков до корня вида раскрыта, плюс представители
  внешних концов связей.
- **Проекция:** конец связи, чей узел не видим, поднимается к ближайшему видимому
  предку-представителю; связи, слившиеся после подъёма, группируются в пучок.
- **Владение раскладкой:** позиции задаёт архитектор; авто-раскладка — только при
  первом показе (own-on-first-render — уже принятое и правильное решение).

Проверка модели: **все существующие фичи — её частные случаи.**

| Фича | Вид | Проекция |
|---|---|---|
| Схема уровня | корень = контейнер, раскрыт только он | концы → дети контейнера / представители гостей |
| Гость | представитель внешнего конца | лист → верхний нераскрытый контейнер-предок |
| Раскрытие гостя лупой | +id в множество раскрытых | представитель опускается глубже |
| Контекст-схема листа | фокус + соседи, политика «только связанные» | внутренние концы → фокус |
| Превью проекта | корень = null, ничего не раскрыто | концы → корневые предки |
| Бизнес-процессы | «вид» = набор участников | концы → ближайший предок-участник (spec) |
| Экспорт поддерева | корень = узел, раскрыто всё | дизамбигуация «Предок / Имя» |
| Алерты | вся схема без свёртки | без проекции (сырые концы) |

Одна модель — восемь фич. В коде же каждая фича несёт свой кусок модели.

## 2. Как это устроено сейчас (карта фактов)

### 2.1 Проекция разрезана надвое и размножена

- Бэкенд `_build_graph.find_effective` (nodes.py:71–87) поднимает **локальный** конец
  до ближайшего предка-узла уровня; **гостевой** конец оставляет сырым (identity листа).
- Фронтенд `projectGhosts` (projectGhosts.ts) сворачивает гостя к верхнему
  нераскрытому контейнеру-предку — вторая половина того же алгоритма, на другом языке.
- `get_node_context` (nodes.py:658–716) — вторая серверная реализация (membership в
  поддереве вместо подъёма), с ручной пересборкой тех же DTO и расходящимся контрактом
  (не отдаёт waypoints и позиции).
- `projects._previews.root_of` (projects.py:86–101) — третья (подъём до корня).
- `get_alerts` (nodes.py:392–429) работает по сырым концам, без проекции.
- Процессы (spec) — проекция концов на ближайшего предка-участника, enforcement на
  POST /messages.

### 2.2 Рамки — производный оверлей, а не объекты

`computeFrames` (frames.ts) вычисляет прямоугольники рамок как bbox позиций
узлов-членов; рисуются оверлеем (boundaries.tsx через ViewportPortal). На холсте
рамка не существует: у неё нет позиции, размера, детей — только эмерджентный bbox.

Инвариант «гость не внутри чужой родной рамки» поэтому держится **тремя проходами**:
`placeGhostsOnRings` (по построению, изнутри наружу, т.к. размещение гостей раздувает
рамки и меняет кольца) + `separateGuests` (VPSC-разведение новичков от вложенного
раскрытия) + `enforceFramesKeepOut` (страховочная сетка для ручных позиций).
Раскрытая гостевая рамка двигается «жёсткой группой» — спец-кодом, потому что дети
и рамка ничем не связаны, кроме одновременного пересчёта.

### 2.3 Хранилище раскладки: 5 мест, 8 писателей, 6 зеркал

| Хранилище | Что | Ключ |
|---|---|---|
| `nodes.pos_x/pos_y` | позиция локала | id узла |
| `edges.source_handle/target_handle` | хэндл локального конца | id ребра |
| `edges.waypoints` | изломы локальной стрелки | id ребра |
| `edges.label_t` | доля плашки (одна на все уровни) | id ребра |
| `ghost_positions` | позиция гостя | (container, **node отображаемой сущности**) |
| `ghost_edge_handles` | хэндл гостевого конца | (container, edge, node) — node в **теле** запроса |
| `edge_waypoints` | изломы гостевой стрелки | (container, edge), якорь — **полем** anchor_node_id |

Асимметрии ключей (node_id то в пути URL, то в теле, то данными), два слоя хранения
одного и того же понятия «геометрия ребра на виде» (колонка vs таблица), fan-out
мастер-стрелок (правка пишется во ВСЕ memberIds, чтение — «первый член с геометрией»),
`label_t` глобален при пер-уровневых хэндлах. На фронте всему этому соответствуют
6 useState-зеркал в TreePage + 5 колбэков-зеркал (`onNodeMoved`, `onEdgeHandlesChanged`,
`onEdgeWaypointsChanged`, `onLevelEdgeWaypointsChanged`, `onEdgeLabelTChanged`),
каждый со своим знанием о двухслойном сплите.

### 2.4 Конвейер раскладки: ~13 стадий, 3 пересчёта плашек, записи в БД изнутри

Async-эффект LevelGraph (строки ~635–1126, ~490 строк в одном эффекте):
projectGhosts → ремап рёбер + резолв хэндлов по префиксу → слияние в мастер-группы →
ELK + savedPos + assignEdgeHandles → кольца (мутируют positions) → separateGuests →
enforceFramesKeepOut → **персист засева владения** → реконструкция изломов +
**персист миграций якорей** → A10-раздвижка под плашки (мутирует positions) →
routeAll (+рельсы A11 + выбор сторон A8) → плашки → A12-детуры со стеком координации
и слотами встречных пар → пере-плашки → A13-nudge → пере-плашки → распорки для fitView.

Стадии связаны хрупкими порядковыми инвариантами, задокументированными в комментариях
(«ВАЖНО — ДО enforce», «на финальных позициях», «оба рендера совпадают»). Раскладка
**пишет в БД как сайд-эффект рендера** (migrateGhostPositions / migrateLevelWaypoints)
и полагается на сходимость «пересчёт → персист → зеркало → пересчёт → no-op».
Композиция стадий не покрыта тестами (тестируются отдельные модули); проверка —
ручные headless-дампы.

Мёртвый груз: `ROUTE_GUESTS_GLOBALLY = true` (LevelGraph.tsx:814) делает
`computeDetours` недостижимым; с ним мертвы ветка рендера `data.detour`, распорки
`__detour_*` и часть проверок `edgeDetours` по конвейеру.

### 2.5 God Components — снова

- **LevelGraph.tsx: 1707 → 553 (рефакторинг 2026-06-08) → 1662 (сейчас).**
  Рост съел весь эффект рефакторинга за месяц. 115 из 372 коммитов проекта (31%)
  трогают этот файл. 33 пропса, 45 ветвлений `isContext`.
- **TreePage.tsx: 1247 строк, 27 useState** (7 — зеркала сервера), 23 точки вызова
  `load()`, знание о двухслойном сплите хэндлов/изломов, о видах сущностей
  (block/ghost/container), о формате хэндла `${nodeId}--...`.
- **nodes.py: 885 строк, 21 эндпоинт** — граф, контекст, алерты, restore, relayout
  и три PUT пер-уровневой раскладки в одном роутере; has_children считается двумя
  разными механизмами (Counter в памяти для гостей, отдельный SQL для локалов).

### 2.6 Контекст-схема — параллельный мини-продукт

Один компонент LevelGraph обслуживает два режима через 45 ветвлений; при этом
у контекста 14 уникальных концепций (звезда, полки, петли, кольца обходов,
слот-раскладка, clearance…) и продублированная математика рамок
(bcIndex/lcaIdx/паддинги: frames.ts:53–111 ↔ context.ts:43–159). Своя серверная
проекция. Хэндлы назначаются третьим способом (hid напрямую).

### 2.7 Асимметрия раскрытия (главный разрыв с задумкой)

- Инлайн-раскрытие есть ТОЛЬКО у гостевых контейнеров (лупа). Локальный контейнер
  раскрыть на месте нельзя — только «Войти» (смена уровня).
- Раскрытый гость показывает только СВЯЗАННЫХ потомков (проекции концов);
  drill-down показывает ВСЕХ детей. Две разные политики без явного выбора.
- Состояние раскрытия эфемерно: `Set` в LevelGraph, сбрасывается при каждой смене
  уровня (LevelGraph.tsx:300–304). Пользователь теряет раскрытие при любой навигации.

### 2.8 Дефекты, найденные по пути

1. **Кросс-уровневый Undo удаления сломан:** команды «Удаление объекта» и «Удаление
   объектов (N)» (TreePage.tsx:471, 494) не проставляют `level` (остальные 5 типов —
   проставляют). dispatchUndo не средиректит, а `refetch` загрузит данные УРОВНЯ
   УДАЛЕНИЯ в холст текущего уровня (расхождение холста и breadcrumb). Комментарий
   TreePage.tsx:463–464 («история чистится при навигации») описывает отменённое
   поведение.
2. Контракт контекста расходится с level: `GraphEdgeResponse` в контексте без
   waypoints — одна и та же связь на двух схемах имеет разную геометрию.
3. Снимок связи создаёт `edgesApi.deletionSnapshot`, а восстанавливает
   `nodesApi.restore` — кросс-модульная связка.
4. Комменты-анахронизмы «dagre» в 4 местах (движок давно ELK), «anchor_rel» в доках
   (в коде только anchor_node_id).
5. Пер-уровневые чтения тянут все строки контейнера и фильтруют в Python (over-fetch,
   не критично).

## 3. Диагноз: симптом → первопричина

| Симптом (реальные баги/спец-код из истории) | Первопричина |
|---|---|
| «Гость садится поверх соседей» (Ф4.3), «рамка убегает», жёсткая группа, keep-out тремя проходами | Рамка — не объект (нет контейнера с геометрией) |
| Изломы гостевых стрелок: anchor_rel → anchor_node_id (Ф3) → фикс B (d9a2894) — три подхода к «излом едет с концом» | Нет локальной системы координат контейнера, в которой излом хранился бы просто относительными точками |
| Полки детей раскрытой рамки, перелив в колонки, «коробка следует за кольцевым слотом» (3c6f352) | То же: дети и рамка не связаны структурно |
| Fan-out правок мастер-стрелки по memberIds, «читаем первого с геометрией» | Геометрия хранится на членах, а не на пучке (нет ключа пучка) |
| 6 зеркал уровня в TreePage + 5 колбэков-зеркал + resync-on-error | 5 хранилищ раскладки → 5 протоколов синхронизации |
| Хэндл гостя резолвится префиксом `startsWith(nodeId + "--")` в 3 местах | Проекция «какой узел сейчас показан» не является объектом — кодируется строкой хэндла |
| Дёрганья «двух рендеров» при раскрытии, порядок стадий «ДО enforce» | Раскладка с побочными записями в БД и сходимостью вместо чистой функции |
| A10/A11/A12/A12.4/A12.5/A13/A14/A15 — каждая правка тяжелее | Роутер и плашки компенсируют не только геометрию, но и последствия гостевой физики; часть входов (кольца/рамки) роутеру не видна |
| Раскрытие теряется при навигации; локальный контейнер не раскрыть | Раскрытие — эфемерный UI-стейт холста, а не свойство вида |

## 4. Что сделано правильно (сохранить, не пересматривать)

1. **Own-on-first-render** — владение позициями с авто-раскладкой только при первом
   показе. Подтверждено болью живых якорей; целевая модель его СОХРАНЯЕТ
   (относительные координаты детей в контейнере — структурная связь, не поведенческая:
   это то, что «жёсткая группа» и так делает вручную).
2. **Свой TS-роутер + плашки (A0–A15)** — соответствует принятой аналитике
   (ARROWS_ROUTING_ANALYSIS.md), чистые модули под тестами, libavoid не нужен.
3. **Кольца (boundary labeling) как концепция** размещения гостей — верная; в целевой
   модели она остаётся, но считается против реальных прямоугольников контейнеров,
   а не эмерджентных bbox (исчезает каскад «изнутри наружу»).
4. **Бэкенд не пишет при чтении** (инвариант F6а) — сохранить.
5. **ELK только для позиций**, контекст-звезда — bespoke: обе ставки подтверждены.
6. **Пер-view геометрия связей** («та же связь на разных уровнях — разная геометрия»)
   — правильный принцип; неправильна только фрагментация хранения.

## 5. Целевая модель

### 5.1 Проекция как модуль

```
ViewSpec = { rootId: id|null, expanded: Set<id>, policy: { children: "all"|"connected", focus?: id } }

projectView(tree, edges, spec) → VisibleGraph {
  entities: [{ id, kind: local|representative, containerChain, source }],
  bundles:  [{ key: "src->tgt", source, target, members: Edge[] }],   // мастер = пучок
}
```

Один чистый модуль на фронте (замещает projectGhosts + ремап + слияние мастеров +
серверный find_effective); один маленький хелпер `lift(endId, visibleSet)` на бэке
для превью/процессов/алертов. Уровень, раскрытие гостя, раскрытие ЛОКАЛЬНОГО
контейнера, контекст — параметры spec, не отдельные механизмы.

Бэкенд-граф при этом упрощается: отдаёт сырьё (узлы уровня/поддерева, связи,
затрагивающие поддерево, с РЕАЛЬНЫМИ концами + цепочки предков внешних концов),
проекцию не делает. Ключевой аргумент за фронт: при раскрытии локального контейнера
подъём локальных концов становится зависимым от expanded — на сервере это потребовало
бы рефетч на каждый клик лупы.

### 5.2 Контейнер как объект холста

Раскрытая сущность (родная рамка, раскрытый гость, позже — раскрытый локальный
контейнер) — реальный узел React Flow (`parentId` + `extent`), размер = bbox детей +
паддинг + полоса подписи. Дети — в относительных координатах родителя.

Что исчезает: enforceFramesKeepOut (де-оверлап соседних прямоугольников одного уровня
вложенности решает это по построению), «жёсткая группа» (нативный drag родителя),
anchor_node_id у изломов (излом внутри контейнера хранится в координатах контейнера),
каскад колец «изнутри наружу» (рамка — реальный rect, не растёт от размещения гостей),
спец-полки детей (внутренняя раскладка контейнера — обычная под-раскладка: полка или
мини-ELK). Роутер получает рамки как препятствия/коридоры (сейчас он их не видит).

### 5.3 Единое хранилище раскладки

```
view_layout(project_id, view_id, item_id, payload JSONB)
  view_id: container_id вида (null = корень)
  item_id: node id | edge id | bundle key | "view"
  payload: {x,y} | {handles, waypoints, label_t?} | {expanded:[...]}
```

Один батч-PUT `/views/{id}/layout`. Мигрируются ghost_positions, ghost_edge_handles,
edge_waypoints, edges.waypoints/handles, nodes.pos_x/pos_y (развилка Д4). На фронте —
ОДНО зеркало (Map) вместо шести, один тип undo-команды «патч раскладки вида»
(items_before → items_after), конец fan-out'а мастеров (геометрия на ключе пучка —
новый член пучка наследует её автоматически).

### 5.4 Раскрытие любых элементов (собственно задумка)

`expanded` расширяется на локальные контейнеры; лупа — у любого контейнера; политика
детей по Д3; персист expanded в view_layout (item "view"). Раскрытие перестаёт
теряться при навигации. Анимация перемещений при перераскладке (идея из бэклога)
становится дешёвой: конвейер чист → интерполяция между двумя LayoutResult.

## 6. План рефакторинга

Каждая фаза — отдельные коммиты с зелёным гейтом; после рендер-меняющих — чекпойнт
с ручной проверкой (как Ф4/A7). Формат заданий исполнителю — как обычно.

- **R0. Полигон (S).** Ground-truth дампы реальных уровней (харнесс есть:
  headless-route-dump) + метрики arrowMetrics «до». Это гейт всех фаз: «дамп не
  изменился / изменился осознанно».

- **R1. Чистый конвейер раскладки (M).** Вынести весь async-эффект LevelGraph в
  модуль `layout/pipeline.ts`: вход — снапшот данных вида, выход —
  `{ LayoutResult, intents[] }` (засев позиций, миграции якорей — как ДАННЫЕ, а не
  побочные вызовы API). Компонент лишь применяет intents. Поведение 1:1 по дампам.
  Выигрыш: композиция стадий впервые под тестами; LevelGraph ~вдвое короче;
  прекращается запись в БД из середины раскладки. Ничего не меняется для бэка.

- **R2. Единая проекция (M+).** `projection.ts` на фронте (обе половины подъёма +
  пучки + provenance); бэкенд /graph переходит на «сырьё» (Pydantic-схемы → gen:api).
  Контекст-эндпоинт и превью пока не трогаем. Дампы уровней неизменны.

- **R3. Единое хранилище (M, бэк+фронт+миграция).** view_layout + батч-PUT; alembic-
  миграция данных из 3 таблиц (+ Д4 про колонки nodes/edges); один mirror и один
  undo-тип на фронте; геометрия пучков вместо fan-out. Старые эндпоинты выпиливаются
  сразу (solo-проект, совместимость не нужна).

- **R4. Контейнеры-объекты (L, самая рискованная).** Compound-узлы RF для раскрытых
  рамок; относительные координаты детей; рамки из реальных rect'ов; выпил
  keep-out/жёсткой группы/якорей изломов; роутер видит рамки. Подфазами:
  R4.1 родные рамки уровня → R4.2 раскрытые гости → R4.3 изломы в координатах
  контейнера → R4.4 чистка. Чекпойнт после каждой.

- **R5. Раскрытие любых элементов (M) — фича задумки.** Лупа у локальных контейнеров,
  политика детей (Д3), ленивая догрузка поддеревьев (/descendants есть), персист
  expanded, анимация перемещений (опционально, из бэклога).

- **R6. Опции (по желанию, после).** Контекст-схема на общий вид (снять 45 isContext-
  ветвлений, вынести холст-ядро); container-aware улучшения роутера; распил nodes.py
  на graph/layout/alerts-роутеры.

**Quick wins (можно сразу, независимо от плана):**
1. Баг: `level` у «Удаление объекта/объектов» + устаревший коммент (TreePage:463) —
   чинит кросс-уровневый Undo удалений.
2. Выпилить мёртвый computeDetours-путь (флаг A9, ветка рендера detour, распорки).
3. has_children одним механизмом (child_counts уже есть в _build_graph).
4. Waypoints в контракт контекста (или явное решение «контекст не рисует изломы»).
5. Комменты-анахронизмы (dagre ×4, anchor_rel в доках).
6. `navigateToLevel(null)` вместо инлайна в кнопке «Контекст»; общий refetch-хелпер.

**Чего НЕ делать (анти-скоуп):**
- Не менять ELK и не брать libavoid (решения из ARROWS_ROUTING_ANALYSIS в силе).
- Не возвращать живые якоря/поведенческие связи позиций (урок own-on-first-render).
- Не переписывать контекст-звезду и процессы (работают, read-only/изолированы).
- Не версионировать раскладку (версионируется только семантика — принцип в силе).

## 7. Развилки для архитектора

- **Д1. Где живёт проекция уровня: фронт (рекомендую) или бэк.**
  За фронт: раскрытие (в т.ч. будущее раскрытие локалов) интерактивно без рефетча;
  бэкенд упрощается до «отдать сырьё». За бэк: тонкий клиент. NB: у бэка в любом
  случае остаётся хелпер lift() для превью/процессов/алертов.

- **Д2. Compound-узлы: нативные RF parentId/extent (рекомендую) или свои группы.**
  За RF: бесплатный групповой drag, extent-клампы, z-порядок. Риск: порядок узлов в
  массиве, measured-размеры — проверить спайком в R4.1.

- **Д3. Политика детей при раскрытии ЛОКАЛЬНОГО контейнера: всех (рекомендую,
  консистентно с drill-down) или только связанных (как у гостей).** Для гостей
  оставить «только связанных» (это и есть C4-контекст).

- **Д4. Объём миграции хранилища в R3: всё сразу (рекомендую: nodes.pos_x/pos_y и
  edges.waypoints/handles тоже) или только 3 гостевые таблицы.** «Всё сразу» даёт
  главный выигрыш (один протокол); половинчатая миграция оставляет 3 хранилища.
  label_t можно оставить колонкой (сознательно глобальна) — решить при R3.

- **Д5. Судьба контекст-схемы: отложить (рекомендую, R6) или унифицировать в первой
  волне.** Работает, read-only, churn низкий — не горит.

## 8. Риски

1. **R4 меняет систему координат** сохранённых позиций детей раскрытых рамок →
   нужна миграция координат (абсолют → относительные) или ленивое пере-засеивание;
   продумать в задании R4.
2. **Дампы как гейт работают, пока раскладка детерминирована** — держать детерминизм
  routeAll/plashek (уже принцип D2 из A7).
3. **Соблазн совместить фазы.** R1 без R2/R3 уже окупается; R4 без R1 — нельзя
   (конвейер должен быть чистым до смены геометрии).
4. **Рост LevelGraph повторится**, если после R1 не зафиксировать правило: новые
   стадии — только модулями в pipeline, компонент не растёт (гейт по строкам в
   pre-commit — опционально).
