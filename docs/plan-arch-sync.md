# План: «Архитектура из кода» — живая синхронизация (вариант B)

Одобрен 2026-08-07 по итогам разбора открытых вопросов эпика. Предыстория: из трёх
задумок эпика две уже в проде — импорт репозитория → C4 (`import_prompt.py` +
`import_merge.py`, 2026-07-16) и автогенерация OpenAPI-спек (BYOA-доки,
SpecAgentModal). Остался третий пункт — «автообновление из кода», и он же упирался
в решение «ре-импорт = только новый проект», которое ему прямо противоречило.

**Цель:** прогнал агента через месяц — схема ОБНОВИЛАСЬ, а не пересоздалась.
Раскладка, схемы логики, спеки, процессы и ручные правки переживают синк.

**Порядок принципиален:** сначала идентичность (Фаза 0), потом синк. Пока узел
опознаётся только по имени из compose, матчить нечего: матчер будет расщеплять один
сервис на два и молча склеивать два разных — и diff-превью покажет мусор.

## Решения и отклонённые альтернативы

- **Якорь идентичности едет в формате как опциональное поле, не как обязательное.**
  `parse_import` молча игнорирует неизвестные ключи (форвард-совместимость) —
  значит YAML старых прогонов продолжает импортироваться, а новый ключ не ломает
  ни одного существующего файла. Агент, не выдавший якорь, деградирует к матчингу
  по имени, то есть к сегодняшнему поведению — не хуже.
- **Якорь — подсказка матчеру, а НЕ уникальный идентификатор.** Уникальность не
  форсим: монорепо легально даёт один `repo` на много узлов, поэтому ключ строится
  по приоритету (deployment > image > repo+path > repo), а коллизия — повод
  посмотреть на следующий уровень приоритета, а не ошибка.
- **Синк НИКОГДА не удаляет.** Пропавшее из импорта либо не трогается (дефолт),
  либо помечается `status: deprecated` (галочка). Поле `status` в модели уже есть и
  кодируется цветом на схеме — пропажа становится видимой, ничего не теряя.
  Удаление остаётся ручным действием в редакторе.
- **Проза не синкается по умолчанию.** `description` дрейфует от прогона к прогону
  (свойство LLM) и мог быть выправлен руками. Обновление описаний — явная галочка.
  `role`/`technology` — по правилу «богатое побеждает» (заполняем пустое, занятое не
  трогаем), как уже делает `merge_imports`.
- **Слой 3 (компоненты) по умолчанию вне синка.** Его состав нестабилен между
  прогонами («3–5 ключевых контейнеров» на усмотрение модели) — включённый по
  умолчанию, он утопил бы настоящий diff в шуме. Галочка «синхронизировать
  компоненты» — для тех, кто готов к шуму.
- **Синк не кладётся в Undo-историю** (как «Применить» BYOA-доков): страховка —
  dry-run превью с явным подтверждением. Настоящий откат придёт с версионированием
  узлов и связей (задача в бэклоге, там же требование включать node_docs в снимок).
- **LLM-мердж отклонён повторно** (решение эпика 2026-07-16): слияние
  структурированных текстов моделью = риск тихой потери. Матчинг — код.
- **Fuzzy-склейка по-прежнему запрещена.** Похожие имена дают предупреждение, но
  никогда не сливаются молча: ложная склейка двух разных сервисов хуже дубля.

## Фаза 0 — Идентичность (блокер, без неё синка нет) — СДЕЛАНА 2026-08-07

Коммиты: d16f291 (identity.py), 820465f (парсинг source), eb38d09 (матчер мерджа),
28345ff (миграция + nodes.source_ref + api.gen), промпт — следом. Отклонение от
плана одно, в лучшую сторону: вместо «канонический ключ + отдельный список
противоречий» получилось однозначное правило — **решает сильнейший общий тип
ключа** (`compare_identity` → same/different/unknown). Первая редакция считала
пересечение наборов достаточным для склейки, и собственный тест это опроверг: два
«api» разных команд имеют общий host, но разные git — совпадение по слабому ключу
не должно перевешивать противоречие по сильному. Порядок силы тоже пересмотрен на
git > img > k8s > host (сила = насколько ГЛОБАЛЬНО значение уникально).
Пункт 0.5 (список репозиториев системы и счётчик покрытия) НЕ делался — ждёт
решения, где хранить список.

**0.1 Формат.** У узла появляется опциональный блок:
```yaml
- name: payments
  source: {repo: "github.com/org/payments", path: "services/api", image: "reg/payments", deployment: "payments"}
```
Все поля опциональны. Нормализация на бэке: у `repo` срезаются схема, креды и
`.git`, регистр приводится к нижнему → `github.com/org/payments`.

**0.2 Промпт** (`import_prompt.py`): шаг обследования «origin» — git remote,
`image:` из compose, `name` деплоймента из k8s/helm. Правила: якорь ставится
ТОЛЬКО своим узлам (что видно в этом репозитории); чужим сервисам-заглушкам якорь
НЕ выдумывается. Встроенный пример обновляется данными (он дампается в YAML и
проверяется тестом — протухнуть относительно формата не может).

**0.3 Канонический ключ и матчер.** Новый модуль `app/identity.py`:
`source_key(node) -> str | None` — первый непустой по приоритету
`deployment > image > repo+path > repo`, с префиксом типа (`k8s:`, `img:`,
`git:`). В `merge_imports` матчинг становится двухступенчатым:
1. по `source_key` — ГЛОБАЛЬНО в пределах системы (не только среди сиблингов):
   чинит расщепление «`app` в своём репозитории / `payments` у вызывающих»;
2. по нормализованному имени в пределах слитого родителя — как сейчас.
Плюс новое правило-предохранитель: **имена совпали, а якоря различны и оба
непусты → НЕ склеивать**, развести в два узла с предупреждением. Это чинит тихую
склейку двух разных `api`/`worker` из разных команд.
Конфликт «якорь совпал, имена разные» → склеиваем, имя берём первое, факт — в
`MergeReport.conflicts` («сервис назван по-разному: app / payments»).

**0.4 Хранение.** Миграция Alembic: `nodes.source_ref` (String(512), nullable) +
индекс `(project_id, source_ref)`. Заполняется при импорте и синке; в API узла
поле только на чтение (руками не правится — это отпечаток прогона).
⚠️ После правки Pydantic-схем — сразу `npm run gen:api` и коммит `api.gen.ts`.

**0.5 (опционально) Покрытие системы.** Список репозиториев системы, заданный при
создании проекта, + счётчик «прогнано N из M» в UI импорта. Закрывает дыру
«система не знает своей полноты». Можно отложить: без него покрытие считается
по факту — сколько разных `source_ref` в схеме.

**Гейт фазы:** `pytest` на матчер (расщепление, ложная склейка, монорепо с одним
repo на много узлов, файл без якорей = сегодняшнее поведение); прогон агента по
2–3 репозиториям вживую; существующие тесты импорта зелёные без правок.

### Хвост Фазы 0, перенесённый сюда (стресс-тест 2026-08-07)

Без деплой-конфигов агент выдумывает ИМЕНА узлов, подсматривая их во встроенном
примере промпта: прогон по ArchMap (нет compose/k8s) назвал сервисы
«storefront»/«api» — оба имени взяты из примера про Ярмарку. Класс — правила
именования, не якоря, поэтому Фазу 0 не держит; но для синка важен: имена и есть
второй ключ матчинга. Лечение на выбор — нейтрализовать пример (имена вида
«сервис-А») либо дописать правило «нет деплой-конфигов — имя бери из структуры
репозитория (каталог сервиса, имя пакета), не из примера». Проверять тем же
прогоном по репозиторию без compose.

## Фаза 1 — План синка (бэк, без записи) — СДЕЛАНА 2026-08-07

Коммиты: 9a49198 (ядро `app/sync_plan.py`), 6fb91d0 (эндпоинт + схемы + api.gen).
Отклонения от плана, принятые по ходу:
- **Добавлена политика `update_names`** (в плане её не было). Имя оказалось такой
  же ручной правкой, как описание: пользователь мог переименовать «payments» в
  «Платежи», и синк молча вернул бы машинное имя. Переименование ВИДНО в плане и
  без применения — якорь уже связал узлы, строка уходит в conflicts.
- **Связь в пропавший узел не помечается пропавшей.** Узел-то не удаляется (максимум
  `deprecated`), значит связь в него остаётся валидной; звать её missing —
  вводить в заблуждение. Пропавшими считаются только связи МЕЖДУ смэтченными узлами.
- **Переезд узла не выполняется** — если прогон положил сервис под другого родителя,
  поддерево остаётся на месте, факт уходит в conflicts (та же логика, что в мердже).
Приятный побочный эффект: первый же синк ЗАЯКОРИВАЕТ узлы, созданные до Фазы 0 —
матч идёт по имени, а план проставляет им `source_ref`.

Новый модуль `app/sync_plan.py` — по образцу `build_docs_plan`/`apply_docs_plan`
(тот же паттерн «dry-run план → применение»).

```
POST /api/v1/projects/{id}/sync/preview   → SyncPlan
```
Вход: те же N текстов YAML, что у импорта (`parse_and_merge` переиспользуется
целиком), плюс флаги политик: `update_descriptions`, `sync_components`,
`mark_missing_deprecated`.

Матчинг импортированного дерева на ЖИВЫЕ узлы проекта:
1. по `source_ref`; 2. по пути имён от корня; 3. не найден → `create`.

`SyncPlan` (симметрично `DocsPlan`):
- `node_actions`: `{path, action, node_id, source_key, fields}` — действия
  `create | update | unchanged | missing`;
- `edge_actions`: `{from, to, action}` — `create | unchanged | missing`;
- `conflicts` — расхождения, решённые правилом (что оставлено и почему);
- `warnings` — fuzzy-пары, разные корни, отсутствие общих корней (уже есть в
  `MergeReport`, прокидываются наверх);
- `summary` — счётчики для шапки превью.

**Гейт фазы:** pytest — переименование сервиса при том же якоре даёт `update`, а не
`create`+`missing`; смена якоря при том же имени даёт два узла; повторный превью на
неизменённом входе даёт все `unchanged`.

## Фаза 2 — Применение — СДЕЛАНА 2026-08-07

Коммит ce6809b (`app/sync_apply.py` + эндпоинт + схемы + api.gen). Отклонения:
- **CAS не по версиям узлов, а по курсору проекта.** План изначально предполагал
  проверять `version` каждого узла. Оказалось проще и честнее: применение
  ПЕРЕСЧИТЫВАЕТ план из присланных YAML (клиентскому плану доверять нельзя), а
  расхождение с увиденным в превью ловится одним `base_graph_rev` — тем же
  курсором, которым живёт поллинг конкурентных сессий. Устарел → 409.
- **План несёт свои политики** (`SyncPlan.policies`): иначе расчёт и запись могли
  бы разойтись, если роутер передал бы политики исполнителю вторым путём.
- **Пропавшие ручные узлы помечаются наравне с исчезнувшими** (решение пользователя:
  так прозрачнее, чем прятать их в отдельную группу).

## Фаза 2 — Применение (исходный набросок)

```
POST /api/v1/projects/{id}/sync/apply    → SyncReport
```
Одна транзакция: создание новых узлов (родители раньше детей), `update` полей по
политикам, создание недостающих рёбер, пометка `deprecated` (если включено),
`bump_graph_rev`. Изменённые узлы получают `version + 1`; если чья-то версия
изменилась между превью и применением — узел пропускается с записью в отчёт (тот
же CAS-принцип, что у остальных правок).

**Не трогаем никогда:** `node_docs`, `openapi_spec`, `view_layout` (раскладка),
бизнес-процессы. Новые узлы координат не получают — их расставит ELK, существующие
остаются на своих местах. Это и есть главная ценность фазы.

**Критерий-фикспойнт (главный):** применить синк, затем сразу запросить превью на
том же входе → план пустой (все `unchanged`, ноль create/update). Ловит
недетерминизм НАШЕЙ логики (агентский — вне зоны ответственности) — тот же приём,
что закрыл осцилляции маршрутов (V54).

## Фаза 3 — UI diff-превью

Модалка по образцу `DocsImportModal`: загрузка N файлов → превью, сгруппированное
по разделам (Новые объекты / Изменённые / Пропавшие / Новые связи / Пропавшие
связи), с галочками политик и счётчиками; кнопка «Применить». Вход — ⋯-меню
страницы проекта, пункт «Обновить из репозитория». Промпт берётся тем же
`GET /projects/import/prompt` (у него уже есть параметры глубины/языка/подсказок).

## Фаза 4 — CI (эскиз, вне текущего объёма)

Токен проекта + приём тех же YAML машиной → GitHub Action «архитектура как код»
(агент в CI на merge в main обновляет схему). Делать по спросу: без Фаз 0–3
бессмысленно, а с ними — тонкая надстройка.

## Риски

- **Агент не выдал якорь** → деградация к матчингу по имени = сегодняшнее
  поведение. Не регресс, но и не выигрыш; лечится промптом, а не кодом.
- **Монорепо**: один `repo` на 20 узлов — ключ не различает. Закрывается
  приоритетом (`deployment`/`image` уникальны на сервис) и `repo+path`.
- **Одновременное переименование сервиса и переезд репозитория** — матч не
  найдётся: получим `create` + `missing`. Автоматически не решаем (fuzzy-склейка
  запрещена), но обе строки видны рядом в превью — человек сводит вручную.
- **Ручные правки поверх импорта.** Дефолтные политики (проза и слой 3 не
  синкаются, ничего не удаляется) сделаны именно под этот риск; агрессивные
  режимы — только явными галочками.

## Что НЕ входит

Версионирование/откат синка (отдельная задача бэклога), серверная интеграция с AI
API и GitHub-App, вложение найденных OpenAPI/Mermaid прямо в YAML импорта
(отдельная ветка «полного архива»), слияние двух существующих проектов.
