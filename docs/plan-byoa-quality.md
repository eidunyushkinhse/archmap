## Мотив

Эксперт по Zabbix разобрал схему, собранную Haiku по промпту импорта (проект
«Zabbix Ctrl»), и назвал систематические недочёты. Подсвеченные классы (по
словам пользователя, хвостов больше):

1. **Пропуски компонентов** — нет history syncer; нет связей zabbix proxy с
   агентами и объектами безагентского мониторинга.
2. **Смысловые дубли связей** — «отправляет данные» и «отправляет собранные
   данные» от proxy в trapper об одном и том же.
3. **Неверная семантика подписей** — «отправляет пассивные данные» у стрелки
   agent→trapper: подпись обязана точно называть режим (активный режим агента /
   пассивный режим сервера).

Вердикт анализа 2026-08-19: потолок Haiku НЕ достигнут — классы систематические
и лечатся приёмами, уже проверенными в проекте на других семьях; главный

## Федерация — анализ 2026-09-06 (вопрос пользователя: почему федерация не удаётся, если это «просто мердж»)

**ПОПРАВКА ПОЛЬЗОВАТЕЛЯ 2026-09-06 (главное):** «федеративных промптов» в замысле НЕ БЫЛО.
Федерация по замыслу — агенты с универсальным (не федеративным) промптом в каждом
репозитории, мердж в один проект, при необходимости общий узел («Мониторинг»); то есть
сумма одиночных проектов, слитых воедино. Федеративный вариант промпта (multi_product,
раздел П1, федеративный пример, политика «repo одному узлу») — наследие эпика «тюнинг
федерации» 2026-08-15, а не замысел; весь замер федерации в Ф3 (столбец multi) шёл через
него и потому мерил не то. Синтетическая федерация ниже — это и есть замысел пользователя,
и она его подтверждает. Направление дальнейших работ: только мердж одиночных моделей;
судьба флага и раздела П1 — решение пользователя (кандидат на снос).

Гипотеза пользователя — «BYOA описывает один проект нормально, значит с механикой
мерджа опишет и мега-проект из N проектов» — ПОДТВЕРЖДЕНА экспериментом.
Синтетическая федерация (tools/f3_fedsynth.py): одиночные модели Haiku Zabbix и
Grafana раунда f3-4x механически уложены в федеративную форму (корень
«Мониторинг» → контейнер-продукт с repo → прежние контейнеры), плагин взят из
федеративного прогона того же раунда, три файла слиты ШТАТНЫМ импортом и
сверены с эталоном федерации. Медианы пяти раундов, федеративные прогоны →
синтетическая федерация: полнота узлов 32 → 56 %, якоря 9 → 61 %, узлов
33 → 71, совпавших рёбер 1 → 2, точность узлов 33 → 27 %, дублей 2 → 4.
Мердж сам по себе узлы не теряет: три продукта под корнем, продукт-дубликатов
нет. Слабое звено — «федеративно оформленные» описания, а не слияние.

Почему федеративные прогоны хуже одиночных — четыре разные причины:
1. УСЛОВИЯ ПРОГОНА (артефакт стенда): один агент Haiku описывает три
   репозитория за одну сессию — 7–47 обращений к инструментам на три
   репозитория против 22–64 на один в одиночных прогонах; модель каждого
   репозитория в 2–3 раза меньше (Zabbix в федерации 12–57 узлов, медиана 21,
   против 32–38 в одиночных того же раунда), а выдуманная схема
   (id/parent_id/source_id) встречалась ТОЛЬКО в федерации (3 из 10) — дрейф
   при трёх файлах с одного прочтения промпта. В реальном применении каждый
   репозиторий описывается отдельной сессией, так что стенд занижает
   федерацию; синтетическая федерация ближе к реальному применению.
2. ПОЛИТИКА ЯКОРЕЙ П1: «repo — одному узлу, контейнеру-продукту», дети без
   path, федеративный пример без path — главный выигрыш одиночного режима
   (правка №2, якоря 5–29 → 38–70 %) в федерацию не переносится (9 %). Правило
   вводилось эпиком тюнинга федерации, чтобы пример не нарушал п. 12 («repo у
   нескольких узлов требует path»); после правки №2 path стал нормой, и правило
   устарело.
3. ФОРМА ЭТАЛОНА ≠ ФОРМА, КОТОРУЮ ВЕЛИТ П1: в эталоне федерации нет корня
   «Мониторинг» — три продукта, акторы и внешние системы лежат в корне; промпт
   же требует корень-систему с продуктами внутри. Итог: корень считается
   выдумкой, все совпавшие узлы помечены «уровень», акторы/внешние (5 узлов)
   не находятся. Эталон федерации — рукотворный «федеративный вид» на 34 узла
   (в одиночных эталонах 117 + 38): декомпозирован только Zabbix server (12),
   у Grafana три контейнера без компонентов — потолок точности структурный
   (компоненты Grafana у Haiku все «выдумки»).
4. СОБСТВЕННО ФЕДЕРАТИВНАЯ СЕМАНТИКА: (а) межпродуктовые связи держатся на
   заглушках по host, и заглушка сливается с ПРОДУКТОМ соседа, а не с его
   контейнером — «plugin → Zabbix» вместо «Датасорс Zabbix (backend) → Zabbix
   frontend»; в эталоне 6 межпродуктовых рёбер, все на контейнеры, в
   синтетической федерации 3, все в коробку продукта; (б) тёзки между
   продуктами (PostgreSQL у обоих) — экспорт корневых тёзок неоднозначен
   (упал измеритель на f3-7e), известная находка Ф2; (в) лишний уровень
   вложенности: компоненты эталона оказываются на глубине 4.

Эскиз отдельной механики (решение пользователя, НЕ начато): федерация =
мердж НЕЗАВИСИМЫХ одиночных моделей силами ArchMap, а не особый промпт.
Каждый репозиторий описывается обычным одиночным промптом (корень — имя
продукта, якоря как обычно, без раздела П1); единый импорт сам оборачивает
корень файла в контейнер-продукт под названным пользователем корнем и
переносит repo на продукт (ровно то, что делает f3_fedsynth.py); заглушки
соседей резолвятся по host в КОНТЕЙНЕР соседнего продукта, а не в продукт
(нет совпадения по host контейнера — тогда в продукт, как сейчас); тёзки
между продуктами живут в своих пространствах путей, экспорт корневых тёзок
чинится; плагин — просто ещё один продукт. Уходит федеративный вариант
промпта вместе с сентинелом «байт-в-байт». Ожидаемый эффект виден уже сейчас:
полнота 56 % при нынешнем мердже. Что не отделяется текущими данными:
доля причины 1 отдельно от 2–3 — проверяется дёшево (федеративный промпт по
одному агенту на репозиторий, 15 прогонов). Точность против грубого эталона
федерации потребует либо пересборки эталона под новую форму (без корня), либо
поправки измерителя (корень не считать).

## Метрика плато и мердж одиночных эталонов — 2026-09-06 (по вопросам пользователя)

**Метрика «ходим кругами» (предложение).** Одно число на конфигурацию промпта —
«совпадение схемы»: Dice по узлам и рёбрам ВМЕСТЕ,
2·(сматчено узлов + совпало рёбер) / (узлы+рёбра эталона + узлы+рёбра кандидата);
усечённые эталоны d3, одиночные проекты, среднее по четырём проектам внутри
раунда, медиана и размах по пяти раундам конфигурации. Правило: правка — сдвиг,
если медиана вышла за размах ТЕКУЩЕЙ принятой конфигурации (не лучшей по
медиане); три конфигурации подряд без сдвига = плато. Ретро по Ф3
(tools/f3_plateau.py, summary-plateau-metric-2026-09-06.md в каталоге материалов):
base2 11.6 → f3-1 12.7 (шум) → f3-2 11.2 (шум) → f3-3 18.7 (СДВИГ) → f3-4 18.4
(шум) → f3-5 15.3 (откат) → f3-6 18.7 (шум) → f3-7 19.9 (шум). Итог: после f3-3
четыре конфигурации подряд без сдвига — по этому правилу плато уже наступило.
Оговорки: №1 (формат) и №2 (якоря) сводная метрика не видит по построению (формат
и якоря в неё не входят) — они принимались по своим мишеням, это нормально; №4
сводно — шум (Zulip +11, Grafana −5 — пулинг прячет разнонаправленные сдвиги
проектов). Размах одной конфигурации 3–6 пунктов, весь ход Ф3 +7 — полтора
размаха. Отвергнутые кандидаты: «экономия ручной работы»
1 − (пропуски+выдумки узлов и рёбер)/(размер эталона) — ОТРИЦАТЕЛЬНА (−20 → −9 %):
доработка модели Haiku до эталона больше, чем рисование с нуля (важный продуктовый
факт), но метрика на 80 % состоит из рёбер эталона и как индикатор плато
нечувствительна; раздельные F1 узлов/рёбер — два числа вместо одного. Разовая
проверка потолка (по запросу): те же 4 проекта сильной моделью тем же промптом —
если Haiku в размахе от потолка, промпт исчерпан и править его бессмысленно.

на компоненты концов межпродуктовых связей — рукотворных решений ровно пять.

**Якоря в новой механике мерджа (оценка).** Для склейки федерации якоря НЕ нужны:
продукты склеиваются по имени корня (имя продукта — единственная общая примета у
соседа-заглушки и самого продукта), тёзки внутри разных продуктов раздельны
областью родителя без якорей, общие внешние системы — по имени на верхнем уровне.
host в эталонах почти нет (Zabbix 0, Grafana 0, Sentry 6, Zulip 1), в моделях Haiku
2–19 и все на приватной инфраструктуре; у контейнера соседа не бывает host, которым
его зовёт вызывающий, поэтому «уточнить конец до компонента соседа» host не решит.
Где якоря остаются нужны — ВНЕ федерации: синк одного продукта из репозитория
(переименования между прогонами; эпик принят, не пересматривается) и предохранитель
«тёзки на одном уровне из разных repo — раздельно» (полевой случай плагин/ядро).
Рекомендация: мердж федерации объяснять одним правилом — «одно имя на одном
уровне — один объект; внешняя заглушка без детей — сам продукт соседа»; якоря в
этом сценарии не показывать и не требовать; политику П1 и федеративный раздел
промпта снести; пять концов «в коробку» — гест пользователя «перевесить на
компонент» из перечня кандидатов (перечень уже есть в замечаниях и алертах).
Возможное упрощение позже — «точка входа продукта» (компонент, принимающий внешние
вызовы; связи в коробку перевешиваются на него сами); не начинать без запроса.

одиночных эталонов новым эталоном федерации (после пяти перевешиваний);
(3) снос федеративного промпта и П1; (4) починка алерта изолированных групп под
связи в коробку.

**Ф-B. Починка алерта «изолированные группы» под связи в коробку.** Сейчас
связность строится по рёбрам без иерархии (alerts.py п. 3, осознанно — «иначе всё
связано через дерево»), поэтому связь в контейнер не соединяет его с детьми и
федерация с пятью связями в коробки даёт ложную «группу из 5 объектов». Правило:
конец связи в контейнере считается касающимся всего его поддерева (для связности
объединять контейнер с потомками, только если у контейнера есть собственная связь;
дерево само по себе связностью не считается). Спека docs/specs/alerts.md —
инвариант в том же коммите; тесты: коробка с детьми + связь в коробку = одна
группа; два продукта без связей между ними = две группы (как сейчас).

**Ф-D. Проверка потолка (после Ф-A…Ф-C).** Четыре одиночных репозитория, тот же
одиночный промпт, сильная модель (предложение — Opus, чтобы не сравнивать Haiku с

Решение по результату: сильная модель ≥ вдвое выше Haiku (около 40 % и выше) —
упёрлась модель, промпт исправен, дальнейшие правки промпта под Haiku закрыты,
продуктовый ответ — рекомендация модели/второй проход скептиком; сильная модель
в размахе от Haiku — потолок в постановке (один проход, глубина ≤ 3, форма
