# План: «Доки от агента» — мульти-логики узла и BYOA-дозаливка доков

Одобрено 2026-07-16 по итогам анализа (диагноз → развилки → рекомендация →
решения пользователя). Цель программы: агент пользователя (BYOA, планка —
слабая модель, как в repo-import) наполняет документный слой ArchMap —
mermaid-логики узлов и OpenAPI-спеки — в СУЩЕСТВУЮЩИЙ проект. Бизнес-процессы
(sequence) агентом в этой программе НЕ генерируются — вынесены в этап 3.

## Решения и отклонённые альтернативы (зафиксированы пользователем)

1. **Мульти-доки раньше агента.** Генерить логики в единственное поле
   node.flowchart — проектировать в тупик: идея бэклога («сценарий на каждую
   API-операцию + фоновые воркеры») требует коллекции именованных схем, и
   переучивание промпта потом = повторный стресс-тест. Этап 1 = модель
   node_docs, этап 2 = BYOA-дозаливка.
2. **Канал доставки — дозаливка в существующий проект,** а не поля формата
   создания. Дозаливка НЕ требует этапа B repo-import: структуру не мерджим —
   адресуем существующие узлы по путям (резолвер parse_import с однозначным
   хвостом переиспользуется). Двухшаговость «сначала схема, потом доки»
   покрывает и новый, и старый проект. Написанная здесь адресация живых узлов
   по путям — общий кирпич будущего этапа B.
3. **Пакет файлов, а не чат-вывод.** Спеки 50–200 КБ нельзя гонять через окно
   вывода модели (порча у Haiku-класса). Промпт велит сложить в репо
   archmap-docs/: манифест YAML (mermaid — инлайн, спеки — ссылкой на файл по
   имени) + файлы спек, скопированные ИНСТРУМЕНТОМ (байтово, не перепечаткой).
   Панель принимает мульти-файлы; чистый копипаст одного YAML тоже работает
   (кейс «только логики»).
4. **Синтез OpenAPI разрешён с пометкой происхождения.** Промпт ранжирует
   добычу: найти готовую → снять с фреймворка (у агента есть терминал:
   app.openapi(), springdoc, swagger-jsdoc) → синтез из кода. Происхождение
   (found | generated | synthesized) едет в манифесте и показывается в превью
   («synthesized — проверь глазами»); не персистится.
5. **Привязка схемы к операции — в модель сразу.** node_docs.operation
   («METHOD /path», свободная строка) — задел под бэклог-идею «Процессы →
   доки шага» (шаг-API-вызов проваливается в спеку операции / схему сценария).
6. **MCP-канал отклонён (пока):** запись мимо dry-run превью ломает паттерн
   «человек-судья», токен ArchMap оказывается в среде агента, настройка
   сложнее копипаста. Триггер пересмотра — спрос.

## Этап 1 — мульти-доки узла (node_docs)

Замена node.flowchart коллекцией именованных mermaid-схем. openapi_spec НЕ
трогаем: одна спека на узел — осознанно, операций много ВНУТРИ спеки.

### Модель и миграция

- Таблица node_docs: id (uuid PK), node_id (FK nodes, ON DELETE CASCADE,
  index), name (String 256, NOT NULL), kind (String 16: overview | operation |
  worker; дефолт overview), operation (String 256, NULL — «METHOD /path» при
  kind=operation), content (Text, NOT NULL, дефолт ''), version (int, CAS как
  у узла), created_at/updated_at; UNIQUE (node_id, name) — имя адресует док
  при дозаливке этапа 2 и в будущей адресации шагов процесса.
- Relationship Node.docs: cascade delete-orphan + passive_deletes,
  lazy="selectin" (мета едет в каждой graph-выдаче — без N+1).
- Миграция: создать таблицу; перенос данных
  `INSERT … SELECT gen_random_uuid(), id, 'Логика', 'overview', flowchart
  FROM nodes WHERE flowchart IS NOT NULL AND flowchart <> ''`;
  DROP COLUMN nodes.flowchart. Downgrade — колонка назад + обратный перенос
  контента дока «Логика» (best-effort).

### API (мутации — require_architect; чтение — обе роли)

- GET /api/v1/nodes/{id}/docs → list[NodeDocResponse] (С content).
- POST /api/v1/nodes/{id}/docs {name, kind, operation?, content?} → 201;
  дубль имени → 409 с человеческим detail (пре-чек, не IntegrityError).
- PATCH /api/v1/nodes/{id}/docs/{doc_id} {name?, kind?, operation?, content?,
  base_version?} — CAS-паттерн update_node: устаревший base_version → 409,
  успешная правка инкрементит version; None = компенсация undo без проверки.
- DELETE /api/v1/nodes/{id}/docs/{doc_id} → 204.
- Все мутации: bump_graph_rev (мета доков едет в graph-выдаче — поллинг
  этапа 1 конкурентности должен увидеть) + touch_project.
- NodeResponse: поле flowchart УХОДИТ, приходит docs: list[NodeDocMeta]
  {id, name, kind, operation} (без content — контент лениво GET-ом при
  открытии оверлея; сегодня полный flowchart грузился в КАЖДУЮ graph-выдачу —
  станет легче). NodeCreate/NodeUpdate теряют flowchart (док создаётся после
  узла своим API). Pydantic → npm run gen:api в том же коммите.

### Целостность соседних механик (карта потребителей flowchart)

- restore.py (undo удаления узла): DeletionSnapshot.node_docs (дефолт [] —
  снимки в памяти старых клиентов без поля не ломаются) + сбор доков
  поддерева в build_deletion_snapshot + воссоздание с исходными id в
  restore_from_snapshot. Иначе регресс: сегодня flowchart — колонка узла и
  восстанавливается сам.
- projects.py (копия проекта): копировать node_docs с новыми id (по nmap).
- export.py / import_yaml.py: формат БЕЗ доков, как был — поправить
  докстринги (упоминают flowchart как поле узла).
- Шаблоны/сиды flowchart не сеяли — не трогаются.
- Тест CAS конкурентности переезжает с flowchart на openapi_spec (дух теста —
  «тексты доков не затираются» — сохраняется).

### Фронтенд

- NodeInspector: строка «Логика» — статус «не задано» / «N сх.» из
  node.docs; открывает DocOverlay (режим flowchart). Режим openapi — как был
  (save/notice через NodeInspector не меняются).
- DocOverlay (режим flowchart): новый компонент-наполнитель FlowchartDocs —
  сам фетчит список доков при открытии, держит активный док, панель-строка
  над сплитом: переключатель доков + создать/переименовать/удалить + kind +
  operation (только архитектор). Тело — прежний FlowchartDoc активного дока
  (key=doc.id — чистый ремаунт стейта редактора); blur → PATCH content с
  base_version, 409 → notice + подтяжка свежего (паттерн текущего оверлея).
- NodeModal (модалка создания узла): textarea flowchart УДАЛЯЕТСЯ.
- Undo (история TreePage): nodeFields теряет flowchart; докам — свои команды
  через колбэк onDocEvent (edit/create/delete со снимками before/after):
  undo/redo = компенсации docs-API БЕЗ base_version (U24); у create/delete
  redo/undo захватывают НОВЫЙ id пересозданного дока в замыкание (на доки
  пока никто не ссылается — сохранение id не требуется, в отличие от узлов).
- node.docs в стейте уровня освежается локально по ответам docs-API,
  чтобы счётчик в инспекторе не отставал; поллинг-ресинк освежает сам.

### Спеки и доки

- docs/specs/node.md: строка модели узла (flowchart? → docs[]) — в том же
  коммите, что перенос поля.
- docs/specs/history.md: команды доков (правка/создание/удаление) — привязка
  к U-инвариантам компенсаций.
- spec.md: раздел документации узла — несколько именованных логик, типы,
  привязка к операции.
- tasks.md: пункт версионирования упоминает flowchart в версионируемых полях
  → заменить на «доки узла (node_docs)».

### Тесты и гейты

- Бэк: CRUD/CAS доков (409 устаревшая версия, 409 дубль имени), каскад при
  удалении узла, снимок/restore с доками, копия проекта с доками, экспорт
  по-прежнему без доков (фикстуры test_export без flowchart).
- Фронт: фикстуры Node без flowchart / с docs; vitest на новые куски логики
  оверлея, если появятся чистые функции; tsc -b + eslint 0.
- Ручной прогон: alembic upgrade, создать/переименовать/удалить схему в
  оверлее, Ctrl+Z по правке контента, наблюдатель read-only.

### Порядок коммитов этапа 1

1. docs: план + tasks.md (эпик в работу, правки смежных идей).
2. feat(back): node_docs — модель, миграция с переносом, CRUD-роутер,
   снимок/restore, копия проекта, схемы + gen:api, тесты.
3. feat(front): инспектор/оверлей мульти-доков, NodeModal без flowchart,
   undo-команды доков, фикстуры.
4. docs: spec.md + specs (node, history) + отметка в tasks.md.

## Этап 2 — BYOA-дозаливка доков (рамочно; детальное ТЗ — перед стартом)

- Промпт: GET /projects/{id}/docs/prompt?node_id&include=logic|api|both&lang&
  hints — шаблон с ВЛОЖЕННЫМ build_export(срез поддерева или весь проект):
  пути узлов в нём — адреса для манифеста. Дисциплина «документируй только
  узлы, реализованные в ЭТОМ репозитории» (урок фантомной БД repo-import).
  Инструкция сложить archmap-docs/ (манифест + спеки байтово, mermaid
  инлайн). Пример манифеста хранится ДАННЫМИ и тестом гоняется через парсер
  (паттерн import_prompt — промпт не протухает). Планка — слабая модель.
- Формат манифеста (эскиз): docs: [{node: "Система / X", logic: [{name,
  kind, operation?, mermaid}], openapi: {file: "x-api.yaml" | inline,
  origin: found|generated|synthesized}}]. Неизвестные ключи игнорируются.
- Парсер: толерантность как parse_import (fence / срез от первой строки),
  резолв узлов по полному пути / голому имени / однозначному хвосту —
  переиспользовать; ошибки с префиксом «файл N: …».
- POST preview (dry-run): адресация (найден / не найден / неоднозначен),
  перезаписи занятых доков, origin-пометки спек. Mermaid валидирует ФРОНТ
  (бэкового валидатора mermaid нет; парсер уже в бандле оверлея); OpenAPI —
  бэк (yaml + эвристика openapi/paths, серверное зеркало docValidate).
- Применение: политика overwrite | skip (выбор в превью), запись node_docs +
  openapi_spec, bump_graph_rev; «Скопировать замечания для агента» — как в
  ImportPane.
- UI: панель в СУЩЕСТВУЮЩЕМ проекте (не витрина создания): выбор поддерева →
  «Скопировать промпт»; мульти-файл пикер + textarea; превью; применить.
- Стресс-тест промпта ПО МЕТОДИКЕ пользователя: статистика на публичных
  репо (клоны потом удалить), механический скоринг, правки только по классам,
  повторившимся из раза в раз; у mermaid-синтаксиса слабых моделей будут
  свои классы — заложить время на 2–3 раунда.

## Этап 3 — бэклог (с триггерами)

- Инлайн-доки в формате СОЗДАНИЯ проекта (отклонённый здесь вариант A):
  опциональные поля узла в YAML repo-import — когда попросят «сразу с доками
  одним прогоном». parse_import форвард-совместим (ключи игнорирует), но
  большие спеки в чат-выводе — против решения №3; сначала спрос.
- Бизнес-процессы от агента: упирается в запертый слой (сообщение = плечо
  живого ребра; несуществующее ребро = правка схемы) и кросс-репозиторность
  (один репо не видит сквозную цепочку). Ждёт связку «схема ↔ операция»
  (поле operation — задел) и/или этап B repo-import (мердж в существующий).
- MCP-сервер ArchMap / GitHub Action «доки как код» — по спросу.
