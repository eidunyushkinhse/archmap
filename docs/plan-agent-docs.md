# План: «Доки от агента» — мульти-логики узла и BYOA-дозаливка доков

Одобрено 2026-07-16 по итогам анализа (диагноз → развилки → рекомендация →
решения пользователя). Цель программы: агент пользователя (BYOA, планка —
слабая модель, как в repo-import) наполняет документный слой ArchMap —
mermaid-логики узлов и OpenAPI-спеки — в СУЩЕСТВУЮЩИЙ проект. Бизнес-процессы
(sequence) агентом в этой программе НЕ генерируются — вынесены в этап 3.

## Решения и отклонённые альтернативы (зафиксированы пользователем)

1. **Мульти-доки раньше агента.** Генерить логики в единственное поле
   node.flowchart — проектировать в тупик: идея бэклога («сценарий на каждую
   API-операцию + фоновые воркеры») требует коллекции именованных схем, и
   переучивание промпта потом = повторный стресс-тест. Этап 1 = модель
   node_docs, этап 2 = BYOA-дозаливка.
2. **Канал доставки — дозаливка в существующий проект,** а не поля формата
   создания. Дозаливка НЕ требует этапа B repo-import: структуру не мерджим —
   адресуем существующие узлы по путям (резолвер parse_import с однозначным
   хвостом переиспользуется). Двухшаговость «сначала схема, потом доки»
   покрывает и новый, и старый проект. Написанная здесь адресация живых узлов
   по путям — общий кирпич будущего этапа B.
3. **Пакет файлов, а не чат-вывод.** Спеки 50–200 КБ нельзя гонять через окно
   вывода модели (порча у Haiku-класса). Промпт велит сложить в репо
   archmap-docs/: манифест YAML (mermaid — инлайн, спеки — ссылкой на файл по
   имени) + файлы спек, скопированные ИНСТРУМЕНТОМ (байтово, не перепечаткой).
   Панель принимает мульти-файлы; чистый копипаст одного YAML тоже работает
   (кейс «только логики»).
4. **Синтез OpenAPI разрешён с пометкой происхождения.** Промпт ранжирует
   добычу: найти готовую → снять с фреймворка (у агента есть терминал:
   app.openapi(), springdoc, swagger-jsdoc) → синтез из кода. Происхождение
   (found | generated | synthesized) едет в манифесте и показывается в превью
   («synthesized — проверь глазами»); не персистится.
5. **Привязка схемы к операции — в модель сразу.** node_docs.operation
   («METHOD /path», свободная строка) — задел под бэклог-идею «Процессы →
   доки шага» (шаг-API-вызов проваливается в спеку операции / схему сценария).
6. **MCP-канал отклонён (пока):** запись мимо dry-run превью ломает паттерн
   «человек-судья», токен ArchMap оказывается в среде агента, настройка
   сложнее копипаста. Триггер пересмотра — спрос.

## Этап 1 — мульти-доки узла (node_docs)

Замена node.flowchart коллекцией именованных mermaid-схем. openapi_spec НЕ
трогаем: одна спека на узел — осознанно, операций много ВНУТРИ спеки.

### Модель и миграция

- Таблица node_docs: id (uuid PK), node_id (FK nodes, ON DELETE CASCADE,
  index), name (String 256, NOT NULL), kind (String 16: overview | operation |
  worker; дефолт overview), operation (String 256, NULL — «METHOD /path» при
  kind=operation), content (Text, NOT NULL, дефолт ''), version (int, CAS как
  у узла), created_at/updated_at; UNIQUE (node_id, name) — имя адресует док
  при дозаливке этапа 2 и в будущей адресации шагов процесса.
- Relationship Node.docs: cascade delete-orphan + passive_deletes,
  lazy="selectin" (мета едет в каждой graph-выдаче — без N+1).
- Миграция: создать таблицу; перенос данных
  `INSERT … SELECT gen_random_uuid(), id, 'Логика', 'overview', flowchart
  FROM nodes WHERE flowchart IS NOT NULL AND flowchart <> ''`;
  DROP COLUMN nodes.flowchart. Downgrade — колонка назад + обратный перенос
  контента дока «Логика» (best-effort).

### API (мутации — require_architect; чтение — обе роли)

- GET /api/v1/nodes/{id}/docs → list[NodeDocResponse] (С content).
- POST /api/v1/nodes/{id}/docs {name, kind, operation?, content?} → 201;
  дубль имени → 409 с человеческим detail (пре-чек, не IntegrityError).
- PATCH /api/v1/nodes/{id}/docs/{doc_id} {name?, kind?, operation?, content?,
  base_version?} — CAS-паттерн update_node: устаревший base_version → 409,
  успешная правка инкрементит version; None = компенсация undo без проверки.
- DELETE /api/v1/nodes/{id}/docs/{doc_id} → 204.
- Все мутации: bump_graph_rev (мета доков едет в graph-выдаче — поллинг
  этапа 1 конкурентности должен увидеть) + touch_project.
- NodeResponse: поле flowchart УХОДИТ, приходит docs: list[NodeDocMeta]
  {id, name, kind, operation} (без content — контент лениво GET-ом при
  открытии оверлея; сегодня полный flowchart грузился в КАЖДУЮ graph-выдачу —
  станет легче). NodeCreate/NodeUpdate теряют flowchart (док создаётся после
  узла своим API). Pydantic → npm run gen:api в том же коммите.

### Целостность соседних механик (карта потребителей flowchart)

- restore.py (undo удаления узла): DeletionSnapshot.node_docs (дефолт [] —
  снимки в памяти старых клиентов без поля не ломаются) + сбор доков
  поддерева в build_deletion_snapshot + воссоздание с исходными id в
  restore_from_snapshot. Иначе регресс: сегодня flowchart — колонка узла и
  восстанавливается сам.
- projects.py (копия проекта): копировать node_docs с новыми id (по nmap).
- export.py / import_yaml.py: формат БЕЗ доков, как был — поправить
  докстринги (упоминают flowchart как поле узла).
- Шаблоны/сиды flowchart не сеяли — не трогаются.
- Тест CAS конкурентности переезжает с flowchart на openapi_spec (дух теста —
  «тексты доков не затираются» — сохраняется).

### Фронтенд

- NodeInspector: строка «Логика» — статус «не задано» / «N сх.» из
  node.docs; открывает DocOverlay (режим flowchart). Режим openapi — как был
  (save/notice через NodeInspector не меняются).
- DocOverlay (режим flowchart): новый компонент-наполнитель FlowchartDocs —
  сам фетчит список доков при открытии, держит активный док, панель-строка
  над сплитом: переключатель доков + создать/переименовать/удалить + kind +
  operation (только архитектор). Тело — прежний FlowchartDoc активного дока
  (key=doc.id — чистый ремаунт стейта редактора); blur → PATCH content с
  base_version, 409 → notice + подтяжка свежего (паттерн текущего оверлея).
- NodeModal (модалка создания узла): textarea flowchart УДАЛЯЕТСЯ.
- Undo (история TreePage): nodeFields теряет flowchart; докам — свои команды
  через колбэк onDocEvent (edit/create/delete со снимками before/after):
  undo/redo = компенсации docs-API БЕЗ base_version (U24); у create/delete
  redo/undo захватывают НОВЫЙ id пересозданного дока в замыкание (на доки
  пока никто не ссылается — сохранение id не требуется, в отличие от узлов).
- node.docs в стейте уровня освежается локально по ответам docs-API,
  чтобы счётчик в инспекторе не отставал; поллинг-ресинк освежает сам.

### Спеки и доки

- docs/specs/node.md: строка модели узла (flowchart? → docs[]) — в том же
  коммите, что перенос поля.
- docs/specs/history.md: команды доков (правка/создание/удаление) — привязка
  к U-инвариантам компенсаций.
- spec.md: раздел документации узла — несколько именованных логик, типы,
  привязка к операции.
- tasks.md: пункт версионирования упоминает flowchart в версионируемых полях
  → заменить на «доки узла (node_docs)».

### Тесты и гейты

- Бэк: CRUD/CAS доков (409 устаревшая версия, 409 дубль имени), каскад при
  удалении узла, снимок/restore с доками, копия проекта с доками, экспорт
  по-прежнему без доков (фикстуры test_export без flowchart).
- Фронт: фикстуры Node без flowchart / с docs; vitest на новые куски логики

- Ручной прогон: alembic upgrade, создать/переименовать/удалить схему в

## Этап 2 — BYOA-дозаливка доков (детальное ТЗ, 2026-07-16)

Пользовательский путь: в открытом проекте архитектор жмёт «Доки от агента» →
копирует промпт (в нём срез схемы с путями узлов) → гонит своим агентом в
репозитории сервиса → агент складывает в репо пакет archmap-docs/ (манифест +
файлы спек) → пользователь загружает ВСЕ файлы пакета в модалку → живой
dry-run показывает адресацию/перезаписи/валидность → «Применить». Несколько
репозиториев = несколько манифестов в одной загрузке.

### Формат пакета и манифеста

Пакет — папка archmap-docs/ в корне репозитория: `manifest.yaml` + файлы
OpenAPI-спек рядом. Файлы различаются ПО СОДЕРЖИМОМУ, не по имени: YAML-словарь
с ключом `docs` — манифест, всё остальное — файл-ресурс (спека), на который
манифест ссылается по имени файла. Манифест:

```yaml
docs:
  - node: "Ярмарка / orders"          # путь узла ДОСЛОВНО из среза схемы
    logic:
      - name: "POST /orders"          # имя схемы, уникально в пределах узла
        kind: operation               # overview | operation | worker
        operation: "POST /orders"     # для kind=operation
        mermaid: |
          graph TD
            A["Приём запроса"] --> B["Валидация"]
    openapi:
      file: orders-api.yaml           # файл из пакета… (XOR с inline)
      origin: found                   # found | generated | synthesized
  - node: "Ярмарка / orders / orders-db"
    logic:
      - name: "Схема хранения"
        kind: overview
        mermaid: |
          graph LR
            T1["orders"] --> T2["order_items"]
```

- `node` — резолв как в импорте схемы: точный полный путь → голое имя (если
  уникально) → однозначный ХВОСТ пути; не найден/неоднозначен → ошибка строки.
- `logic[]` опционален; поля: name (обяз., ≤256), kind (дефолт overview),
  operation (≤256, ожидается при kind=operation — иначе warning), mermaid
  (обяз., ≤200k). Дубль имени в пределах узла ВНУТРИ файла — ошибка.
- `openapi` опционален; ровно одно из file|inline (+ origin, без origin —
  warning «происхождение не указано»). file — имя файла из загрузки (не
  найден → ошибка); inline — текст спеки (≤2МБ, для мелких спек).
- Неизвестные ключи игнорируются (форвард-совместимость); толерантность к
  обёртке — цепочка parse_import: сырой → fenced-блок → срез от строки
  `docs:`. Лимиты: ≤500 записей node, ≤50 схем на узел.
- Мердж N манифестов: идентичность дока = (узел, имя схемы), спеки = узел;
  дубль из РАЗНЫХ файлов → первый побеждает + конфликт в отчёте (паттерн
  merge_imports). Загруженный файл, не являющийся манифестом и не
  упомянутый ни одним file: — warning «файл не использован».

### Семантика применения (политика перезаписи)

Для каждой входящей схемы цель — слот (узел, имя): пусто → создать; занято и
контент+мета совпадают → «без изменений»; занято и отличается → политика:
глобальный тумблер «Перезаписывать занятые» (дефолт ВЫКЛ) — выкл = пропустить
(строка в отчёте), вкл = перезаписать. Та же логика для openapi_spec узла.
Перезапись идёт БЕЗ base_version (bulk-интент архитектора после явного
dry-run, как компенсации undo), бампает version дока/узла и graph_rev.
Применение в undo-историю НЕ кладётся: откат = повторный прогон/ручная правка;
страховка от затирания ручной работы — дефолт «не перезаписывать» + явный
список перезаписей в превью (полноценный откат приедет с версионированием).
Повторный apply того же пакета идемпотентен (всё «без изменений»).

### Бэкенд

- `app/docs_import.py`: `parse_manifest(text) → (ParsedManifest|None, errors)`;
  `build_docs_plan(nodes, manifests, files, overwrite) → DocsPlan` — чистая
  функция: резолв узлов по живому дереву, мердж, действия
  (create_doc | overwrite_doc | skip | unchanged | set_openapi) + отчёт;
  `apply_docs_plan(db, plan)` — запись. Ошибки файлов — с префиксом «файл N:».
- `app/docs_prompt.py`: `build_docs_prompt(export_slice, include, lang, hints)`
  — пример манифеста хранится ДАННЫМИ и тестом гоняется через parse_manifest
  (паттерн import_prompt, промпт не протухает).
- Роутер `app/routers/docs_import.py` (X-Project-Id, require_architect):
  - `GET /api/v1/docs-import/prompt?node_id&include=logic|api|both&lang&hints`
    → {prompt}; срез = build_export(поддерево node_id | весь проект).
  - `POST /api/v1/docs-import/preview` {files: [{name, content}]} → отчёт:
    per-doc действия с mermaid-текстами (фронт валидирует их сам), per-spec
    действия с origin и серверной проверкой (yaml + эвристика openapi/paths →
    warning), unresolved/конфликты/warnings/errors, счётчики.
  - `POST /api/v1/docs-import/apply` {files, overwrite} → тот же отчёт +
    фактические счётчики записи (план пересчитывается на живом состоянии).
- Pydantic-схемы + `npm run gen:api` в том же коммите.

### Промпт (RU-тело; планка — слабая модель; уроки repo-import)

Секции: роль («схема уже создана — дополни её документами, схему НЕ меняй»);
вложенный fenced-срез схемы + «пути узлов бери ДОСЛОВНО»; дисциплина
«документируй ТОЛЬКО узлы, чью реализацию видишь в ЭТОМ репозитории; своего
узла нет в срезе — пропусти и скажи в финальном ответе» (урок фантомной БД);
что собирать: logic — обойти точки входа (роутеры/хэндлеры) и фоновые
воркеры/кроны/консьюмеры, на значимую операцию — kind=operation с operation
«METHOD /path», на воркер — kind=worker, обзорная kind=overview опционально,
≤12 схем на узел, схема обозримая (~30 вершин), только mermaid flowchart
(graph TD/LR), подписи в ["…"]; api — ранжир добычи: готовый файл → СКОПИРУЙ
ИНСТРУМЕНТОМ (cp), НЕ перепечатывай, origin: found / фреймворк отдаёт спеку
(FastAPI app.openapi(), springdoc, swagger-jsdoc) → сгенерируй в файл,
origin: generated / иначе синтез МИНИМАЛЬНОЙ честной спеки (только реально
существующие эндпоинты), origin: synthesized; формат вывода: папка
archmap-docs/ с manifest.yaml (пример — данными) + спеки; правило кавычек при
двоеточии; чек-лист самопроверки (валидный YAML; пути дословно; имена схем
уникальны; у operation-схем заполнено operation; спеки скопированы, не
перепечатаны; у каждой спеки origin; двоеточия в кавычках); починка по
списку замечаний валидатора; подсказки пользователя.

поддерева backend; 71k токенов, ~5 мин, пакет и смоук удалены):

- Формат и адресация — 0 ошибок: 17/17 схем (все operation) + 2 спеки
  применились с первого раза; голые имена узлов из среза поддерева
  разрезолвились; имена операций закавычены, mermaid — литеральными блоками.
- Класс «обёртка вывода» У ДОЗАЛИВКИ НЕ СУЩЕСТВУЕТ ПО ПОСТРОЕНИЮ: результат —
  файлы, а не чат-вывод (решение №3 подтверждено).
- Ранжир добычи спеки сработал сам: агент нашёл venv, снял app.openapi()
  командой в файл (215 КБ, JSON) байтово, origin: generated честный.
- mermaid: 16/17 валидны; 1 слип — незакрытая кавычка ярлыка ромба
  ({"…'} вместо {"…"}). Советующая ⚠ в превью, не блокер. Промпт НЕ правим
  (методика: только по классам, повторившимся на стресс-тесте).
- Дисциплина: воркеров не выдумал («в коде нет кронов» — честно), чужие узлы
  не трогал. Наблюдение на стресс-тест: одну спеку сервиса привязал к ОБОИМ
  компонентам (api и import) вместо узла-сервиса backend — семантическая
  шероховатость, валидатор пропускает законно; если повторится — уточнить в
  промпте «спека привязывается к узлу самого сервиса».

## Журнал: стресс-тест промпта дозаливки (2026-07-16)

8 прогонов Haiku по 4 сценариям (example-voting-app ×2, microblog ×2,
full-stack-fastapi-template ×2 — публичные клоны, удалены; ArchMap frontend/
×2 — срез «узел без API»), смоук-проекты со схемами под каждый сценарий
(удалены). Скоринг механический: превью живого API + mermaid батчем через
продовый валидатор (page.evaluate + import mermaidLoader на vite-деве).

Классы и решения:
- «openapi: {}» как маркер «спеки нет» — 2/8 прогонов (5 вхождений), валил
  весь файл. ПОЧИНЕНО двояко: толерантность парсера (пустой словарь = ключа
  нет) + строка в промпт «у узла без API ключ openapi не пиши вовсе».
  Подтверждение: 0/3.
- Спека/operation-схемы ЧУЖОГО API на узле-клиенте — 2/2 ArchMap-прогонов
  (агент снимал app.openapi() с соседнего backend и вешал на frontend;
  клиентские вызовы оформлял operation-схемами). ПОЧИНЕНО промптом:
  «openapi/operation — ВХОДЯЩИЙ API узла; сценарии узла-клиента — overview с
  человеческим именем» + пункт чек-листа. Подтверждение: 0/1 — образцовый
  прогон (7 overview, спеки нет, агент сам процитировал правило).
- Пути «microblog/api» слэшем без пробелов — 1/8 (3 ссылки). Не повторился,
  но добавлена дешёвая толерантность резолвера (нормализация «a/b» → «a / b»
  финальным фолбэком; настоящие имена со слэшем не задеваются — матчатся
  раньше).
- НЕ повторились (не трогаем): лимит схем на узел (16>12 — 1/8), mermaid-
  синтаксис (0/56 в стресс-тесте; суммарно с dogfood 72/73), перепечатка
  found-спек (путь found в сетке не встретился — в репо не было готовых спек;
  generated покрыт dogfood, синтез — 7 прогонов честно-минимальный).
- Нормой признано: overview-доки на узлах БД/инфраструктуры из кода моделей
  и миграций; спека REST-компонента на компоненте (а не сервисе целиком) —
  семантически точнее, класс «спека на компонентах» из dogfood снят как
  не-ошибка.
Подтверждающий раунд (3 прогона на правленом промпте): 0 ошибок валидатора,
mermaid 33/33, воркеры/overview классифицированы верно. Итог: слабая модель
выдаёт применимый пакет с первого прогона; шум остаточных прогонов ловится
превью (warnings «файл не использован», origin-бейджи).
