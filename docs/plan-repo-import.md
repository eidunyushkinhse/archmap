# План: «Из репозитория» — ИИ-агент описывает систему, ArchMap импортирует

Одобрено 2026-07-16 по итогам двух раундов проектирования (одиночный репозиторий;
мульти-репо и мердж). Цель: пользователю не нужно документировать систему с нуля —
он запускает СВОЕГО ИИ-агента (планка качества: справляется DeepSeek v4 Flash 262k)
в репозитории сервиса с нашим промптом, получает YAML в формате экспорта ArchMap
и импортирует его в новый проект. Система из многих репозиториев = несколько
прогонов одного промпта → несколько YAML → детерминированный мердж на нашей стороне.

## Решения и отклонённые альтернативы

- **BYOA (bring your own agent), а не серверная интеграция с AI API.**
  Код не покидает периметр пользователя (корп. репозитории, секреты в .env);
  анализ репо — агентская задача с инструментами, а не один вызов 262k-контекста
  (строить своего агента-оркестратора в FastAPI = переизобретать Claude Code);
  ключи/биллинг не наши; промпт работает с любым агентом. Серверная интеграция
  (загрузка репо / GitHub-App) — дальний бэклог, триггер: спрос от пользователей
  без собственных агентов.
- **Мердж N файлов — кодом ArchMap, не «ещё одним промптом».** LLM-слияние больших
  структурированных текстов = риск ТИХОЙ потери (валидатор ловит синтаксис, не
  полноту), недетерминизм, лишний круг через CLI. Отклонено.
- **Но половина решения мерджа живёт в промпте**: конвенции именования делают
  входы мердж-дружелюбными (см. «Промпт»). Остаточную двусмысленность («один
  Kafka или два?») не решаем молча — флажим в отчёте слияния, судья — человек.

## Путь пользователя

1. Витрина создания проекта → пятый способ старта **«Из репозитория»**.
2. Слева параметры (имя системы = название проекта; глубина 2/3 слоя; язык
   описаний; свободные подсказки агенту) → «Скопировать промпт».
3. В каждый репозиторий системы — ОДИН И ТОТ ЖЕ промпт своим агентом; каждый
   прогон отдаёт YAML.
4. Все YAML — в панель импорта (несколько документов-чипов). Живой dry-run →
   отчёт слияния: «3 файла → 27 узлов (8 склеено), 1 конфликт, 2 подозрения».
   Ошибки/замечания можно скопировать и унести агенту на починку (промпт заранее
   учит агента чинить по списку ошибок валидатора).
5. Зелёная сводка → «Создать проект» → авто-ELK раскладывает уровни.

## Архитектура

### Бэкенд

- `app/import_prompt.py` — `build_import_prompt(system_name, depth, lang, hints)`.
  Шаблон промпта с ВСТРОЕННЫМ валидным примером YAML; истина формата —
  `parse_import`, их связывает тест «пример из промпта проходит валидатор»
  (промпт физически не может протухнуть относительно формата).
- `GET /projects/import/prompt?system_name&depth&lang&hints` → {prompt}
  (require_architect; статический путь ДО `/{project_id}`, как templates/preview).
- `app/import_merge.py` — `merge_imports(parts: list[ParsedImport]) →
  (ParsedImport, MergeReport)`. Чистая функция БЕЗ БД — мерджим РАЗОБРАННЫЕ
  структуры, не YAML-тексты: ссылки рёбер уже разрезолвлены внутри своего файла,
  кросс-файловая неоднозначность имён в ссылках исчезает как класс.
- API-расширения (аддитивно, без слома контракта):
  `ImportPreviewIn.contents: list[str] | None` (старый `content` жив);
  `ImportPreviewOut` + `files/merged/conflicts/warnings`;
  `ProjectCreate.import_yamls: list[str] | None` (старый `import_yaml` жив).
  Pydantic → `npm run gen:api` в том же коммите.
- `seed_import` НЕ меняется — ест результат мерджа.

### Семантика мерджа (детерминированная, порядок файлов почти не важен)

- Идентичность узла: нормализованное имя (casefold, схлоп пробелов) в пределах
  ОДНОГО смердженного родителя — т.е. по пути «Система / Сервис / …».
- Поля: «богатое побеждает» — заполненное бьёт пустое (описание заглушки из
  чужого файла проигрывает родному описанию); оба заполнены и различаются →
  берём первое по порядку файлов + строка в конфликты отчёта; shape/status:
  не-дефолт бьёт дефолт, два разных не-дефолта → конфликт; external при
  расхождении → true + конфликт (external обычно ставят осознанно).
- children объединяются рекурсивно (та же идентичность).
- Рёбра: перевешиваются на слитые узлы; дедуп ТОЛЬКО точных дублей
  (src, dst, label, technology); одна пара концов с разными label из РАЗНЫХ
  файлов → предупреждение (в одном файле мульти-рёбра осознанны).
- Fuzzy-похожие имена сиблингов из разных файлов (difflib ratio ≥ ~0.78) —
  НИКОГДА не склеиваем сами (ложная склейка хуже дубля), только предупреждение
  «возможно, одно и то же». >1 корня при >1 файле → предупреждение с подсказкой
  «приведите имя системы к одному».
- Лимиты суммарного результата = лимиты parse_import (MAX_NODES/MAX_EDGES) →
  ошибка в отчёте.
- Ошибки парсинга отдельных файлов копятся с префиксом «файл N: …».

### Промпт (главный артефакт; тело RU, планка — слабая модель)

Секции: роль и цель («опиши систему X по этому репозиторию; репозиторий может
быть одним из сервисов — систему целиком, детально только видимое здесь»);
ДЕТЕРМИНИРОВАННЫЙ порядок разведки (compose/k8s/terraform → манифесты сборки →
точки входа → конфиги подключений → README; запреты: lockfiles, node_modules/
vendor, большие файлы целиком); модель 3 слоёв (корень = система РОВНО с именем
X; контейнеры = деплой-единицы; компоненты 3–5 ключевых контейнеров, при
depth=2 — не строить); КОНВЕНЦИИ ИМЕНОВАНИЯ для мерджа (имена сервисов из
деплой-конфигов/хостов URL; чужие сервисы системы — заглушкой name+technology
без children/description; приватная БД «<сервис>-db», разделяемая — по
хосту/кластеру; SaaS по названию продукта + external: true; люди — person);
формат YAML с примером; лимиты и честность (≤12 контейнеров, ≤10 компонентов,
«не уверен — не создавай узел», рёбра только с основанием в коде/конфиге);
контракт вывода (ТОЛЬКО YAML, начиная с nodes:) + чек-лист самопроверки;
инструкция починки по списку ошибок валидатора; подсказки пользователя.

### Фронтенд

- `components/project/ImportPane.tsx` — вынесенная правая панель импорта:
  документы-чипы (добавить/убрать; файл-пикер multiple; вставка в активный),
  textarea активного документа, дебаунс-превью ВСЕХ документов, отчёт слияния,
  «Скопировать замечания для агента». Используется режимами «Импорт» и
  «Из репозитория» (одиночный файл = вырожденный случай, UX как раньше).
- `CreateProjectDialog`: mode "repo" — слева параметры промпта + «Скопировать
  промпт» (кнопка требует названия проекта — оно же имя системы), справа
  ImportPane; сабмит шлёт import_yamls.

## Тесты и гейты

- unit бэка: пример промпта проходит parse_import; матрица мерджа (заглушка+
  богатый, конфликты полей, external, дедуп/предупреждения рёбер, fuzzy-пары,
  разные корни, переполнение лимитов, 1 файл = passthrough, нечувствительность
  набора узлов к порядку файлов); эндпоинты prompt (+auth) / preview
  (мульти, префиксы «файл N») / create (import_yamls).
- Гейты кода: pytest, vitest, tsc -b, eslint — зелёные на каждом коммите.
- **Dogfood-гейт мульти-репо**: промпт прогоняется СЛАБОЙ моделью (Haiku как
  прокси DeepSeek Flash) отдельно по backend/ и frontend/ ArchMap как по «двум
  репозиториям» системы → два YAML → превью зелёное, мердж склеивает корень →
  смоук-проект создаётся и осмысленный (система/контейнеры/компоненты, внешние
  системы). Смоук-проект удалить (archive + DELETE?confirm=). Слабости промпта,
  найденные прогоном, — чинить в промпте, не руками в YAML.

## Этап B (бэклог, сюда не входит)

- **Мердж в существующий проект** («прогнал агента через месяц — обновил схему»):
  ядро уже готово — merge(export(проект), новый YAML) = тот же merge_imports
  (build_export отдаёт проект в том же формате); добавится матчинг к живым id
  ради сохранения раскладки/доков + diff-превью. Это же открывает GitHub Action
  «архитектура как код» (агент в CI обновляет схему по merge в main).
  Мостик до тех пор: полный набор YAML на руках → пересоздать проект; правки
  поверх — скачать экспорт и подмешать (N+1)-м файлом (лоссиво: раскладка и
  вложенные доки в формате не живут).
- Вложение найденных OpenAPI/Mermaid в узлы через опциональные поля формата
  (parse_import игнорирует неизвестные ключи — форвард-совместимо).
- Серверная интеграция с AI API / GitHub-App — триггер: спрос.

## Журнал: стресс-тест промпта на слабой модели (2026-07-16, afcd5a0)

12 прогонов Haiku (прокси DeepSeek Flash): example-voting-app / microblog /
full-stack-fastapi-template (публичные клоны, удалены после) + пара ArchMap;
скоринг механический (валидатор + классы ссылок + отчёт слияния).

- Обёртка вывода (fence/преамбула) — 7/8 прогонов, свойство модели: промптом
  не лечится, лечится толерантностью parse_import (fenced-блок; срез от первой
  строки «nodes:» — покрыл преамбулу без fence). 100% прогонов импортируются.
- Незакавыченное двоеточие в description — единственный класс, ломавший YAML
  (2/8): правило кавычек (формат + чек-лист + пример с закавыченным значением).
  Подтверждение: 0/3 повторов.
- shape broker на прокси/поисковиках (3/8): словарь shape. 0/2 повторов.
- ОСТАТОК (принят): фантомная БД у агента фронт-репозитория — 4/4 при всех
  формулировках запрета; яркий анти-пример («у бэкенда наверняка есть база…»)
  совпал с ухудшением — вероятный прайминг («розовый слон»), откачен; держим
  нейтральный пункт чек-листа. Страховка — отчёт слияния + человек (удалить
  дубль-узел — секунды). Дальнейший тюнинг этого класса — diminishing returns.
- НЕ повторились (не трогать без новых данных): пути рёбер от контейнера
  (0/8; суффиксный резолв остаётся страховкой), латинские имена акторов (0/8),
  лимиты/имя корня/enum'ы — нарушений 0.

Сравнение с Sonnet (2026-07-16, те же 4 сценария × 8 прогонов, текущий промпт):
8/8 валидны с первого раза, ноль ошибок YAML, обе заглушки идеальны, фантомной
БД нет, shape-мисов нет, акторы русские; семантика заметно точнее (акторы по
ролям кода, prestart-джобы, ребро «браузер → Gravatar» от актора). Обёртка
fence — 8/8 (свойство и сильных моделей; толерантность парсера обязательна).
Пути от контейнера пишет и Sonnet (11 ссылок в одном прогоне) — суффиксный
резолв несущий для всех моделей. Цена: ~×2.3 токенов и ~×5.7 времени против
Haiku (≈97k ток / ≈9 мин на репозиторий против ≈42k / ≈1.6 мин). Вывод для
пользователя: слабая модель = рабочий черновик (шум виден в отчёте слияния),
модель класса Sonnet = чистый результат с первого прогона. Промпт по итогам
Sonnet не менялся — повторяющихся ошибок нет.
