## Контекст системы (минимум)

ArchMap — веб-сервис многослойных архитектурных C4-схем. Сцена уровня =
локальные узлы + «гости» (внешние концы связей, спроецированные на уровень).
Конвейер раскладки (`frontend/src/components/graph/layout/pipeline.ts`,
Web Worker): проекция → ELK-раскладка узлов → кольца/разведения/инварианты →
**роутер стрелок** → нуджинг каналов → спрямление джогов → плашки подписей →
**T4-мини-проход** (плашки как штраф-препятствия → перепрокладка «грязных»
рёбер). Прошлый эпик (renderer-perf, слит eb4a324, журнал —
`docs/plan-renderer-perf.md`) снял −42…−83% времени БЕЗ изменения маршрутов
(байт-в-байт), добавил индикацию занятости и авто-пропуск стадий качества на
незамеренных прогонах (P10). Остаток упирается в фундамент роутера — этот
эпик.

Нормативные документы: `docs/specs/edge.md` (528 строк инвариантов E1–E83 —
функциональные требования к маршрутам), `docs/specs/perf.md` (НФТ P1–P10).
Ключевой модульный состав роутера:

- `graph/layout/orthoRoute.ts` — A* одного ребра: Hanan-сетка терминала
  (грид-линии = границы тел ± клиренс + порты всех рёбер набора), состояние =
  (вершина × направление прихода), multi-source/multi-target по 12 портам
  каждого конца (E7–E8), стоимость = длина + 40/излом + moveCost хода (E16);
  мемо направленного шага (mcScratch), генерационный скретч, flood-fill
  достижимости перед поиском, лестница клиренса 12→6→3→1.5→0 (E20).
- `graph/layout/routeAll.ts` — набор: последовательная прокладка (длинные
  первыми, E17), штрафы через `movePenalty` (кресты 200 с дедупом по точке,
  езда 1/px с кредитом легальных стволов E25, порт-конфликт 600 E12) поверх
  индекса `PlacedIndex` (сегменты по ориентации, двоичный поиск); гистерезис
  prev (E35–E37, порог 100), rip-up до фикспойнта с крышкой 3 (E38, скипы
  «чистое ребро» и envVersion), спрямление джогов (E34).
- `graph/layout/autoRoutes.ts` — мост домена: порты-кандидаты, валидация
  prev, штраф границ чужих рамок (150, E21) и чужих плашек (150, E22) как
  `extraMoveCost` — **линейный перебор прямоугольников на каждый ход**;
  distributeSlots (E11), вызов сварки.
- `graph/layout/weldTrunks.ts` — сварка стволов вееров (E78/E79): кандидаты
  расставания → **хвостовой A*** на каждого → двухступенчатое принятие;
  отсечка нижней границей длины уже стоит (Ф3 прошлого эпика).
- `graph/layout/channelNudge.ts`, `placeLabels.ts` и пр. — суммарно <1%
  времени, здесь не трогаются.

Механики стабильности, уже живущие в роутере (их ломать нельзя):
- **Гистерезис** (E35): прежний валидный маршрут удерживается до порога 100.
- **Скоуп после драга** (E82): роутятся только рёбра перетащенных узлов,
  прочие — замороженный preplaced-контекст (restoreFrozen после каждой
  пост-стадии). Санкционированный компромисс: незаскоупленные не чинятся до
  полного пересчёта.
- **Гашение осцилляций** (routeSig): битовое совпадение входов роутинга →
  результат целиком из prev (роутер не идемпотентен относительно prev).
- **P10**: прогон с ≥3 незамеренными узлами И ≥5% сцены идёт без стадий
  качества (его маршруты гарантированно выбрасываются пере-прогоном).

### Ключевые наблюдения из атрибуции

1. **T4 — 63–65% всего конвейера**, при этом его ЭКСПАНСИЙ примерно столько
   же, сколько у прохода-1 (7.0M против 7.1M на Zabbix), а времени — вдвое
   больше. Значит, дорога не структура поиска, а ЦЕНА ОДНОГО ШАГА. Главный
   подозреваемый: `extraMoveCost` в T4 несёт ЧУЖИЕ ПЛАШКИ — линейный перебор
   ~85–128 прямоугольников × borderCrossings на каждый уникальный
   направленный шаг (7.7M вызовов после мемо). В проходе-1 extraMoveCost —
   только границы рамок (единицы прямоугольников). `movePenalty` (кресты/
   езда) уже индексирован (PlacedIndex + lowerBound) и под подозрением не
   первый. Требует подтверждения V8-профилем в Ф0.
2. **Сварка хвостов — 37% экспансий Sentry** даже после отсечки нижней
   границей. Каждый хвост — отдельный `routePorts` БЕЗ грид-кэша: свежая
   Hanan-сетка (сортировка сотен координат, три typed-массива, flood-fill)
   на каждого кандидата.
3. **Маргин-ретраи — 25–29% вызовов A*** (816/2 442): лестница клиренса
   гоняет полную подготовку сетки на каждой ступени; результат flood-fill
   между ступенями не переиспользуется (ступень = другой cacheKey).
4. **Открытие уровня** — единственный сценарий, где скоуп не поможет
   (prev нет): его лечат только удешевление полного прогона и кэш маршрутов.
5. Экспансий на вызов в среднем ~2–4K при сетке ~250×250×5 состояний —
   A* на штрафном ландшафте (кресты 200, езда 1/px) сильно недооценивается
   манхэттеном и раскрывает большие области («вырождение в Дейкстру»).

## Рамки: что неприкосновенно, что правится через спеку

**Неприкосновенно** (функциональные требования, менять нельзя):
- E19 (тела — абсолютное препятствие), E15 (нет шпилек), E14 (ортогональность),
  E9 (стабы), E24 (иерархия штрафов), E12/E10/E11 (порты/рельсы/слоты),
  E25/E78/E79 (легальность и сварка стволов), E28–E34 (каналы/джоги),
  E35–E39 (гистерезис), E17 (детерминизм: тот же вход → тот же результат,
  независимость от порядка входа), E18 (связь не исчезает).
- Инварианты вида: V2.2b (двухфазный замер), own-on-first-render.

**Правится ТОЛЬКО через спеку, с явной санкцией пользователя** (кандидаты
ниже это указывают):
- E40 (состав/критерий T4-мини-прохода) — пересмотр критерия «грязный»
  и/или способа починки.
- E82 (скоуп после драга) — обобщение на любой пересчёт с валидным prev.
- perf.md — новые инварианты: кэш маршрутов, бюджет работ и ступени
  деградации.
- E16 (стоимость A*) — только в экспериментальной фазе, за флагом, при
  доказанном паритете качества.

**Гарантия качества для правок, меняющих маршруты**: прошлый эпик держал
«байт-в-байт» дампами маршрутов. Здесь часть кандидатов меняет геометрию —
для них вводится ЧИСЛОВОЙ ГЕЙТ КАЧЕСТВА (см. «Метрики качества») + приёмка
глазами пользователя на эталонах. Молча качество не жертвуется (урок и
правило прошлого эпика).

## Кандидаты оптимизации

Классы: **А** — маршруты байт-в-байт (гейт: дампы до/после на 4 сценах);
**Б** — маршруты меняются, инварианты спеки держатся (гейт: метрики качества
+ глаза); **В** — смена контракта (нужна правка спеки + санкция).

### А1. Индекс препятствий среды в extraMoveCost (главный удар по T4)

Сейчас: `autoRoutes.ts` строит на каждое ребро замыкание
`for (const r of foreignRects) ... for (const r of foreignLabels) ...` —
O(число прямоугольников) на каждый ход A*. В T4 foreignLabels — все плашки
сцены (85–128). Лечение: разложить прямоугольники в тот же интервальный
индекс, что PlacedIndex (границы по ориентации, отсортированы, lowerBound) —
ход платит только за прямоугольники, чьи границы попадают в его диапазон.
Математика штрафа не меняется → байт-в-байт. Ожидание: цена шага T4
приближается к проходу-1, T4 ~10.6с → ~5.5с на Zabbix (потолок оценки —
если V8-профиль Ф0 подтвердит, что дельта в extra; иначе переоценить).
Риск: низкий. Проверка: дамп маршрутов бит-в-бит + замер.

### А2. Грид-кэш хвостов сварки

Сейчас: 1 815–5 281 хвостовых `routePorts` без gridCache — каждая попытка
строит Hanan-сетку заново (сортировки, аллокации, flood). Хвосты меняют
только 2 порта (точка расставания, док) при НЕИЗМЕННЫХ obstacles на весь
weldTrunks. Лечение: подготовить базовую сетку (координаты от obstacles)
один раз на прогон сварки; на кандидата — слить 2–4 портовые линии с базой
(merge отсортированных списков) и переиспользовать проходимость шагов
базовой части (портовые линии добавляют свои строки/столбцы). Реализация
аккуратная (индексы сдвигаются), но семантика сетки та же: axisLines(base ∪
ports) — байт-в-байт по построению. Ожидание: срез большей части цены
подготовки хвостов; сколько именно — покажет Ф0-профиль (доля prepareGrid).
Риск: средний (арифметика индексов), закрывается дампами.

### А3. Кэш достижимости и схлоп лестницы клиренса

(а) Результат flood-fill («достижимо при этом margin») кэшировать в
PreparedGrid — повторные вызовы того же терминала на той же ступени
(rip-up, гистерезис-сравнения) не гоняют BFS заново. (б) При недостижимости
на ступени N сразу проверять достижимость на следующих ступенях ТЕМ ЖЕ
flood-fill (сетка ступени уже строится при ретрае — но можно решить дешевле:
недостижимость почти всегда «жёсткая», до margin=0) — кандидат: прыгать
сразу на margin, где flood говорит «достижимо», не строя промежуточные A*.
Результат тот же по построению (A* на недостижимой ступени всё равно вернул
бы null и рекурсировал). Байт-в-байт. Ожидание: −816/−2 442 лишних
подготовок; вклад умеренный.

### А4. Микрооптимизации по V8-профилю Ф0

Куча MinHeap на обычных массивах → typed-куча со скретчем; аллокации
замыканий в горячем цикле; прочее, что покажет профиль. Только то, что
байт-в-байт и дёшево в реализации. Ожидание: 10–20% сверху, не больше.

### Б1. Кэш финальных маршрутов вида (лечит «открытие уровня»)

Наблюдение: механика гашения осцилляций УЖЕ умеет «входы совпали по битам →
результат целиком из prev», но живёт только внутри смонтированной сессии
холста. Открытие уровня = prev пуст = полный прогон, хотя пользователь
чаще всего возвращается к сцене, которую уже считали (персист раскрытий
усугубляет: тяжёлая сцена пересчитывается при каждом возврате на карту —
вывод №3 базлайна Ф0 прошлого эпика).

Лечение: персистный кэш `{routeSig, autoRoutes, edgeHandles,
labelPlacements}` пер (проект, вид). При открытии: посчитать routeSig
фактических входов (это дёшево — до стадий качества); совпал с кэшем →
взять маршруты из кэша, СТАДИИ КАЧЕСТВА НЕ ГОНЯТЬ ВООБЩЕ; не совпал →
полный прогон, кэш перезаписать. В routeSig добавить ROUTER_VERSION
(константы/алгоритм меняются → кэш честно протухает).

Свойства: при валидном кэше результат = байт-в-байт то, что посчитал бы
полный прогон (кэш кладётся только из полного прогона с тем же sig) — это
НЕ деградация качества. Меняется только свежесть: маршрут может приехать из
кэша, посчитанного прошлой сессией. Требует нового инварианта в perf.md
(предложение: P11 «кэш маршрутов вида»), решения «где хранить»
(localStorage пер-браузер ИЛИ view_state на бэке — вопрос пользователю) и
инвалидации при конкурентных правках (routeSig сам ловит любое изменение
входов — чужая правка меняет позиции/состав → sig не совпал → пересчёт).
Ожидание: повторные открытия карт/страниц — из секунд в сотни мс (остаётся
ELK + проекция + сборка). Первое в жизни открытие сцены не ускоряет.
Риск: объём (десятки КБ на вид), сериализация Map, дисциплина версии.

### Б2. Инкрементальный скоуп любого пересчёта с валидным prev (лечит раскрытия)

Обобщение E82 (скоуп после драга) на раскрытие/сворачивание/любой re-run,
где есть prevRoutes: конвейер сам вычисляет «грязную зону» diff-ом против
прошлого прогона (LevelGraph передаёт prevPositions/prevSizes — они у него
есть) и роутит только:
- рёбра с изменённым концом (позиция/габарит/появление/пропажа узла);
- рёбра с инвалидным prev (валидация в buildAutoRoutes уже это ловит);
- рёбра, чей prev-маршрут пересекает грязную зону (объединение старых+новых
  тел сдвинутых узлов и новых/умерших рамок ± клиренс);
- ЗАМЫКАНИЕ ПО СТВОЛАМ: ребро в скоупе → его собратья по фактическому порту
  (делят p0 или pN) тоже в скоупе — иначе перепроложенный лидер оставляет
  followers «расслоённым» стволом (сварка followers вне скоупа не гоняется).
Остальные — preplaced/frozen: механика E82 (restoreFrozen) готова.

Компромисс — ровно тот, что уже санкционирован для драга (E82):
незаскоупленные рёбра не подбирают опосредованные улучшения до полного
пересчёта («Переразложить», открытие без кэша). Спека: E82 расширяется
(или новый E84) — правка с санкцией.

Ожидание: раскрытия на тяжёлых сценах платят за окрестность раскрытия, а не
за всю сцену. На сценарии пользователя (раскрытия на карте Zabbix server:
9.9/10.2/15.0с после прошлого эпика) — кратное снижение, точная доля
затронутых рёбер меряется в Ф0 (счётчик размера скоупа).
Риск: кумулятивный дрейф качества после серии раскрытий (лечится полным
пересчётом по «Переразложить»; вопрос пользователю — нужен ли фоновой
полный пересчёт-«уборка» после серии инкрементальных, и когда).

### Б3. T4-пересмотр (после А1, если T4 всё ещё дорог)

Варианты по данным Ф0 (счётчики: сколько рёбер dirty, какова глубина вреза):
- **Б3а. Ужесточить критерий «грязного»**: сейчас dirty = любое касание
  прямоугольника плашки (pathCrossesRects). Вариант: врез глубже порога
  (например, линия проходит ближе N px к центру текста), касание уголком —
  не повод перепрокладывать. Меньше dirty → меньше прогонов. Меняет
  результат (рёбра под краем плашки остаются) — глаза пользователя.
- **Б3б. «Сначала подвинь плашку»**: конфликт чинить пере-размещением плашки
  жертвы (повторный placeLabels с запретом зоны конфликта) и только при
  неудаче — перепрокладкой ребра. Дёшево (размещение — миллисекунды),
  меняет визуал (плашка уезжает в leader чаще).
- **Б3в. Патч-роутинг**: перепрокладывать не всё ребро, а окно из сегментов
  вокруг вреза (между ближайшими изломами, мини-сетка окна). Экономия ×N от
  длины ребра; глобальная оптимальность объезда теряется. Самый сложный из
  трёх.
Спека: E40 правится в любом из вариантов. Приоритет между а/б/в — по
данным Ф0 и вердикту скептика.

### Б4. Общая сетка набора (эксперимент)

Сейчас сетки терминалов почти совпадают (одни obstacles, одни extraXs =
порты всех рёбер), различаясь только стаб-точками своего ребра; T4 к тому
же строит сетки заново с БЕДНЕЕ extraXs (порты только dirty-рёбер).
Кандидат: единая сетка (base + стаб-линии всех рёбер) на весь routeAll и
шаринг hPass/vPass/hMemo между рёбрами и проходами. Не байт-в-байт: линий
больше → пространство путей другое (не хуже, но другое); поиск на более
плотной сетке дороже за вызов — суммарный эффект НЕОЧЕВИДЕН, только замер.
Держать как эксперимент Ф5, не в критическом пути эпика.

### В1. Детерминированный бюджет работ + ступени деградации (гарантия P2)

Гарантию «≤5с на предельной сцене» константные оптимизации не дают —
патологическая сцена всегда найдётся. Лечение: БЮДЖЕТ, но НЕ ПО ВРЕМЕНИ
(время недетерминировано → маршруты зависели бы от машины/нагрузки, E17
умер бы), а ПО СЧЁТЧИКУ РАБОТ — экспансиям A*, детерминированным при том же
входе. Бюджет сцены = f(узлы, рёбра) из спеки; конверсия в секунды — по
замеренной скорости ~1.3–1.9M экспансий/с (эталонное железо, актуализируется
Ф0-профилем).

Нормативные ступени деградации при исчерпании (порядок = от дешёвого к
больному, фиксируется в spec):
1. отключить сварку стволов (вееры остаются параллельными — легальны);
2. отключить rip-up (жертвы порядка остаются с лишними крестами);
3. T4 не запускать (линии сквозь плашки остаются);
4. cap экспансий на один вызов A* → при превышении маршрут фолбэчится
   дешёвым поиском без контекстных штрафов (только тела; E19/E15/E14
   держатся — теряются только уклонения от крестов/езды).
Ступень объявляется пользователю (разовый тост «схема упрощена» — как P8).
Спека: новые инварианты perf.md (P12 бюджет, P13 ступени; формулировки —
частью фазы). Важно: после Ф1–Ф3 на эталонах бюджет НЕ должен срабатывать —
он страховка хвоста распределения, не рабочий режим.

### В2. Взвешенный A* (эксперимент, за флагом)

h × w (w≈1.2–1.5) против «вырождения в Дейкстру»: субоптимальность
ограничена множителем w, экспансии падают в разы на дальних целях. Меняет
маршруты (изломы/объезды могут стать чуть дороже оптимума). Строго за
флагом, только эксперимент Ф5 с метриками качества и глазами; в прод — лишь
при незаметной деградации и заметном выигрыше. Отдельно замерить дешёвую
допустимую подтяжку h (минимальные неизбежные переходы границ рамок до
цели — прекомпьютится в hMemo) — она байт-в-байт по оптимальности... но
НЕ по тай-брейкам (равные стоимости могут разрешиться иначе) — значит,
тоже класс Б, мерить.

### Отклонено на входе (чтобы не возвращаться вслепую)

- **Роутинг вееров деревьями Штейнера** (вместо пост-сварки): полный
  редизайн E78/E79, риск несоизмерим с эпиком.
- **Параллелизм воркеров** (пул для хвостов сварки): детерминизм сохраним
  (сбор в фиксированном порядке), но сложность/выигрыш плохие, пока не
  исчерпаны А/Б; вернуться, только если после Ф1–Ф4 цели не взяты.
- **WASM-перенос A***: переписывание выстраданного модуля, не в этом эпике.
- **weld:false в T4** — уже отвергнуто прошлым эпиком (−14% времени, но
  37/85 маршрутов меняются).

## Метрики качества (гейт для классов Б и В)

По дампам маршрутов реплея (routes-*.json) + существующим инструментам
(`scripts/arrow-metrics.mjs`, `graph/layout/arrowMetrics.ts`) собрать единый
отчёт качества сцены:
- кресты (дедуп по точке — семантика E23), нелегальная езда px (E25),
  изломы, суммарная длина;
- маршруты сквозь тела (обязано быть 0 — E19), сквозь плашки (T4-остаток),
  порт-конфликты (E12);
- развороты/шпильки (обязано быть 0 — E15).
Гейт правки класса Б: ни одна метрика «обязано быть 0» не ломается;
кресты/езда/изломы — не хуже базлайна больше чем на согласованный допуск
(предложение: +2% суммарно по сцене, обсуждаемо); плюс приёмка глазами
пользователя на эталонах. Класс В: метрики снимаются на КАЖДОЙ ступени
деградации и фиксируются в спеке как ожидаемая цена ступени.

## Фазы

- **Ф0 — измеритель v2 + базлайн эпика.** Закоммитить replay-prof.ts (из
  scratchpad) в репо; расширить трассу: дельты weldTails/weldExpansions/
  marginRetries/размер скоупа/|dirty| T4 по стадиям; V8-профиль обоих корней
  (подтвердить гипотезу А1 про extraMoveCost — ДО written кода); отчёт метрик
  качества по дампам (базлайн качества); зафиксировать базлайн времени на
  4 сценах (zabbix-root, sentry-root, zabbix-server-level, «Опрос и сбор»/
  «Консьюмеры Kafka»). Гейт: таблица атрибуции в этом файле.
- **Ф1 — класс А (байт-в-байт).** А1 → А3 → А2 → А4 по одному коммиту,
  каждый с гейтом «дампы маршрутов бит-в-бит на 4 сценах + полный сьют +
  замер». Ожидание (грубо, уточнит Ф0): Zabbix-корень 16.7 → 8–10с,
  Sentry 25 → 14–17с.
- **Ф2 — кэш маршрутов вида (Б1).** Дизайн хранения (вопрос пользователю:
  localStorage или view_state), ROUTER_VERSION в sig, инварианты perf.md
  (P11), тесты (протухание по sig, версия, конкурентная правка). Гейт:
  повторное открытие тяжёлой карты — сотни мс; маршруты из кэша байт-в-байт
  с полным прогоном (тест).
- **Ф3 — инкрементальный скоуп (Б2).** Дифф грязной зоны в конвейере,
  замыкание по стволам, spec-правка E82→обобщение. Гейт: сценарий
  пользователя (три раскрытия на карте Zabbix server) — кратное снижение;
  зонд дрейфа (возврат узла/повторное раскрытие) не хуже текущего; метрики
  качества в допуске; глаза.
- **Ф4 — T4-пересмотр (Б3, если после Ф1 T4 ≥ ~25% прогона).** Выбор
  а/б/в по данным; spec-правка E40. Гейт: метрики + глаза.
- **Ф5 — бюджет и ступени (В1) + эксперименты (Б4/В2 по остатку времени).**
  Бюджет по экспансиям, ступени, тост, spec perf.md; синтетическая
  перегруженная сцена для теста ступеней. Гейт: на эталонах бюджет не
  срабатывает; на синтетике ступени дают ≤5с-эквивалент детерминированно.
- **Ф6 — контроль.** Полная батарея perf-probe против базлайна Ф0 обоих
  эпиков; вердикт P2/P7 в spec; обновление tasks.md/памяти; приёмка
  пользователем.

Порядок Ф2 ↔ Ф3 обсуждаем: Ф2 бьёт «открытия» (самая частая операция),
Ф3 — «раскрытия» (самая больная жалоба). Оба нужны.

## Риски и уроки (перенесены из прошлого эпика + новые)

- Атрибуция ПЕРЕД кодом: гипотеза А1 (extra в T4) обязана подтвердиться
  V8-профилем до реализации — догадки в прошлом эпике дважды врали.
- Замеры на тихой машине; первый прогон vite-node ест перекомпиляцию;
  cwd-ловушка (патчи из корня, vite-node из frontend/).
- Роутер — самый выстраданный модуль: не-байт-в-байт правки только с
  метриками + глазами; жертвы утверждает пользователь.
- Гистерезис/скоуп/осцилляции — троица стабильности: любой новый кэш/скоуп
  обязан пройти зонд дрейфа (возврат к исходному состоянию → маршруты
  возвращаются/не осциллируют).
- Кэш маршрутов (Б1) — новый класс багов «протухший кэш»: единственная
  защита — дисциплина routeSig (все входы + версия). Любая правка констант
  роутера без бампа ROUTER_VERSION = тихая рассинхронизация.
- Бюджет (В1) по времени вместо счётчика — ловушка недетерминизма; по
  счётчику — ловушка «бюджет сработал у пользователя, не воспроизводится у
  нас» (лечится логом ступени в тосте/консоли).
