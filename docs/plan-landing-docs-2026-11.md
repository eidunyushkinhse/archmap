## 0. Принцип (решение владельца 2026-11-01)

- Документация исходит из целей пользователя: «как закрыть мой запрос продуктом». Страница
  отвечает на вопрос, с которым читатель на неё пришёл, шагами в продукте.
- `docs/docs-delta.md` — проверочный список фактов, не оглавление. К каждой записи дельты
  вопрос «какую цель читателя это закрывает?». Нет цели — на сайт не идёт (список таких записей
  в §3.4, чтобы фильтр был виден и проверяем).
- Сайт не растёт от починок: одна новая страница (глоссарий), остальное — правки существующих.
- Перед выкладкой — ревизия архитектором (§3.6) по критериям владельца, затем приёмка владельца
  на локальном сайте, потом выкладка.

### 2.4 Моки лендинга

Решение владельца 2026-11-01: раздел статусов показывает придуманный продукт, где один модуль
заменяется другим (не больше четырёх объектов), раздел развёртывания показывает небольшую систему
(пять-шесть объектов на своих площадках). Моки правдоподобные, но ёмкие. Оба проекта живут в
dev-базе рядом с эталоном и нужны для будущих пересъёмок; пропадут — воссоздаются из фикстур.

| Проект | Фикстура | Что снимает |
|---|---|---|
| «Уведомления заказов» («Переход с прямой SMS-рассылки на центр уведомлений») | `scripts/fixtures/landing-status.yaml` | ролик `vid-status` и постер `shot-status.png` |
| «Онлайн-касса» («Приём платежей и фискализация чеков») | `scripts/fixtures/landing-deploy.yaml` | врезка `crop-deploy-canvas.png` |

Пересоздание (dev-стек поднят):

1. Ввоз: «Новый проект» → «Импорт» → файл фикстуры, имя и описание из таблицы; или
   `POST /api/v1/projects/import-unified` (multipart: `files`, `name`, `description`). После ввоза
   `GET /api/v1/nodes/alerts` с `X-Project-Id` — все списки пусты.
2. «Онлайн-касса»: канал `receipts.new` ввоз заводит заготовкой по связям; вид `queue`,
   гарантию `at-least-once` и описание дописывает `PATCH /api/v1/nodes/{RabbitMQ}/channels/{id}`
   (формат YAML полей канала не несёт).
3. «Уведомления заказов», корень карты: «Переразложить уровень», затем перетаскиванием ромб.
   «Заказы» слева, «SMS-провайдер» справа на той же высоте, «Центр уведомлений» над
   «SMS-рассыльщиком» в среднем столбце. Ряды держать близко: при большом разносе по вертикали
   роутер уводит стрелки в верх и низ блоков, и поток слева направо теряется.
4. «Онлайн-касса», холст «Развёртывание»: рамки площадок не таскаются (их рамка строится по
   карточкам), двигаются карточки. Сверху RabbitMQ (ВМ брокера), в среднем ряду Кластер A
   (Веб-кабинет, API кассы 1/2) и Кластер B (API кассы 2/2, Фискализатор), снизу БД чеков
   (Managed PostgreSQL); RabbitMQ и БД по центру ряда. Двигать по одной карточке так, чтобы
   рамки не наезжали друг на друга: перекрытие рамок раздвигает их, и карточка уезжает.
5. Съёмка: `node scripts/landing-shots.mjs --only status --project "Уведомления заказов"`,
   `node scripts/landing-shots.mjs --only deploy-canvas --project "Онлайн-касса"` и под Xvfb
   `node scripts/landing-videos.mjs --only status --project "Уведомления заказов"` (проверки
   ролика: первый и последний кадр совпадают, PSNR выше 45 дБ; yuv420p; размер). Окно сцены
   status — 1400×600 (21:9, как рамка раздела; рамка той же ширины, что у hero, поэтому интерфейс
   на лендинге того же порядка величины), холст около 1; ролик снимается отдельным прогоном,
   масштаб 1,35 даёт кадр 1888 px. Сцена мока
   снимается только на своём моке, прогон по «Ярмарке» её пропускает (таблица `MOCKS` в обоих
   скриптах). Готовые файлы — в `landing-live/landing-shots/`.

Что показал продукт (2026-11-01): внешняя система на холсте «Развёртывание» не рисуется (Р42:
её размещение не ведётся), поэтому «Оператор фискальных данных» в группу «Размещение не указано»
не попадает, и группы на кадре нет. Подписи связей на кадре развёртывания скрыты (сцена жмёт
тумблер): семь подписей, три из них повторяют соседние, ложатся на плашки площадок.

### 3.2 Цели читателя-архитектора

| Цель читателя | Страница | Что меняется | Факты дельты |
|---|---|---|---|
| Понять слова продукта и решить, что в моей системе система, контейнер и компонент | НОВАЯ `user/glossary.md` «Глоссарий» (решение владельца: отдельная страница-словарь, на которую ссылаются страницы-инструкции; в руководстве пользователя последней, потому что его читают все роли; у каждого термина якорь `{#…}`) | Термины продукта по одному абзацу: проект, объект и уровень, система, контейнер, компонент, база данных, брокер, пользователь, внешний объект, схема логики, спецификация, конфигурация, источник, площадка и размещение, статус страницы, версия документации, рекомендация, бизнес-процесс. У шести типов — развёрнуто: что это в смысле C4, как ArchMap узнаёт тип (поле «Тип» при создании, строка «Тип» в свойствах, первый вложенный объект решает за родителя), как выбрать (контейнер — отдельно запускаемое приложение, компонент — часть его кода, система — то, что состоит из систем и контейнеров, внешний объект — внешняя система), у кого какая документация (схемы логики — у компонента или контейнера без компонентов; спецификация, конфигурация и размещение — у контейнера; у системы только структура), что пользователь живёт вне системы, а у базы данных, брокера и пользователя вложенных объектов не бывает. Что делает ArchMap, когда документация не на месте («Перенести документацию», «Собрать с компонентов») и когда файл кладёт базу в контейнер (поднимает уровнем выше с замечанием) — одной фразой со ссылкой на инструкцию. 80–120 строк, без снимков. Ссылки на якоря глоссария — из `user/levels.md`, `architect/nodes.md`, `architect/alerts.md`, `architect/deployment.md` и других страниц таблиц | Ф1, Ф3а, Ф4, Ф5, Ф8, Ф12, Ф13а, Ф13б |

### 3.5 Порядок исполнения

Один исполнитель (opus-xhigh), последовательно, в щадящем режиме: (1) пересев стенда и снимки;
(2) глоссарий; (3) правки страниц по таблицам §3.1–3.2 с ссылками друг на друга;
(4) гейт `npm run check` и `npm run build`; коммиты в `archmap-docs` по страницам. Задание
исполнителю несёт §0, таблицы и §3.4 целиком и критерии ревизии §3.6 как правило письма.
Лендинг (§2) — отдельное задание тому же исполнителю после сайта или параллельно по решению
владельца; кадры и ролики требуют поднятого стека на копии эталона.

### 3.6 Ревизия перед приёмкой (архитектор, по диффу `archmap-docs`)

Критерии владельца, по каждой изменённой странице:

1. Каждый новый абзац отвечает на вопрос, с которым читатель пришёл на эту страницу. Абзац «есть
   такая кнопка» без вопроса читателя — снять.
2. Шаги описывают действия читателя, а не устройство продукта; запрет формулируется путём
   («база данных кладётся рядом с контейнером»), а не отказом («в контейнер нельзя положить базу»).
3. Слова продукта, без внутреннего словаря («алерты», «доки», «спека», «гость», «рамка»).
4. Числа (классы, инструменты) только там, где страница их уже называла.
5. Тексты окон и ошибок — только те, которые читатель увидит, выполняя шаг.
6. Двоеточие только когда вторая часть раскрывает первую; без многоточий; без «описывают у»,
   «их место у», «живут».

Итог ревизии — список снятых и переписанных мест в отчёте владельцу; затем приёмка владельца на
локальном сайте (`npm run dev` → :8800), правки по списку, выкладка.
