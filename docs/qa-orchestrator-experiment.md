# Эксперимент: Haiku-оркестратор «строитель + скептик» одним промптом (2026-08-15)

Вопрос: жизнеспособна ли фича «один промпт, агент пользователя сам спавнит
субагентов-строителя и скептика», или слабая модель развалит оркестровку /
«сессия защитит свою выдумку». Стенд: клон Zulip, headless Haiku, один
оркестраторный промпт (25.7К знаков): чеклист из 6 шагов, оба под-промпта
вшиты дословными блоками, передача — через файлы (archmap-orch/), правило
«ты маршрутизатор, не судья; непогашенное — дословно в финальный ответ»,
кап 2 круга аудита. Строительный блок — штатный импорт-промпт ArchMap;
скептик-блок — прототип (недоверенная модель, докажи каждый узел/связь по коду,
не чини — только отчёт сомнений с файл:строка).

## Механика — 5 из 5, оркестровка состоялась

| Замер | Результат |
|---|---|
| Спавн субагентов | **4 Agent-вызова ровно по чеклисту** (строитель → скептик → починка → скептик); инструмент нашёл сам через ToolSearch; лишней самодеятельности ноль (Read — только отчёты скептика, по шагу 4) |
| Дословность блоков | 22 454/22 456 и 3 158/3 160 байт — **по одному символу расхождения на файл** (типографская кавычка „X“→„X" при перепечатке Write-ом). Семантика цела; для полной гарантии в промпт стоит добавить «сохраняй через терминал (cat/heredoc), не перенабирай» |
| Изоляция | Субагенты — отдельные сессии со своими транскриптами; модель всех пятерых — чистый Haiku |
| Петля | Два полных круга; строитель РЕАЛЬНО применил правки круга 1 (направления связей исправлены в YAML) |
| Не-арбитраж | Обе строки последнего отчёта скептика процитированы в финальном ответе дословно; непогашенные сомнения задекларированы, не похоронены |

## Качество — данные честные и смешанные

- **Скептик ловит класс, невидимый валидатору**: 5 сомнений круга 1 — направления
  связей с внешними сервисами (Giphy/Tenor зовёт фронтенд, а не webhook-receiver;
  Zoom/Webex — api-endpoints; Jitsi-связь не подтверждена) — все с файл:строка,
  все справедливы, все исправлены строителем на круге 2.
- **Скептик и сам конфабулирует**: сомнение круга 2 «tornado не потребляет из
  RabbitMQ, доставка через HTTP POST» — ЛОЖНО (tornado потребляет notify_tornado:
  runtornado.py:116-124; HTTP-путь — про создание очередей). Второе сомнение
  круга 2 (email-sender привязан к deferred_work вместо email_senders) — верное.
  Оба честно вынесены в финал как неразрешённые.
- **Главный приз не разыгрался из-за дисперсии**: в этом прогоне строитель вовсе
  не нарисовал Elasticsearch (модель вышла скромнее и трезвее: 37 узлов/31 связь,
  4 честных хранилища). Проверка «скептик убивает ES-класс» ждёт прогона, где
  строитель его снова выдумает.
- Финальный YAML валиден для ArchMap (превью: 0 ошибок, 9 предупреждений штатных
  классов — оркестраторный цикл не включал валидаторную петлю ArchMap).

## Выводы для дизайна фичи

1. **Оркестратор на слабой модели жизнеспособен**, если промпт — чеклист с файловой
   передачей и правилом маршрутизатора. Предсказанные режимы отказа (сделает сам,
   перескажет, похоронит) не реализовались ни один.
2. Опасение «сессия защитит выдумку» в оркестраторной схеме снято изоляцией
   субагентов; настоящий новый риск — **ложные сомнения скептика**: слабый скептик
   конфабулирует симметрично строителю. Лечение то же, что Ф8ж: порог уверенности
   в промпт скептика («не уверен в доказательстве — не пиши сомнение») + честный
   вынос неразрешённого пользователю (уже работает).
3. Открытый вопрос интеграции: куда встроить круги скептика относительно
   валидаторной петли ArchMap (превью/замечания). Естественный порядок: скептик —
   ДО первой загрузки (семантика), валидатор — после (согласованность), но это
   уже дизайн фичи, не эксперимента.
