# Разведка: MCP-сервер и всё, что видит агент — эпик «Роли узла: система · контейнер · компонент»

Дата: 2026-10-28. Только чтение: правок, тестов, сборок не было. Ссылки — путь:строка на
состояние main 6869acc3. «Агент» — ИИ-агент пользователя за MCP (локальный stdio или /mcp).

## 0. Коротко

- В MCP роль ляжет без новых инструментов: аргумент у `archmap_create_node`/`archmap_update_node`,
  маркер в `render.tree`/карточке, пересчёт `archmap_deployment` и `archmap_alerts`. Счётчики
  37/34/17 не меняются. Версия 0.10.0 → 0.11.0.
- Главная терминологическая мина. Слово **«роль»** и ключ **`role`** уже заняты свободной подписью
  узла: аргумент MCP, YAML, UI «Роль», предупреждения догрузки «поле «роль»», в демо-шаблоне
  `role: система`. Ключ **`kind`** тоже занят: шапка `%% archmap-kind: operation | worker`,
  `kind` площадки, `kind` канала. Нужно имя, которое агент не спутает ни с тем, ни с другим.
- Сегодня агент узнаёт «контейнер» только по отступу в дереве `archmap_schema`. Ни карточка,
  ни дерево не говорят ни «есть дети», ни сколько их. Роль бэкенд должен отдавать **вычисленной**
  (effective) в NodeResponse. MCP не должен второй раз реализовывать «ближайший контейнер».
- В ответе агенту четыре места, где правило уже зашито **глубиной**, а не ролью:
  `sync_plan._CONTAINER_DEPTH = 2` (по умолчанию синк пропускает узлы глубже второго уровня);
  `FACT_FAMILY` по форме (`service → config`); `_site_members`/«Без размещения» по `has_children`;
  слой 3 в промпте ввоза.

## 4. Синк и повторные прогоны через MCP

**Как устроено сейчас:**
- Синк (`sync_plan.py:238–261` `_diff_fields`) правит только перечисленные поля:
  - `role`/`technology` — «богатое побеждает» (заливает пустое);
  - `shape`/`status` — «не-дефолт бьёт дефолт»;
  - имя и описание — по политике;
  - `source_ref` — всегда.

  Нового поля в списке нет, поэтому синк его **не тронет** ни при создании, ни при обновлении.
- Слой компонентов отрезается **глубиной** прогона (`_CONTAINER_DEPTH = 2`, sync_plan.py:36–38,
  264–273, 345–355), а не ролью. Рёбра к пропущенным узлам выбрасываются (sync_plan.py:385–386).
- Догрузка (`unified_into.py:148` `_FILLABLE = description, role, technology`) — fill-only,
  спор с живым по умолчанию «оставить моё».
- Мердж нескольких YAML — «богатое побеждает», для enum «не-дефолт бьёт дефолт»
  (import_merge.py:66, 390, 585–588).
- Парсер YAML молча игнорирует неизвестные ключи (import_yaml.py:436).

**Что будет с ролью:**

| сценарий | без доработки синка | риск |
|---|---|---|
| YAML прогона роли не несёт (старый промпт, depth=2, ручной YAML) | роль живого узла не трогается | безопасно. Новые узлы-родители получают дефолт (см. камень 2) |
| YAML несёт `container`, живой — дефолт «система» после миграции | синк поле не знает, и роль **не выставится**, хотя агент смоделировал правильно и превью молчит | «не сможет выставить» |
| Добавили поле с семантикой «не-дефолт бьёт дефолт», как у shape | YAML `container` перебьёт и миграционный дефолт, и ЯВНЫЙ выбор человека «система» | «молча перебьёт решение человека» |
| Добавили поле в «богатое побеждает» при хранении без null (дефолт «система» записан в каждую строку) | заполнять нечего: «пустого» нет | то же «не сможет выставить» |
| Синк по умолчанию (без sync_components) на YAML с контейнером и его компонентами | контейнер создаётся ЛИСТОМ (дети отрезаны глубиной), роль `container` у листа хранить по гипотезе нельзя | роль теряется. Позже прогон с компонентами повесит детей на узел с дефолтной ролью «система» |
| Проект глубже двух уровней (контур → система → контейнер) и YAML, который это отражает | контейнеры на глубине 3 синк по умолчанию пропустит как «компоненты» | MCP-описание `sync_components` («без флага — только системы и контейнеры») станет ложью |
| Экспорт → правка агентом → синк | если build_export пишет поле, а синк его не читает, круг теряет роль | нарушение обещания `archmap_export` («то, что подают обратно на импорт и синк», tools.py:1579–1581) |

**Рекомендации для синка** (это область бэкенда, но формулировки видит агент):
1. Хранить роль трёхзначно: `NULL` (не решено, ведёт себя как дефолт), `system`, `container`.
   Тогда «богатое побеждает» работает как у `role`: синк, мердж и догрузка заполняют только
   `NULL`, явный выбор человека не трогают, расхождение идёт строкой «Расхождения (решены
   правилом)» (tools.py:790–795).
2. Резать слой компонентов **ролью** («дети контейнера»), а глубину оставить запасным путём для
   YAML без поля. Тогда слова `sync_components` в MCP и UI (SyncRepoModal.tsx:55–57 «внутреннее
   устройство сервисов») станут правдой.
3. В плане синка печатать новое поле русским словом (как «канал ←» в tools.py:737–756).
4. Важно для дефолта у существующих BYOA-проектов (вопрос владельца №3). YAML прогона **уже
   кодирует роль глубиной**: слой 2 с детьми — контейнер (import_prompt.py:302; это же правило
   `_CONTAINER_DEPTH` в синке). Подсказка «узел второго слоя с детьми → контейнер» работает для
   проектов, собранных промптом ввоза. В федерации под общим узлом сдвигается на уровень.

## 6. Подводные камни, открытые вопросы, порядок фаз

### Камни (от неочевидного к очевидному)

1. **Коллизия имён `role`/`kind`** (§2.1). Две «роли» в карточке, в правке и в отчёте догрузки
   («поле «роль»», unified_into.py:139). Четыре разных `kind` в одном прогоне агента:
   `%% archmap-kind`, площадка, канал, узел. Слабая модель смешает. Решить до контракта.

2. **Создание сверху вниз и дефолт «первого ребёнка».**
   - Агент через MCP создаёт родителя раньше детей: `archmap_create_node`, затем дети с
     `parent_id`. Синк по умолчанию создаёт контейнер без компонентов (дети отрезаны глубиной).
   - Если «у листа роль не задаётся», объявить контейнер в момент создания нельзя.
   - Когда появится первый компонент, родитель получит дефолт «система». Его спека, конфигурация
     и размещение в ту же секунду загорятся перевёрнутым AL24.
   - Размещение спрячется: уже сегодня `placement_map` не считает экземпляры у узла с детьми
     (backend/app/deployment.py:114–118: «Экземпляры у самого контейнера… не в счёт»).
   - Дефолт «лист-контейнер остаётся контейнером» тоже неверен для пустой группы, которую
     создали под будущие сервисы.
   - Нужен ответ: хранить роль у листа как намерение (тогда MCP-аргумент работает при
     создании) или зафиксировать правило первого ребёнка.

3. **Расхождение версий и молчаливые потери.** Локальный MCP у пользователя отстаёт от сервера
   и наоборот; удалённый /mcp всегда синхронен.
   - (a) Новый локальный MCP со старым сервером. NodeCreate/NodeUpdate без
     `extra="forbid"` (schemas/node.py:67–122), поэтому поле роли **молча выброшено**, а ответ
     MCP «обновлён «X»: <поле>» (tools.py:1071–1072) соврёт. Лечится эхом значения из ответа.
   - (b) Сторож тела `check_node_contract` (test_tools.py:574–576) слеп по той же причине.
     Нужна проверка `set(body) <= set(Schema.model_fields)`.
   - (c) Парсер YAML игнорирует неизвестные ключи (import_yaml.py:436). Пример ввоза с новым
     полем пройдёт тест разбора, даже если парсер поле не читает. Нужен явный тест, что роль из
     примера доехала до `_ImpNode`.
   - (d) Старый локальный MCP с новым сервером. `render.alerts` читает только известные ключи
     (render.py:441–457). Если появится новый класс, агент получит «Замечаний нет — схема
     завершена», пока панель горит. Перевёрнутый AL24 он напечатает под старым заголовком
     «Контейнеры со своей документацией». Стоит заранее (фаза 0) научить рендер печатать
     незнакомые непустые списки строкой «Прочие замечания (N) — обновите MCP-сервер ArchMap».

4. **Сторожа MCP связаны с бэкендом и фронтом, а хук видит только фронт.**
   - Тесты MCP читают `SchemaAlerts.tsx`, `types/index.ts`, `nodeTerms.ts` — хук это видит
     (scripts/git-hooks/pre-commit:40–44).
   - Но тесты MCP импортируют и `backend/app/schemas/alerts.py`, `schemas/node.py`,
     `domain_types.py` через `backend("…")`. Хук их **не отслеживает**, поэтому
     бэкенд-коммит с новым классом алерта пройдёт локально и уронит CI.
   - Правку контракта алертов, панели и `render.alerts` делать **одним коммитом**. Или расширить
     `mcp_watch` модулями из `backend("…")`.

5. **У MCP нет удалений, а значит, нет и переносов.**
   - Перевёрнутый AL24 (факт контейнера у компонента или системы) агент починить не может:
     спеку не снять (у `update_node` нет `openapi_spec`), параметры не удалить
     (facts apply «удалений нет», tools.py:1916).
   - Залить заново у контейнера можно, но старое останется гореть.
   - Самое болезненное: проекты, описанные по правилу, влитому **сегодня** (6869acc3,
     «конфигурация у листовых»), после эпика получат замечания, которые чинит только человек.
   - Нужен ответ: модалка «Распределить» для людей и/или инструмент переноса (не удаления)
     для агента.

6. **Разведка → доки ломаются на контейнере с компонентами.**
   - Заглушки разведки ложатся на объект из `node:` — контейнер.
   - Промпт доков (если велеть схемы «вбок», к компонентам) положит описанные схемы к
     компонентам. Р27 сопоставляет заглушку и схему ТОЛЬКО внутри одного узла
     (docs_import.py:446–459, 497–535).
   - В итоге заглушки контейнера «не описаны» навсегда, счётчик «описано N из M» и алерт
     «объекты с неописанными схемами» врут, а сценарий README «Задокументировать монолит»
     перестаёт работать.

7. **Срез промпта доков — поддерево `node_id`** (routers/docs_import.py:75–91).
   - Для компонента в срезе нет его контейнера. Каталог ручек `param_catalog` строится по
     узлам среза, поэтому ручки контейнера агент не увидит. Он напишет «зависит от: X» и
     сообщит «конфигурация неполна», хотя ручка есть.
   - Спека с `only=api` уезжает объекту окна (docs_import.py:779–790) — компоненту.

8. **База и брокер внутри контейнера.**
   - Промпт доков сам называет «БД сервиса» вложенным узлом (docs_prompt.py:464–467).
   - По правилу «лист внутри контейнера = компонент» база станет компонентом без размещения.
     По C4 база — контейнер.
   - Нужен ответ: формы database и broker — всегда контейнер? Это частный случай вопроса №1.

9. **Логика по глубине в трёх местах MCP-клиента и сервера.**
   - `FACT_FAMILY` по форме (tools.py:167–171) у компонента покажет «КОНФИГУРАЦИЯ: (не
     описана)» и «OpenAPI-спека: нет» — ложный повод заливать факты к компоненту.
   - `_site_members`/«Без размещения» (render.py:187–291) — по `has_children`.
   - `sync_components` — по глубине (§4).
   - Всё это должно читать ЭФФЕКТИВНУЮ роль из NodeResponse. Повторять в MCP подъём к
     ближайшему контейнеру нельзя: это вторая реализация доменного правила, которая разойдётся
     с первой (принцип tools.py:351–356 у `step_docs`).

10. **Статус страницы** (approval.py:83, tools.py:1958, render.py:101–116). У C4-контейнера
    есть свои факты: спека, конфигурация, размещение. Складывать его статус только из
    компонентов значит, что согласованная спека контейнера на статус не влияет. Отказ 422
    «Статус контейнера складывается из детей» агент читает дословно.

11. **Побочные находки, не связанные с эпиком, но в тех же файлах:**
    - render.py:1411 `family=channel` при enum `channels`;
    - README:11/15/273 — устаревшие 33/36;
    - tools.py:1427 — «свои или «от контейнера»» устарело с 0.9.0;
    - `DOCS_SCOPE_ARG` (tools.py:1306) не говорит, что спека уезжает этому объекту.
