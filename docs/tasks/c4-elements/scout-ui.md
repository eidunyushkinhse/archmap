# Разведка UI — эпик «Роли узла: система · контейнер · компонент»

Область: страницы, панели и тексты интерфейса фронта (`frontend/src`, кроме движка холста
`components/graph/**`). Только чтение, 2026-10-28, по состоянию main 6869acc3.

Метод инвентаризации: grep плюс самописный снятель комментариев
(`scratchpad/scout-ui/strip.py`: TS/TSX, строки и шаблоны учитываются, `//` и `/* */` снимаются).
Сырые выгрузки лежат рядом: `scout-ui/all.tsv` (все строки с маркерами, колонка ui|cmt),
`scout-ui/ui.tsv` (только строки интерфейса вне graph/**), `scout-ui/tests.tsv` (тесты).

Счёт:
- 253 строки ИНТЕРФЕЙСА вне graph/** несут хотя бы одно слово-маркер (контейнер, компонент, лист,
  объект, узел, абстракц, промежуточн, атомарн, раскры, распредел, систем, дочерн, потомк, дети…).
  Из них «объект» — 157, «узел» — 24, «контейнер» — 33, «система» — 25, «компонент» — 11,
  «распредел» — 9, «раскры» — 10, «дочерн» — 10, «абстракц» — 3, «лист» — 1 (это «чистый лист»).
- ПРАВИТЬ ПО СМЫСЛУ придётся около 55 мест (таблицы 1.1–1.3). Остальные ~200 («объект»,
  «узел» как родовое слово) остаются.
- Ещё 13 строк интерфейса в graph/** (из них 6 по теме), они перечислены в 1.5 для сверки с
  разведчиком холста.
- Комментарии: 236 строк со словом «контейнер» в 72 файлах вне graph/** (плюс 221 в graph/**).
  Почти везде слово означает «узел с детьми». Это не тексты интерфейса, но после эпика они станут
  вводить в заблуждение, так что это долг вычитки.

переформулировать, **О** — остаётся. «⚑» — «контейнер» здесь значит «узел с детьми», и смысл
поменяется. «C4» — «компонент» уже употреблён в смысле C4 (часть контейнера).

## 2. Где в UI живёт новая роль

Сначала общий факт. Решение «узел с детьми = контейнер» во фронте принимается
**в ~25 местах вне graph/**, и каждое по-своему: `canHaveChildren(shape) && has_children`,
просто `has_children` или структурно, через `leavesOf`. Ни одно не знает роли предков. Лист
становится компонентом, только если выше есть контейнер, поэтому **роль листа фронт сам не
вычислит**: у `Node`, `GhostNode` и `AncestorRef` (types/api.gen.ts, AncestorRef = id, name,
is_external) роли предков нет. Значит, сервер должен отдавать вычисленную роль, как сегодня
`approval_effective`, а для «части контейнера X» ещё и id/имя ближайшего контейнера. Иначе
каждой точке придётся грузить всё дерево.

## 7. Подводные камни, вопросы владельцу, фазы

### 7.1. Камни (только проверенные)

1. **Слово «Роль» занято.** Инспектор (NodeInspector.tsx:221-238) и страница (NodeProperties.tsx:152-166)
   уже показывают строку «Роль» — свободный текст с placeholder «сервис, БД, брокер…». В плане синка
   `role: "роль"` (syncPlanView.ts:14), в спорах ввоза `role: «роль указана»` (questionText.ts:127),
   в YAML демо `role: система` у корня Ярмарки (c4.yaml:4). Новый контрол нельзя назвать «Роль»,
   а слово «система» уже стоит значением свободной роли.
2. **Смена роли — не косметика.** Перевод родителя «система → контейнер» делает его листья
   компонентами, и их площадки, спеки и конфигурация становятся «не на месте». Обратный перевод
   делает незаконными спеку, конфигурацию и площадки самого узла. Инструментов переноса почти нет:
   параметры конфигурации в UI не переносятся вообще; «Распределить по детям» переносит только схемы
   и спеку вниз (routers/node_docs.py:232-275); N спек компонентов в одну спеку контейнера
   автоматически не сливаются. Площадки разных компонентов — объединять или спрашивать
   (PlacementConflictList для этого есть). Undo смены роли через PATCH одного поля
   (MapEditorPage.nodeFields) не вернёт побочных изменений, если сервер что-то перенёс сам.
3. **Роль листа фронт не вычислит сам.** Нужна серверная вычисленная роль (по образцу
   `approval_effective`) и ближайший контейнер, причём в NodeResponse, GhostNodeResponse,
   DeploymentNodeOut, а желательно и в AncestorRef. После смены роли меняется роль всего поддерева:
   локальная оптимистичная правка одного узла (MapEditorPage.tsx:558-561) оставит детей, дерево и
   «Развёртывание» устаревшими до перезагрузки.
4. **Интерфейс уже говорит «компонент» про детей любого сервиса**: «Добавить компонент»
   (SchemaSection.tsx:199), «Войти к компонентам» (graph/nodes.tsx:474/516), тур «Видны его
   компоненты» (tourSteps.ts:204). А дефолт роли нового родителя по концепции — «система». Тур
   (шаги 20-21) держится именно на дефолте «система»: связь в рамку — замечание, которое надо
   перевесить. Если при первом ребёнке роль начнут угадывать или спрашивать, урок тура сломается.
5. **Корневые листья и внешние.** По формуле «лист вне контейнера = контейнер» чип «контейнер»
   получат внешние системы на корне (ЮKassa, Провайдер рассылок, Служба доставки — в C4 это
   software system) и свежий «Моя система» в туре (шаг 15 называет его системой). Персоны — без роли.
6. **Эвристика по источникам ломается на самой Ярмарке.** Order API и Оркестратор заказа — один
   репозиторий `github.com/yarmarka/orders` с разными путями, но это два процесса. Компонентов в
   демо нет вообще, так что фича не показана ни в демо, ни в туре.
7. **Тексты-селекторы.** title «Раскрыть содержимое» — селектор в embed/LandingSchema.tsx:20 и в 7
   скриптах лендинга и зондов. Его не трогать.
8. **Сегодняшняя несостыковка AL24.** С 2026-10-28 AL24 считает параметры конфигурации (has_config),
   но секция «Конфигурация» у узла с детьми не предупреждает (ConfigParamsSection знает только форму,
   `allowed`), а окно «Распределить по детям» конфигурацию не переносит. Пользователь видит
   рекомендацию без пути починки. Эпик это переворачивает, но до него дыра есть.
9. **«Зависит:» без узла.** ConfigParamUsage несёт только param/doc. Обратный индекс по поддереву
   контейнера не покажет, чья это схема; нужен узел-компонент в схеме ответа.
10. **«Развёртывание» целиком на has_children**: D22 «цельный контейнер», D30 «контейнер размещается
    целиком», вход на уровень двойным кликом, подсказка «Открыть уровень», размещаемость в дереве,
    `targetsOf/leavesOf`. Тексты PLACE_LEAD/UNPLACE_LEAD называют листья «компонентами», а у системы
    это контейнеры. Площадки на холсте — псевдоузлы с `shape: "service"` и has_children
    (deploymentProjection.ts:99-121): если холст разведёт рамки по роли, их надо учесть.
11. **Технология переворачивается.** Сегодня у узла с детьми технология сводная и только для чтения
    (NodeInspector.tsx:56-62/242-246, NodeProperties.tsx:173-182). У C4-контейнера своя, компоненты
    «наследуют». Хранимая, но скрытая технология у нынешних родителей вдруг проявится.
12. **Статус страницы.** Сегодня у узла с детьми он вычисляется по детям, а ручная правка — 422
    (approval.py:83). У C4-контейнера свои факты (спека, конфигурация, площадки), страницу есть что
    согласовывать.
13. **Компонент «без статуса, технологии и формы»** (прототип) против модели: shape и status
    обязательны, фильтр «Как есть / Как будет» прячет по status, палитра создаёт ребёнка с формой.
    Скрывать ли поля, что делать с БД или брокером внутри контейнера.
14. **Перенос без подтверждений.** Перенос в дереве (nodeTree.useReparent.ts:55-66) и бросок в рамку
    на холсте меняют вычисленную роль переносимого (контейнер ↔ компонент) и тем самым законность его
    фактов, а окна-подтверждения у переноса нет.
15. **Синк считает «компоненты» по глубине** (sync_plan.py:52-54, `_CONTAINER_DEPTH`, глубина 3+).
    С вложенными системами (контур → система → подсистема) глубина врёт; галочка «Обновлять
    внутреннее устройство сервисов» (SyncRepoModal.tsx:56-58) после эпика должна значить «дети
    контейнеров».

### 7.2. Три самых неочевидных

- №1 (коллизия «Роль» и значения «система» в свободной роли),

  листа им противоречат).
