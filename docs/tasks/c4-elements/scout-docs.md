## 3. C4 и Structurizr: что обещано и как соотносится новая терминология

**Что продукт обещает сегодня.**
- spec.md:4–16: «Альтернатива Structurizr без ограничения в 4 слоя», «компоненты содержат
  субкомпоненты произвольной глубины. Structurizr это не решает», «каждый узел — либо атомарный
  компонент, либо контейнер для дочерних узлов».
- README.md:3, 9, 15: «Схемы в духе C4, но без ограничения в четыре уровня», «инструменты вроде
  Structurizr её не выражают», «Любой объект может содержать дочерние».
- Лендинг #depth (:285–290): «В C4 слой контейнеров один… контейнеры вложены друг в друга»,
  «C4: Контейнер внутри контейнера описать нельзя», «ArchMap: Контейнер может содержать
  контейнеры», лестница «L2 Контейнеры — продукты платформы, L3 Контейнеры — сервисы продукта…
  Ln+1 Компоненты».
- Сайт: user/levels.md:7 «Объект, у которого есть компоненты, называется контейнером», без
  упоминания C4.
- Промпт ввоза уже говорит на чистом C4: «Слой 1 — система… Слой 2 — контейнеры: деплой-единицы…
  Слой 3 — компоненты» (import_prompt.py:221, 301–302).

**Как это сочетается с новой моделью.**
1. Обещание произвольной глубины сохраняется, но её носитель меняется. Сегодня
   вкладываются «контейнеры» (в широком смысле), теперь вкладываются **системы**
   (контур → система → подсистема…), а контейнер и компонент становятся одним слоем каждый,
   как в C4. Лендинг утверждает «контейнер может содержать контейнеры», и это становится
   неверным либо открытым вопросом 1 (сайдкар). Лестницу и лид раздела #depth придётся
   переписать: отличие от C4 теперь в том, что **в C4 система не вкладывается в систему**.
2. Исходная постановка spec.md («компоненты содержат субкомпоненты произвольной глубины»)
   новой моделью **не покрыта**. Если узел внутри контейнера получает детей, у него нет
   подходящей роли: «система» — граница из контейнеров, «контейнер внутри контейнера» —
   сайдкар. Либо нужна третья роль (группа компонентов, абстракция внутри контейнера), либо
   постановку продукта переписывают: глубина у систем, у компонентов — нет.
3. Новая модель ближе к C4 и в развёртывании. По памяти о c4model.com (в этой разведке не
   сверялось) на диаграмме развёртывания C4 на вложенные deployment nodes ставятся
   **экземпляры контейнеров**, а не компонентов. Это прямо поддерживает решение «экземпляры у
   контейнера» и пересмотр п.14 от 2026-10-27. Там же C4 отдельно оговаривает, что контейнер ≠
   Docker-контейнер. Это стоит повторить в глоссарии: в DEPLOY.md и admin/* сайта
   «контейнер» — Docker. Большие ландшафты C4 рисует отдельной диаграммой ландшафта систем, а
   не вложением. Перед текстом лендинга эти формулировки нужно сверить на c4model.com.
4. «Structurizr это не решает» — сравнение с чужим продуктом в разведке не проверялось.
   Новый текст лучше опирать на модель C4 («в C4 одна система на диаграмме и один слой
   контейнеров»), а не на возможности Structurizr.

**Где придётся объяснить читателю из C4, что система в ArchMap вкладывается.**
- Лендинг #depth (лид и лестница), README «Зачем», spec.md «Описание продукта».
- Сайт: новая страница-понятие (система / контейнер / компонент, вложенные системы, лист
  вне контейнера — сам контейнер, БД и брокер — контейнеры) плюс заметки в user/levels.md,
  architect/nodes.md (выбор роли) и правило терминологии в README сайта.
- В продукте (код, вне этой области): подсказка «?» у контрола роли в инспекторе, легенда
  холста (рамки системы и контейнера), промпт ввоза (одна фраза о ролях), описания
  инструментов MCP.

  частей), в демо, на лендинге и на снимках сайта не видна.

  стенда и, возможно, отдельная сцена лендинга на другом проекте.
- **(Б) минимальная витрина в Order API.** Order API становится контейнером с 2 компонентами
  («HTTP API заказов» со схемами «Создание заказа» и «Получение заказа», «Планировщик
  автоотмены» со схемой «Автоотмена неоплаченных заказов», если он работает в том же
  процессе). Спека, конфигурация (MAX_ITEMS_PER_ORDER и другие) и площадки остаются на Order
  API. Строка «зависит:» у параметра покажет схемы компонентов — самая наглядная иллюстрация
  формулы. Цена: эталон «Ярмарка v2» → refresh-demo-template → тест пакета → выкатка демо →
  пересев стенда сайта → пересъёмка кадров Order API (source-props, object-logic,
  facts-config; на лендинге crop-config, возможно hero). Тур не задет.
- **(В) витрина в другом сервисе.** Например «Антифрод» (правила и ML-модель как компоненты).
  Меньше кадров задевает, но и менее заметно.

Для живой схемы (embed) при варианте (Б) достаточно перегенерировать scene.gen.ts
(landing-embed-scene.mjs) и пересобрать. Фокус «Сервис заказов» тогда покажет раскрываемый
контейнер внутри системы, а это и есть идея лестницы C4.

## 5. Подводные камни и открытые вопросы владельцу

**Камни (неочевидные).**
1. **Коллизия слов «роль» и «kind».** В интерфейсе уже есть «Тип» (shape: сервис / БД /
   брокер / пользователь) и «Роль» (свободная строка, spec.md:1534; YAML `role:`). Эпик
   называется «Роли узла», концепция предлагает «чипы роли». Ключ `kind:` в YAML проекта уже
   занят видом площадки (`deployment.sites[].kind: cloud|kubernetes…`), а `kind` у NodeDoc —
   операция или воркер. Новое поле с именем `kind` или словом «роль» будет путать людей и
   агентов. Зато свободная `role` уже несёт подсказку для миграции: в пакете «Ярмарки» корень
   с `role: система`, в примере промпта `role: «система» / «компонент» / «воркер»`
   (import_prompt.py:27, 56, 65).
2. **Субкомпоненты.** Узел внутри контейнера, у которого появились дети, не получает
   осмысленной роли (ни «система», ни «контейнер»). При этом это исходная постановка
   продукта (spec.md:9–11). Вопрос шире концептуального вопроса 1 о сайдкаре.
3. **Глубина ≠ роль, а эвристики по источникам ломаются на демо.** Синк считает слоем
   компонентов глубину ≥ 3 (sync_plan.py:36–38), промпт — «children корня = контейнеры».
   С вложенными системами и в федерации (общий корень над продуктами) контейнеры окажутся
   на глубине 3 и выпадут из синка как «компоненты». Эвристика «пути в одном репозитории →
   компоненты» неверно пометит «Сервис заказов» и «Сервис оплаты» как контейнеры: у их детей
   общий репозиторий и разные path, но это разные деплой-единицы. Надёжнее читаются два
   сигнала, оба есть в «Ярмарке»: **ребёнок-БД или брокер → родитель система** (БД в C4 сама
   контейнер) и **у детей разные площадки → система**.
4. **Пример промпта ввоза сам размывает границу.** «orders» с компонентами «api» и
   «billing-worker» (import_prompt.py:43–73), слой 3: «компоненты: api, обработчики, воркеры,
   планировщик». Воркер в отдельном процессе по C4 — контейнер (в Sentry 14 воркеров при
   отдельном запуске каждого). После эпика агенту нужна фраза «отдельно запускаемый воркер —
   контейнер в системе, поток или планировщик в процессе — компонент». Иначе модель
   продолжит делать «сервис + воркеры-компоненты», и факты разъедутся. Отмена правила
   «перенеси связи на компоненты» может вернуть класс «подвисших компонентов», который это
   правило лечило (полевые замеры plan-work-2026-08-08).
5. **Гейт живой схемы лендинга.** frontend/src/embed/scene.gen.ts — снимок 38 узлов в
   контракте NodeResponse. openapi-typescript с default-non-nullable делает поле с дефолтом
   обязательным (память openapi-typescript-gen). Новое поле узла с дефолтом уронит `tsc -b` и
   `build:embed` в CI, пока снимок не перегенерирован на поднятом стеке с эталоном, или пока
   поле не сделано необязательным. Это же касается фикстур тестов с Node и
   mcp/tests/test_alerts_render.py (AlertsResponse, урок pilot-docs).
6. **Статус страницы C4-контейнера.** Решение «складывается из детей, 422» (page-status
   §2.3, «не переигрывать») не даёт согласовать собственные спеку, конфигурацию и размещение
   контейнера.
7. **docs-delta §6 и строка AL24 на сайте.** Пункт заведён сегодня и ещё не перенесён.
   Если перенести его до эпика, строку AL24 придётся переписывать дважды. Лучше влить в
   раздел эпика.
8. **Три смысла слова «контейнер»** после эпика: C4 (продукт), Docker (DEPLOY.md,
   admin/* сайта, spec.md:197 «образ контейнера») и старое «любой родитель» в истории и
   памяти. Правило терминологии сайта (README сайта :206 «Содержимое контейнера —
   „компоненты“») надо переписать первым, иначе авторы воспроизведут старый смысл.
9. **Память агента.** feedback-container-is-abstraction (2026-10-28) прямо требует «не
   предлагать искать по предкам» и опирается на «каждый узел — либо атомарный компонент,
   либо контейнер». После принятия эпика её надо переписать, иначе следующие сессии будут
   спорить с эпиком. Рецепт «нуля алертов» в yarmarka-v2-demo («рёбра только между
   листьями») тоже станет неточным.
10. **Визуальный словарь двух холстов.** Решение развёртывания 2026-10-21 различало
    «сплошное = площадка, пунктир = контейнер». Новая сплошная рамка C4-контейнера на карте
    объектов не конфликтует с зонами-заливками развёртывания (п.4 от 2026-10-23), но
    «Легенда» и тексты о рамках (user/find-project.md:53) должны объяснять оба вида рамок.
