## 1. Узлы, узлы с детьми, глубина и формы

SQL (`q1.sql`): глубина — рекурсивным CTE от корней, «с детьми» — `EXISTS (… parent_id = id)`.
```sql
-- Q1: узлы, контейнеры (узлы с детьми), глубина и форма — по проекту
WITH RECURSIVE pn AS (
  SELECT p.id, row_number() OVER (ORDER BY p.created_at) AS no, p.archived_at IS NOT NULL AS arch
  FROM projects p
), t AS (
  SELECT n.id, n.project_id, n.parent_id, n.shape, n.is_external, 0 AS depth
  FROM nodes n WHERE n.parent_id IS NULL
  UNION ALL
  SELECT c.id, c.project_id, c.parent_id, c.shape, c.is_external, t.depth + 1
  FROM nodes c JOIN t ON c.parent_id = t.id
), k AS (
  SELECT t.*, EXISTS (SELECT 1 FROM nodes x WHERE x.parent_id = t.id) AS has_children FROM t
)
SELECT pn.no, pn.arch,
  count(*) AS nodes,
  count(*) FILTER (WHERE has_children) AS cont,
  count(*) FILTER (WHERE NOT has_children) AS leaves,
  max(depth) AS max_depth,
  count(*) FILTER (WHERE depth = 0) AS d0,
  count(*) FILTER (WHERE depth = 1) AS d1,
  count(*) FILTER (WHERE depth = 2) AS d2,
  count(*) FILTER (WHERE depth >= 3) AS d3p,
  count(*) FILTER (WHERE has_children AND shape = 'service') AS c_svc,
  count(*) FILTER (WHERE has_children AND shape = 'database') AS c_db,
  count(*) FILTER (WHERE has_children AND shape = 'broker') AS c_brk,
  count(*) FILTER (WHERE has_children AND shape = 'person') AS c_pers,
  count(*) FILTER (WHERE has_children AND is_external) AS c_ext,
  count(*) FILTER (WHERE NOT has_children AND shape = 'service') AS l_svc,
  count(*) FILTER (WHERE NOT has_children AND shape = 'database') AS l_db,
  count(*) FILTER (WHERE NOT has_children AND shape = 'broker') AS l_brk,
  count(*) FILTER (WHERE NOT has_children AND shape = 'person') AS l_pers
FROM k JOIN pn ON pn.id = k.project_id
GROUP BY ROLLUP ((pn.no, pn.arch))
ORDER BY pn.no NULLS LAST;
```

```sql
-- Q2: собственные факты узлов с детьми (контейнеров) — по проекту
WITH pn AS (SELECT id, row_number() OVER (ORDER BY created_at) AS no FROM projects),
c AS (
  SELECT n.* FROM nodes n WHERE EXISTS (SELECT 1 FROM nodes x WHERE x.parent_id = n.id)
), f AS (
  SELECT c.id, c.project_id,
    (SELECT count(*) FROM node_docs d WHERE d.node_id = c.id) AS docs,
    coalesce(btrim(c.openapi_spec), '') <> '' AS spec,
    (SELECT count(*) FROM config_params p WHERE p.node_id = c.id) AS cfg,
    (SELECT count(*) FROM db_tables t WHERE t.node_id = c.id) AS tbl,
    (SELECT count(*) FROM broker_channels b WHERE b.node_id = c.id) AS chn,
    (SELECT count(*) FROM deployment_instances i WHERE i.node_id = c.id) AS inst
  FROM c
)
SELECT pn.no,
  count(*) AS cont,
  count(*) FILTER (WHERE docs > 0) AS with_docs, sum(docs) AS docs,
  count(*) FILTER (WHERE spec) AS with_spec,
  count(*) FILTER (WHERE cfg > 0) AS with_cfg, sum(cfg) AS cfg,
  count(*) FILTER (WHERE tbl > 0) AS with_tbl, count(*) FILTER (WHERE chn > 0) AS with_chn,
  sum(inst) AS inst,
  count(*) FILTER (WHERE docs > 0 OR spec OR cfg > 0) AS al24_like
FROM f JOIN pn ON pn.id = f.project_id
GROUP BY ROLLUP (pn.no)
HAVING count(*) FILTER (WHERE docs > 0 OR spec OR cfg > 0 OR tbl > 0 OR chn > 0 OR inst > 0) > 0 OR pn.no IS NULL
ORDER BY pn.no NULLS LAST;
```

## 3. Эвристика роли по источникам

### 3.1. Правило (как в задании — только источники детей)

Разбор `source_ref` детей и самого узла; сигналы (`analyze.py`, функция `classify`):
- «система»: ребёнок `database`/`broker`/`person`; ≥2 разных репозитория (дети + сам узел);
  `host:`-источник у ребёнка; монорепо — узел без источника, ≥2 git-детей в одном репозитории, но их
  пути расходятся уже на первом-втором сегменте (соседние каталоги верхнего уровня);
- «процесс с модулями»: у узла git-путь P, все git-дети того же репозитория и их пути вложены в P
  (сильно); либо узел без источника, а дети — один репозиторий с общим каталогом ≥2 сегментов (слабо);
- оба вида сигналов — «конфликт», нет сигналов — «не определить».
```python
def classify(cid):
    c = N[cid]
    kids = [N[k] for k in c["ch"]]
    sig_sys, sig_proc = [], []
    shapes = Counter(k["shape"] for k in kids)
    if shapes["database"] or shapes["broker"]:
        sig_sys.append("db/broker-ребёнок")
    if shapes["person"]:
        sig_sys.append("person-ребёнок")
    ks = [parse(k["src"]) for k in kids]
    git = [s for s in ks if s and s[0] == "git"]
    hosts = [s for s in ks if s and s[0] == "host"]
    cs = parse(c["src"])
    repos = {s[1] for s in git}
    if cs and cs[0] == "git":
        repos_all = repos | {cs[1]}
    else:
        repos_all = repos
    if len(repos_all) >= 2:
        sig_sys.append("разные репозитории")
    if hosts:
        sig_sys.append("host:-источники детей")
    strong = False
    weak = False
    if cs and cs[0] == "git" and cs[2] and git and len(repos_all) == 1:
        if all(under(s[2], cs[2]) for s in git):
            strong = True
            sig_proc.append("пути детей вложены в путь контейнера")
    if not strong and not cs and len(git) >= 2 and len(repos) == 1:
        cd = common_dir([s[2] for s in git if s[2]])
        if len([s for s in git if s[2]]) >= 2 and len(cd) >= 2:
            weak = True
            sig_proc.append("общий каталог детей ≥2 сегментов (контейнер без источника)")
        elif len([s for s in git if s[2]]) >= 2:
            sig_sys.append("монорепо: дети в соседних каталогах верхнего уровня")
    if sig_sys and (strong or weak):
        cls = "конфликт"
    elif strong:
        cls = "процесс"
    elif weak:
        cls = "процесс (слабо)"
    elif sig_sys:
        cls = "система"
    else:
        cls = "не определить"
    return cls, sig_sys, sig_proc, len(git), len(hosts), len(kids)
```

## 7. Размещение

Площадки есть только в **2 проектах: 30 «Ярмарка» v2 (7 площадок, 23 экземпляра) и 58 «Мок» (12
площадок, 11 экземпляров)**. Все 34 экземпляра — на листьях (32 под системами, 2 в корне).

SQL (`q7.sql`): по каждому узлу с детьми — листья поддерева без person, их экземпляры, объединение
площадок, число разных наборов (D22):
```sql
-- Q7: размещение — по каждому узлу с детьми в проектах с площадками:
-- листья поддерева (без person), экземпляры листьев, объединение площадок, число разных наборов
WITH RECURSIVE pn AS (SELECT id, row_number() OVER (ORDER BY created_at) AS no FROM projects),
c AS (SELECT n.id, n.project_id, n.name FROM nodes n
      WHERE EXISTS (SELECT 1 FROM nodes x WHERE x.parent_id = n.id)
        AND EXISTS (SELECT 1 FROM deployment_sites s WHERE s.project_id = n.project_id)),
sub AS (SELECT c.id AS cid, k.id AS nid FROM c JOIN nodes k ON k.parent_id = c.id
        UNION ALL SELECT sub.cid, k.id FROM sub JOIN nodes k ON k.parent_id = sub.nid),
lf AS (SELECT sub.cid, n.id FROM sub JOIN nodes n ON n.id = sub.nid
       WHERE n.shape <> 'person' AND NOT EXISTS (SELECT 1 FROM nodes x WHERE x.parent_id = n.id)),
sets AS (SELECT lf.cid, lf.id, coalesce(string_agg(i.site_id::text, ',' ORDER BY i.site_id), '∅') AS siteset,
                count(i.id) AS inst
         FROM lf LEFT JOIN deployment_instances i ON i.node_id = lf.id GROUP BY lf.cid, lf.id)
SELECT pn.no, c.name AS container, count(*) AS leaves, sum(s.inst) AS leaf_instances,
  (SELECT count(DISTINCT i.site_id) FROM lf JOIN deployment_instances i ON i.node_id = lf.id WHERE lf.cid = c.id) AS sites_union,
  count(DISTINCT s.siteset) AS distinct_sets,
  CASE WHEN count(DISTINCT s.siteset) = 1 THEN 'цельный' ELSE 'рассыпается' END AS d22
FROM c JOIN pn ON pn.id = c.project_id JOIN sets s ON s.cid = c.id
GROUP BY pn.no, c.id, c.name ORDER BY pn.no, c.name;
```

- Все 9 узлов с детьми в этих проектах — **системы** и по источникам, и по расширенной эвристике
  (у «сервисов» Ярмарки: API + воркер + своя БД, разложенные по разным площадкам, — 5 из 6
  «рассыпаются»). **Экземпляров у листьев внутри «похожих на процесс» — 0, сокращение — 0.**
- Мысленный опыт: если бы шесть сервисов Ярмарки по ошибке стали «контейнерами», 19 экземпляров

  Это довод против авто-роли «контейнер» по одной лишь роли «сервис» и за то, что БД-ребёнок — сигнал

## 8. Вывод для миграции и дефолтов

**Сколько узлов с детьми получили бы роль автоматически** (273 всего; эталоны — 79):
- только по источникам детей (как в концепции): контейнер 14 (5%), система 99 (36%), остальное 160 (59%)
  — ручной выбор. Как единственный автомат источник детей НЕ годится: дети без источника, монорепо
  у 85 из 91 узла с git-детьми;
- по расширенной эвристике: **контейнер 108 (40%)** — A 8 / B 90 / C 10; **система 96 (35%)** — A 63 /
  B 32 / C 1; **внутри контейнера 64 (23%)** — группы компонентов; **ручной 5 (2%)**. В эталонах:
  контейнер 11, система 17, внутри контейнера 48, ручной 3.
- Уверенно (A, по источникам детей) — 71 (26%); средне (B: свой путь/host у узла, форма детей) — 122
  (45%); слабо (C: технология/роль) — 11 (4%). Ручная проверка ~40 контейнеров открытых проектов нашла 2
  спорных (консьюмеры Sentry — B, воркеры очередей Zulip — C) и 8 «процессов с хранилищем» (п. 3.3).

**Безопасные дефолты:**
1. **«Система» всем узлам с детьми** воспроизводит сегодняшнее поведение байт-в-байт: листья под
   системой — контейнеры, факты остаются законными там, где они сейчас (157 параметров и 61 спека на
   листьях, все 34 экземпляра), AL24 и «связь в промежуточный узел» горят как сегодня. Ни один факт не становится
   «не на месте». Это единственный дефолт без побочных эффектов.
2. Автоподсказку (не автозапись) «похоже на контейнер» имеет смысл показывать по сигналу B — свой
   git-путь или host у узла + нет БД/брокера среди детей: это 90 узлов, и на них погаснет основная
   масса алертов связей (64 из 72 концов). Включать молча опасно: роль «контейнер» превращает детей в
   компоненты, и 26 параметров на компонентах (29, 49, 51) сразу станут предупреждением.
3. «Один репозиторий у детей → контейнер» — НЕбезопасно (55 из 85 случаев — системы-монорепо).
   Безопасна только вложенность путей детей в путь самого узла.

**Редкие формы и нужны ли правила:**
- `database`/`broker`/`person` с детьми — **0** случаев: роль можно не показывать для них вовсе
  (или запретить), миграции они не касаются.
- `person` внутри узла с детьми — 2 (только под системами; AL «люди внутри» уже есть): правило «person
  не может быть компонентом» достаточно.
- **БД/индекс внутри процесса — 8 узлов в 6 проектах (32, 34, 37, 38, 50, 51)** (Zabbix proxy + «БД прокси» ×4, «Сервер
  Grafana» + Bleve-индекс ×4): нужен ответ, кем становится хранилище внутри контейнера. Компонентом —
  неверно (таблицы — факт хранилища, а не кода); вариант «контейнер в контейнере» (открытый вопрос 1)
  или «встроенное хранилище» как законный ребёнок контейнера.
- **Группы внутри процесса — 64 узла с детьми в 6 проектах** (60 «доменов» Zabbix server/proxy и 4
  «Алертинга» Grafana) — самый массовый случай третьего уровня. Ни «система» (сумма контейнеров), ни
  «контейнер» (запускается отдельно) к ним не подходят; нужен явный вывод «узел с детьми внутри
  контейнера = группа компонентов» (без выбора роли, обход «ближайшего контейнера» её пропускает).
  Иначе 19 параметров «Алертинга» (50) так и останутся «не у контейнера».
- Схемы логики у узла-контейнера с компонентами (открытый вопрос 2): живых случаев 4 (6 — 3 схемы у
  zabbix-agent2, 10 — нарочный стенд) — выбор между «алерт» и «норма» почти ничего не стоит на данных.
- Связи в контейнер: 72 конца в 10 проектах; разрешение «конец в контейнере законен» снимет 64 из них
  при условии, что роль проставлена; при дефолте «система» не изменится ничего.
