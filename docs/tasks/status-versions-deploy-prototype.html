Статус страницы, версии документации, схема развёртывания

Прототип трёх фич ArchMap, редакция 2026-10-22 по решениям пользователя. Макеты живые: пилюля и выпадашки открываются, версия фиксируется и откатывается, объекты на холсте выделяются и размещаются. Подробные ТЗ — в docs/tasks.

Статус страницы

Пилюля рядом с именем объекта: «В работе» (жёлтая) или «Согласовано» (зелёная). У контейнера статус складывается из детей, клик по пилюле открывает их список.

Дерево объектов (панель слева) — необязательная фаза: точки статуса в строках

Правила решения приняты 2026-10-22

  • Два значения: «В работе» (по умолчанию у всех новых объектов) и «Согласовано». Это статус страницы; жизненный цикл объекта остаётся как есть.
  • Лист: статус хранится у объекта, меняет его редактор или владелец проекта. Читатель видит пилюлю без стрелки.
  • Контейнер: статус вычисляется — «Согласовано», когда согласованы все дети, включая внешние объекты и «Пользователей» (их согласуют одним кликом). Пилюля открывает список детей с точками, строка ведёт на страницу ребёнка; список открывают обе роли.
  • Статусом управляет человек: правка документации рукой или агентом статус не сбрасывает. Контейнер, оставшийся без детей, показывает свой прежний сохранённый статус.
  • MCP: карточка объекта показывает статус («в работе», «согласовано 3 из 5»), archmap_update_node меняет его только по явной просьбе человека.

Версии документации

Версия — у объекта. Редактор фиксирует срез его документации (у контейнера — вместе с поддеревом) и пишет комментарий. Панель показывает одно за раз: список версий, что изменилось в версии, одну дельту.

Страница объекта — тихая кнопка «Версии» у имени

Кнопка показывает номер последней версии и открывает панель справа. В реальном приложении панель выезжает поверх страницы.

Пример для агента по MCP
Как изменился процесс оформления заказа в новой версии сервиса заказов относительно предыдущей?
archmap_version_diff(project: "Ярмарка", node: "Сервис заказов") Сервис заказов — v2 (orders 2.2) → v3 (orders 2.3 · ORD-412) Процесс «Оформление заказа»: ~ шаг 4: Сервис заказов → База заказов: «проверить остаток» → «зарезервировать остаток» + шаг 6: Сервис заказов → Kafka заказов: заказ создан (событие) + шаг 7: Kafka заказов → Сервис уведомлений: заказ создан (событие) Схема логики «Создать заказ»: изменена (+3 −2 строки) Конфигурация: + ORDER_CANCEL_WINDOW_MIN, ~ ORDER_TTL_H (24 → 48)
В версии 2.3 оформление заказа стало событийным: вместо проверки остатка сервис резервирует его в базе, а после записи публикует «заказ создан» в Kafka, и событие забирает сервис уведомлений. В 2.2 уведомлений в процессе не было.

Панель «Версии» — один экран за раз

Правила решения приняты 2026-10-22

  • Версия у объекта. В срез входят свойства, связи, схемы логики, OpenAPI, структура, каналы, конфигурация, статус страницы, размещение и процессы с участием объекта; у контейнера — всё поддерево. Раскладка холста не входит.
  • Фиксирует редактор явно, с комментарием. Между фиксациями история не пишется.
  • Что изменилось — короткий список по версии; дельта открывается по одному элементу, с переключателем «Изменения · Было · Стало». Так же читают старую версию.
  • Откат возвращает документацию объекта к выбранной версии и сам записывает версию «Откат к vN»; незафиксированные правки перед откатом сохраняются версией «Перед откатом». Процессы общие с другими объектами, поэтому в откат не входят.
  • Хранение — сжатый JSON-снимок на версию в PostgreSQL. MCP — список версий, дельта, текст на версии; фиксация только по явной просьбе человека, отката у агента нет.

Схема развёртывания

Третий режим рядом с «Объектами» и «Процессами». Площадки — сплошные рамки, вложенные одна в другую (облако → кластер); объект может стоять на нескольких площадках экземплярами. Размещение задаётся мультивыбором и кнопкой «Указать размещение».

Правила решения приняты 2026-10-22

  • Площадка — сущность проекта: имя, вид (облако, Kubernetes, ВМ, физический сервер, другое), технология, описание, родитель. Вложенность рисуется рамкой в рамке; глубина не ограничена моделью, рендер проверим на спайке.
  • Экземпляры: объект стоит на любом числе площадок, на холсте — карточка в каждой рамке с пометкой «1/2». Контейнер передаёт экземпляры потомкам, пока у потомка нет своих.
  • Связи идут между экземплярами: от каждого экземпляра источника к ближайшему экземпляру цели (та же площадка, та же ветка вложенности, иначе любой).
  • Холст показывает листья выбранного уровня; объекты без размещения — в пунктирной группе «Размещение не указано». «Пользователей» на схеме нет.
  • «Указать размещение» — набор площадок галочками (задаёт экземпляры целиком), новая площадка с родителем тут же в окне, «Убрать размещение».
  • Одна целевая топология, без разделения сред. Площадки и экземпляры едут в экспорт, архив, версии и MCP.
