Прототип трёх фич ArchMap к обсуждению 2026-10-21. Макеты живые: пилюля и выпадашки открываются, версия фиксируется, объекты на холсте выделяются и размещаются. Правила и развилки — в заметках под каждым экраном, подробные ТЗ — в docs/tasks.

Клик по строке выпадашки открывает страницу ребёнка — в макете она появляется слева. Согласуйте всех пятерых, и пилюля контейнера позеленеет сама.

Дерево объектов (панель слева) — необязательная фаза: точки статуса в строках

Правила

  • Два значения: «В работе» (по умолчанию у всех новых объектов) и «Согласовано». Это статус страницы, а не жизненного цикла объекта (существует / планируется / выводится остаётся как есть).
  • Лист: статус хранится у объекта, меняет его редактор или владелец проекта из выпадашки пилюли. Читатель видит пилюлю без стрелки, клик ничего не делает.
  • Контейнер: статус не хранится, а вычисляется: «Согласовано», когда все дети согласованы (у детей-контейнеров — их вычисленный статус), иначе «В работе». Пилюля открывает список детей с точками, строка ведёт на страницу ребёнка.
  • Обе роли открывают список детей: это навигация, а не правка.
  • Где ещё видно: карточка объекта в MCP («Статус страницы: в работе, согласовано 3 из 5»), правка через archmap_update_node. Точки в дереве и счётчик на странице проекта — следующей фазой.
  • Не делаем в первой версии: автосброс в «В работе» при правке документации, отдельный статус у связей, история согласований (она придёт с версиями).

Развилки — нужны решения

Считать ли внешние объекты и людей? Предлагаю одно правило без исключений: все дети считаются, внешний объект согласуют одним кликом. Альтернатива — не учитывать is_external и «Пользователь».
Сбрасывать ли «Согласовано» при изменении документации? Предлагаю нет: статус ставит и снимает человек; агент по MCP статус не трогает, если его явно не попросили. Позже версии покажут «изменено после согласования».
Контейнер, у которого удалили всех детей, снова становится листом и показывает свой прежний сохранённый статус. Предлагаю так и оставить (редкий случай), либо сбрасывать в «В работе» при появлении первого ребёнка.

Версии документации

Версия — срез всего знания проекта, который редактор фиксирует явно, с комментарием (номер релиза, версии, задачи). История показывает, что изменилось между любыми двумя версиями, старые тексты открываются только для чтения. Тем же пользуется агент по MCP.

В версии 2.3 (v7) оформление заказа стало событийным: вместо проверки остатка сервис заказов теперь резервирует его в базе, а после записи публикует событие «заказ создан» в Kafka, которое забирает сервис уведомлений. В 2.1 (v4) уведомлений в процессе не было вовсе.

Правила

  • Версия = срез проекта целиком: схема (объекты, связи), схемы логики, OpenAPI, структура БД, каналы, конфигурация, процессы, статусы страниц, позже — размещение. Раскладка холста в версию не входит.
  • Фиксирует редактор явно, с комментарием. Автоматических версий нет: сохранения между фиксациями в историю не попадают. Перед фиксацией — что войдёт.
  • Дельта считается между любыми двумя версиями (и версией и текущим состоянием) по id объектов: переименование — это изменение, а не удаление с созданием.
  • Оформление дельты своё у каждого типа: схема — списком объектов и связей; тексты (mermaid, OpenAPI) — построчной дельтой; факты — таблицей строк; процесс — списком шагов и участников плюс дельта mermaid-экспорта.
  • Открыть старую версию можно у каждого текста (только чтение, с плашкой «версия N»); весь проект на версии N выгружается архивом знания и ввозится новым проектом.
  • MCP: archmap_versions, archmap_version_diff (с фильтром по объекту, схеме или процессу), archmap_version_doc (текст на версии N). Токену «только чтение» доступно всё это; фиксация версии — пишущий инструмент, только по явной просьбе человека.

Развилки — нужны решения

Версия всего проекта или объекта? Предлагаю проект: релиз трогает несколько страниц и процесс сразу, одна кнопка. Если один проект держит много сервисов с разным ритмом релизов, у версии появится необязательная область (объект), которая подписывает версию и задаёт фильтр дельты по умолчанию — срез всё равно целый.
Откат к версии. Предлагаю не в первой очереди: восстановление — это ввоз среза поверх живого проекта с CAS и процессами. Сначала история и дельта; откат — отдельной фазой после приёмки.
Хранение: снимок — сжатый JSON в Postgres (десятки–сотни КБ на версию), в демо — предел числа версий. Альтернатива «хранить архив zip» отклонена: дельта по путям не видит переименований.

Схема развёртывания

Третий режим рядом с «Объектами» и «Процессами». Площадки (кластер Kubernetes, ВМ, физический сервер, облачный сервис) рисуются сплошными рамками, объекты внутри — те же сервисы, базы и брокеры схемы. Размещение задаётся мультивыбором на холсте и кнопкой «Указать размещение».

Правила

  • Площадка — сущность проекта: имя, вид (Kubernetes, ВМ, физический сервер, облачный сервис, другое), технология свободным текстом, описание. Список площадок общий на проект.
  • Размещение — ссылка объекта на площадку, одна на объект. Контейнер передаёт размещение потомкам, пока у потомка нет своего («от контейнера «Заказы»»).
  • Холст режима показывает поддерево выбранного уровня: листья сгруппированы по действующей площадке в сплошные рамки, связи между ними — те же стрелки. Объекты без размещения — в пунктирной группе «Размещение не указано». Людей (форма «Пользователь») на схеме нет.
  • «Указать размещение» появляется при выделении: выбор площадки из списка, новая площадка тут же в окне, «Убрать размещение». После применения рамки перегруппируются с анимацией.
  • Движок тот же: площадка для раскладки — рамка, как раскрытый контейнер (ELK compound), стиль рамки — сплошной. Первая фаза — полигонный спайк: проекция «уровень → площадки» на существующий LevelGraph против отдельного лёгкого холста на том же конвейере.
  • Экспорт и MCP: площадки и размещение едут в c4.yaml и архив знания; archmap_node показывает размещение, archmap_update_node его задаёт; позже промпт импорта попросит агента вычитать площадки из helm/compose/terraform.

Развилки — нужны решения

Одно размещение на объект или несколько? Предлагаю одно: рамки не пересекаются, окно — один выбор. Реплика в двух ЦОД — вторая очередь (понятие «экземпляр»).
Вложенность площадок (облако → кластер → namespace): в первой версии плоско, модель оставляет место под parent_id.
Одна схема без разделения сред (прод/стейдж): описываем целевую топологию, как и конфигурацию — без значений сред.
