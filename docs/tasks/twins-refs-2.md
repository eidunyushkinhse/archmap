## Проблемы и решения

**А. Тёзки, которых якорь не различает.** Это группы с одинаковым путём, где
якоря у всех разные и присутствуют НЕ у всех, — например, два узла «api»,
созданные вручную. Сейчас такие пары со связями ломают догрузку и создание
проекта.

Решение — ПОРЯДКОВЫЙ уточнитель `путь @ #N`. N начинается с 1 и равен позиции
узла среди узлов с этим путём в порядке документа.

- Правило по ГРУППЕ одного пути. Если у всех узлов группы якоря есть и попарно
  различны, пишем якорные уточнители, как сейчас. Иначе ВСЕЙ группе пишем
  порядковые.
- Порядок тёзок в экспорте должен быть детерминирован и не зависеть от выдачи
  БД или от id: `created_at` после импорта одинаков у всех узлов одной
  транзакции. Сортируй детей по имени, при равенстве — по содержательному
  ключу: сериализации узла вместе с поддеревом (якорь, форма, роль, технология,
  описание, дети). Полные двойники неразличимы, их порядок байтам безразличен.
  Критерий: экспорт → создание нового проекта → экспорт дают одинаковые байты
  для проекта с тёзками обоих видов.
- Резолвер понимает `@ #N` так: N-й из кандидатов с точным путём в порядке
  документа. Проверь, как догрузка поведёт себя с живыми тёзками без якорей.
  Сейчас там есть «узлы-тёзки … слились в один — знание приедет к первому», и
  собственный архив не должен ломать инвариант «ноль изменений».

**Б. Дети тёзок-контейнеров.** Уточнитель ставится на ТОТ СЕГМЕНТ пути, где
стоит тёзка: `Ярмарка / Каталог-БД @ git:github.com/org/x / reader`. Путь
режется по « / » (с пробелами). В ключах якоря слэши и решётка идут без пробелов,
поэтому разрез безопасен — но проверь это тестом, в том числе на `git:repo#a/b`.
Резолверы разбирают сегменты по очереди. Экспорт связей и адреса семей несут
уточнители всех неоднозначных сегментов предков. Без тёзок вывод прежний
байт-в-байт: сторож — фикспойнт md5 архива демо-шаблона.

**В. Процессы.**
- В архиве участник-тёзка экспортируется так, чтобы создание из архива привязало
  его к правильному узлу. Имя участника, видимое пользователю, остаётся голым,
  без уточнителя.
- Привязка шага `%% archmap-doc: путь / имя` несёт уточнитель в пути.
- Разбор и сопоставление (`process_import`, `match_nodes_by_name` или его
  аналог, `unified_apply`) понимают уточнитель.
- Процессы, которые человек вставляет вручную в окно импорта процесса, работают
  как раньше: неоднозначное имя даёт выбор кандидатов в превью.
- Критерий: создание из архива проекта, где процесс идёт между тёзками, —
  участники привязаны, шаги «со связью», привязки шагов к схемам на месте.

**Г. Споры о знании тёзок.** `FamilyConflict.id` (и родственные id в
`unified_import`, если они адресуют узел путём) строится по адресу с
уточнителем, чтобы выбор по одному тёзке не применялся к спору другого. Тест:
два спора у двух тёзок, выбор только по одному.

**Д. Окна «Доки от агента» и «Список операций».** `docs_import`,
`recon_import` и другие приёмники, которые резолвят путь узла, должны понимать
уточнитель, если это делается через готовый `anchored_node_hits` или близкий
помощник. Если нужно больше, опиши в отчёте и не делай.
