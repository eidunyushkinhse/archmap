# Тип выбран всегда (эпик 2026-11-01, вариант Б)

Ветка `feat/type-always`. Продолжение эпика «Элемент архитектуры» (docs/plan-c4-elements.md,
раздел 14). Решение владельца старше плана эпика и spec.md.

## Решение владельца 2026-11-01

«Старый проект» (объект, у которого тип не выбран) как случай не признаётся: такие данные есть
только в наших тестовых базах. Файл от агента, в котором у объекта с вложенными объектами тип не
указан, ArchMap отвергает. Вариант Б: тип хранится явно у каждого сервиса вне контейнера,
ветки «не сказано» из продукта уходят.

## ТЗ

### 1. Инвариант хранения
- У сервиса (`shape: service`) вне контейнера `element` ∈ {system, container} всегда. У
  компонента (сервис внутри контейнера), базы данных, брокера и пользователя `element` = NULL,
  как сейчас (тип задан положением или формой). Это инвариант приложения, не NOT NULL в БД.
- Один помощник на все пути записи (создание, ввоз, догрузка, синк, восстановление Undo,
  откат версии, копия проекта, перенос в дереве, смена внешности): сервис, оказавшийся вне
  контейнера без `element`, получает **container** (лист или с детьми — всё равно: контейнер с
  компонентами); перенесённый внутрь контейнера — NULL. Перенос наружу с детьми делает объект
  контейнером с компонентами; если владельцу переноса нужна система — он меняет тип строкой
  «Тип», как и сегодня.
- `element_effective` считается по-прежнему ТОЛЬКО в `app/element.py`, но ветка «NULL у
  сервиса с детьми → система» перестаёт быть правилом: оставь один защитный fallback с
  комментарием «после миграции не встречается» (чтобы чтение не падало на чужой базе), без
  упоминаний в текстах, API-описаниях и документации. Р42 (внешний лист без элемента —
  внешняя система) становится правилом ЗАПИСИ: при создании внешнего объекта типом
  «Система» хранится system; снятие и установка флажка «Внешний» элемент не меняют.

### 2. Миграция Alembic
- Данные: каждому сервису вне контейнера с `element IS NULL` записать то, что сегодня даёт
  `element_effective` (система, если есть дети или внешний лист; контейнер, если лист). Обход
  дерева — в миграции на Python по таблице nodes (родитель → дети), без импорта app.*
  (миграции не зависят от кода приложения). Идемпотентна. Проверь на dev-базе: до/после
  число NULL у сервисов вне контейнера, `GET /nodes/alerts` эталона «… v2» — по-прежнему 0.
- Тест миграционной логики: функция обхода вынесена в модуль миграции так, чтобы её можно
  было вызвать из pytest на SQLite с фикстурой дерева (система с детьми, лист, внешний лист,
  компонент внутри контейнера, база внутри системы).

### 3. Ввоз, догрузка, синк, MCP: файл без типа отвергается
- YAML: у `shape: service` с вложенными объектами и БЕЗ `element` — документ отвергается
  целиком (422 словами продукта, один список: «У объектов с вложенными объектами не указан
  тип: «Заказы», «Сервис каталога». Укажите element: system или element: container.»). Лист
  без `element` — контейнер, это не «не выбран». `element` у объекта внутри контейнера и у не-
  сервиса — как сейчас (снимается с замечанием). Та же проверка в превью единого ввоза (в
  превью — ошибкой, не замечанием: документ не применяется), в догрузке архивом, в синке из
  репозитория (план не строится, причина в ответе) и во всех инструментах MCP этих путей
  (отказ словами продукта, `isError`).
- Архив знания: экспорт после миграции всегда пишет `element` у систем и контейнеров (сейчас
  «только если задан» — проверь, что после миграции он задан у всех, и сними оговорку в
  комментариях/документации). Ввоз архива — та же проверка, что у YAML.
- Вопрос «похоже на контейнер» (`container_hints.py`, ответы в `unified_apply.py`, схемы
  `unified_import`, тексты `questionText.ts`/`questions.ts`, рендер MCP) — удалить целиком:
  он существовал для файлов без типа. Вопрос «спор поля» система/контейнер между файлами —
  остаётся. Правило синка «если элементов нет ни в проекте, ни в прогоне — зона по глубине»
  (`sync_plan.py`, `_CONTAINER_DEPTH`) — удалить, остаётся зона по элементам.
- Промпты агенту (`*_prompt.py`) НЕ ТРОГАТЬ: промпт ввоза с 2026-10-31 уже требует `element` у
  объектов с вложенными. Если найдёшь в промпте фразу, которая после Б стала неверной
  («без поля — система»), — в отчёт, не править.

### 4. Интерфейс
- Окно «Что такое «Y» внутри «X»?» (FirstChildDialog, useFirstChild, firstChild.ts,
  `awaitsFirstChild`), строка под полем «Тип» ««orders» станет контейнером», поле
  `NodeCreate.parent_element` и `element_rules.first_child_refusal` — удалить: у листа тип всегда
  есть, первый вложенный объект родителя не меняет. Предвыбор типа в окне «Новый объект»
  остаётся: внутри контейнера — «Компонент», иначе тип плитки или последнего соседа.
- Перенос в дереве в лист-контейнер: переносимый сервис становится компонентом через окно
  последствий (как сегодня, когда у родителя элемент задан); базу и брокер строка контейнера
  не принимает (как сегодня).
- Справка «?» у строки «Тип» и `nodeTerms`: убрать слова о «не выбранном» типе, если есть.
- Тур (`components/tour`): шаги про создание системы и контейнера не меняются; проверь, что
  тур не опирается на `parent_element` (`node-created` несёт `element`).
- `frontend/src/types/api.gen.ts` — перегенерировать (`npm run gen:api`), `tsc -b`.

### 5. Данные и фикстуры
- После миграции на dev-базе: `scripts/refresh-demo-template.py` → пакет демо получает
  `element` у систем; сторож `tests/test_template_package.py`; ввоз пакета — без вопросов.
- `scripts/fixtures/mock-import.yaml` (кадр импорта лендинга) и всё, что ввозится тестами и
  скриптами (`backend/tests/**/*.yaml` и YAML в тестах строками, `scripts/seed-alerts-demo.py`,
  `scripts/c4-compare`, `mcp/tests`): дописать `element` там, где у сервиса есть вложенные,
  иначе они теперь отвергаются. Тесты, проверявшие «не сказано», «похоже на контейнер»,
  `parent_element`, окно первого вложенного — удалить или переписать на новое поведение; новые
  тесты: отказ файла без типа (YAML, превью, архив, синк, MCP), помощник записи, миграция.
- Кадр лендинга `crop-import.png`: сцена `import` `scripts/landing-shots.mjs` должна давать
