# Задание: проект с законными тёзками должен догружаться

Бэклог tasks.md, пункт «ПРОЕКТ С ЗАКОННЫМИ ТЁЗКАМИ НЕ ДОГРУЖАЕТСЯ» (2026-09-28).
Работа — коммитами прямо в main (баг, не эпик). Исполнитель — opus-xhigh, приёмка —
архитектор.

## Контекст

«Законные тёзки» — два узла с одним именем в одном родителе, которых мердж держит
раздельно, потому что их якоря противоречат друг другу (`import_merge`,
`identity.compare_identity`). Типичный путь появления такой пары: создать проект из
`design_briefs/design_handoff_remainder_questions/smoke-inputs/shop.yaml` и
`warehouse.yaml`. В результате внутри «Ярмарка» окажутся два «Каталог-БД» с repo
`github.com/org/shop-db` и `github.com/org/warehouse-catalog`.

Во всех ввозных форматах узел адресуется ПУТЁМ («Ярмарка / Каталог-БД»), а путь
тёзок не различает. Архитектор воспроизвёл баг (тест-набросок удалён, его нужно
написать заново как настоящий):

1. **Фатально — связи.** В живом проекте есть тёзки со своими связями
   (`orders → Каталог-БД#1` и `Склад → Каталог-БД#2`). В таком проекте
   `build_into_plan` + `apply_into_plan` падают на ЛЮБОЙ догрузке, даже когда
   догружается его собственный архив (`build_archive`):
   `UnifiedImportError: … Текущий проект: edges[0]: имя "Ярмарка / Каталог-БД"
   неоднозначно, укажите путь через " / "`.
   Причины:
   - `export.ref_name` пишет путь, который не различает тёзок;
   - `import_yaml.parse_import → resolve` отвечает «неоднозначно»;
   - догрузка разбирает экспорт ТЕКУЩЕГО проекта, поэтому ошибка возникает при
     любом входе.

   По той же причине не создаётся новый проект из архива или из YAML-экспорта
   такого проекта.
2. **Тихо — семьи.** Файлы семей тёзок (доки `.mmd` с `%% archmap-node:`, а также
   `db/`, `channels/`, `config/`, спеки с `# archmap-node:`) адресованы тем же
   путём. `unified_import._Resolver.resolve` их пропускает с пометкой
   «путь «Ярмарка / Каталог-БД» неоднозначен (узлы-тёзки) — файл пропущен»: знание
   тёзок теряется при переносе, а в свёртку «Придется подправить вручную» попадает
   сырая строка.

Санкция: расширить грамматику ссылки на узел во ввозных форматах (связи и адреса
семей) — это НЕ меняет API-контракт; схемы Pydantic не трогать.

## Решение архитектора (не переигрывать без доказательства)

**Уточнитель-якорь в ссылке.** Если путь узла в экспортируемом наборе не уникален,
а у узла есть якорь, экспорт пишет ссылку так:

    Ярмарка / Каталог-БД @ git:github.com/org/shop-db

Справа от ` @ ` стоит канонический ключ якоря `source_ref` как есть: `git:repo`,
`git:repo#path` или `host:name`.

Резолверы понимают эту форму так:

1. Сначала ищут точный путь, как сейчас. Имя, в котором законно встречается « @ »,
   продолжает работать.
2. Если точного пути нет, отрезают хвост по ПОСЛЕДНЕМУ « @ ». Если хвост —
   распознаваемый ключ якоря (`identity.known_key` или ближайшая функция), берут
   кандидатов по голове-пути и фильтруют по якорю. Кандидат ровно один — это и
   есть ответ.

**Тёзки без противоречия якорей** (оба без якоря, одинаковые якоря, нет общего
типа ключа) мерджем всё равно склеятся в один узел. Сначала ПРОВЕРЬ это тестом:
разбери один документ с двумя тёзками без якорей через штатный путь создания
проекта и посчитай, сколько узлов получится. Если склейка подтвердилась, резолвер
для такой группы тёзок без уточнителя берёт первого по документу, а не выдаёт
ошибку: после склейки это один и тот же узел. Если не подтвердилась — СТОП, опиши
в отчёте, что происходит, и ничего не выдумывай.

Для группы, где якоря противоречат друг другу, ссылка без уточнителя — по-прежнему
ошибка, но с полезным текстом. В нём перечислены готовые ссылки с уточнителями
(по образцу перечня кандидатов в `resolve`, по алфавиту, с капом
`_MAX_AMBIGUOUS_PATHS`). Нынешний текст «укажите путь через " / "» при уже
указанном пути бесполезен.

## Шаги

1. **Тесты-воспроизведения.** Добавь в `backend/tests/test_unified_into.py` рядом с
   `test_узлы_тёзки_не_путают_карту` (плюс, где уместно, в `test_export.py`,
   `test_import.py`, `test_archive_export.py`, `test_unified_import.py`):
   - живой проект с якорными тёзками, у каждого своя связь, свой док и своя
     таблица → догрузка своего архива: `превью.ok`, `превью.errors == []`, живое
     не тронуто (`_снимок` до и после), нет пропущенных файлов тёзок;
   - создание нового проекта из архива такого проекта: оба тёзки на месте, связи и
     знание у правильного тёзки;
   - YAML-экспорт такого проекта разбирается `parse_import`, связи попадают к
     правильным узлам;
   - полевой путь: `shop.yaml` + `warehouse.yaml` → проект → догрузка своего
     архива.

   Сначала убедись, что тесты КРАСНЫЕ на текущем main.
2. **Экспорт.** `export.ref_name`: уточнитель для не уникального пути при наличии
   якоря. Путь уникален или якоря нет — вывод байт-в-байт прежний.
   ⚠️ Проверь, что поддерево и корень набора (`build_export(…, root_id)`) считают
   уникальность в пределах набора, как сейчас.
   ⚠️ Сортировка `edge_dicts` должна остаться детерминированной.
3. **Резолвер связей.** `import_yaml.parse_import → resolve`, правила выше.
   ⚠️ Слэш-фолбэк (`"/" in ref`) не должен съесть уточнитель: `git:github.com/org/x`
   содержит слэши. Отрезай уточнитель ДО слэш-нормализации.
4. **Адреса семей в архиве.** `archive_export.build_archive_ordered` (`path_of`):
   тот же уточнитель в `%% archmap-node:` и `# archmap-node:`. Он нужен только
   тёзкам, у остальных адрес прежний. Приёмник — `unified_import._Resolver`
   (и `archive_import.resolve`, если он ещё жив и адресует так же): те же правила.
   Ему нужны якоря разобранных узлов, их даёт `ParsedImport`.
   ⚠️ `mmd_header` разбирает шапку; убедись, что « @ git:…#path» с решёткой не
   обрезается как комментарий или разделитель.
5. **Процессы — разведка, не обязательно правка.** Выясни, что происходит с
   процессом, где участник или привязка шага (`%% archmap-doc: путь / имя`) — это
   тёзка:
   - при создании из архива;
   - при догрузке своего архива.

   Если падает или теряет данные, а починка — тот же уточнитель в
   `%% archmap-doc` плюс резолвер в том же духе, чини. Если нужно больше (выбор
   участника по имени в превью и т. п.), опиши в отчёте и НЕ чини.
6. **Шум в своём архиве.** Для якорных тёзок догрузка своего архива сейчас даёт в
   свёртке пункт «… в разных файлах имеет разные метаданные. ArchMap не знает, это
   один и тот же объект или нет…», хотя тёзки — одна и та же живая пара. Выясни,
   откуда он берётся. Если его можно погасить тем же механизмом, что гасит
   остальной остаток своего архива (догрузка своего архива обязана давать чистое
   превью, это инвариант `test_свой_архив_не_меняет_ни_одной_живой_записи`),
   гаси. Иначе опиши в отчёте. На СОЗДАНИИ из `shop.yaml` + `warehouse.yaml` этот
   пункт законен и должен остаться.
7. **Документация.** Коротко о грамматике уточнителя там, где описан формат
   архива и экспорта (найди grep'ом `archmap-node` в `docs/` и `spec.md`). Пункт
   бэклога в `tasks.md` перенеси в «Сделано» с датой и одной строкой сути.

Гейт после каждого шага: `cd backend && ./venv/bin/python -m pytest -q` (весь
набор, особенно `test_archive_*`, `test_unified_*`, `test_export`, `test_import*`,
фикспойнт md5 архива Ярмарки) и `./venv/bin/ruff check .`. Фронт не
трогается — если придётся, `npx tsc -b` + `npx vitest run`.

Коммиты по одному на логический шаг, на русском, `fix: …` / `test: …` /
`docs: …`, последняя строка
`Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`. Пушить в
origin после каждого коммита.

## Скоуп-гард

- Промпты (`app/*_prompt.py`) и их снапшоты НЕ трогать. Агентам уточнитель не
  нужен и не объявляется: это деталь экспорта. Резолвер его просто понимает.
- Схемы Pydantic, API и фронт не трогать. Перегенерация `api.gen.ts` не
  ожидается.
- Мердж, правила склейки и сравнения якорей (`import_merge`, `identity`) не
  менять (решение пользователя: одно очевидное правило склейки, никаких новых
  матчеров).
- Не делать запрет тёзок в UI или API и уникальность имён в родителе — это
  отдельный вопрос продукта.
- Множественные якоря узла — за рамками MVP, не трогать.
- Публичный репозиторий: в тестах и доках только демо-имена («Ярмарка», «Склад»,
  `github.com/org/…`).
