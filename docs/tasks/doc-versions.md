# Задание: версии документации объекта (эпик, ветка feat/doc-versions)

ТЗ 2026-10-21, редакция 2026-10-22 по решениям пользователя (§2). Прототип —
`docs/tasks/status-versions-deploy-prototype.html`, вкладка «2 · Версии документации».
Заменяет бэклог «версионирование узлов и связей» (ТЗ 2026-08-02) и «версионирование
процессов». Работа в отдельной ветке, слияние `--no-ff` после приёмки. Код пишет
opus-xhigh, принимает архитектор.

## 1. Мотив

Документация живёт вместе с кодом: релиз сервиса меняет его схемы логики, спеку,
конфигурацию и процессы, в которых он участвует. Нужно зафиксировать срез под номер
релиза или задачи, открыть старую версию, увидеть дельту, вернуться к прежнему
состоянию. Тот же вопрос задаёт агент по MCP: «как изменился процесс создания
пользователей в новой версии сервиса X относительно предыдущей?»

## 2. Решения пользователя (не переигрывать)

1. **Версия — у объекта** (2026-10-22). Срез документации объекта; у контейнера —
   вместе со всем поддеревом.
2. **Версионируется вся документация** объекта: свойства, связи, схемы логики, спека
   OpenAPI, структура БД, каналы, конфигурация, статус страницы, размещение, а также
   процессы с участием объекта (2026-10-21).
3. **В историю попадает только то, что редактор явно фиксирует,** с произвольным
   комментарием — номер версии, релиза или задачи (2026-10-21).
4. **Откат к версии — сразу,** в первой очереди (2026-10-22).
5. **Хранение — сжатый JSON-снимок в PostgreSQL** (2026-10-22); не Git.
6. **Интерфейс минималистичный:** один экран за раз, без попытки показать всё
   сразу (2026-10-22). Панель: список версий → что изменилось в версии → одна
   дельта с переключателем «Изменения · Было · Стало».
7. Прежние принципы в силе: только семантика, раскладка холста в версию не входит;
   автор и время — на уровне версии целиком.
8. **История версий — под ⋯-меню страницы объекта,** не отдельным элементом рядом
   с пилюлей статуса (2026-10-22).

Принято по умолчанию, если не возразите: **страница проекта — корень:** та же
кнопка «Версии» на ней фиксирует срез всего проекта (`node_id = null`), иначе
появление системы на верхнем уровне не попадёт ни в одну историю.

## 3. Модель

Таблица `node_versions`:

| колонка | назначение |
|---|---|
| `id uuid`, `project_id` FK CASCADE, `node_id` FK CASCADE (null — проект целиком) | |
| `number int` | порядковый номер у объекта, `unique (project_id, node_id, number)` (у корня `node_id` null — `postgresql_nulls_not_distinct`, как у `view_layout`) |
| `comment Text NOT NULL` | комментарий редактора; пустой → 422; длина — `column_limits` |
| `kind String(16)` | `manual` \| `pre_restore` \| `restore` — ручная, автоматическая «перед откатом», автоматическая «откат к vN» |
| `restored_from int` | номер версии-источника у `restore` |
| `created_at`, `created_by_id` FK SET NULL | автор и время |
| `snapshot bytea`, `snapshot_format int` | zlib(JSON) снимка |
| `content_hash String(64)` | sha256 канонического JSON — «есть ли изменения с vN» без дельты |
| `stats JSON` | счётчики по категориям и список изменённых элементов относительно предыдущей версии — для строки списка и для «в каких версиях менялась схема» |

**Снимок** — `app/versions_snapshot.py`, `build_snapshot(db, project, node) -> dict`,
поддерево объекта (или весь проект):

- объекты поддерева, связи с хотя бы одним концом в поддереве (с именем и путём
  другого конца для показа), схемы логики с текстом, спеки, таблицы с колонками,
  каналы с полями, параметры, экземпляры размещения (эпик развёртывания), статусы
  страниц;
- процессы, в которых участвует объект поддерева: detail целиком плюс готовый
  mermaid-экспорт (`process_export.detail_to_mermaid`) — он нужен дельте и дёшев.

Схемы строк — те же, что у снимка удаления (`schemas/restore.py`: `NodeSnapshot`,
`NodeDocSnapshot`, `DbTableSnapshot`…): они уже несут исходные id, а их полноту
сторожит `test_restore` по декларации `copy_plan`. Снимок версии = снимок удаления
без раскладки + процессы + размещение. Новое поле модели попадает в версию само.

Детерминизм: списки по id, JSON с сортировкой ключей — два снимка одного состояния
совпадают байт-в-байт и дают один `content_hash` (тест).

## 4. Дельта — `app/versions_diff.py`

`diff(a, b) -> VersionDiff` (`schemas/versions.py`): плоский список ЭЛЕМЕНТОВ, как в
панели прототипа. Элемент — `{category, node_path, name, status, summary, item_id}`,
категории: свойства, связи, схема логики, OpenAPI, структура БД, каналы,
конфигурация, размещение, статус страницы, процесс. У контейнера элементы несут
путь объекта внутри поддерева.

Одна дельта (`GET …/diff/{item_id}`) отдаёт три представления:
- **изменения** — построчная дельта для текстов (`difflib.unified_diff`, контекст 2),
  таблица «поле, было, стало» для свойств, строки с пометками для фактов и связей,
  шаги с пометками для процесса (added/removed/changed/reordered по id шага);
- **было** и **стало** — полный текст или таблица на каждой из версий; так читают
  старую версию без отдельного режима страницы.

Сопоставление — по id (объекты, доки, таблицы, колонки, каналы, поля, параметры,
шаги); переименование — изменение, а не удаление с созданием. Сравнение «с текущим
состоянием» — дельта снимка версии и снимка, собранного на лету.

## 5. Откат — `app/versions_restore.py`

`restore_version(db, project, node, version)` возвращает документацию поддерева к
снимку версии и пишет историю вперёд:

1. Если `content_hash` живого состояния отличается от последней версии — сперва
   автоматическая версия `pre_restore` «Перед откатом к vN» (незафиксированное не
   теряется).
2. Применение снимка к поддереву в одной транзакции:
   - объекты: есть в снимке и живы → обновить поля; есть в снимке, удалены →
     воссоздать с исходным id (механика `app/restore.py`); живы, но созданы после
     версии → удалить вместе с их документацией (в окне подтверждения — число таких
     объектов);
   - схемы логики, спека, таблицы, колонки, каналы, поля, параметры — так же по id;
   - связи поддерева: воссоздать, обновить, удалить; связь, чей другой конец
     больше не существует, пропускается с замечанием в отчёте;
   - размещение: экземпляры по снимку; площадка, которой больше нет, —
     пропуск с замечанием;
   - **процессы не откатываются:** они общие с другими объектами. В окне
     подтверждения — строка «процессы не откатываются», их дельта остаётся в
     истории;
   - **статус страницы не откатывается:** им управляет человек.
3. Автоматическая версия `restore` «Откат к vN» (`restored_from = N`); её
   `content_hash` обязан совпасть с `content_hash` версии N — это и сторож отката
   (тест-фикспойнт: зафиксировать, изменить всё, откатить, сравнить хэши).
4. Курсоры: `bump_graph_rev`, `bump_meta_rev`, при необходимости
   `bump_process_rev` не нужен (процессы не трогаем); `touch_project`. Раскладка
   воссозданных объектов — по правилу own-on-first-render.

Права — редактор; демо — пределы объектов и текста действуют как при импорте.
В MCP отката нет: удаления объектов через агента исключены принципиально.

## 6. API — `routers/versions.py`

| ручка | кто | что |
|---|---|---|
| `GET /nodes/{id}/versions` | reader+ | список: номер, комментарий, вид, автор, время, счётчики; плюс `pending` — есть ли изменения с последней версии (сравнение хэшей) и короткий перечень изменённых элементов |
| `POST /nodes/{id}/versions {comment}` | editor+ | снимок и запись; предел демо |
| `GET /nodes/{id}/versions/{n}/diff?base=prev\|{m}\|live` | reader+ | список элементов |
| `GET /nodes/{id}/versions/{n}/diff/{item_id}?base=` | reader+ | три представления элемента |
| `GET /nodes/{id}/versions/{n}/doc/{doc_id}`, `/spec`, `/process/{process_id}` | reader+ | текст на версии (для MCP) |
| `POST /nodes/{id}/versions/{n}/restore` | editor+ | откат; ответ — номера созданных версий и замечания |
| `DELETE /nodes/{id}/versions/{n}` | owner | удаление версии (с подтверждением) |

Корень проекта — те же ручки с `/versions` без объекта (если корень подтверждён).
Домен — в `app/versions*.py`, роутер — HTTP, коды и перевод доменных отказов.

## 7. Интерфейс (по прототипу)

- **Вход — пункт «Версии документации» в ⋯-меню** страницы объекта; отдельной
  кнопки рядом с пилюлей статуса нет. Меню показывается и читателю — с пунктами
  просмотра («Открыть в карте», «Версии документации»); пункты правки остаются у
  редактора. Панель открывается поверх страницы (тот же стек окон, Escape
  закрывает).
- **Экран «список»:** строка «Есть изменения с v3: …» с кнопкой «Зафиксировать
  версию» (редактор; у читателя строки нет) и список версий — номер, комментарий,
  дата, автор. Автоматические версии («Перед откатом», «Откат к vN») — обычным
  весом, без пометок-чипов.
- **Экран «версия»:** назад, заголовок «vN · комментарий», тихий селект «с vN−1 / с
  текущим состоянием», список элементов (категория, имя, короткий статус), внизу
  «Восстановить эту версию» (редактор; недоступна, когда версия последняя и
  изменений нет).
- **Экран «элемент»:** назад, заголовок «категория · имя», сегменты «Изменения ·
  Было · Стало», содержимое одного элемента.
- **Окно фиксации:** одна строка «объект · изменения с vN: …», поле комментария,
  «Зафиксировать» слева, «Отмена» справа; Enter подтверждает.
- **Окно отката:** «Восстановить версию N?», одна фраза о сохранении
  незафиксированного, число удаляемых объектов (если есть), строка о процессах;
  «Восстановить» (красная) слева, «Отмена» справа.
- Ничего из этого на холсте и в дереве не появляется.

## 8. MCP

| инструмент | пишет | что |
|---|---|---|
| `archmap_versions(project, node)` | нет | список версий объекта с комментариями и `pending` |
| `archmap_version_diff(project, node, from?, to?, item?)` | нет | элементы дельты; `from`/`to` — номера или `live`, по умолчанию предыдущая и последняя; `item` — одна дельта текстом |
| `archmap_version_doc(project, node, version, doc? \| spec? \| process?)` | нет | текст на версии |
| `archmap_version_create(project, node, comment)` | да | только по явной просьбе человека (в описании инструмента) |

Отката в MCP нет. Рендер — `render.version_list`, `render.version_diff`. Все
четыре — в удалённом наборе. Тесты поверх подменённого httpx; `README.md` MCP и
каталог обновить.

## 9. Производительность и демо

Замерить на эталоне «Ярмарка v2»: размер снимка листа и корня (сырой и сжатый),
время сборки, хэша и дельты. Снимок листа — несколько выборок, сравнение хэшей
при открытии панели — дёшево; дельта считается по запросу. Демо: `MAX_VERSIONS`
на объект, превышение — тост предела.

## 11. Скоуп-гард

Существующие контракты API не менять. Промпты агента не трогать. Undo-история
холста и CAS-версии сущностей (`version`) с версиями документации не связаны: в
коде версия документации зовётся `node_version`. Процессы и статус страницы при
откате не трогать — осознанно (§5).
