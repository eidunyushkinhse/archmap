# Задание: версии документации (эпик, ветка feat/doc-versions)

ПРОЕКТ ЗАДАНИЯ 2026-10-21 — ждёт решений пользователя по развилкам §3. Прототип —
`docs/tasks/status-versions-deploy-prototype.html`, вкладка «2 · Версии документации».
Заменяет бэклог «версионирование узлов и связей» (ТЗ 2026-08-02, отложено на
переанализ) и «версионирование процессов». Работа в отдельной ветке, слияние
`--no-ff` после приёмки. Код пишет opus-xhigh, принимает архитектор.

## 1. Мотив

Документация живёт вместе с кодом: релиз меняет схему, спеки, конфигурацию,
процессы. Нужно зафиксировать срез под номер релиза или задачи, открыть старую
версию, увидеть дельту между версиями. Тот же вопрос задаёт агент по MCP: «как
изменился процесс создания пользователей в новой версии сервиса X относительно
предыдущей?» — и должен ответить по документации.

## 2. Решения пользователя (2026-10-21 и прежние, не переигрывать)

1. **Версионируется вся документация:** архитектура (объекты и связи), спеки OpenAPI,
   конфигурация, структура БД, каналы, процессы, схемы логики. Статусы страниц и
   размещение войдут, когда появятся.
2. **В историю попадает только то, что редактор явно фиксирует как версию.** Обычные
   сохранения между фиксациями в истории не остаются.
3. **При фиксации редактор оставляет произвольный комментарий** — номер версии,
   релиза или задачи, по которой менялся код.
4. **Старые версии открываются, дельта сравнивается** — и в интерфейсе, и агентом по
   MCP.
5. Из прежнего обсуждения (spec.md «Версионирование документации», память):
   версионируется только семантика, раскладка холста в версию не входит; хранение в
   PostgreSQL, не в Git; автор и время — на уровне версии целиком, без аудита
   отдельных действий.

## 3. Развилки — нужны решения

| № | Вопрос | Предложение |
|---|---|---|
| Р1 | Единица версии: проект целиком, объект с поддеревом или отдельный документ? | **Проект целиком.** Релиз трогает несколько страниц и процесс разом, фиксация — одна кнопка, а дельта по id показывает только изменившееся. Если в одном проекте много сервисов с разным ритмом релизов и правки идут параллельно, у версии появится необязательная область (`scope_node_id`): она подписывает версию и задаёт фильтр дельты по умолчанию, срез всё равно целый. В первой версии — без области. |
| Р2 | Откат к версии? | **Не в первой очереди.** Восстановление — ввоз среза поверх живого проекта с CAS, процессами и раскладкой. Сначала история, просмотр и дельта. Замена на первое время — «выгрузить версию N архивом знания» и ввезти новым проектом (архивный ввоз уже есть): даёт «открыть весь проект на версии N». |
| Р3 | Хранение снимка | **Сжатый JSON (zlib) в `bytea`** плюс отдельная колонка счётчиков для списка. JSONB удобнее запросами, но раза в три больше; запросов внутрь снимка не планируется. Архив zip как снимок отклонён: дельта по путям не видит переименований. В демо — предел числа версий (например 10) и размер снимка под `MAX_TEXT_BYTES`. |
| Р4 | Индикатор «есть незафиксированные изменения» | Дёшево: `project.updated_at` трогается только семантикой (`touch_project`), версия хранит его на момент фиксации. Точный перечень «что войдёт» считается только при открытии окна фиксации — дельта живого состояния с последним снимком. ⚠️ Проверить, что ВСЕ пишущие ручки доков, фактов и процессов идут через `commit_change`/`touch_project`, иначе индикатор молчит. |
| Р5 | Может ли агент по MCP фиксировать версию? | Пишущий инструмент `archmap_version_create` есть (архитектор просит в чате «зафиксируй 2.3»), описание требует явной просьбы человека. Альтернатива — не давать вовсе. |
| Р6 | Удаление версии | Только владелец проекта, с подтверждением; в MCP удалений нет. |

## 4. Модель

Таблица `project_versions`:

| колонка | назначение |
|---|---|
| `id uuid` | |
| `project_id` FK CASCADE | |
| `number int` | порядковый номер в проекте, `unique (project_id, number)` |
| `comment Text NOT NULL` | комментарий редактора (пустой → 422; длина — `column_limits`) |
| `created_at`, `created_by_id` FK SET NULL | автор и время версии |
| `snapshot bytea` | zlib(JSON) снимка, `snapshot_format int` |
| `stats JSON` | счётчики по категориям и множества id изменённых объектов, доков и процессов относительно предыдущей версии — для списка и для «в каких версиях менялась эта схема» без распаковки |
| `base_updated_at` | `project.updated_at` на момент фиксации (индикатор Р4) |

**Снимок** — `app/versions_snapshot.py`, `build_snapshot(db, project) -> dict`:
объекты (все поля семантики, включая `source_ref`, `approval`, `openapi_spec`),
связи, схемы логики с текстом, таблицы с колонками, каналы с полями, параметры,
процессы с участниками, шагами, фрагментами и ветвями, плюс готовый mermaid-экспорт
каждого процесса (`process_export.detail_to_mermaid`) — он нужен дельте и дёшев.
Позже — площадки и размещение.

Принцип полноты — тот же, что у копии проекта: перечень полей берётся из
декларации `app/copy_plan.py` (data-колонки моделей), а не пишется руками. Сторож в
тестах: снимок обязан нести каждую data-колонку каждой модели плана, кроме явно
объявленных исключений с причиной (раскладка, версия вида, участники, токены).
Новое поле попадает в снимок само.

Детерминизм: списки по id, JSON с сортировкой ключей — два снимка одного состояния
совпадают байт-в-байт (тест), иначе дельта будет шуметь.

## 5. Дельта — `app/versions_diff.py`

`diff(a, b, *, scope) -> VersionDiff` (`schemas/versions.py`), сопоставление по id
(у таблиц, колонок, каналов, полей и параметров id в снимке есть):

- **схема** — объекты added/removed/changed с полями `{name, was, now}` (имя, описание,
  роль, технология, форма, статус, внешность, родитель путём, источник); связи так же;
- **схемы логики** — по доку: статус, изменения меты (имя, вид, операция),
  построчная дельта текста (`difflib.unified_diff`, контекст 2 строки), счётчики
  строк; у новой схемы — весь текст как добавленный;
- **OpenAPI** — по объекту: построчная дельта;
- **структура БД, каналы, конфигурация** — по объекту-владельцу: строки
  added/removed/changed с изменёнными полями (таблица → колонки, канал → поля);
- **процессы** — участники added/removed, шаги added/removed/changed/reordered
  (`from → to: подпись`), фрагменты, плюс построчная дельта mermaid-экспорта;
- **статусы страниц** — объект, было → стало.

Пути объектов — из снимка «to» (для удалённых — из «from»), помощник на словарях
без БД (та же грамматика, что `node_ref`). Фильтр `scope`: `node_id` (поддерево:
объекты, их доки, спеки, факты; связи, касающиеся поддерева; процессы с участником
из поддерева), `process_id`, `doc_id`. Построчные дельты обрезаются по числу строк
с пометкой; полный текст — ручкой «документ на версии».

## 6. API — `routers/versions.py`, `/api/v1/versions` (проект — `X-Project-Id`)

| ручка | кто | что |
|---|---|---|
| `GET /versions` | reader+ | список: номер, комментарий, автор, время, счётчики; `?doc_id=`/`?node_id=`/`?process_id=` — только версии, где это менялось (по `stats`) |
| `POST /versions {comment}` | editor+ | снимок и запись; предел демо |
| `GET /versions/pending` | reader+ | `{changed, since}` по Р4; `?detail=1` — дельта живого с последней версией («что войдёт») |
| `GET /versions/{n}/diff?base=prev\|{m}\|live&node_id=&process_id=&doc_id=` | reader+ | `VersionDiff` |
| `GET /versions/{n}/doc/{doc_id}`, `/spec/{node_id}`, `/process/{process_id}` | reader+ | содержимое на версии (текст, mermaid, detail процесса для read-only рендера) |
| `DELETE /versions/{n}` | owner | Р6 |
| `GET /versions/{n}/archive` | reader+ | архив знания на версии (необязательная Ф5: рендеры архива от словарей снимка) |

Домен — в `app/versions*.py`, роутер — HTTP и коды.

## 7. Интерфейс

**Ф2 — панель «Версии проекта».** Кнопка в шапке `ProjectShell` рядом с
«Рекомендациями» (иконка часов; точка-счётчик, когда `pending.changed`). Панель —
окно во всю ширину (`ui/Modal`) с двумя колонками: слева список версий и блок
«незафиксированные изменения» с кнопкой «Зафиксировать версию» (редактор), справа
дельта выбранной версии с селектором «сравнить с: предыдущей / v… / текущим
состоянием». Окно фиксации: перечень «что войдёт» по категориям и поле
комментария (Enter подтверждает по правилам окон 2026-10-16; пустой комментарий —
отказ текстом). Общий рендерер дельты по секциям: списки изменений, таблицы строк,
раскрывающиеся построчные дельты.

**Ф3 — входы по типам документации.**
- Окно схемы логики и спеки (`inspector/DocOverlay`): селект «Версия» в шапке —
  только версии, где документ менялся; старая версия — только чтение с плашкой
  «Версия N · дата · комментарий», кнопка «Сравнить с текущей» — построчная дельта.
- Секции фактов (`DbStructureSection`, `BrokerChannelsSection`,
  `ConfigParamsSection`): «История» в шапке секции → выбор версии → табличная дельта.
- Процессы (`processes/ProcessToolbar`): «Версия» → дельта шагов и участников, дельта
  mermaid; старый процесс рисуется `SequenceDiagram` из detail на версии, только
  чтение.
- Страница объекта: ⋯-меню «История изменений» → панель версий с фильтром по
  поддереву объекта.

**Ф5 (необязательная)** — «показать на схеме»: locate добавленных и изменённых
объектов дельты через `NavigateMap`.

## 8. MCP

| инструмент | пишет | что |
|---|---|---|
| `archmap_versions(project)` | нет | список с комментариями, авторами, датами и счётчиками |
| `archmap_version_diff(project, from?, to?, node_id?, process?, doc?)` | нет | дельта; `from`/`to` — номера или `live`, по умолчанию последняя и предыдущая; процесс и схема — по имени, как ищет `archmap_doc` |
| `archmap_version_doc(project, version, doc? \| node_id? \| process?)` | нет | текст схемы, спеки или mermaid процесса на версии |
| `archmap_version_create(project, comment)` | да | Р5 |

Рендер — `render.version_list`, `render.version_diff` (те же секции текстом, как
в прототипе). Все четыре — в удалённом наборе (диска нет). Тесты поверх
подменённого httpx; `README.md` MCP и каталог инструментов обновить.

## 9. Производительность и демо

Замерить на эталоне «Ярмарка v2»: размер сырого и сжатого снимка, время сборки и
дельты. Ожидание: сотни КБ сырого JSON, десятки–сотни КБ сжатого, сборка — те же
выборки, что у архива знания. Дельта — линейна по спискам, difflib только на
изменённых текстах. Демо: `MAX_VERSIONS`, превышение — тост предела, как у прочих.

## 11. Скоуп-гард

Существующие контракты API не менять. Промпты агента не трогать. Undo-история
холста и CAS-версии сущностей (`version`) с версиями документации не связаны —
не путать в именах: в коде версия документации зовётся `project_version`.
