# Задание: схема развёртывания (эпик, ветка feat/deployment)

ПРОЕКТ ЗАДАНИЯ 2026-10-21 — ждёт решений пользователя по развилкам §3. Прототип —
`docs/tasks/status-versions-deploy-prototype.html`, вкладка «3 · Схема
развёртывания». Работа в отдельной ветке, слияние `--no-ff` после приёмки. Код
пишет opus-xhigh, принимает архитектор.

## 1. Мотив

Четвёртый вид C4 — развёртывание: где физически крутятся сервисы, базы и брокеры
(кластер Kubernetes, виртуальная машина, физический сервер, управляемый облачный
сервис). Нужно эксплуатации и для вопросов «что ляжет, если ляжет кластер X».

## 2. Идея пользователя (2026-10-21, подтвердить)

1. Редактор описывает размещение **в отдельном редакторе схемы**.
2. **Мультивыбор объектов → кнопка «Указать размещение» → окно,** где указать, где
   сервис, база или брокер крутится.
3. **Рендерер объединяет объекты одной площадки в рамки** — сплошные, чтобы
   отличались от пунктирных рамок контейнеров.

## 3. Развилки — нужны решения

| № | Вопрос | Предложение |
|---|---|---|
| Р1 | Термин для «где крутится» | **«Площадка»** (в API `site`). Альтернативы: «среда исполнения», «узел развёртывания» (термин C4, но «узел» у нас занят). |
| Р2 | Одно размещение на объект или несколько? | **Одно.** Рамки не пересекаются, окно — один выбор. Реплика в двух ЦОД — вторая очередь через понятие «экземпляр» (объект появляется в нескольких рамках). |
| Р3 | Наследование от контейнера | **Да:** объект без своего размещения наследует площадку ближайшего размещённого предка. Разместил систему «Заказы» — все её сервисы в кластере; исключение задаётся у одного сервиса. На карточке так и пишется: «от контейнера «Заказы»». |
| Р4 | Плоский список площадок или вложенность (облако → кластер → namespace)? | **Плоско** в первой версии; модель оставляет место под `parent_id`, рендер вложенных рамок — потом. |
| Р5 | Где живёт редактор | **Третья вкладка переключателя режимов:** «Объекты · Процессы · Развёртывание». Альтернатива — тумблер на карте объектов, но смешивать сплошные и пунктирные рамки на одном холсте нельзя: площадка режет контейнер поперёк. |
| Р6 | Виды площадок | `kubernetes`, `vm`, `physical`, `cloud`, `other` (`Literal` в `domain_types`) плюс технология свободным текстом («Yandex Managed Kubernetes 1.30», «VMware ESXi 8»). Serverless и браузер — в `cloud`/`other`, пока нет спроса. |
| Р7 | Что показывать на холсте режима | **Листья поддерева выбранного уровня** (по умолчанию весь проект), сгруппированные по действующей площадке. Контейнеры — логика, а не исполняемые единицы. Большой проект — выбор уровня в тулбаре. «Пользователь» на схеме не показывается. |
| Р8 | Объекты без размещения | Отдельная пунктирная группа «Размещение не указано» — видно, что осталось. Алерт «объект без размещения» — необязательная Ф5 и только когда в проекте есть хоть одна площадка (как `has_status_info`). |
| Р9 | Среды (прод, стейдж) | **Одна целевая топология,** как у конфигурации нет значений сред. |

## 4. Модель и API

**Таблица `deployment_sites`:** `id`, `project_id` FK CASCADE, `name String(256)`
(`unique (project_id, name)`), `kind String(16)` Literal, `technology String(128)`,
`description Text`, `version int` (CAS), `created_at`, `updated_at`.

**Колонка `nodes.site_id`** uuid FK `deployment_sites.id` `ondelete SET NULL`,
nullable, index. Копия проекта — `copy_plan`: новая модель и `mapped site_id`
(карта новых id); снимок удаления — `NodeSnapshot.site_id` (площадки уже нет →
null); `column_limits` подхватит строки сам; демо — предел площадок.

**Действующее размещение** — `app/deployment.py`:
`effective_sites(all_nodes) -> dict[node_id, (site_id, inherited_from_id | None)]`,
один проход сверху вниз по дереву.

**Роутер `routers/deployment.py`, `/api/v1/deployment`:**

| ручка | кто | что |
|---|---|---|
| `GET /deployment/sites` | reader+ | площадки с числом размещённых объектов |
| `POST /deployment/sites`, `PATCH /sites/{id}` (CAS), `DELETE /sites/{id}` | editor+ | удаление — объекты в null, подтверждение с числом объектов в UI |
| `POST /deployment/assign {site_id \| null, node_ids[]}` | editor+ | все узлы — своего проекта (`owned_or_404`); `bump_graph_rev`, `touch_project` |
| `GET /deployment/graph?level=` | reader+ | `{sites, nodes, edges, layout}`: листья поддерева уровня с `site_id`, `site_effective_id`, `inherited_from_id`; связи между ними (сырые, как у графа уровня); раскладка вида |
| `PATCH /nodes/{id} {site_id}` | editor+ | то же со страницы объекта |

`NodeResponse` получает `site_id` и `site_effective` (id, имя, вид) — для строки
«Размещение» на странице объекта и карточки MCP.

**Раскладка вида развёртывания.** `view_layout.view_id` — uuid контейнера уровня,
отдельной колонки «род вида» нет. Предложение без миграции: строки раскладки
развёртывания живут в виде того же уровня с префиксом `item_id` `deploy:<uuid>`;
граф уровня такие ключи отфильтровывает (легаси-пучки `b:` уже фильтруются так же),
граф развёртывания берёт только их. Площадки тоже получают строки (`expanded`
всегда true, позиция рамки).

**Экспорт, импорт, архив.** В c4.yaml появляется раздел
`deployment: {sites: [{name, kind, technology, description}]}`, у узла — `site: имя`.
`import_yaml` принимает (площадки создаются по имени, единый импорт N входов
склеивает по имени), экспорт пишет. Синк с прогоном агента размещение НЕ меняет:
агент его не знает. Архив знания едет через c4.yaml сам. Снимок версий (эпик
версий) подхватит через `copy_plan`.

## 5. Фронт

**Ф1 — спайк на полигоне (день).** Два варианта холста:
- **А.** `LevelGraph` с проекцией «площадки как раскрытые контейнеры»: площадка —
  синтетический контейнер (`ContainerData`/`FrameData`, цепочка предков `[site]`),
  листья — блоки с `parent_id = site`, объекты без размещения — под синтетической
  группой; `mode: arrangeOnly`, без drill, quick-connect и rehang; стиль рамки —
  класс `lg-frame--site` (сплошная) по данным рамки. Проверить, что `frames.ts
  computeFrames` и конвейер работают на таких цепочках без правок ядра.
- **Б.** Отдельный `DeploymentCanvas` на `layout/pipelineClient` (ELK в воркере) и
  рендерерах `graph/nodes.tsx`, `graph/edges.tsx`, без интеракций уровня.

Критерий: А заводится без правок ядра конвейера — берём А (рамки, анимация,
персист, undo бесплатно). Иначе Б. Итог спайка — короткая запись в этом файле.

**Ф2 — режим «Развёртывание».** `ProjectShell`: `WorkMode = "schema" | "proc" |
"deploy"`, третья кнопка переключателя. `pages/DeploymentPage.tsx`: тулбар (выбор
уровня, «Переразложить», «Легенда»), холст, плавающая панель выделения «Выбрано N ·
Указать размещение · Снять выделение» (мультивыбор React Flow: Shift+клик и рамка —
проверить, что `LevelGraph` их не глушит), окно `PlacementDialog` (`ui/Modal`:
список площадок, «Новая площадка» с полями, «Убрать размещение»; главная кнопка
слева, «Отмена» справа). После применения — перезагрузка графа и анимированная
пере-раскладка конвейером. Стили рамок площадок: сплошная граница 1.5px, плашка
слева-внизу с иконкой вида и технологией; группа «не указано» — пунктир.

**Ф3 — страница объекта и легенда.** `NodeProperties`: строка «Размещение» (чтение:
иконка, имя, вид, технология, у унаследованного — «от контейнера «…»»; редактор —
«изменить» → тот же `PlacementDialog` для одного объекта). `SchemaLegend` —
«площадка (сплошная рамка)». Алерты не трогаем.

**Ф4 — экспорт, импорт, MCP.** `export.py`/`import_yaml.py`/единый импорт/архив (§4);
`t_node` — строка «Размещение: …»; `archmap_update_node` — аргумент `site` (имя
площадки, пустая строка снимает); новый читающий `archmap_deployment(project,
node_id?)` — площадки с составом. Промпт импорта — необязательная Ф6: попросить
агента вычитать площадки из helm/compose/terraform.

**Ф5 (необязательные).** Алерт «объект без размещения», вложенность площадок,
несколько размещений (экземпляры), площадки в демо-пакете «Ярмарка».
