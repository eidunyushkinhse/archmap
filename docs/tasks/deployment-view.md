# Задание: схема развёртывания (эпик, ветка feat/deployment)

ТЗ 2026-10-21, редакция 2026-10-22 по решениям пользователя (§2). Прототип —
`docs/tasks/status-versions-deploy-prototype.html`, вкладка «3 · Схема
развёртывания». Работа в отдельной ветке, слияние `--no-ff` после приёмки. Код
пишет opus-xhigh, принимает архитектор.

## 1. Мотив

Четвёртый вид C4 — развёртывание: где физически крутятся сервисы, базы и брокеры
(облако, кластер Kubernetes, виртуальная машина, физический сервер). Нужно
эксплуатации и для вопросов «что ляжет, если ляжет кластер X».

## 2. Решения пользователя (не переигрывать)

1. **Отдельный редактор схемы**; мультивыбор объектов → «Указать размещение» →
   окно, где указать, где объект крутится (2026-10-21).
2. **Объекты одной площадки объединяются в сплошные рамки** — в отличие от
   пунктирных рамок контейнеров (2026-10-21).
3. **Экземпляры сразу:** объект может стоять на нескольких площадках
   (2026-10-22).
4. **Вложенность площадок сразу** (облако → кластер → …); «посмотрим, как
   получится, и решим» — рендер вложенных рамок проверяется спайком Ф1
   (2026-10-22).
5. **Одна схема без разделения сред** (прод, стейдж): целевая топология, как у
   конфигурации нет значений сред (2026-10-22).

Принято по умолчанию, если не возразите:
- термин **«площадка»** (в API `site`);
- режим — **третья вкладка переключателя** «Объекты · Процессы · Развёртывание»;
  тумблер на карте объектов не годится: сплошная рамка площадки режет пунктирный
  контейнер поперёк;
- виды площадок: `cloud` (облако, управляемый сервис), `kubernetes`, `vm`,
  `physical`, `other` (ЦОД, стойка) плюс технология свободным текстом;
- холст показывает **листья поддерева выбранного уровня** (по умолчанию весь
  проект); «Пользователь» не показывается; объекты без размещения — в пунктирной
  группе «Размещение не указано»;
- алерт «объект без размещения» — необязательная фаза, и только когда в проекте
  есть хоть одна площадка.

## 3. Модель

**Таблица `deployment_sites`:** `id`, `project_id` FK CASCADE, `parent_id` FK на
себя (`ondelete RESTRICT`: площадку с вложенными не удалить — 422 «сначала
перенесите вложенные площадки»), `name String(256)` (`unique (project_id, name)`),
`kind String(16)` Literal, `technology String(128)`, `description Text`,
`version int` (CAS), `created_at`, `updated_at`. Смена родителя — с проверкой
цикла (обход с seen).

**Таблица `deployment_instances`:** `id`, `project_id` FK CASCADE, `node_id` FK
CASCADE, `site_id` FK CASCADE, `unique (node_id, site_id)`. Экземпляр = «объект
стоит на площадке»; у объекта их ноль или больше.

Копия проекта — `copy_plan`: две новые модели, `mapped` ссылки через карты новых
id. Снимок удаления (`restore`) — экземпляры узла (площадки, которой нет, — пропуск).
Снимок версии документации подхватит экземпляры через те же схемы. `column_limits`
— сам. Демо — предел площадок.

**Действующее размещение** — `app/deployment.py`:
`effective_instances(all_nodes, instances) -> dict[node_id, list[(site_id, inherited_from_id | None)]]`:
свои экземпляры, а без своих — экземпляры ближайшего предка с экземплярами
(«от контейнера «Витрина»»). Один проход сверху вниз по дереву.

## 4. API — `routers/deployment.py`, `/api/v1/deployment`

| ручка | кто | что |
|---|---|---|
| `GET /deployment/sites` | reader+ | площадки деревом (`parent_id`) с числом экземпляров |
| `POST /deployment/sites`, `PATCH /sites/{id}` (CAS), `DELETE /sites/{id}` | editor+ | удаление снимает экземпляры (в UI — подтверждение с числом) и запрещено при вложенных |
| `PUT /deployment/placements {node_ids[], site_ids[]}` | editor+ | задаёт НАБОР экземпляров каждого объекта целиком (пустой набор — снять); узлы — своего проекта (`owned_or_404`); `bump_graph_rev`, `touch_project` |
| `GET /deployment/graph?level=` | reader+ | `{sites, nodes, edges, layout}`: листья поддерева уровня с `instances` (своими) и `effective` (действующими, с `inherited_from_id`); связи между ними сырые, как у графа уровня; раскладка вида |
| `PATCH /nodes/{id} {site_ids}` | editor+ | то же со страницы объекта |

`NodeResponse` получает `sites` (действующие экземпляры: id, имя, вид, родитель,
унаследовано ли) — для строки «Размещение» и карточки MCP.

**Раскладка вида развёртывания.** Без миграции: строки раскладки живут в виде того
же уровня с префиксом `item_id` — `deploy:<node_id>@<site_id>` у экземпляра и
`deploy:site:<site_id>` у рамки площадки; граф уровня такие ключи отфильтровывает
(легаси-пучки `b:` уже фильтруются так же).

**Экспорт, импорт, архив.** В c4.yaml — раздел `deployment: {sites: [{name, kind,
technology, description, parent}]}`, у узла — `sites: [имена]`. `import_yaml`
принимает (площадки по имени, родитель по имени; единый импорт N входов склеивает
по имени), экспорт пишет. Синк с прогоном агента размещение НЕ меняет: агент его не
знает. Архив знания едет через c4.yaml сам.

**Ф0 (2026-10-22) — фактический контракт.**
- Модели `DeploymentSite`, `DeploymentInstance`, миграция `bb77466716fb`. FK родителя
  площадки — NO ACTION, а не RESTRICT: запрет тот же, но RESTRICT в SQLite тестов
  проверяется построчно и ронял бы каскадное удаление проекта (Postgres пропускает обе).
- Домен `app/deployment.py`: `effective_instances(parent_of, pairs)` — по карте «узел →
  родитель», не по ORM-узлам; `check_site_parent`, `set_placements`, `mark_sites`.
  «Пользователь» не размещается (422) и не наследует; объект со своими экземплярами в
  «Пользователя» не превращается (400).
- Схемы `app/schemas/deployment.py`: `SiteCreate`, `SiteUpdate` (`parent_id: null` — в
  корень), `SiteOut` (+ `instance_count` — свои экземпляры), `PlacementsIn`,
  `EffectiveInstanceOut`, `DeploymentNodeOut` (`NodeResponse` + `instances` +
  `effective`), `DeploymentGraph {sites, nodes, edges, layout, version, graph_rev,
  meta_rev}`. `NodeResponse.sites: NodeSiteOut[] {id, name, kind, parent_id,
  inherited_from_id}`, `NodeUpdate.site_ids`.
- Ручки: `GET/POST /deployment/sites`, `PATCH/DELETE /deployment/sites/{id}`,
  `PUT /deployment/placements`, `GET /deployment/graph?level=`. Имя занято и CAS — 409,
  цикл — 400, чужой родитель — 404, вложенные при удалении — 422.
- `PUT /placements` и `site_ids` — набор площадок КАЖДОГО объекта целиком; `[]` снимает
  своё (остаётся унаследованное); `site_ids` не прислан или `null` — не трогаем. Отказ —
  до любой записи. Изменение набора двигает `graph_rev` и `meta_rev`, CAS узла — нет.
- Граф: листья поддерева уровня (сам контейнер уровня — рамка, не объект), без
  «Пользователей»; связи — оба конца среди листьев; площадки — все. Граф уровня и
  контекст-схема `sites` не заполняют (`[]`), выдачи роутера узлов и граф развёртывания —
  заполняют.
- Раскладка: ключи `deploy:…` пишет тот же `PUT /views/{view_id}/layout` (формат ключа
  там не проверяется — строка до 128). `read_view_layout(…, deploy=)` разводит холсты,
  «Переразложить уровень» ключи `deploy:` не трогает, удаление площадки снимает её
  ключи. Сброса раскладки развёртывания отдельной ручкой нет — решит Ф2.
- Курсоры площадок: создание — `graph_rev`; правка — `graph_rev`, и `meta_rev`, если на
  площадке кто-то стоит; удаление — оба.
- Демо: `MAX_SITES = 20` на проект, текст площадок — в объёме текста; в превью ввоза вид
  `sites` не попадает до Ф4.
- Отложено в Ф0б: снимок версии документации (площадки и экземпляры пока в
  `NOT_IN_VERSION`), дельта «размещение», откат экземпляров.

**Ф0б (2026-10-22) — размещение в версиях.**
- Снимок версии несёт свои экземпляры узлов среза: `VersionSnapshot.instances:
  VersionInstance[]` (дефолт `[]`, снимки формата 1 без поля читаются как есть; формат
  не менялся) с путём площадки `site_path` («Облако / Кластер prod») для показа.
  Унаследованное размещение — производное, в снимок не входит. Площадка в версию не
  входит (`NOT_IN_VERSION`: общая сущность проекта, как процесс) — её правка и удаление
  версией не откатываются.
- Экземпляры без `site_path` — в `semantic` (значит, в `content_hash`) и в
  `restorable`: переименование и перенос площадки изменением не считаются. Хэш версий,
  снятых до Ф0б, посчитан без ключа `instances` и с живым расходится; `pending` по
  пустому перечню отвечает «изменений нет» (тест).
- Дельта: категория `placement` между `config` и `approval`, элемент `placement:<id
  узла>` на объект, у которого изменился набор своих экземпляров. Имя — «N площадок»,
  подробность — «+1 −1», статус на фронте — «указано» (своих не было), «снято» (своих
  не осталось), «изменено». Представления — таблица «Площадка» с путями площадок.
  Снять и снова поставить ту же площадку значит завести новый экземпляр (id входит в
  проекцию), поэтому элемент будет «+1 −1».
- Откат: экземпляры — своя семья. Лишние у уцелевших объектов снимаются первым шагом
  и освобождают пару «объект, площадка», недостающие воссоздаются с исходными id.
  Экземпляр на площадке, которой больше нет, пропускается с замечанием «размещение
  «<путь объекта>» на площадке «<путь площадки>» не восстановлено: площадки больше
  нет» (путь объекта — по снимку, от корня среза). Курсоры — схема и мета, как у
  всего отката.
- `NodeSiteOut` получил `parent_name` (имя площадки-родителя) и `inherited_from_name`
  (имя предка, от которого размещение унаследовано) — для строки «Размещение» (Ф3) и
  карточки MCP (Ф4).

## 5. Рендер

- **Площадка — сплошная рамка** (граница 1.5px, плашка слева-внизу с иконкой вида,
  именем и технологией), вложенная площадка — рамка в рамке; группа «не указано» —
  пунктир.
- **Экземпляры:** объект рисуется карточкой в каждой рамке, где у него действующий
  экземпляр, с пометкой «1/2»; выделение одной карточки выделяет объект (все его
  карточки).
- **Связи между экземплярами:** от каждого экземпляра источника к ближайшему
  экземпляру цели — та же площадка, затем та же корневая площадка, иначе первый.
  Правило — часть спеки, чтобы роутер и рендер читали его одинаково.
- Цвет и форма карточек — как на схеме объектов (статусы, внешность, формы).

## 6. Фронт

**Ф1 — спайк на полигоне (день).** Два варианта холста:
- **А.** `LevelGraph` с проекцией «площадки как рамки»: цепочка предков экземпляра =
  цепочка площадок от корневой до его собственной (ровно то, на чём уже стоят
  вложенные гостевые рамки, `frames.ts computeFrames` и `frameChains.ts`),
  экземпляр — блок с id `node@site`, объекты без размещения — под синтетической
  группой; `mode: arrangeOnly`, без drill, quick-connect и rehang; стиль рамки —
  класс `lg-frame--site` по данным рамки. Проверить вложенность трёх уровней и
  экземпляр в двух ветках без правок ядра конвейера.
- **Б.** Отдельный `DeploymentCanvas` на `layout/pipelineClient` (ELK в воркере) и
  рендерерах `graph/nodes.tsx`, `graph/edges.tsx`, без интеракций уровня.

Критерий: А держит вложенность и экземпляры без правок ядра — берём А (рамки,
анимация, персист, undo бесплатно). Иначе Б. Итог спайка — короткая запись здесь.

**Итог спайка (2026-10-22): вариант А.** Тест
`components/__tests__/deploymentSpike.test.ts`: площадки — раскрытые ЛОКАЛЬНЫЕ
контейнеры уровня (R5: `nodes` — корневые площадки, `localChildren` — вложенные
площадки и экземпляры, все площадки в `expanded`), экземпляр — обычный блок
`deploy:<узел>@<площадка>`, объект без размещения — голый локал уровня. Конвейер как
есть держит три вложенные рамки (по членству и по геометрии), экземпляр одного
объекта в двух ветках, связи между экземплярами с авто-маршрутами и фикспойнт
повторного прогона на засеянных позициях. Единственное препятствие — предел
инлайн-вложенности `MAX_INLINE_DEPTH = 2` (container.md C8): третий уровень площадок
остался бы свёрнутой карточкой (сторож — pipeline.test «R5-предел»); в спайке предел
подменён моком на 3. Гостевой путь (экземпляры — гости с цепочкой площадок в
`ancestors`) отвергнут: гость рисуется пунктиром как внешний, а без единого локала на
уровне `computeFrames` рамок не строит вовсе.

Правки ядра для Ф2 — три аддитивных хука с дефолтами (старое поведение байт-в-байт):
1. предел вложенности — входом конвейера и флагом режима (`PipelineInput` /
   `LevelModeFlags`), в обеих точках применения: `expandLocal` в pipeline.ts и
   `atInlineLimit` в assembleRf.ts; развёртывание — без предела;
2. декор рамки по данным (`FrameData`): сплошная граница, класс `lg-frame--site`,
   иконка вида площадки на плашке, без свёртки (`onCollapse` не задаётся). Текст плашки
   (имя · технология) — имя узла-площадки, тогда препятствие плашки для роутера
   (`framePlaqueRect`) считается от того же текста без правок;
3. пометка карточки экземпляра (`BlockData.mark` — «1/2»).
Бесплатно: драг и персист в `view_layout` по ключам `deploy:…` (id сущностей = ключи
раскладки), undo, анимация переездов, роутер с рамками-воротами (стрелка упирается в
границу площадки, C19), «Переразложить». В Ф2 мок предела в тесте спайка заменяется
настоящим входом.

**Ф2 — режим «Развёртывание».** `ProjectShell`: `WorkMode = "schema" | "proc" |
"deploy"`, третья кнопка переключателя. `pages/DeploymentPage.tsx`: тулбар (выбор
уровня, «Переразложить», «Легенда»), холст, плавающая панель «Выбрано N · Указать
размещение · Снять выделение» (мультивыбор React Flow: Shift+клик и рамка —
проверить, что `LevelGraph` их не глушит), окно `PlacementDialog` (`ui/Modal`:
площадки деревом с галочками — набор экземпляров целиком; «Новая площадка» с
полями и родителем; «Убрать размещение»; главная кнопка слева, «Отмена» справа).
После применения — перезагрузка графа и анимированная пере-раскладка.

**Ф3 — страница объекта и легенда.** `NodeProperties`: строка «Размещение» — все
действующие экземпляры (иконка, имя, «в <родитель>», у унаследованных — «от
контейнера «…»»; редактор — «изменить» → тот же `PlacementDialog` для одного
объекта). `SchemaLegend` — «площадка (сплошная рамка)».

**Ф4 — экспорт, импорт, MCP.** §4; `t_node` — строка «Размещение: …»;
`archmap_update_node` — аргумент `sites` (имена площадок, пустой список снимает);
читающий `archmap_deployment(project, node_id?)` — площадки деревом с составом.
Промпт импорта — необязательная Ф6: попросить агента вычитать площадки из
helm/compose/terraform (снапшоты промптов).

**Ф5 (необязательные).** Алерт «объект без размещения», площадки в демо-пакете
«Ярмарка», подсчёт «что ляжет, если ляжет площадка X» (обратный индекс).
