# Задание: статус страницы «В работе» / «Согласовано» (эпик, ветка feat/page-status)

ПРОЕКТ ЗАДАНИЯ 2026-10-21 — ждёт решений пользователя по развилкам §3. Прототип —
`docs/tasks/status-versions-deploy-prototype.html`, вкладка «1 · Статус страницы».
Работа в отдельной ветке от main, слияние `--no-ff` после приёмки. Код пишет
opus-xhigh, принимает архитектор.

## 1. Мотив

Архитектор ведёт документацию десятков объектов и должен видеть, какие страницы уже
проверены, а какие ещё правятся, и находить непроверенные через контейнер: с
корня — к системе, с системы — к сервису.

## 2. Решения пользователя (2026-10-21, не переигрывать)

1. **Два значения:** «в работе» (жёлтая пилюля) и «согласовано» (зелёная). У всех
   новых объектов — «в работе».
2. **Пилюля — рядом с именем объекта на его странице.**
3. **Контейнер:** статус «согласовано», когда ВСЕ его дети согласованы; иначе «в
   работе». Клик по пилюле контейнера открывает выпадашку с дочерними страницами:
   в строке — жёлтая или зелёная точка и имя; клик по строке открывает страницу
   ребёнка.
4. **«Согласовано» ставит редактор** (архитектор проекта — роль owner/editor);
   читатель статус не меняет.

Это статус СТРАНИЦЫ (документации), а не жизненный цикл объекта: `status`
existing/planned/deprecated остаётся как есть и в коде зовётся по-прежнему.

## 3. Развилки — нужны решения

| № | Вопрос | Предложение |
|---|---|---|
| Р1 | Считать ли детей-внешние объекты (`is_external`) и «Пользователь»? | Да, одно правило без исключений: внешний объект согласуют одним кликом. |
| Р2 | Сбрасывать ли «согласовано» в «в работе», когда документация объекта меняется (рукой или агентом)? | Нет в первой версии: статус ставит и снимает человек; агент по MCP статус не трогает без явной просьбы. Позже версии документации покажут «изменено после согласования». |
| Р3 | Контейнер, у которого удалили всех детей, снова лист — показывает прежний сохранённый статус. | Оставить (редкий случай). Альтернатива — сбрасывать в «в работе» при появлении первого ребёнка, но это четыре места (создание, перенос, импорт, восстановление). |
| Р4 | Где ещё показывать статус: дерево объектов (точки), страница проекта (счётчик «согласовано N из M»), холст? | Первая версия — страница объекта и MCP. Точки в дереве — необязательная Ф3, счётчик на странице проекта — там же. На холсте не показывать (узел и так несёт цвет статуса жизненного цикла). |
| Р5 | Показывать ли статус в дереве `archmap_schema` для агента? | Нет: шум в каждой строке; статус есть в карточке `archmap_node`. |

## 4. Модель и API

**Домен** (`app/domain_types.py`): `NodeApproval = Literal["in_progress", "approved"]`,
`NODE_APPROVALS`. Разбор входа — через `pick`.

**Колонка** `nodes.approval String(16) NOT NULL server_default "in_progress"` — одна
миграция Alembic. Снимок удаления (`schemas/restore.NodeSnapshot.approval`) и копия
проекта (`copy_plan`: data-колонка) — сторожа `test_restore` и `test_copy_plan`
покажут, где забыли.

**Вычисление** — `app/approval.py`:
- `effective_approvals(all_nodes: dict[uuid, Node]) -> dict[uuid, NodeApproval]` —
  один проход снизу вверх: лист — своё значение, контейнер — `approved`, если все
  дети `approved` по вычисленному, иначе `in_progress`. Без рекурсии по глубине
  (обход с seen, как велит урок аудита).
- `mark_approval(db, nodes)` рядом с `_mark_has_children` в `routers/nodes.py`: одна
  выборка `(id, parent_id, approval)` по проекту, проставляет `approval_effective` на
  экземплярах (вычисляемый атрибут, как `has_children`).

**Контракт** (`schemas/node.py`):
- `NodeResponse.approval` (хранимое) и `approval_effective` (вычисленное; у листа
  совпадает). Несут все выдачи `NodeResponse`, включая граф уровня и `/children`:
  выпадашка контейнера берёт точки детей из `GET /nodes/{id}/children`, который
  страница контейнера уже грузит (`useContainerChildren`).
- `NodeUpdate.approval: NodeApproval | None` — не прислано → не трогаем. Контейнер
  (`has_children`) → 422 «Статус контейнера складывается из детей». `NodeCreate` поле
  не принимает (всегда «в работе»).
- Смена статуса — семантика страницы: `bump_meta_rev` (страница объекта в другой
  сессии освежится), `touch_project`.
- Права — как у любого PATCH узла: `require_project_editor`.

**Импорт, синк, архив:** YAML агента и синк статус не несут и не меняют. Архив
знания — необязательная Ф4: `approved: true` у листьев в c4.yaml архива,
восстанавливается только при ввозе архива (агентский YAML этот ключ не пишет).

## 5. Фронт

- `types/index.ts`: `NodeApproval` из генерата (`npm run gen:api`).
- `components/nodeTerms.ts`: `APPROVAL_LABEL = {in_progress: "В работе", approved: "Согласовано"}`.
- Новый `components/nodePage/ApprovalPill.tsx`: пилюля + выпадашка. Пропсы: `node`,
  `isArchitect`, `children` (для контейнера), `onNavigateNode`, `onChange`.
  - лист + редактор: кнопка-пилюля со стрелкой, выпадашка из двух строк («В работе —
    страница ещё правится», «Согласовано — проверено редактором»), текущая помечена;
  - лист + читатель: `span` без стрелки, подсказка «Статус меняет редактор проекта»;
  - контейнер (обе роли): пилюля «Согласовано · 3 из 5», выпадашка-список детей с
    точками, клик по строке — `onNavigateNode(child.id)`.
  - Механика выпадашки — та же, что у ⋯-меню страницы (`np-backdrop` + `np-dropdown`);
    Escape закрывает. Стили — в `NodePage.css` (`np-approval--work/--ok`).
- `useNodePatch`: `commitApproval(value)` — CAS `base_version`, как у прочих полей;
  `nodeSig` на странице добавляет `approval` и `approval_effective` (чужая смена
  статуса ребёнка меняет пилюлю контейнера — страница обязана освежиться по
  `meta_rev`).
- Тесты vitest: пилюля лист/контейнер/читатель, смена статуса шлёт PATCH, клик по
  строке зовёт навигацию, 422 показывается текстом.

## 6. MCP

- `t_node`: строка «Статус страницы: в работе» / «согласовано»; у контейнера —
  «складывается из детей: согласовано 3 из 5».
- `archmap_update_node`: аргумент `approval` (enum), описание: «ставить только по
  явной просьбе человека — согласование это решение архитектора».
- Тесты mcp поверх подменённого httpx.
