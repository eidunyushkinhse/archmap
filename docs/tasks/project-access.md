# Задание: доступ к проектам по участникам (эпик, ветка feat/project-access)

Работаем в ОТДЕЛЬНОЙ ветке `feat/project-access` от main. Сливать в main (`--no-ff`)
будет архитектор после приёмки пользователем. Код пишет opus-xhigh, принимает архитектор.

## Мотив

Сейчас любой вошедший видит и правит все проекты. Это блокер публичного сервиса и
неудобство для закрытого контура. Пункт `tasks.md` «Multi-tenant» решаем доступом к
проектам по участникам (отдельные организации в одной установке НЕ делаем).

## Решения пользователя (2026-10-01), не переигрывать

1. **Роли в проекте:**
   - владелец (`owner`): правит, управляет участниками и видимостью,
     переименовывает, архивирует, восстанавливает, удаляет, передаёт владение;
   - редактор (`editor`): правит схему, доки, процессы, факты, импорт в проект;
   - читатель (`reader`): только смотрит, экспортирует.

   Владелец у проекта РОВНО ОДИН. Создатель проекта становится владельцем.
2. **Передача владения:**
   - владелец передаёт проект другому активному пользователю;
   - новый владелец становится `owner` (если не был участником — добавляется);
   - прежний владелец остаётся в проекте редактором.
3. **Общая роль architect/viewer остаётся** только как право СОЗДАВАТЬ проекты
   (`POST /projects`, единый импорт в новый проект: как сейчас, `require_architect`).
   Внутри проекта права определяет ТОЛЬКО роль в этом проекте: viewer может быть
   редактором чужого проекта, architect без участия в проекте правит его, только если
   он редактор.
4. **Видимость:**
   - по умолчанию проект виден только участникам;
   - у проекта флажок `visible_to_all` («Виден всем пользователям»): все, кто не
     участник, получают чтение.
5. **Администратор (`is_admin`) видит и правит ВСЁ:**
   - в любом проекте его действующая роль — `owner`, включая участников и передачу
     владения;
   - видит все проекты в списке.

   Решение пользователя: «никогда не знаешь, с каким запросом придут — пусть может
   помочь с чем угодно».
6. **Добавление участника:** владелец выбирает логин из списка активных пользователей
   сервиса. Почты и приглашений нет.
7. **Существующие проекты** — полигоны, ничего ценного. Миграция данных
   (решение архитектора), чтобы после обновления ни у кого ничего не пропало:
   - владелец — `created_by_id`, если он есть; иначе первый по `created_at`
     администратор; иначе первый по `created_at` architect; если пользователей нет
     вовсе — проект без владельца, и это допустимо только как наследие миграции;
   - `visible_to_all = true`;
   - все пользователи с общей ролью architect становятся редакторами (кроме
     владельца).

## Решения архитектора (техника)

- **Модель:**
  - таблица `project_members`: `project_id` FK CASCADE, `user_id` FK, `role`
    (`owner`|`editor`|`reader`), `created_at`, уникальность `(project_id, user_id)`;
  - `projects.visible_to_all bool NOT NULL default false`;
  - владелец хранится строкой участника с ролью `owner`. «Ровно один» держит код,
    а не частичный индекс: тесты на SQLite.
- **Одна функция действующей роли**, например `app/access.py`:
  `effective_role(db, user, project) -> "owner" | "editor" | "reader" | None`.
  Порядок проверок:
  1. администратор → `owner`;
  2. участник → его роль;
  3. `visible_to_all` → `reader`;
  4. иначе → `None`.

  Все проверки прав — через неё.
- **Недоступный проект = 404 «Проект не найден»**: существование не выдаём. Проверка
  доступа идёт ДО проверки архива (чужой архивный → 404, а не 409).
- **`get_current_project`** (`deps.py`):
  - получает пользователя и требует `effective_role != None`: чтение закрывается
    во всех роутерах проекта одним местом;
  - для записи — новая зависимость `require_project_editor` (`editor` или `owner`)
    и `require_project_owner`;
  - во всех роутерах, где `get_current_project` + `require_architect`, заменить
    `require_architect` на `require_project_editor`;
  - `require_architect` остаётся только там, где создаётся НОВЫЙ проект.
- **`routers/projects.py`** с `project_id` в пути, а не в заголовке:
  - `get` — чтение;
  - `patch`, `archive`, `restore`, `delete` — владелец;
  - `import-archive/*` и `sync/*` — редактор;
  - копия (`start: "copy:<id>"`) требует чтения источника, иначе 404 «Исходный проект
    не найден»;
  - список проектов фильтруется по доступу, у администратора — все, в обеих вкладках
    (активные и архив).
- **`ProjectResponse`** дополнить:
  - `my_role` (`owner`|`editor`|`reader`, обязательное);
  - `owner_username` (nullable);
  - `visible_to_all`.

  Pydantic → `npm run gen:api`, закоммитить `api.gen.ts`.
- **API участников:**
  - `GET /api/v1/projects/{id}/members` — любой с доступом: логин, роль;
  - `PUT /api/v1/projects/{id}/members/{user_id}` `{role: editor|reader}` — владелец:
    добавить или сменить роль. Роль `owner` так не выдаётся, владельца так не
    понизить;
  - `DELETE /api/v1/projects/{id}/members/{user_id}` — владелец; владельца удалить
    нельзя (409, понятный `detail`);
  - `POST /api/v1/projects/{id}/transfer` `{user_id}` — владелец; заблокированному
    передать нельзя;
  - `PATCH /projects/{id}` принимает `visible_to_all` — только владелец (как и
    остальные поля PATCH).
- **Список пользователей для выбора:** `GET /api/v1/users` — любому вошедшему, только
  активные, только `id` и `username`. Это не `/admin/users`.
- **Ошибки** — `{"detail": ...}` по-русски, без длинных тире.
- **Миграция Alembic** (`--autogenerate` + шаг данных по п.7). Данные переносить
  простым SQL в `upgrade`: позже по миграциям соберут Liquibase-changelog для прода
  закрытого контура. Проверить на живой dev-базе: `upgrade` → `downgrade -1` →
  `upgrade`.
- **MCP:**
  - агент работает под учёткой пользователя, поэтому фильтр приходит сам;
  - в выводе `archmap_projects` (`render.py`) показать роль в проекте (`my_role`)
    по-русски: владелец, редактор, чтение;
  - обновить тесты и README, если там описан вывод;
  - гейт MCP зелёный.

## Шаги

1. **Бэк: модель, миграция, `access.py`**, зависимости в `deps.py`. Тесты прав.
2. **Бэк: роутеры.**
   - Заменить `require_architect` на проектные зависимости во всех роутерах
     проекта.
   - `projects.py` по списку выше.
   - API участников, передача владения, `/users`, поля `ProjectResponse`.
   - `gen:api`.

   ⚠️ **Ловушка тестов.** Много тестов создают проекты прямо в БД или через API
   под одним пользователем. После шага проекты, созданные в БД без участника,
   станут недоступны (404).
   - Чини фикстуры (хелпер «создать проект с владельцем»), а НЕ делай тестового
     пользователя администратором по умолчанию: это спрячет баги прав.
   - Новые тесты `tests/test_project_access.py` покрывают:
     - матрицу «роль × действие»: чтение, запись в схему, PATCH проекта, участники,
       архив, удаление;
     - не-участника при `visible_to_all` false и true;
     - администратора без участия;
     - 404 вместо 409 для чужого архивного;
     - копию из недоступного источника;
     - передачу владения: прежний стал редактором, «ровно один владелец»,
       заблокированному нельзя;
     - запрет удалить или понизить владельца;
     - viewer-редактор может править;
     - architect не-участник не может;
     - фильтр списка проектов;
     - `/users` без заблокированных.
3. **Фронт: права в проекте.**
   - `ProjectShell` сейчас считает `isArchitect = getUserRole() === "architect"` —
     одна точка. Брать право правки из `my_role` текущего проекта (`owner` или
     `editor`).
   - Имя пропа `isArchitect` в 40 компонентах НЕ переименовывать (лишний шум диффа).
     В `ProjectShell` одна строка комментария: что теперь оно значит «может править
     этот проект».
   - Проверь другие места, где `getUserRole()` решает права ВНУТРИ проекта
     (`ProjectHomePage`, `MapEditorPage`, `NodePage`, `ProjectSwitcher` и т.п.), и
     переведи их на роль проекта. Глобальная роль остаётся только для кнопок
     создания проекта.
4. **Фронт: список проектов и окно «Доступ».**
   - **Меню карточки проекта** (`ProjectsPage`):
     - «Редактировать», «В архив», «Восстановить», «Удалить» — только владельцу;
     - новый пункт «Доступ» — всем, кто видит проект; у не-владельца окно только
       для чтения.
   - **На карточке** при `my_role === "reader"` — тихая метка «Только чтение».
   - **Окно «Доступ к проекту»** (`ui/Modal`, компонент в `components/project/`):
     - флажок «Виден всем пользователям» с подсказкой «Остальные пользователи
       смогут только смотреть»;
     - список участников: логин, роль (выбор «Редактор» / «Читатель»), удалить;
     - строка владельца с меткой «Владелец» и кнопкой «Передать владение»: выбор
       пользователя и `ConfirmDialog` «Передать проект «{имя}» пользователю
       {логин}? Вы останетесь редактором.»;
     - добавление: поле логина с подсказками из `/users`, роль, «Добавить».
   - Тексты короткие, без длинных тире.
   - vitest на окно, на видимость пунктов меню по роли, на `ProjectShell` (правка
     по `my_role`).
5. **Документация.**
   - `spec.md`: раздел «Доступ к проектам».
   - `tasks.md`: пункт «Multi-tenant» переписать — что решено, статус «сделано в
     ветке, ждёт приёмки».
   - `CLAUDE.md` и `QWEN.md` синхронно: в «Ключевые сущности» добавить
     `ProjectMember` и `visible_to_all`; в дереве — `access.py`, если появился.
   - `DEV.md`: одна-две строки про доступ и администратора.

## Гейты

После каждого шага:
- бэк: `./venv/bin/python -m pytest -q`, `ruff check .`, `mypy app/`;
- фронт: `npx tsc -b` (не `--noEmit`), `npx eslint .`, `npx vitest run`;
- MCP-гейт — после шага с MCP и в конце.

Коммиты:
- по одному на шаг (шаг 2 можно двумя), на русском, последняя строка
  `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`;
- коммитить через `git commit --only <пути>`, `git add -A` / `commit -a` не
  использовать;
- ветку пушить в origin после каждого коммита. Если DNS в WSL отвалился — повторять
  раз в минуту, не бросать;
- первым коммитом в ветке — этот файл задания.

⚠️ `./dev.sh` работает в фоне на main и использует живую dev-базу. Не перезапускать.
Миграцию накатывай осознанно. После неё проверь, что учётки из `mcp/.env` логинятся и
видят свои проекты: `GET /projects` под ними не пустой.

Headless-браузер не нужен, UI смотрит пользователь.

## Скоуп-гард

Не трогать:
- холст и раскладку;
- промпты;
- админку пользователей (кроме того, что `is_admin` теперь даёт права в проектах).

Не делать:
- организации и тенанты;
- группы пользователей;
- приглашения по почте;
- журнал действий;
- `DEMO_MODE`;
- переименование пропа `isArchitect`.

Публичный репозиторий: в коде, тестах и доках только демо-имена («Ярмарка» и т.п.).
