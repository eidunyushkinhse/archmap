## Контекст (1 абзац)

Сегодня мердж N входов (import_merge.py) оставляет пользователю «остаток» строками
текста: споры полей равной содержательности уходят в `MergeReport.conflicts`
(«оставлено «…» (файл 1), отброшено …»), связи в контейнер, изолированные группы и
похожие имена — в `warnings`/`schema_warnings`. Пользователь читает строки и правит
проект после импорта руками. Теперь остаток должен приезжать в превью СТРУКТУРОЙ
(чтобы фронт задал по нему вопросы), а ответы пользователя — уезжать в применение
словарём `decisions` и менять слитое дерево ДО записи в БД. Два сценария: создание
проекта (`/projects/import/unified-preview` → `/projects/import-unified`) и догрузка
архивов к живому (`/projects/{id}/import-archive/preview` → `/apply`).

## САНКЦИИ (иначе запрещено CLAUDE.md)

- Разрешено расширять контракты превью и применения: новые поля в
  `UnifiedPreviewOut`, `IntoPreviewOut`, `FamilyCandidateOut`, `ArchiveImportResult`

## Решения архитектора (не пересматривать; отклонение — только с раскрытием в отчёте)

Р1. **Строки остаются.** В отличие от §10.1 ТЗ строки `conflicts` / `warnings` /
`schema_warnings` из ответа НЕ убираются: их читает MCP (mcp/archmap_mcp/render.py)
и на них держится инвариант «объединение корзин == плоские списки». Структура
`remainder` — ДОПОЛНЕНИЕ. Фронт сам перестанет показывать строки, превращённые в
вопросы. Замечания, НЕ превращённые в вопросы, приезжают в `remainder.unfixable`
структурой (текст + how + agent + if_left), чтобы фронту не парсить строки.

Р2. **Вопрос о поле — только при равной содержательности.** `_Merger._decide`: если
`sub != keep_sub`, содержательный вклад побеждает молча, вопроса НЕТ. Если `sub ==
keep_sub` — вопрос (сегодня «первый побеждает» — это остаётся ДЕФОЛТОМ).

Р3. **Догрузка: остаток только с участием архива.** Вопросы о связях в контейнер,
изолированных группах и похожих именах, все сущности которых пришли из входа №0
(живой проект), в `remainder` не попадают — это дело панели незавершённости, а не
догрузки. Спор поля живого узла с архивным — вопрос, дефолт — кандидат `current`
(«оставить моё»), как у споров семей.

Р4. **Склейка при догрузке сохраняет живой узел.** Если один из пары — живой,
выживает он (его id), получает выбранное имя; связи и семьи второго переезжают на
него. При создании выживает первый по порядку файлов. Дети поглощённого узла
переезжают под выжившего. Ничего иного не удаляется.

Р5. **Память ответов между импортами не заводим.** «Разные объекты» и «оставить как
есть» действуют на один прогон; при следующем импорте вопрос повторится (текст
сноски в ТЗ это уже обещает). Никаких новых таблиц.

Р6. **Известное ограничение, не чинить:** повторная догрузка того же архива или синк
могут привезти связь в контейнер заново (перевешенная связь на другие концы — уже
другая связь). Записано в плане, в этой фазе не трогать.

## Контракт (форма — предложение; имена полей держать, состав можно уточнить с раскрытием в отчёте)

`app/schemas/unified_import.py`:

```python
class RemainderCandidateOut(BaseModel):
    origin: int            # индекс входа
    origin_label: str      # как сегодня у FamilyCandidateOut («2 · grafana.yaml»)
    source_label: str      # §4.7 ТЗ: «От агента Grafana» | «Из архива плагина» | «Из проекта»
    value: str
    current: bool = False  # живой проект (догрузка)

class FieldDisputeOut(BaseModel):
    id: str                # детерминирован: «field|<путь узла>|<поле>»
    node_path: str
    field: Literal["description", "technology", "role"]  # + иные строковые поля узла, если спорят
    candidates: list[RemainderCandidateOut]  # в порядке входов
    default: int           # индекс кандидата-дефолта: 0 при создании; current при догрузке

class ComponentOut(BaseModel):
    path: str              # полный путь «Grafana / Сервер Grafana / Рантайм плагинов»
    has_children: bool

class ContainerEdgeOut(BaseModel):
    id: str                # «edge|<from_path>|<to_path>|<label или ''>|<end>»
    from_path: str
    to_path: str
    label: str | None
    technology: str | None
    end: Literal["source", "target"]   # какой конец лёг на контейнер; оба — ДВА элемента
    container_path: str
    components: list[ComponentOut]     # всё поддерево контейнера, порядок обхода дерева, без капа

class IsolatedGroupOut(BaseModel):
    id: str                # «group|<путь первого узла группы по сортировке>»
    node_paths: list[str]  # все узлы группы (не только первые 4 — кап делает фронт)

class FuzzyPairOut(BaseModel):
    id: str                # «pair|<a_path>|<b_path>»
    a_path: str
    b_path: str
    a_source: str          # source_label входа-владельца A
    b_source: str
    a_edges: int           # число связей у A в слитом дереве
    b_edges: int
    where: str             # «на верхнем уровне» | «внутри «X»»
    a_current: bool = False  # A — живой узел (догрузка)
    b_current: bool = False

class UnfixableOut(BaseModel):
    id: str
    text: str              # строка замечания как есть
    how: str               # путь починки, начинается с «Можно доработать прогоном агента.»
    agent: str | None      # имя корня файла-владельца (None — общего файла нет)
    if_left: str           # «Если оставить: …» двумя предложениями
    file: int | None       # индекс входа-владельца

class RemainderOut(BaseModel):
    field_conflicts: list[FieldDisputeOut] = []
    container_edges: list[ContainerEdgeOut] = []
    isolated_groups: list[IsolatedGroupOut] = []
    fuzzy_pairs: list[FuzzyPairOut] = []
    unfixable: list[UnfixableOut] = []
    node_paths: list[str] = []   # ПОЛНЫЕ пути всех узлов слитого дерева (пикер концов новой связи)
    node_has_children: list[bool] = []  # строка в строку с node_paths
```

Куда: `UnifiedPreviewOut.remainder: RemainderOut = RemainderOut()` и
`IntoPreviewOut.remainder: RemainderOut = RemainderOut()`. Плюс
`FamilyCandidateOut.source_label: str = ""` (те же формы §4.7).

`source_label` (§4.7 ТЗ): YAML → `От агента {имя корня файла}`; корней несколько →
`От агента · {имя файла}`; zip → `Из архива {имя корня}` (если у архива один корень;
иначе `Из архива · {имя файла}`); вход №0 догрузки → `Из проекта`. Функция одна на
всех — в unified_import.py, используется и семьями, и остатком.

Применение: Form-поле `decisions: str | None` (JSON) у обоих apply-эндпоинтов:

```
{
  "fields":    { "<id>": <candidate_index> },
  "edges":     { "<id>": { "to_path": "<путь компонента>" } | "keep" },
  "new_edges": [ { "group_id": "<id>", "from_path", "to_path", "label", "tech", "channel": "sync"|"async" } ],
  "merges":    { "<id>": { "name": "<имя>" } | "diff" }
}
```

Разбор — по образцу `_parse_resolutions` (400 с человеческим текстом при кривой
форме). Неизвестный id или путь не из плана → 400 «Превью устарело — обновите его и
повторите»: молча применить «не то» хуже. `keep` / `diff` / отсутствие ключа —
поведение как сегодня. Отчёт применения: ОДНА строка в `warnings` результата (и
`ArchiveImportResult`, и `IntoApplyOut`), только если хоть что-то решено:
`Ваши решения: перевешено связей 5 · добавлено связей 1 · склеено объектов 1 ·
выбрано значений полей 2` (нулевые части опустить).

## Шаги (каждый — свой коммит; гейт после каждого)

Гейт бэка: `cd backend && ./venv/bin/ruff check . && ./venv/bin/python -m pytest -q`

**Шаг 1. Структурный захват остатка в `import_merge.py` (рядом со строками, строки не трогать).**
В `MergeReport` добавить поля-списки dataclass-записей (индексы — по `merged.nodes` /
`merged.edges`, как у `node_files`):
- `field_disputes: list[FieldDispute(node_idx, field, contributions: list[(file_idx, value)])]`
  — заполняется в `_Merger._decide` ТОЛЬКО в ветке равной содержательности (Р2).
  ⚠️ Три файла могут спорить об одном поле дважды: копить в ОДНУ запись по ключу
  (node_idx, field), кандидаты в порядке файлов, без дублей значений. ⚠️ `_decide`
  вызывается с индексом узла ДО финального `finish()` — проверь, что индексы merged
  не переупорядочиваются после (`_regroup` перезапускает мердж целиком через
  `_run_merge` — записи должны собираться в том прогоне, чей результат возвращён).
- `container_edges: list[(edge_idx, end, container_idx, warning_idx)]` — в
  `_warn_container_edges` рядом с `report.warn` (оба конца → две записи); в структуру
  кладём ВСЕ, включая те, что текст скрыл за «…ещё N» (кап — дело текста).
- `isolated_groups: list[(node_idxs, warning_idx)]` — в `_warn_isolated_groups`, все
  группы кроме ядра, без капа `_MAX_ISOLATED_GROUPS` для структуры.
- `fuzzy_pairs: list[(ia, ib, parent_idx | None, warning_idx)]` — в `warn_fuzzy_siblings`.
`warning_idx` — индекс строки в `report.warnings` (взять `len(report.warnings)` до
`warn`), нужен, чтобы отделить превращённые строки от `unfixable`.
Тесты в `tests/test_import_merge.py`: спор поля возникает при равной содержательности
и НЕ возникает, когда один вклад содержательный; контейнерная связь даёт запись с
верным `end`; группа; fuzzy-пара; при трёх файлах один спор с тремя кандидатами.

**Шаг 2. `source_label` и сборка `RemainderOut` в `unified_import.py`.**
Функция `source_label(plan, origin) -> str` по §4.7 (корни входа — из
`plan.origin_paths[origin]`: пути без « / »). Проставить `FamilyCandidateOut.source_label`
(и `FamilyCandidate` в плане, если удобно). Функция
`remainder_from_plan(plan, current: int | None) -> RemainderOut`:
- пути — `plan.node_paths`; `components` контейнера — все узлы с путём, начинающимся
  на `container_path + " / "`, в порядке обхода; `has_children` — по `parent_idx`;
- `default` спора поля: индекс кандидата входа `current`, если он среди кандидатов,
  иначе 0;
- `a_edges`/`b_edges` — число связей узла в `merged.edges`;
- при `current is not None` применить Р3: элемент отбрасывается, если ВСЕ его
  сущности целиком из входа `current` (по `report.node_files` / `edge_files`);
- `unfixable`: строки `schema_warnings` (из `split_remarks`) МИНУС строки с
  `warning_idx` превращённых элементов МИНУС строки `conflicts` (расхождения полей,
  где победил содержательный вклад, — чтение, не действие). Для каждой — `how` /
  `if_left` по классу (словарь по префиксу/подстроке текста, тексты ниже),
  `agent` — имя единственного корня файла-владельца (`report.warning_files[idx]`),
  иначе None; `file` — тот же индекс. Хвосты «…ещё N таких …» — приклеить второй
  строкой к тексту последнего элемента того же класса, отдельного элемента не делать.
`preview_from_plan` → `remainder=remainder_from_plan(plan, None)`;
`unified_into.into_preview` → `remainder_from_plan(plan, 0)`, `current` у кандидатов
входа №0 = True. Тесты в `tests/test_unified_import.py` / `test_unified_into.py`:
формы меток источника (один корень, несколько корней, архив, живой), детерминизм id
между двумя сборками плана, Р3 (чисто живая группа не попадает; живой узел + архивный
— попадает), дефолт спора поля при догрузке — кандидат `current`.

Тексты `how` / `if_left` по классам (финальные; класс узнаётся по устойчивой подстроке):
- «указывают один источник» / «разведите source» / «слиты в ОДИН объект»:
  how `Можно доработать прогоном агента. Пусть он задаст каждому объекту свой source.path — путь внутри репозитория — и выдаст файл заново. Чип файла подмените здесь же, без закрытия окна.`
  if_left `Если оставить: следующий прогон агента опознает по этому источнику только один из объектов. Второй при обновлении из кода станет дублем.`
  (для «слиты в ОДИН объект» if_left: `Если оставить: вместо нескольких объектов в проекте будет один, а их компоненты окажутся внутри него. Разделить их потом придётся руками.`)
- «встречается в файлах как РАЗНЫЕ объекты»:
  how `Можно доработать прогоном агента. Если это один объект, пусть агенты укажут ему один и тот же источник; если разные — дайте им разные имена. Файлы подмените здесь же.`
  if_left `Если оставить: в проекте будут два объекта с одним именем в одном контейнере. Различить их можно будет только по якорю в карточке.`
- «разные подписи из разных файлов»:
  how `Можно доработать прогоном агента. Пусть агент того файла, где подпись неточная, назовёт связь так же, как сосед, или уберёт дубль. Файл подмените здесь же.`
  if_left `Если оставить: между теми же объектами будут две связи с разными подписями. Лишнюю можно удалить на холсте.`
- «не имеют общих корневых узлов»:
  how `Можно доработать прогоном агента. Если это одна система, пусть все агенты назовут корень одинаково и выдадут файлы заново. Файлы подмените здесь же.`
  if_left `Если оставить: проект создастся с несколькими корнями, по одному на файл. Связи между ними можно дорисовать на холсте.`
- «внутри системы оказались люди»:
  how `Можно доработать прогоном агента. Пусть он вынесет людей из системы в корень схемы: по C4 человек пользуется системой, а не входит в неё. Файл подмените здесь же.`
  if_left `Если оставить: проект создастся, а панель незавершённости покажет этих людей внутри системы. Перенести их в корень можно перетаскиванием в дереве.`
- «объектов без единой связи»:
  how `Можно доработать прогоном агента. Пусть он проверит по коду, с чем взаимодействуют эти объекты, и дорисует связи. Файл подмените здесь же.`
  if_left `Если оставить: проект создастся, а объекты без связей будут ждать в панели незавершённости. Связи можно дорисовать на холсте.`
- «иерархия уже выражает вложенность» (связь с собственным потомком):
  how `Можно доработать прогоном агента. Пусть он уберёт связь между объектом и его собственной частью или перевесит её на компонент, с которым часть на самом деле взаимодействует. Файл подмените здесь же.`
  if_left `Если оставить: проект создастся, а такие связи будут ждать в панели незавершённости. Там же их можно удалить или перевесить.`
- «конец — брокер» / «канал не указан»:
  how `Можно доработать прогоном агента. Пусть он укажет у связи с брокером канал: имя топика или очереди из кода. Файл подмените здесь же.`
  if_left `Если оставить: проект создастся, а связь с брокером без канала будет ждать в панели незавершённости. Канал можно вписать в карточке связи.`
- «в channel перечень»:
  how `Можно доработать прогоном агента. Пусть он разведёт перечень каналов на отдельные связи, по одной на топик или очередь. Файл подмените здесь же.`
  if_left `Если оставить: проект создастся с одной связью, у которой в канале перечень. Панель незавершённости попросит разделить её.`
- любой другой класс (запасной вариант):
  how `Можно доработать прогоном агента. Унесите замечание агенту того файла, к которому оно относится, и подмените файл здесь же.`
  if_left `Если оставить: проект создастся, а замечание останется в отчёте импорта.`

**Шаг 4. Разбор `decisions` и применение при создании (`unified_apply.py`).**
`parse_decisions(raw: str | None) -> Decisions` (dataclass) по образцу `_parse_resolutions`
в роутере; валидация против плана — ДО любой записи (как `_winners`): id из
`remainder_from_plan(plan, None)`, `to_path` компонента — из `components` того же
элемента, пути новой связи — из `node_paths`, иначе 400 «Превью устарело — обновите
его и повторите». Применение (рекомендуемый порядок, метод — пример, цель — гейт):
1. Поля: до `seed_import` присвоить `merged.nodes[idx].<field>` значение кандидата.
2. Перевес: до `seed_import` заменить `source_idx`/`target_idx` связи индексом компонента

5. Строка отчёта «Ваши решения: …» в `warnings` результата.
