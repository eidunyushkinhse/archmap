# Локальный запуск ArchMap

Инструкция, чтобы поднимать проект самому — без участия Claude.

## TL;DR — быстрый старт

Если окружение уже настроено (см. «Первичная настройка» ниже), всё сводится к одной команде из корня проекта:

```bash
./dev.sh
```

Скрипт сам проверит Postgres, создаст БД при необходимости, применит миграции и поднимет бэк + фронт. Открывай **http://localhost:5173**. Остановить — **Ctrl+C** (гасит оба процесса разом).

Если что-то осталось висеть в фоне:

```bash
./stop.sh
```

---

## Что из чего состоит

| Сервис   | Адрес                       | Чем поднимается           |
|----------|-----------------------------|---------------------------|
| Frontend | http://localhost:5173       | Vite (`npm run dev`)      |
| Backend  | http://localhost:8000       | Uvicorn (FastAPI)         |
| Swagger  | http://localhost:8000/docs  | — встроен в бэкенд        |
| Postgres | localhost:5432, БД `archmap`| системная служба          |

Фронт ходит в бэк через прокси Vite: запросы на `/api` проксируются на `localhost:8000` (см. `frontend/vite.config.ts`). Отдельный URL прописывать не нужно.

## Первичная настройка (один раз)

Нужна, если клонировал проект заново или снёс venv/node_modules.

### 1. Postgres

Должен быть установлен и запущен, БД создаст скрипт. Проверить, что служба жива:

```bash
pg_isready -h localhost -p 5432        # → accepting connections
# если нет — запустить:
sudo service postgresql start          # или: sudo systemctl start postgresql
```

Дефолтные доступы (зашиты в `backend/app/config.py`): пользователь `postgres`, пароль `postgres`, БД `archmap`.

### 2. Бэкенд — venv и зависимости

```bash
cd backend
python3 -m venv venv
./venv/bin/pip install -r requirements.txt
```

(Опционально) свои доступы к БД/секрет — через `.env`:

```bash
cp .env.example .env       # потом поправить значения при необходимости
```

### 3. Фронтенд — зависимости

```bash
cd frontend
npm install
```

После этого `./dev.sh` поднимет всё сам.

## Ручной запуск (без скрипта)

Если хочется по отдельности — в двух терминалах:

**Терминал 1 — бэкенд:**
```bash
cd backend
./venv/bin/alembic upgrade head          # применить миграции
./venv/bin/uvicorn app.main:app --reload --port 8000
```

**Терминал 2 — фронтенд:**
```bash
cd frontend
npm run dev
```

## Частые проблемы

- **`Postgres не отвечает`** — служба не запущена: `sudo service postgresql start`.
- **`Не найден backend/venv`** — не сделана первичная настройка (см. шаг 2).
- **Порт занят (8000/5173)** — остался висеть старый процесс: `./stop.sh`, затем снова `./dev.sh`. Либо запустить на других портах: `BACKEND_PORT=8001 FRONTEND_PORT=5174 ./dev.sh`.
- **Ошибки про отсутствующие таблицы/колонки** — не накатились миграции: `cd backend && ./venv/bin/alembic upgrade head`.

## Пользователи и администратор

Учётки бывают двух общих ролей: **architect** (может создавать проекты) и **viewer** (не может). Отдельно от роли у пользователя есть признак **администратора**: он управляет людьми на экране «Пользователи» (меню профиля → «Пользователи») и при этом остаётся architect или viewer.

**Доступ к проектам** — по участникам (spec.md, «Доступ к проектам»): внутри проекта права решает роль в нём (владелец, редактор, читатель), а не общая роль; чужой проект без флажка «Виден всем пользователям» не виден вовсе. Участников и видимость задаёт владелец в окне «Доступ» (меню ⋯ карточки проекта). Администратор видит все проекты и в любом действует как владелец: это и путь починить доступ, если владелец недоступен.

**Первый администратор** создаётся командой на сервере, без интернета и без регистрации:

```bash
cd backend
./venv/bin/python -m app.admin create-admin <логин> [--role architect|viewer]
```

Пароль команда спросит в консоли дважды (в аргументах его нет). Новому пользователю по умолчанию достаётся роль architect. Если пользователь с таким логином уже есть, команда делает его администратором, снимает блокировку и не трогает пароль; `--role` меняет роль, `--reset-password` спрашивает новый пароль. Это же путь восстановления доступа, если администраторов не осталось.

Дальше администратор заводит людей на экране «Пользователи»: логин, роль, признак администратора и временный пароль, который он передаёт человеку сам (почты нет). Человек меняет его пунктом меню профиля «Сменить пароль». Пароль не короче 8 символов. Удаления нет: вместо него блокировка (заблокированный не входит, его открытые сессии закрываются сразу).

**Открытая регистрация** (`POST /api/v1/auth/register`, роль выбирает сам регистрирующийся) управляется настройкой `ALLOW_SIGNUP` в `backend/.env`:

- `ALLOW_SIGNUP=true` (по умолчанию) — как раньше: регистрация открыта;
- `ALLOW_SIGNUP=false` — регистрация отвечает 403, учётки заводит только администратор. Так настраивают закрытый контур.

Регистрация никогда не даёт прав администратора. Текущее значение настройки отдаёт `GET /api/v1/auth/config` (без авторизации).

## Демо-режим (публичный стенд)

Режим, а не форк: `DEMO_MODE=true` в окружении или `backend/.env` (поведение — spec.md, «Демо-режим»). Вместо формы входа — «Попробовать без регистрации»: каждый посетитель получает личную песочницу (временный гость и его копия «Ярмарки»), которая живёт сутки бездействия. Вход по логину и регистрация выключены, проекты ограничены пределами (100 объектов, 120 связей, 75 схем логики, 10 процессов, 250 КБ текста, файл до 250 КБ; константы в `backend/app/demo.py`).

Настройки (`backend/app/config.py`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `DEMO_MODE` | `false` | включает демо-режим |
| `DEMO_MAX_SANDBOXES` | `300` | сколько живых песочниц разом; дальше «На демо сейчас слишком много пользователей…» |
| `DEMO_START_PER_IP_PER_HOUR` | `10` | сколько песочниц в час с одного адреса (счётчик в памяти процесса) |

Уборка просроченных песочниц идёт сама раз в 10 минут, пока работает приложение. Администрирование стенда — только командами на сервере:

```bash
cd backend
./venv/bin/python -m app.admin demo-stats                  # живые песочницы, проекты гостей, самые давние
./venv/bin/python -m app.admin demo-cleanup                 # убрать песочницы без активности дольше суток
./venv/bin/python -m app.admin demo-cleanup --idle-hours 0  # убрать все песочницы сейчас
```

Команды берут БД из `DATABASE_URL` (окружение важнее `.env`): для локального демо — `DATABASE_URL=postgresql://postgres:postgres@localhost:5432/archmap_demo`.

**Демо локально рядом с основным сервисом** — второй экземпляр со своей БД `archmap_demo` на портах 8001/5174:

```bash
scripts/dev-demo.sh         # поднять (терминал занят, как у ./dev.sh; Ctrl+C гасит)
scripts/dev-demo.sh stop    # остановить только демо-экземпляр
```

Открывать **http://localhost:5174**. Скрипт — обёртка над `./dev.sh`: переменные окружения (`DATABASE_URL`, `DEMO_MODE=true`, `CORS_ORIGINS`, порты) перекрывают `backend/.env` основного экземпляра, миграции накатываются в `archmap_demo`, прокси Vite второго фронта смотрит на 8001 (`frontend/vite.config.ts` читает `BACKEND_PORT`). `./stop.sh` для демо не годится: он гасит все uvicorn и vite, включая основной экземпляр.

## Переменные окружения для `dev.sh`

Все необязательные, можно переопределить перед запуском:

```bash
BACKEND_PORT=8001 FRONTEND_PORT=5174 DB_NAME=archmap_test ./dev.sh
```

Доступны: `BACKEND_PORT`, `FRONTEND_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`. Прокси Vite (`/api`) идёт на `BACKEND_PORT`, поэтому второй экземпляр на других портах ходит в свой бэкенд. Переменные окружения бэкенда (`DATABASE_URL`, `DEMO_MODE` и другие из `config.py`) важнее значений в `backend/.env`.
