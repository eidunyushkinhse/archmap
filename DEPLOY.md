# Развёртывание ArchMap

Три способа — от «попробовать» до своего кластера. Внешних запросов приложение не делает.

- [Docker Compose](#docker-compose) — одна команда на своей машине: ArchMap и PostgreSQL в
  двух контейнерах.
- [Kubernetes](#kubernetes) — Helm-чарт и образ для linux/amd64 и linux/arm64.
- [Сервер без Kubernetes](#сервер-без-kubernetes) — архив с переносным Python, служба
  systemd и nginx; ставится и на сервер без интернета.

Во всех трёх ArchMap сразу принимает ИИ-агентов пользователей по адресу `…/mcp` — см.
[ИИ-агенты (MCP)](#ии-агенты-mcp).

## Docker Compose

ArchMap и PostgreSQL в двух контейнерах на одной машине. Нужны Docker с Compose v2 и
интернет: образ собирается из исходников, Node.js и Python ставятся внутри сборки.

```bash
git clone https://github.com/eidunyushkinhse/archmap.git
cd archmap
docker compose up -d
docker compose exec archmap archmap-admin create-admin admin
```

Первая сборка занимает несколько минут. Интерфейс — http://localhost:8080: войдите
администратором, остальных пользователей заведите на экране «Пользователи».

- **Данные** — в томах `archmap_db` (база) и `archmap_data` (ключ подписи входа: создаётся
  при первом старте; свой ключ задаёт переменная `SECRET_KEY` сервиса `archmap`).
- **Порт и пароль базы** — переменные `ARCHMAP_PORT` и `POSTGRES_PASSWORD` в файле `.env`
  рядом с `compose.yaml`. Пароль задаётся до первого запуска: PostgreSQL запоминает его при
  создании тома.
- **Обновление:** `git pull && docker compose up -d --build` — миграции применяются при
  старте контейнера.
- **Копия базы:** `docker compose exec db pg_dump -U archmap -Fc archmap > archmap.dump`.
- **Доступ для других.** Контейнер отдаёт http без TLS. Чтобы открыть ArchMap коллегам,
  поставьте перед ним обратный прокси с TLS. Прокси дописывает адрес клиента в
  `X-Forwarded-For`; тогда задайте сервису `archmap` `TRUST_FORWARDED_FOR: "true"`, иначе
  лимит попыток входа посчитает всех пользователей одним адресом прокси. Без прокси
  оставьте `false`: заголовок присылал бы сам клиент и обходил им лимит.

## Что нужно в любом случае

**PostgreSQL**
- Версия 15 или новее: схема использует `UNIQUE … NULLS NOT DISTINCT`. Проверено на 15.15 и 16.
- Отдельная база в UTF-8; пользователь ArchMap — её владелец. Расширения не нужны.
- ArchMap должен достучаться до PostgreSQL по сети.

**Адрес**
- Своё DNS-имя для ArchMap: приложение работает от корня адреса, подпуть вида
  `https://portal/archmap/` не поддерживается.
- TLS: по сети ходят пароли и токены входа.

## Подготовка базы (для администратора PostgreSQL)

```sql
CREATE ROLE archmap LOGIN PASSWORD '…';
CREATE DATABASE archmap OWNER archmap ENCODING 'UTF8' TEMPLATE template0;
```

И разрешить в `pg_hba.conf` подключение пользователя `archmap` к базе `archmap` с адресов,
откуда ходит ArchMap: узлов кластера или сервера. Таблицы ArchMap создаст сам.

В адресе базы спецсимволы пароля кодируются: `@` → `%40`, `:` → `%3A`, `/` → `%2F`,
`%` → `%25`, `#` → `%23`, `?` → `%3F`. Если PostgreSQL требует TLS, допишите к адресу
`?sslmode=require`.

## Kubernetes

Helm-чарт `deploy/helm/archmap`. В поде один процесс отдаёт и API, и интерфейс; перед его
стартом init-контейнер проверяет базу и применяет миграции. Под работает без root и
привилегий, с корневой ФС только для чтения — проходит Pod Security «restricted». База
PostgreSQL — своя, внешняя (см. «Что нужно в любом случае»): чарт её не ставит.

### Что нужно

- Kubernetes 1.25 или новее (в CI чарт ставится в kind), Helm 3.8+.
- Способ опубликовать сервис с TLS: Gateway API (HTTPRoute к Gateway кластера) или
  Ingress-контроллер.
- Сетевой доступ из подов к PostgreSQL.
- Ресурсы пода по умолчанию: запрос 0,1 CPU и 256 МБ, предел 1 ГБ.

### Образ

Готовый — `ghcr.io/eidunyushkinhse/archmap:<версия>` для linux/amd64 и linux/arm64,
чарт — `oci://ghcr.io/eidunyushkinhse/charts/archmap`; выпускаются по тегам версий.
Чарт по умолчанию берёт образ своей версии.

Свой образ — из исходников, в свой реестр:
```bash
docker build -t registry.example.com/archmap:1.0.0 .
docker push registry.example.com/archmap:1.0.0
```
и при установке `--set image.repository=registry.example.com/archmap --set image.tag=1.0.0`.
В кластер без интернета образ и чарт переносят обычным путём: `docker pull` (или `skopeo
copy`) готового образа в свой реестр и `helm pull oci://ghcr.io/eidunyushkinhse/charts/archmap
--version <версия>` — архив чарта ставится как локальный файл.

### Установка

1. Адрес базы и (по желанию) ключ подписи — в Secret:
   ```bash
   kubectl create namespace archmap
   kubectl -n archmap create secret generic archmap-db \
     --from-literal=database-url='postgresql://archmap:ПАРОЛЬ@pg.example.com:5432/archmap'
   ```
   Ключ подписи токенов входа чарт создаст сам и сохранит при обновлениях. Свой —
   `secretKey.existingSecret` (Secret с ключом `secret-key`, не короче 32 символов).
2. Установите чарт. С Gateway API:
   ```bash
   helm install archmap oci://ghcr.io/eidunyushkinhse/charts/archmap -n archmap \
     --set database.existingSecret=archmap-db \
     --set httpRoute.enabled=true \
     --set 'httpRoute.parentRefs[0].name=main-gateway' \
     --set 'httpRoute.parentRefs[0].namespace=gateway-system' \
     --set 'httpRoute.hostnames[0]=archmap.example.com' \
     --wait
   ```
   С Ingress вместо HTTPRoute — `ingress.enabled=true`, `ingress.className`, `ingress.hosts`
   и `ingress.tls` (как у обычных чартов). Из клона репозитория вместо
   `oci://…` — `./deploy/helm/archmap`. Все настройки — в `deploy/helm/archmap/values.yaml`.
3. Проверка и первый администратор (пароль команда спросит дважды):
   ```bash
   helm test archmap -n archmap
   kubectl -n archmap exec -it deploy/archmap -c archmap -- archmap-admin create-admin admin
   ```
4. Откройте адрес, войдите и заведите людей на экране «Пользователи» (меню профиля). Почты
   нет: временный пароль администратор передаёт сам, человек меняет его в меню профиля.

**Что требуется от Gateway или Ingress.** TLS; ответ до 300 с (ввоз большого архива) — у
HTTPRoute чарт задаёт `timeouts.request` сам, у Ingress это аннотации контроллера в
`ingress.annotations`; тело запроса не меньше `config.maxRequestMb` (64 МБ); адрес клиента
дописывается последним в `X-Forwarded-For` (так делают все распространённые контроллеры) —
по нему считаются попытки входа. Если перед подом нет прокси (Service типа LoadBalancer
наружу), задайте `config.trustForwardedFor=false`: иначе заголовок присылает сам клиент.

### Что где

| Объект | Что это |
|---|---|
| Deployment `archmap` | init-контейнер `migrate` (проверка базы и миграции) и приложение на порту 8080 |
| Service `archmap` | порт 80 внутри кластера |
| Secret `archmap` | `database-url` (если нет `database.existingSecret`) и `secret-key` |
| HTTPRoute или Ingress `archmap` | вход снаружи, если включён |

### Настройки

| Значение чарта | По умолчанию | Что задаёт |
|---|---|---|
| `config.allowSignup` | `false` | самостоятельная регистрация |
| `config.workers` | `2` | рабочих процессов uvicorn в поде |
| `config.loginAttemptsPerMinute` | `10` | неудачных попыток входа в минуту с адреса, дальше отказ; `0` — без ограничения |
| `config.maxRequestMb` | `64` | предел размера запроса (ввоз архива проекта) |
| `config.trustForwardedFor` | `true` | адрес клиента — последний в `X-Forwarded-For` (за Gateway/Ingress) |
| `extraEnv` | — | другие переменные из `backend/.env.example` |
| `replicaCount` | `1` | число подов; миграции при этом идут по очереди (блокировка в базе) |

Каждый рабочий процесс держит до 15 соединений с PostgreSQL: сверьте `max_connections`
базы с произведением «реплики × workers × 15». Попытки входа каждый процесс считает сам,
поэтому реальный предел — `loginAttemptsPerMinute`, умноженное на число процессов во всех
подах. Удачные входы не считаются.

### Обновление

Сделайте резервную копию базы (см. ниже) и обновите релиз:
```bash
helm upgrade archmap oci://ghcr.io/eidunyushkinhse/charts/archmap -n archmap --version <новая> --reuse-values --wait
```
Новый под сначала применяет миграции в init-контейнере, затем сменяет старый. Миграции
ArchMap аддитивные: старый под до остановки работает и с новой схемой. Ключ подписи
сохраняется — пользователей не разлогинит.

**Откат.** `helm rollback archmap -n archmap`. Если новая версия уже изменила схему так,
что прежний код с ней не работает, сначала восстановите базу из резервной копии.

### Если что-то не так

- **Под в `Init:Error` или `Init:CrashLoopBackOff`.** Init-контейнер не прошёл проверку
  базы или миграции: `kubectl -n archmap logs <под> -c migrate`. Сообщение «БАЗА: …»
  называет, что поправить: подключение, версию, кодировку или права.
- **`ImagePullBackOff`.** Неверный `image.repository`/`image.tag` или у namespace нет доступа
  к реестру (`imagePullSecrets`).
- **`CreateContainerConfigError`.** Нет Secret из `database.existingSecret` или в нём другое
  имя ключа (`database.existingSecretKey`).
- **Долгий ввоз обрывается или отвечает 413.** Тайм-аут или предел тела у Gateway/Ingress —
  см. «Что требуется от Gateway или Ingress».
- **«Слишком много попыток входа» у всех сразу.** Перед подом прокси, а
  `config.trustForwardedFor=false`: все пользователи видны одним адресом.
- **Администратор потерял доступ.**
  `kubectl -n archmap exec -it deploy/archmap -c archmap -- archmap-admin create-admin <логин> --reset-password`:
  команда делает пользователя администратором, снимает блокировку и задаёт новый пароль.
- **Журнал приложения.** `kubectl -n archmap logs deploy/archmap`.

## Сервер без Kubernetes

ArchMap ставится на голый Linux-сервер из одного архива. На сервере не нужны ни Python,
ни Node.js: в поставке переносной Python со всеми зависимостями, бэкенд и собранный фронт.

### Что нужно

- Linux x86_64 с systemd и glibc 2.17 или новее (подходит любой дистрибутив последних лет).
- root или sudo на время установки.
- nginx из репозитория дистрибутива. Если перед сервером уже стоит свой обратный прокси,
  можно обойтись без nginx (см. «Без nginx»).
- 1–2 ГБ памяти, около 1 ГБ на диске: установщик хранит три последних релиза по ~220 МБ.

### Сборка поставки

На машине с интернетом (Linux x86_64, git, Node.js 22+, curl), из репозитория:

```bash
deploy/build-bundle.sh
```

Получится `dist-bundle/archmap-<дата>-<коммит>-linux-x86_64.tar.gz` (около 55 МБ) и файл
с его контрольной суммой. Поставка собирается из закоммиченного состояния; пробная сборка
с незакоммиченными правками — `deploy/build-bundle.sh --worktree`.

### Установка

1. Перенесите архив и `.sha256` на сервер и проверьте целостность:
   ```bash
   sha256sum -c archmap-*.tar.gz.sha256
   tar -xzf archmap-*.tar.gz && cd archmap-*-linux-x86_64
   ```
2. Запустите установщик:
   ```bash
   sudo ./deploy/install.sh --server-name archmap.example.local \
     --tls-cert /etc/ssl/archmap.crt --tls-key /etc/ssl/archmap.key
   ```
   Без TLS (только для тестового сегмента) — без двух последних параметров.
   Первый запуск создаёт `/etc/archmap/archmap.env` со случайным `SECRET_KEY` и останавливается.
3. Впишите в `/etc/archmap/archmap.env` адрес базы:
   ```
   DATABASE_URL=postgresql://archmap:ПАРОЛЬ@pg.example.local:5432/archmap
   ```
4. Запустите ту же команду ещё раз. Установщик проверит базу (версию, кодировку, права),
   применит миграции, разложит релиз в `/opt/archmap`, запустит службу `archmap` и настроит nginx.
5. Создайте первого администратора — пароль команда спросит дважды:
   ```bash
   sudo archmap-admin create-admin <логин>
   ```
6. Откройте `https://archmap.example.local`, войдите и заведите людей на экране
   «Пользователи».

### Что где лежит

| Путь | Что это |
|---|---|
| `/opt/archmap/releases/<версия>` | релизы (хранятся три последних) |
| `/opt/archmap/current` | ссылка на работающий релиз |
| `/etc/archmap/archmap.env` | настройки (права 640, root:archmap) |
| `/etc/systemd/system/archmap.service` | служба; работает от пользователя `archmap` |
| `/etc/nginx/conf.d/archmap.conf` | сайт в nginx |
| `/usr/local/bin/archmap-admin` | команды администрирования |

### Настройки

Файл `/etc/archmap/archmap.env`, после правки — `sudo systemctl restart archmap`.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `DATABASE_URL` | — | адрес PostgreSQL |
| `SECRET_KEY` | случайный | подпись токенов входа; смена ключа разлогинит всех |
| `ALLOW_SIGNUP` | `false` | самостоятельная регистрация; в закрытом контуре выключена |
| `CORS_ORIGINS` | адрес из `--server-name` | адрес, с которого открывают ArchMap |
| `ARCHMAP_PORT` | `8000` | порт бэкенда на 127.0.0.1 (к нему ходит nginx) |
| `ARCHMAP_WORKERS` | `2` | рабочие процессы бэкенда; при заметной нагрузке — 4 |

Каждый процесс держит до 15 соединений с PostgreSQL: проверьте `max_connections`, если
поднимаете число процессов.

### Обновление

Распакуйте новую поставку и запустите установщик без параметров:
```bash
sudo ./deploy/install.sh
```
Он сделает копию базы, применит миграции, переключит `/opt/archmap/current` на новый релиз
и перезапустит службу. Настройки и конфигурация nginx не трогаются.

**Сервер, поставленный до версии с удалённым MCP.** Раз конфигурация nginx не
переписывается, в ней нет пути `/mcp`: агенты не подключатся (nginx ответит 405 или
страницей интерфейса), а установщик напишет об этом предупреждение. Добавьте в
`/etc/nginx/conf.d/archmap.conf`, в `server { … }` рядом с `location /api/`:

```nginx
location = /mcp {
    proxy_pass http://archmap_backend;
    proxy_read_timeout 300s;
    proxy_buffering off;
}
location ^~ /.well-known/oauth- {
    proxy_pass http://archmap_backend;
}
```

и выполните `sudo nginx -t && sudo systemctl reload nginx`. Если конфигурацию писал
установщик, можно вместо этого запустить его с прежним `--server-name` (и `--tls-cert`,
`--tls-key`, если они были) — он перепишет её целиком, со всеми путями новой версии.

**Копия базы перед миграциями.** Если новая версия меняет схему, установщик сначала делает
`pg_dump -Fc` в `/opt/archmap/backups` (каталог `700`, файлы `600`; другой каталог —
переменная `ARCHMAP_BACKUP_DIR`) и хранит последние пять копий. Когда схема уже актуальна,
копия не делается. Нужен `pg_dump` той же или более новой версии, что сервер базы (пакет
`postgresql-client`); если его нет или копия не удалась, установка останавливается до
миграций. Копию можно сделать самому (см. «Резервные копии») и запустить установщик с
`--no-backup`.

**Откат.** Если новый релиз за минуту не ответил на `/ready`, установщик сам вернёт
прежний релиз (симлинк и юнит службы), перезапустит службу и завершится с ошибкой — сервис
не остаётся лежать. Схема базы при этом уже новая: миграции ArchMap аддитивные, и прежний
код с ней обычно работает. Откатить вручную после удачного обновления — командой, которую
установщик печатает в конце; если новый релиз изменил схему базы так, что прежний код с ней
не работает, сначала восстановите базу из резервной копии.

### Повседневное

- Состояние и журнал: `systemctl status archmap`, `journalctl -u archmap -f`.
- Проверка бэкенда: `curl -s http://127.0.0.1:8000/health` → `{"status":"ok"}` (процесс жив);
  `curl -s http://127.0.0.1:8000/ready` → `{"status":"ok"}`, если база отвечает, иначе 503.
- Восстановить доступ администратору: `sudo archmap-admin create-admin <логин> --reset-password`
  (команда делает пользователя администратором, снимает блокировку и задаёт новый пароль).

### Журналы

Своих файлов журнала у ArchMap нет: система для службы только для чтения.

| Что | Где | Кто ротирует |
|---|---|---|
| бэкенд: строка на каждый запрос (метод, путь, код ответа, адрес) и ошибки с трассировкой | journald: `journalctl -u archmap` | journald |
| nginx: доступ и ошибки | `/var/log/nginx/access.log`, `error.log` — установщик своих путей не задаёт | logrotate из пакета nginx (`/etc/logrotate.d/nginx`) |
| установщик | только терминал; сохранить — `sudo ./deploy/install.sh 2>&1 \| tee install.log` | — |

Пароли и токены входа в журналы не попадают: они идут в теле запроса и в заголовке, а не в
адресе. Запросы к `/health` и `/ready` nginx в журнал доступа не пишет.

Объём и срок хранения журнала службы задаёт journald, например
`/etc/systemd/journald.conf.d/archmap.conf`:
```ini
[Journal]
Storage=persistent
SystemMaxUse=1G
MaxRetentionSec=90day
```
и `sudo systemctl restart systemd-journald`. Без `Storage=persistent` (или каталога
`/var/log/journal`) некоторые системы держат журнал только в памяти, и после перезагрузки он
пропадает. Если журналы собирает центральная система, забирайте их из journald и nginx
штатным агентом сбора.

В Kubernetes журнал — `kubectl logs deploy/archmap` (бэкенд пишет только в stdout); сколько
он хранится, решает сбор журналов кластера.

### Если что-то не так

- **«Встроенный Python не запускается».** Каталог поставки смонтирован с `noexec`;
  на Astra Linux SE включена замкнутая программная среда — она запускает только
  подписанные программы; политика SELinux запрещает запуск (`ausearch -m avc`).
- **nginx отвечает 502.** Служба не работает: `journalctl -u archmap -n 50`. При включённом
  SELinux nginx нужно право обращаться к бэкенду — установщик выставляет
  `httpd_can_network_connect` сам.
- **Ввоз архива падает с 413.** Ограничение размера запроса: nginx от установщика принимает
  до 64 МБ; если перед ним стоит ещё один прокси, поднимите лимит и там.
- **«Слишком много попыток входа».** nginx пропускает 10 попыток входа в минуту с адреса.
  Если все пользователи приходят через один прокси (один адрес), поднимите `rate` в
  `/etc/nginx/conf.d/archmap.conf` и выполните `sudo systemctl reload nginx`.
- **Установщик остановился на проверке базы.** Сообщение называет, что поправить: версию,
  кодировку или права пользователя.

### Без nginx

`sudo ./deploy/install.sh --no-nginx` ставит только службу. Тогда ваш обратный прокси
должен отдавать файлы из `/opt/archmap/current/frontend` (для неизвестных путей —
`index.html`), проксировать на `127.0.0.1:8000` пути `/api/`, `/mcp` (с таймаутом ответа
300 с — см. «ИИ-агенты (MCP)») и `/.well-known/oauth-…` и принимать запросы до 64 МБ.
Образец — конфигурация, которую установщик пишет для nginx (функция `render_nginx` в
`deploy/install.sh`).

`--no-systemd` — то же для службы: установщик пишет юнит в `/etc/systemd/system`, но не
включает и не запускает его; бэкенд запускаете своим супервизором командой из `ExecStart`
юнита, а готовность проверяете по `/ready`.

### Публичный сервер: Let's Encrypt и демо-режим

Так поднят публичный стенд https://demo.archmap.tech. Сертификат Let's Encrypt выпускается
после первой установки по http, затем установщик запускается ещё раз уже с ним:

```bash
sudo ./deploy/install.sh --server-name demo.example.org
sudo certbot certonly --nginx -d demo.example.org --deploy-hook "systemctl reload nginx"
sudo ./deploy/install.sh --server-name demo.example.org \
  --tls-cert /etc/letsencrypt/live/demo.example.org/fullchain.pem \
  --tls-key /etc/letsencrypt/live/demo.example.org/privkey.pem
```

Сертификат продлевает `certbot.timer`, после продления nginx перечитывает его
(`--deploy-hook`). Первая установка по http записала в `CORS_ORIGINS` адрес с `http://` —
исправьте на `https://`.

Демо-режим — `DEMO_MODE=true` в `archmap.env`: вход только гостем, у каждого гостя своя
песочница с пределами, через сутки бездействия она удаляется. Процесс на демо один
(`ARCHMAP_WORKERS=1`): уборка песочниц и счётчик стартов с адреса живут внутри процесса —
с двумя процессами уборка шла бы наперегонки, а лимит стартов удвоился бы. Адрес гостя
бэкенд берёт последним в `X-Forwarded-For`: его дописывает nginx, так что подделать адрес
клиент не может.

Сервер, открытый в интернет, перебирают сразу: на стенде за первую неделю было почти 87 тысяч
попыток подобрать пароль SSH. Вход — только по ключу (файл в `/etc/ssh/sshd_config.d/`, который
читается раньше `50-cloud-init.conf`: `PasswordAuthentication no`, `PermitRootLogin
prohibit-password`), входящие — только 22, 80 и 443 (`ufw default deny incoming`, затем `ufw
allow` на эти порты и на агента мониторинга провайдера с его адресов). Включая файрвол по SSH,
поставьте страховку `systemd-run --on-active=600 --unit=ufw-rescue ufw disable` и снимите её
(`systemctl stop ufw-rescue.timer`), когда новое соединение пройдёт.

## Резервные копии

Всё состояние ArchMap — в базе, на диске приложение ничего не хранит.

```bash
pg_dump -Fc -h pg.example.local -U archmap archmap > archmap-$(date +%F).dump
pg_restore --clean --if-exists -h pg.example.local -U archmap -d archmap archmap-ГГГГ-ММ-ДД.dump
```

Отдельный проект можно выгрузить архивом из интерфейса — меню «Действия со схемой»
(три точки в шапке) → «Экспорт проекта (zip)» — и ввезти на другом экземпляре.

## ИИ-агенты (MCP)

ИИ-агент пользователя (Claude Code, Cursor, VS Code, Qwen Code) подключается к ArchMap по
адресу интерфейса плюс `/mcp` — например, `https://archmap.example.com/mcp` — с личным
токеном. Токен пользователь выпускает сам: меню профиля → «Токены для агентов»; окно сразу
показывает строки подключения. На машины пользователей ставить ничего не нужно;
подробности для пользователей — `mcp/README.md`.

- **Отдельной службы нет.** Эндпоинт живёт в процессе бэкенда. В Docker Compose и
  Kubernetes `/mcp` идёт тем же путём, что интерфейс; на сервере nginx от установщика ведёт
  его в бэкенд (при обновлении старой установки — см. «Обновление»).
- **Только HTTPS вне localhost**: токен в заголовке — тот же пароль.
- **Прокси перед ArchMap** (Ingress, свой обратный прокси): таймаут ответа на `/mcp` — 300
  с (превью крупного пакета документации считается дольше минуты), тело — до
  `MAX_REQUEST_MB`. Ответы — обычный JSON, буферизация не мешает. `/.well-known/oauth-…` —
  тоже в бэкенд: клиенты MCP ищут там метаданные OAuth и должны получить 404 JSON, а не
  страницу интерфейса.
- **Права агента** — права владельца токена, кроме удалений, «Принять переход», управления
  проектом (карточка, видимость, архив, участники, передача), администрирования, смены
  пароля и токенов. Токен «только чтение» ничего не меняет.
- **Лимиты** — запросов по одному токену `MCP_REQUESTS_PER_MINUTE` в минуту (по умолчанию
  300, `0` — без предела) и 30 неудачных проверок токена в минуту с адреса. Считает каждый
  рабочий процесс сам, поэтому предел приблизительный: умножьте на число процессов. В
  Kubernetes переменная задаётся через `extraEnv`.
- **Origin.** Агенты его не шлют. Запрос из браузера с заголовком `Origin`, которого нет в
  `MCP_ALLOWED_ORIGINS` (по умолчанию пусто), получит 403 — защита от чужих страниц.
- **Журнал** — строка на каждый вызов инструмента в журнале службы (`journalctl -u
  archmap`, `docker compose logs archmap`, `kubectl logs`), логгер `archmap.mcp`:
  пользователь, токен (имя и начало), инструмент, проект, итог (ок / отказ / сбой),
  длительность и адрес. Аргументы не пишутся — в них документы целиком.
- **Демо-режим** (`DEMO_MODE=true`): `/mcp` выключен (404), токены не выпускаются.
- **Файлы.** Ввоз и выгрузка архивов удалённо недоступны: «диском агента» был бы диск
  сервера. Для них остаётся локальный вариант MCP-сервера из `mcp/` — с тем же токеном.

## Безопасность

- Регистрации нет (`ALLOW_SIGNUP=false`): учётки заводит администратор.
- Неудачные попытки входа ограничены: в Kubernetes и Docker Compose — самим приложением, на
  сервере — nginx.
- Swagger и описание API наружу не отдаются.
- Личные токены ИИ-агентов хранятся только хэшем (sha256), сам токен показывается один раз
  при выпуске. Срок — 30 или 90 дней, год или бессрочно; отзыв — в меню профиля,
  блокировка учётки гасит её токены сразу. Токеном нельзя удалять, управлять проектом и
  пользователями, менять пароль и выпускать новые токены (см. «ИИ-агенты (MCP)»).
- В Kubernetes под работает без root и привилегий (UID 10001, все capabilities сброшены,
  seccomp RuntimeDefault) и проходит Pod Security «restricted»; корневая файловая система
  только для чтения, токен сервис-аккаунта в под не монтируется.
- На сервере служба работает от непривилегированного пользователя `archmap`, система для
  неё только для чтения; ядро, устройства, пространства имён и привилегии для неё закрыты
  песочницей systemd (`systemd-analyze security archmap` — около 1.5, «OK»). Если своя
  среда требует ослабить ограничение, делайте это через `systemctl edit archmap`: сам юнит
  перезаписывается при обновлении.
- Без TLS пароли и токены идут открытым текстом — так можно только в доверенном тестовом сегменте.
- Заголовки безопасности у каждого ответа — и в контейнере (их ставит приложение), и на
  сервере (их пишет nginx): `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`,
  `Permissions-Policy` без камеры, микрофона и геолокации, `Content-Security-Policy` с
  `frame-ancestors 'none'` — ArchMap нельзя встроить в чужую страницу (iframe). Полная
  политика источников пока в режиме `Content-Security-Policy-Report-Only`: нарушения видны в
  консоли браузера, но ничего не блокируют. HSTS на сервере nginx ставит в TLS-ветке; в
  Kubernetes его задаёт тот, кто держит TLS (Gateway или Ingress-контроллер).
- На сервере nginx ограничивает и регистрацию (3 в минуту с адреса), и старт песочницы
  демо (6 в минуту); версию nginx не называет (`server_tokens off`).
- Установщик не перезаписывает уже существующий конфиг nginx: заголовки и лимиты новой
  версии попадут в него при установке с `--server-name` (если конфиг писал установщик) или
  правкой по образцу `render_nginx` в `deploy/install.sh`.

## Ограничения

- Только x86_64.
- Вход через доменные учётные записи (AD/LDAP) пока не поддерживается.
- Документирование кода ИИ-агентом (BYOA, MCP) работает с теми агентами, что разрешены в
  контуре: агент подключается к `…/mcp` самого ArchMap или запускает локальный MCP-сервер
  из `mcp/`. Удалённо подключаются клиенты, которые умеют заголовок `Authorization`;
  Claude Desktop и коннекторы claude.ai ждут OAuth — его ArchMap пока не умеет.
