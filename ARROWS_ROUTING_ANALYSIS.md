# ЭПИК стрелок — глубокая аналитика (R1–R4)

Аналитический документ ПЕРЕД кодом. Цель — выбрать самый оптимальный способ
реализации требований архитектора к маршрутизации стрелок и размещению плашек на
**схеме уровня** (level graph). Решения по форкам — за архитектором (в конце).

Статус: аналитика, кода ещё нет. Полигон-симптомы и фазовый план — ниже.

---

## 0. Требования и их приоритет

Дословно (из tasks.md):
- **R1.** Кратчайший путь — но с учётом ВСЕХ остальных ограничений (не в ущерб им).
- **R2. КРИТИЧЕСКОЕ:** плашки с текстом НЕ наползают друг на друга и НЕ залезают под узлы.
- **R3.** Путь выбирается с НАИМЕНЬШИМ числом пересечений с другими стрелками.
- **R4.** Если две стрелки идут вместе (часть плеч совпадает до определённых изломов),
  плашки НЕ должны стоять на «совпадающих» плечах — только на однозначно своей части.

**Прочтение приоритета** (важно — оно определяет архитектуру):
R1 сформулирован как «кратчайший, НО с учётом остальных» → длина это **целевая функция
среди допустимых решений**, а не жёсткое ограничение. Тогда иерархия такая:

1. **R2 — жёсткое ограничение** (hard constraint). Плашка под узлом или поверх другой
   плашки недопустима в принципе.
2. **R3, R4 — структурные ограничения/штрафы** маршрута и размещения.
3. **R1 — целевая функция** (минимизируем длину среди тех маршрутов, что уже
   удовлетворяют R2/R3/R4).

Это разводит задачу на **минимизацию со штрафами** (routing) и **выполнимость с
запасным планом** (labels). Из приоритета сразу следует: чисто «кратчайший» маршрут
(евклид/манхэттен) — НЕ цель; цель — кратчайший из «хороших».

## 1. Что уже есть (на этом строим, не с нуля)

Движок уже зрелый — эпик его расширяет, а не заменяет.

**Раскладка узлов.** ELK `layered` (RIGHT, `nodeNodeBetweenLayers=120`, `nodeNode=60`),
`graph/layout/engine.ts`. ВАЖНО: мы берём из ELK **только позиции узлов**, маршруты
рёбер не берём. Для гостей позиции потом переопределяем (кольца `ringPlacement.ts`,
разведение `separateGuests.ts`, own-on-first-render).

**Геометрия ребра** — ортогональная ломаная `[S, …waypoints, T]`, чистый модуль
`graph/edgePath.ts` (под тестами): `orthogonalPointsForHandles`, `ensureOutwardStubs`,
`buildRenderPoints`. Рендер — `roundedPolyline` (скругление r=12) в `graph/edges.tsx`.
Хэндлы выбираются по доминирующей оси (`layout/level.ts autoHandles`).

**Обводы (detours)** — `graph/layout/detours.ts`: ТОЛЬКО для гостевых стрелок, чей
прямой путь пересекает чужие узлы. Пробный ортомаршрут + `pathCrossesRects`, обвод
сверху/снизу (`clearY`), параллельные обводы разносятся `DETOUR_STEP=30`. **Уступает
ручной правке** (если юзер трогал waypoints/хэндлы — обвод не применяется). Это
зародыш роутера — но узкий (только гость↔локал, только вверх/вниз, без учёта пересечений).

**Мостики (jumps)** — `edgeJumps.ts` + `EdgeJumpContext.tsx`: полудуги над
**перпендикулярными** пересечениями. Коллинеарные (наложенные) сегменты НЕ
обрабатываются — две стрелки на одном плече рисуются буквально одна поверх другой.

**Изломы (waypoints)** — ручные, три слоя хранения: локальная стрелка → колонка
`edges.waypoints`; гостевая/сквозная → таблица `edge_waypoints` пер-уровень (с
`anchor_node_id`, Ф3); мастер-стрелка → fan-out по членам.

**Плашки** — `graph/edges.tsx` + `edgePath.ts`. Позиция = доля arc-length
`label_t∈[0,1]` (дефолт — середина среднего сегмента, `pathMidpoint`). Перетаскивание
1D вдоль пути (`nearestFraction`). Габариты плашки меряются ПОСЛЕ рендера (getBBox) и
используются ТОЛЬКО для драга — **в размещении не участвуют**. **Анти-наложения нет.**

**Слияние параллельных** — рёбра одной пары (source,target) сливаются в мастер-стрелку
(один путь, буллет-список подписей). Разные пары с совпадающими плечами — НЕ
разводятся и НЕ детектируются (это и есть пробел R4).

**Контекст-схема** — отдельный дисциплинированный механизм (полки `EdgeShelf`, обходы
`EdgeLoop`, ширины подписей через `ctxLabelWidth`), `layout/context.ts`. Он R2/R4 в
своей модели уже во многом решает. **Эпик его не трогает** (scope — только level).

## 2. Класс задачи

Это классическая связка из graph drawing, и она **разбивается на два почти
независимых подмодуля** — это ключ к «оптимальной реализации»:

### (A) Ортогональная маршрутизация с обходом препятствий + минимизация пересечений — R1+R3
Эталон — **libavoid** (Adaptagrams). Каноническая схема в два прохода:
1. **Маршрут каждого ребра** как ортогонального кратчайшего пути по *visibility graph /
   Hanan-сетке* (линии, проведённые через границы всех узлов-препятствий + терминалы +
   зазор). A\* с весом = длина + штраф за поворот + штраф за пересечение + штраф за
   близость к узлу. Препятствия — ВСЕ видимые прямоугольники узлов.
2. **Расталкивание (nudging)** наложенных/параллельных плеч: упорядочить рёбра,
   проходящие по одному коридору, и развести их на несколько px, минимизируя пересечения.

Минимизация пересечений в общем виде NP-трудна; на практике решается (а) порядком
маршрутизации + (б) штрафом за crossing в A\* + (в) перестановкой в nudging.

### (B) Размещение подписей рёбер — R2+R4
Тоже изучено (edge label placement, родственно map labeling, NP-трудно в общем виде).
Прагматичная схема:
1. Для каждого ребра — **множество допустимых интервалов** на пути (в arc-length):
   вычесть участки под узлами (R2) и участки на «совпадающих плечах» (R4).
2. Разместить плашку (с её реальными габаритами!) внутри допустимых интервалов так,
   чтобы боксы плашек **не пересекались** между собой (R2). Это 1D-вдоль-пути или 2D
   де-оверлап → решаемо нашим **VPSC** (`vpsc.ts`, из Ф4!) либо greedy + локальный поиск.
3. Если допустимого места нет — **запасной план** (см. §3, конфликт R2∩R4).

Важно: **(A) и (B) разделимы** (сначала маршруты, потом плашки). Совместная
оптимизация (joint routing+labeling) даёт чуть лучший результат, но кратно сложнее и
нестабильна — НЕ рекомендуется для первой версии.

## 3. Конфликты требований (для решений архитектора)

1. **R1 ↔ R3.** Кратчайший путь может давать много пересечений; меньше пересечений —
   длиннее. Решается весовой функцией A\* (штрафы настраиваемы). Приоритет из §0:
   сначала меньше пересечений, длина — вторична.
2. **R2 (hard) ↔ R1.** Кратчайший маршрут может прижаться к узлам так, что для плашки
   нет чистого места. Чистый конвейер «маршрут → плашка» может НЕ выполнить R2. Лечится
   тем, что у нас плашка ездит вдоль ВСЕГО пути (не только середина) — почти всегда есть
   чистый интервал; в редком тупике — запасной план (ниже).
3. **R2 ↔ R4 (может быть невыполнимо).** Если две стрелки слиты почти целиком,
   «однозначно своя» часть короче плашки → места под R2+R4 нет. **Политика запасного
   плана — РЕШЕНО (см. §7):** сейчас — выноска-leader (a); предпочтительный апгрейд на
   будущее — двигать узлы, чтобы уникальное плечо стало длиннее текста (идея архитектора).
   Варианты, что рассматривались: (a) выноска-leader; (b) ослабить R4 (плашка на общем
   плече как последнее средство); (c) подпись только по наведению; (d) сузить/перенести.
4. **Авто-роутер ↔ ручные waypoints/хэндлы.** Если юзер кастомизировал ребро —
   авто-роутер не вмешивается (как уже делает detours). Подтвердить инвариант.
5. **R3 глобальна ↔ гибридная раскладка.** Пересечения считаются по ВСЕМ стрелкам
   сразу. Поэтому роутер должен быть **пост-раскладочным и единым** для локальных и
   гостевых рёбер (видеть их все). Сплит-роутер (ELK для локалов + своё для гостей) НЕ
   сможет минимизировать пересечения глобально — это аргумент против варианта R-3 ниже.
6. **R4: «слить» или «развести»?** Принципиальный выбор:
   - (4a) Оставить стрелки **визуально слитыми** на общих плечах (как просит R4
     буквально) и просто запретить там плашки. Чище визуально.
   - (4b) **Развести** общие плечи на параллельные рельсы (как делает libavoid nudging) →
     каждая стрелка получает свою линию, R4 автоматически отпадает, но картинка меняется
     (вместо одной линии — пучок). Архитектор описывал кейс «идут вместе» → вероятно (4a).
7. **Детерминизм/стабильность.** Маршруты не должны прыгать при мелких правках (у
   libavoid это известная боль). Нужна стабильная сортировка/якорение результата.
8. **Производительность.** Роутер + A\* на ребро + де-оверлап плашек крутятся на каждой
   раскладке (она уже async). Пересчитывать только при структурных изменениях, дебаунс.

## 4. Маршрутизация (R1+R3): build vs buy

### Вариант R-1 — РАЗВИТЬ СВОЁ (рекомендую)
Обобщить `detours.ts` в полноценный пост-раскладочный ортогональный роутер на TS:
- routing graph (Hanan-сетка по границам узлов+терминалы+зазор) → A\* с весами
  (длина + поворот + пересечение + близость к узлу);
- nudging наложенных плеч переиспользует **наш VPSC** (`vpsc.ts`);
- порядок маршрутизации + штраф crossing для R3.
- **Плюсы:** полный контроль; бесшовно с нашими хэндлами/waypoints/мастер/гость/detour
  (всё это надо уважать — чужой роутер будет с этим воевать); чистый TS, тестируемо
  модулями (как edgePath/vpsc/separate\*); нет WASM-веса; единый роутер → R3 глобально.
- **Минусы:** это серьёзный объём (по сути мини-libavoid); крайние случаи (стабильность,
  тупики) надо аккуратно отлаживать.

### Вариант R-2 — libavoid-js (WASM)
Готовый промышленный роутер (R1+R3+nudging «из коробки», penalty-модель).
- **Плюсы:** зрелые алгоритмы crossing-min и nudging; меньше своего кода для ядра.
- **Минусы:** в 8–11× медленнее нативного, грузится только async (+ ~сотни КБ WASM);
  он **владеет маршрутизацией** → конфликт с нашей моделью ручных waypoints/хэндлов/
  мастер-стрелок/гостевых слоёв и detours (всё переосмысливать в терминах его
  ConnEnd/Obstacle); плашки всё равно наши (R2/R4 он не делает); чёрный ящик при отладке
  стабильности. Интеграционная поверхность большая.

### Вариант R-3 — взять маршруты ELK для локальных рёбер
ELK умеет отдавать ортогональные `sections/bendPoints`. Для чисто-локального уровня —
качественно и почти «бесплатно» (мы уже платим за ELK).
- **Минусы:** ELK роутит в СВОЕЙ модели layered, а мы позиции гостей переопределяем →
  для гостей/колец маршруты ELK неверны; смешение двух роутеров не даёт глобального R3
  (см. конфликт §3.5); воюет с ручными waypoints. Годится лишь как частный случай, не
  как основа.

**Вывод по маршрутизации:** **R-1 (своё)**. Наш слой уже наполовину туда идёт
(detours+edgeJumps+edgePath+vpsc), а главное — единый пост-раскладочный роутер
обязателен для глобального R3 и для сосуществования с ручными правками. libavoid-js
держать как план Б, если своё ядро crossing-min окажется неподъёмным по качеству.

## 5. Плашки (R2+R4)

1. **Габариты плашки ДО размещения.** Сейчас меряются после рендера. Нужен либо
   measure-pass (скрытый рендер/canvas measureText), либо оценка как `ctxLabelWidth`
   (моноширинная) обобщённая на level. Без габаритов R2 не выполнить → это предусловие.
2. **Допустимые интервалы.** На arc-length пути вычесть: (а) проекции прямоугольников
   узлов +зазор (R2-«не под узлами»); (б) совпадающие плечи (R4) — детект коллинеарных
   наложенных под-сегментов между рёбрами (порог по px). Остаток = кандидаты.
3. **Размещение без наложений (R2-«не друг на друга»).** Боксы плашек в кандидат-
   интервалах развести так, чтобы не пересекались. Варианты: VPSC вдоль общей оси/в 2D;
   либо greedy (поставить в дефолт-центр своего лучшего интервала) + локальный поиск
   разрешения коллизий. Переиспользуем `vpsc.ts`.
4. **Запасной план при невыполнимости** (см. §3.3, РЕШЕНО §7) — выноска-leader сейчас;
   двигать узлы — на будущее. Но ДО fallback: роутер при выборе среди почти равных
   маршрутов предпочитает тот, что оставляет ДЛИННЕЕ уникальное плечо под плашку
   («двигаем маршрут, а не узлы» — дешёвая версия идеи архитектора, режет частоту fallback).
5. **Совместимость:** ручной `label_t` уважаем (юзер двигал плашку — не перетираем
   авто-размещением; авто только для нетронутых, как с detours/waypoints).

## 6. Рекомендованная декомпозиция на фазы (аналитика → изолированные модули → интеграция)

По образцу Ф4: каждая фаза — изолированный чистый модуль + юнит-тесты, чекпойнт между.

- **A0. Полигон и метрики.** Зафиксировать тест-проект(ы) с симптомами (наложенные
  плашки, плашка под узлом, пучок совпадающих стрелок) и метрики «хорошо» (число
  наложений плашек, число плашек под узлами, число пересечений стрелок). Замер ДО.
- **A1. Измерение габаритов плашек** (предусловие R2) — функция оценки/мера размера.
- **A2. Routing graph + ортогональный A\*** (R1) — чистый модуль, тесты на геометрии.
- **A3. Глобальная минимизация пересечений** (R3) — порядок + штраф crossing + nudging
  наложенных плеч (VPSC). Интеграция роутера вместо/над detours.
- **A4. Детект совпадающих плеч** (основа R4) — коллинеарные наложения, «уникальная»
  часть каждого ребра.
- **A5. Допустимые интервалы плашек** (R2-под-узлами + R4) — вычитание зон.
- **A6. Размещение плашек без наложений** (R2-друг-на-друга) — VPSC/greedy + запасной план.
- **A7. Интеграция в LevelGraph + уважение ручных правок + персист/стабильность.**

Маршрутизация (A2–A4) и плашки (A5–A6) разрабатываются параллельно после A1; сходятся
на A7.

## 7. Решения архитектора (ПРИНЯТЫ 2026-06-29)

1. **Build vs buy роутера → R-1 (своё на TS).** Единый пост-раскладочный ортогональный
   роутер: Hanan-сетка + A\* со штрафами + nudging через `vpsc.ts`. (libavoid-js — план Б.)
2. **R4 → (4a) оставить слитыми + запрет плашек на общем плече.** Совпадающие плечи
   рисуются одной линией; плашка только на однозначно своей части.
3. **Запасной план при R2∩R4 невыполнимости → выноска-leader (a) СЕЙЧАС.** Единственный
   вариант, строго держащий R2 и R4 и всегда показывающий подпись. ДО fallback роутер
   предпочитает маршрут с более длинным уникальным плечом (см. §5.4).
   **На будущее (записано, идея архитектора):** двигать УЗЛЫ, чтобы уникальное плечо
   стало длиннее текста — визуально оптимальнее (нет выносок/усечений), но снова свяжет
   позиции узлов с раскладкой стрелок (риск — тот же класс багов, что лечил own-on-first-
   render: оскилляции, конфликт с сохранёнными позициями, рябь). Вернуться, если leader
   не зайдёт.
4. **Scope → только level-схема.** Контекст-схема (полки/обходы) не трогается.
5. **Габариты плашек → быстрая моноширинная оценка** (обобщить `ctxLabelWidth` на level);
   точный measure-pass добавим, только если оценки не хватит.

NB. «Хэндлы гостевых стрелок при раскрытии рамки» (бэклог) — частный случай этого
эпика: после общего роутера точка входа/выхода (хэндл) должна выбираться им же.
