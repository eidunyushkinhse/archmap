# ArchMap MCP — сервер для ИИ-агента пользователя

Даёт агенту (Claude Code, Cursor, VS Code, Qwen Code и любому MCP-клиенту) прямой доступ
к ArchMap: читать архитектуру, строить её по исходникам, поддерживать в актуальном
состоянии и дописывать документацию — без копипасты YAML руками.

Подключиться можно двумя способами:

- **Удалённо — рекомендуемый.** ArchMap сам служит MCP-сервером по адресу
  `https://archmap.example.com/mcp` (адрес интерфейса плюс `/mcp`). Агенту нужны только
  адрес и личный токен из меню профиля; ставить ничего не нужно. 32 инструмента — всё,
  кроме работы с файлами на диске. См. «Удалённое подключение».
- **Локально — для файлов.** Этот пакет, который клиент запускает по stdio на машине
  агента. Нужен, чтобы выгрузить проект архивом на диск, ввезти или догрузить архив с
  диска. 35 инструментов. См. «Локальное подключение».

До этого сервера работал паттерн BYOA: агент выдавал YAML/`.mmd`, человек
переносил их в интерфейс. MCP убирает перенос, оставляя те же правила формата
(промпты) и ту же двухшаговость (превью → применение). С версии 0.2.0 (эпик
«доработка MCP», 2026-09-04) агенту доступен весь цикл: разведка → схемы логики и три
семьи табличных фактов → привязка процессов → архив, и те же 15 классов алертов, что у человека.
С версии 0.3.0 (эпик «якорь как первоклассная сущность»; с 2026-10-17 якорь зовётся источником) агент видит и задаёт
ИСТОЧНИК объекта, а превью импорта, догрузки и синка называют, ЧЕМ объекты признаны
одним и тем же. С версии 0.4.0 (2026-09-06) параметр multi_product у
`archmap_import_prompt` снят: федеративного варианта промпта нет — федерация продуктов
собирается одиночными прогонами в каждом репозитории и мерджем их результатов.
С версии 0.5.0 (2026-09-29) агент ищет по всему знанию проекта (`archmap_search`) и
открывает одну схему логики по id (`archmap_doc`): разбор инцидента начинается со
строки лога, а не с перебора карточек объектов подряд.
С версии 0.6.0 (2026-10-17) ArchMap отвечает агенту сам, по адресу `…/mcp` с личным
токеном, а локальный вариант принимает тот же токен (`ARCHMAP_TOKEN`) вместо пароля.
Отказы инструментов в обоих способах помечены `isError`: клиент и агент видят, что
вызов не удался, а не принимают отказ за результат; текст причины прежний.
С версии 0.7.0 (2026-10-22) агент читает историю версий документации объекта и
проекта (`archmap_versions`, `archmap_version_diff`, `archmap_version_doc`) и по явной
просьбе человека фиксирует версию (`archmap_version_create`); отката в MCP нет.

## Что умеет

35 инструментов по задачам, а не по эндпоинтам (удалённо — 32, см. «Что доступно
удалённо»). Каждый требует проект явно
(`project` — имя или uuid; по подстроке имя тоже находится, но неоднозначность —
ошибка со списком).

**Чтение** — понять систему

| Инструмент | Зачем |
|---|---|
| `archmap_projects` | список доступных учётке проектов и роль в каждом: `[владелец]`, `[редактор]` (можно править), `[чтение]` (только смотреть); с него начинают |
| `archmap_schema` | дерево объектов и связи; `node_id` — только поддерево |
| `archmap_search` | поиск по ВСЕМУ знанию проекта: объекты, схемы логики построчно, OpenAPI-спеки, структура БД, каналы и поля, параметры конфигурации, процессы и шаги. Строку лога вставляют целиком — переменные части не мешают, решают редкие слова. Выдача по объектам, у находки адрес (путь, схема, номер строки) и id: `doc_id` → `archmap_doc`, `node_id` → `archmap_node`, `process_id` → `archmap_processes`; `limit` (до 100), `kinds` — только эти виды |
| `archmap_node` | карточка объекта: путь, мета, ИСТОЧНИК («код github.com/org/repo, путь src/api» / «имя зависимости postgres» / «нет — опознаётся по имени»), статус страницы («в работе» / «согласовано»; у контейнера — из детей со счётчиком), связи, схемы логики (вид, операция, «не описана» у заглушек, «в N процессах»), участие самого объекта в процессах, а по форме объекта — структура БД, каналы брокера с полями или параметры конфигурации; `include_docs`/`include_spec` — тексты целиком |
| `archmap_doc` | одна схема логики целиком по `doc_id`: путь объекта, имя, вид, эндпоинт, «не описана» у заглушки, в каких процессах документирует шаги, полный текст — дешевле `archmap_node` с `include_docs`, когда нужна одна схема |
| `archmap_versions` | версии документации объекта (у контейнера — с поддеревом), новые сверху: номер, комментарий, дата, автор, автоверсии отката словами, «изменено: …» относительно предыдущей; первой строкой — есть ли незафиксированные изменения. Без `node_id` — версии всего проекта |
| `archmap_version_diff` | что изменилось в версии: элементы (свойства, связи, схемы логики, OpenAPI, таблицы, каналы, конфигурация, статус страницы, процессы) со статусом и `item`. `version` — номер (без него — последняя), `base` — `prev` (с предыдущей, по умолчанию), `live` (от версии до текущего состояния) или номер; с `item` — одна дельта текстом (построчно или таблицей), `with_sides` — ещё «было» и «стало» |
| `archmap_version_doc` | текст на версии: схема логики (`doc_id`), OpenAPI-спека (`spec_node_id`) или процесс в mermaid (`process_id`) — ровно один; id — часть `item` после двоеточия |
| `archmap_alerts` | незавершённость схемы — те же 15 классов и те же слова, что в панели интерфейса |
| `archmap_processes` | бизнес-процессы: список (область, число шагов) или один процесс — участники, шаги с привязкой к схеме логики, `id` и `version` шага, фрагменты |
| `archmap_step_docs` | каталог схем логики, которыми можно задокументировать шаг (считает сервер: оба участника и их потомки, схемы исполнителя первыми) |
| `archmap_export` | семантический срез схемы в YAML ArchMap (без раскладки, доков и фактов) — то, что подают на импорт и синк |
| `archmap_export_archive` | ПОЛНЫЙ архив знания проекта zip-файлом на диск (`out_path`): C4, схемы логики, спеки, структура БД, каналы, конфигурация, процессы; сводка по манифесту |

**Правила формата** — те же промпты, что выдаёт интерфейс. Вызывать ДО того,
как строить YAML, `.mmd` или пакет фактов: они задают формат и запреты.

| Инструмент | Зачем |
|---|---|
| `archmap_import_prompt` | как построить YAML архитектуры по репозиторию (промпт один и универсальный: федерация продуктов — те же одиночные прогоны в каждом репозитории и мердж) |
| `archmap_docs_prompt` | как оформить `.mmd` схемы логики и OpenAPI-спеки (`include`: logic / api / both, `target` — описать одну точку входа: имя заглушки разведки или «METHOD /путь») |
| `archmap_recon_prompt` | как составить ПЕРЕЧЕНЬ точек входа объекта (операции и воркеры) — нулевой шаг документирования монолита |
| `archmap_facts_prompt` | как оформить табличные факты семьи `family`: `tables` (структура БД у формы database), `channels` (каналы брокера у формы broker), `config` (параметры конфигурации у формы service; только дефолт из кода, значений сред не бывает) |

У всех промптов есть `variant`: `builder` — строительный (по умолчанию),
`orchestrated` — обёртка «построил → аудит скептика → починил» (агенту нужны
субагенты), `skeptic` — только промпт аудита готового пакета.

**Запись пачкой** — всегда парой «превью → применение». Превью ничего не пишет.

| Инструмент | Зачем |
|---|---|
| `archmap_import_preview` / `archmap_import_apply` | НОВЫЙ проект из N входов вперемешку: YAML текстом (`files`) и zip-архивы с диска (`paths`); споры содержимого между входами печатаются в превью с id и кандидатами, выбор — `resolutions` («id спора → `cand:<i>`», для схем логики ещё `all`); `name` обязателен, кроме единственного входа-архива — тогда имя из манифеста. Превью называет основание каждой склейки и сколько объектов приедет без источника |
| `archmap_import_into_preview` / `archmap_import_into_apply` | ДОГРУЗКА архивов (только `.zip` путями) к существующему проекту диффом: аддитивно по умолчанию, перезапись только явным выбором; превью печатает найденное в проекте с основанием, источника новых объектов и `base_graph_rev`/`base_meta_rev`, применение их требует (параллельная правка → 409, перечитать превью) |
| `archmap_sync_preview` / `archmap_sync_apply` | обновить схему живого проекта из свежего прогона кода (YAML); не удаляет объекты и не трогает раскладку. План называет ОСНОВАНИЕ каждого решения: у обновляемых — «по коду» / «по имени зависимости» / «по имени внутри «X»», у создаваемых — какой источник они получат |
| `archmap_docs_preview` / `archmap_docs_apply` | залить схемы логики и спеки |
| `archmap_recon_preview` / `archmap_recon_apply` | положить перечень точек входа заглушками схем логики (только создаёт; повторный перечень даёт дифф, не дубли) |
| `archmap_facts_preview` / `archmap_facts_apply` | залить табличные факты семьи `family` (tables / channels / config); `node_id` — объект по умолчанию, если в файле нет `# archmap-node` |
| `archmap_bind_step` | привязать шаг процесса к схеме логики (`doc_id`; `null` — снять) под CAS по `base_version` шага |

**Точечные правки**: `archmap_create_node`, `archmap_update_node`,
`archmap_create_edge`, `archmap_update_edge`. У обоих инструментов объекта есть
аргумент `source` — источник (см. «Источник объекта» ниже); пустой объект `{}` в
`archmap_update_node` источник снимает. Аргумент `approval` у `archmap_update_node`
ставит статус страницы («в работе» / «согласовано») — только по просьбе человека и
только объекту без детей: у контейнера статус складывается из детей.
`archmap_version_create` фиксирует версию документации объекта (без `node_id` — всего
проекта) с комментарием — номером релиза или задачи. Только по явной просьбе человека,
потому что версия — его решение и агент её не придумывает.

### Чего сервер НЕ умеет — и почему

**Удалений нет ни одного.** Снос объекта уводит с собой поддерево, связи, схемы
логики и спеки — такое делают глазами, а не «на всякий случай» из разговора.
Чтобы пометить лишнее, агент ставит `status=deprecated`; физически удалит
человек кнопкой «Принять переход», увидев полный список того, что исчезнет.
Дозаливки фактов и разведка тоже ничего не удаляют: агент не сносит то, чего
не увидел.

**Отката к версии нет.** Откат к версии — только в интерфейсе, потому что он удаляет
объекты, появившиеся после версии. Агент читает версии и дельты и фиксирует новую версию по
просьбе человека, но вернуть документацию к прошлой версии может только человек.

**Нет «текущего проекта».** Каждый инструмент требует проект явно — именем или
uuid. Скрытое состояние на сервере сделало бы результат зависимым от порядка
вызовов, а агент этот порядок не контролирует.

**Имя проекта не угадывается.** Если под строку подходит несколько проектов,
сервер отвечает ошибкой со списком, а не берёт первый похожий: правки, уехавшие
не в тот проект, обнаруживает человек, и поздно.

**Файлы — с диска агента, а не телом вызова, и только локально.** Локальный сервер
работает по stdio на той же машине, что агент, поэтому архивы передаются путями, а не
base64 в контексте модели. Удалённо «диск» был бы диском сервера ArchMap, поэтому там
путей нет совсем: YAML — только текстом, архивы — в интерфейсе или локальным вариантом.

## Удалённое подключение

### Токен

Меню профиля (кружок с инициалом в шапке) → «Токены для MCP»: имя, срок (30 дней,
90 дней — по умолчанию, год или бессрочно), «Только чтение» → «Выпустить токен». Токен
показывается ОДИН раз — вместе с готовыми строками подключения: «CLI» — команда
`mcp add` (вместо `<cli>` — `claude`, `qwen` и т. п.), «Desktop» — блок для mcp.json;
дальше в списке видно только его начало (`archmap_Ab3dEf…`), когда им пользовались и до
какого числа он действует. Отозвать — там же. Выпускает и отзывает токены только человек
в интерфейсе: токеном этого сделать нельзя.

Агент действует от имени владельца токена и видит ровно то, что видит он. Чего токен не
может, даже если владелец может:

- удалять — ни объекты, ни что-либо ещё (метод DELETE закрыт целиком);
- «Принять переход» — физическое удаление по списку;
- управлять проектом: карточка и видимость, архив, участники, передача владения;
- администрирование, смена пароля, управление токенами.

Блокировка учётки гасит её токены сразу, смена роли действует сразу: права решает учётка
на каждом запросе, сам токен прав не несёт.

**Только чтение.** У «Пользователя» (роль viewer) любой токен — только для чтения, даже
если в проекте он редактор: в окне галочка включена и закрыта. Агент с таким токеном видит 16 инструментов: чтение (и версии документации), поиск, экспорт
YAML и промпты. Пишущие отвергаются с объяснением, а бэкенд отвечает таким токеном 403 на
всё, кроме чтения.

### Строки подключения

Адрес — `https://archmap.example.com/mcp`, заголовок — `Authorization: Bearer <токен>`.
Вне localhost — только HTTPS: токен в заголовке — тот же пароль. **Не кладите токен в
файлы, которые попадают в git.**

В окне выпуска строки общие: вкладка «CLI» — команда `mcp add` с заглушкой `<cli>` вместо
имени программы (такой синтаксис у Claude Code, Qwen Code, Gemini CLI, Copilot CLI),
вкладка «Desktop» — блок `mcpServers` с `url` и `headers` для mcp.json приложения. Ниже —
те же строки для известных клиентов и их особые форматы.

**Claude Code** — команда из вкладки «CLI» с `claude` вместо `<cli>`:

```bash
claude mcp add --transport http archmap https://archmap.example.com/mcp \
  --header "Authorization: Bearer archmap_…"
```

Без `--scope` запись уходит в личный конфиг (`~/.claude.json`), а не в репозиторий. Общий
для команды `.mcp.json` в корне репозитория — с подстановкой переменной окружения: каждый
держит свой токен в `ARCHMAP_TOKEN`.

```json
{
  "mcpServers": {
    "archmap": {
      "type": "http",
      "url": "https://archmap.example.com/mcp",
      "headers": { "Authorization": "Bearer ${ARCHMAP_TOKEN}" }
    }
  }
}
```

**Cursor** — `~/.cursor/mcp.json` (блок из вкладки «Desktop») или `.cursor/mcp.json`
проекта; в файле проекта — переменная `${env:ARCHMAP_TOKEN}` вместо токена:

```json
{
  "mcpServers": {
    "archmap": {
      "url": "https://archmap.example.com/mcp",
      "headers": { "Authorization": "Bearer ${env:ARCHMAP_TOKEN}" }
    }
  }
}
```

**VS Code** — `.vscode/mcp.json`; ключ верхнего уровня `servers`, токен VS Code спросит
при первом запуске и сохранит в своём защищённом хранилище:

```json
{
  "inputs": [
    { "type": "promptString", "id": "archmap-token", "description": "Токен ArchMap", "password": true }
  ],
  "servers": {
    "archmap": {
      "type": "http",
      "url": "https://archmap.example.com/mcp",
      "headers": { "Authorization": "Bearer ${input:archmap-token}" }
    }
  }
}
```

**Qwen Code** — команда (пишет в `~/.qwen/settings.json`):

```bash
qwen mcp add --transport http archmap https://archmap.example.com/mcp \
  --header "Authorization: Bearer archmap_…"
```

В `settings.json` адрес Streamable HTTP задаётся ключом `httpUrl` (ключ `url` у Qwen Code
— для SSE, им ArchMap не отвечает).

Claude Desktop и коннекторы claude.ai подключают удалённые серверы только через OAuth —
его ArchMap пока не умеет; Claude Desktop работает с локальным вариантом.

Ключи конфигов сверены с документацией клиентов 2026-10-17; если клиент не подключается,
сверьте с его документацией формат «удалённый сервер с заголовком».

### Что доступно удалённо

32 инструмента из 35. Нет трёх, что работают только с файлами:

- `archmap_export_archive` — архив пишется на диск; в интерфейсе для этого есть «Экспорт
  проекта (zip)»;
- `archmap_import_into_preview` / `archmap_import_into_apply` — догрузка принимает только
  архивы путями.

`archmap_import_preview` / `archmap_import_apply` удалённо принимают только YAML текстом
(`files`), без `paths`. Остальные инструменты — как в локальном варианте, теми же словами.

### HTTPS с внутренним центром сертификации

Сертификат ArchMap теперь проверяет сам клиент. Клиенты на Node.js (Claude Code, Qwen
Code) берут дополнительные корневые сертификаты из `NODE_EXTRA_CA_CERTS` — файл PEM с вашим
центром, переменная окружения процесса клиента. Редакторы на основе VS Code (VS Code,
Cursor) обычно доверяют системному хранилищу: достаточно установить центр в систему.
Прокси — по правилам самого клиента; внутренний адрес ArchMap обычно вносят в `NO_PROXY`.

### Если не подключается

- **401 «Нужен личный токен…»** — нет заголовка или в нём не токен ArchMap (`archmap_…`).
- **401 «Токен недействителен…»** — токен отозван, истёк или скопирован с ошибкой:
  выпустите новый.
- **404 «На демо-стенде подключение агента недоступно»** — демо-стенд агентов не
  подключает.
- **405 или страница интерфейса** на сервере, обновлённом со старой версии, — в nginx нет
  `location = /mcp`: администратору — `DEPLOY.md`, «Обновление».
- **429** — предел запросов по токену (по умолчанию 300 в минуту) или неудачных проверок
  токена с адреса: подождите минуту.

## Локальное подключение

### Установка

```bash
cd mcp
python3 -m venv venv
./venv/bin/pip install -r requirements.txt
# для разработки сервера (тесты и линтеры гейта, пины как в CI):
./venv/bin/pip install -r requirements-dev.txt
```

### Настройка клиента

Токен или учётка — в файле `mcp/.env` рядом с сервером (он в `.gitignore`):

```bash
cp mcp/.env.example mcp/.env   # и впишите токен — или логин и пароль
```

**Не кладите токен или пароль в конфиг MCP-клиента.** У Claude Code это `.mcp.json` в корне
проекта, и он трекается git: пароль уехал бы в репозиторий. В конфиг клиента — только
запуск сервера (для Claude Code — `.mcp.json`, для Claude Desktop —
`claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "archmap": {
      "command": "/абсолютный/путь/mcp/venv/bin/python",
      "args": ["-m", "archmap_mcp.server"],
      "env": {
        "PYTHONPATH": "/абсолютный/путь/mcp"
      }
    }
  }
}
```

Переменные (в `mcp/.env`; настоящее окружение процесса их переопределяет):

- `ARCHMAP_URL` — адрес бэкенда, по умолчанию `http://localhost:8000`;
- `ARCHMAP_TOKEN` — личный токен из меню профиля → «Токены для MCP»; **рекомендуемый
  способ**: пароль в файле не нужен, токен отзывается, а с токеном «только чтение» агент
  ничего не поменяет. Запреты те же, что удалённо (см. «Токен»);
- `ARCHMAP_USERNAME`, `ARCHMAP_PASSWORD` — учётка ArchMap: нужны, если токена нет;
- `ARCHMAP_EXPORT_DIR` — необязательно: каталог, вне которого `archmap_export_archive`
  архив не пишет (относительный `out_path` считается от него). Без неё архив пишется
  куда скажет агент, но только в файл `.zip`, не через символическую ссылку и без
  перезаписи без `overwrite=true`.

**HTTPS с внутренним центром сертификации.** Сертификат ArchMap сервер проверяет по
корневым сертификатам пакета certifi, а не по системному хранилищу, поэтому сертификат,
выпущенный корпоративным центром, отвергнет (`CERTIFICATE_VERIFY_FAILED`). Укажите
файл корневых сертификатов (PEM, с вашим центром) переменной `SSL_CERT_FILE` или каталог —
`SSL_CERT_DIR`. Это переменные окружения процесса: их ставят в блок `env` конфига клиента
рядом с `PYTHONPATH`, из `mcp/.env` они не читаются. Обычно подходит системный набор, если
центр в него установлен: `/etc/ssl/certs/ca-certificates.crt` (Debian, Ubuntu, Astra Linux)
или `/etc/pki/tls/certs/ca-bundle.crt` (RHEL и родственные). Прокси сервер берёт из
`HTTPS_PROXY` и `NO_PROXY` того же окружения — внутренний адрес ArchMap обычно вносят в
`NO_PROXY`.

Без `ARCHMAP_TOKEN` сервер входит логином и паролем сам и держит сессию в памяти
процесса, перелогиниваясь при истечении. Отказ в токене (отозван, истёк) он называет
прямо и советует выпустить новый.

Агент видит ровно то, что видит его учётка: проекты, где она участник, и
проекты, видимые всем. Править можно там, где роль учётки в проекте владелец
или редактор; с ролью «чтение» запись получит внятный отказ с причиной.
Создавать новые проекты (импорт в новый проект) может только учётка с общей
ролью architect.

## Типовые сценарии

**Построить схему по коду.** `archmap_import_prompt` → агент читает исходники и
строит YAML по полученным правилам → `archmap_import_preview` (разбор, слияние
нескольких репозиториев, замечания по входам) → `archmap_import_apply`.

**Поддерживать схему актуальной.** Тот же промпт по свежему коду →
`archmap_sync_preview` (что создастся, что обновится, что пропало из кода) →
`archmap_sync_apply`. Синк не удаляет объекты и не трогает раскладку.

**Задокументировать монолит.** `archmap_recon_prompt` для объекта → агент
приносит перечень точек входа → `archmap_recon_preview` → `archmap_recon_apply`
(заглушки) → затем по каждой точке `archmap_docs_prompt` с `target` (имя заглушки) →
`archmap_docs_preview` → `archmap_docs_apply`. Прогресс виден в `archmap_node`
(«описано N из M») и в `archmap_alerts` («объекты с неописанными схемами»).

**Описать данные, события и настройки.** `archmap_facts_prompt` с `family`
(tables у базы, channels у брокера, config у сервиса) → пакет →
`archmap_facts_preview` → `archmap_facts_apply`. Пометки «читает:/пишет:»,
«публикует:/потребляет:», «зависит от:» в схемах логики после этого резолвятся,
а нерезолвленные видны в `archmap_alerts`.

**Задокументировать сценарий.** `archmap_processes` с `process_id` (у шагов `id`
и `version`) → `archmap_step_docs` для шага → `archmap_bind_step`. Шаги без
схемы видны в `archmap_alerts`.

**Перенести или сохранить проект.** `archmap_export_archive` → zip на диске;
`archmap_import_apply` с `paths=[zip]` восстанавливает копию (имя из манифеста);
`archmap_import_into_preview`/`apply` доливает архив к живому проекту, не
затирая его правок без явного выбора.

**Разбор инцидента: строка лога → поиск → схема → ветка отказа → процесс.**
Строку из лога или текст ошибки — целиком, как есть — в `archmap_search`:
переменные части (`/dev/ttyUSB0`, id, пути) поиску не мешают, а редкие слова
(`SMSDevices`) поднимают нужную строку наверх. Первая находка обычно — строка
схемы логики с веткой отказа («Ошибка: SMSDevices not configured for
<устройство>»), с номером строки и `doc_id`. Дальше `archmap_doc(doc_id)` — схема
целиком: что проверяется перед этой веткой, от какого параметра зависит развилка
(«зависит от: SMSDevices»), что происходит после ошибки (повтор или сразу сбой).
Если схема задокументировала шаги процессов, `archmap_doc` их назовёт —
`archmap_processes(process_id)` покажет, где в сценарии случилась ошибка. Параметр
из развилки находится тем же поиском (`kinds: ["param"]`) или в `archmap_node`
объекта. Перебирать карточки подряд с `include_docs` не нужно.

**Что изменилось в новой версии.** Вопрос «как изменился процесс создания
пользователей в новой версии сервиса X относительно предыдущей?» —
`archmap_versions` для сервиса (номера и комментарии версий, что менялось в каждой) →
`archmap_version_diff` с номером версии (по умолчанию — последняя против предыдущей) →
у элемента процесса `item=process:<id>` → `archmap_version_diff` с этим `item`: шаги
с пометками «+ − ~ ↕» и «было → стало» в ячейках. Если нужен текст целиком, его даёт
`archmap_version_doc` (`process_id`, а для схемы логики — `doc_id`) на каждой из двух
версий.

**Ответить на вопрос по архитектуре.** `archmap_schema` для общей картины,
`archmap_search` — найти, где записано нужное знание, `archmap_node` по
конкретному объекту (там же факты по форме), `archmap_processes` для сценариев.

**Источник объекта.** Источник — то, чем ArchMap опознаёт объект при обновлениях из
кода: у объекта со своим кодом это репозиторий и путь в нём (`source: {repo:
"github.com/org/repo", path: "src/api"}`; можно вставить адрес клона целиком —
сервер приведёт его к одному виду), у зависимости без кода в продукте (база,
брокер, соседний продукт) — имя, под которым продукт сам называет её в манифестах
и настройках (`source: {host: "postgres"}`; без порта и схемы). Адреса сред
(localhost, 127.0.0.1, конкретные серверы) источником не бывают — сервер откажет с
объяснением. Источник описывает продукт, а не контур развёртывания, и на схему со
связями не влияет: он решает только, узнают ли объект при следующем прогоне.
Объект без источника опознаётся по имени внутри своего контейнера — переименуют, и
следующий прогон сделает из него дубль.

Отсюда сценарий «ручной объект против агентского»: объект, созданный руками,
живёт без источника, а его агентский двойник — с источником, и ведут они себя при
обновлениях по-разному. Привяжите ручной объект к коду — `archmap_update_node`
с `source` (или сразу `archmap_create_node` с `source`) — и синк узнает его как
свой: `archmap_sync_preview` покажет строку «— по коду» вместо «— по имени».

**Найти незавершённость.** `archmap_alerts` — те же 15 классов замечаний, что
видит человек в интерфейсе.

## Разработка

```bash
./venv/bin/ruff check .
./venv/bin/mypy
./venv/bin/python -m pytest -q
```

Тесты идут поверх подменённого транспорта httpx — живой ArchMap им не нужен:
они про клиент (логин, токен, скоуп, перевод отказов), про то, во что инструменты
сворачивают ответ, и про удалённый набор (`remote.py`, `tools.call_remote`: файловых
путей нет, «только чтение» шлёт только GET). Контракты самих эндпоинтов держит pytest
бэкенда, `/mcp` в процессе бэкенда — `backend/tests/test_mcp_http.py`.

Удалённый режим — тот же пакет: бэкенд импортирует `archmap_mcp` (в поставках пакет
лежит рядом с `app/`, в репозитории — `mcp/` через запасной путь импорта в
`app/mcp_http.py`), а инструменты ходят в HTTP API в процессе, с токеном вызывающего.
